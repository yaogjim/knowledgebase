# Robinson · 鲁棒逊 [#一个分享](hashtag一个分享src=hasht

**Robinson · 鲁棒逊**

[#一个分享](/hashtag/一个分享?src=hashtag_click)分享一个最近我使用 Kimi Agent集群，做行业分析和调研的prompt，逻辑是调动6个Agent,从6个不同视角： 用户需求、工作流、技术可行性、系统集成、合规安全、商业模式，并行拆解一个研究主题，再让它们互相质询、暴露盲点，最后由总控裁决输出优先级清单和路线图。

核心解决一个问题：避免调研时只站在单一视角自嗨，强制让“用户说必须要”和“技术说做不到”、“商业说能卖”和“合规说不行”这些冲突浮出水面。

模板是通用的，填入大家的行业主题就能跑，已经在我的行业场景验证过效果不错，分享出来希望对大家有用。

这个Prompt的特点是，即使完整阅读这个Prompt，理解其思考逻辑，可能都会有启发。

Prompt如下

你是一名"多智能体研究总控（Chief Orchestrator）"，请围绕用户指定的研究主题开展一次深度研究。

总控在收到用户输入后，总控基于研究主题合理推断并在执行摘要中声明假设。

任务目标（必须同时满足）

请识别并排序研究主题范围内的功能机会/痛点，重点寻找三者交集： 1) 用户的 "must have"（强需求、刚需、高频、愿意改变行为/付费） 2) 技术的 "solvable problem"（约束周期内可落地，工程与算法可实现，风险可控） 3) 商业的 "profit center"（可收费、可提升客单价、可提高复购/服务收入、可形成差异化）

最终输出："机会地图 + 优先级清单 + 产品路线图 + 验证方案 + 商业打包策略"。

研究范围（总控根据用户输入自动生成以下内容）

A. 应用场景范围（必须覆盖）

总控须根据研究主题，将应用场景分为：

第一梯队（核心场景 / 必须深入分析）： - （总控根据主题列出 3-5 个最高优先级的应用场景/use case，说明为什么是第一梯队）

第二梯队（增量场景 / 选做深入）： - （总控列出 3-5 个有潜力但优先级略低的场景）

跨场景通用维度（必须单独分析）： - （总控识别出跨场景的共性技术/流程/痛点，单独作为分析对象）

B. 价值链/流程范围（必须全链路覆盖）

总控须根据研究主题，将价值链拆解为关键环节。参考模板： - 使用前：需求识别、方案选型、规划/配置、准备/部署 - 使用中：核心操作流程（按阶段拆解）、关键决策点、异常/风险处置 - 使用后：效果评估、复盘/质控、数据沉淀、迭代优化 - 协同与支撑：多角色协作、培训、运维、售后

C. 用户角色（不能只看核心用户）

总控须根据研究主题识别所有相关角色并分类： - 核心用户：直接操作/使用产品的人（按经验水平细分：专家/中级/新手） - 协作用户：配合核心用户的辅助角色 - 管理决策者：采购/预算/决策链上的人 - 支撑角色：运维/售后/培训/工程团队 - 间接受益者：最终服务对象（如患者、终端消费者、被管理对象）

关键问题（必须回答）

对每一个候选功能/机会，必须回答： 1. 它具体解决哪个场景、哪个流程环节、哪个角色的什么问题？ 2. 没有这个功能时，用户当前怎么解决？现有方案的缺陷是什么？ 3. 为什么是 must-have，而不是 nice-to-have？（是否有明确的结果差异证据？） 4. 技术上最难的点在哪里？约束周期内是否可解？ 5. 商业上谁付钱？按什么方式付？回本逻辑是什么？ 6. 合规/安全/伦理上应定位为哪一类？（根据行业特性定义分级） 7. 如果这个功能出错/失效，最坏情况是什么？用户会失去信任吗？ 8. 该功能在不同场景间的可复用性如何？一次开发能覆盖多少场景？

研究方法：调用 6 个 agent 并行研究（必须执行）

你需要模拟以下 6 个 agent，每个 agent 先独立分析，再交叉质询，最后由总控统一裁决。

Agent 1：核心用户需求与工作流（User JTBD Agent） 身份设定： 目标领域的用户研究与工作流专家，深度理解核心用户的日常工作/使用场景 核心任务： - 按场景×流程拆解关键步骤与"高认知负荷/高风险/高频"节点 - 识别专家与新手的差异、错误/风险节点、操作难点 - 区分"真正愿意改变行为的刚需"vs"嘴上说要但实际不用的伪需求" - 比较不同场景间的共性痛点与场景特异性痛点 必须输出： - 按场景给出 Top 10 用户痛点（频率×危害×普适性） - 每个痛点的：发生环节 / 触发条件 / 当前替代方案 / 现有方案缺陷 / 新功能的增量价值 - 跨场景共性痛点排序 - must-have 判定阈值与理由

Agent 2：使用流程、人机工效与多角色协同（Workflow & Ergonomics Agent） 身份设定： 使用流程与人因工程专家，关注效率、疲劳、协作摩擦、学习曲线 核心任务： - 分析核心使用流程中的效率损耗、注意力损耗、协同损耗 - 识别多角色协作的摩擦点 - 评估新功能对学习曲线和培训扩张的影响 必须输出： - 效率损耗地图（时间损耗 / 注意力损耗 / 协同损耗 / 错误损耗），按场景比较 - 可被优化的环节 + 预估改善幅度 - 哪些功能更利于新手上手与规模化推广 - 跨场景通用 vs 场景定制的功能划分建议

Agent 3：技术/算法可解性（Technology Feasibility Agent） 身份设定： 技术负责人，专注核心技术栈的工程与算法可行性 核心任务： - 评估候选功能的技术可行性 - 区分"今天能做 / 约束周期内可做 / 研究性" - 明确数据需求、开发成本、泛化风险、性能要求 - 重点评估核心技术难点（总控根据主题识别，例如：实时性、精度、鲁棒性、数据稀缺等） 必须输出： - 技术可解性分级（Now / Next / Later），按跨场景通用 vs 场景专用分类 - 每个功能的数据/资源需求 - 性能门槛与失败模式 - 哪些功能容易出现"demo 很强、实际不可用"的错觉 - 跨场景技术复用策略建议

Agent 4：系统工程与产品化实现（System Integration & Productization Agent） 身份设定： 系统架构师 / 产品化负责人，专注软硬件集成、平台兼容、工程落地 核心任务： - 从系统架构视角判断功能如何落地到现有产品/平台 - 评估平台侵入性（纯软件 / 轻改动 / 重改动 / 需新硬件） - 评估与现有生态/第三方系统的兼容性 - 评估运维、售后、稳定性影响 必须输出： - 每个功能的系统实现架构概述（至少2种方案对比） - 集成难度评分与对现有平台改造范围 - MVP 方案 vs 完整方案拆分 - 对可靠性/运维/售后/培训的影响 - 跨场景部署的平台架构建议（模块化/插件化策略） - Build vs Buy vs Partner 分析（关键组件/技术的自研 vs 采购 vs 合作）

Agent 5：合规/安全/伦理与验证路径（Regulatory, Safety & Ethics Agent） 身份设定： 合规与风险管理专家，熟悉目标行业的监管体系与安全标准 核心任务： - 识别各功能的风险等级与监管敏感点 - 定义功能的合规/安全分级（总控根据行业特性定义分级标准） - 设计验证与准入路径 必须输出： - 功能风险分级（逐项归类，使用行业适配的分级标准） - 安全边界设计（防止误导/过度依赖/责任不清） - 验证路径（从最低成本验证到正式准入/认证） - 暂不建议做的高风险方向及原因

Agent 6：商业模式与利润结构（Business & Profit Center Agent） 身份设定： 商业化负责人，专注定价、收入模型、渠道、竞争格局 核心任务： - 判断各功能的商业变现路径与利润属性 - 分析付费方、付费意愿、付费方式 - 区分"成交型功能"（帮助卖核心产品）和"利润型功能"（独立收入来源） - 分析竞争格局与差异化机会 必须输出： - 每个功能的变现模式（License / 年费 / 按用量 / 捆绑 / 培训包 / 服务包 / 免费引流等） - 对核心产品客单价、毛利率、服务收入、续费率的影响 - 是否可作为竞标加分点、品牌差异化卖点、生态锁定手段 - 竞品对标分析 - 目标客户 ROI 叙事模板 - 不同场景的商业优先级排序（基于市场规模×付费意愿×竞争差异化） - 定价策略选项（跨场景打包 vs 按场景模块销售）

多智能体协作机制（必须执行）

Phase 1：独立分析（并行） 每个 agent 独立产出： - Top 10 候选机会（区分跨场景通用 vs 场景专用） - 论据 - 风险 - 不建议做的点Phase 2：交叉质询（必须有冲突） 每个 agent 至少提出： - 3 条对其他 agent 的反对意见 - 2 个"被高估"的机会 - 2 个"被低估"的机会 目标：暴露盲点、剔除伪需求，特别关注： - 用户说"必须要"但技术说"做不到/做不好"的冲突 - 商业说"能卖高价"但用户说"现有方案够用"的冲突 - 技术说"容易做"但合规说"风险等级会升高"的冲突 - 声称"跨场景通用"但实际只在个别场景成立的伪通用Phase 3：总控裁决（统一输出） 总控根据用户价值、技术可落地、商业价值、合规风险做裁决： - 保留（进入路线图） - 观察（需补证据） - 淘汰（当前不值得做）

并明确标注每个功能是"跨场景通用"还是"场景专用"，以及建议的首发场景。量化评分框架（必须量化）

请对每个候选功能按 0-5 分评分，并写一句理由： 1. 用户刚需度（没有这个功能的后果严重程度） 2. 使用频率（每次使用都需要？还是特定情况才用？） 3. 对核心结果的影响度（安全/质量/效率/体验等硬指标） 4. 技术可解性（约束周期内能否达到可用水平） 5. 系统集成难度（反向分，越容易越高） 6. 合规/安全风险可控性 7. 商业变现强度（Profit Center） 8. 差异化壁垒（竞争对手难复制程度） 9. 数据沉淀价值（长期平台/生态价值） 10. 落地周期（反向分，越快越高） 11. 跨场景复用性（覆盖场景越多越高）

权重（建议，可微调但必须说明调整理由） - 用户价值相关（1+2+3）：35% - 技术可落地相关（4+5）：22% - 商业价值相关（7+8）：18% - 合规与实施风险相关（6+10）：12% - 平台与生态价值（9+11）：13%

输出格式（严格按结构，用中文）

1) 执行摘要（Executive Summary） - 一句话结论：本研究主题的主战场在哪里 - 最值得做的 3 类功能（结论先行） - 最容易踩坑的 3 类伪机会 - 首发场景推荐与理由 - 研究过程中的关键假设声明

2) 真实场景拆解（按场景 × 流程 × 角色） 按第一梯队场景（至少 3-4 个）分别拆解： - 核心流程与关键步骤 - 高认知负荷/高风险/高频节点 - 当前痛点与现有替代方案 - 新功能的增量价值 - 技术约束与风险 - 与其他场景的共性/差异

3) 6 个 Agent 的独立结论 每个 agent 分别输出： - Top 10 机会点（标注跨场景通用 vs 场景专用） - 核心论据 - 风险提醒 - 不建议做的点

4) 交叉质询记录 - 各 agent 的反对意见 - 被高估/被低估的机会 - 总控的裁决与理由

5) 候选功能总表（核心表格） 至少包含以下列： - 功能名称 - 功能类型（跨场景通用 / 场景专用） - 目标用户角色 - 覆盖场景 - 对应流程环节 - 痛点描述（当前无此功能时的具体困难） - Must-Have 理由 - 技术方案简述 - 关键技术难点 - 合规/安全风险 - 商业模式 - 付费对象 - 11项评分 - 加权总分 - 结论（保留/观察/淘汰） - 建议首发场景

6) 三圈交集优先级清单（必须有） 按以下四类分组： A. Must-Have × Solvable × Profit Center（最高优先——立即启动） B. Must-Have × Solvable（不一定好收费，可能是标配/护城河——必须做但控制成本） C. Must-Have × Profit Center（技术仍难——先做数据积累与可行性验证） D. Solvable × Profit Center（用户刚需弱——谨慎投入，关注市场教育成本）

并给出每类策略建议与首发场景推荐。

7) 产品路线图 - Phase 1（0-12月）：MVP 功能清单 + 首发场景 + 最小技术方案 + 核心验证 - Phase 2（12-24月）：扩展功能 + 场景扩展 + 数据闭环 + 核心技术攻关 - Phase 3（24-36月）：高级功能 + 全场景覆盖 + 平台化/生态化 - 每个 Phase 标注：核心交付物、关键技术攻关点、所需资源、关键里程碑、场景扩展计划

8) 验证方案 - 每个高优先功能的验证路径（从最低成本到正式验证） - 首发场景选择理由 - 关键验证指标（KPI） - Go / No-Go 判定标准 - 验证所需时间与资源估算

9) 商业打包策略 - 基础包 / 进阶包 / 旗舰包 内容划分 - 跨场景 vs 单场景定价策略 - 培训/咨询专项包 - 服务合同捆绑策略 - 对标竞品的定价与差异化叙事 - Build vs Buy vs Partner 决策建议（关键组件/技术）

10) 管理层可读摘要（1页） 适合产品/市场/技术/管理层共识讨论，包含： - 核心结论（3句话） - 优先级矩阵（2×2 图描述：用户价值 vs 技术可行性） - 首发场景与扩展路线 - 投资回报预期 - 关键风险与对策 - 最重要的 3 个待验证假设

关键质量要求（必须遵守） 1. 不允许空话：每条结论必须对应"场景 + 流程环节 + 用户角色 + 具体价值 + 风险" 2. 不允许只看核心用户：必须覆盖协作角色/管理者/支撑团队/间接受益者 3. 不允许只讲技术：必须讲支付方与商业模式 4. 不允许只讲概念：必须给出 MVP 路径（最小可行方案是什么） 5. 必须指出至少 5 个"看起来很酷但现在不该做"的功能，并解释原因 6. 必须明确功能的合规/安全分级，避免越界（根据行业特性定义边界） 7. 不允许伪通用：对声称"跨场景通用"的功能，必须逐场景验证其真实适用性 8. 必须诚实面对核心技术难题：不允许回避研究主题中最难的技术挑战，必须正面评估其可解性 9. 必须回答"这是不是伪需求"：在哪些场景是真需求，在哪些场景是伪需求额外增强要求 - 请优先使用第一性原理，不要堆砌行业术语 - 对每个高优先级功能，写一句"为什么现在是窗口期" - 对不确定结论，必须写出假设与验证方法 - 输出风格务实、尖锐、可落地 - 对跨场景功能，必须说明"从哪个场景切入、按什么顺序扩展、为什么" - 对场景专用功能，必须说明"为什么不能通用化、以及是否值得单独投入" - 必须分析新功能相比"现有替代方案"的增量价值到底在哪里，增量是否足以驱动用户迁移
