# 第一部分：S 级深度阅读

## 1. DualPath 论文详解

### 论文信息

**标题**: DualPath: Breaking the Storage Bandwidth Bottleneck in Agentic LLM Inference
**作者**: 北京大学、清华大学、DeepSeek-AI
**arXiv**: 2602.21548v2 [cs.DC]
**发布日期**: 2026 年 2 月 26 日

### 摘要

LLM 推理的性能瓶颈正在从计算转向存储 I/O，尤其是在多轮 Agent 场景中。本文揭示了当前分层架构中的根本性问题，并提出了 DualPath 双路径加载机制，实现了 1.87 倍的吞吐量提升。

### 问题背景

#### 1.1 KV-Cache 的主导地位

在传统的 LLM 推理优化中，人们的注意力主要集中在计算效率上。然而，在多轮、Agent 式的推理场景中，KV-Cache 的存储 I/O 已经成为了性能的主要瓶颈。

**关键数据**:
- Agent 多轮推理中，KV-Cache 读取次数是模型权重的 40-64 倍
- 在 128K 上下文场景中，KV-Cache 的大小是模型权重的 4-8 倍
- 存储 NIC 带宽利用率在预填充引擎侧达到饱和，而解码引擎侧闲置

#### 1.2 存储带宽的不平衡

在主流的分层推理架构中，KV-Cache 存储在外部存储（如 NVMe SSD 或分布式存储）中，预填充引擎（Prefill Engine）负责从存储加载 KV-Cache 并执行预填充计算。这种架构存在一个根本性的不平衡：

```
┌─────────────────┐     ┌─────────────────┐
│  Prefill Engine │     │  Decode Engine  │
│  (NIC 饱和)      │     │  (NIC 闲置)      │
│  ↓↓↓↓↓↓↓↓↓↓     │     │                 │
│  从存储加载      │     │                 │
└────────┬────────┘     └─────────────────┘
         │
         ▼
┌─────────────────┐
│  External Store │
│  (NVMe/分布式)   │
└─────────────────┘
```

这种架构的问题在于：所有的 KV-Cache 加载流量都集中在预填充引擎的存储 NIC 上，而解码引擎的 NIC 却完全闲置。

### DualPath 的核心创新

#### 2.1 双路径加载机制

DualPath 的核心思想是引入第二条数据路径：KV-Cache 不仅可以从存储直接加载到预填充引擎，还可以先加载到解码引擎，然后通过计算网络（RDMA）传输到预填充引擎。

```
┌─────────────────┐     ┌─────────────────┐
│  Prefill Engine │←→→→│  Decode Engine  │
│  ↑↑↑↑↑↑↑↑↑↑     │ RDMA│  ↑↑↑↑↑↑↑↑↑↑     │
│  Path 1: 存储→预填充  │     │  Path 2: 存储→解码  │
└────────┬────────┘     └────────┬────────┘
         │                       │
         └───────────┬───────────┘
                     ▼
            ┌─────────────────┐
            │  External Store │
            └─────────────────┘
```

**Path 1（传统路径）**: 存储 → 预填充引擎
- 适用于：小批量、低延迟场景
- 优势：直接，无需额外传输
- 劣势：NIC 带宽饱和

**Path 2（创新路径）**: 存储 → 解码引擎 → （RDMA）→ 预填充引擎
- 适用于：大批量、高吞吐场景
- 优势：利用闲置 NIC 带宽，分散负载
- 劣势：增加一次 RDMA 传输

#### 2.2 为什么 RDMA 传输不会造成拥塞？

这是一个关键的设计洞察。DualPath 作者发现：

1. **计算网络与存储网络物理隔离**: 在典型的分层架构中，存储 NIC 和 RDMA NIC 是分开的物理接口，使用不同的网络基础设施。

2. **RDMA 流量模式更平滑**: 解码引擎到预填充引擎的传输可以调度和批处理，避免突发流量。

3. **无干扰原则**: DualPath 的 RDMA 流量与模型执行通信（如张量并行）使用不同的虚拟通道，互不干扰。

#### 2.3 全局调度器

DualPath 不仅是一个数据路径优化，还包含一个智能调度器，负责：

1. **动态路径选择**: 根据当前负载、KV-Cache 大小、网络状况选择最优路径
2. **负载均衡**: 在预填充引擎和解码引擎之间平衡负载
3. **批处理优化**: 将多个小请求合并为批量传输，提高 NIC 利用率

### 实现细节

#### 3.1 系统架构

```
┌─────────────────────────────────────────────────────┐
│                    Global Scheduler                  │
│  (动态路径选择、负载均衡、批处理优化)                  │
└─────────────────────────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│ Prefill Pool  │  │ Decode Pool   │  │   RDMA Net    │
│ (多引擎并行)   │  │ (多引擎并行)   │  │  (高带宽低延迟) │
└───────────────┘  └───────────────┘  └───────────────┘
```

#### 3.2 KV-Cache 管理

**缓存分层**:
- L1: GPU HBM（热 KV-Cache）
- L2: CPU RAM（温 KV-Cache）
- L3: NVMe/分布式存储（冷 KV-Cache）

**预取策略**:
- 基于注意力模式的预测性预取
- 基于历史访问模式的学习

#### 3.3 性能优化技术

1. **零拷贝传输**: 使用 GPUDirect RDMA，避免 CPU 中间拷贝
2. **流水线加载**: KV-Cache 加载与计算重叠
3. **压缩传输**: 对 KV-Cache 进行有损/无损压缩

#### 4.4 消融实验

**Path 1 vs Path 2 贡献**:
- 仅 Path 1: +35% 吞吐
- 仅 Path 2: +45% 吞吐

- 结论：两条路径互补， synergistic 效应显著

**调度器贡献**:
- 无调度器（随机选择）: +52%
- 有调度器（动态优化）: +87%
- 结论：智能调度贡献约 35% 的性能提升

### 对 Agent 系统设计的影响

#### 5.1 硬件选型启示

1. **解码引擎也需要存储 NIC**: 传统架构中解码引擎不需要直接访问存储，但 DualPath 要求每个解码引擎都有存储 NIC。

2. **RDMA 网络带宽很重要**: 建议至少 400Gbps RDMA 网络，以支持大规模 KV-Cache 传输。

3. **存储分层值得投资**: 高速 NVMe（如 PCIe 5.0）对性能提升显著。

#### 5.2 软件架构启示

1. **KV-Cache 感知调度**: 应用层应该感知 KV-Cache 的位置和状态，优化请求路由。

2. **前缀一致性的重要**: DualPath 的性能优势依赖于高 KV-Cache 命中率，这要求 Agent 系统设计时保持 prompt 前缀一致性。

3. **批处理窗口**: 适当延迟请求以形成更大的批处理，可以显著提高 NIC 利用率。

#### 5.3 与 AlexZ 原则的对应

DualPath 论文的技术发现与 AlexZ 提出的 Agent 设计原则高度一致：

- **C2（KV Cache 前缀一致性）**: DualPath 的性能依赖于高缓存命中率
- **P1（前缀一致性最高优先级）**: 违反 P1 会导致 DualPath 优势消失
- **P9（可观测性优先）**: DualPath 调度器依赖详细的指标监控

### 局限性与未来工作

#### 6.1 当前局限

1. **额外复杂度**: DualPath 增加了系统复杂度，需要维护两套数据路径
2. **小规模场景收益有限**: 在低并发场景下，DualPath 的优势不明显
3. **网络故障敏感**: RDMA 网络故障会影响 Path 2 的可用性

#### 6.2 未来方向

1. **自适应压缩**: 根据网络状况动态调整 KV-Cache 压缩率
2. **多级 RDMA**: 支持跨机房的 RDMA 传输
3. **与模型架构协同**: 与 MoE、稀疏注意力等模型特性协同优化

### 总结

DualPath 论文揭示了 Agent LLM 推理系统中的根本性瓶颈，并提出了创新的双路径解决方案。其核心贡献不仅是技术实现，更是对问题本质的深刻洞察：

1. **瓶颈转移**: 从计算到存储 I/O
2. **不平衡利用**: 预填充引擎 NIC 饱和 vs 解码引擎 NIC 闲置
3. **路径多样性**: 利用计算网络分散存储负载

这篇论文对于设计和优化 Agent 系统具有重要的实践指导意义。

#### 第一阶段：工作规范建立（30-60 分钟）

##### 2.1.1 为什么需要 AGENTS.md

在基础配置中，我们已经创建了：
- `SOUL.md`: 描述 AI 性格和行为风格
- `USER.md`: 描述用户背景和需求

但这些文件只解决了"AI 是谁"和"用户是谁"的问题，并没有告诉 AI"如何工作"。

**AGENTS.md 的作用**:
- 定义工作流程和行为准则
- 类似员工手册
- 告诉 AI 每次启动时应该做什么

**类比说明**:
| 文件 | 作用 | 类比 |
|------|------|------|
| SOUL.md | 性格和行为风格 | 个人性格档案 |
| USER.md | 用户背景和需求 | 服务对象信息 |
| IDENTITY.md | 身份定义 | 身份标识 |
| AGENTS.md | 工作流程 | 员工手册 |

##### 2.1.2 Session 启动配置

OpenClaw 每次启动新会话时都处于"初始状态"，需要通过读取文件来恢复记忆和上下文。

**推荐启动流程**:

```markdown
# Session 启动流程

每次会话开始时，按以下顺序自动执行：

1. 读取 `SOUL.md` - 加载性格和行为风格
2. 读取 `USER.md` - 了解用户背景和偏好
3. 读取 `memory/YYYY-MM-DD.md` - 加载今天和昨天的日志
4. 如果是主会话：额外读取 `MEMORY.md` - 加载核心记忆索引

以上操作无需询问，自动执行。
```

**配置说明**:

**步骤 1-2：基础信息**
- SOUL.md 和 USER.md 通常很小（<1KB）
- 每次都读取不会造成性能负担
- 确保 AI 知道角色定位

**步骤 3：近期日志**
- 读取今天和昨天的日志文件
- 让 AI 快速了解最近发生的事情
- 包含昨天的日志是因为凌晨时段今天的日志可能为空

**步骤 4：条件加载核心记忆**
- MEMORY.md 可能包含敏感信息
- 只在主会话中加载
- 群聊/子 Agent 会话不加载

##### 2.1.3 记忆管理规范

OpenClaw 采用分层记忆设计：

**记忆层级**:
```
┌─────────────────────────────────────┐
│ MEMORY.md (核心记忆索引)             │
│ - 长期偏好                           │
│ - 项目背景                           │
│ - 关键决策记录                       │
└─────────────────────────────────────┘
              ↑↓
┌─────────────────────────────────────┐
│ memory/YYYY-MM-DD.md (日志层)        │
│ - 对话日志                           │
│ - 事件记录                           │
│ - 临时状态                           │
└─────────────────────────────────────┘
```

**写入规范**:
- 短期记忆：按日期追加到日志文件
- 长期记忆：经过整理后沉淀到 MEMORY.md
- 敏感信息：加密或单独存储

#### 第二阶段：记忆系统优化（60-120 分钟）

##### 2.2.1 启用 memoryFlush

memoryFlush 的作用是防止信息丢失。在长时间运行的会话中，由于 token 限制，部分上下文可能被截断。memoryFlush 确保关键信息被持久化到日志文件。

**配置示例**:
```yaml
memory:
  flush:
    enabled: true
    interval: 10  # 每 10 轮对话 flush 一次
    critical_keywords:  # 触发立即 flush 的关键词
      - "重要"
      - "记住"
      - "TODO"
```

##### 2.2.2 优化日志格式

日志格式直接影响检索精度。推荐的日志格式：

```markdown
## {{timestamp}} [{{type}}] {{summary}}

**Context**: {{context}}
**Action**: {{action}}
**Result**: {{result}}
**Tags**: {{tags}}

---
```

**字段说明**:
- `timestamp`: ISO 8601 格式时间戳
- `type`: 事件类型（对话/工具调用/决策/错误）
- `summary`: 一句话摘要
- `context`: 上下文背景
- `action`: 执行的动作
- `result`: 结果/输出
- `tags`: 标签列表

##### 2.2.3 自动维护机制

**日志轮转**:
```yaml
maintenance:
  rotation:
    max_file_size: 1MB
    max_age_days: 30
    compress_old_files: true
```

**自动摘要**:
```yaml
maintenance:
  summarization:
    enabled: true
    interval_days: 7
    summary_model: claude-sonnet-4
```

##### 2.2.4 Embedding 模型配置

**推荐配置**:
```yaml
embedding:
  model: text-embedding-3-small
  dimension: 1536
  batch_size: 100
  cache_enabled: true
```

**优化建议**:
- 使用小型模型降低成本
- 启用缓存减少重复计算
- 批处理提高吞吐量

## 4. Agent 分层记忆系统深度研究

### 核心判断

> "记忆不是 Agent 的附属模块。记忆就是 Agent 的基础设施。"

这是 Ray Wang 对 Agent 记忆系统的核心判断。没有稳定记忆系统的 Agent，本质上很像一个每次醒来都只剩下模糊印象的人。

### 记忆系统的演进

#### 4.1.1 第一阶段：向量检索

**方法**: 对话切块 → embedding → 向量库 → 检索

**问题**:
1. 只能解决"找相似内容"，很难解决"理解什么重要"
2. 能把旧信息找回来，但不太会处理新旧冲突
3. 更像外置检索器，不像真正会成长的记忆系统
4. 数据变多后，噪音也会变多

#### 4.1.2 第二阶段：分层系统

**新方向**:
- 怎么分层存储
- 怎么抽取重点
- 怎么把事件变成知识
- 怎么处理更新和冲突
- 怎么在必要时遗忘

### 五类主流方案

#### 4.2.1 OpenClaw 类：可解释记忆层

**核心思想**: 直接把记忆写进 Markdown 文件里

**优点**:
- 透明：用户能看到、能检查、能修改
- 可调试：出了问题能排查
- 不是黑箱数据库

**缺点**:
- 依赖 Agent 主动写入
- 缺少自动更新机制
- 缺少遗忘机制
- 长期运行后容易臃肿

**定位**: 优秀的起点，但不是完整答案

#### 4.2.2 QMD 类：混合检索后端

**核心思想**: 给可读的记忆层补上一套真正的搜索系统

**技术栈**:
- 关键词全文检索：负责精确匹配
- 向量检索：负责语义召回
- 本地重排序：负责把结果重新排序

**价值**: 记忆系统不只是数据库，还是一个高质量检索系统

#### 4.2.3 Viking/OpenViking：上下文数据库路线

**核心思想**: 把"记忆"提升为 Agent 的核心资产

**功能**:
- 事件抽取
- 用户建模
- 长期画像
- 上下文统一管理

**视角升级**: 从"聊天记录的副产物"到"主资产来经营"

#### 4.2.4 Letta/MemGPT：自管理记忆路线

**核心思想**: 借鉴操作系统的内存分层思想

**分层**:
- 当前上下文：注意力核心
- 外部存储：需要时再调用
- Agent 自己决定哪些内容应该进入当前上下文

**关键洞察**: 上下文窗口不等于全部记忆

#### 4.2.5 Mem0：智能更新路线

**核心思想**: 记忆系统最难的问题不是"怎么记住"，而是"新信息来了以后，旧记忆怎么办"

**更新类型**:
- 新增
- 修改
- 合并
- 忽略
- 删除
- 归档

**风险**: 更新问题没做好，记忆越多，污染越重

### 认知科学的启发

#### 4.3.1 短期记忆 vs 长期记忆

**人脑机制**:
- 感知信息 → 短暂缓冲
- 一小部分被注意力选中 → 工作记忆
- 经过加工和整合 → 长期记忆

**对 Agent 的启发**:
- 不是所有信息都值得被长期保存
- 临时状态会污染长期判断
- 长期事实会挤占短期注意力

#### 4.3.2 情景记忆 vs 语义记忆

**人脑机制**:
- 情景记忆：发生过什么（具体时间、地点、上下文、细节）
- 语义记忆：总结出什么（抽象、稳定、可迁移）

**对 Agent 的启发**:
- "用户昨天提到想做一个 iOS App" → 情景记忆
- "这个用户长期偏好做高杠杆、可迭代、可产品化的项目" → 语义记忆

**关键判断**:
> "记忆整合这一步，比'写入更多日志'重要得多。"

### 分层记忆架构

#### 4.4.1 推荐结构

```
┌─────────────────────────────────────┐
│ 高层：稳定规则、长期偏好、用户画像    │
│      任务经验、世界知识              │
└─────────────────────────────────────┘
              ↑↓
┌─────────────────────────────────────┐
│ 中间层：摘要、聚类、阶段性整理        │
└─────────────────────────────────────┘
              ↑↓
┌─────────────────────────────────────┐
│ 底层：原始事件和交互日志（可追溯）    │
└─────────────────────────────────────┘
```

#### 4.4.2 记忆类型

| 类型 | 内容 | 存储位置 | 更新频率 |
|------|------|----------|----------|
| 短期工作记忆 | 任务步骤、当前状态 | 内存/日志 | 实时 |
| 中期上下文记忆 | 项目背景、进展 | 中期文件 | 每天 |
| 长期画像 | 偏好、习惯、画像 | MEMORY.md | 每周 |
| 情景记忆 | 具体事件 | 日志 | 按需 |
| 语义记忆 | 规则、知识 | 知识库 | 按需 |
| 程序性记忆 | 工作流、技能 | Skills | 按需 |
| 资源记忆 | 位置、引用 | 索引 | 按需 |

### 遗忘机制

#### 4.5.1 为什么需要遗忘

**问题**:
- 检索噪音增加
- 旧偏好干扰新判断
- 过时信息和当前信息争夺权重
- 系统整体判断变混浊

**人脑的启示**:
- 遗忘不是缺陷，是高级能力
- 会弱化、会压缩、会归档

#### 4.5.2 遗忘策略

1. **时间衰减**: 长期未访问记忆的激活权重降低
2. **频率调整**: 按访问频率和使用价值动态调整权重
3. **任务相关性**: 低价值记忆转入冷存储
4. **重大变化清理**: 用户目标或项目阶段变化时主动清理

### 可靠性保障

#### 4.6.1 三种能力

1. **来源可追溯**: 关键记忆知道来自哪次对话、哪个事件
2. **冲突可裁决**: 新旧信息不一致时有明确规则
3. **检索后验证**: 先验证再塞回上下文

#### 4.6.2 验证规则

- 按时间戳更新
- 按来源可信度更新
- 按用户明确指令更新
- 进入待确认状态

## 5. Agent 设计约束与原则完整框架

### 背景

这是 AlexZ 在发布了一篇关于"滑动窗口"机制的推文后，引发的讨论和思考。他花了几个小时阅读资料、研究开源 Agent 设计、翻阅相关论文，最终总结出的框架。

**参考来源**: OpenClaw / Agent-ZERO / Pi-Mono / Manus / DualPath 论文

### 第一部分：物理约束（不可违抗的现实）

这些是 LLM Agent 运行环境的硬性约束，不是我们选择的，是物理世界强加的。

#### C1. 上下文窗口有限且昂贵

**事实**:
- 128K token 窗口 ≈ 一本 300 页的书
- 每次 API 调用都要为窗口中的每个 token 付费
- 未缓存 input: $3/M tokens
- 50 轮对话可能花 $75

**推论**: 上下文是最稀缺的资源，每个 token 都有机会成本

#### C2. KV Cache 前缀一旦改变，全部重算

**事实**:
- Anthropic Prompt Caching:
  - 前缀匹配 → $0.30/M（缓存价）
  - 前缀不匹配 → $3.00/M（全价）
- DualPath 论文证明：
  - Agent 多轮推理中 KV-Cache 命中率 ≥ 95%
  - 瓶颈不在算力，在"把缓存搬回来的 I/O"

**推论**: 前缀的任何变动都有 10 倍成本放大效应

#### C3. 注意力在中间衰减（Lost in the Middle）

**事实**:
- LLM 对 prompt 开头和末尾的 token 注意力最强
- 中间部分的信息容易被"遗忘"
- 上下文越长，中间的衰减越严重

**推论**: 重要信息必须在开头（system prompt）或末尾（最近的 tool_result）

#### C4. LLM 输出不可靠

**事实**:
- LLM 会循环（同一个工具调同样参数 20 次）
- LLM 会幻觉（编造不存在的文件路径）
- LLM 会忘记（30 轮后忘了最初的任务目标）
- LLM 会偏移（被最近的错误带偏，忽略全局计划）

**推论**: 不能信任 LLM 会自己停下来、自己记住、自己纠偏

#### C5. 工具执行不可预测

**事实**:
- bash 命令可能跑 0.1 秒，也可能跑 10 分钟
- 文件读取可能返回 100 字节，也可能返回 2MB
- 网络请求可能成功，也可能超时
- 用户可能随时想中断当前操作

**推论**: 任何工具调用都必须可取消、可超时、可截断

#### C6. 信息有不同的半衰期

**分类**:
| 信息类型 | 半衰期 |
|----------|--------|
| 决策（"我们选 JWT 而不是 session"） | 整个 session |
| 错误教训（"这个方法行不通"） | 当前任务 |
| 文件内容（"auth.rs 第 42 行"） | 下次修改前 |
| 命令输出（"npm install 的日志"） | 几分钟 |
| 中间推理（"让我想想..."） | 当前轮次 |

**推论**: 不同类型的信息应该有不同的保留策略

---

### 第二部分：设计原则（我们的选择）

#### P1. KV Cache 前缀一致性 ← [C1, C2]

**要求**:
连续 API 调用之间，prompt 的前缀必须保持字节级一致。

**具体要求**:
1. System prompt 构建完成后永远不变
   - 不放时间戳
   - 不动态增删工具 schema
   - 不更新技能列表
2. 信息只通过 tool_result 追加到末尾，不在中间插入
3. 技能指南附着在 tool_result 上，不改 system prompt
4. 序列化必须确定性
   - JSON key 排序
   - 浮点格式一致
   - 空格/换行规范
5. 压缩段一旦生成就不再修改
6. Skill snapshot 在 session 开始时锁定

**违反信号**:
- 往 system prompt 里塞动态信息
- 在对话历史中间插入新消息
- 修改已发送的 tool_result 内容
- 每轮重新生成 system prompt

#### P2. Append-Only 上下文 ← [C1, C2, C3]

**要求**: 上下文只能追加，不能插入、不能重排。

**允许的操作**:
- ✓ 在末尾追加 user/assistant/tool_result 消息
- ✓ 对旧消息做"原地缩减"（Soft Trim）
- ✓ 对旧消息做"原地替换"（Hard Clear）
- ✓ 整段替换为压缩摘要（Stage 3 pruning）

**禁止的操作**:
- ✗ 在中间插入新消息
- ✗ 重排消息顺序
- ✗ 修改已有消息的内容
- ✗ 删除消息后让后续消息"前移"

#### P3. 按需加载一切 ← [C1, C3]

**要求**: 不预装任何可以推迟加载的信息。

**技能加载**:
- System prompt 放一行摘要（~50 tokens/skill）
- 首次使用工具时 → 完整指南（~2K tokens）
- 后续使用 → 关键提醒（~100 tokens）

**记忆检索**:
- 不预加载任何历史记忆
- Agent 主动调用 memory_search → 结果作为 tool_result 返回

**判断标准**: 如果一段信息放进 system prompt 后，有>30% 的 session 不会用到它，就不该预装。

#### P4. 渐进降级 ← [C1, C6]

**要求**: 资源紧张时，按信息价值从低到高逐步丢弃。

**三阶段 Pruning**:
- Stage 1 (30%): Soft Trim — 只缩减大 tool result
- Stage 2 (50%): Hard Clear — 旧 tool result → 占位符
- Stage 3 (70%): 分级压缩 — 按事件类型差异化处理

**事件类型分级**:
| 类型 | 级别 | 处理 |
|------|------|------|
| Decision | Level 1 | 保留关键细节 |
| Error | Level 1 | 保留失败路径 |
| FileModified | Level 2 | 一行摘要 |
| FileRead | Level 3 | 删除，可检索召回 |
| Output | Level 3 | 删除 |

#### P5. 末尾复述 ← [C3, C4]

**要求**: 关键工作状态必须被"复述"到上下文末尾。

**机制**: todo.md 复述模式
- Agent 读取 todo.md
- 工作状态作为 tool_result 出现在末尾
- LLM 在做决策时直接"看到"当前进度

**何时复述**:
- 任务切换时
- 长工具执行后
- 连续 10+ 轮工具调用后

#### P6. 系统级不信任 ← [C4]

**要求**: 系统必须有独立于 LLM 的防护机制。

**四层循环检测**:
1. Generic Repeat — 同工具同参数重复 N 次
2. Poll No Progress — 轮询结果无变化
3. Ping-Pong — 两工具交替循环
4. Circuit Breaker — 全局连续 30 次无进展

**错误触发技能重载**:
- 连续 2 次同类错误 → 系统自动重新注入完整指南

#### P7. 可中断性 ← [C5]

**要求**: Agent 的任何操作都必须可以被用户随时中断。

**三种中断粒度**:
1. Steering（软中断）: 当前工具完成后，跳过剩余工具
2. Abort（硬中断）: 当前工具立即终止
3. Session Reset（最硬中断）: 重建 session

#### P8. 信息只转换，不消失 ← [C6]

**要求**: 信息可以被压缩、摘要、降级，但不应该被默默删除。

**机制**: 事件日志（旁路存储）
- 每个 tool call、每个决策、每个错误，都 append 到 JSONL
- 上下文中被 pruning 掉的内容，在事件日志中依然完整
- 检索路径：memory_search → 事件日志 → tool_result

#### P9. 可观测性优先 ← [全部]

**要求**: 每个关键路径都必须有指标。

**必须追踪的指标**:
- prefix_stability_ratio — 连续调用间 prefix 不变的比例（目标>85%）
- cache_hit_ratio — Prompt Caching 命中率（目标>85%）
- pruning_stage_distribution — 各阶段触发比例
- loop_detection_blocks — 循环阻止次数
- context_utilization — 上下文使用率分布

#### P10. 文件系统即记忆 ← [C1, C3]

**要求**: Agent 通过正常的文件读写管理工作状态。

**为什么不用专门的 memory 系统**:
- 文件系统已经是持久化的、可搜索的、人可读的
- Agent 写 todo.md = 在"记笔记"
- Agent 读 todo.md = 在"回忆"
- Agent grep 项目 = 在"搜索记忆"

---

### 第三部分：原则间的优先级

**优先级顺序**:
P1 > P2 > P7 > P6 > P4 > P3 > P5 > P8 > P9 > P10

**典型冲突示例**:

**冲突 1: P3 vs P5**
- 场景：Agent 需要技能指南，但 tool_result 已经很长了
- 裁决：P3 > P5。技能指南按需加载

**冲突 2: P1 vs P4**
- 场景：上下文 70%，需要 Stage 3 pruning，但 cache 还在 TTL 内
- 裁决：P1 > P4。延迟 pruning，等 cache TTL 过期

**冲突 3: P7 vs P2**
- 场景：用户 steering 中断，需要跳过剩余 tool calls
- 裁决：不冲突。跳过的 tool calls 仍然追加"[Skipped]"占位符

## 6. Agent 生产环境可观测性

### 作者

Harrison Chase，LangChain 创始人

### 核心观点

Agent 的生产环境监控与传统软件有本质区别。

### 两大差异

#### 6.1.1 无限的输入空间

**传统软件**:
- 用户通过按钮、下拉菜单、表单和 API 调用交互
- 可以列举所有故障模式
- 可以制定更全面的错误处理方案

**Agent**:
- 自然语言没有固定的有效输入集
- 用户可以用无数种方式表达同一个请求
- 可以在一条消息中组合多个意图
- 可以将同一个请求分散到多个对话回合

**例子**:
```
"我想退货"
"你能帮我把上周买鞋的钱要回来吗？"
"我收到的商品已损坏，我该怎么办？"
"请退款，订单号#12345"
```
这四个输入都代表相同的意图，但需要 Agent 理解差异。

#### 6.1.2 LLM 对微小变化不够稳健

**原因**:
- 概率抽样引入变异性
- 对措辞、语境或指令顺序的细微变化有不同反应
- 相同的输入有时产生不同的输出

**结果**: 开发过程中观察到的行为可能与生产环境中发生的情况不符。

### 监控重点

#### 6.2.1 监测自然语言交互

需要捕捉:
1. **完整的提示 - 响应对**: 不仅包括请求的发生，还包括用户提出的请求和代理的响应
2. **多轮对话情境**: 将相关的互动分组在一起
3. **智能体轨迹和中间步骤**: 了解轨迹中的每一步

**对比**:
- 传统 Web 请求："POST /api/checkout 200 OK 342ms"
- Agent 交互：一场自然语言对话，可能包含数十个步骤

#### 6.2.2 大规模人类判断的挑战

**问题**: 自然语言交互通常需要人工判断才能做出恰当的评估。

**人工审核限制**:
- 每小时可以有效地评估 50-100 条跟踪记录
- 每天 1000 个请求需要 10-20 小时的人力

**两种解决方案**:

**方案 1: 标注队列**
- 以结构化的格式呈现特定运行情况
- 遵循预定义的评分标准
- 针对特定路径的跟踪进行审查
- 明确评审标准
- 实现团队协作
- 建立反馈循环

**方案 2: LLM 作为评估器**
- 检查无参考质量指标（连贯性、语调）
- 安全与合规检查
- 格式验证
- 主题分类

**权衡**:
- 延迟：评估人员可能会在每个跟踪过程中增加几秒钟的延迟
- 成本：评估所有流量会增加推理成本
- 准确性：需要定制和校准

### Insights Agent

**功能**: 使用自动聚类系统识别:
- 使用模式：用户最常提出的请求类型
- 错误模式：代理在哪些方面出错
- 特殊情况：用户发送了哪些未预料到的查询

## 9. 代理沙箱基础设施架构

### 作者

Larsen Cundric，Browser Use

### 两种隔离模式

#### 9.1.1 模式 1：隔离工具

```
[代理在后端] ←HTTP→ [沙箱运行代码]
```
- 代码执行在沙箱
- 代理在后端
- 沙箱通过 HTTP 调用

#### 9.1.2 模式 2：隔离代理

```
[沙箱中的代理] ←控制平面→ [外部世界]
```
- 整个代理在沙箱
- 通过控制平面与外部通信
- 控制平面掌握所有凭证

### 技术选型

| 环境 | 技术 | 启动时间 |
|------|------|----------|
| 生产 | Unikraft 微型虚拟机 | <1 秒 |
| 开发/评估 | Docker 容器 | 数秒 |

### 关键设计

> "沙箱不应该有任何值得偷窃的东西，也不应该有任何值得保存的东西。"

### 控制平面功能

- LLM 代理：重建会话历史记录
- 文件同步：预签名 URL
- 计费：成本上限处理
