# 我们如何构建安全、可扩展的代理沙箱基础设施

从 AWS Lambda 到采用控制平面架构的 Unikraft 微型虚拟机。

# 

我们是如何走到这一步的

在 Browser Use，我们运行着数百万个 Web 代理。我们最初在 AWS Lambda 上使用仅限浏览器的代理，这样每次调用都是独立的，扩展速度极快，而且无需担心任何安全问题。

然后我们添加了代码执行功能。代理可以编写和运行 Python 代码、执行 shell 命令、创建文件。我们将其构建为一个隔离的沙箱，代理将其作为工具调用。安全性没有问题：代码在沙箱中运行，而不是在后端运行。

但代理循环仍然运行在与 REST API 相同的后端上。重新部署？所有正在运行的代理都会崩溃。内存占用过高的代理？API 速度变慢。两种截然不同的工作负载共享同一个进程。

# 

两种模式

当代理程序可以运行任意代码时，它就能访问机器上的任何内容：环境变量、API 密钥、数据库凭据、内部服务等等。因此，它必须与您的基础架构和机密信息隔离。有两种方法可以实现这一点。

模式 1：隔离工具。 代理程序运行在您的基础设施上。危险操作（代码执行、终端访问）在单独的沙箱中运行。代理程序通过 HTTP 调用沙箱。代码在不会泄露任何信息的环境中运行。

代理程序变得可有可无。无需窃取任何秘密，无需维护任何状态，你可以随时终止它、重启它、独立扩展它。控制平面掌握着真相。

# 

沙盒

同一个容器镜像在所有地方运行。在生产环境中，它作为……运行。

[Unikraft](https://unikraft.cloud/)

微型虚拟机。在本地开发和评估中，它作为虚拟机运行。

[Docker](https://www.docker.com)

容器。一个配置开关（sandbox\_mode: 'docker' | 'ukc'）控制配置代码采取的路径。

## 

Unikraft 正在生产中

每个代理都拥有自己的 Unikraft 微型虚拟机，启动时间不到一秒。我们通过 Unikraft Cloud 的 REST API 在 AWS 的专用裸机上部署这些虚拟机。

沙箱仅从外部接收三个环境变量：SESSION\_TOKEN、CONTROL\_PLANE\_URL 和 SESSION\_ID。不接收 AWS 密钥、数据库凭证或 API 令牌。

Unikraft 为我们提供了开箱即用的零扩展能力。当沙箱空闲时，虚拟机将进入挂起状态。当下一个请求到来时，虚拟机将自动恢复运行。查询间隙的沙箱几乎不消耗任何资源，却能立即唤醒以执行后续任务。

我们在 Unikraft 的多个都市区部署沙箱，以防止任何一个都市区成为瓶颈。

## 

Docker 在开发和评估中的应用

在本地和我们的评估流程中，同一个镜像都以 Docker 容器的形式运行。相同的镜像、相同的入口点、相同的控制平面协议。我们可以在开发笔记本电脑上运行完全相同的代理，并行启动数百个实例进行评估，并部署到 Unikraft 用于生产环境。

## 

硬化

在任何代理代码运行之前，沙箱会执行以下几项操作：

1\. 仅执行字节码。 在 Docker 构建过程中，我们会将所有 Python 源代码编译成 .pyc 字节码，然后删除所有 .py 文件。代理框架代码以 root 用户身份加载到内存中。加载完成后，源代码将被删除。

2\. 权限降低。 入口点以 root 用户身份启动（需要读取 root 用户拥有的字节码），然后立即通过 \`setuid\`/\`setgid\` 命令将权限降至 \`sandbox\` 用户。从那时起，所有操作都将以非特权用户身份运行。

3\. 环境剥离。 将 SESSION\_TOKEN 、 CONTROL\_PLANE\_URL 和 SESSION\_ID 读取到 Python 变量后，我们会从 os.environ 中删除它们 。这样，代理检查环境时，这些变量就不存在了。无论如何，该令牌在沙箱网络之外都无法使用。虚拟机位于私有 VPC 中，除了与控制平面通信之外，没有任何其他权限。

# 

控制平面的工作原理

可以将控制平面视为代理服务。沙箱无法直接访问外部世界。所有请求都必须经过控制平面。需要调用 LLM？必须通过控制平面。需要上传文件到 S3？也必须通过控制平面。这是代理与虚拟机外部任何事物通信的唯一途径。

这是一个无状态的 FastAPI 服务。沙箱发出的每个请求都带有 Bearer: {session\_token} 标头。控制平面通过令牌查找会话，验证其是否仍然有效，并使用真实凭据执行操作。

## 

LLM 代理

对于每个 LLM 调用，沙箱仅发送新消息。控制平面拥有数据库中完整的会话历史记录，并在每次调用时重建该历史记录，并将完整的上下文转发给提供程序。这使得沙箱保持无状态。您可以终止它并启动一个新的沙箱，会话将从上次中断的地方继续。

控制平面还负责实施成本上限和处理计费。沙箱则只专注于执行该任务。

## 

通过预签名 URL 进行文件同步

沙箱包含一个 /workspace 目录，代理程序在该目录中读取和写入文件。文件同步服务会监视目录变更并定期将其同步到 S3，但沙箱永远不会接触到 AWS 凭证。相反，它会向控制平面请求预签名 URL：

1.  沙箱检测到 /workspace 中的文件已更改。
 
2.  Sandbox 调用 POST /presigned-urls 并传入文件路径
 
3.  控制平面生成预签名的 S3 上传 URL（作用域限定于会话）
 
4.  Sandbox 使用这些 URL 直接将文件上传到 S3。
 

下载过程则相反。沙盒环境无需持有任何 AWS 凭证即可直接访问特定范围的 S3 存储库。

## 

网关协议

在沙箱环境中，代理通过“网关”协议与控制平面通信：

python

```python
class AgentGateway(Protocol):
 async def invoke_llm(self, new_messages, tools, tool_choice) -> LLMResponse: ...
 async def persist_messages(self, messages) -> None: ...
```

在生产环境中，ControlPlaneGateway 会向控制平面发送 HTTP 请求。而在本地开发和评估环境中，DirectGateway 会直接调用 LLM 并将历史记录保存在内存中。代理代码并不知道它使用的是哪一个。相同的接口，相同的行为，不同的后端。

# 

规模化

控制平面是无状态的：验证令牌，执行任务，返回结果。需要更多代理？启动更多沙箱。需要更高吞吐量？在负载均衡器后添加控制平面实例。每一层都根据自身的瓶颈进行扩展。

我们的后端运行在位于应用负载均衡器 (ALB) 后方的私有子网中的 ECS Fargate 上。控制平面会根据 CPU 利用率自动扩展。沙箱通过 Unikraft 独立扩展。每个会话都拥有自己的虚拟机，Unikraft 负责跨城域的调度。

# 

总结

对能够执行代码的代理进行沙箱隔离有两种方法。您可以隔离工具（在沙箱中运行代码执行，将代理保留在您的后端），或者隔离代理（将整个代理放在沙箱中，通过控制平面与外部世界通信）。

我们采用了模式 2。 控制平面保存所有凭证，并充当所有操作的代理：LLM 调用、文件存储、计费。沙箱接收三个环境变量，除此之外没有任何其他访问权限。它在生产环境中以 Unikraft 微型虚拟机的形式运行，在开发和评估环境中则以 Docker 容器的形式运行。所有环境都使用相同的镜像。

这样做的代价是每次操作都需要额外增加一次网络跃点，并且需要部署三个服务而不是一个。实际上，与 LLM 的响应时间相比，这种延迟可以忽略不计，而且运维团队早已知道如何应对运维的复杂性。

关键在于 ：你的经纪人不应该有任何值得偷窃的东西，也不应该有任何值得保存的东西。
