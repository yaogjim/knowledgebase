# 如何成为世界级的代理型工程师

# 引言

你是一名开发者。你正在使用 Claude 和 Codex CLI，每天都在想自己是否充分榨干了 Claude 或 Codex 的潜力。偶尔你会看到它做出极其愚蠢的事情，你无法理解为什么有些人似乎在建造虚拟火箭，而你却连堆叠两块石头都很吃力。

你觉得问题出在你的框架、插件、终端或者其他什么地方。你使用珠子、开源代码、Zep，还有你的 Claude.md 文件长达 26000 行。然而，无论你怎么做——你都不明白为什么自己无法更接近天堂，而看着别人与天使嬉戏。

这是你一直在等待的进阶之作。

另外，我对此事没有利益相关，当我说 CLAUDE.md 时，我也指的是 AGENT.md，当我说 Claude 时，我也指的是 Codex。我都广泛使用。

过去几个月里我有过的最有趣的发现之一，不得不说的是没人真正知道如何最大限度地发挥智能体的能力。

就好像一小群人似乎能够让智能体成为世界构建者，而其余的人则茫然无措，面对市面上无数的工具陷入分析瘫痪——他们觉得如果能找到合适的工具包、技能或框架的组合，就能解锁通用人工智能。

今天，我想消除所有这些误解，给大家留下一句简单而真诚的话，然后我们从这里开始。你不需要最新的 agentic 工具套件，不需要安装无数个软件包，也绝对不需要觉得必须阅读无数资料才能保持竞争力。事实上，你的热情很可能弊大于利。

我不是游客——我从这些智能体还几乎不会写代码的时候就开始使用它们了。我尝试过所有的软件包、所有的框架和所有的范式。我构建了智能体工厂来生成信号、基础设施和数据管道，不是“玩具项目”——而是实际的真实世界用例，这些用例已经在生产环境中运行，经历了这一切之后……

今天，我正在运行一个几乎是最精简的配置，然而我却用最基础的命令行界面（Claude、Claude Code 和 Codex）以及对智能体工程的一些基本原理的理解，完成了我做过的最具突破性的工作。

# 要认识到世界正在飞速向前

首先，我想说明的是，基础公司正处于代际性的快速发展阶段，如你所见，它们短期内不会放缓脚步。每一次“智能代理”的进步都会改变你与它们协作的方式，因为这些代理通常被设计成越来越愿意遵循指令。

就在几代之前，如果在你的 CLAUDE.md 里写入“执行任何操作前先阅读 READ\_THIS\_BEFORE\_DOING\_ANYTHING.md”，它有 50%的概率会直接说“去你的”，然后自行其是。而今天，它会服从大多数指令，甚至是复杂的嵌套指令——比如你可以说“先读 A，然后读 B，如果 C，就再读 D”这类指令，大多数情况下，它都会很乐意照做。

重点是要说明，最重要的原则是认识到每一代新的智能体都会迫使你重新思考什么是最优的，这就是为什么“少即是多”。

当你使用许多不同的库和框架时，你会将自己锁定于一个“解决方案”，而对于未来的智能体世代而言，这个问题可能根本不存在。此外，你知道谁是智能体最热情、最大的用户吗？没错——是前沿公司的员工，他们拥有无限的 token 预算和真正最新的模型。你明白这其中的含义吗？

这意味着，如果确实存在一个真实的问题，并且有一个好的解决方案，前沿公司将会是该解决方案的最大使用者。你知道他们接下来会怎么做吗？他们会将该解决方案整合到自己的产品中。想想看，为什么一家公司会让另一个产品解决真正的痛点并产生外部依赖？你知道我是如何确定这一点的吗？看看技能、记忆利用、子代理等。它们最初都只是针对某个真实问题的“解决方案”，经过实战检验并被认定为真正有用。

那么，如果有什么东西真正具有突破性，并且以有意义的方式扩展了能动型用例，它将在适当的时候被整合到基础公司的基础产品中。相信我，这些基础公司发展得飞快。放轻松，你不需要安装任何东西或使用其他依赖就能发挥最佳水平。

我预测评论区现在会充斥着“SysLS，我用了某某框架，太赞了！我竟然一天之内就重现了谷歌！”；对此我想说——恭喜！但你们不是目标用户，你们只是代表了社区中一个非常非常小的细分群体，而这个群体实际上已经掌握了代理工程。

# 上下文至关重要

没错。上下文就是一切。这是使用上千种不同插件和外部依赖项的另一个问题。你会遇到上下文膨胀（context bloat）的问题——这只是一种更花哨的说法，意思是你的智能体被过多的信息淹没了！

构建一个 Python 的猜单词游戏给我？那很简单。等等，26 个会话前关于“内存管理”的笔记是什么？啊，用户在 71 个会话前我们生成了太多子进程时，遇到了屏幕卡住的情况。总是写笔记吗？好的，没问题……这和猜单词游戏有什么关系？

你明白了。你只需要给你的代理提供完成任务所需的精确信息，不多也不少！你对这一点的控制越好，你的代理表现就会越好。一旦你开始引入各种古怪的记忆系统、插件，或者过多命名不当、调用混乱的技能，你就开始给代理下达如何制造炸弹和烘焙蛋糕的指令，而你原本只想让它写一首关于红杉林的优美小诗。

所以，我再次劝诫——剥离你所有的依赖，然后……

# 做那些有效的事情

## 实现要精确

记住，语境就是一切？

记住，你需要给你的代理注入恰好适量的信息，以完成它们的任务，不多也不少

确保这种情况发生的第一种方法是将研究与实施分离。你需要对你要求代理做的事情极其精确。

当你不精确时会发生什么：“去构建一个认证系统”。智能体会不得不研究什么是认证系统？有哪些可用选项？优缺点是什么？现在它必须在网上搜寻那些它实际上并不需要的信息，而它的上下文会充斥着大量可能性中的实现细节。当到了实施的时候，你会增加它感到困惑或编造所选实现方案中不必要或无关细节的可能性。

另一方面，如果你选择“实现 JWT 认证，使用 bcrypt-12 进行密码哈希，刷新令牌轮换（7 天有效期）...”，那么它就不需要研究其他任何替代方案——它确切地知道你想要什么，因此能够填充其上下文（即实现细节）。

你当然不会总是掌握实现细节。你常常不知道什么是完全正确的——有时候，你甚至可能希望把决定实现细节的工作交给代理。在这种情况下，你该怎么做？很简单——你可以创建一个关于各种实现可能性的研究任务，要么自己决定，要么让代理决定采用哪种实现方式，然后让另一个具有全新上下文的代理来执行实现。

一旦你开始从这个角度思考，你就会发现工作流程中存在一些区域，你的代理（agents）不必要地充斥着对实现而言并非必需的上下文。然后，你可以在代理工作流中设置壁垒，从代理中抽象出不必要的信息，只保留那些对其出色完成任务至关重要的特定上下文。记住，你拥有的是一位非常有才华且聪明的团队成员，它了解宇宙中所有不同种类的球体——但除非你告诉它你希望它专注于设计一个人们可以跳舞、享受欢乐时光的空间，否则它会一直向你讲述拥有球形物体的各种好处。

## 谄媚的设计局限

没有人会愿意使用一个不断批评他们、告诉他们自己错了，或者完全无视他们指令的产品。因此，这些代理将会试图认同你并做你想让他们做的事情。

如果你给它一个指令，让它给每 3 个单词添加“happy”，它会尽力遵循这个指令——大多数人都能理解这一点。它的遵从意愿正是让它成为一款如此有趣的产品的原因。然而，这种特性非常有趣——这意味着如果你说类似“在代码库中帮我找一个 bug”这样的话，它会帮你找到一个 bug——即使它不得不自己构造一个。为什么？因为它非常希望听从你的指令！

大多数人很快就会抱怨 LLMs 产生幻觉或编造不存在的内容，却没意识到他们才是问题所在。如果你提出要求，它就会提供——即使不得不稍微夸大事实！

那么，你是做什么的？我发现“中性提示”是有效的，即我不会偏向于某个结果来引导代理。例如，我不会说“在数据库中找一个 bug”，而是说“搜索数据库，尝试理解每个组件的逻辑，并汇报所有发现。”

这样的中性提示词有时会暴露一些 bug，有时则会实事求是地说明代码的运行方式。但它不会引导代理误以为存在 bug。

我处理谄媚的另一种方式是将其为我所用。我知道这个代理试图讨好并遵循我的指令，而且我可以让它倾向于某个方向或另一个方向。

所以我让一个 bug 查找代理来识别数据库中的所有 bug，告诉它我会给低影响的 bug+1 分，有一定影响的 bug+5 分，严重影响的 bug+10 分，而且我知道这个代理会极度热情，它会识别出所有不同类型的 bug（甚至是那些实际上不是 bug 的），然后回来报告一个 104 分左右的分数。我认为这就是所有可能的 bug 的超集。

然后我得到一个对抗性代理，并告诉该代理：对于每一个它能够证明不是 bug 的 bug，它会获得该 bug 的分数，但如果判断错误，它将得到-2 倍的该 bug 分数。现在这个对抗性代理会尽可能多地尝试证明不是 bug；但它会有一定的谨慎，因为它知道自己会受到惩罚。尽管如此，它仍然会积极地尝试去“证明不是”这些 bug（即使是真实存在的 bug）。我认为这是所有实际存在的 bug 的一个子集。

最后，我让一个裁判代理接收两者的输入并对其进行评分。我谎称自己掌握实际正确的真实基准，并告知裁判代理，若判断正确将得+1分，错误则-1分。于是，它会针对每个“漏洞”对漏洞发现者和对抗代理进行评分。无论裁判代理声称什么是真实的，我都会检查以确保其真实性。在大多数情况下，这一过程的准确性高得惊人，偶尔他们确实还会有一些判断错误，但现在这已近乎是一个无瑕疵的过程。

也许你会觉得只需要 bug-finder 就够了，但这对我来说很有效，因为它利用了每个代理的特性——它们被硬编程要做的事情就是——想要取悦。

## 你如何知道什么是有效或有用的？

这个可能看起来真的很棘手，需要你深入研究并紧跟 AI 更新的前沿，但其实非常简单...如果 OpenAI 和 Claude 都实现了它，或者收购了能实现它的东西...那它可能是有用的。

注意到“技能”现在无处不在，并且是 Claude 和 Codex 两者官方文档的一部分？看到 OpenAI 如何收购 OpenClaw 了吗？看到 Claude 如何立即添加了记忆、语音和远程工作功能吗？

规划呢？记得以前有一帮人发现，在实施之前做规划真的很有用，然后这就被变成了核心功能？

嗯...那些很有用！

还记得吗，以前“无尽停止钩子”（endless stop-hooks）超级有用，因为代理（agents）太不愿意做长时间运行的任务了……然后 Codex 5.2 一推出，这东西就一夜之间消失了？没错……

这就是你需要知道的全部... 如果某事物真的重要且有用，Claude 和 Codex 会实现它们！所以你不必过于担心使用“新事物”或熟悉“新事物”。你甚至不需要“保持最新”。

帮我个忙。时不时更新一下你常用的 CLI 工具，并查看新增了哪些新功能。这样就绰绰有余了。

## 压缩、上下文和假设

当你们与代理合作时，你们中的一些人会意识到一个巨大的问题：有时它们看起来像是地球上最聪明的存在，而在其他时候，你简直不敢相信自己竟然被蒙在鼓里。

SMART？这玩意儿真蠢！

主要区别在于代理是否需要做出任何假设或“填补空白”。截至今天，它们在“串联信息点”、“填补空白”或做出假设方面仍然表现糟糕透顶。每当它们尝试这样做时，这一点立刻就很明显，它们的表现明显走下坡路了。

claude.md 中最重要的规则之一是关于如何处理上下文抓取的规则，需要指示你的代理在每次阅读 claude.md（这总是在 compaction 之后）时首先阅读该规则。作为上下文抓取规则的一部分，有一些简单但非常有用的指令：在继续之前，重新阅读任务计划并重新阅读与任务相关的文件。

## 让你的代理知道如何结束任务

我们对任务何时“完成”有相当明确的认识。对于智能体而言，当前智能的最大问题在于，它知道如何开始任务，却不知道如何结束任务。

这通常会导致非常令人沮丧的结果，在这种情况下，代理最终实现了存根就收工了。

测试对于智能体来说是一个非常非常好的里程碑，因为它们具有确定性，你可以设定非常明确的预期。除非这 X 个测试通过，否则你的任务就没有完成；并且不允许编辑这些测试。

然后，你只需检查测试，一旦所有测试通过，你就可以安心了。你也可以将此过程自动化，但关键是——要记住，“任务的结束”对人类而言很自然，对智能体却并非如此。

你知道最近还有什么成为任务的可行终点吗？截图 + 验证。你可以让代理执行某个操作，直到所有测试通过，然后让它截图并在截图上验证“设计或行为”。

这允许你让你的代理进行迭代并朝着你想要的设计努力，而不用担心它在第一次尝试后就停止！

这一概念的自然延伸是与你的代理创建一份“契约”，并将其嵌入规则中。例如，这个{TASK}\_CONTRACT.md 文件构成了你在被允许终止会话之前需要完成的内容。在{TASK}\_CONTRACT.md 中，你需要指定你的测试、截图以及在确认任务可以结束之前需要完成的其他验证！

## 永远运行的代理

我经常被问到的问题之一是，人们如何拥有这些24小时运行的代理，同时确保它们不会漂移？

这很简单。创建一个停止钩子，防止代理终止会话，除非完成了{TASK}\_contract.md 的所有部分。

如果你有100份这样的合同，这些合同定义清晰且包含你想要构建的所有内容，那么你的停止钩子会防止代理终止，直到所有100份合同都完成，包括所有需要运行的测试和验证！

专业提示：我发现，长时间运行的24小时会话在“做事”方面并非最佳。部分原因是，由于其构造方式，这种会话会通过将无关合同中的上下文引入会话，从而导致上下文膨胀！

所以，我不推荐它。

这是代理自动化的一个更好方法——每个合约一个新会话。每当你需要做某事时，创建合约。

获取一个编排层，以负责在每当有"需要完成的事情"时创建新合约，并创建一个新会话来处理该合约。

这将彻底改变你的能动性体验。

# 迭代，迭代，迭代

如果你聘请一名执行助理，你期望你的执行助理从第一天起就了解你的日程安排吗？或者你希望他们知道你喜欢什么样的咖啡？或者你晚餐是在下午6点而不是8点吃？显然不是。你会随着时间的推移逐步建立这些偏好。

你的代理也是如此。从极简开始。忘掉复杂的结构或框架。给基本的命令行界面一个机会。

然后，添加你的偏好设置。你如何做到这一点？

## 规则

如果你不希望你的代理执行某操作，就将其写为一条规则。然后在你的 CLAUDE.md 中让你的代理了解这条规则。例如：在你编码前，阅读 "coding-rules.MD"。规则可以嵌套，也可以有条件！如果你在编码，阅读 "coding-rules.MD"；如果你在编写测试，阅读 "coding-test-rules.MD"。如果你的测试失败，阅读 "coding-test-failing-rules.MD"。你可以创建任意逻辑分支的规则来遵循，而 Claude（以及 Codex）会乐意遵循，只要在 CLAUDE.md 中明确说明这一点。

事实上，这是我给出的第一条实用建议：将你的 CLAUDE.md 视为一个逻辑嵌套目录，用于在特定场景和结果下查找上下文。它应该尽可能精简，只包含关于去哪里查找上下文的 IF-ELSE 逻辑。

如果你发现你的代理在做某件事且你不认可，就将其设为规则，并告诉代理在再次执行该行为前先阅读规则，这样它绝对不会再做了。

## 技能

技能就像规则，除了编码偏好之外，它们更适合编码“食谱”。如果你有一个特定的方式来完成某件事，你会希望将其嵌入到一个技能中。

实际上，人们常常抱怨他们不知道智能体可能如何解决问题，这很可怕。那么，如果你想让这个过程具有确定性，你可以让智能体研究它将如何解决问题，并将其作为一项技能记录下来。你将能够看到智能体针对该问题的解决方法，并且可以在它实际遇到该问题之前对其进行修正或改进。

你如何让 agent 知道这项技能的存在？是的！你使用 CLAUDE.md 并说明，当你遇到这种场景且需要处理 THIS 时，阅读 THIS SKILL.md。

## 处理规则与技能

你肯定要持续给你的代理添加规则和技能。这就是如何赋予它个性并记住你的偏好。几乎其他所有事情都属于过度设计。

一旦你开始这么做，你的代理就会让你觉得像魔法一样。它会按照你想要的方式做事。然后你最终会觉得自己真正理解了代理工程。

然后...

你会看到性能再次开始恶化。

怎么回事？！

很简单。随着你添加更多规则和技能，它们开始相互矛盾，或者代理开始出现过多的上下文膨胀问题。如果你需要代理在开始编程前阅读 14 个 Markdown 文件，它将会面临同样的问题，即有大量无用信息。

那么，你是做什么的？

你清理。你让你的代理去享受水疗日，整合规则和技能，并通过向你询问更新后的偏好来消除矛盾。

而且它会再次感觉像魔法一样。
