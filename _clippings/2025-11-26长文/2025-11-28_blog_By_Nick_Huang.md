# By Nick Huang

By Nick Huang

深度智能体的一个关键特性是能够访问一套文件系统工具。它们可以运用这些工具对文件系统中的文件进行读取、写入、编辑、列表查看及搜索操作。

在这篇文章中，我们将探讨为何文件系统对智能体至关重要。要理解文件系统的价值，首先需要审视当前智能体的局限性——它们失败的原因不外乎（a）模型能力不足，或（b）缺乏恰当的上下文支撑。上下文工程正是 [“一门精妙的艺术与科学，旨在将最契合下一步行动的信息精准填充至上下文窗口”](https://x.com/karpathy/status/1937902205765607626?ref=blog.langchain.com) 。理解上下文工程的运作机制及其失效原理，是构建可靠智能体的关键所在。

### 语境工程概览

现代智能体工程师的工作可以理解为一种 [语境工程](https://blog.langchain.com/the-rise-of-context-engineering/) 。智能体通常 **能够访问** 大量语境信息（所有支持文档、全部代码文件等）。为了回答输入的问题，智能体 **需要** 某些关键语境（其中包含回答问题所需的背景信息）。在尝试解答特定问题时，智能体 **会检索** 特定语料（将其纳入自身的语境窗口）。

![](https://blog.langchain.com/content/images/2025/11/Screenshot-2025-11-12-at-6.24.44---PM-1.png)

从这个视角来看，情境工程在智能体应用中存在多种“失效”可能：

- 若智能体所需的情境信息不在整体语境中，它便无法成功完成任务。例如：客服智能体需要查阅某个文档页面来解答问题，但该页面尚未被索引收录。
- 若智能体检索到的上下文未能涵盖其所需信息，则无法给出正确答案。例如：客服智能体需要访问特定文档页面来回答问题，该页面虽存在且已被索引，却未被智能体检索到。
- 若智能体检索的上下文远大于其实际所需，则会造成资源浪费（时间、计算量或两者兼有）。例如：客服智能体只需获取特定页面，却检索了100个页面。

我们作为智能体工程师的职责是 **将红色适配到绿色（确保智能体检索的上下文信息尽可能接近所需信息的超集）**

在尝试分离恰当语境时，会遇到一些具体挑战

1.  **令牌过多** （检索到的上下文 >> 必要上下文）
 
 某些工具，比如网络搜索，可能会返回大量令牌。几次网络搜索就能迅速让对话历史积累数万令牌。最终你可能会遇到烦人的 400 错误请求，但在此之前，你的 LLM 账单会激增且性能下降。
2.  **需要大量上下文** （必要上下文 > 支持上下文窗口）
 
 有时，智能体确实需要大量信息才能回答问题。这些信息通常无法通过单次搜索查询返回，因此许多人倾向于采用“代理式搜索”的理念——让智能体反复调用搜索工具。但问题在于，上下文信息量会迅速增长到无法全部容纳在其上下文窗口中的程度。
3.  **寻找小众信息** （检索到的上下文 ≠ 必要上下文）
 
 智能体可能需要查阅深藏在数百甚至数千个文件中的专业信息来处理输入。如何让智能体可靠地找到这些信息？如果无法做到——那么检索到的上下文将无法满足回答问题的需求。除了语义搜索，是否存在替代方案（或补充方案）？
4.  **随时间学习** （总语境 ≠ 必要语境）
 
 有时，智能体可能无法获取回答问题所需的必要上下文（无论是其工具还是指令中）。最终用户在与智能体的互动中，常常会（隐晦或明确地）提供关于这些上下文的线索。是否有方法能让智能体将这些线索纳入其上下文，以供后续迭代使用？

这些都是常见的障碍，我们大多数人都曾遇到过不同形式的类似问题！

### 文件系统如何提升智能体的性能？

简而言之：文件系统为智能体提供了一个统一接口，使其能够灵活地存储、检索和更新海量上下文信息。

让我们看看这如何帮助解决上述列出的各种场景。

**令牌过多** （检索到的上下文 >> 必要上下文）

与其依赖对话历史来存储所有工具调用结果和笔记，智能体可以将这些内容写入文件系统，并在需要时选择性查找 ***相关信息*** 。马努斯是 [最早公开讨论这种方法](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus?ref=blog.langchain.com) 的先行者之一——下图即出自其博客文章。

![](https://blog.langchain.com/content/images/2025/11/Manus-Context-Engineering.004-1.png)

以那个网页搜索工具为例。我执行一次网页搜索，工具会返回 1 万个 token 的原始内容。这些内容大部分通常并非必需。如果我将全部 1 万 token 存入消息历史，整个对话过程中这些内容都会持续占用空间，推高 Anthropic 的账单。但若将庞大的工具结果转存至文件系统，智能体就能通过 grep 精准检索关键词，仅将必要上下文载入对话。

在这个例子中，智能体有效地将文件系统用作 **大容量上下文的临时存储区。**

**需要大量上下文（必要上下文量 < 支持的上下文窗口）**

有时智能体需要大量上下文才能回答问题。文件系统提供了一个很好的抽象层，让 LLMs 能够根据需要动态存储和提取更多信息。具体示例包括：

- 对于需要长期规划的任务，智能体需先制定计划并严格执行。通过将计划写入文件系统，智能体后续可随时调取这些信息至上下文窗口，以此自我提醒当前应执行的任务（例如 [“通过复述引导注意力”](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus?ref=blog.langchain.com) ）。
- 为了梳理所有这些上下文信息，智能体可能会启动子智能体。当这些子智能体执行任务并学习知识时，它们不会仅仅将所学内容反馈给主智能体，而是可以将知识写入文件系统（例如 [减少信息传递过程中的失真](https://www.anthropic.com/engineering/multi-agent-research-system?ref=blog.langchain.com) ）。
- 有些智能体需要大量操作指引。与其将所有指令塞进系统提示（导致上下文臃肿），不如将其存储为文件，让智能体根据需要动态读取（例如 [Anthropic 技能库](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills?ref=blog.langchain.com) ）。

**寻找小众信息** （检索到的上下文 ≠ 必要上下文）

在 LLM 浪潮早期，语义搜索曾是获取上下文最主流的方法之一。虽然它在某些场景下表现不俗，但对于特定类型的文档（如技术 API 参考手册、代码文件），由于文本本身缺乏语义信息，语义搜索的适用性可能大打折扣。

文件系统提供了一种替代方案，让智能体能够通过 ls、glob 和 grep 工具智能搜索上下文。如果你最近使用过 Claude Code，就会知道它严重依赖 glob 和 grep 搜索来寻找所需的确切上下文。这项技术之所以成功，有几个关键因素。

- 如今的模型经过 [专门训练](https://platform.claude.com/docs/en/agents-and-tools/tool-use/bash-tool?ref=blog.langchain.com) ，能够理解文件系统的遍历操作
- 信息通常已经按逻辑结构（目录）组织好了
- glob 和 grep 让智能体不仅能筛选特定文件，还能精准定位到具体行与特定字符
- [`read_file`](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool?ref=blog.langchain.com) 工具允许代理指定从文件中读取哪些行

正因如此，在某些情况下，利用文件系统（以及通过文件系统获得的搜索能力）能够产生更优的效果。

请注意，语义搜索依然有其用武之地！并且可以与文件系统搜索结合使用。Cursor 最近 [发表了一篇博客](https://cursor.com/blog/semsearch?ref=blog.langchain.com) ，重点介绍了将两者结合使用的优势。

**随时间学习** （总语境 ≠ 必要语境）

智能体表现不佳的一个重要原因是缺乏相关上下文。提升智能体性能的关键通常在于确保它们能够获取恰当的上下文信息。有时这表现为增加数据源或更新系统提示。

更新系统提示词的一种常见做法是：

1.  看一个智能体因缺乏适当指令而表现不佳的例子
2.  从领域专家处获取相关指导
3.  根据这些指示更新提示

通常，最终用户实际上是最佳领域专家。通过与智能体对话，他们可能（隐晦或明确地）提供关于正确相关指令的重要线索。考虑到这一点——是否有办法将上述第三步（用这些指令更新提示）自动化？

我们认为，智能体的指令（或技能）与其可能需要处理的其他上下文并无二致。文件系统可以成为智能体存储和更新自身指令的场所！

用户反馈后，智能体可立即将重要信息写入自有文件系统实现记忆。这种机制特别适合处理快速、一次性的关键信息，例如用户专属的姓名、邮箱或个人偏好等定制化内容。

这个问题尚未完全解决，仍是一种新兴模式，但 LLMs 通过这种方式能够随时间推移自主扩展技能库和指令集，确保在后续迭代中获取必要上下文，这无疑是一种令人振奋的新途径。
