# 深入解析 LangChain 新特性：Agent Middleware（智能体中间件）
### Metadata
- **Title**: 深入解析 LangChain 新特性：Agent Middleware（智能体中间件）
- **Author**: 小猫头
- **URL**: [https://blog.langchain.com/agent-middleware/](https://blog.langchain.com/agent-middleware/)

### Overview
LangChain 新推出的 `Agent Middleware`（智能体中间件）功能，旨在解决当前 AI Agent 框架在实际应用中普遍存在的灵活性不足和控制力有限的核心痛点。特别是在 `context engineering`（上下文工程）等复杂场景下，开发者难以精细化地管理模型的输入与 Agent 的内部状态。通过引入一种类似于网络服务中常见的中间件架构，LangChain 1.0 允许开发者在 Agent 的核心运行循环中插入自定义逻辑，从而实现对模型请求、状态更新以及执行流程的精细化控制。这一新特性不仅极大地提升了 Agent 的可组合性与可扩展性，也为构建更健壮、更可控的 AI 应用提供了强大的新范式。

### 现有 Agent 框架的挑战与核心理念

自 LangChain 推出 Agent 抽象概念以来，近三年的时间里，AI 应用开发框架层出不穷。然而，尽管这些框架在原型设计阶段表现出色，一旦进入复杂的生产环境，它们共同的短板便暴露无遗——灵活性不足。这个问题的核心症结在于 `context engineering`（上下文工程），即如何精确地构建和管理传递给大语言模型的上下文信息。在许多现有框架中，上下文的构建过程被高度封装，开发者如同面对一个“黑箱”，无法在需要时对模型的输入进行细致的干预和调整。这种控制权的缺失，导致许多开发者在面对需要动态调整提示词、管理工具调用或精细控制对话历史的复杂用例时，最终不得不放弃框架的便利，回归到编写大量自定义代码的老路上，这无疑违背了框架简化开发的初衷。

要理解 LangChain 为何要引入 Middleware，我们首先需要回归 Agent 的本质。一个 Agent 的核心构成其实非常简单，可以概括为三个基本要素：
*   **A model (一个模型)**: 负责进行思考和决策的大语言模型。
*   **A prompt (一个提示词)**: 指导模型如何行动、如何使用工具的指令模板。
*   **A list of tools (一组工具)**: Agent 可以调用的外部函数或 API，用以获取信息或执行操作。

Agent 的核心算法同样直观：它接收用户的输入消息，然后启动一个循环（loop）。在这个循环中，Agent 会根据当前状态和提示词，决定是调用某个工具，还是直接生成最终答案。如果决定调用工具，它会执行工具，并将工具的返回结果作为新的观察信息，再次进行决策。这个过程会不断重复，直到 Agent 认为任务已经完成，便会跳出循环，输出最终结果。这个流程看似简单，但在实际应用中，要确保 Agent 的行为可靠且符合预期，开发者必须能够介入并影响这个循环的每一个环节。例如，在调用模型前，可能需要根据历史对话动态修改提示词；在模型返回工具调用请求后，可能需要进行一次人工审核；在多次对话后，为了避免超出模型的上下文长度限制，还需要对历史消息进行压缩或摘要。这些细致入微的控制需求，正是现有框架所欠缺的。

### LangChain 1.0 的解决方案：Middleware 概念

为了赋予开发者更强大的控制能力，LangChain 在其 1.0 版本中借鉴了 Web 开发中成熟的中间件思想，推出了全新的 `Middleware`（中间件）抽象层。这个概念的核心在于，它允许开发者在 Agent 的核心循环（特别是模型调用前后）“挂载”自定义的逻辑片段。这些逻辑片段就是所谓的“中间件”。通过这种方式，开发者不再需要修改 Agent 的核心代码，就能以一种非侵入式的方式，精确地干预和扩展 Agent 的行为。

这种设计的精妙之处在于它的**可组合性（Composability）**。就像 Web 服务器可以依次通过身份验证、日志记录、数据压缩等多个中间件来处理一个 HTTP 请求一样，LangChain 的 Agent 也可以应用一个中间件链条。例如，你可以定义一个用于记录 Token 消耗的中间件，再定义一个用于对话历史摘要的中间件，然后将它们串联起来。当 Agent 运行时，请求会依次穿过这个链条，每个中间件都可以对请求或状态进行处理和修改。这种模式极大地提升了代码的模块化程度和复用性，让开发者能够像搭积木一样，将各种独立的功能（如日志、监控、缓存、人工干预）灵活地组合进自己的 Agent 应用中。

为了支撑这一强大的功能，Middleware 提供了三个简洁而核心的接口，供开发者实现自定义逻辑：
*   **`before_model`**: 这个函数会在 Agent 决定调用大语言模型**之前**被执行。它接收 Agent 的当前状态 `state` 作为输入。在这个阶段，你可以执行一些预处理操作，比如打印日志、检查当前状态是否满足特定条件。你甚至可以修改 `state`，或者根据某些逻辑决定跳过这次模型调用，直接跳转到其他流程节点。
*   **`after_model`**: 这个函数会在大语言模型调用完成并返回结果**之后**被执行。它同样接收 `state` 作为输入，此时的 `state` 已经包含了模型最新的输出。这是执行后处理逻辑的理想位置，比如视频案例中演示的，从模型的响应元数据中提取 Token 使用信息并进行统计。同样，你也可以在此处修改 `state` 或改变 Agent 的后续行为。
*   **`modify_model_request`**: 这是功能最强大的一个接口，它同样在模型调用前运行。与 `before_model` 不同的是，它允许用户直接修改本次模型调用的**所有关键参数**。这意味着你可以动态地更改将要发送给模型的工具列表、提示词、消息历史、模型本身（例如，在不同任务间切换模型）、模型的配置参数（如温度 `temperature`）、甚至是期望的输出格式。这个接口为实现高度动态和自适应的 Agent 行为提供了无限可能。

为了方便开发者快速上手，LangChain 1.0 的 alpha 版本已经内置了一些开箱即用的中间件，包括用于对话历史管理的 `Summarization`（摘要）、用于引入人工审核的 `Human-in-the-loop`（人工干预），以及针对特定模型的 `Anthropic prompt caching`（Anthropic 提示词缓存）。

### 实战演示：通过代码理解 Middleware

理论的讲解固然重要，但通过一个实际的代码案例，我们能更深刻地理解 Middleware 的工作原理和应用价值。视频中通过一个在 Google Colab 环境下运行的 Python Notebook，手把手地演示了如何自定义并使用一个中间件来追踪 Agent 的 Token 消耗。

**第一步：环境准备**
由于 Agent Middleware 是 LangChain 1.0 的新特性，首先需要安装其 alpha 版本。在演示中，通过 `pip install -q langchain==1.0.0a5` 命令精确地锁定了版本，这在快速迭代的 alpha 阶段是保证代码稳定运行的好习惯。接着，配置了 `OPENAI_API_KEY`，因为后续将使用 OpenAI 的 GPT 模型。

**第二步：自定义一个 Token 追踪中间件**
这个案例的核心目标是创建一个能够自动统计每次模型调用所消耗 Token 数量的中间件。为此，我们创建了一个名为 `TrackingMiddleware` 的类，它继承自 LangChain 提供的 `AgentMiddleware` 基类。

*   **定义数据结构**: 为了清晰地存储每次的消耗数据，代码首先利用 `pydantic` 定义了一个 `ModelUsage` 数据类。这个类包含了我们关心的几个字段：`model_name` (模型名称), `prompt_tokens` (输入 Token 数), `completion_tokens` (输出 Token 数), 和 `total_tokens` (总 Token 数)。
*   **实现核心逻辑**: 在 `TrackingMiddleware` 类中，我们重点实现了 `after_model` 方法。这个方法会在每次模型调用成功后自动执行。其内部逻辑如下：
    1.  从传入的 `state`（Agent 的当前状态）字典中，获取 `messages` 列表，并取出最后一个元素。这个元素就是刚刚由 AI 模型生成的消息对象。
    2.  从该 AI 消息对象中，访问其 `response_metadata` 属性。对于 OpenAI 模型，这个元数据字典中会包含一个名为 `token_usage` 的字段，其中就存储了详细的 Token 消耗信息。
    3.  代码解析这个 `token_usage` 字典，提取出 `prompt_tokens`、`completion_tokens` 和 `total_tokens` 的值。
    4.  最后，将这些信息以及模型名称（同样可以从元数据中获取）打包成一个 `ModelUsage` 对象，并将其添加到一个类级别的列表 `model_usages` 中。

通过这几个简单的步骤，一个功能完备的 Token 追踪中间件就完成了。它可以在不干扰 Agent 核心业务逻辑的情况下，默默地记录下所有的 Token 开销。

**第三步：创建 Agent 并集成中间件**
定义好中间件之后，我们需要在创建 Agent 时将其“挂载”上去。LangChain 的 `create_agent` 函数为此提供了一个 `middleware` 参数。

*   `tracking_middleware = TrackingMiddleware()`: 首先，实例化我们自定义的中间件。
*   `agent = create_agent(model="openai:gpt-4o", middleware=[tracking_middleware])`: 在创建 Agent 时，指定要使用的模型（这里是 `gpt-4o`），并将中间件实例放在一个列表中传给 `middleware` 参数。

**第四步：运行与验证**
Agent 创建完毕后，我们通过 `agent.invoke()` 方法与其进行交互。
*   **首次调用**: 我们首先向 Agent 提问 `{"messages": [HumanMessage(content="What is LangChain?")]}`。执行后，我们可以观察到控制台的输出。首先打印了 "Before model:" 和调用前的 `state`，这证明 `before_model` 被成功触发。紧接着，在模型响应后，打印出了包含 `token_usage` 信息的 `AI response metadata`，这表明 `after_model` 逻辑也已执行。
*   **再次调用**: 为了模拟多轮对话，代码将第一次的问答结果追加到消息列表中，然后再次调用 Agent，提出新问题 `{"messages": messages}`，其中包含了新的问题 "How to use it?"。
*   **查看最终结果**: 在所有交互结束后，我们打印 `tracking_middleware.model_usages` 的内容。输出结果是一个包含两个 `ModelUsage` 对象的列表，每个对象都精确地记录了对应模型调用的模型名称和三类 Token 的消耗数量。这完美地证明了我们的自定义中间件成功地完成了它的监控任务。

这个简单的例子有力地展示了 Middleware 模式的优雅与强大。它将“业务逻辑”（回答问题）与“横切关注点”（Token 统计）清晰地分离，使得代码更加模块化，易于维护和扩展。

### 框架 & 心智模型（Framework & Mindset）

LangChain Agent Middleware 的引入，不仅仅是增加了一个新功能，更重要的是它为构建复杂的 AI 应用带来了一种先进的心智模型——**将“面向切面编程”（Aspect-Oriented Programming, AOP）思想应用于 AI Agent 开发**。这种思维模式鼓励开发者将 Agent 的核心任务逻辑与通用的、可复用的“横切关注点”（Cross-Cutting Concerns）分离开来。

在传统的 Agent 开发模式中，我们可能会将日志记录、性能监控、数据缓存、权限校验等逻辑直接硬编码到 Agent 的主流程代码中。这样做会导致核心逻辑变得臃肿不堪，且这些通用功能难以在不同的 Agent 之间复用。每次需要调整或增加新功能时，都可能需要深入修改已经稳定运行的核心代码，增加了引入错误的风险。

而 Middleware 框架提供了一种全新的解法。我们可以将 Agent 的核心执行循环（即思考-行动循环）视为主业务流程。而像 Token 消耗统计、对话历史摘要、人工审核介入、错误重试机制等功能，则可以被抽象为一个个独立的“切面”。每个切面都只关注自己的特定任务，并通过 Middleware 接口，在主流程的特定“连接点”（Join Points）——例如 `before_model` 和 `after_model`——被动态地织入。

建立这种心智模型，会给我们的 Agent 开发带来以下几个核心优势：
*   **高度解耦 (Decoupling)**: Agent 的核心职责是解决用户提出的问题。它不应该也不需要关心自己的 Token 是如何被统计的，或者对话历史是在何种条件下被压缩的。这些功能通过中间件实现后，与核心逻辑完全解耦。我们可以独立地开发、测试和维护每一个中间件，而无需触及 Agent 的主体。
*   **强大的可组合性 (Composability)**: Middleware 的链式调用机制是其精髓所在。我们可以像搭建乐高积木一样，根据具体应用场景，自由组合不同的中间件。例如：
    *   一个用于调试的 Agent，其 `middleware` 链可能是 `[LoggingMiddleware, TrackingMiddleware]`，用于详细记录每一步的日志和资源消耗。
    *   一个需要处理超长对话的生产环境 Agent，其 `middleware` 链可能是 `[SummarizationMiddleware, CachingMiddleware, ErrorHandlingMiddleware]`，用于自动管理上下文、缓存重复请求的结果并处理潜在的 API 错误。
    这种即插即用的组合能力，使得构建复杂而健壮的 Agent 变得前所未有的灵活。
*   **极致的可重用性 (Reusability)**: 一旦我们编写了一个高质量的中间件，比如视频中演示的 `TrackingMiddleware`，它就可以被项目中的任何一个 Agent 复用。一个为特定 API 设计的缓存中间件，也可以被所有需要调用该 API 的 Agent 共享。这大大减少了重复代码的编写，提升了开发效率和代码质量，也促进了团队内部最佳实践的沉淀和共享。
*   **卓越的可扩展性 (Extensibility)**: 当应用需要增加新的全局功能时，我们不再需要去修改每一个 Agent 的代码。我们只需要开发一个新的中间件，然后将其添加到相应 Agent 的 `middleware` 列表中即可。例如，如果未来需要为所有 Agent 调用增加一个成本控制中间件，当累计费用超过预算时自动停止，我们只需实现这个 `CostControlMiddleware` 并全局应用它。这种模式使得系统能够轻松地适应未来的需求变化，保持了长期的技术活力。

综上所述，Agent Middleware 不仅仅是一个技术实现，更是一种架构思想。它引导我们从“过程式”地编写 Agent 逻辑，转向“声明式”地组合 Agent 能力。通过将复杂的 Agent 系统拆解为纯粹的核心逻辑和一系列可插拔的通用功能模块，我们能够构建出更清晰、更健壮、更易于维护和扩展的下一代 AI 应用。


# LangChain Agent Middleware 概览

本期视频分享了 LangChain 新推出的 Agent Middleware（智能体中间件）功能。这是一个旨在解决现有 Agent 框架灵活性不足问题的新特性，尤其是在上下文工程方面。通过引入中间件概念，开发者可以更精细地控制 Agent 的内部运行流程。

### 现有 Agent 框架的挑战与核心理念

尽管 LangChain 的 Agent 抽象已存在近三年，市面上也涌现了许多类似的 AI 应用开发框架，但它们在实际生产环境中普遍存在灵活性不足的问题。特别是在 `context engineering`（上下文工程）方面，开发者往往难以完全掌控输入到模型中的内容。这导致在处理复杂场景时，开发者不得不放弃框架，转而编写自定义代码。实际上，Agent 的核心组成非常简单，主要包括一个模型（A model）、一个提示词（A prompt）和一组工具（A list of tools）。其核心算法是：用户输入消息，Agent 随即进入一个循环，不断调用工具和模型，直到任务完成并最终输出结果。然而，要让 Agent 可靠地运行，开发者需要更细致地控制其执行流程，包括中间状态、模型输入等。

### LangChain 1.0 的解决方案：Middleware 概念

为了解决 Agent 开发中的控制难题，LangChain 在 1.0 版本中引入了全新的 `Middleware`（中间件）概念。该机制允许开发者在模型调用的前后执行自定义逻辑，或修改模型请求本身。这使得开发者能够非常灵活地调整工具、提示词、消息甚至是模型的设置。更重要的是，多个中间件可以像 Web 服务器的中间件一样串联起来，按顺序执行。这种设计极大地提升了 Agent 的可组合性和扩展性，让开发者能以更模块化的方式构建复杂的应用。

### Middleware 的核心接口与内置功能

从核心概念和开发接口来看，Middleware 的设计非常简洁易用。它主要提供了三大核心接口：
*   **`before_model`**: 在模型调用前运行，可以用来更新状态或跳转到其他节点。
*   **`after_model`**: 在模型调用后运行，同样可以更新状态或进行跳转。
*   **`modify_model_request`**: 在模型调用前运行，允许用户修改该次请求的几乎所有内容，包括工具、提示词、消息列表、模型、模型设置、输出格式和工具选择。

目前，在 LangChain 1.0 的 alpha 版本中，框架已经内置了一些实用的中间件，例如：
*   **`Summarization`（摘要）**: 能够根据 Token 数量自动对历史对话进行摘要，以在保留关键上下文的同时，避免超出模型的限制。
*   **`Human-in-the-loop`（人工干预）**: 允许在 Agent 运行过程中引入人工审核或操作的环节。
*   **`Anthropic prompt caching`（Anthropic 提示词缓存）**: 针对 Anthropic 模型的特有提示词缓存机制。

### 实战演示：通过代码理解 Middleware

视频通过一个在 Colab 上运行的 Python Notebook 实例，详细演示了如何使用 Agent Middleware。首先，需要安装 LangChain 1.0 的 alpha 版本，演示中指定的版本为 `1.0.0a5`。在 Alpha 阶段，锁定特定版本可以确保代码的可复现性，避免因接口频繁变动导致的问题。

### 自定义 Middleware：追踪 Token 使用情况

演示的核心是创建了一个名为 `TrackingMiddleware` 的自定义中间件，其目的是追踪并统计模型每次调用的 Token 消耗情况。

该中间件的实现步骤如下：
1.  **定义数据模型**: 首先使用 Pydantic 定义了一个 `ModelUsage` 类，用于存储单次模型调用的消耗数据，包括模型名称（`model_name`）、提示词 Token 数（`prompt_tokens`）、补全 Token 数（`completion_tokens`）和总 Token 数（`total_tokens`）。
2.  **实现 `after_model` 方法**: 在 `TrackingMiddleware` 类中，主要实现了 `after_model` 方法。该方法会在每次模型调用结束后被触发。
3.  **提取消耗数据**: 在 `after_model` 方法内部，代码从 Agent 状态（`state`）中获取最后一条 AI 消息，并从该消息的响应元数据（`response_metadata`）中提取出 `token_usage` 信息。这些信息包含了详细的 Token 消耗数据。
4.  **记录数据**: 最后，将提取到的消耗数据实例化为一个 `ModelUsage` 对象，并将其追加到一个列表（`model_usages`）中进行保存。

通过这种方式，所有经过该中间件的模型调用，其 Token 消耗都会被自动记录下来。

### 创建并运行带有 Middleware 的 Agent

定义好中间件后，下一步是创建一个 Agent 并将中间件注入其中。
1.  **实例化中间件**: `tracking_middleware = TrackingMiddleware()`。
2.  **创建 Agent**: 使用 `create_agent` 函数创建 Agent 实例。在此过程中，通过 `middleware` 参数传入一个包含 `tracking_middleware` 实例的列表。`agent = create_agent(model="openai:gpt-4o", middleware=[tracking_middleware])`。
3.  **调用 Agent**: 首次调用 Agent 并提问“`What is LangChain?`”。从输出可以看到，在模型实际调用前，`before_model` 方法被触发，并打印出了当前的 Agent 状态。调用完成后，`after_model` 方法被触发，并打印出了包含 Token 消耗信息的 AI 响应元数据。
4.  **多轮对话与统计**: 接着，代码向对话历史中追加了新的消息，并再次调用 Agent 提问“`How to use it?`”。
5.  **查看统计结果**: 最后，通过访问 `tracking_middleware.model_usages`，可以看到一个包含了两次模型调用消耗记录的列表，清晰地展示了每一次调用的具体 Token 开销。

这个简单的例子充分展示了 Middleware 的强大之处，它能以非侵入的方式为 Agent 增加额外的功能，如监控、日志、缓存等。
