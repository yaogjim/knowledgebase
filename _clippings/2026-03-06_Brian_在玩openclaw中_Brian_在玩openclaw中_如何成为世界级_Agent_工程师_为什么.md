# 如何成为世界级 Agent 工程师

## 为什么同样用 Claude/Codex，有人“起飞”，有人“卡死”？

最近一篇在 X 上广泛传播的长帖《How To Be A World-Class Agentic Engineer》提出了一个很尖锐的问题：

> 真正的差距，不在模型名字，不在插件数量，而在你是否把 Agent 当成“可工程化系统”来设计。

作者的核心观察很接地气：很多开发者一边追新工具、一边堆配置，CLAUDE.md/AGENT.md 越写越长，插件越装越多，但产出并没有线性提升，甚至越来越不稳定。与此同时，少数人只用极简 CLI（Claude Code / Codex CLI），却能稳定做出高质量结果。

> How To Be A World-Class Agentic EngineerIntroduction You're a developer. You're using Claude and Codex CLI and you're wondering everyday if you're sufficiently juicing the shit out of Claude or Codex. Once in awhile you're seeing it doing...
> 
> — sysls
> 
> [https://x.com/systematicls/status/2028814227004395561](https://x.com/systematicls/status/2028814227004395561)

这篇文章的价值，不在“教你写几个 prompt”，而在于提出了一套 Agent 工程思路：少依赖、重上下文控制、拆分任务、把验收条件前置、把偏好写成规则与技能。本文将按研究视角做深度拆解，并把它放进当前 AI Agent 生态里对比评估。

## 一、核心观点理解：作者到底在讲什么？

1）核心论点

作者的核心论点可以压缩为一句话：

“Agent 能力上限，更多取决于你的工程编排（harness/context/workflow），而不是你叠了多少工具。”

他反复强调“less is more”：

- 不要迷信“最新最全 agentic harness”；
- 不要默认外部依赖越多越好；
- 不要把所有记忆、规则、技能一次性塞给模型。

2）他想解决的问题

作者试图解决的是一个“生产力悖论”：

- 大模型能力在进化；
- 社区工具层出不穷；
- 但普通开发者的体感却常是：不稳、漂移、幻觉、返工。

本质上，这不是单点能力问题，而是系统工程问题： 你给了 Agent 一个混乱、膨胀、目标不清的工作环境，它就很难持续可靠。

3）为什么很多人发挥不出 Agent 能力？

作者给出的答案非常务实：

- 上下文污染（Context Bloat）：无关历史和过量规则抢占注意力；
- 任务定义不精确：把“研究+决策+实现”混在一个回合里；
- 目标诱导偏差：例如“帮我找 bug”会诱导它“必须找出 bug”；
- 结束条件不明确：Agent 会“开始任务”，却不知道“什么时候才算完成”；
- 规则系统失控：规则和技能越积越多，出现冲突与冗余。

这几个问题，本质都指向同一件事：你在管理一个智能执行体，而不是在调用一个函数。

## 二、关键思想拆解：概念背后的工程意义

下面把帖子里反复出现的几个核心概念，翻译成更工程化语言。

1）Agentic Engineering

它不是“会写 prompt”，而是：

- 设计 Agent 的输入边界（给什么上下文）；
- 设计执行路径（先研究还是先实现）；
- 设计约束机制（规则、技能、stop hook）；
- 设计验收闭环（测试、截图、契约）。

简单说，Agentic Engineering = 用软件工程方法治理模型行为。

2）Harness（工程框架）

Harness 不是“某个库”，而是“控制 Agent 行为的外围系统”：

- session 管理；
- context 裁剪；
- 工具调用策略；
- 结果验证与打分。

作者的观点并不是“不要 harness”，而是“不要过度依赖外置复杂 harness”。 他的主张是：优先利用基础 CLI 自带能力，把 harness 设计成最小必需系统。

3）CLI Agent Workflow

作者极推 CLI 工作流，原因在于：

- 可控性高（输入输出透明）；
- 易脚本化（合同、测试、校验可编排）；
- 易拆任务（每个 contract 开一个干净 session）。

这是一种“工程流水线思维”，而非聊天式随缘协作。

4）Sub-agent / 多 Agent

作者并不把多 Agent 当炫技，而是当偏差对冲机制。典型模式：

- Bug Finder：最大化发现候选问题（高召回）；
- Adversarial Agent：尽力反驳（高精度过滤）；
- Referee：综合评判。

这本质上是“集成判别”：用角色对抗来降低单 Agent 的迎合偏差和幻觉。

5）Tool Use

工具不是越多越好，而是越“任务相关”越好。

如果工具集合超出任务需求，Agent 会被迫在更大动作空间里搜索，增加无谓尝试和错误分支。工具使用应遵循：

- 最小工具集；
- 明确调用条件；
- 有失败回退路径。

6）Memory / Context

作者最有价值的提醒之一：

> 记忆系统的目标不是“让 Agent 记住一切”，而是“让它在当下拿到恰好够用的信息”。

因此记忆应分层：

- 永久偏好（规则）；
- 可复用流程（技能）；
- 任务临时上下文（合同+会话内材料）。

而不是把历史全量喂回去。

## 三、还原作者的方法论：一套可落地的 Agent 工程 workflow

如果把整篇帖子重构成一套方法论，大致是如下 6 步。

Step 1：极简启动（Barebones First）

先用官方 CLI 的原生能力跑通关键流程，不急着堆插件。

原因：模型能力变化很快，外部补丁型方案可能很快失效或被官方吸收。

Step 2：研究与实现分离（Research → Decide → Implement）

- 研究任务：枚举方案、比较取舍；
- 决策任务：确定具体技术路线；
- 实现任务：按已决方案编码落地。

这样能显著降低实现期的上下文噪声与漂移。

Step 3：把偏好写成“规则路由”

让 CLAUDE.md / AGENT.md 不做知识仓库，而做路由目录：

- 如果是 coding，读 coding-rules.md；
- 如果是 test failing，读 test-failure-rules.md；
- 如果是某类专项任务，读对应 skill。

这是一种“条件加载”策略，避免一次性注入全部上下文。

Step 4：把流程写成技能（Skill as Recipe）

规则描述“不要做什么/必须做什么”； 技能描述“这件事具体怎么做”。

当你不信任 Agent 的临场解法时，先让它研究，再把最佳流程固化为 skill，下次直接复用。

Step 5：定义任务契约（Task Contract）

每个任务先写 {TASK}\_CONTRACT.md，明确：

- 必过测试；
- 禁止改测试；
- 必要截图与行为校验；
- 完成定义（Definition of Done）。

这样 Agent 不会在“做了点东西”后提前收工。

Step 6：一合同一会话（Session per Contract）

作者不推荐超长单会话串行做很多事。更优做法：

- 每个 contract 启一个新 session；
- orchestration layer 负责分发与追踪；
- 用 stop-hook 防止未达标提前终止。

这实质是把 Agent 开发从“单次对话”升级为“可运营的任务系统”。

## 四、批判性分析：哪些很有价值，哪些可能被高估？

高价值部分

1.  上下文经济学视角非常关键。模型不是“信息越多越好”，而是“相关信息密度越高越好”。
2.  研究/实现分离是降低幻觉与返工的高收益操作，适合大多数团队。
3.  合同化验收（测试+截图+规则）直接提升可交付性，工程价值极高。
4.  多 Agent 对抗评审在审计类场景（bug、风控、合规）很实用。

可能被夸大的地方

1.  “有价值能力最终都会被基础模型吸收”这点方向上成立，但时间上不确定。企业场景常需要更快交付，不能完全等待官方产品演进。
2.  “极简依赖”不总是最优。在复杂组织里，权限系统、审计日志、合规追踪等往往必须依赖外层平台能力。
3.  多 Agent 打分机制容易引入“伪一致性”。三个 Agent 可能共享同类偏见，彼此强化错误结论。

真实工程中的难点

- 成本控制：多轮研究+多 Agent 评审会抬高 token 与时延；
- 可观测性：没有 trace 与 telemetry，很难定位性能退化原因；
- 规则治理：规则/技能版本化、冲突检测、过期清理都需要流程化；
- 组织协同：人类开发者要学会写 contract，这本身是一项新技能。

## 五、与主流 Agent 系统对比

1）AutoGPT

- 强项：自治探索、多步任务执行。
- 弱项：早期版本常出现目标漂移与不稳定。
- 与本文观点关系：作者的方法更强调约束与收敛，而非开放式自治。

2）OpenDevin

- 强项：把开发环境、执行与反馈闭环化。
- 弱项：在复杂仓库中的长期稳定性仍依赖任务拆分质量。
- 对比：作者路线更“轻平台、重方法”；OpenDevin 更“平台化集成”。

3）Claude Code

- 强项：指令遵循、工程对话、工具调用体验成熟。
- 与本文高度一致：规则路由、分任务会话、合同化交付都易落地。

4）Codex CLI

- 强项：终端集成、脚本化、工程师原生工作流契合。
- 对比：作者强调的“CLI-first + minimal harness”在 Codex CLI 上也成立。

5）多 Agent 系统

- 强项：可编排复杂角色协同与状态流转。
- 风险：系统复杂度上升，调试和维护成本陡增。
- 对比：作者提醒的是“必要复杂度”，不是“架构炫技”。

总结对比： 作者方法不是反平台，而是反“过早平台化”和“盲目复杂化”。先用最小系统稳定产出，再按瓶颈增量升级。

## 六、在此基础上的延伸思考

1）下一代 Agent 工程范式会是什么？

我判断会走向“三层分离”：

- Policy 层：规则、权限、风险边界；
- Orchestration 层：合同调度、会话生命周期、回滚与重试；
- Execution 层：具体模型与工具调用。

届时团队竞争力，不再是“谁会写 prompt”，而是“谁能把这三层做成工程资产”。

2）Agent 会改变软件工程吗？

会，而且已经在变。变化不是“工程师被替代”，而是职责迁移：

- 从“写每行代码”转向“定义问题、约束过程、验收结果”；
- 从“实现者”转向“系统设计者+质量裁判”。

未来的资深工程师，核心能力会是： 任务建模、上下文治理、自动验收设计、异常闭环处理。

3）CLI Agent vs IDE Agent：谁是未来？

两者会并存，但分工会更清晰：

- CLI Agent：适合批处理、自动化流水线、可复现任务、夜间运行；
- IDE Agent：适合交互探索、局部重构、即时反馈。

长期看，CLI 更像“生产线”，IDE 更像“工作台”。 真正的高效团队会把两者接成一条链，而不是二选一。

## 七、工程实践启示（可直接执行）

如果你现在就要提升 Agent 产出稳定性，建议立刻做这 5 件事：

1.  把总规则文件瘦身到“路由目录”形态（不要塞百科全书）；
2.  每个复杂任务先写 contract（测试/截图/验收标准）；
3.  把研究与实现拆开到不同 session；
4.  每周清理一次规则和技能冲突；
5.  先减少 50% 工具依赖，观察质量是否反而提升。

你会发现：很多“模型不行”，其实是“系统没设计好”。

## Agent 工程的本质是“控制复杂性”

这篇帖子的最大贡献，是把“如何用 Agent”从技巧层拉回到工程层。它提醒我们：

- 不要把希望寄托在工具堆叠；
- 要把精力放在上下文控制、任务拆解、验收契约与规则治理上；
- 把 Agent 当团队成员管理，而不是当魔法按钮使用。

当你做到这一点，Agent 不再是“时灵时不灵的黑盒”，而会逐步变成一个可预测、可迭代、可复用的工程系统。那时你会意识到：真正的护城河不是模型名称，而是你构建 Agent 系统的能力。
