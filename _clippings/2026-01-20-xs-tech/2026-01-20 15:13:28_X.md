在这篇文章中，我们将探讨多智能体架构在何时变得必要、我们观察到的四种主要模式，以及 LangChain 如何赋能你有效地构建多智能体系统。

许多代理任务最好由配备设计良好工具的单个代理来处理。你应该从这里开始——单个代理在构建、推理和调试方面都更简单。但随着应用程序的规模扩大，团队会面临一个常见的挑战：他们拥有大量分散的代理能力，希望将这些能力整合到一个统一的界面中。随着他们想要整合的功能数量增加，出现了两个主要的限制：

上下文管理 : 每个能力对应的专业知识无法轻松放在一个提示中。如果上下文窗口是无限的且延迟为零，你可以在一开始就包含所有相关信息。实际上，你需要策略来在代理工作时选择性地呈现信息。

分布式开发：不同团队独立开发和维护各自的功能，边界和所有权明确。单一的整体式代理提示在团队边界之间变得难以管理。

当你需要管理大量领域知识、跨团队协调或处理真正复杂的任务时，这些约束就变得至关重要。在这些情况下，多智能体架构可以成为正确的选择。

最近的 表明多智能体系统在这些场景中表现更好。在 Anthropic 的多智能体研究系统中，以 Claude Opus 4 为主导代理、Claude Sonnet 4 为子代理的多智能体架构，在内部研究评估中比单代理的 Claude Opus 4 表现高出 90.2%。该架构通过独立上下文窗口在代理间分配工作的能力，实现了单代理无法实现的并行推理。

四种架构模式构成了大多数多智能体应用的基础：子智能体、技能、交接和路由器。每种在任务协调、状态管理和顺序解锁方面采用不同的方法。下面我们概述一个框架，用于选择最能满足您最关键约束的架构。

在子代理模式中，监督代理通过将专门的子代理作为工具来调用以进行协调。主代理维护对话上下文，而子代理保持无状态，从而提供强大的上下文隔离。

工作原理 : 主代理决定调用哪些子代理、提供什么输入以及如何整合结果。子代理不记得过去的交互。这种架构提供了集中式控制，所有路由都经过主代理，主代理可以并行调用多个子代理。

最适合: 具有多个不同领域且需要集中式工作流控制，并且子代理无需直接与用户交互的应用。例如协调日历、电子邮件和 CRM 操作的个人助手，或委派任务给专业领域专家的研究系统。

关键权衡点: 每次交互增加一次额外的模型调用，因为结果必须通过主代理返回。这种额外开销提供了集中控制和上下文隔离，但会增加延迟和 token 消耗。

对于希望以最少配置实现这种模式的开发者， 提供了开箱即用的实现，只需几行代码即可添加子代理。

在技能模式中，智能体按需加载专门的提示词和知识。可以看作是智能体能力的渐进式披露。

虽然技能架构技术上采用单个智能体，但它通过让该智能体动态地采用专门角色，具有多智能体系统的特征。这种方法带来与多智能体模式类似的优势——比如分布式开发和细粒度上下文控制——但采用的是更轻量的提示驱动方法，而非管理多个智能体实例。因此，或许颇具争议的是，我们认为技能架构是一种准多智能体架构。

工作原理 : 技能主要是由提示驱动的专业领域，被打包为包含指令、脚本和资源的目录。启动时，代理仅了解技能名称和描述。当某个技能变得相关时，代理会加载其完整上下文。技能内的附加文件提供第三层级的细节，代理仅在需要时才会发现这些细节。

最适合 ：单个智能体拥有多种可能的专长，无需在能力间施加约束的场景，或者团队分配中不同团队掌握不同技能的情况。常见例子包括编码智能体或创意助手。

关键权衡点 : 随着技能加载，上下文会在对话历史中积累，这可能导致后续调用时的 token 膨胀。然而，这种模式在整个过程中提供了简洁性和直接的用户交互。

在交接模式中，主动代理会根据对话上下文动态变化。每个代理都能够通过工具调用转移给其他代理。

工作原理 : 当代理调用交接工具时，它会更新决定下一个要激活的代理的状态。这可能意味着切换到另一个代理，或者更改当前代理的系统提示和可用工具。该状态会在对话轮次中保留，从而实现顺序工作流。

最适合：分阶段收集信息的客户支持流程、多阶段对话体验，或任何需要顺序约束且功能需满足前提条件才解锁的场景。

关键权衡：比其他模式更有状态，需要谨慎的状态管理。但这使得多轮对话更加流畅，上下文在各个阶段之间自然延续。

在路由模式中，路由步骤会对输入进行分类并引导至专门的代理，并行执行查询并综合结果。

它是如何工作的 : 路由器分解查询，并行调用零个或多个专门代理，并将结果整合成连贯的响应。路由器通常是无状态的，独立处理每个请求。

最适合 : 适用于具有不同垂直领域（独立知识领域）、需要同时跨多个来源进行查询的场景，或需要整合多个智能体结果的情况。例如企业知识库和多垂直领域的客户支持助手。

关键权衡 : 无状态设计意味着每个请求的性能一致，但如果需要对话历史会产生重复的路由开销。可通过将路由器封装为有状态对话代理中的工具来缓解。

架构选择直接影响延迟、成本和用户体验。我们分析了三种典型场景，以了解不同模式在实际条件下的表现。

关键见解 : 有状态模式（交接，技能）通过保持上下文，在重复请求时节省 40-50%的调用次数。子代理通过无状态设计保持每次请求的成本一致，以重复调用模型为代价提供强大的上下文隔离。

有用户询问：“比较 Python、JavaScript 和 Rust 在 Web 开发中的应用。”每个语言代理包含约 2000 个 token 的文档。所有模式都能进行并行工具调用。

![Image](https://pbs.twimg.com/media/G-p3SxkXQAAhpkW?format=jpg&name=medium)

关键见解：对于多领域任务，采用并行执行的模式（子代理、路由器）效率最高。技能调用次数较少，但由于上下文积累导致 token 使用量较高。交接必须按顺序执行，无法利用并行工具调用同时咨询多个领域。

[

![Image](https://pbs.twimg.com/media/G-p3Ph5XYAADdZS?format=jpg&name=large)

在这种情况下，Subagents 总体上比 Skills 少处理 67% 的 token，这是由于上下文隔离。每个子代理只处理相关上下文，避免了在将多个技能加载到单个对话中时积累的 token 膨胀。

多智能体系统协调专门组件以处理复杂的工作流程。当你确实需要多智能体能力时，请将你的需求与上述决策框架匹配。对于想要快速起步的团队， 提供开箱即用的实现方案，结合子智能体和技能以支持复杂任务规划。

不过在很多情况下，更简单的架构往往就足够了。从单个智能体和良好的提示词工程开始。先添加工具，再添加智能体。只有当你遇到明显的限制时，才逐步过渡到多智能体模式。
