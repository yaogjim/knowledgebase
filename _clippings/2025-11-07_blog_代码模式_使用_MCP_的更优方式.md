# 代码模式：使用 MCP 的更优方式

## 代码模式：使用 MCP 的更优方式

2025-09-26

9 min read

![](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/6XsnzCDczGdIKX6ddLVYLT/1cad4424f9b90001286b682c7caad683/image1.png)

原来我们一直都用错了 MCP。

目前大多数智能体通过直接向 LLM 暴露“工具”的方式来使用 MCP。

我们尝试了一种不同的方法：将 MCP 工具转换为 TypeScript API，然后让 LLM 编写调用该 API 的代码。

结果令人瞩目：

1.  我们发现，当工具以 TypeScript API 的形式呈现而非直接调用时，智能体能够处理更多工具及更复杂的工具。这可能是因为 LLMs 的训练集中包含了海量真实世界的 TypeScript 代码，而仅包含少量人为设计的工具调用示例。
 
2.  当智能体需要串联多个调用时，这种方法才能真正大放异彩。传统模式下，每次工具调用的输出都必须输入到 LLM 的神经网络中，仅仅是为了复制到下一个调用的输入里，这无疑浪费了时间、精力和计算资源。而当 LLM 能够编写代码时，它就能跳过所有这些步骤，只读取最终需要的结果。
 

简而言之，LLMs 更擅长编写调用 MCP 的代码，而非直接调用 MCP。

## What's MCP?

对于不熟悉的人来说： [模型上下文协议](https://modelcontextprotocol.io/docs/getting-started/intro) 是一种让 AI 智能体能够调用外部工具的标准协议，使其能够直接执行实际工作，而不仅仅是与你对话。

换个角度看，MCP 是一种统一的方式，用于：

- 提供一个用于执行某操作的 API，
 
- 以及 LLM 理解所需的文档，
 
- 授权在带外处理。
 

MCP 在 2025 年掀起巨大波澜，它突然大幅扩展了 AI 智能体的能力范围。

MCP 服务器暴露的“API”表现为一组“工具”。每个工具本质上是一个远程过程调用（RPC）函数——它通过特定参数调用并返回响应。大多数现代 LLM 具备 [使用“工具”的能力（有时称为“函数调用”）](https://developers.cloudflare.com/workers-ai/features/function-calling/) ，这意味着它们经过训练，在需要调用工具时会以特定格式输出文本。调用 LLM 的程序识别该格式后按规范调用工具，并将结果作为输入反馈给 LLM。

### 工具调用的剖析

在底层，LLM 会生成一个代表其输出的“令牌”流。一个令牌可能代表一个单词、一个音节、某种标点符号或文本的其他组成部分。

然而，工具调用涉及一个 *没有* 任何文本对应物的标记。LLM 经过训练（或更常见的是微调）后，能够理解一个特殊标记——当其输出该标记时意味着“后续内容应被解析为工具调用”，以及另一个表示“工具调用结束”的特殊标记。在这两个标记之间，LLM 通常会写入对应某种描述调用的 JSON 消息的标记。

例如，假设您已将智能体连接至提供天气信息的 MCP 服务器，随后询问该智能体德克萨斯州奥斯汀的天气情况。在后台，LLM 可能会生成如下输出。请注意，此处我们使用 `<|` 和 `|>` 中的文字来代表特殊标记，但实际上这些标记并不表示任何文本内容，仅为示意用途。

我将使用天气 MCP 服务器查询德克萨斯州奥斯汀市的天气情况。

```rust
I will use the Weather MCP server to find out the weather in Austin, TX.

<|tool_call|>
{
  "name": "get_current_weather",
  "arguments": {
 "location": "Austin, TX, USA"
  }
}
<|end_tool_call|>
```

当输出中出现这些特殊标记时，LLM 的控制器会将此序列解析为工具调用。检测到结束标记后，控制器将暂停 LLM 的执行，解析 JSON 消息并将其作为结构化 API 结果的独立组件返回。调用 LLM API 的智能体看到工具调用后，会启动相应的 MCP 服务器，再将结果传回 LLM API。随后，LLM 的控制器会使用另一组特殊标记将结果反馈给 LLM：

```rust
<|tool_result|>
{
  "location": "Austin, TX, USA",
  "temperature": 93,
  "unit": "fahrenheit",
  "conditions": "sunny"
}
<|end_tool_result|>
```

LLM 读取这些标记的方式与读取用户输入完全相同——只是用户无法生成这些特殊标记，因此 LLM 知道这是工具调用的结果。随后，LLM 会像往常一样继续生成输出。

不同的 LLM 可能采用不同的工具调用格式，但这是基本思路。

### 这有什么问题吗？

工具调用中使用的特殊标记是 LLM 在现实数据中从未见过的。它们必须基于合成训练数据专门训练才能使用工具，而且在这方面并不总是表现优异。如果向 LLM 提供过多工具或过于复杂的工具，它可能难以选择正确的工具或正确使用它们。因此，我们建议 MCP 服务器设计者提供极度简化的 API，而非传统面向开发者的复杂接口。

与此同时，LLMs 在编写代码方面正变得越来越出色。事实上，当要求 LLMs 针对通常向开发者开放的完整复杂 API 编写代码时，它们似乎并不觉得太困难。那么，为什么 MCP 接口必须“简化”呢？编写代码和调用工具几乎是同一回事，但 LLMs 似乎在一方面比另一方面表现得好得多？

答案很简单：LLMs 见过大量代码，却很少接触“工具调用”。实际上，它们见过的工具调用可能仅限于开发者人为构建的训练集，旨在对其进行训练。而它们早已从数百万开源项目中见识过真实世界的代码。

***让 LLM 通过工具调用来执行任务，就如同让莎士比亚参加一个月的普通话速成班后，要求他用中文写剧本。这注定无法诞生他的巅峰之作。***

### 但 MCP 仍然有用，因为它具有统一性

MCP 专为工具调用而设计，但实际上并非必须如此使用。

MCP 服务器所暴露的“工具”实际上只是附带文档的 RPC 接口。我们并非必须将其呈现为工具形式，而是可以将这些工具转化为编程语言 API。

既然编程语言 API 已经独立存在，我们为何还要这样做呢？几乎每个 MCP 服务器都只是对现有传统 API 的封装——为何不直接开放这些 API 呢？

原来，MCP 还有另一项非常实用的功能： **它提供了一种统一的方式来连接并了解 API。**

AI 智能体可以使用 MCP 服务器，即使该智能体的开发者从未听说过这个特定的 MCP 服务器，而 MCP 服务器的开发者也不了解这个特定的智能体。这种情况在过去传统的 API 中很少出现。通常，客户端开发者总是明确知道他们正在为哪个 API 编写代码。因此，每个 API 在基础连接、授权和文档等方面都可能存在细微差异。

这种一致性即使在 AI 代理编写代码时也很有用。我们希望 AI 代理在沙箱环境中运行，仅能访问我们提供的工具。MCP 通过以标准化方式处理连接和授权（独立于 AI 代码），使得智能体框架能够实现这一目标。我们也不希望 AI 必须去互联网搜索文档；MCP 直接在协议中提供了文档支持。

## 好的，它是如何运作的？

我们已经扩展了 [Cloudflare Agents SDK](https://developers.cloudflare.com/agents/) 以支持这一新模型！

例如，假设你有一个使用 ai-sdk 构建的应用，其外观如下：

```typescript
const stream = streamText({
  model: openai("gpt-5"),
  system: "You are a helpful assistant",
  messages: [
 { role: "user", content: "Write a function that adds two numbers" }
  ],
  tools: {
 // tool definitions 
  }
})
```

您可以将工具和提示封装在代码模式助手中，并在您的应用程序中使用它们：

```typescript
import { codemode } from "agents/codemode/ai";

const {system, tools} = codemode({
  system: "You are a helpful assistant",
  tools: {
 // tool definitions 
  },
  // ...config
})

const stream = streamText({
  model: openai("gpt-5"),
  system,
  tools,
  messages: [
 { role: "user", content: "Write a function that adds two numbers" }
  ]
})
```

随着这一改动，您的应用将开始生成并运行能够直接调用已定义工具（包括 MCP 服务器）的代码。我们将在近期为其他库推出相应版本。 [查阅文档](https://github.com/cloudflare/agents/blob/main/docs/codemode.md) 获取更多详情和示例。

### 将 MCP 转换为 TypeScript

当你在“代码模式”下连接到 MCP 服务器时，Agents SDK 将获取该 MCP 服务器的架构，并将其转换为完整的 TypeScript API，同时根据架构生成文档注释。

例如，连接到位于 [https://gitmcp.io/cloudflare/agents](https://gitmcp.io/cloudflare/agents) 的 MCP 服务器，将生成如下所示的 TypeScript 定义：

```typescript
interface FetchAgentsDocumentationInput {
  [k: string]: unknown;
}
interface FetchAgentsDocumentationOutput {
  [key: string]: any;
}

interface SearchAgentsDocumentationInput {
  /**
 * The search query to find relevant documentation
 */
  query: string;
}
interface SearchAgentsDocumentationOutput {
  [key: string]: any;
}

interface SearchAgentsCodeInput {
  /**
 * The search query to find relevant code files
 */
  query: string;
  /**
 * Page number to retrieve (starting from 1). Each page contains 30
 * results.
 */
  page?: number;
}
interface SearchAgentsCodeOutput {
  [key: string]: any;
}

interface FetchGenericUrlContentInput {
  /**
 * The URL of the document or page to fetch
 */
  url: string;
}
interface FetchGenericUrlContentOutput {
  [key: string]: any;
}

declare const codemode: {
  /**
 * Fetch entire documentation file from GitHub repository:
 * cloudflare/agents. Useful for general questions. Always call
 * this tool first if asked about cloudflare/agents.
 */
  fetch_agents_documentation: (
 input: FetchAgentsDocumentationInput
  ) => Promise<FetchAgentsDocumentationOutput>;

  /**
 * Semantically search within the fetched documentation from
 * GitHub repository: cloudflare/agents. Useful for specific queries.
 */
  search_agents_documentation: (
 input: SearchAgentsDocumentationInput
  ) => Promise<SearchAgentsDocumentationOutput>;

  /**
 * Search for code within the GitHub repository: "cloudflare/agents"
 * using the GitHub Search API (exact match). Returns matching files
 * for you to query further if relevant.
 */
  search_agents_code: (
 input: SearchAgentsCodeInput
  ) => Promise<SearchAgentsCodeOutput>;

  /**
 * Generic tool to fetch content from any absolute URL, respecting
 * robots.txt rules. Use this to retrieve referenced urls (absolute
 * urls) that were mentioned in previously fetched documentation.
 */
  fetch_generic_url_content: (
 input: FetchGenericUrlContentInput
  ) => Promise<FetchGenericUrlContentOutput>;
};
```

随后，这段 TypeScript 代码会被载入智能体的上下文环境。目前，整个 API 会被完整加载，但未来的改进可能让智能体更动态地搜索和浏览 API——就像具备自主编码能力的助手那样。

### 在沙盒环境中运行代码

我们的智能体不再需要面对所有已连接 MCP 服务器的全部工具，而是只需使用一个能够执行 TypeScript 代码的单一工具。

代码随后在一个安全沙箱中执行。该沙箱与互联网完全隔离，其与外部世界的唯一连接是通过代表其所连接 MCP 服务器的 TypeScript API 实现的。

这些 API 通过 RPC 调用实现，该调用会回传至代理循环。在此过程中，Agents SDK 将调用分派至相应的 MCP 服务器。

沙盒代码通过调用 `console.log()` 这一直观方式将结果返回给代理。脚本执行完毕后，所有输出日志都会传回给代理。

![](https://cf-assets.www.cloudflare.com/zkvhlag99gkb/6DRERHP138FSj3GG0QYj3M/99e8c09b352560b7d4547ca299482c27/image2.png)

这种新方法需要访问一个能运行任意代码的安全沙箱。那么，我们该去哪里找呢？必须运行容器吗？成本会不会很高？

不，没有容器。我们有更好的选择：隔离环境。

Cloudflare Workers 平台始终基于 V8 隔离环境，即由 [V8 JavaScript 引擎](https://v8.dev/) 驱动的独立 JavaScript 运行时。

**隔离区比容器轻量得多。** 一个隔离区仅需几毫秒即可启动，且仅占用几兆字节的内存。

隔离区的速度极快，我们可以为代理运行的每段代码都创建一个新的。无需重复使用它们，也无需预先预热。只需按需创建，运行代码，然后丢弃。整个过程如此迅速，以至于开销几乎可以忽略不计；就像直接对代码进行 eval()操作一样，但具备了安全保障。

### Worker Loader API

然而，迄今为止，Worker 仍无法直接加载包含任意代码的隔离环境。所有 Worker 代码都必须通过 Cloudflare API 上传，随后进行全局部署，以便在任何地方运行。但这并非我们对代理程序的期望！我们希望代码能在代理所在的位置直接运行。

为此，我们在 Workers 平台新增了一个 API： [Worker Loader API](https://developers.cloudflare.com/workers/runtime-apis/bindings/worker-loader/) 。通过它，您可以按需加载 Worker 代码。具体示例如下：

```javascript
// Gets the Worker with the given ID, creating it if no such Worker exists yet.
let worker = env.LOADER.get(id, async () => {
  // If the Worker does not already exist, this callback is invoked to fetch
  // its code.

  return {
 compatibilityDate: "2025-06-01",

 // Specify the worker's code (module files).
 mainModule: "foo.js",
 modules: {
 "foo.js":
 "export default {\n" +
 "  fetch(req, env, ctx) { return new Response('Hello'); }\n" +
 "}\n",
 },

 // Specify the dynamic Worker's environment (`env`).
 env: {
 // It can contain basic serializable data types...
 SOME_NUMBER: 123,

 // ... and bindings back to the parent worker's exported RPC
 // interfaces, using the new `ctx.exports` loopback bindings API.
 SOME_RPC_BINDING: ctx.exports.MyBindingImpl({props})
 },

 // Redirect the Worker's `fetch()` and `connect()` to proxy through
 // the parent worker, to monitor or filter all Internet access. You
 // can also block Internet access completely by passing `null`.
 globalOutbound: ctx.exports.OutboundProxy({props}),
  };
});

// Now you can get the Worker's entrypoint and send requests to it.
let defaultEntrypoint = worker.getEntrypoint();
await defaultEntrypoint.fetch("http://example.com");

// You can get non-default entrypoints as well, and specify the
// `ctx.props` value to be delivered to the entrypoint.
let someEntrypoint = worker.getEntrypoint("SomeEntrypointClass", {
  props: {someProp: 123}
});
```

您现在就可以在本地使用 Wrangler 运行 `workerd` 时开始体验这个 API（ [查看文档](https://developers.cloudflare.com/workers/runtime-apis/bindings/worker-loader/) ），也可以 [申请测试资格](https://forms.gle/MoeDxE9wNiqdf8ri9) 以便在生产环境中使用它。

## 工作者是更优的沙盒环境

Workers 的设计使其在沙箱隔离方面表现卓越，尤其适用于此类应用场景，原因如下：

### 更快、更便宜、可随意丢弃的沙盒环境

[Workers 平台采用隔离实例而非容器。](https://developers.cloudflare.com/workers/reference/how-workers-works/) 隔离实例的资源消耗更少且启动速度更快。启动全新隔离实例仅需数毫秒，其资源开销之低使得我们可以为智能体生成的每个代码片段都创建新实例。无需考虑隔离实例的池化复用、预热等问题。

我们尚未最终确定 Worker Loader API 的定价，但由于其基于隔离环境技术，我们将能够以远低于基于容器解决方案的成本提供该服务。

### 默认隔离，但通过绑定连接

工人们更擅长应对隔离环境。

在代码模式下，我们禁止沙盒工作线程访问互联网。全局函数 `fetch()` 和 `connect()` 会抛出错误。

但在大多数平台上，这会成为一个问题。通常在这些平台上，获取私有资源访问权限的方式是：你首先需要具备通用网络访问能力。随后，利用这种网络访问权限向特定服务发送请求，并通过传递某种 API 密钥来获得私有访问授权。

但 Workers 一直有更优的解决方案。在 Workers 中，“环境”（ `env` 对象）不仅包含字符串， [还包含动态对象](https://blog.cloudflare.com/workers-environment-live-object-bindings/) ，也称为“绑定”。这些对象能够直接访问私有资源，无需经过通用网络请求。

在代码模式下，我们为沙箱提供代表其所连接 MCP 服务器的绑定访问权限。因此，智能体能够在不具备通用网络访问权限的情况下， *专门* 访问这些 MCP 服务器。

通过绑定来限制访问比通过网络层过滤或 HTTP 代理等方式要清晰得多。过滤对 LLM 和监管方都很困难，因为边界往往不明确：监管方可能难以准确识别哪些流量是合法访问 API 所必需的。与此同时，LLM 也难以猜测哪些请求会被拦截。而采用绑定方式则界限分明：绑定提供 JavaScript 接口，该接口允许被使用。这种方式显然更优。

### No API keys to leak

绑定的另一个好处是它们能隐藏 API 密钥。绑定本身为 MCP 服务器提供了一个已授权的客户端接口。所有通过它发起的调用都会先经过代理监管器处理，该监管器持有访问令牌，并将这些令牌添加到最终发往 MCP 的请求中。

这意味着人工智能不可能编写出泄露任何密钥的代码，从而解决了当前人工智能编写代码中常见的安全问题。
