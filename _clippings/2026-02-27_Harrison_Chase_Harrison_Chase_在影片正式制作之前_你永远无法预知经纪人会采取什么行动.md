# 在影片正式制作之前，你永远无法预知经纪人会采取什么行动。

将传统软件部署到生产环境时，您对预期结果通常心中有数。用户点击按钮、填写表单、按照预设路径操作。您的测试套件可能覆盖 80-90% 的代码路径，监控工具也会追踪一些常见指标：错误率、响应时间、数据库查询。一旦出现问题，您只需查看堆栈跟踪和日志即可。

智能体的运行方式截然不同。它们接受自然语言输入，而可能的查询空间是无限的。它们由大型语言模型驱动，这些模型能够感知提示语中的细微差别，并能针对相同的输入产生不同的输出。此外，它们通过多步骤推理链、工具调用和检索操作来做出决策，而这些操作在开发过程中很难完全预测。

这意味着，代理的生产环境监控所需的能力与传统可观测性有所不同。在本文中，我们将探讨代理可观测性面临的独特挑战、需要监控的内容，以及我们从大规模部署代理的团队那里获得的经验。

## 

为什么代理与传统软件不同

在与将代理部署到生产环境的团队合作中，我们观察到影响监控方法的两个关键区别。

智能体拥有无限的输入空间

传统软件的输入空间有限且受限。用户通过按钮、下拉菜单、表单和 API 调用等特定格式进行交互。设计结账流程时，您可以精确地了解屏幕顺序和用户可能的操作。由于您可以列举所有故障模式，因此可以制定更全面的错误处理方案。

相比之下，智能体主要接受自然语言作为输入。自然语言没有固定的有效输入集。用户可以用无数种方式表达同一个请求——模糊的或具体的，正式的或随意的，可以在一条消息中组合多个意图，也可以将同一个请求分散到多个对话回合中。

以客服人员为例。在传统软件中，用户会导航至“订单历史记录”，点击某个订单，点击“申请退款”，最后填写一份包含预设选项的表单。这条路径是固定的，并且易于测试。

使用代理时，用户可能会说：

- “我想退货”
 
- “你能帮我把上周买鞋的钱要回来吗？”
 
- “我收到的商品已损坏，我该怎么办？”
 
- “请退款，订单号#12345”

每个输入都代表着相同的潜在意图，但智能体需要理解其中的差异，提取相关信息，并确定相应的操作。 这种无限的输入空间意味着，在真实用户开始与其交互之前，你无法完全预测智能体将如何使用。

LLM 模型对微小变化不够稳健

第二个关键区别在于，LLM 具有快速响应和非确定性行为。即使输入发生微小变化，也可能导致不同的输出，而相同的输入有时也会产生不同的结果。

这种情况的出现有几个原因。LLM 在生成过程中使用概率抽样，这会引入变异性。最重要的是，LLM 对措辞、语境或指令顺序的细微变化会有不同的反应。

这种不确定性意味着你在开发过程中观察到的行为可能与生产环境中发生的情况不符。在测试中可靠运行的提示信息，在你未遇到的极端情况下可能会失效。一个在评估期间能够正确使用工具的代理，有时可能会为措辞略有不同的用户查询选择错误的工具。

## 

代理商的生产监控方式有所不同。

传统的应用性能监控 (APM) 工具侧重于延迟、流量、错误和饱和度等指标。它们跟踪 HTTP 请求、数据库查询和系统资源。这些工具是为结构化、确定性的系统设计的，在这些系统中，所有可能的代码路径都是已知的。

代理可观测性要求监控输入和输出本身，而不仅仅是监控它们周围的系统指标。

监测自然语言交互

当您的代理与用户进行对话时，主要信号就存在于对话本身。您需要捕捉到：

- 完整的提示-响应对 ：不仅包括请求的发生，还包括用户提出的请求以及代理的响应。
 
- 多轮对话情境 ：代理通常会在一次对话中进行多次互动，因此您需要将相关的互动分组在一起。
 
- 智能体轨迹和中间步骤 ：智能体可以采取多步骤路径来达到最终输出，在此过程中，它们会调用工具并推理各种选项。您需要了解轨迹中的每一步，而不仅仅是最终响应。
 

这与传统的日志记录有着本质区别。传统的 Web 请求可以概括为“POST /api/checkout 200 OK 342ms”。而代理交互则是一场自然语言对话，可能包含数十个步骤——状态码无法回答交互是否成功的问题。

大规模人类判断的挑战

自然语言交互通常需要人工判断才能做出恰当的评估。这个回复是否有帮助？代理是否理解了用户的意图？语气是否恰当？它是否检索到了相关信息？

在开发阶段，这尚可管理——您可以手动审核跟踪记录，调整提示信息并不断迭代。但在生产环境中，您可能需要处理成千上万甚至数百万次的交互。人工审核员每小时可以有效地评估 50-100 条跟踪记录，但如果每天有 1000 个请求，那么完全的人工审核将需要每天投入 10-20 小时的人力。这就引出了一个重要问题： 当人工审核无法扩展时，如何将人类智慧应用于生产数据？

我们发现两种互补的方法都有效。

用于结构化人工审核的标注队列

标注队列有助于最大限度地提高人工审核效率。标注队列无需审核人员在生产日志中查找数据，而是以结构化的格式呈现特定运行情况，并遵循预定义的评分标准。

一个高效的标注队列系统可以让你：

- 针对特定路径的跟踪进行审查 ：与其审查所有内容，不如将特定子集发送到队列中（例如，包含负面反馈的运行、高成本交互或来自特定时间窗口的查询）。
 
- 明确评审标准 ：制定评审细则，以便评审人员确切地知道要评估哪些方面（相关性、正确性、语气、安全性）。
 
- 实现团队协作 ：多个审阅者可以处理队列，并可跟踪进度和分配角色。
 
- 建立反馈循环 ：审核后的数据可以添加更正注释并添加到评估数据集中。

![Image](https://pbs.twimg.com/media/HCGu6K4bMAABHU4?format=jpg&name=medium)


](/hwchase17/article/2027094058330656814/media/2027093621670096896)

当您试图了解新的故障模式、为评估人员构建训练数据或获取有关特定查询的领域专家反馈时，标注队列尤其有价值。

需要考虑的权衡因素：标注队列需要审阅者投入专门的时间，并且可能会延长改进周期。我们发现，与其试图全面覆盖，不如专注于特定的高价值轨迹，这样效果最佳。

法学硕士作为人类判断的替代指标

第二种方法是利用逻辑逻辑模型本身来衡量人类的判断能力。虽然逻辑逻辑模型并非完美的评估工具，但它们能够以人类无法企及的规模评估许多质量维度。

具体来说，您可以进行配置

[在线评估者](https://docs.langchain.com/langsmith/evaluation-concepts#online-evaluations)

在生产流量上自动运行，可以针对所有运行或抽样子集进行运行。这些评估器可以检查：

- 无参考质量指标 ：诸如连贯性和语调等无需真实答案的属性
 
- 安全与合规 ：回复是否包含敏感信息、违反政策或表现出有害行为
 
- 格式验证 ：输出是否符合预期结构或包含必需元素
 
- 主题分类 ：用户提出的请求属于哪些类别
 

语言学习管理系统（LLM）能够以远超人工审核的规模评估自然语言 。人工审核可能一次只能审核几十条文本痕迹，而 LLM 评估器可以评估数千条，标记潜在问题并提供汇总指标。

然而， 基于 LLM 的评估也引入了自身的成本和限制 ：

- 延迟 ：评估人员可能会在每个跟踪过程中增加几秒钟的延迟，这对于异步批量评估来说或许可以接受，但对于同步用户反馈来说则不可接受。
 
- 成本 ：评估所有流量轨迹会增加推理成本，因此我们通常建议对 10-20% 的流量进行抽样。
 
- 准确性 ：现成的评估工具可能无法反映“好”对您的特定应用意味着什么。通常需要定制与您的用例相匹配的基于 LLM 的评估工具，但要确保它们与人类判断一致也可能很困难。我们构建了
 
 [对齐评估](https://blog.langchain.com/introducing-align-evals/)
 
 帮助团队验证其自定义评估器是否已根据人类标签进行校准，然后再大规模信任它们。
 
- 评估偏差 ：随着生产流量的变化，评估工具可能需要重新调整或更换。
 

基于这些原因，我们建议将自动化评估与定期的人工审核相结合，而不是仅仅依赖 LLM 评估人员。

## 

生产代理可观测性工具

为代理构建有效的生产可观测性需要一系列特定的功能，而大多数通用监控工具并非旨在提供这些功能。基于我们在数十个生产部署中观察到的模式，我们构建了以下功能

[朗史密斯](https://smith.langchain.com/)

。

Insights Agent：发现使用情况和错误模式

生产中最具挑战性的方面之一就是了解用户如何使用你的代理。

当我们分析各个团队如何使用生产跟踪数据时，我们发现他们需要一种方法来自动发现模式，而无需预先指定要查找的内容。这促使我们构建了……

[洞察代理](https://docs.langchain.com/langsmith/insights)

它使用自动聚类系统，将相似的痕迹分组以进行识别：

- 使用模式 ：用户最常提出的请求类型是什么？他们试图使用哪些功能或特性？
 
- 错误模式 ：代理在哪些方面出错？是否存在常见的故障模式，例如工具选择错误、检索失败或误解用户意图？
 
- 特殊情况 ：用户发送了哪些您未预料到的意外查询？
 

[

![Image](https://pbs.twimg.com/media/HCGu9WeagAAB9tQ?format=jpg&name=medium)

Insights Agent 可以配置为按使用模式、故障模式或特定于您领域的自定义属性对跟踪数据进行分组。您还可以将分析结果筛选到特定子集（时间窗口、用户群组、功能区域），并保存配置以便重复分析。

例如，一家拥有嵌入式副驾驶系统的公司的一位产品经理可能会问：“用户最常使用副驾驶系统来执行我们产品的哪些操作？” Insights Agent 可以分析数千条跟踪记录，按意图对其进行分组，并找出使用频率最高的类别。

调试质量问题的工程师可能会问：“我的代理在哪里选择了错误的工具？” Insights Agent 可以识别工具选择失败的常见模式，并提供代表性示例。

这种自动化模式发现有助于使大量的生产跟踪信息更易于管理和操作。

在线评估：持续质量监控

我们提到过

[在线评价](https://docs.langchain.com/langsmith/evaluation#online-evaluation-flow)

早些时候，人们将其作为一种衡量人类判断力的方法。让我们来看看它们在实践中是如何运作的。

通过在线评估，您可以设置评估程序，使其在生产跟踪数据上自动运行。您可以配置：

- 要评估哪些痕迹 ：所有痕迹、抽样百分比（通常为 10-20%）或特定的筛选子集
 
- 评估内容 ：质量指标、安全检查、格式验证或自定义标准
 
- 何时发出警报 ：指标下降时触发通知的阈值
 

在线评估除了传统的“测试”之外，还有以下几个用途：

- 质量监控 ：您可以跟踪代理在一段时间内生成有用、相关且正确回复的频率。这使您能够检测到由于模型更新、数据漂移或新的用户模式而导致的质量下降。
 
- 主题标签 ：您可以自动将生产环境中的查询分类到不同的类别中，以便进行产品分析。这样，您就可以了解用户实际想要完成的任务。
 
- 轨迹评估 ：对于使用多种工具或推理步骤的智能体，您可以评估智能体是否采取了合适的路径来找到答案。它是否以合理的顺序调用了正确的工具？它是否检索了相关信息？
 
- 安全保障 ：您可以实时检查输出中的敏感信息、策略违规或其他安全问题。

能够在生产流量上持续运行评估，从而实现开发工作流程，您可以深入研究特定的故障跟踪，将其添加到注释队列以供人工审查，将其纳入评估数据集，并在重新部署之前测试修复程序。

仪表盘和警报：监控关键信息

最后，生产环境可观测性需要仪表盘和针对特定用例重要指标的告警机制。有效的可观测性平台提供：

- 自定义仪表盘提供特定领域的洞察，使您能够跟踪不同工作流程的成功指标（例如任务完成率或用户满意度评分）。您还可以比较不同模型版本之间的性能，并按功能区域监控成本和延迟。
 
- 当指标超过阈值时，通过 Webhook 或 PagerDuty 发出灵活的警报
 
- 从汇总指标向下钻取到特定轨迹的功能

生产环境可观测性要求跟踪与代理实际行为相关的特定指标。除了标准的延迟和错误率之外，这意味着还要监控工具调用失败率和每个工具的运行次数等指标。这些信号可以告诉你代理是否真正按预期工作，而不仅仅是系统是否在运行。

关键在于监控业务关键指标，而不仅仅是技术指标。没错，延迟和错误率固然重要，但用户满意度以及代理是否用于预期用途等指标也同样重要。

## 

为什么通用工具会不足

此时你可能会想：我难道不能用像 Datadog 或 New Relic 这样的传统可观测性工具来构建这个吗？为什么我需要一个专门的平台？

许多团队最初尝试使用传统的应用性能管理 (APM) 工具来监控代理。我们发现，这种方法对于基本指标（例如延迟、错误率）有效，但在处理特定代理需求时存在局限性。这些局限性主要体现在三个方面：有效负载、连接性和用户。

有效载荷：自然语言数据

传统的应用性能管理 (APM) 工具针对结构化日志和数值指标进行了优化。当需要存储、搜索和分析包含多轮上下文的完整对话线程时，就会遇到不同的需求：

- 存储规模 ：生产规模下的完整提示-响应对需要大量的存储空间。您需要对提示进行语义搜索，而不仅仅是关键词匹配。此外，您还需要保留完整的上下文，包括系统消息和少量示例。
 
- 数据模型 ：维护对话线程和状态需要与传统跟踪不同的数据结构。
 

我们看到一些团队基于 APM 工具构建了此功能，但这需要大量的定制开发。

连接性：与开发循环的集成

代理的可观测性与代理开发工作流程紧密相关，在这个工作流程中，您需要不断地在生产监控、评估数据集、实验和重新部署之间移动数据。循环过程如下：

1.  生产跟踪揭示了故障案例或极端案例。
 
2.  注释队列允许您查看和标注它们
 
3.  数据集包含了这些用于测试的示例。
 
4.  实验检验了修复措施是否能改善行为
 
5.  在线评估验证了生产环境中的修复方案。
 

这需要将可观测性平台、评估框架和开发工具紧密集成。与传统的可观测性工具不同，LangSmith 提供了这种连接性。您可以点击一个失败的生产环境跟踪并立即将其添加到数据集，在测试环境中修改提示信息，运行实验比较新旧版本，并充满信心地重新部署。

用户：跨职能团队

最后，需要访问代理可观测性的人员与通常使用 APM 工具的人员有所不同。传统的可观测性主要面向 SRE 和 DevOps 团队，他们专注于改善系统健康状况、性能退化和基础设施问题。

智能体可观测性适用于跨职能团队，包括：

- AI/ML 工程师调试提示问题和模型行为
 
- 产品经理了解使用模式和功能需求
 
- 领域专家（SME） 审查专业领域的准确性和质量
 
- 数据科学家分析模式并构建评估

我们观察到，代理的可观测性对于这些团队如何协作改善用户体验至关重要。他们定期审查生产环境中的跟踪数据，讨论其中的模式，并根据观察到的情况确定优先级。

这需要一个专为这些角色之间的协作而设计的界面和工作流程，而不仅仅是为基础设施工程师而设计的。

## 

开放性挑战

虽然我们所描述的方法已被证明对大规模部署代理的团队有效，但仍然存在重大挑战：

- 评估器的准确性和可靠性 ：随着模型的改进，LLM 评估器也在不断改进，但它们并非完美无缺。了解何时应该信任自动化评估，何时应该信任人工评估至关重要。
 
 [需要人工审核](https://www.langchain.com/articles/ai-observability)
 
 仍取决于具体情况。
 
- 规模化成本 ：对大批量生产系统进行全面监控成本高昂。如何平衡抽样、自动化评估和人工审核是一项持续优化的工作。
 
- 隐私和合规性 ：在遵守隐私限制和妥善处理敏感数据的同时捕获完整的响应对，会增加可观测性基础设施的复杂性。
 

##

智能体与传统软件的运行方式截然不同。它们接受自然语言输入，表现出非确定性行为，并通过复杂的推理链做出决策。这些特性使得生产监控的重点从系统指标转移到实际的输入和输出本身。
