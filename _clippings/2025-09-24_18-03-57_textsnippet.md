# 让大语言模型（LLM）自己编写提示

***

### **内容摘要**

#### **引言：提示工程的双重困境**

讲者以计算机领域的名言“有些人遇到问题时，会想‘我知道了，用正则表达式吧’。于是他们就有了两个问题”为引子，将其引申到当前的人工智能领域，指出“提示工程（Prompting）”也面临同样的困境：它既是解决问题的强大工具，也可能引入新的复杂性。

#### **提示工程的“礼物”与“诅咒”**

*   **礼物（优点）**：提示工程极大地降低了与大语言模型（LLM）交互的门槛。任何人，特别是领域专家，都可以快速、轻松地用自然语言描述任务，并且这些提示本身具有自文档化的特性。
*   **诅咒（缺点）**：提示是脆弱且难以维护的。它们在不同模型上表现各异，容易随着需求增加而变成一堆处理边缘情况的补丁集合，并且将指令、上下文、格式要求等多个组件混杂在一个不透明的字符串中，难以管理和迭代。

#### **解决方案：引入DSPy框架**

为了解决提示工程的痛点，讲者介绍了DSPy框架。其核心思想是“将任务与大语言模型解耦”，把提示工程转变为一种更结构化、可重复和可优化的编程范式。这使得开发者可以专注于定义任务本身，而不是手动调整和维护冗长的提示字符串。

#### **DSPy的核心机制与优势**

*   **编写任务而非提示**：通过定义“签名”（Signatures），开发者只需明确任务的输入和输出字段，而无需手写具体的提示。
*   **自动优化**：DSPy利用优化器（如MIPROv2），结合评估数据集，让大语言模型（LLM）自己生成、测试并迭代出最优的提示指令和示例（Few-shot examples）。
*   **模型可移植性**：由于任务定义与具体提示解耦，开发者可以轻松更换底层的大语言模型，只需重新运行优化过程，DSPy就能为新模型生成最合适的提示，实现了“一次编写，到处优化”。

#### **实践案例与成果**

讲者以Overture Maps地理空间数据“融合”（Conflation）任务为例，展示了DSPy的强大效果。通过仅约14行代码定义任务，DSPy不仅自动生成了约700个词元（token）的高质量复杂提示，还将模型在评估集上的准确率从60.7%提升至82.0%。更进一步，当更换不同的模型（如从Qwen-0.6B换到Phi-4-Mini-3.8B）时，无需修改代码，准确率能进一步提升至95.0%，证明了其高效和未来适应性。

### **各部分详细内容**

#### **从“正则表达式”到“提示工程”的共同难题**

演讲者Drew Breunig在开场时，引用了Jamie Zawinsky一句关于正则表达式的经典名言：“当一些人面对一个问题时，他们会想‘我知道了，我可以用正则表达式来解决’。于是，他们就有了两个问题。” 讲者认为，在过去一年半的时间里，这个道理同样适用于人工智能领域的提示工程。

他生动地将这句名言改编为：“当一些人面对一个问题时，他们会想‘我知道了，我可以用提示工程（Prompting）来解决’。于是，他们就有了两个问题。” 这点出了本次演讲的核心议题：提示工程虽然强大，但其脆弱、难以维护的特性，尤其是在复杂的AI流程中，会带来新的、更棘手的问题。

#### **提示工程：既是礼物，也是诅咒**

讲者将提示工程形容为一把双刃剑，它既是“礼物”，也是“诅咒”。

*   **作为礼物，提示的优点显而易见**：
    1.  **易于上手**：任何人，尤其是那些不具备编程背景的领域专家，都可以用自然语言描述程序功能和任务。
    2.  **快速编写**：创建提示的过程非常迅速和简单，极大地加速了原型开发。
    3.  **自文档化**：提示本身就是对程序意图的描述，阅读提示就能大致理解程序的功能。

*   **但作为诅咒，提示的缺点同样致命**：
    1.  **模型依赖性强**：同一套提示在不同的模型上表现可能天差地别，更换模型往往意味着需要重写提示。
    2.  **难以维护**：随着时间的推移，为了处理各种边缘情况，提示会变得越来越长，最终成为一个庞大且难以管理的补丁集合。
    3.  **结构混杂**：一个提示通常将任务描述、指令、上下文信息、 few-shot示例和格式要求等多种元素全部混杂在一个不透明的字符串里，这让维护和调试变得异常困难。

讲者通过一个来自OpenAI的SWE-Bench提示示例进行了说明。这个长达1806个词元（token）的提示，虽然功能强大，但在代码中只是一个巨大的、无法结构化理解的文本块。他将其分解为任务（1%）、思维链指令（19%）、详细上下文与指令（39%）、工具定义（5%）、格式化指令（32%）等多个组成部分，直观地展示了其内部的复杂性和维护的挑战。

#### **DSPy：将提示工程转变为结构化编程**

为了应对上述挑战，讲者隆重推出了解决方案——DSPy框架。DSPy的核心理念是将开发者的任务与具体的大语言模型（LLM）进行解耦，让开发者回归到编程的本质。

DSPy实现了功能化、结构化和面向未来的开发范式，它让开发者能够将任务定义为一种“契约”，并由框架来管理底层的提示策略、优化和模型交互。其优势主要体现在三个方面：

1.  **编写任务，而非提示**：开发者通过“签名”（Signatures）来定义任务。这就像定义函数一样，只需明确规定输入的字段和类型，以及期望输出的字段和类型。例如，一个简单的签名可以是`'question -> answer'`，或者更复杂的带有类型的`'baseball_player -> is_pitcher: bool'`。开发者无需关心这些字段如何被组织成一个有效的提示。

2.  **自动优化函数（任务）**：DSPy提供了一个强大的优化器（Optimizer），比如MIPROv2。这个优化器可以做到：
    *   **生成示例**：基于你的数据集，运行几次程序以生成高质量的输入输出对作为few-shot示例。
    *   **生成指令**：将你的程序描述、生成的示例和一些通用的提示技巧，输入给一个强大的“教师模型”（如GPT-4），让它为你编写一系列候选的指令。
    *   **测试与组合**：在小批量数据上随机测试不同的指令和示例组合，最终找到表现最好的组合，形成最优的提示。

3.  **拥抱模型可移植性**：由于任务的定义（签名）和提示的生成（优化器）是分开的，当出现一个更新、更好、更便宜的模型时，开发者可以轻松地将任务移植过去。只需更换模型配置，然后重新运行优化器，DSPy就能为新模型量身定制一套最优的提示，而无需修改任何核心的任务代码。

#### **实践案例：利用DSPy优化地理信息“融合”任务**

讲者以他目前参与的Overture Maps Foundation项目为例进行了实战演示。该项目旨在创建一个免费、开放的全球地理空间基础数据层，其中一个核心挑战是“融合”（Conflation）——即合并来自Meta、微软等多个来源的兴趣点（POI）数据，判断它们是否指向同一个现实世界的实体。这是一个典型的、充满人类创造的“脏数据”的难题。

他展示了如何使用DSPy来解决这个问题：

1. **定义签名类**：他创建了一个`PlaceMatcher`签名，输入是两个地点对象（`place_one`和`place_two`），每个对象都有地址和名称。输出则是一个布尔值的`match`字段（判断是否匹配）和一个表示置信度的`match_confidence`字段（分为“低”、“中”、“高”三档）。通过这种方式，他将模糊的匹配问题变成了一个结构化的编程任务。

2. **运行优化器**：他配置了MIPROv2优化器，使用一个强大的模型（GPT-4.1）作为“教师模型”来生成和优化提示，同时使用一个更小、更经济的模型（如Qwen 3 0.6B）作为最终执行任务的“学生模型”。

3. **显著的成果**：

   *   **性能飞跃**：仅通过优化，Qwen模型在评估集上的准确率就从**60.7%**大幅提升到了**82.0%**。
   *   **轻松切换模型**：当他将“学生模型”更换为Llama 3 2.1B时，准确率从84.0%提升至91.0%；更换为Phi-4-Mini 3.8B时，准确率更是从86.0%飙升至**95.0%**。整个过程中，他几乎没有修改任何代码，只是更换了模型名称并重新运行了优化流程。

   

   

   

   

   # 让大语言模型（LLM）自己编写提示**

   #### **一个程序员的老笑话，一个AI时代的新问题**

   在数据和AI的世界里，我们经常会遇到一个经典的程序员笑话，它出自Jamie Zawinsky之口，流传甚广：

   > “有些人，当他们遇到一个问题时，会想：‘我知道了，我可以用正则表达式来解决。’于是，他们就有了两个问题。”

   在过去的一年半里，我越来越发现，这个笑话完美地映射到了我们今天所处的AI时代。我们只需要把“正则表达式”换成“提示工程”，这个笑话就变得异常贴切：

   > “有些人，当他们遇到一个问题时，会想：‘我知道了，我可以用提示工程（Prompting）来解决。’于是，他们就有了两个问题。”

   这正是我们今天要探讨的核心。

   ### **提示工程的礼物与诅咒**

   提示工程（Prompting）是大语言模型（LLM）在过去几年取得巨大成功并被广泛接纳的关键因素之一。它是一份“礼物”，也是一个“诅咒”。

   幻灯片上用一个生动的对比图展示了这一点：左边是笑脸表情符号下的 **“提示的优点 (Prompts are Great!)”**，右边是惊恐表情符号下的 **“提示的缺点 (Prompts are Terrible!)”**。

   **🎁 提示是伟大的礼物，因为：**

   *   **任何人都能描述任务**：它极大地降低了技术门槛，使得领域专家无需编写复杂的代码，就能描述程序的功能和任务。
   *   **编写快速简单**：提示可以被快速、轻松地写出来，极大地加速了从想法到原型的过程。
   *   **程序即文档**：提示本身就是对功能的描述，具有天然的“自文档化”特性。

   **😱 提示也是可怕的诅咒，因为：**

   *   **模型表现各异**：同一段提示在不同的模型上表现可能天差地别。更换模型往往意味着大量的重写工作。
   *   **沦为边缘情况的集合**：随着业务逻辑的复杂化，提示会不断膨胀，最终变成一堆为了处理各种边缘情况而打上的“补丁”，难以维护。
   *   **组件混杂**：一个提示通常将**指令、上下文、示例、格式要求**等多种组件全部混杂在一个不透明的字符串里，这让维护和迭代变得异常困难。

   #### **可视化一个“糟糕”的提示**

   为了让大家更直观地理解这个问题，我们来看一个来自OpenAI GPT-4.1提示指南中的例子，这是一个用于SWE-Bench（软件工程基准测试）的提示，它长达1806个词元（大约9000个字符）。

   

   这张图清晰地展示了这个庞大提示的构成：

   *   **任务本身 (The Task)**：只占了 **1%**。
   *   **思维链指令 (Chain-of-Thought Instructions)**：占了 **19%**。
   *   **详细上下文与指令 (Detailed Context & Instructions)**：这是最大头，占了 **39%**。
   *   **工具定义 (Tool Definitions)**：占了 **5%**。
   *   **格式化指令 (Formatting Instructions)**：同样是重要部分，占了 **32%**。
   *   **其他 (Other)**：占了 **4%**。

   当这个庞然大物被硬编码在你的代码里时，它看起来就是下面这样——一个巨大的、难以阅读和维护的文本块。

   ```python
   oai_prompt = """
   You will be tasked to fix an issue from an open-source repository.
   
   Your thinking should be thorough and so it's fine if it's very long. You can think step by step
   and after each action you decide to take.
   
   You MUST iterate and keep going until the problem is solved.
   ...
   ... (此处省略数百行)
   ...
   ## High-Level Problem Solving Strategy
   1. Understand the problem deeply. Carefully read the issue and think critically about what is required.
   2. Investigate the codebase. Explore relevant files, search for key functions, and gather context.
   ...
   """```
   
   这显然不是一个理想的工程实践。
   
   ### **解决方案：进入DSPy的世界——将提示转为编程**
   
   为了解决这个困境，我们需要一种新的范式，一种能将“提示工程”转变为“编程”的框架。这就是 **DSPy**。
   
   DSPy的核心思想是：**将你的任务与大语言模型（LLM）解耦**。
   
   
   
   它通过提供一种**功能化（Functional）、结构化（Structured）且面向未来（Future-Proof）** 的方法，让你能够：
   
   1.  **编写任务，而非提示 (Write Tasks, Not Prompts)**
       *   你只需通过“签名”（Signature）来定义任务的输入和输出字段，而不是编写脆弱的、长篇大论的提示字符串。
   
   2.  **优化你的函数 (Optimize Your Function)**
       *   利用各种优化算法，持续地改进你的提示和权重，以达到最佳性能。
   
   3.  **拥抱模型可移植性 (Embrace Model Portability)**
       *   当新的、更强的模型出现时，你可以快速地将你的函数移植过去，并针对新模型进行优化，而无需重写所有逻辑。
   
   #### **DSPy的“Hello World”**
   
   用DSPy上手非常简单。下面是一个基础的“Hello World”示例：
   
   ```python
   import dspy
   
   # 1. 连接到你的大语言模型
   lm = dspy.LM('openai/gpt-4o-mini', api_key='YOUR_OPENAI_API_KEY')
   dspy.configure(lm=lm)
   
   # 2. 定义一个模块（Predict）并为其分配一个签名
   # 签名定义了任务的输入（question）和输出（answer）
   qa = dspy.Predict('question -> answer')
   
   # 3. 运行模块
   response = qa(question="Why is the sky blue?")
   print(response.answer)
   ```

   在这背后，DSPy为你做了什么？它根据你的签名`'question -> answer'`和`Predict`模块，自动生成了一个结构化的系统提示（System Prompt），告诉模型输入和输出字段是什么，以及如何格式化它们。

   

   更酷的是，如果你只是简单地将`Predict`模块换成`ChainOfThought`模块，DSPy会自动生成一个支持思维链推理的、更复杂的提示，而你的签名`'question -> answer'`完全不需要改变！

   #### **MIPROv2：让LLM成为你的提示工程师**

   DSPy最神奇的地方在于它的优化器，其中一个强大的工具是**MIPROv2**。它的核心理念是：**让LLM自己编写提示，然后让它们为结果负责。**

   

   这个过程分为三步：

   1.  **生成示例 (Generate Examples)**：
       运行你的程序几次，从你的数据集中生成一些高质量的输入/输出对（即 few-shot examples）。
   2.  **生成指令 (Generate Instructions)**：
       将你的程序描述、生成的示例以及一些提示技巧，喂给一个强大的“教师”LLM（比如GPT-4），让它为你生成多个候选的指令版本。
   3.  **测试多种组合 (Test Many Combinations)**：
       随机地在小批量数据上测试不同的指令和示例组合，然后将表现最好的组合起来，形成最终的优化后提示。

   ### **实战：用DSPy解决地图数据融合难题**

   接下来，我们看一个真实的案例。我目前在为**Overture Maps Foundation**工作，这是一个由AWS、Meta、微软和TomTom联合发起的项目，旨在创建一个免费、开放的全球地理空间数据层。

   这个项目面临的一个核心挑战是“融合”（Conflation）。我们需要合并来自不同来源（如Meta和微软）的兴趣点（POI）数据，比如判断两个地址和名称略有不同的“星巴克”记录是否指向同一家咖啡店。

   

   这是一个非常棘手的问题，因为这些数据都是由人类创建的，充满了各种不一致性：

   *   **糟糕的数据录入**：比如“Walmart”可能会有无数种拼写方式。
   *   **相似的区域名称**：在亚特兰大，有大约300个地方的名字里都包含“Peachtree”。
   *   **错误的地址/地理编码**：地址格式 notoriously difficult and inconsistent, and pins can be dozens of meters away from the actual location.

   这个问题非常适合用LLM来解决，但由于数据量巨大（约7000万个兴趣点），我们不可能为每一次比较都调用一次LLM。因此，我们构建了一个多阶段的复合AI流水线。

   #### **用DSPy定义融合任务**

   在DSPy中，我们可以优雅地定义这个任务。

   1. **定义数据结构**：首先，我们用一个简单的类来定义“地点”（Place）的数据结构。

   2. **定义签名类**：然后，我们创建一个`PlaceMatcher`签名类，它清晰地定义了任务的输入和输出。

      ```python
      class Place(BaseModel):
          address: str = dspy.InputField()
          name: str = dspy.InputField()
      
      class PlaceMatcher(dspy.Signature):
          """Determine if two points of interest refer to the same place."""
          
          place_one: Place = dspy.InputField()
          place_two: Place = dspy.InputField()
          
          match: bool = dspy.OutputField(desc="Do the two places refer to the same place?")
          match_confidence: Literal["low", "medium", "high"] = dspy.OutputField()
      
      # 将签名与一个Predict模块绑定
      matcher = dspy.Predict(PlaceMatcher)
      ```    这段代码不仅定义了任务，还通过`desc`参数给输出字段添加了描述，这些都会被DSPy用来生成更精准的提示。
      ```

   #### **优化与惊人结果**

   有了定义好的任务和评估数据集，我们就可以启动优化流程了。

   ```python
   # ...（前面的定义）
   
   # 定义验证函数（Metric）
   def validate_match(example, pred, trace=None):
       return example.match == pred.match
   
   # 设置优化器
   tp = dspy.MIPROv2(metric=validate_match, auto="light", 
                     prompt_model=prompt_lm, task_model=lm)
                     
   # 编译（优化）我们的matcher
   optimized_matcher = tp.compile(matcher, trainset=trainset)
   
   # 保存优化后的结果
   optimized_matcher.save("optimized_matcher_full_light.json")
   ```

   结果如何？

   *   **性能提升**：对于一个小型模型 Qwen 3 (0.6B)，优化后的准确率从 **60.7%** 提升到了 **82.0%**。
   *   **代码简洁**：我们只用了**14行代码**就管理了一个最终生成出来的、长达**约700个词元**的复杂提示。
   *   **可读性与可追溯性**：代码清晰易读，并且优化后的提示可以被保存、版本化、追踪和加载，这对于团队协作至关重要。

   #### **轻松切换模型，性能更上一层楼**

   DSPy最大的魅力在于其模型可移植性。当新的、更优秀的模型问世时，我们无需重写代码，只需更换模型，重新运行优化即可。

   

   我们用同样的MIPRO优化器和训练数据集，在不同的模型上进行了测试：
