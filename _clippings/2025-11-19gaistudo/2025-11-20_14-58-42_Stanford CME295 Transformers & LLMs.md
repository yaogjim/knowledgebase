# Stanford CME295 Transformers & LLMs | Autumn 2025 | Lecture 7 - Agentic LLMs

YouTube 视频地址: https://www.youtube.com/watch?v=h-7S6HNq0Vg

## 引言与回顾

大家好，欢迎来到 CME 295 的第七讲。今天我们将重点讨论实用的技术，让我们的 LLM（大语言模型）能够与外部世界及其他系统进行交互。因为直到现在，我们的 LLM 还是完全独立的。我们已经训练了它，也看到了它是如何在数学和编程问题上进行推理的。现在我们想做的是在其他系统的上下文中使用我们的 LLM。

今天的课程将重点介绍你们可能听说过的 RAG（检索增强生成）、工具调用（Tool Calling）和智能体（Agents）。

但在开始之前，照例我要回顾一下上次的内容。如果大家还记得的话，上次我们专注于推理模型，并探讨了推理模型与我们所说的“原生 LLM”之间的区别。特别是直到倒数第二讲之前，我们看到的都是给 LLM 一个提示词（Prompt），它直接给出一个回答。但上次我们看到，如果让 LLM 在输出回答之前先进行推理，那么在数学和编程等推理任务上的表现会有所提升。

具体来说，推理模型将提示词作为输入，输出一个通常对用户隐藏的推理链（Reasoning Chain），然后再输出回答。以此为基础，我们看到了如何训练一个模型使其更具推理能力。特别地，我们介绍了一种核心的强化学习算法，叫做 GRPO（Group Relative Policy Optimization，组相对策略优化）。

我们看到这种算法与之前的算法相比有一些不同之处。一个显著的特点是它不训练价值函数（Value Function）。GRPO 的训练过程是这样的：它接受一个查询作为输入，然后通过计算同一提示词的不同补全（Completion）的奖励，并计算一个相对于该组其他奖励的优势（Advantage）值，来计算每个输出的优势。

我们还看到，如果应用 GRPO 并精心选择奖励——即奖励模型输出推理链，以及奖励模型生成好的回答——随着强化学习训练的进行，模型在这些推理任务上的表现会有所提高。我们看的一个任务是数学问题，比如在 AIM 数据集上的表现。我们观察到虽然性能最终趋于平稳，但输出长度却在持续增加。

这让我们回到了 GRPO 使用的损失函数公式，并意识到其中有一项会导致 Token 在短回答或长回答中的贡献不同。这种现象称为“长度偏差（Length Bias）”。我们看到了一些最近的论文探索的缓解策略，比如 DAPO（使用了不依赖于 Token 所在句子的归一化因子）以及“GRPO Done Right”这篇论文（实际上只是移除了归一化项）。

这是上次的内容。上次我们在开始推理课程之前，列举了原生 LLM 的优点和缺点。上一讲主要集中在如何改善原生 LLM 有限的推理能力。而在这一讲中，我们将做两件事：第一，看看如何将我们的 LLM 连接到不断更新的知识库，特别是如何获取最新信息；第二，看看 LLM 如何帮助我们执行动作，这部分将由 Shervin 来讲，内容包括工具调用和智能体工作流。

## RAG：检索增强生成 (Retrieval Augmented Generation)

让我们从第一个方法开始，也就是大家可能听说过的 RAG。

假设你训练了一个模型，但问题是你的模型预训练数据截止到一个前。假设你想向模型询问几周前发生的选举的获胜者。你的模型将无法回答你，或者会输出错误的答案，因为直到现在，我们的 LLM 没有任何与外部来源的链接。它只依赖于训练期间获得的知识。因此，它给出的回答只能基于截至截止日期之前的数据。

这是一个很大的限制：我们的 LLM 只知道它被训练过的事情。你会发现外面所有的模型，比如 OpenAI 的 GPT-5，如果你看它们的模型卡片（Model Cards），总是写着某个知识截止日期。例如 GPT-5 的知识截止日期是 2024 年 9 月 30 日。这意味着如果你很天真地问它在那之后发生的任何事情，基础模型本身是无法回答的。

你可能会问，为什么不直接用之后发生的数据继续训练模型呢？这样做有几个问题。首先，在不导致其他方面退化的情况下改变 LLM 的知识是非常棘手的。人们通常尽量避免这样做。其次，这不太实用，因为你可能有许多需要微调模型的用例。如果你为了注入知识而更新模型权重，你必须为你所有的用例都这样做，这会增加大量的开销和维护成本。所以人们通常不倾向于通过额外训练来注入知识。

另一个想法可能是把截止日期之后发生的所有事情都添加到提示词（Prompt）中，让模型知道发生了什么。这种天真做法的问题在于上下文长度（Context Length）是有限的。通常模型的上下文长度在数十万 Token 的数量级。一个 Token 大约等于 4 个字符，数十万 Token 大概相当于几百页，或者一本非常厚的书。虽然很大，但不足以让我们采用这种简单粗暴的方法。

而且，即使上下文长度是无限的，人们也发现如果给 LLM 灌输大量不相关的信息，LLM 的性能实际上会下降。如果给它一堆不相关的信息，LLM 会感到困惑。人们进行了一项名为“大海捞针（Needle in a Haystack）”的测试：给 LLM 一个巨大的提示词（草堆），在其中放置一个事实（针），然后问模型那个事实是什么。

实验表明，提示词的长度和事实放置的位置都很重要。对于超过一定 Token 数量的提示词，LLM 实际上很难检索到正确的信息。特别是当事实位于提示词的前半部分时，通过率会下降。这告诉我们，即使上下文无限，简单地放入所有信息也会有问题。

此外，还有成本问题。LLM 的调用通常是按 Token 收费的。输入的提示词越长，费用就越高。因此，我们有动力不要在提示词中放入太多内容。

出于所有这些原因，我们需要一种更聪明的方法：不要一次性把所有新信息都放在提示词中，而是只找到相关信息并将其放入提示词。这就是 **RAG（检索增强生成）** 背后的想法。这里的核心是如何将**相关**的部分放入提示词中。

### RAG 的三个主要步骤

1.  **检索（Retrieve）：** 从知识库中检索相关文档。
2.  **增强（Augment）：** 将检索到的相关信息放入提示词中。例如，不再只问“谁赢了选举”，而是问“谁赢了选举，顺便说一下，这次选举是这样举行的，这是获胜者……”。我们在提示词中提供了答案。
3.  **生成（Generate）：** 将增强后的提示词输入 LLM 以生成回答。

检索步骤非常重要，因为如果你检索到了错误的信息，后续步骤就会出错。

### 构建知识库

为了进行检索，我们首先需要整理文档并建立知识库。
1.  **收集文档：** 收集所有可能有用的文档。
2.  **分块（Chunking）：** 将文档分成“块”。块是文档的子集，具有给定的最大长度（通常是几百个 Token）。
3.  **嵌入（Embeddings）：** 计算每个块的嵌入向量。

在构建知识库时，有几个超参数需要调整：
*   **嵌入大小：** 更大的尺寸可能表达更复杂的细微差别，但计算和存储成本更高。通常在 1500 左右。
*   **块大小（Chunk Size）：** 太小会导致脱离上下文，太大则嵌入可能无法有效代表内容。通常在 500 Token 左右。
*   **重叠（Overlap）：** 为了保持上下文连贯，块之间通常会有重叠（例如几百个 Token）。

### 检索过程：两阶段方法

有了知识库后，给定一个提示词，我们通常分两步检索相关文档。这种方法借鉴了推荐系统和搜索领域的思想。

#### 第一阶段：候选检索 (Candidate Retrieval)
目标是从海量的块中筛选出一个小得多的潜在相关候选集（例如 100 个）。在这个阶段，我们试图最大化**召回率（Recall）**。
*   **语义相似度搜索（Semantic Similarity Search）：** 使用嵌入向量。将查询（Query）转换为嵌入，与块的嵌入进行比较（通常使用余弦相似度 Cosine Similarity），保留相似度最高的 Top K。这通常使用**双编码器（Bi-encoder）**架构，即查询和文档分别通过独立的编码器（如 BERT 的变体 Sentence-BERT）。
*   **近似最近邻（ANN）：** 对于大型知识库，使用 ANN 算法来避免线性搜索，提高速度。
*   **关键词搜索（BM25）：** 有时我们需要确保文档包含查询中的确切关键词。BM25 是一种基于词重叠的启发式评分。
*   **混合搜索（Hybrid Search）：** 结合语义搜索和关键词搜索（BM25），以利用两者的优势。

#### 解决查询与文档性质不匹配的问题
通常用户的查询很短（问题），而文档块很长。这会导致嵌入在空间上不具备完全的可比性。
*   **HyDE (Hypothetical Document Embeddings)：** 一种扩展方法。先让 LLM 基于查询生成一个“虚构文档”，然后计算这个虚构文档的嵌入来寻找相关块。
*   **特定编码器：** 理论上可以分别训练查询编码器和文档编码器，但通常出于维护原因，人们不这样做。

#### 解决分块上下文缺失的问题
如果一个块被切分得不合理，可能会失去意义。
*   **上下文增强：** 我们可以使用 LLM 为每个块生成一个简短的上下文摘要，并将其添加到块的前面。
*   **提示词缓存（Prompt Caching）：** 由于这需要大量的 LLM 调用，我们可以利用提示词缓存技术。如果提示词的前缀相同，我们可以缓存激活值（Activations），避免重复计算，从而降低成本和延迟。许多模型提供商（如 Anthropic）现在都提供这种功能，价格通常只是未缓存 Token 的一小部分。

#### 第二阶段：重排序 (Ranking / Reranking)
在第一阶段筛选出数百个候选后，我们需要更精确地排序，以确保最相关的文档排在最前面。
*   **交叉编码器（Cross-encoder）：** 将查询和文档块**同时**输入到一个编码器中，利用模型捕捉两者之间的交互，输出一个相关性分数。这种方法计算量大，但因为只对少量候选文档进行操作，所以是可行的。

### 评估 RAG 系统

为了量化检索器的性能，我们使用类似推荐系统的指标。假设我们将检索到的 Top K 文档与真实相关的文档（Ground Truth）进行比较：
1.  **NDCG (Normalized Discounted Cumulative Gain)：** 归一化折损累计增益。它不仅看你是否检索到了相关文档，还看你把它们排在什么位置。如果相关文档排名靠前，分数就高。
2.  **MRR (Mean Reciprocal Rank)：** 平均倒数排名。它是第一个相关文档排名的倒数。它只关心第一个相关文档出现的位置。
3.  **Recall@K (召回率)：** 在检索到的前 K 个文档中，包含了多少个实际相关的文档。
4.  **Precision@K (精确率)：** 在检索到的前 K 个文档中，有多少个是实际相关的。

有一个流行的基准测试叫 **MTEB (Massive Text Embedding Benchmark)**，用于评估检索器的性能。

## 工具调用 (Tool Calling)

接下来我们将进入智能体世界。RAG 解决了非结构化数据的问题，但如果我们想注入结构化数据，或者让 LLM 执行动作，就需要**工具调用**（在某些上下文中也称为函数调用 Function Calling）。

### 定义与示例
IBM 将工具调用定义为：“允许自主系统通过动态访问并可能作用于外部资源来完成复杂任务。”
两个关键点：完成任务，以及依赖外部资源。

举个例子：假设你想要找附近的泰迪熊。如果你直接问 LLM，它不知道你的实时位置或附近的库存，只能回答“我不知道”。使用工具，我们可以注入必要的信息。

### 工具调用的流程
1.  **定义函数（API）：** 你定义一个函数，例如 `find_teddy_bear(location)`。LLM 只需要看到函数的 API（名称、描述、输入参数说明），而不需要看到具体的代码实现。
2.  **LLM 预测参数：** 在提示词的开头包含函数 API。当用户提问时，LLM 的目标不是生成最终文本，而是根据用户的查询和上下文（如你的位置信息），预测应该传递给函数的参数。
3.  **执行函数：** 获取 LLM 输出的参数，在后端执行实际的函数代码（例如调用地图 API）。这将返回结构化的数据（如 JSON 格式的泰迪熊列表）。
4.  **生成最终回答：** 将函数的输出（JSON）传回给 LLM，让 LLM 将其转换为自然语言回答用户。

### 如何训练模型使用工具？
1.  **SFT（有监督微调）：** 准备包含对话历史、工具调用和工具输出的数据对。你需要两类数据：一类是将查询映射到工具参数，另一类是将工具输出映射到最终回答。
2.  **仅通过提示词（Prompting/Context）：** 现在的模型推理能力很强，有时不需要微调。你可以提供一个详细的系统提示词（System Prompt），解释如何使用工具。
    *   **Few-shot Learning（少样本学习）：** 在上下文中提供示例。
    *   **推理生成说明：** 不要自己手写复杂的说明，可以使用一个强大的推理模型，基于评估集的反馈，自动迭代和优化工具使用的说明提示词。

### 扩展：多个工具与选择
现实中我们会有很多工具（查天气、发邮件、计算器等）。
*   **挑战：** 如果工具太多，全部放入上下文会超出长度限制，或者让模型困惑（迷失在上下文中）。
*   **解决方案：工具选择器（Tool Selector/Router）：** 这是一个两步过程。
    1.  首先列出所有工具的简要名称和描述，让 LLM 选择可能相关的工具。
    2.  然后只将选定工具的完整 API 放入上下文，进行后续的工具调用。

### 标准化：MCP (Model Context Protocol)
为了避免为每个 LLM 重复编写工具定义，Anthropic 提出了 **MCP（模型上下文协议）**。它标准化了工具向模型展示的方式。
*   **MCP Server：** 提供工具的实例（例如由图书供应商提供）。
*   **MCP Client：** LLM 主机端的连接组件。
*   **Resources & Prompts：** 协议中定义的资源和模板。

## 智能体 (Agents)

智能体比工具调用更进一层。
**定义：** 一个自主追求目标并代表用户完成任务的系统。
与单纯的工具调用相比，智能体具有**推理循环**和**迭代能力**。

### ReAct 框架 (Reason + Act)
这是一个标志性的论文概念，将任务分解为循环步骤：
1.  **观察 (Observe)：** 将用户查询转化为可操作的表述。例如，用户说“泰迪熊很冷”，智能体观察到这与“温度”有关。
2.  **计划 (Plan)：** 决定下一步做什么。例如，“我需要知道当前室温”。
3.  **行动 (Act)：** 使用工具（如获取温度 API）。
4.  **再次观察：** 解读工具的输出（“室温是 65 度，太低了”）。
5.  **再次计划与行动：** “我需要调高温度”。调用调温 API。
6.  **循环：** 直到目标达成，退出循环并回复用户。

这种循环机制（观察-计划-行动）是智能体工作流的核心。

### 多智能体系统 (Multi-Agent Systems)
你可以有多个专门的智能体（如恒温器代理、能源管理代理），它们可以相互通信。Google 发布了 **Agent-to-Agent Protocol** 来标准化这种通信，定义了智能体如何暴露技能（Skills）以及如何请求和取消任务。

### 安全性 (Safety)
赋予模型执行动作的能力带来了巨大的风险。
*   **风险：** 例如数据泄露（Data Exfiltration）。恶意提示词可能诱导智能体读取你的邮件并将其发送给攻击者。
*   **防御：**
    *   **训练阶段：** 在 SFT 和 RL 阶段加入安全性数据（Harmlessness）。
    *   **推理阶段：** 使用安全分类器（Safety Classifiers）监控输入和输出。
    *   **基准测试：** 使用如 Agent Safety Bench 等工具进行评估。

最近 Anthropic 披露了一起利用工具和智能体能力的大规模网络攻击，这凸显了安全的重要性。

## 总结与建议

1.  **从简单开始：** 构建智能体时，先从单一工具、简单用例开始，确保能跑通。
2.  **从强模型开始：** 先使用最强大的模型（如 Claude 3.5 Sonnet, GPT-4o）来验证概念，然后再尝试优化延迟或迁移到更小的模型。
3.  **可调试性：** 经常查看模型的推理链，了解哪里出了问题。
4.  **AI 辅助编程：** Shervin 强烈推荐使用 AI 智能体进行辅助编程（Coding Assistant），这能极大减轻认知负担。但前提是你必须懂代码，因为你需要能够判断生成的代码是否正确。
