# LangChain Agent Middleware 完全解析：掌控 AI 智能体的核心循环

### **Metadata**

*   **Author**: 小毛头

### **Overview**

本视频的核心议题是深入探讨 LangChain 框架最新推出的 **Agent Middleware（智能体中间件）** 功能。这一功能旨在解决当前 AI 智能体开发中普遍存在的痛点，即开发者对模型输入的 **Context Engineering（上下文工程）** 缺乏足够灵活和精细的控制权。视频通过剖析智能体的基本工作原理，引出了 Middleware 作为 LangChain 1.0 的核心解决方案。其结论是，通过引入 Middleware 机制，开发者可以在不改变核心 Agent 逻辑的前提下，以一种可组合、可扩展的方式，在模型调用前后注入自定义逻辑或修改模型请求，从而极大地提升了构建可靠、可控、可观测的 AI 智能体的能力。

### **第一章：AI 智能体开发的困境：失控的“上下文工程”**

LangChain 作为当今最受欢迎的 AI 应用开发框架之一，其 Agent（智能体）的抽象概念已经发展了近三年时间。在这期间，社区涌现了大量基于其核心思想构建的智能体框架。然而，无论是 LangChain 本身还是其他同类框架，在将智能体从实验原型推向实际生产环境时，都面临着一个共同的挑战——灵活性不足。

视频开篇便指出了这个核心痛点：“他们在实际生产环境中往往不够灵活，特别是在上下文工程方面”。这里提到的 **Context Engineering（上下文工程）**，是近期在 AI 开发领域备受关注的一个关键概念。它指的是为了引导大型语言模型（LLM）产生期望的输出，而对输入给模型的所有信息（即“上下文”）进行设计、构建和管理的过程。这个上下文不仅仅是用户的单次提问，还可能包括历史对话、可用的工具列表、系统指令、少量示例（Few-shot Examples）等。

现有的大多数智能体框架，为了简化开发流程，对这个上下文的构建过程进行了高度封装。虽然这种封装在入门时非常友好，但在复杂的实际应用中却带来了严重的限制。视频中提到，在这种模式下，“开发者很难完全掌控模型输入的具体内容”。具体来说，你可能无法：

*   **动态调整提示词**：根据对话的进展或中间步骤的失败，动态地向提示词中添加警告、修正建议或额外的指导信息。
*   **精细控制工具的呈现**：你可能希望在某个特定步骤中，只向模型展示一部分可用的工具，或者动态修改工具的描述以更好地引导模型。
*   **干预模型的决策过程**：在模型决定调用某个工具之前，你可能希望进行一次安全检查或成本预估。

这种控制权的缺失，导致开发者在面对一些非标准或复杂的任务时，会发现框架的抽象反而成了束缚。最终，他们不得不绕过框架，直接编写底层的、自定义的代码来手动管理上下文和模型调用，这完全违背了使用框架以提高效率的初衷。这正是 LangChain 推出 Agent Middleware 所要解决的根本问题。

### **第二章：揭秘智能体（Agent）的本质：一个简单的循环**

在深入了解 Middleware 如何解决问题之前，我们必须首先理解 Agent 的工作原理。视频中强调，“实际上 Agent 核心是蛮简单的”。一个典型的智能体，其核心构成可以被分解为三个基本要素：

1.  **一个模型（A Model）**：通常是一个大型语言模型（如 GPT-4），作为智能体的大脑，负责思考和决策。
2.  **一个提示词（A Prompt）**：这是一套结构化的指令，它告诉模型其角色、目标、可用资源（如工具），以及如何格式化其思考过程和最终答案。
3.  **一组工具（A List of Tools）**：这些是智能体可以调用的外部函数或 API，用于执行模型本身无法完成的任务，例如进行网络搜索、执行代码、查询数据库等。

智能体的运行机制本质上是一个循环，这个循环通常被称为 **ReAct（Reasoning and Acting）** 循环。视频通过一张流程图清晰地展示了这个过程：

*   **步骤一：接收输入（Input）**
    用户向智能体发出一个指令或问题。这构成了循环的初始状态。

*   **步骤二：模型决策（Model Decision）**
    智能体将当前的全部上下文（包括用户输入、历史交谈记录、可用工具列表等）打包成一个提示词，发送给模型。模型根据这些信息进行“思考”，并决定下一步该做什么。

*   **步骤三：解析模型输出与分支**
    模型的输出通常包含两部分：思考过程和具体行动。智能体解析这份输出，并根据内容进入不同的分支：
    *   **分支 A：执行动作（Action）**
        如果模型决定使用一个工具，它的输出会指明要调用的工具名称和所需的参数。例如，`Action: search(query="What is LangChain Agent Middleware?")`。智能体会立即执行这个工具调用。
    *   **分支 B：完成任务（Finish）**
        如果模型认为它已经收集到足够的信息并可以回答用户的问题了，它的输出会包含一个特殊的“Final Answer”标识，后面跟着最终的答案。

*   **步骤四：获取观察结果（Observation）**
    在执行完一个工具动作后，工具会返回一个结果。这个结果被称为“观察（Observation）”。例如，搜索引擎工具会返回搜索结果的摘要。

*   **步骤五：更新状态并循环**
    智能体将上一步的动作和这一步的观察结果追加到历史记录中。现在，上下文变得更丰富了。然后，整个过程回到步骤二，智能体将这个更新后的、更完整的上下文再次发送给模型，让模型进行下一步的决策。

这个“思考 → 动作 → 观察”的循环会一直持续，直到模型在某一步决定“完成任务”并给出最终答案为止。虽然这个流程的逻辑很简单，但它的可靠性高度依赖于每一步中输入给模型的信息是否精确和有效。如果开发者无法精细地控制这个循环中的状态和输入，智能体的行为就很容易偏离轨道。这就是为什么我们需要一个机制来“介入”这个循环，而这个机制就是 Middleware。

### **第三章：LangChain 1.0 的破局之道：引入 Middleware（中间件）**

为了解决对智能体核心循环缺乏控制权的问题，LangChain 在其 1.0 版本（视频中提到，当前仍处于 Alpha 测试阶段）中，引入了一个强大而优雅的概念——**Middleware（中间件）**。这个设计的核心思想，是为开发者提供一系列“钩子（hooks）”，让他们能够在智能体运行的关键节点上，非侵入式地注入自定义的逻辑。

Middleware 允许你在不修改 Agent 核心执行器代码的情况下，实现对 Agent 行为的观测、干预和扩展。它就像一个插件系统，你可以根据需求加载不同的中间件来增强 Agent 的功能。视频中强调，多个中间件可以像 Web 服务器中的中间件那样被“串联（chain）”起来，按顺序依次执行，这极大地提升了 Agent 的“**可组合性（composability）**”和“**可扩展性（extensibility）**”。

从开发者的角度来看，LangChain 的 Middleware 提供了简洁明了的接口。要创建一个自定义中间件，你只需要继承 `AgentMiddleware` 类，并实现以下一个或多个方法：

*   `before_model`: 这个方法会在 Agent 准备调用语言模型 **之前** 执行。它接收当前的 Agent 状态（`state`）作为参数，你可以在这里读取状态，或者在将状态传递给模型之前对其进行修改。例如，你可以动态地向历史消息中添加一条系统提示。
*   `after_model`: 这个方法会在语言模型返回响应 **之后**，但在 Agent 解析该响应并决定下一步行动之前执行。它同样可以访问包含了模型新响应的 `state`。这个节点非常适合用于日志记录、性能监控或数据统计。
*   `modify_model_request`: 这是一个功能更强大的钩子，它允许你直接修改即将发送给模型的完整请求。通过这个方法，你可以精细地控制该次调用的所有方面，包括要使用的工具集、提示词模板、消息列表、甚至是模型的具体参数（如温度 `temperature` 等）。

为了让开发者能快速上手，LangChain 框架已经内置了一些实用的中间件。视频中列举了几个例子，它们也很好地展示了 Middleware 的应用场景：

*   **Summarization（摘要中间件）**：用于处理长对话。当对话历史的 Token 数量接近模型上下文窗口的上限时，这个中间件会自动触发，将早期的对话内容进行摘要，然后用凝练的摘要替换原始的多轮对话。这样既保留了关键的上下文信息，又为新的对话腾出了空间。
*   **Human-in-the-loop（人工干预中间件）**：在关键决策点暂停 Agent 的执行，并将当前状态和计划的下一步行动呈现给人类用户，等待用户的批准或修改。这对于在金融、医疗等高风险领域部署 Agent 至关重要。
*   **Anthropic prompt caching（Anthropic 提示词缓存）**：这是专为 Anthropic 模型设计的优化工具，它可以缓存重复的提示词请求，从而减少延迟和 API 调用成本。

通过这些灵活的接口和开箱即用的组件，Middleware 将 Agent 的控制权重新交还给了开发者，使构建复杂、可靠且可维护的 AI 智能体成为可能。

### **第四章：实战演练：用 Middleware 打造 Token 追踪器**

理论终须实践。视频的后半部分，主讲人通过一个在 Google Colab 环境中运行的 Python 笔记本，一步步演示了如何利用 Middleware 机制构建一个实用的 **Token 使用量追踪器**。这个例子完美地展示了 Middleware 的强大之处——在不修改任何 Agent 内部代码的情况下，为其增加全新的监控功能。

以下是完整的实现步骤：

*   **第一步：环境设置**
    *   首先，需要安装 LangChain 的 Alpha 版本，视频中使用的命令是 `pip install -q langchain==1.0.0a5`。指定版本是为了确保代码的可复现性，因为 Alpha 版本的 API 可能会频繁变动。
    *   同时，安装 `langchain-openai` 包以支持 OpenAI 的模型。
    *   最后，在环境中设置好你的 `OPENAI_API_KEY`，以便 Agent 能够调用 GPT 模型。

*   **第二步：定义自定义中间件 (`TrackingMiddleware`)**
    *   我们创建一个名为 `TrackingMiddleware` 的 Python 类，并让它继承 LangChain 提供的基类 `AgentMiddleware`。
    *   在这个类中，我们主要实现 `after_model` 方法。这个方法会在每次模型调用结束后被自动触发。
    *   `after_model` 方法的逻辑如下：
        1.  从传入的 `state`（一个字典）中，获取 `messages` 列表，并取出最后一项。这最后一项就是刚刚由 AI 模型生成的消息对象（`AIMessage`）。
        2.  访问该消息对象的 `response_metadata` 属性。这是一个包含了模型调用详细信息的字典，其中通常会有一个名为 `token_usage` 的子字典。
        3.  从 `token_usage` 中解析出我们关心的几个关键指标：`completion_tokens`（生成内容的 Token 数）、`prompt_tokens`（输入提示的 Token 数）和 `total_tokens`（总 Token 数）。
        4.  为了方便管理，代码还定义了一个 Pydantic 数据模型 `ModelUsage`，用于结构化地存储这些信息，同时记录下本次调用的模型名称（`model_name`）。
        5.  将新创建的 `ModelUsage` 对象追加到一个类级别的列表 `self.model_usages` 中。这样，每一次模型调用，其 Token 消耗都会被记录下来。

*   **第三步：创建并配置 Agent**
    *   首先，实例化我们刚刚定义的中间件：`tracking_middleware = TrackingMiddleware()`。
    *   然后，使用 LangChain 的 `create_agent` 函数来构建智能体。关键在于，通过 `middleware` 参数将我们的实例传入。这个参数接受一个中间件列表，这意味着你可以同时使用多个中间件。
    *   代码中还指定了使用的模型为 `openai:gpt-4o`。

*   **第四步：与 Agent 交互并触发中间件**
    *   演示者进行了两轮对话来测试效果。
    *   **第一轮**：调用 `agent.invoke` 方法，输入问题 `{"messages": [HumanMessage(content="What is LangChain?")]}`。
        *   调用发生后，`after_model` 方法被触发。在 Colab 的输出中，可以看到打印出的 `AI response metadata`，其中清晰地包含了 `token_usage` 信息，例如 `{'completion_tokens': 171, 'prompt_tokens': 12, 'total_tokens': 183}`。
    *   **第二轮**：为了模拟多轮对话，代码将上一轮的完整对话历史（包括用户的提问和 AI 的回答）与一个新问题“How to use it?” 组合在一起，再次调用 `agent.invoke`。
        *   同样，`after_model` 再次被触发，并打印出第二次调用的 Token 消耗。

*   **第五步：验证追踪结果**
    *   在所有交互结束后，通过访问 `tracking_middleware.model_usages` 属性，可以得到一个包含了两次交互中所有模型调用消耗的完整列表。
    *   输出结果清晰地展示了两条 `ModelUsage` 记录，每一条都包含了模型名称和对应的 Token 数量，证明了我们的追踪器成功地捕获了每一次模型调用的成本。

这个简单的例子有力地证明了 Middleware 的价值：它提供了一个标准化的、解耦的方式来为 Agent 增加横切关注点（cross-cutting concerns）的功能，如日志、监控、成本分析等。

### **框架与心智模型 (Framework & Mindset)**

从 LangChain 的 Agent Middleware 设计中，我们可以抽象出一个强大的、通用的框架和心智模型，即 **“基于拦截与修改的 AI 系统可观测性与可控性框架”**。这个模型不仅仅是 LangChain 的一个具体实现，更是一种构建复杂、可靠的 AI 系统时应具备的思考方式。

*   **核心原则一：分离关注点（Separation of Concerns）**
    *   **心智模型**：将一个复杂的 AI Agent 系统看作两部分：**核心业务逻辑** 和 **横切关注点（Cross-Cutting Concerns）**。
        *   **核心业务逻辑**：即 Agent 的主要任务循环，也就是前面提到的“思考（Reason）→ 动作（Act）”循环。这部分代码应该专注于如何解决用户的根本问题。
        *   **横切关注点**：这些是与核心业务逻辑正交，但又贯穿系统多个层面的通用功能。典型的例子包括：日志记录、性能监控、成本追踪、错误处理、安全校验、缓存机制、用户认证等。
    *   **Middleware 的作用**：Middleware 正是实现这种分离的完美工具。它允许你将每一个横切关注点封装在一个独立的、可复用的中间件模块中。例如，`TrackingMiddleware` 只关心 Token 追踪，`HumanInTheLoopMiddleware` 只关心人工审批。这种设计使得核心的 Agent 代码保持干净、简洁，而复杂但通用的功能则被模块化地管理起来，极大地提高了代码的可维护性和可读性。

*   **核心原则二：通过拦截实现可观测性（Observability through Interception）**
    *   **心智模型**：一个无法被观测的系统是一个黑盒，而黑盒是难以调试、优化和信任的。要让 AI Agent 成为一个“白盒”，你必须能够在它的“神经中枢”——即核心决策循环中，设置“观测点”。
    *   **Middleware 的作用**：`before_model` 和 `after_model` 这两个钩子，就扮演了“观测点”的角色。
        *   **`before_model`**：它让你能够精确地看到在 Agent 做出关键决策（调用 LLM）之前，它所掌握的全部信息（`state`）。这对于调试“为什么 Agent 会做出某个奇怪的决定？”这类问题至关重要。你可以检查历史记录是否完整、工具描述是否清晰、提示词是否被污染等。
        *   **`after_model`**：它让你能在第一时间看到模型的“原始想法”，以及调用 API 的元数据（如 Token 消耗、响应时间等）。这为性能分析、成本统计和模型行为分析提供了第一手数据。视频中的 Token 追踪器就是这个原则的最佳体现。

*   **核心原则三：通过修改实现可控性（Controllability through Modification）**
    *   **心智模型**：真正的强大系统不仅要能被观测，还要能被干预和控制。在 AI Agent 的语境下，可控性意味着你能够在运行时动态地影响它的行为，引导它走向正确的路径，或者阻止它执行危险的操作。
    *   **Middleware 的作用**：`before_model` 和 `modify_model_request` 提供了强大的修改能力，是实现可控性的关键。你可以利用它们来实现一系列高级功能：
        *   **动态提示工程（Dynamic Prompt Engineering）**：一个中间件可以分析当前 `state`，如果发现 Agent 陷入了重复的错误循环，它可以在下一次模型调用前，通过 `modify_model_request` 动态地在提示词中插入一条指令，如：“注意：你之前尝试使用工具 X 失败了，请考虑使用工具 Y，或者换一种方式思考。”
        *   **运行时安全护栏（Runtime Guardrails）**：一个安全中间件可以在 `after_model` 钩子中拦截模型生成的动作。在 Agent 执行该动作之前，中间件可以进行校验。例如，如果模型决定执行一条 `os.remove('/')` 的危险命令，中间件可以立即捕获并阻止它，或者将其转交人工审批。
        *   **成本与预算控制**：Token 追踪器可以被升级为一个预算控制器。在 `before_model` 阶段，它检查累计的 Token 消耗是否已超出预设的阈值。如果超出，它可以直接抛出异常，终止 Agent 的执行，从而避免失控的 API 调用产生高昂费用。

这个“拦截与修改”的框架，将 Agent 从一个难以捉摸的黑盒，转变为一个透明、可调试、可扩展的模块化系统。它鼓励开发者将复杂问题分解，用一系列可组合的、单一职责的中间件来构建健壮的解决方案，这是从“能用”的 AI 应用迈向“可靠”的 AI 产品的关键心智转变。


# 概要版

### **各段落主题摘要**

**一、 LangChain Agent Middleware 简介**
本段落介绍了视频的主题，即 LangChain 框架新推出的“Agent Middleware”（智能体中间件）功能，旨在解决现有AI智能体开发的痛点。

**二、 现有智能体框架的挑战与“上下文工程”**
此部分探讨了当前包括 LangChain 在内的智能体框架所面临的普遍问题。核心挑战在于开发者对模型的“上下文工程”（Context Engineering）缺乏足够的控制权，导致在复杂场景下灵活性不足，难以完全掌控模型的输入内容。

**三、 智能体（Agent）的核心构成与运行逻辑**
该段落阐述了智能体的基本组成部分和工作流程。一个典型的智能体由模型、提示词和工具集构成，其运行方式是一个循环过程：接收用户输入，调用模型决策，使用工具执行动作，观察结果，直至最终完成任务并输出。

### **详细内容**

#### **一、 LangChain Agent Middleware 简介**

视频开篇，主讲人小毛头向观众问好，并明确了本期视频的核心内容：分享 LangChain 新推出的 “Agent Middleware”，并将其翻译为“智能体中间件”。这是一个旨在增强 AI 应用开发灵活性的新功能。

#### **二、 现有智能体框架的挑战与“上下文工程”**

主讲人指出，LangChain 作为一个流行的 AI 应用开发框架，其智能体（Agent）抽象概念已经存在了大约三年。然而，市面上包括 LangChain 在内的许多类似框架，在实际应用中都面临一个共同的弊端。关键问题在于“在实际生产环境中往往不够灵活，特别是在上下文工程方面”。

他进一步解释了这个近期非常热门的概念——“Context Engineering”（上下文工程）。在现有框架下，开发者很难完全掌控模型输入的具体内容。这种控制权的缺失，导致在处理一些复杂场景时，开发者不得不放弃框架，转而编写自定义的代码来满足需求。

#### **三、 智能体（Agent）的核心构成与运行逻辑**

为了更好地理解中间件的作用，主讲人首先简化了智能体的核心概念。他总结道：“实际上 Agent 核心是蛮简单的”，主要由三部分组成：
1.  **一个模型（A model）**
2.  **一个提示词（A prompt）**
3.  **一组工具（A list of tools）**

接着，他通过一张流程图展示了智能体的典型执行流程：
*   **输入（Input）**：用户提供初始信息。
*   **模型（Model）**：模型根据当前状态和输入进行决策。
*   **决策分支**：
    *   **动作（Action）**：决定调用某个工具。
    *   **观察（Observation）**：工具执行后返回结果。
    *   **完成（Finish）**：模型判断任务已完成。
*   **输出（Output）**：向用户返回最终结果。

整个过程是一个循环，智能体会不断调用工具和模型，直到任务完成。然而，要让这个过程变得可靠且可控，开发者需要更精细地管理其中间状态、模型输入和执行流程，这正是现有框架的不足之处。

#### **四、 Middleware：LangChain 1.0 的解决方案**

为了解决上述挑战，LangChain 在其 1.0 版本（目前为 Alpha 测试版）中，引入了全新的“Middleware”（中间件）概念。这个机制的核心思想是让开发者能够介入并修改智能体的核心循环。

主讲人介绍，中间件的核心功能是：
*   **可以在模型调用的前后运行**，执行额外的逻辑。
*   **可以修改模型请求**，灵活调整工具、提示词、消息、甚至模型的设置。

多个中间件可以像 Web 服务器的中间件一样被串联起来，按顺序执行，这极大地提升了智能体的“可组合性和可扩展性”。从开发接口上看，中间件的设计非常简洁，主要提供了三个核心接口：
*   `before_model`：在模型被调用前运行。
*   `after_model`：在模型被调用后运行。
*   `modify_model_request`：在模型调用前运行，允许用户修改该次请求的所有内容。

#### **五、 LangChain 内置的中间件**

根据 LangChain 的官方文档，框架已经内置了一些可以直接使用的中间件，主讲人列举了三个例子：
1.  **Summarization**：这是一个用于自动管理对话历史的摘要中间件。当对话长度接近 Token 限制时，它会自动对较早的消息进行摘要，以在保留上下文的同时避免超出模型限制。
2.  **Human-in-the-loop**：提供人工干预的机制，允许在智能体执行过程中加入人的决策。
3.  **Anthropic prompt caching**：这是 Anthropic 公司特有的提示词缓存中间件，用于优化对特定模型的调用。

主讲人特别提醒，由于 LangChain 1.0 目前仍是 Alpha 版本，其代码和文档可能会随时发生变动。

#### **六、 Python 代码实例：实现 Token 用量追踪中间件**

视频的最后部分，主讲人通过一个 Google Colab 上的 Python 笔记本，进行了一次实操演示。

1.  **环境准备**：首先，他指定安装了 LangChain 1.0.0a5 的 Alpha 版本，并配置了 OpenAI 的 API 密钥。
2.  **自定义中间件**：他创建了一个名为 `TrackingMiddleware` 的自定义中间件，其目标是“做模型的 token 使用的跟踪”。
3.  **代码实现**：
    *   该中间件继承自 `AgentMiddleware`。
    *   在 `before_model` 方法中，只是简单地打印出调用模型前的状态（State），以展示状态中包含了哪些信息。
    *   核心逻辑在 `after_model` 方法中。该方法在模型调用后执行，从返回的状态（State）中提取最后一条 AI 消息（`ai_message`），并从该消息的 `response_metadata` 中解析出 Token 的使用情况，包括模型名称、提示词 Token 数、补全 Token 数和总 Token 数。
    *   解析出的数据被存储在一个名为 `model_usages` 的列表中。
4.  **创建和使用 Agent**：
    *   在创建智能体时，通过 `middleware` 参数将刚才定义的 `tracking_middleware` 实例注入进去。
    *   随后，他连续调用了两次 Agent，第一次提问“What is LangChain?”，第二次提问“How to use it?”。
5.  **结果展示**：
    *   每次调用后，`after_model` 方法都成功捕获了 AI 响应的元数据，并打印了 Token 使用量。
    *   最后，通过访问 `tracking_middleware.model_usages`，可以看到一个包含了两次模型调用 Token 消耗记录的列表，证明了中间件成功地完成了追踪任务。

这个实例清晰地展示了如何利用中间件机制，非侵入式地为智能体增加额外的监控和统计功能。
