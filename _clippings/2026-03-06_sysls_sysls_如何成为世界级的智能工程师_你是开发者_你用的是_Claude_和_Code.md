# 如何成为世界级的智能工程师

# 简介

你是开发者。你用的是 Claude 和 Codex 的 CLI，每天都在想自己是否充分榨取了 Claude 或 Codex 的效能。偶尔你会看到它做一些非常愚蠢的事情，你无法理解为什么有一群人在造虚拟火箭，而你却在努力堆两块石头。

你以为是你的线束、插件、终端或者其他什么问题。你用珠子、OpenCode 和 zep，CLAUDE.md 长达 26000 行。然而，无论你做什么——你都不明白为什么你无法更接近天堂，同时看着别人与天使嬉戏。

这就是你一直在等待的升华碎片。

另外，我没有任何参赛者，说的 CLAUDE.md 指的是 AGENT.md，说克劳德也指法典。我两者都用得很广泛。

过去几个月我观察到的最有趣的一点是，没有人真正知道如何最大化提取代理的能力。

就像一小群人能让特工成为世界构建者，而其他人却在无数工具中陷入分析瘫痪——认为只要找到合适的包、技能或背带组合，就能解锁通用人工智能。

今天，我想打消这些，给大家一个简单、诚实的陈述，然后我们再继续。你不需要最新的代理工具，不需要安装一百万个软件包，更不需要为了保持竞争力而读一大堆资料。事实上，你的热情可能弊大于利。

我不是游客——我一直用代理，从他们几乎不会写代码的时候开始。我试过所有的软件包、所有的线束和各种范式。我建造过代理工厂来编写信号、基础设施和数据流水线，而不是“玩具项目”——那些在生产环境中运行的真实现实用例，经历了这些......

如今，我运行的配置几乎是最简陋的，但我用的是基础 CLI（Claude 代码和 codex）和理解一些代理工程的基本原理，做着我迄今为止最开创性的工作。

# 要明白，世界正在飞奔

首先，我想说明基金会公司正处于一代更替的状态，正如你所见，他们短期内不会放缓脚步。每一次“智能体”的进步都会改变你与他们合作的方式，因为这些特工通常被设计成越来越愿意服从指令。

几代人前，如果你在 CLAUDE.md 里写“READ\_THIS\_BEFORE\_DOING\_ANYTHING.md”，它会有一半的概率说“去你的”，然后随心所欲。如今，它能顺应大多数指令，甚至复杂的嵌套指令——例如你可以说类似“读 A，然后读 B，如果读 C，再读 D”，大多数情况下它会乐意跟随。

这里的重点是，最重要的原则是认识到每一代代理都会迫使你重新思考什么是最优，这也是为什么少即是多。

当你使用许多不同的库和工具时，你会把自己锁定在一个“解决方案”中，而这个问题在未来几代代理可能不存在。另外，你知道谁是最热情、最常用经纪人的人吗？没错——这是前沿公司的员工，拥有无限的代币预算和真正最新的型号。你明白这意味着什么吗？

这意味着如果真的存在问题，并且有好的解决方案，前沿公司将是该解决方案的最大用户。你知道他们接下来会做什么吗？他们会将该解决方案融入产品中。想想看，为什么一家公司会让另一个产品解决真正的痛点，并制造外部依赖？你知道我怎么知道这是真的吗？看看技能、记忆束、子代理等。它们最初都是作为一个经过实战考验且被认为有用的真实问题的“解决方案”。

因此，如果某项产品真正具有突破性且具有显著意义，能够有效扩展代理性应用场景，它将最终被纳入基础公司的基础产品中。相信我，基金会公司很快就过去了。所以放轻松，你不需要安装任何东西，也不需要使用其他依赖，就能发挥最佳效果。

我预测评论区现在会充满“SysLS，我用某某线束，太棒了！我竟然在一天之内重建了谷歌！“;对此我说——恭喜！但你们不是目标受众，你们代表的是社区中非常非常小的一部分，真正弄清楚了代理工程。

# 情境就是一切

真的。情境就是一切。这也是使用成千上万个插件和外部依赖的另一个问题。你有上下文膨胀的问题——这其实就是说你的经纪人被信息量压得喘不过气！

用 Python 给我做一个绞刑架人游戏？这很简单。等等，这条关于“管理内存”的笔记是 26 次会话前写的吗？啊，用户遇到过一个屏幕卡住了，因为 71 个会话前我们生成了太多子进程。总是写笔记？好吧，没问题......这和绞刑架有什么关系？

你明白我的意思了。你只想给你的客服人员他们完成任务所需的准确信息，不能多说！你对此的掌控越好，经纪人表现也会越好。一旦你开始引入各种奇怪的记忆系统、插件，或者太多名字和调用都不合适的技能，你就会开始给你的经纪人讲怎么制造炸弹和烤蛋糕的配方，而你只想让它写一首关于红木森林的小诗。

所以，我再说一遍——剥离你所有的依赖，然后......

# 做那些有效的事

## 实施要精准

记住，情境就是一切。

记住，你想向你的代理人注入恰当数量的信息以完成他们的任务，仅此而已？

确保这一点的第一步是将研究与实施分开。你需要对经纪人提出的要求非常明确。

当你不够精准时会发生什么：“去建立一个认证系统。”代理需要研究什么是认证系统？有哪些可选方案？有哪些优缺点？现在它不得不在网上搜寻其实并不需要的信息，而其上下文中充满了涵盖各种可能性的实现细节。到了实施时，你增加了它被混淆或产生不必要或无关细节的可能性。

另一方面，如果你说“实现 JWT 认证并使用 bcrypt-12 密码哈希，刷新令牌轮换并有 7 天有效期......”这样它就不用再研究其他替代方案——它完全知道你想要什么，因此可以用实现细节填充上下文。

当然，你并不总是能掌握实现细节。你常常不知道什么才是正确的——有时甚至想把决定实施细节的工作交给代理。那你该怎么办？很简单——你创建一个关于各种实现可能性的研究任务，要么自己决定，要么让代理决定采用哪种实现，然后再找一个有新上下文的代理来实现。

一旦你开始沿着这些思路思考，你会发现工作流程中代理被不必要的上下文污染的领域。然后，你可以在代理工作流程中设置墙壁，抽象化代理人不必要的信息，除了那些为他们完成任务所需的非常特定上下文。记住，你拥有的是一个非常有才华且聪明的团队成员，他了解宇宙中各种球——但除非你告诉它你想让它专注于设计一个可以跳舞和享受乐趣的空间，否则它会不断告诉你拥有球形物体的所有好处。

## 谄媚的设计局限性

没人愿意用一个不断诋毁他们、告诉他们错误或完全无视说明的产品。因此，这些经纪人会试图与你达成一致，按你意愿行事。

如果你给它一个指令，每三个词加一个“happy”，它会尽力去执行——大多数人都能理解这一点。它愿意跟随，正是它成为一款如此有趣的产品。不过，这有个很有趣的特点——意思是如果你说“在代码库里找个 bug”，它会帮你发现一个漏洞——即使它得自己设计一个。为什么？因为它非常需要听从你的指示！

大多数人都急于抱怨大型语言模型会产生幻觉或制造不存在的东西，却没意识到问题出在它们身上。如果你提出要求，它会带来回报——即使需要稍微夸大事实！

那么，你是做什么的？我发现“中性”提示有效，这样我不会偏袒代理的某个结果。例如，我不会说“在数据库里帮我找一个漏洞”，而是说“搜索数据库，尽量跟随每个组件的逻辑，并反馈所有发现”。

像这样的中性提示有时会发现漏洞，有时则只是平淡地说明代码的运行方式。但这并不会让客服误以为存在漏洞。

我应对谄媚的另一种方式是利用它为自己谋利。我知道客服是想取悦我，也想遵循我的指示，我可以偏袒任何一方。

于是我让一个 bug-finder 代理识别数据库中的所有 bug，告诉它我会给低影响的 bug+1，有影响的 bug 给+5，严重影响的 bug 给+10，我知道这个代理会非常热情，会识别所有不同类型的 bug（甚至是那些其实不是 bug 的），然后回来，报告 104 分左右的分数。我把它看作是所有可能漏洞的超集。

然后我会得到一个对抗性代理，告诉他，对于代理能够证明为错误的每个错误，它都会得到该漏洞的分数，但如果错误，它将获得该漏洞的-2\*分数。所以现在这个对抗性代理会尽可能多地推翻各种漏洞;但它也保持谨慎，因为它知道自己可能会受到惩罚。不过，它会积极“推翻”这些漏洞（即使是真正的漏洞）。我把它看作是所有实际漏洞的子集。

最后，我请了一位裁判代理，同时收集他们的意见并评分。我撒谎告诉裁判代理我有真正的真实情况，如果对了会得+1分，错了会扣1分。于是，发现漏洞的人和对抗代理人都会对每个“漏洞”进行评分。裁判说的都是真话，我都会仔细检查以确保其真实性。大多数情况下，这已经是令人恐惧的高保真了，偶尔还是会出错，但现在几乎是一次完美的练习。

也许你会发现仅仅有 bug-finder 就够了，但这对我来说有效，因为它利用了每个代理被硬编程的目的——想要取悦。

## 你怎么知道什么有效或有用？

这个可能看起来很棘手，需要你深入研究并站在 AI 更新的前沿，但其实非常简单......如果 OpenAI 和 Claude 都实现了它，或者收购了实现它的东西......这可能有用。

注意到“技能”现在无处不在，并且是克劳德和 Codex 官方文档的一部分吗？看到 OpenAI 收购了 OpenClaw 吗？看到 Claude 立刻添加了内存、语音和远程工作？

规划方面怎么样？还记得当年一群人发现实施前的规划非常有用，然后它被变成了核心功能吗？

是的......这些很有用！

还记得无尽的终止钩曾经非常有用吗，因为特工们不愿意做长期工作......然后 Codex 5.2 发布后，那个东西一夜之间就消失了？是的......

这就是你需要知道的全部......如果真的重要且有用，Claude 和 Codex 会实现它们！所以你不必太担心使用“新东西”或熟悉“新东西”。你甚至不需要“保持最新”。

帮我个忙。只要偶尔更新你喜欢的 CLI 工具，看看新增了哪些功能。这已经足够了。

## 压缩、上下文与假设

你们中有些人在与特工合作时会发现一个巨大的陷阱：有时他们看起来是地球上最聪明的生物，而有时你简直不敢相信自己被蒙蔽了眼睛。

聪明？这东西真是太蠢了！

主要区别在于经纪人是否需要做出任何假设或“填补空白”。直到今天，他们在“连接点”、“填补空白”或做出假设方面依然糟糕透顶。每当他们这样做时，立刻就能看出他们明显的状况变糟了。

claude.md 中最重要的规则之一是关于如何抓取上下文的规则，并指示你的代理在读取 claude.md 时首先阅读该规则（总是在压缩之后）。作为抓取上下文规则的一部分，有几个简单且有效的指导：重新阅读你的任务计划，并在继续前重新阅读与任务相关的文件。

## 让你的经纪人知道如何结束任务

我们对任务“完成”的时间有相当清晰的认识。对于智能体来说，当前智能最大的问题是它知道如何开始任务，却不知道如何结束任务。

这通常会导致非常令人沮丧的结果，代理人最终只实施了存根，然后就此结束。

测试对代理来说是一个非常好的里程碑，因为它们是确定性的，你可以设定非常明确的期望。除非这 X 次测试通过，否则你的任务还不算完成;而且你不允许修改测试。

然后，你只需审核测试，所有测试通过后你就能安心。你也可以自动化，但关键是——记住“任务结束”对人类来说很自然，但对代理来说却不然。

你知道最近还有什么成为任务的可行终点吗？截图+验证。你可以让代理在所有测试通过之前实现某个东西，然后让它截图并验证截图上的“设计或行为”。

这让你的代理人不断迭代，朝着你想要的设计努力，而不用担心第一次尝试就停下来！

自然的延伸是与代理人创建“合同”，并将其嵌入规则中。比如说，这个{TASK}\_CONTRACT.md 构成了你被允许终止会话之前必须完成的事情。在{TASK}\_CONTRACT.md 中，你需要指定测试、截图和其他验证，这些都是在你确认任务可以结束之前完成的！

## 永恒奔跑的特工

我经常被问到的一个问题是，人们是如何拥有这些24小时运行的代理，同时确保他们不会偏离目标的？

这里有个非常简单的方法。创建一个停止钩子，防止代理在{TASK}\_contract.md 的所有部分完成后终止会话。

如果你有100个这样的合同，且这些合同规格明确，且包含你想要构建的内容，那么你的停机机制将阻止代理终止，直到所有100个合同完成，包括所有需要执行的测试和验证！

专业提示：我觉得长时间的24小时训练并不适合“做事”。部分原因是，这种设计从结构上会强制上下文膨胀，通过引入无关合同的上下文进入会话！

所以，我不推荐。

这里有一种更好的代理自动化方式——每个合同开一个新会话。需要做什么时就签合同。

找一个编排层，负责在“需要做什么”时创建新合同，并创建一个新会话来处理该合同。

这将彻底改变你的代理体验。

# 不断迭代，不断迭代，再迭代

如果你雇佣了执行助理，你是不是期望你的助理从第一天起就知道你的排班？或者你喜欢的咖啡？你是不是在晚上6点吃晚餐，而不是晚上8点？显然不是。你的偏好是随着时间的调整而形成的。

你的经纪人也是一样。从最基础开始。别管复杂的结构或安全带了。给基础 CLI 一个机会。

然后，加入你的偏好。你是怎么做到的？

## 规则

如果你不想让你的经纪人做某件事，就把它写成规则。然后让你的经纪人知道你 CLAUDE.md 里的这条规则。比如：在写代码之前，先读“coding-rules”。MD“。规则可以嵌套，也可以有条件的！如果你在写代码，请阅读“coding-rules”。MD“，如果你在写测试，读”coding-test-rules“。MD“。如果你的测试失败了，可以读“coding-test-failing-rules”。MD“。你可以创建任意的逻辑分支来遵循规则，只要 CLAUDE.md 中有明确规定，Claude（和 codex）也会乐意跟随。

事实上，这是我给出的第一个实用建议：把你的 CLAUDE.md 当作一个逻辑嵌套的目录，告诉你在情景和结果下该从哪里找到上下文。它应尽可能简洁，只包含去哪里寻找上下文的 IF-ELSE。

如果你看到代理人做了什么而你不同意，就把它作为规则加入，告诉代理人在再次做那件事之前先阅读规则，它肯定不会再这样做了。

## 技能

技能就像规则，只不过它们不是编码偏好，而是更适合编码配方。如果你有特定的完成方式，你就想把它融入技能中。

事实上，人们常抱怨不知道客服如何解决问题，这让人感到害怕。如果你想让它变得确定性，可以让代理研究它如何解决问题，然后把它写成一项技能。你会看到代理对该问题的处理方式，并且可以在它现实生活中遇到问题之前就进行纠正或改进。

你如何让代理知道这项技能的存在？是的！你用 CLAUDE.md 说，当你看到这种情况并且需要处理这个时，读这个 SKILL.md。

## 应对规则与技能

你绝对需要不断为经纪人添加规则和技能。这就是你赋予它个性和记忆的方式，满足你的喜好。几乎其他所有东西都太过头了。

一旦你开始这样做，你的经纪人就会让你觉得自己像魔法一样。它会“按照你想要的方式”完成任务。然后你终于会感觉自己“理解”了代理工程。

然后......

你会看到性能再次开始下降。

这是怎么回事？！

慢点。随着规则和技能的增加，它们开始互相矛盾，或者代理的上下文过于膨胀。如果你需要代理在开始编程前读取 14 个 Markdown 文件，它也会遇到同样的问题，就是会有很多无用的信息。

那么，你是做什么的？

你来收拾。你告诉经纪人去做个水疗日，整合规则和技能，消除矛盾，通过询问你更新的偏好。

那时它会再次感觉像魔法一样。

就这样。这才是真正的秘诀。保持简单，使用规则、技能和 CLAUDE.md 作为目录，并严格关注它们的上下文和设计限制。

# 拥有结果

如今没有哪个经纪人是完美的。你可以把大部分设计和实现工作交给代理，但你必须对结果负责。

所以要小心......祝你玩得开心！

玩未来的玩具真是一种乐趣（当然还能做些严肃的事情）！
