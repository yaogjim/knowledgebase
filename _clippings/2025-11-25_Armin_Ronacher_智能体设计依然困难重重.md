# ## 智能体设计依然困难重重

## 智能体设计依然困难重重

我觉得现在或许是时候写下一些新学到的知识了。主要内容将围绕智能体的构建展开，同时也会涉及一些自动化编程工具的使用心得。

简而言之：构建智能体依然混乱不堪。一旦涉及实际工具使用，SDK 抽象层就会崩溃。自主管理缓存效果更佳，但不同模型间存在差异。强化学习最终承担的任务比预期更繁重，且必须严格隔离故障以防循环失控。基于类文件系统层的共享状态是重要基础架构。输出工具的设计出乎意料地棘手，而模型选择仍需视具体任务而定。

## 该选择哪种智能体开发工具包？

当你构建自己的智能体时，可以选择基于底层 SDK（如 OpenAI SDK 或 Anthropic SDK）进行开发，也可以选用更高层级的抽象方案，例如 Vercel AI SDK 或 Pydantic。我们之前的选择是采用 Vercel AI SDK，但仅使用其供应商抽象层，本质上 [由我们自主驱动智能体运行逻辑](https://ai-sdk.dev/cookbook/node/manual-agent-loop) 。目前 [我们](https://earendil.com/) 不会再次做出那样的选择。Vercel AI SDK 本身没有任何问题，但当你试图构建一个智能体时，会出现两个我们最初未曾预料到的情况：

首要问题是，不同模型之间的差异相当显著，以至于你需要构建自己的智能体抽象层。我们发现这些 SDK 提供的解决方案中，没有一种能为智能体构建出恰当的抽象。我认为部分原因在于，尽管基础智能体设计只是一个循环结构，但根据所提供工具的不同，会存在细微差别。这些差异影响着找到合适抽象层的难易程度（比如缓存控制、对强化的不同需求、工具提示、平台侧工具等）。由于合适的抽象尚未明确，使用专用平台的原生 SDK 能让你保持完全掌控。而某些高层级 SDK 要求你在其现有抽象之上进行构建，但这些抽象最终可能并非你真正所需。

我们在处理供应商端工具时，发现与 Vercel SDK 的协作也极具挑战性。其试图统一消息格式的做法并不完全奏效。例如，Anthropic 的网络搜索工具经常在使用 Vercel SDK 时破坏消息历史记录，我们至今尚未完全查明原因。此外，针对 Anthropic 的场景，直接使用其原生 SDK 而非 Vercel 的方案能让缓存管理变得简单许多——当操作出错时，错误提示信息也会清晰得多。

这种情况或许会改变，但目前我们在构建智能体时可能不会采用抽象层，至少要等到技术生态稍趋稳定。对我们而言，当前阶段的收益尚不足以覆盖其成本。

或许有人已经找到了答案。如果你读到此处并认为我的观点有误，请务必给我发邮件。我渴望学习。

## Caching Lessons

各平台在缓存处理上采取了截然不同的方式。关于这一点已有诸多讨论，但 Anthropic 的独特之处在于要求用户为缓存付费。它强制用户显式管理缓存点，这从根本上改变了从智能体工程层面与其交互的方式。起初我认为这种手动管理相当愚蠢——为什么平台不能自动处理？但现在我完全转变了看法，反而更青睐显式缓存管理。它让成本控制和缓存利用率变得高度可预测。

显式缓存让你能够实现一些在其他情况下难以完成的操作。例如，你可以拆分对话并让其同时朝两个不同方向展开。你还能够进行上下文编辑。虽然最佳策略尚不明确，但显然你拥有更多控制权，而我很欣赏这种掌控感。这也让理解底层智能体的成本变得更为容易。你可以更准确地预估缓存的利用效率，相比之下，其他平台的缓存效果往往难以预测。

我们在智能体中与 Anthropic 合作实现的缓存机制相当直接。一个缓存点设在系统提示之后。两个缓存点位于对话开头，其中最后一个会随着对话尾部移动而前移。此外，过程中还可以进行一些优化操作。

由于系统提示和工具选择现在必须基本保持静态，我们稍后会输入一条动态消息来提供诸如当前时间之类的信息。否则，这会破坏缓存。我们在循环中也更充分地利用了强化机制。

## 智能体循环中的强化机制

每次代理运行工具时，你不仅有机会返回工具产生的数据，还能向循环中反馈更多信息。例如，你可以提醒代理总体目标和各项任务的进度状态。当工具调用失败时，你还可以提供关于如何成功调用工具的提示。强化的另一个用途是向系统通报后台发生的状态变化。如果你的代理采用并行处理，可以在每次工具调用后，当状态发生变化且与完成任务相关时，注入相关信息。

有时，智能体仅需自我强化即可推进任务。以 Claude Code 为例，其待办事项写入工具就是一种自我强化工具。该工具仅从智能体处获取它认为应该执行的任务清单，并将输入内容原样输出。本质上这只是一个回声工具，并不执行其他操作。但这种方式远比在上下文开始时仅给出单一主任务及子任务、而期间发生过多干扰的情况更能有效驱动智能体前进。

当执行过程中环境发生对智能体不利的变化时，我们也会通过强化信号告知系统。例如，若智能体执行失败并从某步骤重试，但恢复操作基于损坏数据时，我们会注入提示信息，建议其回退若干步骤重新执行先前操作。

## Isolate Failures

若预期代码执行过程中会出现大量失败，可以通过两种方式将这些失败信息对上下文隐藏。其一是将可能需要迭代的任务单独运行：在子智能体中持续执行直至成功，仅反馈最终成功结果，并可附上已尝试但未奏效的简要方法总结。让智能体了解子任务中的失败经验很有价值，这些信息可输入后续任务，从而有效规避同类错误。

第二种选项并非所有智能体或基础模型都具备，但在 Anthropic 平台上可以实现上下文编辑功能。迄今为止，我们在上下文编辑方面尚未取得显著成效，但我们认为这是个值得深入探索的有趣方向。我们也非常期待了解其他使用者是否通过该功能获得成功。上下文编辑的精妙之处在于，它能够为后续迭代循环保留令牌资源。您可以从上下文中剔除那些无助于循环成功完成、仅对执行过程中某些尝试产生负面影响的失败记录。但正如我先前所述：让智能体理解失败原因同样重要，不过或许并不需要保留所有失败案例的完整状态和全部输出细节。

遗憾的是，上下文编辑会自动使缓存失效。这确实无法避免。因此，很难判断何时进行这种权衡能弥补清空缓存的额外成本。

## 子代理 / 子推理

正如我在本博客中多次提及，我们的大多数智能体都基于代码执行和代码生成。这确实需要为智能体提供一个存储数据的公共空间。我们选择的是文件系统——在我们的案例中是虚拟文件系统——但这需要不同的工具来访问它。当你拥有子智能体或子推理功能时，这一点尤为重要。

你应该尝试构建一个没有死胡同的智能体。所谓死胡同，是指任务只能在已构建的子工具内继续执行。例如，你可能开发了一个生成图像的工具，但这个工具只能将生成的图像再传递给另一个特定工具。这会产生问题——比如当你想要通过代码执行工具将这些图像打包成 zip 压缩文件时就会受阻。因此必须建立一套系统，使得图像生成工具能够将图像写入代码执行工具可读取的相同位置。本质上，这就是文件系统的功能。

显然，反过来也必须可行。你可能需要使用代码执行工具来解压一个 zip 压缩包，然后回到推理环节描述所有图片，以便下一步能再次回到代码执行，如此循环往复。文件系统正是我们为此设计的机制。但这要求工具在构建时能够接收指向虚拟文件系统的文件路径来进行操作。

因此，一个 `ExecuteCode` 工具将能够访问与 `RunInference` 工具相同的文件系统，后者可以获取该虚拟文件系统上文件的 `path` 路径。

## 输出工具的使用

我们设计智能体架构时，有个有趣的特点：它并不代表聊天会话。虽然最终会向用户或外界传递信息，但过程中发送的所有消息通常不会对外展示。关键在于：它是如何生成这些信息的？我们配备了一个核心工具——输出工具。智能体通过明确调用这个工具来与人类沟通，再通过提示词引导其使用时机。在我们的场景中，这个输出工具负责发送邮件。

但事实证明，这种做法也带来了其他挑战。其中之一是，与直接使用主代理循环的文本输出来与用户对话相比，控制输出工具的措辞和语气出人意料地困难。我无法确切解释原因，但推测这可能与这些模型的训练方式有关。

一次不太成功的尝试是让输出工具调用另一个轻量级 LLM（如 Gemini 2.5 Flash）来调整语气以符合我们的偏好。但这会增加延迟，实际上反而降低了输出质量。部分原因在于，模型本身的措辞就不够准确，而子工具又缺乏足够的上下文。将主智能体上下文的更多片段提供给子工具不仅成本高昂，也未能完全解决问题。有时还会在最终输出中泄露我们本不希望出现的信息，比如导致最终结果的中间步骤。

输出工具的另一个问题是，有时它根本不会调用工具。我们强制解决这个问题的方法之一是记录输出工具是否被调用过。如果循环结束时仍未使用输出工具，我们会注入一条强化信息来鼓励它使用输出工具。

## Model Choice

总的来说，我们目前对模型的选择并未发生巨大变化。我认为 Haiku 和 Sonnet 仍然是最佳的工具调用模型，因此它们非常适合用于智能体循环。这些模型在强化学习的具体表现方面也相对透明。另一个显而易见的选择是 Gemini 系列模型。截至目前，我们在主循环中使用 GPT 系列模型尚未取得显著成效。

对于需要处理大文档摘要、PDF 文件等任务的独立子工具（部分可能还需推理），我们目前推荐选用 Gemini 2.5 模型。该模型在图像信息提取方面表现尤为出色——毕竟 Sonnet 系列模型常会触发安全过滤器，这种干扰实在令人困扰。

还有一个显而易见的道理是，仅凭令牌成本并不能真正决定一个智能体的昂贵程度。更高效的工具调用器能用更少的令牌完成任务。虽然如今有些模型比 Sonnet 更便宜，但在循环使用中它们未必更经济。

但总的来说，过去几周并没有发生太多变化。

## Testing and Evals

我们发现测试与评估是当前最棘手的难题。这并不完全出乎意料，但智能体的自主特性使其更具挑战性。与普通提示不同，你无法仅通过外部系统完成评估，因为需要输入的信息量过于庞大。这意味着评估必须基于实际测试运行的可观测数据或埋点信息。迄今为止，我们尝试过的解决方案都未能证明其找到了正确方向。遗憾的是，目前我们尚未找到真正令人满意的方案。我期待能尽快解决这个问题，因为它正逐渐成为构建智能体过程中最令人挫败的环节。

## 编程智能体更新

至于我在编程助手方面的体验，其实并没有太大变化。主要的新进展是我正在更多地试用 [Amp](https://ampcode.com/) 。如果你好奇原因的话：并不是说它客观上比我正在使用的助手更好，而是我非常欣赏他们通过发布内容所展现的对助手的思考方式。像 Oracle 这样的不同子助手与主循环的交互设计得非常精妙，目前很少有其他框架能做到这一点。这也是我验证不同助手设计如何运作的好方法。与 Claude Code 类似，Amp 确实给人一种由实际使用自己工具的人所打造产品的感觉——我并不认为业内其他每个助手都做到了这一点。

## 我读过并觉得不错的内容

这不过是我觉得或许也值得分享的一些零散想法：

- [如果根本不需要 MCP 会怎样？](https://mariozechner.at/posts/2025-11-02-what-if-you-dont-need-mcp/) ：马里奥认为许多 MCP 服务器存在过度设计问题，它们包含的大型工具集会消耗大量上下文资源。针对浏览器智能体使用场景，他提出了一种极简主义方案——通过 Bash 执行简单的 CLI 工具（如启动、导航、执行 JS、截图），既能控制令牌使用量，又能保持工作流程灵活性。我 [基于此构建了 Claude/Amp 技能](https://github.com/mitsuhiko/agent-commands/tree/main/skills/web-browser) 。
- [“小型”开源项目的命运](https://nolanlawson.com/2025/11/16/the-fate-of-small-open-source/) ：作者认为，单一功能微型开源库的时代正走向终结，主要是因为平台内置 API 和 AI 工具已能按需生成简单工具。 [真他妈谢天谢地](https://lucumr.pocoo.org/2025/1/24/build-it-yourself/) 。
- [Tmux 就是爱](https://x.com/mitsuhiko/status/1991997262810218983) 。虽然没什么文章专门论述这一点，但简而言之 Tmux 非常棒。如果你有任何看起来像是智能体应该与之交互的互动系统，你都应该 [赋予它一些 Tmux 技能](https://github.com/mitsuhiko/agent-commands/tree/main/skills/tmux) 。
- [LLM API 是一个同步问题](/2025/11/22/llm-apis/) 。这个独立的认识篇幅过长，不适合放在这篇文章中，因此我另写了一篇专门讨论。
