# 注：本文同样适用于 `AGENTS.md` ，这是面向 OpenCode、Zed、Cursor

*注：本文同样适用于 `AGENTS.md`* ，这是面向 OpenCode、Zed、Cursor 和 Codex 等智能体与开发框架的开源版 `CLAUDE.md` 等效文件。

## \## 原则：LLMs（大多）是无状态的

LLMs 是无状态函数。它们的权重在用于推理时已被冻结，因此不会随时间推移而学习。模型对你的代码库的唯一了解就是你输入其中的标记。

类似地，编码助手工具（如 Claude Code）通常需要您显式管理智能体的记忆。 `CLAUDE.md` （或 `AGENTS.md` ）是默认情况下唯一会载入 *每次对话* 的文件。

**这具有三个重要含义：**

1.  在每个会话开始时，编程助手对你的代码库一无所知。
2.  每次启动会话时，都必须告知代理关于代码库需要了解的所有重要信息。
3.  `CLAUDE.md` 是实现此功能的首选方法。

## \## CLAUDE.md 让 Claude 融入你的代码库

由于 Claude 在每次会话开始时对你的代码库一无所知，你应该使用 `CLAUDE.md` 文件来引导 Claude 熟悉你的代码库。从宏观层面来看，这个文件应当涵盖：

- **内容说明** ：向 Claude 介绍技术栈、项目结构。为 Claude 提供代码库的导航图，这在单体仓库中尤为重要！说明应用模块、共享包的功能定位，让 Claude 明确各组件用途及代码检索路径
- **为何** ：向 Claude 阐明项目的 *宗旨* 以及代码仓库中各项内容的作用。项目的不同部分分别承担怎样的目标与功能？
- **操作方式** ：向 Claude 说明它应如何在项目中工作。例如，是否使用 `bun` 替代 `node` ？您需要包含所有必要信息，使其能真正对项目开展有意义的工作。Claude 如何验证其修改？如何运行测试、类型检查和编译步骤？

但关键在于方法！不要试图把所有 Claude 可能需要运行的指令都塞进 `CLAUDE.md` 文件里——这样只会适得其反。

## \## Claude 经常忽略 CLAUDE.md

无论你使用哪种模型，都可能发现 Claude 经常忽略你的 `CLAUDE.md` 文件内容。

您可以通过在 Claude 代码 CLI 与 Anthropic API 之间设置日志代理来亲自验证这一点，具体方法是使用 `ANTHROPIC_BASE_URL` 。Claude 代码会在用户消息中向智能体注入以下系统提示，同时附带您的 `CLAUDE.md` 文件：

```
<system-reminder>
 IMPORTANT: this context may or may not be relevant to your tasks. 
 You should not respond to this context unless it is highly relevant to your task.
</system-reminder>
```

因此，如果 Claude 判定您 `CLAUDE.md` 文件中的内容与当前任务无关，就会忽略这些内容。文件中包含的与当前工作任务的 **普适性** 越低的信息越多，Claude 忽略文件中指令的可能性就越大。

*Anthropic 为何要添加这个功能？* 虽然难以断言，但我们可以稍作推测。我们遇到的大多数 `CLAUDE.md` 文件都包含大量 *并非* 普遍适用的指令。许多用户将该文件视为对不满意行为添加"热修复"的途径，通过追加大量未必具有普适性的指令来实现。

我们只能推测，Claude 法典团队发现，通过指示 Claude 忽略不良指令，测试框架反而能产生更好的结果。

## \## 如何编写一份优秀的 CLAUDE.md 文件

以下章节将根据 [语境工程最佳实践](https://github.com/humanlayer/12-factor-agents/blob/d20c728368bf9c189d6d7aab704744decb6ec0cc/content/factor-03-own-your-context-window.md) ，提供一系列关于如何编写优质 `CLAUDE.md` 文件的建议。

*效果因人而异。* 并非所有规则都适用于每种配置。就像其他事情一样，偶尔打破规则也无妨……

1.  你明白何时以及为何可以打破规则
2.  你这么做自有你的道理

### 少即是多

人们很容易想把 Claude 可能需要运行的所有命令，以及代码规范和风格指南都塞进 `CLAUDE.md` 文件里。 **但我们不建议这样做。**

虽然这一课题尚未经过极其严谨的调研，但 [已有研究](https://arxiv.org/pdf/2507.11538) 表明以下几点：

1.  **前沿思维型 LLMs 能够以合理的一致性遵循约 150-200 条指令。** 较小模型能处理的指令数量少于较大模型，非思维型模型能处理的指令数量少于思维型模型。
2.  **较小模型的性能衰退速度更快、程度更剧烈** 。具体而言，随着指令数量增加，较小模型的指令遵循能力往往呈现指数级衰减，而前沿大模型仅表现出线性衰减（如下所示）。因此，我们不建议将较小模型用于多步骤任务或复杂的实施方案。
3.  **LLMs 更倾向于关注提示文本边缘的指令** ：位于最开头的部分（Claude 系统法典消息和 `CLAUDE.md` 文件），以及最末尾的部分（最近期的用户消息）。
4.  **随着指令数量增加，指令遵循质量会均匀下降** 。这意味着当你给 LLM 下达更多指令时，它并非简单地忽略较新的指令（即"文件中靠后的指令"），而是开始 **均匀地忽略所有指令** 。

![Instruction following](/blog/writing-a-good-claude-md/instructionfollowing.png)

我们对 Claude 法典系统的分析表明， **Claude 法典的系统提示包含约 50 条独立指令** 。根据您使用的模型不同，这已接近您的智能体可稳定遵循指令总量的三分之一——而这还不包括规则、插件、技能或用户消息的指令量。

这意味着你的 `CLAUDE.md` 文件应尽可能少地包含指令——理想情况下只包含那些普遍适用于你任务的指令。

### \### CLAUDE.md 文件长度与适用范围

在其他条件相同的情况下， **当 LLM 的上下文窗口充满专注、相关的内容时** （包括示例、相关文件、工具调用和工具结果），其任务表现会优于上下文窗口充斥大量无关信息的情况。

由于 `CLAUDE.md` 会应用于 *每个会话* 中，你应当确保其内容尽可能具有普适性。

例如，避免包含（比如）如何构建新数据库模式的说明——这在处理其他不相关事务时毫无意义，只会分散模型的注意力！

从长度来看， *少即是多* 的原则同样适用。虽然 Anthropic 对 `CLAUDE.md` 文件的具体长度没有官方建议，但普遍共识是最好控制在 300 行以内，越短越好。

在 HumanLayer，我们的根 `CLAUDE.md` 文件 *不足六十行* 。

### \### 渐进式呈现

撰写一份简洁的 `CLAUDE.md` 文件，涵盖您希望 Claude 了解的所有内容，可能颇具挑战性，尤其是在大型项目中。

为了解决这个问题，我们可以运用 **渐进式披露** 原则，确保 Claude 仅在需要时看到特定任务或项目的指令。

与其在 `CLAUDE.md` 文件中包含所有关于构建项目、运行测试、代码规范或其他重要背景的不同说明，我们建议将特定任务的说明保存在项目中的 *单独的 markdown 文件* 里，并使用自描述性的文件名。

For example:

```
agent_docs/
  |- building_the_project.md
  |- running_tests.md 
  |- code_conventions.md
  |- service_architecture.md
  |- database_schema.md
  |- service_communication_patterns.md
```

然后，在你的 `CLAUDE.md` 文件中，可以列出这些文件并附上简要说明，指示 Claude 判断哪些文件（如果有的话）相关，并在开始工作前阅读它们。或者，要求 Claude 先向你展示它想要阅读的文件，待你批准后再进行阅读。

**优先使用指针而非副本** 。尽可能不要在这些文件中包含代码片段——它们很快就会过时。相反，应包含 `文件:行号` 引用，将 Claude 指向权威的上下文。

从概念上讲，这与 [Claude 技能](https://code.claude.com/docs/en/skills) 的设计理念非常相似，不过技能更侧重于工具使用而非指令执行。

### Claude 是（不是）一个昂贵的代码检查工具

我们经常看到人们在 `CLAUDE.md` 文件中添加代码风格指南。 **切勿让 LLM 执行代码检查器的任务** 。与传统代码检查器和格式化工具相比，LLM 不仅成本相对高昂，而且 *极其* 缓慢。我们认为 *任何时候都应优先使用确定性工具* 。

代码风格指南不可避免地会在上下文窗口中塞入大量指令和多数无关的代码片段，这会降低 LLM 的性能和指令遵循能力，并耗尽你的上下文窗口。

**LLMs 是情境学习者** ！如果你的代码遵循特定的风格指南或模式，你会发现只需对代码库进行几次搜索（或准备一份优质的研究文档），你的智能体就会自然而然地遵循现有的代码模式和规范，无需额外指示。

如果你对此有强烈的执念，甚至可以考虑设置一个 [Claude 代码 `终止` 钩子](https://code.claude.com/docs/en/hooks#stop) ，让它运行你的格式化程序和代码检查工具，并将错误呈现给 Claude 进行修复。不要让 Claude 自己去寻找格式问题。

**加分项** ：使用能够自动修复问题的代码检查工具（我们推荐 Biome），并仔细调整可安全自动修复的规则，以实现最大程度的（安全）覆盖范围。

你也可以创建一个 [斜杠命令](https://code.claude.com/docs/en/slash-commands) ，其中包含你的代码规范，并让 Claude 关注版本控制中的变更，或者你的 `git status` 等类似内容。这样，你就可以分别处理实现和格式化。 **两者结合使用会带来更好的效果** 。

### \### 请勿使用 /init 或自动生成您的 CLAUDE.md

无论是 Claude Code 还是其他搭载 OpenCode 的工具，都提供了自动生成 `CLAUDE.md` 文件（或 `AGENTS.md` ）的功能。

由于 `CLAUDE.md` 会伴随 *每一次会话* 进入 Claude 的代码空间，它因此成为 **驾驭工具最关键的支点之一** ——其效果好坏，完全取决于你如何运用。

一行糟糕的代码只是糟糕的代码。但实施方案中的一行疏漏，可能催生出 **大量** 糟糕的代码。而研究中若出现对系统运作原理的误解，则可能导致方案中滋生大量缺陷，最终 **成倍放大** 为代码层面的问题。

但 `CLAUDE.md` 文件会影响 **工作流程的每个环节** 及其产生的所有成果。因此，我们认为您有必要仔细斟酌其中的每一行内容：

## \## In Conclusion

1.  `CLAUDE.md` 文件用于引导 Claude 熟悉您的代码库。它应明确项目的 **核心理念** 、 **核心内容** 和 **实现方式** 。
2.  **少即是多** 。虽然不应省略必要的指令，但应尽可能在文件中包含最少的指令。
3.  保持你的 `CLAUDE.md` **内容简洁且普适** 。
4.  采用 **渐进式披露** 策略——不要一次性告诉 Claude 所有可能用到的信息。相反，应当告知它 *如何查找* 关键信息，使其能在需要时自主检索并运用，从而避免上下文窗口或指令数量过度膨胀。
5.  Claude 不是代码检查工具。请使用专门的代码检查器和格式化工具，必要时可搭配 [钩子函数](https://code.claude.com/docs/en/hooks) 和 [斜杠命令](https://code.claude.com/docs/en/slash-commands) 等功能。
6.  **`CLAUDE.md` 是驾驭工具的最高杠杆支点** ，请避免自动生成。你应当精心雕琢其内容以获得最佳效果。
