# ### 我使用 Claude Code 的完整心得总结

### 我使用 Claude Code 的完整心得总结

Audio playback is not supported on your browser. Please upgrade.

我经常使用 Claude Code。

作为业余爱好者，我每周会在副业项目中用虚拟机运行几次，经常搭配 `--dangerously-skip-permissions` 随心编码脑海中的各种想法。而在专业领域，我的团队部分成员负责构建 AI 集成开发环境规则和工具，供工程团队使用——仅代码生成这一项，每月就要消耗 *数十亿个 token* 。

命令行智能体领域正变得日益拥挤，在 Claude Code、Gemini CLI、Cursor 和 Codex CLI 之间，真正的竞争似乎集中在 Anthropic 与 OpenAI 之间。但说实话，当我与其他开发者交流时，他们的选择往往取决于一些表面因素——比如某个“幸运”的功能实现，或是他们更偏爱的系统提示“氛围”。现阶段这些工具其实都已相当成熟。我也发现人们常常过度关注输出风格或界面设计，比如那种“您说得完全正确！”的奉承语气，在我看来并非重大缺陷，而是暗示你可能过于沉浸在这个圈子里的信号。我的目标始终是“发射后不管”——布置任务、设定上下文，然后放手让它自行完成。评判工具的标准应该最终落在合并请求的质量上，而非实现过程的具体细节。

在坚持使用 Claude Code 数月之后，本文是我对 Claude Code 整个生态系统的思考总结。我们将涵盖我使用的几乎所有功能（同样重要的是那些我不使用的功能），从基础的 `CLAUDE.md` 文件和自定义斜杠命令，到强大的子代理、钩子和 GitHub Actions 世界。 **这篇文章最终有点长，我建议将其更多地作为参考指南，而非需要通篇阅读的内容。**

## CLAUDE.md

在代码库中，要高效使用 Claude Code，最重要的文件是根目录下的 `CLAUDE.md` 。这个文件就像是智能体的"宪法"，是它理解你特定代码仓库运作方式的核心依据。

你如何处理这个文件取决于具体情境。对于我的业余项目，我会让 Claude 随心所欲地往里存放内容。

在我的专业工作中，我们单体代码库的 `CLAUDE.md` 文件被严格维护，目前体积为 13KB（我预计它很容易会增长到 25KB）。

- 它仅记录被我们 30%（任意设定）或更多工程师使用的工具和 API（其他工具则记录在特定产品或库的 markdown 文件中）
 
- 我们甚至开始为每个内部工具的文档有效分配最大令牌数，几乎就像向团队"出售广告位"一样。如果你无法简洁地说明你的工具，那它就不适合放入 `CLAUDE.md` 。
 

#### 技巧与常见误区

随着时间的推移，我们形成了一套明确而坚定的理念，用于编写高效的 `CLAUDE.md` 文件。

1.  **从规范入手，而非编写手册。** 你的 `CLAUDE.md` 文件应当从小处着手，根据 Claude 常犯的错误来记录规范。
 
2.  **切勿** `@` **引用文档文件。** 若其他位置有大量文档，人们常倾向于在 `CLAUDE.md` 中用 `@` 提及这些文件。这会导致每次运行时嵌入整个文件，拖垮上下文窗口。但若仅 *提及* 文件路径，Claude 往往会忽略。必须向智能体 *阐明* 读取文件的 *原因* 与 *时机* ：“处理复杂…用法或遇到 `FooBarError` 时，请参阅 `path/to/docs.md` 获取高级故障排除步骤。”
 
3.  **不要只说“绝不”。** 避免仅使用否定性限制，例如“绝不使用 `--foo-bar` 标志”。当智能体认为它 *必须* 使用该标志时，会陷入困境。务必提供替代方案。
 
4.  **将** `CLAUDE.md` **作为强制简化工具。** 若你的命令行指令复杂冗长，不必撰写长篇文档来解释——这只是在修补人为问题。不如编写一个具有清晰直观 API 的简易 bash 封装器，并为其编写文档。尽可能保持 `CLAUDE.md` 的简洁性，能有效倒逼代码库和内部工具的简化。
 

这是一个简化的概览：

```markup
# Monorepo

## Python
- Always ...
- Test with <command>
... 10 more ...

## <Internal CLI Tool>
... 10 bullets, focused on the 80% of use cases ...
- <usage example>
- Always ...
- Never <x>, prefer <Y>

For <complex usage> or <error> see path/to/<tool>_docs.md

...
```

最后，我们将此文件与 `AGENTS.md` 文件保持同步，以维持与我们工程师可能使用的其他 AI 集成开发环境的兼容性。

*如需获取更多为编码智能体编写 Markdown 的提示，请参阅 [《AI 无法读取你的文档》](https://blog.sshh.io/p/ai-cant-read-your-docs) [《AI 驱动的软件工程》](https://blog.sshh.io/p/ai-powered-software-engineering) 以及 [《Cursor（AI IDE）工作原理》](https://blog.sshh.io/p/how-cursor-ai-ide-works)*

**核心要点：** 将你的 `CLAUDE.md` 视为一套经过精心设计的高层级指导原则和方向标。用它来指引你在哪些方面需要投入开发更友好的人工智能（及人类）工具，而非试图将其变成一本面面俱到的操作手册。

## 紧凑、关联、清晰

我建议在编码会话中至少运行一次 `/context` 命令，以便了解你如何利用 200k token 的上下文窗口（即使使用 Sonnet-1M 模型，我也不完全信任整个上下文窗口能被有效利用）。对我们而言，在单体仓库中开启新会话会消耗约 2 万 token（10%）的基础成本，剩余的 18 万 token 用于代码修改——这部分额度消耗起来可能非常快。

我有三个主要的工作流程：

- `/compact` **（避免使用）：** 我尽可能避免使用此功能。自动压缩过程不透明、容易出错且优化不佳。
 
- `/clear` **\+** `/catchup` **（简易重启）：** 我的默认重启方式。先执行 `/clear` 清除状态，再运行自定义的 `/catchup` 命令让 Claude 读取我 git 分支中的所有变更文件。
 
- “文档与清空” **（复杂重启）：** 针对大型任务。我会让 Claude 将其计划和进度转储到 `.md` 文件中， `/clear` 清空状态，然后开启新会话让它读取 `.md` 文件继续工作。
 

**核心要点：** 不要依赖自动压缩功能。使用 `/clear` 进行简单重启，并通过“文档与清除”方法为复杂任务创建持久的外部“记忆”。

## 自定义斜杠命令

我将斜杠命令视为常用提示词的简易快捷方式，仅此而已。我的设置极为精简：

- `/catchup` ：我前面提到的命令。它只是提示 Claude 读取我当前 git 分支中所有已更改的文件。
 
- `/pr` ：一个简单的助手，用于清理我的代码、暂存更改并准备拉取请求。
 

在我看来，如果你有一长串复杂、自定义的斜杠命令，那你就创造了一个反模式。对我来说，像 Claude 这样的智能体的全部意义在于，你可以输入 *几乎* 任何你想要的内容，并获得一个有用、可合并的结果。一旦你强迫工程师（或非工程师）为了完成工作而去学习一套新的、需要查阅文档的魔法命令列表，那你就失败了。

**核心要点：** 斜杠命令应作为简单的个人快捷方式使用，而非替代构建更直观的 `CLAUDE.md` 和更完善工具化智能体的方案。

## Custom Subagents

理论上，自定义子代理是 Claude Code 最强大的上下文管理功能。其原理很简单：复杂任务需要 `X` 个输入上下文标记（例如如何运行测试），积累 `Y` 个工作上下文标记，并生成 `Z` 个标记的答案。运行 `N` 个任务意味着主窗口需要处理 `(X + Y + Z) * N` 个标记。

子代理解决方案是将 `(X + Y) * N` 的计算任务分配给专门的代理，这些代理仅返回最终的 `Z` 标记答案，从而保持主上下文的整洁。

我发现它们是一个强大的概念，但在实践中， *自定义* 子代理会引发两个新问题：

1.  **他们封锁了上下文：** 如果我创建一个 `PythonTests` 子代理，就等于把所有测试相关的上下文都从 *主* 代理中隐藏了。这样一来，主代理就无法全面思考代码变更的影响，现在它不得不调用子代理，才能知道如何验证自己的代码。
 
2.  **它们强制推行人工流程：** 更糟糕的是，这些功能迫使 Claude 遵循僵化的、由人类定义的工作流程。现在反而变成由我来规定它 *如何* 分配任务——这恰恰是我原本希望智能体为我解决的问题。
 

我更喜欢使用 Claude 内置的 `Task(...)` 功能来生成 *通用* 智能体的克隆副本。

我将所有关键上下文都存放在 `CLAUDE.md` 文件中，然后由 *主智能体* 自主决定何时以及如何将任务分配给自身的副本。这样既保留了子智能体节省上下文的优势，又避免了其弊端。该智能体能够动态地自我协调管理。

在我 [《构建多智能体系统（第二部分）》](https://blog.sshh.io/p/building-multi-agent-systems-part) 的文章中，我将此称为"主控-克隆"架构，并且我坚决认为它优于定制子智能体所推崇的"主导-专家"模式。

**关键要点：** 自定义子代理是脆弱的解决方案。应为主代理提供上下文（保存在 `CLAUDE.md` 中），让其运用自带的 `Task/Explore(...)` 功能来管理任务委派。

## 恢复、继续与历史

在简单层面上，我经常使用 `claude --resume` 和 `claude --continue` 。它们非常适合重启出现故障的终端或快速恢复旧会话。我常常会通过 `claude --resume` 恢复几天前的会话，只为让智能体总结它如何解决某个特定错误，随后将这些经验用于改进我们的 `CLAUDE.md` 和内部工具。

更深入地说，Claude Code 将所有会话历史存储在 `~/.claude/projects/` 中，以便利用原始的历史会话数据。我编写了一些脚本对这些日志进行元分析，寻找常见的异常、权限请求和错误模式，以帮助改进面向智能体的上下文。

**核心要点：** 使用 `claude --resume` 和 `claude --continue` 命令来重启会话，挖掘被遗忘的历史上下文。

## Hooks

钩子功能至关重要。虽然我在业余项目中不会使用它们，但在复杂的企业代码库中引导 Claude 时，它们起着关键作用。这些是确定性的"必须执行"规则，对 `CLAUDE.md` 中的"建议执行"内容形成了有力补充。

We use two types:

1.  **提交时拦截钩子：** 这是我们的核心策略。我们设置了 `PreToolUse` 钩子来包裹所有 `Bash(git commit)` 命令。它会检查 `/tmp/agent-pre-commit-pass` 文件是否存在——该文件 *仅当* 所有测试通过时才会由我们的测试脚本生成。若文件缺失，钩子将拦截提交操作，迫使 Claude 进入“测试-修复”循环，直至构建状态变绿。
 
2.  **提示钩子：** 这类轻量级非阻塞钩子能在智能体执行次优操作时提供“即发即弃”的反馈。
 

我们特意不使用“写入即拦截”的钩子（例如在 `Edit` 或 `Write` 操作时）。在智能体执行计划中途进行拦截会使其困惑甚至“受挫”，更有效的方式是让其完成工作后，在提交阶段检查最终成品。

**核心要点：** 使用钩子在提交时执行状态验证（ `block-at-submit` ）。避免在写入时阻塞——让智能体完成其计划，然后检查最终结果。

## Planning Mode

对于 AI 集成开发环境中的任何“重大”功能变更，规划都至关重要。

在我的个人兴趣项目中，我完全依赖内置的规划模式。这种方式能让我在 Claude 开始工作前就与之达成共识，明确 *如何* 构建某个功能，并设定需要暂停展示进度的"检查点"。经常使用这一模式，能培养出精准的直觉，让我懂得需要提供多少最小化上下文，才能让 Claude 制定出完善的计划而不搞砸具体实施。

在我们的工作单体仓库中，我们开始推广一款基于 Claude Code SDK 构建的定制规划工具。它类似于原生规划模式，但经过深度提示优化，使其输出与我们现有的技术设计格式保持一致。该工具还开箱即用地强制执行我们的内部最佳实践——从代码结构到数据隐私和安全性。这让我们的工程师能够像高级架构师一样“沉浸式规划”新功能（至少宣传上是这么说的）。

**关键要点：** 进行复杂修改时务必使用内置规划模式，以便在智能体开始工作前就实施方案达成一致。

## Skills

我赞同 [西蒙·威利森](https://simonwillison.net/2025/Oct/16/claude-skills/) 的观点： **技能（或许）比 MCP 更重要。**

如果你一直关注我的文章，就会知道我已经在大多数开发工作流中逐渐远离 MCP，转而倾向于构建简单的 CLI 工具（正如我在 [《AI 无法读懂你的文档》](https://blog.sshh.io/p/ai-cant-read-your-docs) 中所阐述的那样）。我对智能体自主性的心智模型已经演变为三个阶段：

1.  **单次提示：** 将所有上下文一次性塞给智能体。（脆弱，不可扩展）
 
2.  **工具调用：** 经典的智能体模型。我们为智能体精心设计工具，并将现实世界抽象化。（虽有所改进，但会催生新的抽象层和上下文瓶颈）。
 
3.  **[脚本编写](https://blog.sshh.io/i/167598476/scripting-agents) ：** 我们让智能体直接访问原始环境——包括二进制文件、脚本和文档——它能够 *实时编写代码* 与这些资源进行交互。
 

基于这一模型， **智能体技能** 自然成为下一项核心功能。它们正是"脚本层"的正式产品化形态。

如果像我一样，你已经更倾向于使用 CLI 而非 MCP，那么你其实一直在潜移默化中享受着技能带来的好处。 `SKILL.md` 文件只是用一种更有条理、可共享且易于发现的方式来记录这些 CLI 和脚本，并将它们暴露给智能体。

**核心要点：** 技能是最合适的抽象层级。它们将基于“脚本”的智能体模型规范化，这种模型比 MCP 所代表的僵化、类 API 式模型更具鲁棒性和灵活性。

## MCP（模型上下文协议）

技能的出现并不意味着 MCP 已死（另见 [《MCP 的全面症结》](https://blog.sshh.io/p/everything-wrong-with-mcp) ）。过去，许多人构建了糟糕且上下文繁重的 MCP，包含数十种工具，这些工具仅仅是对 REST API 的简单映射（ `read_thing_a()` 、 `read_thing_b()` 、 `update_thing_c()` ）。

“脚本”模型（现已被技能正式化）更胜一筹，但它需要一种安全的方式来访问环境。在我看来，这正是 MCP 全新且更专注的角色定位。

MCP 不应是臃肿的 API，而应成为简洁安全的中枢，提供少量强大高效的工具：

- `download_raw_data(filters…)`
 
- `take_sensitive_gated_action(args…)`
 
- `execute_code_in_environment_with_state(code…)`
 

在这种模式下，MCP 的任务不是为智能体抽象现实，而是管理认证、网络和安全边界，然后退居幕后。它为智能体提供 *入口点* ，智能体随后利用其脚本和 `markdown` 上下文来完成实际工作。

我目前仍在使用的唯一 MCP 是用于 [Playwright](https://github.com/microsoft/playwright-mcp) 的——这很合理，因为它是一个复杂的有状态环境。我所有的无状态工具（如 Jira、AWS、GitHub）都已迁移至简单的命令行界面。

**核心要点：** 选用充当数据网关的 MCP 工具。为智能体配备一两个高层级工具（如原始数据转储 API），使其能够基于这些工具编写脚本来操作数据。

## Claude Code SDK

Claude Code 不仅是一个交互式命令行工具，更是构建全新智能体的强大开发套件——无论是编程任务还是非编程任务皆可胜任。在大多数新兴趣项目中，我已开始将其作为默认的智能体框架，取代了 LangChain/CrewAI 等工具。

我主要通过三种方式使用它：

1.  **大规模并行脚本处理：** 面对大型重构、缺陷修复或迁移任务时，我不会采用交互式对话模式，而是编写调用 `claude -p “in /pathA change all refs from foo to bar”` 的简易 bash 脚本进行并行处理。这种方式比试图让主智能体管理数十个子任务更具可扩展性和可控性。
 
2.  **构建内部聊天工具：** 该 SDK 非常适合将复杂流程封装成简易聊天界面，供非技术用户使用。就像安装程序在出错时，能自动回退至 Claude Code SDK 直接为用户 *修复* 问题。又或是我们内部的“ [家庭版 v0](http://v0.dev/) ”工具，让设计团队能在自研 UI 框架中沉浸式编写前端原型，既确保创意高保真呈现，又让代码能更直接地应用于前端生产环境。
 
3.  **快速智能体原型开发：** 这是我最常用的场景，不仅限于编程。每当产生任何智能体任务的构想（比如利用自定义 CLI 或 MCP 的"威胁调查智能体"），我都会通过 Claude Code SDK 快速搭建测试原型，待验证可行后再投入完整的部署框架建设。
 

**核心要点：** Claude Code SDK 是一款功能强大的通用智能体框架。它适用于批量处理代码、构建内部工具，以及在采用更复杂框架 *之前* 快速搭建智能体原型。

## Claude Code GHA

Claude Code GitHub Action（GHA）可以说是我最钟爱却又最被低估的功能之一。它的理念很简单：就是在 GHA 中运行 Claude Code。但正是这种简洁性让它如此强大。

这类似于 [Cursor 的后台代理](https://cursor.com/docs/cloud-agent) 或 Codex 托管的网页界面，但可定制性远超前者。您可以完全控制整个容器和环境，不仅能获取更多数据访问权限，更重要的是提供了比其他任何产品都更强大的沙箱和审计控制功能。此外，它还支持 Hooks 和 MCP 等所有高级特性。

我们已利用它构建了自定义的“随处发起 PR”工具。用户可以从 Slack、Jira 甚至 CloudWatch 警报中触发 PR，GHA 将自动修复错误或添加功能，并返回一个经过完整测试的 PR [1](#fn:1) 。

由于 GHA 日志是完整的代理日志，我们制定了运维流程，定期在公司层面审查这些日志，以发现常见错误、bash 错误或不符合规范的工程实践。这形成了一个数据驱动的飞轮效应：发现缺陷 -> 改进 CLAUDE.md/CLI 工具 -> 优化代理性能。

```markup
$ query-claude-gha-logs --since 5d | claude -p “see what the other claudes were getting stuck on and fix it, then put up a PR“
```

**核心要点：** GHA 是将 Claude Code 投入实战应用的终极方案，它让这项技术从个人工具蜕变为工程系统中可审计、能自我进化的核心组件。

## settings.json

最后，我有一些特定的 `settings.json` 配置，发现它们对业余爱好和专业工作都至关重要。

- `HTTPS_PROXY` / `HTTP_PROXY` ：这对调试非常有用。我会用它来检查原始流量，准确查看 Claude 发送的具体提示内容。对于后台代理而言，它也是实现精细化网络沙箱隔离的强大工具。
 
- `MCP_TOOL_TIMEOUT` / `BASH_MAX_TIMEOUT_MS` ：我会调高这些值。我喜欢运行耗时较长、结构复杂的命令，而默认的超时设置往往过于保守。说实话，现在既然有了 bash 后台任务功能，不确定是否还需要这样设置，但我还是保留这个习惯以防万一。
 
- `ANTHROPIC_API_KEY` ：工作中我们使用企业级 API 密钥（ [通过 apiKeyHelper](https://www.reddit.com/r/ClaudeAI/comments/1jwvssa/comment/mtt0urz/?utm_source=share&utm_medium=web3x&utm_name=web3xcss&utm_term=1&utm_content=share_button) ）。这使我们的授权模式从“按席位计费”转变为“按用量计费”，更符合我们的工作方式。
 
 - 这解释了开发者使用量 *巨大* 的差异（我们观察到工程师之间的差距高达 1:100 倍）。
 
 - 它让工程师能够在我们的单一企业账户下，对非 Claude 代码的 LLM 脚本进行调试。
 
- `“权限”` ：我会定期自查允许 Claude 自动运行的命令列表。
 

**要点：** 你的 `settings.json` 是进行高级自定义的强大工具。
