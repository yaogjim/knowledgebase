# 代理的上下文工程

**YouTube 视频链接:** https://www.youtube.com/watch?v=sNBk_aCMg7Y

---

大家好，我是 LangChain 的 Lance Martin。我想谈谈几个通用的上下文工程（Context Engineering）原则，以及它们如何在各种流行的代理（Agent）中体现，比如 Manus、Claude Code，以及我们最近发布的 Deep Agents 包和命令行界面（CLI）。

### 代理（Agent）

首先，代理可以简单地理解为在一个循环中调用工具的大语言模型（LLM）。一个 LLM 进行工具调用，工具被执行，从工具得到的观察结果（Observation）返回给 LLM。这个过程会一直持续，直到满足某个终止条件。

### 挑战

现在，AI 代理能够执行的任务长度越来越长。来自 METR 的一个很好的研究结果表明，任务长度大约每 7 个月翻一番。

这里的挑战在于，随着代理承担更长的任务，你会累积更多的工具结果。例如，Manus 提到，平均一个 Manus 任务包含超过 50 次工具调用。同样，Anthropic 也提到，生产环境中的代理通常会有数百轮的交互。

问题是，当你用所有这些不同工具调用的结果来填充上下文窗口时，你需要在每一轮都将所有之前的工具结果传回给模型。因此，运行代理的成本和延迟可能会急剧增加。

不仅如此，性能也可能下降。Chrome 有一份关于“上下文腐烂”（Context Rot）的精彩报告，其中讨论了性能如何随着上下文长度的增加而下降。

我们看到的是，代理的设计越来越多地采用一些不同的原则来解决这个问题。

### 代理组件（Agent Harness）

当然，代理有几个常见的原语（primitives）：

*   **模型 (Model)**
*   **提示 (Prompt)**
*   **工具 (Tools)**
*   **钩子 (Hooks)**

以 Claude Code 为例，它使用 Claude 系列模型。它的系统提示是公开的，你可以通过这里的链接查看（我会确保这个文档在视频描述中）。它大约有十几个原生工具，并且它允许使用钩子（Hooks），这些钩子基本上是可以在美国东部夏令时间代理生命周期的不同点（例如，在每次工具调用之前或之后）以编程方式运行的脚本。

我们的 Deep Agents 包和 Deep Agents CLI 的设置也类似，都使用了这些原语。这个包允许使用任何模型提供商，而 CLI 目前使用 OpenAI 和 Anthropic。你可以看到提示，它们都是开源的。它分别为包和 CLI 使用了 8 个和 11 个原生工具，我稍后会详细展示。我们也允许在代理生命周期的不同点使用钩子。

### 上下文工程原则

现在，考虑到构成我们所谓的“代理组件”的这些原语，我们看到了哪些跨不同代理的通用技术来管理上下文腐烂和由多轮工具调用累积的 token 问题呢？

“上下文工程”是一个广义的术语，涵盖了许多这些原则。Karpathy 在这里很好地概述了它：“上下文工程是为下一步填充上下文窗口提供恰到好处的信息的精巧艺术和科学。” 这非常适用于代理，你试图引导代理沿着一个动作轨迹，做出正确的下一次工具调用。

我喜欢提炼出的三个常见原则是：**卸载（Offload）**、**减少（Reduce）** 和 **隔离（Isolate）**。

1.  **卸载 (Offload)**：将内容从 LLM 上下文窗口移动到外部系统，如文件系统。
2.  **减少 (Reduce)**：减小传递给 LLM 的上下文的大小。
3.  **隔离 (Isolate)**：为任务隔离上下文窗口。

### 卸载上下文（Offload Context）

#### 将上下文卸载到文件系统

首先，卸载上下文。我们反复看到的一个趋势是，让代理能够访问文件系统非常有用。这让代理能够在长时间运行的任务中保存和回忆信息。

这很直观。我在这里分享了一个来自 Anthropic 多代理研究的链接，他们基本上让研究员代理写一个计划，把它写入一个文件，然后去做一堆工作。然后，在一些子代理完成工作后，它们只需检索那个计划，确保所有事情都已处理。所以你可以写入文件，并在需要重新强化已制定的计划时，再把它读回上下文中。

这对于确保你不会忘记计划中的特定步骤非常有用，通过将其外部化到文件中，再读回上下文中，你确保了它的持久性，并且代理可以更容易地被引导。因为你只是在需要时有选择地把它拉回上下文窗口，以帮助代理保持在正轨上。

关于文件系统的另一个有趣之处是，它通常在不同的代理调用之间是持久的。例如，如果你在笔记本电脑上本地运行 Claude Code，Claude Code 可以随时引用这个 `claude.md` 文件，它可以存在于项目级别，也有一个全局的 `claude.md`。这个 `claude.md` 可以存储你想在所有与 Claude Code 的不同交互中都持久化的信息。

Manus 也使用同样的想法。当然，Manus 是远程运行的，所以它使用一个包含文件系统的沙箱环境，让代理能够访问一台计算机，并且它支持用户内存。

Deep Agents 包允许使用不同的后端。你可以使用 LangGraph 的状态对象，它只存在于内存中，或者你可以使用文件系统后端，例如你的本地机器。Deep Agents CLI 很像在你笔记本上运行的 Claude Code，它只使用你的本地文件系统作为后端。Deep Agents CLI 还支持通过一个 `memories` 目录以及一个 `agent.md` 文件来实现记忆功能。

我们反复看到的原则是，赋予代理将上下文卸载到文件系统的能力有很多好处。你可以在长时间的轨迹中持久化信息，也可以在不同的代理调用之间持久化上下文，比如在 `claude.md`、`agent.md` 文件中，或者在 Deep Agents CLI 的 `memories` 目录中。

#### 将动作从工具卸载到文件系统中的脚本

文件系统的另一个好处是，你实际上可以将动作从工具卸载到脚本中。

这是什么意思呢？我们希望代理执行动作。假设我们想给一个代理 10 种不同的动作。通常，你会想到，好吧，对于每一种动作，我都会定义一个独特的工具，我会把所有这些工具都绑定到代理上。所以我就有了一个带有 10 个不同工具的代理。现在，该代理中的 LLM 必须确定何时使用这 10 个工具中的每一个，而且你还必须将所有这些工具的指令加载到系统提示中。

所以这里有两个问题。一是关于使用哪个工具会产生混淆，二是你正在用一大堆工具描述来“臃肿”你的指令。现在，你看，对于 3、4 个甚至 10 个工具来说，这不算大问题。但如果我们谈论数百个工具，这可能会在工具描述上花费大量的 token。

所以，我们在与 Manus 的网络研讨会中深入探讨了一个原则，那就是实际上保持函数调用层非常轻量。只给代理少数几个函数来调用，但要确保它们是非常通用、原子化的函数，可以做很多事情。然后将大量的动作推送到外部，比如文件系统中的脚本。

例如，Manus 给了代理一个 bash 工具和文件系统操作工具。有了这两样东西，它就可以使用各种工具来导航文件系统，搜索一个脚本目录，并使用 bash 工具执行任何一个脚本。所以，通过三四个用于文件操作和代码执行的简单工具，它就可以执行大量由你提供的脚本所指定的动作。这是一种在不向系统提示中添加大量工具描述，也不必绑定额外工具的情况下，显著扩展代理动作空间的方法。

这个原则我们反复看到。如果你看 Claude Code，Boris Cherny 和 Cat Wu——Claude Code 的工程和产品负责人——最近在一个很棒的播客上提到，Claude Code 只用了大约十几个工具。当你使用它时你也能看到，它使用 glob、grep、bash、fetch 来获取 URL，但它并没用那么多工具，就只有十几个。Manus 使用的工具不到 20 个。对于 Deep Agents，我们的包里实际上只有 8 个原生工具，CLI 有 11 个原生工具，我下面会展示。

与此相关的一个想法是“渐进式披露”（progressive disclosure）动作。Anthropic 在他们最近发布的“技能”（Skills）中专门讨论了这一点。

Claude 的技能非常简单，就是一个 `skills` 文件夹，里面有一堆子文件夹，每个子文件夹都是一个特定的技能。每个子文件夹里都有一个 `skill.md` 文件，一个 Markdown 文件，带有一个头部。头部用非常简洁的语言解释了该技能的作用。只有这个头部被加载到 Claude Code 的初始上下文中。你可以在这个图表中看到，这正是他们展示的。所以，对于每个可用的技能，都有一小段简短的描述。在 Claude Skills 的情况下，如果 Claude 想要使用任何给定的技能，它就可以有选择地读取完整的 `skill.md` 文件。同样，只有头部被默认读入系统提示。如果 Claude 想要实际执行一个技能，它会读取完整的 `skill.md` 文件。那个 `skill.md` 文件可以引用同一技能目录中的任何其他文件。所以它可以包含脚本，也可以包含其他包含更多上下文的文件。

所以这很巧妙，因为 Claude 只需用它的 bash 工具，就可以读取 `skill.md` 文件，然后执行该技能文件夹中的任何脚本，或者读取其中的任何其他文件。所以我认为这是一种非常简单的方式，让代理能够访问不同的动作，既节省了 token，因为它是有选择地、渐进地披露的——只有在 Claude 需要该技能时才披露——而且它只使用了简单的内置工具，比如 bash 工具和一些文件操作工具。

所以 Manus 也使用了非常相似的原则。Manus 代理可以访问大量不同的脚本，并且它可以利用其原生的文件搜索和 bash 工具，按需浏览该目录来发现这些脚本。我们还没有在 Deep Agents CLI 中实现“技能”这个概念，但我现在正在努力添加它，因为它是一种非常好的方式，让代理能够访问大量动作，同时又不会用指令来“臃肿”其上下文窗口，也不必绑定额外的工具。

### 减少上下文

现在让我们谈谈减少上下文。这里有三个有趣的想法：压缩（compaction）、总结（summarization）和过滤（filtering）。

首先，我想谈谈 Manus 的做法。Manus 使用了“压缩”这个想法。左边展示的是一个工具调用和工具结果的轨迹。当然，工具结果可能包含大量 token。他们所做的就是，他们将旧的工具结果压缩，方法是将其完整结果保存到一个文件中，然后在消息历史中只引用该文件。现在，他们只对你所谓的已经“陈旧”的、已经被处理过的工具结果这样做。但这是减少消息历史中 token 的一种很好的方式。

这是他们展示的一张很棒的图表。想象一下你的代理正在运行，它执行了很多轮次。所以在一定数量的轮次之后，你非常接近 LLM 的上下文窗口。这时他们就应用这种压缩。他们把所有那些“臃肿”了消息历史的历史工具结果，把它们全部压缩下来，卸载到文件系统。这显著降低了整体上下文的使用率。代理继续运行，这个过程逐渐饱和，然后他们应用总结。

总结会查看整个消息历史，包括完整的工具结果消息，并将其全部总结成一个更紧凑、精炼的摘要，然后代理可以继续使用这个摘要前进。

一个重要的点是，这个压缩步骤是可逆的，因为你可以随时回去查看保存在这些文件中的原始工具结果。这是使用文件系统的另一个好处。但是，总结则不是可逆的。所以这是一个需要仔细考虑的步骤，因为当你做总结时，你必然会丢失信息。

你会看到 Anthropic 也采用了这些想法。Anthropic 最近推出了“上下文编辑”（context editing），它只是以一种可配置的方式修剪旧工具结果的消息历史。而 Claude Code 在你达到上下文窗口的约 95% 时会应用总结。

Deep Agents 包通过“总结中间件”（SummarizationMiddleware）来应用总结。它会在达到某个阈值后自动启动，比如 170k token，并且会保留一定数量的最新消息。当然，这一切都是开源和可配置的。

Deep Agents 包和 CLI 中采用的另一个方法是，文件系统中间件（FileSystemMiddleware）实际上会过滤掉大的工具结果。这是防止过大的工具结果被直接传递给 LLM 的一种好方法。

### 隔离上下文

最后，让我们谈谈上下文隔离。这是我们反复看到的一种技术。这个想法很简单。代理执行的许多任务可以被分配给一个子代理。该子代理有自己的上下文窗口。所以它可以从一个全新的状态开始处理一个特定的任务，特别是如果那个任务是很好地自包含的。执行该任务，然后只将输出返回给父代理。这就是这里展示的第一个模式，Manus 也讨论过，这种通信模式。你有一个父代理或主代理，它想要生成一个子代理来做某个任务。它将一些指令传递给那个子代理，子代理自己运行，然后将结果传回主代理。这是一个非常常见的模式。

这里有一些细微差别。有时你希望与子代理共享更多的上下文。实际上，Manus 允许共享父代理的完整消息历史给子代理。同样，对于 Deep Agents CLI，子代理实际上可以访问与父代理相同的（共享的）文件系统。所以它们之间有一些共享的上下文。

### 总结

总而言之，代理组件通常至少采用三种原则来管理上下文：卸载、减少和隔离。

一些最常见的上下文卸载想法包括使用文件系统。我们看到 Claude Code、Manus 和 Deep Agents CLI 都支持使用文件系统。启用用户记忆，这直观上是跨代理调用记住信息的能力。Claude 用 `claude.md` 实现，Deep Agents CLI 有一个 `memories` 目录和 `agent.md`，Manus 支持跨会话记忆。

使用最少的工具。这可以在工具描述方面显著节省 token，并最大限度地减少代理在不同工具之间需要做出的决策数量。Claude Code 大约使用 12 个工具，Manus 少于 20 个，Deep Agents CLI 有 11 个。

给代理一台计算机，即一个 bash 工具。所有这些代理组件都这样做。

渐进式披露动作。Claude Code 通过“技能”实现，Manus 通过让代理访问一个包含大量不同脚本的目录，并让它根据需要使用其现有的文件系统和 bash 工具来浏览该目录来实现。Deep Agents CLI 的“技能”功能正在开发中。

关于压缩，即修剪旧的工具消息，Manus 肯定会这样做。Claude SDK 支持这个想法，他们称之为“上下文编辑”，我假设这在 Claude Code 中被使用，但不完全确定，所以我应该把它标记为黄色，因为我不是百分之百确定，但我猜它正在被使用。我们确切知道的是，Claude Code 在达到上下文窗口的约 95% 时会进行总结。Manus 这样做，Deep Agents CLI 也这样做。

所有这三者都支持子代理，用于将不同任务隔离到独特的上下文窗口中。

Deep Agents CLI 是开源的，欢迎贡献。在一个可以与许多不同模型一起使用的开源组件中尝试和应用这些想法是很有趣的。

希望这个关于这些原则如何在不同流行代理组件中运作，以及它们如何被用于 Deep Agents CLI 的概述对你有用。任何问题或贡献都非常欢迎。谢谢。
