人工智能代理开发的格局正在快速演变。我们已不再局限于单轮对话机器人的原型设计，如今各组织正部署精密的自主代理来处理 **长期任务** ：自动化工作流程、开展深度研究以及维护复杂代码库。

这一雄心立刻遇到了瓶颈： **上下文** 。

随着智能体运行时间增长，需要追踪的信息量——对话记录、工具输出、外部文档、中间推理——会 **呈指数级暴增**

要构建 **可靠、高效且可调试** 的生产级智能体，业界正在探索一门新学科：

**语境工程** ——将语境视为具有独立架构、生命周期和约束条件的一等公民系统。

基于我们在扩展复杂单智能体或多智能体系统方面的经验，我们设计并优化了 [**Google 智能体开发套件（ADK）**](https://github.com/google/adk-python) 中的上下文堆栈，以支持这一规范。ADK 是一个开源、原生支持多智能体的框架，旨在让 **主动上下文工程** 在实际系统中得以实现。

### 扩展瓶颈

大容量上下文窗口有助于解决与上下文相关的问题，但无法应对所有此类问题。实践中，那种 **将所有内容塞进一个巨型提示词** 的简单模式，会在三重压力下崩溃：

1. **成本与延迟螺旋上升：** 模型成本和首词生成时间随上下文规模快速攀升。将原始历史记录和冗长的工具负载"硬塞"进上下文窗口，会导致智能体运行速度极慢且成本高昂。
2. **信号衰减（"迷失在中间"）：** 当上下文窗口充斥着无关日志、陈旧工具输出或过时状态时，会分散模型的注意力，使其固着于过往模式而非当前指令。为确保决策的稳健性，我们必须最大化相关信息的密度。
3. **物理限制：** 现实世界的工作负载——包含完整的 RAG 结果、中间产物和长对话记录——最终会超出最大固定窗口的承载能力。

单纯增加令牌数量只能拖延时间，却无法改变曲线的走势。要实现规模化，我们需要改变 **上下文的表示和管理方式** ，而不仅仅是往单次调用中塞入更多内容。

### 设计理念：将上下文视为编译视图

在上一代智能体框架中，上下文被当作可变的字符串缓冲区处理。而 ADK 基于一个不同的核心理念构建： **上下文是对更丰富的有状态系统的编译视图。**

In that view:

- **会话、记忆与工件（文件）** 是交互的 *源头* ——承载着完整结构化的互动状态及其数据。
- **流程与处理器** 构成了 *编译器流水线* ——一系列改变状态的转换环节。
- **工作上下文** 是您为本次调用向 LLM 交付的 *编译视图* 。

一旦采纳这种思维模式，语境工程就不再是提示词的技巧堆砌，而开始呈现出系统工程的特质。你将不得不思考那些经典的系统问题： *中间表示形式是什么？在哪个环节进行压缩？如何让转换过程可观测？*

ADK 的架构通过三大设计原则回应了这些问题：

- **存储与呈现分离：** 我们将持久化状态（会话）与单次调用视图（工作上下文）进行区分。这使您能够独立演进存储架构和提示词格式。
- **显式转换：** 上下文通过命名有序的处理器构建，而非临时字符串拼接。这使得"编译"步骤可观察、可测试。
- **默认范围限制：** 每次模型调用和子智能体仅能访问所需的最小上下文。智能体必须通过工具明确获取更多信息，而非默认接收海量数据。

ADK 的分层结构、关联机制以及多智能体交接语义——本质上正是对这套"编译器"理论及其三大原则的应用实践

- **结构** ——一种分层模型，将信息存储方式与模型所见内容相分离。
- **相关性** ——由智能体与人工共同决定 当下 重要事项的控制机制。
- **多智能体上下文** ——用于在智能体间传递正确上下文片段的显式语义规范。

接下来的章节将逐一探讨这些核心支柱。

### 1\. 结构：分层模型

大多数早期智能体系统都默认采用 **单一上下文窗口** 。而 ADK 反其道而行，它将存储与呈现分离，并将上下文组织成不同的层级，每个层级各司其职：

- **工作上下文** ——本次模型调用的即时指令：系统指令、智能体身份、选定历史记录、工具输出、可选记忆结果以及工件引用。
- **会话** ——交互的 **持久化日志** ：每条用户消息、智能体回复、工具调用、工具结果、控制信号和错误，都以结构化事件对象的形式被记录。
- **记忆** ——超越单次会话的长期、 **可检索知识** ：包括用户偏好和过往对话记录。
- **构件** ——与会话或用户相关的大型二进制或文本数据（文件、日志、图像），通过名称和版本进行寻址，而非直接粘贴到提示中。

### 1.1 工作上下文作为可重新计算的视图

每次调用时，ADK 都会从底层状态重建工作上下文。它从指令和身份信息开始，拉取选定的会话事件，并可选择附加记忆结果。这种视图具有 **临时性** （调用结束后即丢弃）、 **可配置性** （无需迁移存储即可更改格式）以及 **模型无关性** 。

这种灵活性是编译器视角带来的首要优势：你不再硬编码"提示词"，而是将其视为可迭代优化的派生表达。

### 1.2 流与处理器：将上下文处理构建为流水线

一旦将存储与呈现分离，就需要一套机制将前者"编译"为后者。在 ADK 中，每个基于 LLM 的智能体都由 **LLM 流程** 驱动，该流程维护着处理器的有序列表。

### 1.3 会话与事件：结构化、语言无关的历史记录

ADK 会话代表对话或工作流实例的最终状态。具体而言，它充当会话元数据（ID、应用名称）的容器、结构化变量的状态暂存区，以及最重要的——按时间顺序排列的 **事件** 列表。

ADK 不存储原始提示字符串，而是将每次交互——用户消息、智能体回复、工具调用、结果、控制信号和错误——都捕获为强类型事件记录。这种结构化设计带来三大显著优势：

- **模型无关性：** 由于存储格式与提示格式解耦，您无需重写历史记录即可更换底层模型。
- **丰富操作：** 压缩、时间旅行调试和内存摄取等下游组件能够直接处理丰富的事件流，无需解析不透明的文本。
- **可观测性：** 为数据分析提供了直观界面，便于精确检查状态转换与操作过程。

连接此会话与工作上下文之间的桥梁是 `contents` 处理器。它通过执行三个关键步骤，承担将会话转化为工作上下文历史部分的核心任务：

- **选择：** 它对事件流进行过滤，剔除不应传至模型的无关事件、不完整事件及框架噪声。
- **转换处理：** 将剩余事件展平为具有正确角色（用户/助手/工具）的 `Content` 对象，并针对所使用的特定模型 API 添加标注。
- **注入：** 它将格式化后的对话历史写入 `llm_request.contents` ，确保下游处理器（包括模型自身）能获得清晰连贯的对话轨迹。

在此架构中，会话是您的 **基准事实** ；工作上下文仅是一个 **计算投影** ，您可以随时间推移不断优化和完善。

### 1.4 会话层的上下文压缩与过滤

若持续无限制地追加原始事件，延迟和令牌使用量必将失控激增。ADK 的上下文压缩功能在会话层直面这一问题。

当达到可配置的阈值（例如调用次数）时，ADK 会触发异步处理流程。它利用 LLM 在滑动窗口（由压缩间隔和重叠大小定义）内对较早的事件进行摘要，并将生成的摘要作为带有"压缩"操作的新事件写回会话中。关键在于，这使得系统能够修剪或降低已摘要原始事件的优先级。

由于压缩操作直接作用于事件流本身，其优势会向下游层层传递：

- **可扩展性：** 即使面对极长时间运行的对话，会话仍能保持物理层面的可管理性。
- **简洁视图：** `contents` 处理器自动在已压缩的历史记录上运行，无需在查询时执行复杂逻辑。
- **解耦：** 无需修改任何智能体代码或模板逻辑，即可调整压缩提示与策略。

这为长上下文创建了一个可扩展的生命周期。对于严格基于规则的缩减，ADK 提供了一个配套操作—— **过滤** ——预构建插件可在上下文到达模型前，根据确定性规则全局删除或修剪内容。

### 1.5 Context caching

现代模型支持 **上下文缓存** （前缀缓存），允许推理引擎在多次调用间复用注意力计算。ADK 将"会话"（存储）与"工作上下文"（视图）分离的设计，为这项优化提供了天然的底层支持。

该架构将上下文窗口有效地划分为两个区域：

- **稳定前缀：** 系统指令、智能体身份标识与长期存续摘要。
- **变量后缀：** 最新的用户轮次、新工具输出及小幅增量更新。

由于 ADK 流程和处理器具有显式特性，您可以将缓存友好性作为硬性设计约束。通过调整流水线顺序，可使频繁重用的内容段稳定保持在上下文窗口前端，同时将高度动态的内容推向末端。为贯彻这一严谨设计，我们引入了 `静态指令` 原语，它能确保系统提示词不可变，从而保证缓存前缀在多次调用间持续有效。

这是上下文工程作为全栈系统工作的一个典型范例：你不仅决定了模型能看到什么，还优化了硬件需要重新计算底层张量操作的频率。

### 2\. 相关性：对当前重要事项的自主管理

一旦结构确立，核心挑战便转向相关性考量： *在分层语境架构中，当前哪些具体信息应置于模型的活跃视窗内？*

ADK 通过人类领域知识与智能体决策的协作来解决这一问题。仅依赖硬编码规则虽成本低廉但过于僵化；而完全依赖智能体浏览所有信息虽灵活，但成本高昂且稳定性差。

理想工作情境是两者协商的结果。人类工程师负责架构设计——确定数据存储位置、汇总方式及筛选规则；而智能体则提供动态决策能力，根据即时用户需求灵活调用特定记忆模块或成果物。

### 2.1 构件：外部化大型状态

早期智能体实现常陷入“上下文堆砌”的陷阱：将大型数据载荷——如 5MB 的 CSV 文件、庞大的 JSON 接口响应或完整 PDF 文本——直接塞入对话记录。这相当于对会话施加永久性负担：后续每个交互回合都会拖拽这些冗余数据，既淹没关键指令又推高运算成本。

ADK 通过将大数据作为 **构件** 来处理解决此问题：这些是由 `ArtifactService` 管理的带名称、版本化的二进制或文本对象。

从概念上讲，ADK 对海量数据采用了 **句柄模式** 。海量数据存储在工件库中，而非提示词内。默认情况下，智能体通过请求处理器只能看到轻量级引用（名称和摘要）。只有当智能体需要原始数据来回答问题时才使用 `LoadArtifactsTool` 工具，该操作会临时将内容载入工作上下文。

关键在于，ADK 支持 **瞬时扩展** 功能。模型调用或任务完成后，相关产物默认会从工作环境中卸载。这将"每次提示中的 5MB 干扰"转化为精准的按需资源。数据量可以庞大，但上下文窗口始终保持精简。

### 2.2 记忆：长期知识，按需检索

在 Artifact 处理离散大型对象的同时，ADK 的 **记忆** 层负责管理超越单次会话的长期语义知识——包括用户偏好、过往决策与领域事实。

我们围绕两大原则设计了 `MemoryService` ：记忆必须可被 **搜索** （非永久固定），且检索过程应由 **智能体主导** 。

`MemoryService` 将数据（通常来自已完成的会话）摄取到向量或关键词语料库中。随后智能体通过两种不同模式访问这些知识：

- **反应式回忆：** 智能体识别出知识缺口（"用户的饮食限制是什么？"），并明确调用 `load_memory_tool` 来检索语料库。
- **主动召回：** 系统通过预处理器基于最新用户输入进行相似性搜索，在调用模型前就通过 `preload_memory_tool` 注入可能相关的信息片段。

这种方法用“基于记忆”的工作流取代了“上下文填充”这一反模式。智能体仅精确调取当前步骤所需的片段，而非背负所有历史对话的沉重负担。

### 3\. 多智能体上下文：谁在何时看到什么

单智能体系统难以应对上下文膨胀；多智能体系统则加剧了这一困境。若根智能体将其完整历史传递给子智能体，而子智能体又进行相同操作，便会引发 **上下文爆炸** 。令牌数量激增，子智能体被无关的对话历史所干扰。

每当一个智能体调用另一个智能体时，ADK 允许您 **显式限定** 被调用方能访问的内容——可能仅包含最新用户查询和一项成果物——同时屏蔽大部分历史传承信息。

从宏观层面来看，ADK 将多智能体交互映射为两种不同的架构模式。

首先是“将智能体视为工具”。在这种模式下，根智能体将专业智能体严格当作函数来调用：通过精准指令触发功能，获取结果后立即转向下一个任务。被调用的智能体仅能接触到特定指令和必要数据，无法获取任何历史交互信息。

其次是代理转移（层级结构）。在此模式下，控制权完全移交至子代理以延续对话。子代理将继承会话的视图，能够驱动工作流程，调用自身工具或向更下游的链式环节转移控制权。

### 3.2 用于智能体传输的限定范围移交

切换行为由被调用方上的参数（如 include\_contents）控制，这些参数决定了从根智能体流向子智能体的上下文量。在默认模式下，ADK 会传递调用方工作上下文的全部内容——当子智能体真正受益于完整历史记录时，这非常有用。在无历史模式下，子智能体看不到任何先前历史；它只接收您为其构建的新提示（例如，最新的用户回合加上几个工具调用和响应）。专用智能体仅获取所需的最少上下文，而非默认继承庞大的对话记录。

由于子代理的上下文也是通过处理器构建的，这些交接规则与单代理调用共享相同的流程管道。您无需单独的多代理机制层；只需调整现有上下文编译器能够获取的上游状态范围即可。

### 3.3 为智能体迁移转换对话内容

基础模型遵循固定的角色架构： `system` 、 `user` 和 `assistant` 。它们本身无法区分“助手 A”和“助手 B”。

当 ADK 移交控制权时，通常需要 **重构** 现有对话内容，使新智能体能接收到连贯的工作上下文。若新智能体仅看到前序智能体发出的一连串"助手"消息，它会错误地 *认为* 这些操作是由自己执行的。

为防止这种情况发生，ADK 在切换过程中会执行主动翻译：

- **叙事式角色转换：** 之前的“助手”消息可被重塑为叙事背景（例如修改角色或添加类似 `[For context]: Agent B said...` 的标签），而非作为新智能体自身的输出呈现。
- **行动归属：** 来自其他智能体的工具调用会被标记或汇总，使新智能体能够基于 *结果* 行动，而不会将 *执行过程* 与自身能力混淆。

实际上，ADK 从子智能体的视角构建了一个全新的工作上下文，同时保留了会话中的事实历史。这确保了正确性，使每个智能体都能承担"助手"角色，而不会将整个系统的历史错误地归因于自身。

### Conclusion

随着我们推动智能体处理更长的时间跨度，"上下文管理"已不能仅停留在"字符串操作"层面，而必须将其视为与存储和计算同等重要的架构问题。

ADK 的上下文架构——分层存储、编译视图、流水线处理和严格作用域——正是我们对这一挑战的回应。它凝聚了将智能体从有趣的原型转化为可扩展、可靠生产系统所需的严谨系统工程。
