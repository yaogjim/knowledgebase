# **Deep Agents 与 Human-in-the-Loop 功能介绍**

Deep Agents 是一种能够通过结合规划工具、文件系统、子代理和详细的系统提示，在更长的时间范围内执行更复杂任务的代理。然而，当这些代理需要使用敏感工具时，就产生了一个问题：如何在执行前加入人工审批环节。为了解决这个问题，Deep Agents 新增了 Human-in-the-Loop（人工循环）功能，允许用户对工具调用进行批准、拒绝、编辑和响应。

### **配置 Human-in-the-Loop**

要启用此功能，用户需要在创建 Deep Agent 时传递一个名为 `interrupt_config` 的参数。这个配置是一个字典，它将工具名称映射到具体的人工干预模式。`HumanInterruptConfig` 支持四种特定的交互模式：
*   **allow_ignore**: 允许用户跳过工具调用（目前 Deep Agents 尚不支持此功能）。
*   **allow_respond**: 允许用户直接为工具调用添加一个文本响应，而不是实际执行该工具。
*   **allow_edit**: 允许用户编辑工具调用的参数。
*   **allow_accept**: 允许用户接受并执行工具调用。

用户可以精细地配置每种模式的开关状态（`True` 或 `False`）。作为一种快捷方式，也可以直接将工具的配置设置为 `True`，这将默认启用 `allow_respond` 和 `allow_edit`。为了实现人工循环，系统必须附加一个检查点（Checkpointer）来保存和恢复代理的状态，如果使用 LangGraph 平台，检查点会自动附加。

### **代码实践：演示环境设置**

在 Jupyter Notebook 的演示中，首先导入了 `create_deep_agent` 和 `tool`。接着，定义了一个模拟的敏感工具 `send_email`，它接收邮件内容和收件人地址作为参数。为了对这个工具启用人工审批，创建了一个 `interrupt_config`，将 `send_email` 工具的配置设为 `True`，意味着允许接受、编辑和响应这三种操作。

随后，创建了一个 Deep Agent 实例，并为其设置了 `send_email` 工具、系统提示以及刚才定义的人工循环配置。为了管理会话状态，还设置了一个内存检查点（InMemorySaver）。因为人工循环功能需要在某个时间点中断并等待用户输入，检查点对于保存代理中断时的状态至关重要，这也是 LangGraph 框架的核心优势之一。最后，定义了一条简单的消息“告诉 jim@gmail.com 我会迟到”，用于后续的流程演示。

### **人工循环流程演示**

#### **1. 接受（Accept）流程**

首先演示“接受”流程。当代理收到发送邮件的指令后，它的执行会在调用工具前中断。此时，代理已经生成了完整的邮件内容，包括问候语和正文。用户可以通过发送一个 `type` 为 `accept` 的 `Command` 对象来批准这个操作。一旦收到批准指令，代理会继续执行，调用 `send_email` 工具，并最终返回邮件已发送的确认信息。

#### **2. 编辑（Edit）流程**

接着演示“编辑”流程。与“接受”流程类似，代理在收到指令后首先会中断。但这次，用户不只是批准，而是希望修改邮件内容。通过发送一个 `type` 为 `edit` 的 `Command` 对象，并附带一个新的 `args` 参数，用户可以覆盖原始的邮件内容。例如，将原本详细的邮件正文修改为一句简单的“我会迟到”。代理在收到编辑指令后，会使用更新后的参数来执行 `send_email` 工具。

#### **3. 响应（Response）流程**

最后演示“响应”流程。此流程允许用户完全绕过工具的实际执行，而是直接提供一个模拟的返回结果。当代理中断后，用户可以发送一个 `type` 为 `response` 的 `Command` 对象，并在 `args` 中提供一个自定义的字符串。这个字符串将被当作工具的执行结果直接返回给代理。例如，用户可以提供“错误：用户中断并提供了反馈：请用 Harrison 的名义签名”这样的信息。代理接收到这个模拟的响应后，会根据这个新信息重新规划，并生成一个新的邮件草稿，这次邮件的末尾就加上了“Best regards, Harrison”。由于这又是一次新的工具调用，代理会再次中断，等待用户的最终批准。此时，用户再发送一个“接受”指令，整个流程才算完成。

### **在 LangSmith 中追踪执行过程**

通过 LangSmith 的追踪界面，可以清晰地看到整个交互过程。在“Threads”视图中，每个唯一的 `thread_id` 都代表一个独立的对话。点进最后一次“响应”流程的追踪记录，可以看到多轮交互的详细情况：
*   **第一轮**: 人类用户输入初始指令。AI 生成了第一次的工具调用请求，然后执行中断。
*   **第二轮**: 用户输入了“响应”指令，提供了模拟的工具返回结果。这个结果作为 `tool` 的输出被记录下来，并反馈给 AI。AI 据此生成了第二次的工具调用请求（即签名后的新邮件），然后再次中断。
*   **第三轮**: 用户输入了“接受”指令，批准了第二次的工具调用。工具（`send_email`）被实际执行，并返回“sent!”。
*   **第四轮**: AI 收到工具的成功回执，向用户输出最终的确认信息，流程结束。

### **Deep Agents 新功能：Human-in-the-Loop 人工审批**

#### **Deep Agents 简介与挑战**

发言人：Deep Agents 是一种可以在更长的时间跨度内行动的代理。它们通过使用规划工具、文件系统以及生成子代理来实现这一点。

你可以为它们传递任意的工具来执行相应的操作。但这引入了一个问题：如果其中一些工具是敏感的，而你希望在它们被执行之前，能有一个人工审批的环节，该怎么办呢？

我们刚刚为 Deep Agents 添加了以人工循环（Human-in-the-Loop）的方式批准、拒绝和响应工具调用的能力。在本视频中，我想详细介绍一下这个功能。

#### **Human-in-the-Loop 功能配置**

发言人：在 README 文档中，我们现在有了关于 Human-in-the-Loop 支持的说明。

你可以看到，我们指定 Human-in-the-Loop 支持的方式，是在创建 Deep Agent 时传递一个 `interrupt_config` 参数。

`interrupt_config` 是一个从工具名称到你想要启用的人工循环交互模式的映射。目前有几种不同的模式可以启用。

现在支持的三种是 `allow_accept`、`allow_edit` 和 `allow_respond`。

`allow_accept` 会添加一个中断，并允许人类用户接受该工具调用，然后代理将从那里继续执行。

`allow_edit` 允许人类用户编辑工具调用的参数，甚至可能编辑被调用的工具的名称，然后使用编辑后的参数继续执行。

而 `allow_respond` 则会直接响应工具调用，并将用户的响应内容放入工具消息中。所以它实际上不会执行任何工具，而是用用户的响应来模拟工具的输出，然后将这个结果返回给模型。

你也可以直接将配置指定为 `True`，这会默认启用所有这三种操作。

接下来，让我们看看如何在 Notebook 中使用它。

#### **代码实践：配置与环境设置**

发言人：我这里有一个 Notebook，装有最新版本的 Deep Agents。我将导入 `create_deep_agent`，以及 LangChain 核心库中的 `tool` 对象。

我将模拟一个在现实中会很敏感的工具：`send_email`。我可能想加入人工循环来批准将要发送的邮件。这个工具有两个参数：`content`（邮件内容）和 `recipient`（收件人），都是字符串。

现在，我来创建我的人工循环配置 `hitl_config`。我将 `send_email` 这个工具的名称映射到 `True`。这意味着我将能够执行接受（accept）、编辑（edit）和响应（respond）这三种操作。

我将创建一个非常简单的 Deep Agent。使用 `create_deep_agent`，传入 `send_email` 工具、指令，以及这个人机循环配置。

现在我需要设置检查点（Checkpointer）。检查点是必需的，因为要让人工循环支持起作用，就需要有一个检查点来保存代理在中断发生时的状态，并无限期地等待，直到用户发来下一个信号，无论是接受、编辑还是响应。

这种由检查点提供的状态持久化能力，对于人工循环的场景至关重要。LangGraph 拥有非常出色的检查点和持久化层，它能以生产就绪的方式启用这种人工循环场景，这也是使用 LangGraph 的主要好处之一。

所以，我将创建这个检查点，并设置 `agent.checkpointer` 来开始使用它。

另一件我需要做的事情是，当我调用这个 Deep Agent 时，我需要传入一个 `config`。这个 `config` 在可配置字段中会有一个 `thread_id`。我可以将这个 `thread_id` 设置为任何我想要的值，但我会为不同的对话使用不同的 ID，这样它就能记住哪个是哪个。

我将在接下来的几个例子中使用的消息是这个：“告诉 jim@gmail.com 我会迟到”。这是一个非常简单的消息，我将用它来展示首先是接受（accept）流程，然后是编辑（edit）流程，最后是响应（response）流程。

#### **流程一：接受（Accept）**

发言人：好的，我们先从接受流程开始。在这里，我将使用 `1-accept` 这个线程 ID，只是为了保持唯一性。然后我将流式传输代理的响应，看它在处理这条消息时如何逐个节点地运行。

我可以看到，第一个流式返回的消息来自代理节点。它包含一条 AI 消息和一个工具调用。然后我们看到中断发生了。这个中断包含一个动作请求，它想要用指定的参数调用 `send_email`。

要从这里继续，我可以使用 `Command` 对象。当我需要执行比简单地在线程上追加消息更复杂的操作时，`Command` 对象就很有用。在这种情况下，我需要对人工中断做出响应。

我将传回这个 `Command` 对象，使用 `resume` 关键字参数，并传入一个对象列表。为什么要传入列表呢？因为中断的值本身就是一个列表，你实际上可以一次中断多次。这个功能在 Deep Agents 中目前是禁用的，但在 LangGraph 中通常是支持的。所以，我传入的参数是一个字典，`type` 为 `accept`。对于接受操作来说，不需要其他参数，因为它非常简单。

在我们从那里恢复后，我们可以看到它经过了 `post_model_hook`，这是中断发生的地方。然后它打印出了邮件内容——我在我的模拟工具中加入了这个打印语句，这样我们就能确切地看到发生了什么。接着它进入工具节点，获取工具的响应，也就是“sent!”，然后返回到代理节点。代理接着发送最终消息：“邮件已发送！我已通知 jim@gmail.com...”，然后再次经过 `post_model_hook`。这次 `post_model_hook` 中没有中断，所以流程就结束了。这就是非常简单的接受流程。

#### **流程二：编辑（Edit）**

发言人：现在让我们看一下编辑流程。在这里，我使用的是一个不同的线程 ID，所以这将是一个新的对话，但消息是相同的。

所以我们可以看到，到目前为止，情况看起来应该非常相似。我得到了代理的响应，它打算给 Jim 发送一封邮件，然后我看到了这里的中断。

现在情况会有所不同。我仍然使用 `Command` 和 `resume`，但现在的 `type` 是 `edit`。我还会传入另一个东西：`args`。`args` 里面是什么呢？

`args` 是一个字典，代表了接下来应该执行的工具调用。我可以看到它有一个 `action` 名称，这里是 `send_email`，因为这是我拥有的工具的名称。然后，这里的 `args` 将是那个工具的参数。我现在用新的内容覆盖了它，内容字段是“我会迟到”，而收件人是“jim@gmail.com”。这将会成为新的输入。之前，你可以看到内容是“嗨 Jim，我想让你知道我今天会迟到...”。

好的，现在我们从这里恢复。

我们可以看到有一个 `post_model_hook`，它基本上是在运行并表示我们更新了一些东西。我们现在可以看到它打印出了我们发送的邮件内容。现在它变成了一句非常简单的“我会迟到”。所以，这个操作在工具执行之前影响了它。现在它正在用这些新的、编辑过的参数来执行。

然后我们看到工具节点运行，然后我们看到代理生成了另一个响应：“完成！我已经发送了邮件...”，然后 `post_model_hook` 再次运行，然后就完成了。这就是编辑流程。

#### **流程三：响应（Response）**

发言人：现在让我们看看响应流程。同样，我正在切换线程 ID，其他一切都一样。初始的步骤应该非常相似。我会得到一个来自代理节点的响应，说它已经草拟了这个工具调用，它正在调用 `send_email` 工具并附带这些参数。

现在，这里是事情再次变得不同的地方。现在的 `type` 是 `response`。参数 `args` 存在，但它只是一个字符串。这个字符串将被用作工具调用的消息内容，而不是实际运行工具。所以，我再重复一遍，当你传回 `response` 时，它不会调用工具，而是将这个字符串作为工具调用的消息发送。

所以在这里，我们可以看到我传入的是“错误：用户中断并提供了反馈：请用 Harrison 的名义签名”。

这基本上是要告诉大语言模型，调用工具时发生了错误，并且用户中断了，希望邮件能以 Harrison 的名义签名。这一切都是通过人工循环启用的。让我们运行这个。

我们可以看到，现在这个 `post_model_hook` 运行了，它添加了一条消息。它添加了这个消息，并且添加了一个工具调用，这个工具调用和之前的 ID 相同，但是内容是“错误：用户中断并提供了反馈...”。

然后它会进入代理节点。它不会进入工具节点，因为没有待处理的工具调用了，因为我们已经模拟了那个工具调用的响应。所以现在它返回到这个代理节点，我们可以看到它重新生成了一个对大语言模型的调用，现在它把邮件签名为 Harrison。

然后它再次中断，因为它返回到了人工循环配置，有一个新的邮件需要发送。现在我可以接受它。当我接受它时，我们可以看到它现在发送了这封邮件，并且确实是以 Harrison 的名义签名的，然后它从那里继续执行。

#### **在 LangSmith 中追踪流程**

发言人：让我们看一下最后这个例子在 LangSmith 中是什么样的，因为它在展示线程，特别是在处理这些响应时，会非常有启发性。

你会注意到，这是运行页面，我可以看到我这里的所有运行。但还有一个“Threads”（线程）页面。这个页面现在会根据那个线程 ID 来对事物进行分组。

所以如果我点击这里，进入这个最新的线程，我可以看到我刚刚进行的交互。

*   首先，我向代理发送消息：“告诉 jim@gmail.com 我会迟到”。AI 生成了这个消息并调用了工具。
*   在第二轮中，我输入了恢复指令，其中包含了参数：“错误：用户中断并提供了反馈：请用 Harrison 的名义签名”。我看到这个工具调用在这里，内容是“错误：用户中断并提供了反馈...”，这被表示为一个工具调用。然后我得到了另一个 AI 调用。
*   然后在第三轮中，是这个接受响应，然后我在这里也收到了消息，然后它继续往下走。

如果我们在第三轮中查看，然后看这个序列中最后一次对模型的调用，我可以看到整个消息序列，就像它呈现给大语言模型的那样。有系统消息，这是 Deep Agent 的系统消息；第一个人类消息；AI 消息生成了工具调用；工具调用本身，但这个工具调用的内容现在是我的中断信息：“错误：用户中断并提供了反馈...”；然后是另一个 AI 消息，调用 `send_email` 工具；然后我得到了工具的真实响应“sent!”；最后是来自代理的最终响应。
