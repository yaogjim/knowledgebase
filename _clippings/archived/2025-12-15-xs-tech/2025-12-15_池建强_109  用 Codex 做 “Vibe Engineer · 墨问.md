**109 | 用 Codex 做 “Vibe Engineering”：让 AI 成为能干的同事，但每一行上线代码仍由人负责**

周末看了个 OpenAI 论坛的内部分享，叫 Vibe Engineering，学习资料整理了一下

![](https://priv-sdn-001.mowen.cn/mo/file/meta/10/79/95/2000113658683179009.png?Expires=1765872023&OSSAccessKeyId=LTAI5tE16jzdfWCPVBmyB5Nn&Signature=G3cdNcoGFcRmx1PGOuSqr2dlZxU%3D&response-expires=Tue%2C%2016%20Dec%202025%2008%3A00%3A23%20GMT&x-oss-process=image%2Fresize%2Cw_1200)

大家好，欢迎来到 OpenAI Forum。我叫 Chris Nicholson，在全球事务团队工作，也是 Codex 的重度用户。很高兴你们今天能来。

我敢打赌，很多正在观看的工程师都经历过 deadline 时刻：你恨不得有个同事永远不累、永远在线。在 OpenAI，Codex 就坐在那个位置上。

但我们今天我们要聊的是 “Vibe Engineering”：用 AI 更快地构建真正可上线、可维护、可扩展的生产级软件，同时仍然坚持一个底线—— **发到生产环境的每一行代码，人类要对它负责** 。

把大模型当成“代码生成器”，让它哗啦啦输出，然后指望测试和 Code Review 把所有坑都填上，这当然很诱人。但更有意思、也更接近真实工程实践的，是把 AI 放到设计、架构、调试、以及长链路多步骤项目里去用。

在开始之前我想说一句：希望在座每个人，今天至少带走一个能落地的工作流改动，最好在年底前就试一试。

今天和我一起分享的有两位非常懂“怎么把 Codex 用到工程里”的人：

**Romain Huet** ：OpenAI 开发者体验负责人。法国企业家和工程师，曾在 Twitter、Stripe 等公司做开发者平台与社区。

**Aaron Friel** （大家常叫他 Friel）：OpenAI 技术团队的软件工程师，长期做开源，写过编译器、Web 框架、密码学库等。他在今年秋天的 Dev Day 展示过如何用 Codex 把一个多步骤项目从想法推进到可工作的系统，而且项目只会越来越长、越来越复杂。

我们今天选了一个非常完整的 demo 项目。现场会展示启动和过程，然后直接跳到后面的结果。Friel 也会把结果和提示词放到 GitHub repo 里。你会看到：工程师如何保持控制权，而 AI 一步步承担更多体力活。

仓库链接： [https://github.com/friel-openai/bazel-differous](https://github.com/friel-openai/bazel-differous)

论坛的最后是问答环节。

**一、Friel 的现场演示：从零重写一个项目，用 Rust 复刻 Kotlin 版本**

**Aaron Friel：** 谢谢 Chris。我在 OpenAI 做开发者系统，目标是加速工程团队。很多任务都是在看我们需要改进的系统：可能是性能、可能是工具易用性，有时要重写，有时要给上游项目打补丁，也可能需要内部从头造一个。

我们很受益于开源生态：很多项目本身就像“软件应该怎么工作”的规格说明。我们把这些规格、以及已经存在的可运行软件当作参照，推动 Codex 每天产出可靠结果。

我屏幕上这个任务挺重的：我们内部用 Bazel，也用一个叫 Bazel Diff 的工具来判断 CI 里需要构建哪些项目。上游有一个 Match Group 的项目实现了这件事，用 Kotlin 写的，支持我们需要的 Bazel 特性。但我们想要更多功能，或者更高性能。

所以我要让它做一件大事： **把整个项目从 Kotlin 重写成 Rust，从零开始。** 现在这个目录是空的，除了这段提示词什么都没有。我会让它把上游 repo 作为 submodule 引入，并围绕它写测试。我们会做一个 test harness：既能知道“现有正确行为长什么样”，也能对照新项目表现如何。

我还会让它使用一个 **exec plan** 。细节我不展开，在 OpenAI Cookbook 里有专门讲 exec plan 的内容：它本质是一个规划文档，用来支撑 agent 跑更长时间的任务，并持续跟踪长期目标。

我的目标是：让新项目（我叫它 BazelDifferis）和 BazelDiff **达到 100% 兼容** 。我给了很多约束条件。按传统方式，这可能要工程师花几周来实现和验证。但我们很快会看到它能直接开工——当然今天这场分享时间内大概率做不完。

不过这反而是好事：昨晚我让它跑了一夜，完成这个任务大概用了 12 小时。这种长周期任务现在是很常见的。我要补充一点：我用的是内部 fork 的 Codex 版本，我自己也在“hack”它做实验。这些想法不代表 Romain 团队承诺会把你今天看到的每个特性原样上线。

好，我们开始。我在终端里启动 Codex，粘贴提示词。你很可能会先看到它拉起 sub-agent：先想清楚要做什么、怎么跟踪工作。它第一步做的是创建一个 **watchdog（看门狗）** ——这是一个sub-agent，会不断提醒主 Agent：总体目标是什么、用户要求是什么，用主代理的上下文持续把它“拽回正轨”。

你还会看到它并行拉起一些研究型 sub-agent：混合使用模型（比如 GPT-5.1 Codex mini），去研究上游项目结构、调查 Bazel 8 和 Bazel 9 的差异等。

我先承认：这活有点“非主流领域”。Bazel 在训练数据里并不多，互联网上也没多少 Bazel 开源内容，所以很难。现在它已经在并行推进，接下来会添加 submodule，这会花一会儿，短时间不一定能看到大量代码，我们让它继续跑。

**二、从 “Vibe Coding” 到 “Vibe Engineering”：模型不只是写代码，而是做工程**

**Chris Nicholson：** 我们先聊聊概念。Simon Willison 提过 “Vibe Engineering”。它不同于 “Vibe Coding”：后者偏“让模型写代码”，前者更严肃—— **资深工程师全程负责，用 agent 和模型尽可能多地覆盖工作链路** 。你怎么看这个说法？它和真实工作重合多少？

**Romain Huet：** 我觉得这就是模型能力演进的自然结果。回到一年前，模型已经很擅长“输出代码”，所以 “vibe coding” 一度很火，大家都兴奋地在做东西。我记得我们发布 O1（第一个推理模型）时，我最早的 demo 就包括零样本从零做一个 iPhone app，或者给一个小无人机编程。

但当时那已经算“前沿”了。现在模型强大到了另一个阶段：它更像队友。你看 demo 里它能连续工作几十分钟甚至数小时，做非常复杂的任务。于是从 coding 到 engineering，就覆盖了工程师真实工作里的更多部分：不仅是写代码，还包括制定计划、做架构决策、写测试、验证工作。我们也观察到： **当模型能够检查自己的工作时，它表现会更好** 。这正是 agentic coding 能力的一部分。它正在变成一个队友，帮你更快完成工作。

**Chris Nicholson：** Friel，你作为一线工程师，这个词对你意味着什么？

**Aaron Friel：** 软件开发一直是“deadline”和“无穷多方案选择”之间的权衡。我们常常花很多时间思考哪条路最好，也会放弃很多可能性。

有了 agentic coding 工具之后，我日常做法是： **让 agent 多跑几次同一个任务，然后对比结果；让它用不同路径实现；最后选更好的那个。** 所以我们更接近某种“真正的工程工作”：先构建出来、测试，不行就撤，换路线再试。只是现在迭代速度快了很多，因为很多基础铺垫工作 agent 可以替我们做。

这次任务也特别符合 “vibe engineering”：问题非常明确，成功标准也非常明确。我也必须致敬 Bazel Diff 的作者——他们做了很多规格化工作，这依然是好软件的基础。但我可以用 agent 把开发速度提起来。

**Chris Nicholson：** 所以你能更“经验主义”地做架构决策：因为你能更快做出更多版本、跑基准测试、再选对的？

**Aaron Friel：** 对。我为今天准备时跑了几轮，会让它做 benchmarks、对比结果，再挑一个我们更可能采用的版本。

**三、平台视角的变化：从“能力”到“协作者”，以及“反向 onboarding”**

**Chris Nicholson：** Romain 你做过 Twitter、Stripe 这种开发者平台。你觉得现在最不同的是什么？

**Romain Huet：** 以前我们很清楚什么是好的 API、好的开发者工具：好的 meta 语言、好的文档，关键是让开发者上手——让他们学习 API 能力。

但现在，像 Codex 这样的工具，把我们从 “capabilities（能力）” 推到了 “collaborators（协作者）”。有点像 onboarding 被反过来了：作为平台，你不仅要让人理解能力，更要让模型理解能力。

更重要的是：开发者可以从一个想法，更快走到原型、再到生产。比如过去你需要深入读 Stripe 文档才能把支付搞定；现在你有一个商业想法，Codex 很可能帮助你把它做出来、甚至更快变现，而不需要你把文档读成圣经。

同时，AI 能力本身也在变强。比如语音（speech-to-speech）：去年音质够了但价格偏高；现在价格变化会让很多语音应用成为可能。对开发者来说，这既是“更强的 coding 工具”，也是“更强的新能力”，能帮你重新发明软件交互。

**Aaron Friel：** 我也感受到 Codex 特别强的一点：它是个很厉害的研究员。你给它源码和 repo，它会自己去找“ground truth”。比如现在它就在研究 Bazel 新引入的 Bazelmod。很多时候它会 clone 仓库、对照实现，自己得出结论，再告诉你应该怎么用。

**我经常把一个 repo 加进 Codex Web 环境里，直接问它系统怎么工作。这非常适合学习一个新项目或新技术。**

你看，现在 repo 里它已经把项目脚手架搭好了，还有一个 plan 文件。我打开看看：它给了大图景描述，也完成了部分任务，但还远没结束。我们让它继续。

**Chris Nicholson：** 它做这么多，你怎么跟得上？

**Aaron Friel：** 确实会出现“推理能力不匹配”：模型能做的比我能实时消化的更多。所以我觉得 **plan 文件或持续维护的 artifact** 非常关键：不仅对模型有用，对人也有用。

我经常跟团队说：如果有更多时间，我们会更好地写文档、补测试。这些事情对人也重要。Agent 让我们有机会把这些“本该做但总没时间做”的事做完。测试越好，项目越不容易跑偏；文档越好，下一个工程师或下一个 agent 越容易上手。

**Chris Nicholson：** 所以你认为： **做“人类可读”的 artifact，会显著提升 agent 在代码库里的表现？**

**Aaron Friel：** 是的。

**四、在 OpenAI 内部怎么用：代码评审、提效、以及“用 Codex 构建 Codex”**

**Chris Nicholson：** Romain，你从全局看内部使用情况，有哪些很酷的用法？

**Romain Huet：** 今年夏天出现了一个明显拐点：模型能力强到可以完成有意义的工作。现在内部几乎每个技术人员都在用 Codex——我记得超过 92%，现在可能更高。

一个特别强的场景是 **代码评审** ：OpenAI 内部所有 PR 都会被 Codex review，我们确实提前抓到过一些复杂 bug，本来可能会进生产。Codex 也让工程师平均产出 **70% 更多 PR** ，而且是会被合并、会进生产的真实改动，不是噪音。

我们也在 **用 Codex 来做 Codex** 。这也是为什么你可能看到我们几乎每隔几天就发布更新：变化速度非常快，Codex 在帮我们加速。

**Chris Nicholson：** 递归式自我改进，从 Codex 开始。

**Aaron Friel：** 我也补一句：不仅技术团队。我还在教一些非技术或弱技术同事用 Codex 的 Slack 集成，问关于代码库的问题。对很多部门来说，“想知道一个功能怎么工作”，第一步可能就是问 Codex。它经常比我答得更好。

这能缓解工程团队长期的瓶颈：非工程团队想要答案，但工程师时间有限、会议太多。Codex 能把很多“第一问”直接解决掉，让大家自己继续深入。

**Romain Huet：** 还有一个很有意思的趋势：即使不是每个人都要当工程师， **每个人都在变得更技术化** 。比如设计师天天在 Figma 里，现在 Codex 能通过 Figma 的 MCP server，把 Figma 组件拉进代码；营销想改官网文案，也能让 Codex 帮你找到该改的地方。公司的每个人都更容易“参与交付”。

**五、长任务、少改动：不要再问“写了多少行”，而要问“质量如何”**

**Chris Nicholson：** Friel，在 Dev Day 你提过让 Codex 跑七小时，那件事最令你意外的是什么？

**Aaron Friel：** 我当时躺沙发看电视，顺手让它跑一个问题，电脑也设置成不休眠。第二天醒来发现：它还在跑，而且真的还在工作。

很多工程师听到会担心：是不是写了十万行垃圾？但那次七小时最终只产生了大约 500 行 diff。它做的是很复杂的变更，还迭代了两百多个回合：跑测试、改、再跑、再改。最后那份改动我合进去了。

所以让我震撼的是：只要目标足够具体，它可以长时间持续推进，而且不是靠堆代码取胜。

**Romain Huet：** 这也呼应一个变化：以前有人会问我们“AI 给你写了多少行代码”。那也许是一年前更合适的问题。现在更重要的是 **输出质量** 。即便只改几百行，但其中的思考、验证、质量控制，才是核心。

**六、并行化：Best of N、把 Codex 当“收件箱”，以及“没有 backlog 的未来”**

**Romain Huet：** 我很喜欢 Codex 的一个功能叫 **Best of N** ：即便你的想法很模糊，也能让 Codex 并行给出四种不同路线，并给你结果截图。你会立刻发现：方案 1、2 不对味，方案 3 有意思，然后基于它继续迭代。

关键是：你把测试、脚手架这些工作交给模型，你把自己的 **品味（taste）、视角（vantage point）** 带进来。任何人都能做一个“能跑的方案”，但如果你对问题执着了很久，你才知道什么是“更好的解法”。这就是人的价值，模型负责其他。

**Aaron Friel：** 我也很认同。我常给它最终目标，中间过程故意不写死，然后看不同 agent 怎么走。这像在用工程做“进化算法”：多试、选胜者、再衍生新变体。

我准备今天的分享时经常并行跑四五个任务。成功率其实挺高：这么复杂的任务，我测试里“单 prompt 完成”的成功率超过 75%。你只要发出去几个，往往会得到不错的结果。

此外，我把 Codex Cloud 界面当成一个“收件箱”：我可以把任务丢给它，去开会、去聊人、去思考下一件事；再回来 review 结果，挑一个继续推进。我还在努力实现 “Codex inbox zero”。

**Romain Huet：** 我们团队也在这样做。现在的并行化更容易，因为你可以更信任 Codex 先“强力跑一遍”，你再回来验证。

我甚至觉得，最会用的人会越来越“没有 backlog”。所谓 backlog，就是你想做但很久之后才会做的想法清单。现在很多任务都可以先让 Codex 做一个 V0。

**Aaron Friel：** 我们内部还在探索更进一步的自动化：比如 CI 某个测试变慢了，自动起一个 Codex 任务看看能不能提速；某个测试失败被标记成 flake，试着让 Codex 修；甚至对每个新进问题自动 triage。

我特别想要的体验是：我把方案写到 99%，剩下只是 lint error 之类的小尾巴，我不想再来回切换上下文，让 agent 直接把最后 1% 补齐。

我还有个需求：我需要 Codex 帮我更擅长上下文切换。

**七、关键技能与瓶颈：品味、沟通、清晰的目标，以及“模型看不见的世界”**

**Chris Nicholson：** 要最大化这些工具，你认为最关键的能力是什么？

**Romain Huet：** 我觉得依然是： **设计、品味、观点** 。你仍然坐在驾驶位，决定什么是“好功能”、什么是“够用”、什么是“卓越”。如果你对客户问题足够痴迷，你就有独一无二的判断力。模型是队友，用来卸掉其他负担。

同时，团队协作能力也重要：清晰沟通、关注点分离，这些老原则仍成立，只是现在你要把 AI 队友也纳入协作系统。

**Aaron Friel：** 我最近开玩笑说：我们工程师都在“升职”——变成了 manager，甚至 director。因为你要用 sub-agent、用任务生成任务的方式来推进工作。

我觉得另一点是保持学习与适应：能力变化太快了。你需要愿意尝试，更新策略。下一代 GPT 往往能解决更多问题，你不必像以前那样教它每一步怎么做。

**Chris Nicholson：** 我想补一句：LLM 看不见整个世界。它有能力处理数据，但前提是你把数据给到它。所以作为“LLM 使用者/管理者”，你要一直问自己：\*\*世界上有哪些关键信息模型还没看到？\*\*那就是你的工作：去把数据找来，给它一个更好的罗盘。

**Aaron Friel：** 这点我太有共鸣了。比如我在 Mac 上开发，但 GitHub 的 Linux runner 会暴露差异。如果我把 GitHub MCP 接进去，让它直接看测试结果，它是不是就能更自主地解决？当你把 Codex、MCP 和更多系统连接起来，让它获得更多上下文，它就能做更不可思议的事。

**Romain Huet：** 是的。公司里的信息都散在生态里：数据、backlog、bug、Slack 对话。现在如果“编码队友”能读到这些上下文，结果当然更好。

**八、一个“还没被建出来的东西”：当软件变得非常便宜，热爱会被看见**

**Chris Nicholson：** 最后一个快问：你希望有人做出什么产品？但还没出现的。

**Aaron Friel：** 我喜欢《龙与地下城》，我也尊重做 DnD 模组的创作者。对我个人来说，我想做很多“整理生活的小工具”：比如追踪家里东西放哪了、怎么整理衣柜。未来软件会非常便宜，甚至接近“免费”，我很期待。

**Romain Huet：** 我想到 John Carlison 以前发过的一条推文：世界像个“未完成的热爱项目博物馆”。很多 passion project 本该存在，但被生活挡住——没时间、没技能。希望 Codex 能成为桥梁，让这些只存在于脑子里的东西变成现实。

**九、Q&A：初学者、可靠工作流、从 IC 到“指导 Codex”的非技术能力、以及如何保持代码功底**

Natalie Cone 上场后先聊了些轻松的花絮：她想在论坛里组织一次 DnD 活动；她提到大家往往只通过产品认识 OpenAI，而不了解“产品背后的人”。她还说 Chris 曾在法国生活 14 年，希望未来能做一场法语场。

接着进入提问。

**1）Codex 适合编程初学者吗？**

**提问（Madina Akhan）：** Codex 对初学者友好吗？怎么支持初学者？

**Aaron Friel：** 我需要支持不同产品上的工程师，也不得不学很多我从没接触过的框架。用 Codex 问“这东西怎么工作”“我应该怎么做”，非常有效。但关键是：我们必须理解它在做什么。总体来说，Codex 对学习编程非常有价值；它既能跑很长很复杂的任务，也能服务专业工程师。

**Romain Huet：** 它也能给不同角色超能力。比如产品经理或产品思考者，通过 Codex Cloud 和 Best of N，也能做功能原型，变得更“技术化”。

**Chris Nicholson：** 我也补一句：LLM 是一个无限耐心、不会评判你的导师。很多人会把平时不好意思问资深工程师的“真问题”拿来问模型，这很关键。

**2）如何让 LLM 成为可靠工作流的一部分，而不是偶尔提速？**

**提问（Svetlana Romanava）：** 有哪些具体实践，能把 LLM 变成稳定可靠的开发流程组成部分？比如测试、代码评审、架构等。

**Romain Huet：** 我们团队很多想法，以前会被放进“以后再说”。现在没必要了：想到就试，因为成本变低了。它改变了我们对“工作量”和“难度”的感知。

**Aaron Friel：** 对我来说，最值钱的不是某个单点技巧，而是 **plan 文件/持续维护的文档** 。它像“这次任务做了什么、为什么这么做”的证词，能极大降低摩擦。

**3）从 IC 到“指导 Codex”，最有用的非技术能力是什么？**

**提问（Daniel Green）：** 哪些非技术能力最能帮助工程师从独立贡献者转向“指导 Codex”？

**Aaron Friel：** 我越来越需要戴“产品经理的帽子”：学习他们如何思考终局、如何描述问题、如何定义成功。这个能力非常可迁移到给 Codex 下指令。

**Romain Huet：** 以前我们强调 prompt engineering 的技巧，因为模型能力有限，需要“引导”。现在更关键的是：你如何精确描述问题、描述你希望解决方案走向哪里。能力越强，越考验你的 **判断、品味、沟通** 。

**Chris Nicholson：** 再提醒一次：模型看不见世界。你要不断补齐它没看到的那部分现实数据。

**4）当 Codex 写了很多代码，工程师如何保持“代码功底”？**

**提问（Andrew Mendez）：** 工具写了大量代码，工程师会不会变钝？需要保持代码技能吗？有什么个人实践？

**Aaron Friel：** 当代码变得便宜，最终检验标准就是“它是否实现了我想要的”。你至少要能读懂代码。我现在花更多时间在阅读、理解、调试——只是对象从同事的 PR，扩展到模型的输出。你要能辨别质量；如果看到不熟的技巧，就追问“为什么”“怎么做的”。这会让你成为更有判断力的工程师，也会反过来提升你下一次的指令质量。

**Romain Huet：** 工程师本来就大量时间在读代码、review 同事 PR。现在只是把 AI 同事也加进来。你还能从 code review 抓到的错误里学习：很多时候你会惊讶“原来还有这种风险点”，这也会让你更强。
