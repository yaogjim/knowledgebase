# ### 我使用 Claude Code 的各种方式全记录。

### 我使用 Claude Code 的各种方式全记录。

Audio playback is not supported on your browser. Please upgrade.

我经常使用 Claude Code。

作为业余爱好者，我每周会在副业项目中用虚拟机运行几次，经常搭配 `--dangerously-skip-permissions` 来随心编码脑海中的任何想法。在专业层面，我的团队部分成员负责为工程团队构建 AI 集成开发环境规则与工具，仅代码生成每月就要消耗 *数十亿个 token* 。

CLI 智能体领域正变得日益拥挤，在 Claude Code、Gemini CLI、Cursor 和 Codex CLI 之间，真正的竞争似乎集中在 Anthropic 和 OpenAI 之间。但说实话，当我与其他开发者交流时，他们的选择往往取决于一些表面因素——比如某个“幸运”的功能实现，或是他们更偏爱的系统提示“氛围”。目前这些工具其实都相当不错。我也感觉人们常常过度关注输出风格或用户界面。就我而言，那种“您说得完全正确！”的奉承并非显著缺陷，而是表明你已过于深入细节。我的目标通常是“发射后不管”——委派任务、设定上下文，然后让它自行工作。评判工具的标准应是最终的 PR 成果，而非其实现过程。

过去几个月坚持使用 Claude Code 后，本文是我对其整个生态系统的思考总结。我们将涵盖我使用的几乎所有功能（同样重要的是那些我不使用的功能），从基础的 `CLAUDE.md` 文件和自定义斜杠命令，到强大的子代理、钩子和 GitHub Actions 世界。 **这篇文章最终篇幅略长，建议将其视为参考资料而非需要通篇阅读的内容。**

## CLAUDE.md

要在代码库中有效使用 Claude Code，最重要的文件是根目录下的 `CLAUDE.md` 。该文件相当于智能体的“宪法”，是其理解特定代码仓库运作方式的主要依据。

如何处理这个文件取决于具体情境。在我的业余项目中，我会让 Claude 随心所欲地往里面添加内容。

在我的专业工作中，我们单体代码库的 `CLAUDE.md` 文件被严格维护，目前大小为 13KB（我预计它很容易会增长到 25KB）。

- 仅记录被我们 30%（任意设定）或以上工程师使用的工具和 API（其余工具则记录在特定产品或库的 markdown 文件中）
 
- 我们甚至开始为每个内部工具的文档有效分配最大令牌数，几乎就像向团队出售“广告位”一样。如果你无法简洁地说明你的工具，那它就不够资格写入 `CLAUDE.md` 。
 

#### 技巧与常见反模式

随着时间的推移，我们形成了一套明确而坚定的理念，用于编写高效的 `CLAUDE.md` 文件。

1.  **从设定边界开始，而非编写手册。** 你的 `CLAUDE.md` 文件应该从小处着手，根据 Claude 常犯的错误来记录规范。
 
2.  **切勿** `@` **引用文档文件。** 如果你在其他地方有大量文档，很容易想在 `CLAUDE.md` 中用 `@` 提及这些文件。但这会在每次运行时嵌入整个文件，导致上下文窗口臃肿。但如果你只是 *提及* 文件路径，Claude 通常会忽略它。你必须向智能体 *说明* 读取文件的 *原因* 和 *时机* ：“遇到复杂…用法或 `FooBarError` 时，请参阅 `path/to/docs.md` 获取高级故障排除步骤。”
 
3.  **不要只是说“绝不”。** 避免仅使用否定性限制，例如“绝不使用 `--foo-bar` 标志”。当智能体认为它 *必须* 使用该标志时，会陷入困境。务必提供替代方案。
 
4.  **将** `CLAUDE.md` **用作强制驱动工具。** 如果你的 CLI 命令复杂冗长，不要编写长篇文档来解释它们——这只是在修补人为造成的问题。相反，应该编写一个具有清晰直观 API 的简单 bash 封装脚本，并为其编写文档。尽可能保持 `CLAUDE.md` 的简洁性，是简化代码库和内部工具的绝佳强制手段。
 

这是一个简化的概览：

```markup
# Monorepo

## Python
- Always ...
- Test with <command>
... 10 more ...

## <Internal CLI Tool>
... 10 bullets, focused on the 80% of use cases ...
- <usage example>
- Always ...
- Never <x>, prefer <Y>

For <complex usage> or <error> see path/to/<tool>_docs.md

...
```

最后，我们通过同步此文件与 `AGENTS.md` 文件，来保持与其他 AI 集成开发环境的兼容性，以便我们的工程师能够无缝使用。

*如需获取更多为编码智能体编写 Markdown 的技巧，请参阅 [《AI 无法读取你的文档》](https://blog.sshh.io/p/ai-cant-read-your-docs) [《AI 驱动的软件工程》](https://blog.sshh.io/p/ai-powered-software-engineering) 以及 [《Cursor（AI IDE）工作原理》](https://blog.sshh.io/p/how-cursor-ai-ide-works) 。*

**要点：** 将你的 `CLAUDE.md` 视为一套经过精心设计的高层级指导原则和提示。用它来指引你在哪些方面需要投入开发更适配 AI（及人类）的工具，而非试图将其变成一本面面俱到的操作手册。

## 紧凑、情境与清晰

我建议在编程会话中至少运行一次 `/context` 命令，以了解你如何利用 20 万 token 的上下文窗口（即便使用 Sonnet-1M 模型，我也不完全信任整个上下文窗口能被有效利用）。对我们而言，在单体仓库中开启新会话会消耗约 2 万 token 的基准成本（占 10%），剩余 18 万 token 用于代码变更——这部分额度消耗起来可能相当快。

我有三个主要的工作流程：

- `/compact` **（避免使用）：** 我尽可能避免使用此功能。自动压缩过程不透明、容易出错且优化不佳。
 
- `/clear` **\+** `/catchup` **（简单重启）：** 我的默认重启方式。先使用 `/clear` 清除状态，再运行自定义的 `/catchup` 命令让 Claude 读取我 git 分支中的所有变更文件。
 
- “文档与清空” **（复杂重启）：** 针对大型任务。我会让 Claude 将其计划和进度转储到 `.md` 文件中，通过 `/clear` 清空状态，然后开启新会话，指示它读取 `.md` 文件并继续执行。
 

**要点：** 不要依赖自动压缩。使用 `/clear` 进行简单重启，并通过“文档与清除”方法为复杂任务创建持久的外部“记忆”。

## 自定义斜杠命令

我认为斜杠命令不过是常用提示的简单快捷方式，仅此而已。我的设置极为精简：

- `/catchup` ：我之前提到的命令。它只是提示 Claude 读取我当前 git 分支中所有更改的文件。
 
- `/pr` ：一个简单的助手，用于清理我的代码、暂存更改并准备拉取请求。
 

在我看来，如果你有一长串复杂、自定义的斜杠命令，那其实是形成了一种反模式。对我而言，像 Claude 这样的智能助手的全部意义在于，你可以输入 *几乎* 任何内容，就能获得有用且可合并的结果。一旦你强迫工程师（或非工程师）为了完成工作而去学习一套新的、需要查阅文档的必备魔法命令，那你就已经失败了。

**要点：** 斜杠命令应作为简单的个人快捷方式使用，而非替代构建更直观的 `CLAUDE.md` 文件和配备更优工具的智能体。

## Custom Subagents

理论上，自定义子代理是 Claude Code 在上下文管理方面最强大的功能。其原理很简单：复杂任务需要 `X` 个输入上下文标记（例如如何运行测试），积累 `Y` 个工作上下文标记，并生成 `Z` 个标记的答案。运行 `N` 个任务意味着主窗口需要处理 `(X + Y + Z) * N` 个标记。

子代理解决方案是将 `(X + Y) * N` 的计算工作分配给专门代理处理，这些代理仅返回最终的 `Z` 标记答案，从而保持主上下文的整洁。

我发现它们是一个强大的概念，但在实践中， *自定义* 子代理会引发两个新问题：

1.  **他们封锁了上下文：** 如果我创建一个 `PythonTests` 子代理，就等于把所有测试相关的上下文从 *主* 代理中隐藏了。主代理再也无法全面考量代码变更的影响，现在必须调用子代理才能知道如何验证自己的代码。
 
2.  **它们强制采用人工工作流程：** 更糟糕的是，它们迫使 Claude 遵循僵化的人工预设流程。现在反而变成由我来规定 *具体执行方式* ，这恰恰与我期望智能体解决的问题背道而驰。
 

我偏好的替代方案是利用 Claude 内置的 `Task(...)` 功能来生成 *通用* 智能体的副本。

我将所有关键上下文都放在 `CLAUDE.md` 文件中，然后让 *主代理* 自行决定何时以及如何将工作委派给自身的副本。这样既能享受子代理保存上下文的所有优势，又避免了其缺点。代理能够动态管理自身的编排工作。

在我关于 [《构建多智能体系统（第二部分）》](https://blog.sshh.io/p/building-multi-agent-systems-part) 的文章中，我将此称为“主控-克隆”架构，并且我坚决倾向于这种模式，而非定制子代理所推崇的“主导-专家”模型。

**要点：** 自定义子代理是一种不稳定的解决方案。应将上下文（置于 `CLAUDE.md` 中）赋予主代理，让其运用自身的 `Task/Explore(...)` 功能来管理任务分配。

## 简历、继续与历史

简单来说，我经常使用 `claude --resume` 和 `claude --continue` 命令。它们非常适合重启出错的终端或快速恢复旧会话。我常会通过 `claude --resume` 恢复几天前的会话，只为让智能体总结它当时如何解决特定错误，随后将这些经验用于改进我们的 `CLAUDE.md` 文档和内部工具。

更深入来说，Claude Code 将所有会话历史存储在 `~/.claude/projects/` 目录中，以便利用原始历史会话数据。我编写了脚本对这些日志进行元分析，寻找常见的异常、权限请求和错误模式，以帮助改进面向智能体的上下文。

**要点：** 使用 `claude --resume` 和 `claude --continue` 命令重启会话，挖掘被遗忘的历史上下文。

## Hooks

钩子功能非常重要。虽然我在业余项目中不常使用它们，但在复杂的企业代码库中引导 Claude 时，它们至关重要。这些是确定性的“必须执行”规则，对 `CLAUDE.md` 中的“建议执行”内容形成了有力补充。

We use two types:

1.  **提交时拦截钩子：** 这是我们的核心策略。我们设置了 `PreToolUse` 钩子来包裹所有 `Bash(git commit)` 命令。它会检查 `/tmp/agent-pre-commit-pass` 文件是否存在——该文件 *仅当* 所有测试通过时才会由我们的测试脚本生成。若文件缺失，钩子将拦截提交操作，迫使 Claude 进入“测试-修复”循环，直至构建状态转为绿色。
 
2.  **提示钩子：** 这些是简单、非阻塞的钩子，当智能体执行次优操作时，它们会提供“触发即忘”的反馈。
 

我们有意不使用“写入时拦截”钩子（例如在 `Edit` 或 `Write` 操作时）。在智能体执行计划过程中进行拦截会使其困惑甚至“受挫”。更有效的方式是让其完成工作，然后在提交阶段检查最终完成的结果。

**要点：** 使用钩子在提交时强制执行状态验证（ `block-at-submit` ）。避免在写入时进行阻塞——让智能体完成其计划，然后检查最终结果。

## Planning Mode

在 AI 集成开发环境中，任何“大型”功能变更都离不开周密的规划。

在我的业余项目中，我专门使用内置的规划模式。这是一种在 Claude 开始工作前与其对齐的方式，既明确了 *如何* 构建某个功能，也设定了需要暂停并向我展示进度的“检查点”。经常使用这种方法能培养出强烈直觉，让我明白需要提供哪些最小化上下文才能获得优质方案，同时避免 Claude 搞砸具体实现。

在我们工作的单体代码库中，我们已开始推广一款基于 Claude Code SDK 构建的定制规划工具。它类似于原生规划模式，但经过深度提示调整，使其输出与我们现有的技术设计格式保持一致。该工具还开箱即用地强制执行我们的内部最佳实践——从代码结构到数据隐私与安全。这让我们的工程师能够像高级架构师那样“氛围式规划”新功能（至少宣传上是这么说的）。

**关键点：** 进行复杂改动时，务必使用内置规划模式，以便在代理开始工作前就方案达成一致。

## Skills

我赞同 [Simon Willison 的观点](https://simonwillison.net/2025/Oct/16/claude-skills/) ： **技能（或许）比 MCP 更重要。**

如果你一直关注我的文章，就会知道我已经在大多数开发工作流中逐渐远离 MCP，更倾向于构建简单的 CLI 工具（正如我在《AI 无法读取你的文档》一文中阐述的那样）。我对智能体自主性的心智模型已演变为三个阶段：

1.  **单一提示：** 将所有上下文一次性提供给智能体。（脆弱，难以扩展）。
 
2.  **工具调用：** 这是“经典”的智能体模型。我们手工构建工具，并为智能体抽象出现实环境。（虽然更优，但会带来新的抽象层和上下文瓶颈问题）。
 
3.  **[脚本编写](https://blog.sshh.io/i/167598476/scripting-agents) ：** 我们让智能体直接访问原始环境——包括二进制文件、脚本和文档——它能 *实时编写* 代码与之交互。
 

考虑到这一模式， **智能体技能** 便成为顺理成章的下一项功能。它们是对“脚本”层的正式产品化实现。

如果像我一样，你早已 [偏爱 CLI 而非 MCP，](https://blog.sshh.io/i/171208815/pattern-choose-the-right-interface-cli-vs-mcp) 那么你其实一直在潜移默化中享受着技能带来的好处。 `SKILL.md` 文件只是用一种更有条理、可共享且易于发现的方式，来记录这些 CLI 和脚本并将其暴露给智能体。

**关键点：** 技能是恰当的抽象方式。它们将基于“脚本”的智能体模型规范化，这种模型比 MCP 所代表的僵化、类似 API 的模型更为稳健和灵活。

## MCP（模型上下文协议）

技能的存在并不意味着 MCP 已死（另见 [《MCP 问题全解析》](https://blog.sshh.io/p/everything-wrong-with-mcp) ）。过去，许多人构建了糟糕且上下文繁重的 MCP，其中包含数十个仅镜像 REST API 的工具（ `read_thing_a()` 、 `read_thing_b()` 、 `update_thing_c()` ）。

“脚本”模型（现由技能正式化）更胜一筹，但它需要一种安全的方式来访问环境。在我看来，这正是 MCP 全新且更专注的角色定位。

MCP 不应是臃肿的 API，而应作为简洁安全的中介，提供少量强大而高级的工具

- `download_raw_data(filters…)`
 
- `take_sensitive_gated_action(args…)`
 
- `execute_code_in_environment_with_state(code…)`
 

在此模型中，MCP 的职责并非为智能体抽象现实，而是管理认证、网络与安全边界，随后便退居幕后。它为智能体提供入口点，后者则利用其脚本和\`markdown\`上下文来执行实际工作。

目前我唯一还在使用的 MCP 是用于 [Playwright](https://github.com/microsoft/playwright-mcp) 的，这很合理——因为它是一个复杂的有状态环境。我所有的无状态工具（如 Jira、AWS、GitHub）都已迁移至简单的 CLI。

**要点：** 使用充当数据网关的 MCP。为智能体提供一个或两个高级工具（如原始数据转储 API），使其能够基于这些工具编写脚本进行操作。

## Claude Code SDK

Claude Code 不仅是一个交互式 CLI，更是构建全新智能体的强大 SDK——无论是编程还是非编程任务。在大多数新兴趣项目中，我已开始将其作为默认的智能体框架，替代 LangChain/CrewAI 等工具。

我主要通过三种方式使用它：

1.  **大规模并行脚本处理：** 面对大规模重构、漏洞修复或迁移任务时，我从不使用交互式聊天界面。而是编写简单的 bash 脚本并行调用 `claude -p “in /pathA change all refs from foo to bar”` ，这种方式比依赖主代理管理数十个子代理任务更具可扩展性和可控性。
 
2.  **构建内部聊天工具：** 该 SDK 非常适合将复杂流程封装成简单的聊天界面，供非技术用户使用。比如一个安装程序，在出错时会回退到 Claude Code SDK，直接为用户 *修复* 问题。又或者像我们内部的“ [家装版 v0](http://v0.dev/) ”工具，让设计团队能在我们自研的 UI 框架中快速编写前端原型，既确保创意呈现高保真度，又让代码能更直接地应用于前端生产环境。
 
3.  **快速智能体原型开发：** 这是我最常用的功能。它不仅仅局限于编码。如果我对任何智能体任务有想法（例如使用自定义 CLI 或 MCP 的“威胁调查智能体”），我会先通过 Claude Code SDK 快速构建并测试原型，再投入完整的部署框架开发。
 

**要点：** Claude Code SDK 是一款功能强大的通用智能体框架。它适用于批量处理代码、构建内部工具，以及在选用更复杂框架之前快速搭建智能体原型。

## Claude Code GHA

Claude Code GitHub Action（GHA）可以说是我最偏爱却又最容易被忽视的功能之一。它的概念很简单：就是在 GHA 中运行 Claude Code。但正是这种简洁性让它如此强大。

这类似于 [Cursor 的后台代理](https://cursor.com/docs/cloud-agent) 或 Codex 托管的网页界面，但可定制性更强。您可以完全控制整个容器和环境，不仅能获取更多数据访问权限，更重要的是提供了比其他任何产品都更强大的沙箱和审计控制功能。此外，它还支持 Hooks 和 MCP 等所有高级特性。

我们已利用它构建了自定义的“随处发起拉取请求”工具。用户可以从 Slack、Jira 甚至 CloudWatch 警报中触发 PR，而 GHA 将修复错误或添加功能，并返回一个经过全面测试的拉取请求 [1](#fn:1) 。

由于 GHA 日志是完整的代理日志，我们建立了运维流程，定期在公司层面审查这些日志，以发现常见错误、bash 错误或不符合规范的工程实践。这形成了数据驱动的飞轮效应：发现缺陷 → 改进 CLAUDE.md/CLI 工具 → 优化代理性能。

```markup
$ query-claude-gha-logs --since 5d | claude -p “see what the other claudes were getting stuck on and fix it, then put up a PR“
```

**关键要点：** GHA 是将 Claude Code 操作化的终极方式，它能将这一工具从个人辅助转变为工程系统中可审计、可自我完善的核心组成部分。

## settings.json

最后，我还有一些特定的 `settings.json` 配置，这些配置对于业余爱好和专业工作都至关重要。

- `HTTPS_PROXY` / `HTTP_PROXY` ：这对调试非常有用。我会用它来检查原始流量，准确查看 Claude 发送的具体提示内容。对于后台代理来说，它也是实现精细化网络沙箱隔离的强大工具。
 
- `MCP_TOOL_TIMEOUT` / `BASH_MAX_TIMEOUT_MS` ：我会调高这些值。我喜欢运行长时间、复杂的命令，而默认的超时设置往往过于保守。老实说，我不确定现在有了 bash 后台任务功能是否还需要这样做，但为了以防万一，我还是保留了这个设置。
 
- `ANTHROPIC_API_KEY` ：在工作中，我们使用企业级 API 密钥（ [通过 apiKeyHelper](https://www.reddit.com/r/ClaudeAI/comments/1jwvssa/comment/mtt0urz/?utm_source=share&utm_medium=web3x&utm_name=web3xcss&utm_term=1&utm_content=share_button) ）。这使我们从“按席位”许可模式转向“按使用量”计费模式，更符合我们的工作方式。
 
 - 它解释了开发者使用情况的 *巨大* 差异（我们观察到工程师之间的差异高达 1:100 倍）。
 
 - 它让工程师能够在我们的单一企业账户下，对非 Claude 代码的 LLM 脚本进行调试。
 
- `“权限”` ：我会偶尔自查已允许 Claude 自动运行的命令列表。
 

**要点：** 你的 `settings.json` 是实现高级自定义的强大工具。
