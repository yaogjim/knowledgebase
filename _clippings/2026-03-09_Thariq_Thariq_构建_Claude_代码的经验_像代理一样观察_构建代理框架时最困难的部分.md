# 构建 Claude 代码的经验：像代理一样观察

构建代理框架时最困难的部分之一是构建其动作空间。

Claude 通过工具调用发挥作用，但在 Claude API 中，工具可以通过多种方式构建，使用 bash、技能以及最近新增的代码执行等原语（有关 Claude API 中程序化工具调用的更多信息，请参阅 @RLanceMartin 的新文章 ）

考虑到所有这些选项，你该如何设计代理的工具？你只需要一个工具（比如代码执行或 bash）吗？如果有 50 个工具，每个用例对应代理可能遇到的场景，又会怎样？

为了站在模型的角度思考，我喜欢想象自己面临一道难题。为了解决这个问题，你会需要哪些工具？这取决于你自己的技能！

最基础的方法是使用纸张，但你会受手动计算的限制。计算器会更好，但你需要知道如何操作更高级的功能。最快且最强大的选择是计算机，但你必须知道如何用它来编写和执行代码。

这是一个设计你的代理的有用框架。你希望给它提供与其自身能力相匹配的工具。但你如何知道这些能力是什么呢？你需要关注、查看它的输出、进行实验。你要学会像代理一样去观察。

以下是我们在开发 Claude Code 时关注 Claude 所获得的一些经验教训。

# 改进需求获取与 AskUserQuestion 工具

在开发 AskUserQuestion 工具时，我们的目标是提升 Claude 的提问能力（通常称为引导）。

虽然 Claude 可以直接用纯文本提问，但我们发现回答这些问题似乎花费了不必要的大量时间。我们该如何降低这种摩擦并提高用户与 Claude 之间的沟通带宽？

## 尝试 #1 - 编辑 ExitPlanTool

我们首先尝试的是向 ExitPlanTool 添加一个参数，以便在计划中包含一个问题数组。这是最容易实现的，但它让 Claude 感到困惑，因为我们同时请求了一个计划和一组关于该计划的问题。如果用户的回答与计划中所述的内容相冲突怎么办？Claude 是否需要两次调用 ExitPlanTool？我们需要另一种方法。

(你可以在我们关于提示缓存的文章中了解更多我们开发 ExitPlanTool 的原因我们关于提示缓存的文章 )

## 第2次尝试 - 更改输出格式

接下来，我们尝试修改 Claude 的输出指令，使其能够使用稍作修改的 Markdown 格式来提问。例如，我们可以要求它输出带方括号选项的项目符号问题列表。然后我们可以解析并将该问题格式化为用户界面。

虽然这是我们能做的最一般性的改动，Claude 甚至似乎能够很好地输出这个内容，但这并不确定。Claude 可能会添加额外的句子、遗漏选项，或者完全使用不同的格式。

## 尝试#3 - AskUserQuestion 工具

最后，我们决定创建一个工具，Claude 可以在任何时候调用它，但特别会在规划模式下被提示调用。当工具被触发时，我们会显示一个模态框来展示问题，并阻止代理的循环，直到用户回答。

这个工具使我们能够提示 Claude 生成结构化输出，并帮助我们确保 Claude 为用户提供多种选择。它还为用户提供了实现这一功能的方法，例如在 Agent SDK 中调用它，或在技能中引用它。

最重要的是，Claude 似乎喜欢调用这个工具，我们发现它的输出效果很好。即使是设计最精良的工具，如果 Claude 不知道如何调用它，也无法正常工作。

这是 Claude Code 中引导的最终形式吗？我们不确定。正如你在下一个示例中所见，对一个模型有效的方法可能对另一个模型并非最佳。

# 能力更新 - 任务和待办事项

当我们首次推出 Claude Code 时，我们意识到这个模型需要一个待办事项列表来保持正轨。待办事项可以在开始时记录，随着模型完成工作而勾选。为此，我们为 Claude 提供了 TodoWrite 工具，该工具可以写入或更新待办事项，并将它们展示给用户。

但即便如此，我们经常看到 Claude 忘记了自己需要做什么。为了适应，我们每 5 轮插入一次系统提醒，提醒 Claude 其目标。

但随着模型的改进，它们不仅不再需要被提醒待办事项列表，反而觉得这很有局限性。收到待办事项列表的提醒让 Claude 觉得它必须严格遵守这个列表，而不是修改它。我们还看到 Opus 4.5 在使用子代理方面也变得更好了，但子代理如何在共享的待办事项列表上进行协作呢？

看到这一点，我们将 TodoWrite 替换为 Task Tool（ 了解更多关于任务的信息 ）。而待办事项是为了让模型保持正轨，任务则更侧重于帮助智能体之间进行沟通。任务可以包含依赖关系，在子智能体之间共享更新，并且模型可以修改和删除它们。

随着模型能力的提升，你先前模型所需的工具现在可能反而会限制它们。不断重新审视先前关于所需工具的假设是很重要的。这也是为什么坚持使用一小部分具有相当相似能力特征的模型是很有用的。

# 设计一个搜索界面

对于 Claude 来说，一组特别重要的工具是可以用来构建自身上下文的搜索工具。

当 Claude Code 首次推出时，我们使用 RAG 向量数据库为 Claude 查找上下文。虽然 RAG 功能强大且速度快，但它需要索引和设置，并且在众多不同环境中可能会不稳定。更重要的是，Claude 被提供了这个上下文，而不是自己查找上下文。

但是如果 Claude 能够在网上搜索，为什么不搜索你的代码库呢？通过给 Claude 一个 Grep 工具，我们可以让它搜索文件并自行构建上下文。

这是我们观察到的一种模式：随着 Claude 变得更智能，只要给它合适的工具，它构建上下文的能力就会越来越强。

当我们引入 Agent 技能时，我们明确阐述了渐进式披露的概念，这使得智能体能够通过探索逐步发现相关上下文。

Claude 可以读取技能文件，这些文件可以引用其他模型能够递归读取的文件。事实上，技能的一个常见用途是为 Claude 增加更多搜索能力，比如向它提供如何使用 API 或查询数据库的指导。

在一年的时间里，Claude 从无法真正构建自己的上下文，发展到能够在多层文件中进行嵌套搜索，以找到它所需的确切上下文。

渐进式展示现在是我们常用的一种技术，用于添加新功能而无需额外添加工具。

# 渐进式披露 - Claude 代码指南代理

Claude Code 目前拥有约 20 个工具，我们一直在思考是否需要所有这些工具。添加新工具的门槛很高，因为这会给模型多一个需要考虑的选项。

例如，我们注意到 Claude 对如何使用 Claude Code 了解不足。如果您问它如何添加 MCP 或斜杠命令是做什么的，它都无法回答。

我们本可以将所有这些信息都放在系统提示中，但考虑到用户很少询问这方面的内容，这会导致上下文衰减，并干扰了 Claude Code 的主要工作：编写代码。

相反，我们尝试了一种渐进式展示的方式。我们给了 Claude 一个文档链接，它可以加载该链接以搜索更多信息。这一方法有效，但我们发现，Claude 会加载大量结果到上下文中以找到正确答案，而实际上你真正需要的只是答案。

因此我们构建了 Claude 代码指南子代理，当你询问关于它自己的问题时，Claude 会被提示调用这个子代理。该子代理包含关于如何有效搜索文档以及应该返回什么内容的详细指令。

虽然这并不完美，但当你询问 Claude 如何自我配置时，它仍然可能会感到困惑，不过它比以前好多了！我们能够在不添加新工具的情况下，向 Claude 的操作空间中添加内容。

## 一种艺术，而非科学

如果你期望有一套关于如何构建你的工具的严格规则，很遗憾，本指南并非如此。为你的模型设计工具既是一门科学，也是一门艺术。它在很大程度上取决于你所使用的模型、代理的目标以及它所处的环境。

经常实验，解读输出，尝试新事物。像代理一样观察。
