**Viv**

# 我们如何构建深度智能体的评估

TLDR: 最佳的代理评估直接衡量我们关心的代理行为。以下是我们如何获取数据、创建指标，并随着时间的推移开展范围明确、针对性强的实验，以提高代理的准确性和可靠性。

## 评估塑造代理行为

我们一直在精心构建评估以衡量和改进

[Deep Agents](https://github.com/langchain-ai/deepagents). Deep Agents 是一个开源的、与模型无关的代理工具包，可为像

[Fleet](https://www.langchain.com/langsmith/fleet)

以及

[Open SWE](https://github.com/langchain-ai/open-swe)

. 评估定义并塑造代理行为，因此精心设计它们非常重要。

每次评估都是一个会改变你的代理系统行为的向量。例如，如果一个关于高效文件读取的评估失败，你可能会调整系统提示或 read\_file 工具描述来引导行为，直到评估通过。你保留的每次评估都会随着时间的推移对整个系统施加压力。

在添加评估时要深思熟虑，这一点至关重要。盲目地添加数百（或数千）个测试可能会很诱人。但这会导致一种错觉，即通过在评估套件中取得高分来“提升你的智能体”，而该评估套件可能无法准确反映你在生产环境中关注的行为。

更多的评估 ≠ 更好的智能体。相反，构建有针对性的评估以反映生产环境中期望的行为。

在构建 Deep Agents 时，我们梳理生产环境中关键的行为，例如从文件系统中的多个文件中检索内容，或准确地按顺序组合 5 个以上的工具调用。与整体使用基准测试任务不同，我们采用以下方法进行评估整理：

1.  决定我们希望代理遵循哪些行为。然后研究并精心挑选针对性的评估，以可验证的方式衡量这些行为。
2.  对于每个 eval，添加一个 docstring 来解释它如何衡量 agent 能力。这确保每个 eval 是自文档化的。我们还为每个 eval 标记如 tool\_use 之类的类别，以支持分组运行。
3.  检查输出跟踪以了解故障模式并更新评估覆盖率

因为我们将每次评估运行追溯到一个共享的

[LangSmith](https://docs.langchain.com/langsmith/observability) 项目，团队中的任何人都可以参与进来分析问题、进行修复，并重新评估特定评估的价值。这为添加和维护良好的评估创建了共同责任。在许多评估中运行多个模型可能会成本高昂，因此有针对性的评估可以节省成本，同时改进你的代理。

在本博客中我们涵盖：

- 我们如何整理数据
- 我们如何定义指标
- 我们如何运行评估

## 我们如何整理数据

我们有几种获取 evals 的方式：

1.  利用我们代理内部试用的反馈
2.  从外部基准测试中拉取选定的评估数据（如
 
 [终端基准测试 2.0](https://www.tbench.ai/) 或
 
 [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html)
 
 ）并经常为特定代理调整这些评估数据
 
3.  编写我们自己的（手工的）评测和单元测试，针对我们认为重要的行为

![Image](https://pbs.twimg.com/media/HET8gsLWkAAun5Q?format=jpg&name=large)

我们每天都在内部试用我们的代理。每个错误都成为编写评估和更新我们代理定义及上下文工程实践的机会。

> 注意：我们将 SDK 单元测试和集成测试（系统提示透传、中断配置、子代理路由）与模型能力评估区分开来。任何模型都能通过这些测试，因此将它们纳入评分不会增加任何信号。你绝对应该编写单元测试和集成测试，但本博客仅关注模型能力评估。

## 内部试用代理和读取痕迹是评估的重要来源

这使得发现错误成为可能。

[跟踪记录](https://docs.langchain.com/langsmith/observability-concepts#traces)给我们提供数据以了解代理行为。由于跟踪记录通常很大，我们使用内置代理，如

[Polly](https://docs.langchain.com/langsmith/polly)

或

[Insights](https://docs.langchain.com/langsmith/insights)

以大规模分析它们。你也可以对其他代理（如 Claude Code 或

[Deep Agents CLI](https://docs.langchain.com/oss/python/deepagents/cli/overview)

）以及一种获取跟踪记录的方法，如

[LangSmith CLI](https://docs.langchain.com/langsmith/langsmith-cli)

。我们的目标是理解每种失败模式，提出修复方案，重新运行代理，并跟踪进度和随时间的回归情况。

例如，现在很大一部分修复 bug 的拉取请求（PR）是通过

[Open SWE](https://blog.langchain.com/open-swe-an-open-source-framework-for-internal-coding-agents/)，我们的开源背景编码代理。使用它的团队会接触许多不同的代码库，这些代码库具有不同的上下文、规范和目标。这自然会导致错误。Open SWE 的每一次交互都会被追踪，因此这些交互可以很容易地成为评估，以确保错误不再发生。

其他评估是从现有的基准测试中提取并调整，如

[BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) 用于函数调用。对于编码任务，我们与

[Harbor](https://github.com/laude-institute/terminal-bench)

以运行选定的任务来自数据集（如

[Terminal Bench 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0)

在沙箱环境中执行的任务。许多评估是从头编写的，作为专注的测试以观察孤立行为，例如测试 read\_file 工具。

## 我们根据它们测试的内容对评估进行分组

建立一个评估的分类体系来获得对智能体表现的中间视角是很有帮助的（不是单一的数字，也不是单个的运行结果）。

> 提示： 创建该分类法时，应关注它们测试的内容，而非它们的来源。例如，来自
> 
> [FRAMES](https://huggingface.co/datasets/google/frames-benchmark) 和
> 
> [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html)
> 
> 可以标记为“外部基准测试”，但这无法分别展示它们如何衡量检索和工具使用。

以下是我们定义的一些类别以及它们测试的内容：

如今，所有评估均是智能体在某个任务上的端到端运行。我们刻意鼓励评估结构的多样性。有些任务从输入提示开始一步完成，而另一些任务则需要经过10+轮交互，由另一个模型模拟用户。

## 我们如何定义指标

在为我们的代理选择模型时，我们首先考虑正确性。如果一个模型不能可靠地完成我们关注的任务，其他一切都无关紧要。我们在评估中运行多个模型，并随着时间的推移不断优化评估框架，以解决我们发现的问题。

测量正确性取决于测试的内容。大多数内部评估使用自定义断言，例如“代理是否并行调用了工具？”。像 BFCL 这样的外部基准测试使用与数据集中真实答案的精确匹配。对于像代理是否在内存中持久化了正确内容这类语义层面的正确性评估，我们使用以 LLM 作为评判者的方法。

一旦几个模型达到了那个标准，我们就转向效率。 两个解决相同任务的模型在实际中可能表现得非常不同。 一个模型可能会进行额外的交互轮次，进行不必要的工具调用，或者由于模型大小而在完成任务时更慢。在生产环境中，这些差异会表现为更高的延迟、更高的成本以及更差的整体用户体验。

总体而言，我们为每次评估器运行所测量的指标是：

![Image](https://pbs.twimg.com/media/HET_GObbYAECk4q?format=jpg&name=large)

解决率衡量智能体解决任务的速度，通过预期步骤数进行归一化。与延迟比类似，它捕捉解决任务的端到端时间，包括模型往返、服务提供商延迟、错误转向和工具执行时间。对于能够定义理想轨迹的简单任务，解决率比延迟比更容易处理，因为它只需要测量给定智能体的任务持续时间。

这为我们提供了一种选择带有针对性评估集的模型的简单方法：

1.  首先检查准确性：哪些模型在你真正关心的任务上足够准确？
2.  然后，比较效率：在足够好的模型中，哪一个在正确性、延迟和成本之间提供最佳的权衡？

## 评估相关的有用指标示例

为了让模型比较具有可操作性，我们研究模型如何成功和失败。这需要一个具体的参考点，来定义“良好执行”在准确性之外的样子。我们使用的一个基本概念是理想轨迹。 这是一系列步骤，能够产生正确的结果，且不包含“不必要”的操作。

对于简单且范围明确的任务，变量定义得足够严格，使得最优路径通常很明显。对于更开放的任务，我们使用到目前为止表现最佳的模型近似生成一条轨迹，然后随着模型和工具的改进重新审视基准。通过这种方式，观察智能体的行为有助于我们优化关于理想轨迹的先验知识。

考虑一个简单的请求：

> 我住的地方当前的时间和天气是什么？

一个智能体的理想轨迹可能如下所示：

- 它进行最少的必要工具调用（例如：确定用户 → 确定位置 → 获取时间和天气）
- 它在可能的情况下并行化独立的工具调用
- 它生成最终答案，不经过不必要的中间步骤

理想轨迹： 4 步骤，4 工具调用，约 8 秒

![Image](https://pbs.twimg.com/media/HEUAv4bbYAAtFOs?format=jpg&name=large)

现在将其与一条在技术上仍然正确但效率较低的轨迹进行比较。

低效轨迹: 6步，5次工具调用，约14秒。

![Image](https://pbs.twimg.com/media/HEUAy-UbwAAQTf3?format=jpg&name=large)

正确但低效的轨迹: 6 个代理步骤，5 次工具调用，包含一次不必要的工具调用，且未并行化工具调用。

上面的例子具有说明性：REPL 可以更快地解决这个任务，但调用工具的版本让这个想法更容易解释。

两次运行都是正确的，但第二次运行会增加延迟和成本，并增加了更多的失败机会。

这种框架使我们能够在评估中同时评估正确性和效率。我们维护并更新指标，以将运行结果提炼为可衡量的数值，从而用于比较实验。从上面的例子中，低效但正确的运行得分会是：

## 我们如何进行评估

我们使用 pytest 和 GitHub Actions 在 CI 中运行评估，以便代码变更能在干净、可重现的环境中执行。每次评估都会创建一个使用指定模型的 Deep Agent 实例，向其输入任务，并计算正确性和效率指标。

我们也可以通过标签来运行评估的一个子集，以节省成本并衡量针对性实验。例如，如果要构建一个需要大量本地文件处理和合成的智能体，我们可能会专注于带标签为 file\_operations 和 tool\_use 的子集。

```bash
export LANGSMITH_API_KEY="lsv2_..."

uv run pytest tests/evals --eval-category file_operations --eval-category tool_use --model baseten:nvidia/zai-org/GLM-5
```

我们的评估架构和实现已在

[Deep Agents 代码仓库](https://github.com/langchain-ai/deepagents/tree/main/libs/evals) 。
