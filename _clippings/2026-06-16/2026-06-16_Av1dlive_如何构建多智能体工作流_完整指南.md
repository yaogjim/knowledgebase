## 模块 1：多智能体系统实际上是什么

* * *

## 单元和运行时

智能体是一个单元：一个 LLM 实例，拥有自己的系统提示词、工具集、记忆窗口，有时还拥有自己的模型。多智能体系统是一种运行时：一种协调两个或多个智能体、在它们之间路由任务、处理交接并执行治理层的机制。

这种区别很重要，因为多智能体系统中的大多数故障是运行时故障，而非智能体故障。单个智能体通常能够正确推理。系统在协调、上下文传播和权限边界方面出现故障。

## 为什么单个代理会失效

单个代理处理大型任务时会遇到三个硬性限制：

- 上下文饱和度： 每一个中间结果都会占用上下文窗口。在大规模场景下，智能体是基于自身大量的历史记录进行推理，而非实际问题。
- 串行瓶颈： 代理一次执行一个步骤。本可并行的 200 个文件迁移却串行运行数小时。
- 脆弱恢复： 如果代理在任务中途崩溃或漂移，整个任务将重新启动。没有检查点。

多智能体系统通过在孤立的智能体之间分配工作、在任何智能体的上下文之外存储中间状态以及添加阶段级别的恢复点，解决这三个问题。

## 模块 2：Claude 的三种编排原语

在选择拓扑结构之前，请先了解 Claude Code 提供的三个协调原语。选错适合这项工作的原语是最常见的架构错误。

决策规则：

- 使用子代理，当您需要一两个独立的调查并向单个会话汇报时。
- 使用 agent teams 当队友需要直接与彼此以及与你沟通，无需经过中央编排器。
- 使用动态工作流当编排本身需要可重复执行时，计划必须能够在上下文限制下保持有效，或者任务需要数小时到数天。

## 模块 3：六种编排拓扑结构

你构建的每个多智能体系统都会使用六种拓扑结构之一或它们的组合。将拓扑结构与问题匹配，而非与框架匹配。

## 顺序流水线

以链式排列的代理。代理 A 生成输出，将其传递给代理 B，代理 B 再将其传递给代理 C。

```markdown
text[Agent A: Parse] -> [Agent B: Analyze] -> [Agent C: Format]
```

使用场景： 工作严格依赖。每个步骤必须在前一步完成后才能开始。数据只有一条路径，便于调试。

Claude 实现: 提示链在单个动态工作流脚本中。每个阶段运行一个子代理，等待完成，将结果作为输入传递给下一阶段。

故障模式： 延迟加剧。如果 Agent B 运行缓慢，整个流程将等待。请勿用于处理具有独立并行路径的工作。

* * *

## 2\. 协调器-工作节点（中心-分支）

一个协调器代理接收顶层任务，将其分解为子任务，并将每个子任务分配给一名专业工作者。工作者将结果返回给协调器，协调器进行综合。

```markdown
text[Coordinator]
 / | \
[Security]  [Perf]  [Auth] [Coverage]
 \ | /
 [Coordinator: Synthesize]
```

使用场景： 工作分解为不同的专业领域。路由逻辑在规划阶段稳定且可预知。

Claude 实现： 这是 Claude 动态工作流的默认形态。工作流脚本是协调者；子代理是执行者。Claude 将分解逻辑写入脚本，而非对话中。

故障模式： 协调器存在单点故障。如果协调器的上下文填满或漂移，整个系统会降级。解决方法是让协调器的职责范围缩小：仅进行分解和路由，不进行领域推理。

* * *

## 3\. 并行扇出带合并

多个代理同时处理独立的子任务。合并步骤收集并协调它们的输出。

```markdown
text[Orchestrator]
 |  |  |  |
 [A][B][C][D] <- simultaneous
 |  |  |  |
[Merge + Reconcile]
```

适用场景： 子任务之间无依赖。典型使用场景：审计 200 个文件、查询多个数据源、同时进行五次 bug 类调查。

Claude 实现： Claude 的动态工作流默认最多运行 16 个并发代理。设计工作流阶段，确保扇出任务真正独立。结果存储在脚本变量中，而非编排器的上下文。

性能提升： 并行执行可将无步骤依赖的任务的处理时间减少 60-80%。

故障模式： 合并逻辑是难点。如果代理返回不一致的模式或冲突的结果，简单的合并会产生无效数据。在编写扇出之前设计输出契约。

* * *

## 4\. 生成器-验证器

一个代理生成输出。第二个代理根据显式标准对其进行评估。结果反馈给生成器。循环运行直到输出通过或达到最大迭代次数。

```markdown
text[Generator] -> [Verifier] -> passes? -> done
 ^ |
 |-- feedback --| fails? -> iterate
```

使用场景： 输出质量至关重要且评估标准可以明确地写下来。测试编写、安全发现、迁移计划。

Claude 实现： 两阶段动态工作流。阶段 1 并行运行生成器代理。阶段 2 对每个生成器输出运行独立验证器代理。只有通过验证的输出才会被合并。这是所有 Claude 动态工作流默认内置的对抗性验证。

故障模式: 如果核实者的标准模糊，就会变成橡皮图章。请在工作流提示中，将核实标准写为明确、可检查的规则。

* * *

## 5\. 共享状态

代理通过一个它们都可以直接读写的持久化存储进行协调。没有中央编排器来路由消息；共享存储就是协调机制。

```markdown
text[Agent A] ---|
[Agent B] ---|--> [Shared Store: Markdown / JSON / DB]
[Agent C] ---|
```

使用时机：Agents 逐步基于彼此的发现进行构建。一个 Agent 发现的上下文信息对处理相同问题的其他方来说是立即可用的。

Claude 实现： 实际上，这是一个 git worktree 中的文件系统或结构化文档文件夹。我的生产环境 Claude Code 配置采用这种方式：每一个决策、每一个计划、每一个已完成的事项都以 Markdown 文件的形式存入结构化文档文件夹。下游代理会自动获取这些文件。

故障模式: 上下文污染（模块 5 中介绍）。代理将错误发现写入共享存储。每个下游代理将其视为基准事实。错误在整个系统中传播。

* * *

## 6\. 辩论（对抗性多智能体）

两个或多个代理从对立的立场攻击同一问题。裁判代理（或编排者）调和辩论结果。

```markdown
text[Agent: Find Issues] -> claim
[Agent: Refute Issues] -> counter-claim
[Judge: Reconcile] -> verified finding
```

使用时机： 你需要在发现到达你之前，这些发现能够经受住对抗性压力的考验。安全审计、迁移风险评估、任何假阳性或假阴性会带来实际成本的工作。

Claude 实现：Claude 动态工作流原生包含这种模式。“代理从独立角度处理问题。其他代理随后尝试反驳他们发现的内容。运行过程会迭代直到答案收敛”。你无需显式编写辩论逻辑；它作为工作流验证阶段的一部分运行。

* * *

## 模块4：通信架构

代理如何传递信息是大多数系统的薄弱环节。设计决策不在于使用哪种消息格式，而在于代理是直接通信还是通过一个中间件进行通信。

* * *

## 直接通信 vs. 底层通信

生产系统中的实用规则

> 代理不应直接相互通信。它们应向共享内存层写入数据并从中读取数据。规范知识应集中存储在一个位置。每个代理都应在明确的角色、明确的工具和明确的输出条件下独立运作。

Claude 的动态工作流默认实现基于基底的通信。中间结果存在于脚本变量中，而非任何代理的上下文窗口中。这就是为什么编排脚本是 JavaScript 在架构上很重要的原因：脚本变量是基底。

* * *

## 输出契约

生产系统中的每个代理都需要一个明确的输出契约：一个定义它必须返回的确切内容的模式。如果没有它，合并步骤和下游代理将不得不猜测他们收到的内容。

```javascript
/ Example output contract for a security audit agent
{
  "finding_id": "string",
  "file_path": "string",
  "line_number": "number",
  "severity": "critical | high | medium | low",
  "description": "string",
  "confirmed": "boolean",
  "suggested_fix": "string"
}
```

在你的工作流程提示中强制执行此操作

```markdown
Return results in this exact JSON schema. If a field cannot be populated, return null for that field. Do not add fields not in the schema.
```

* * *

## 上下文窗口预算

每个智能体都有一个有限的上下文窗口。在多智能体系统中，你需要同时管理一组上下文窗口。重要的设计决策：

- 保持编排器的范围窄小。 编排器应进行分解和路由。领域推理属于专业代理。范围狭窄的编排器不会将未使用的领域知识填充到其上下文中。
- 限制代理接收的内容。 只传递代理完成其特定任务所需的内容。不要向需要三个文件的代理传递完整的文件树。
- 对短期记忆使用热路径限制。 在代理循环中，仅保留活跃上下文中最近的 3-5 次交互。将较旧的上下文丢弃到共享存储中。

* * *

## 模块5：故障模式

这些是五个摧毁生产多智能体系统的失败。每一个都是可预测且可预防的。

* * *

## 上下文污染

一个代理向共享存储写入错误输出（幻觉结果、错误模式、损坏状态）。下游代理将其视为事实并基于此进行构建。错误在整个流程中不断累积。

生产中的迹象： 看似合理但无法追溯到实际文件内容的发现。针对同一文件自信地相互矛盾的代理。

预防:

- 在每个写入点进行模式验证。没有代理会将原始文本写入共享存储；所有内容都必须经过类型化模式的处理。
- 验证代理在输出到达共享存储之前检查它们，而不是之后。
- 人工审核关卡在一个阶段的结果为下一阶段奠定基础之前。

* * *

## 2\. 级联故障

一个代理失败。编排器未隔离故障，而是将错误结果路由到下游。基于失败输出构建的代理也会失败。缺乏适当编排的多代理系统，其已记录的失败率为41-86.7%。

预防:

- 断路器：如果代理返回错误或空输出，停止该分支，不转发。
- 流程检查点处的置信度评分：低于阈值的输出不通过。
- 来自多个代理的独立发现：单个失败无法破坏整个运行，如果其他代理独立得出相同或不同的结论。

* * *

## 3\. 范围蔓延

编排器的分解过于宽泛。代理对其任务的解读过于宽泛。一个被指派负责“审计代码库”的代理开始编辑它本不该触碰的文件。

预防:

- 每个代理在其任务提示中都有明确的、有边界的范围：路径、文件类型、允许的操作。
- 编辑策略：只读，除非明确授予特定路径的写入权限。
- Anthropic 自身的设计指导原则：最小化占用，仅请求必要的权限，优先选择可逆操作。

* * *

## 4\. 静默替换

代理无法完成某个步骤（API 调用失败、文件不可读），并在 try/catch 块中悄无声息地插入占位数据。它报告成功。流水线将占位符视为真实结果。

预防: 在 CLAUDE.md 或您的工作流的代理系统提示中：

```markdown
 Error Handling
- NEVER substitute mock or placeholder data for a real result
- If a step fails, report the error and halt this agent's execution
- A fallback is acceptable ONLY if explicitly logged as a fallback with the reason
```

* * *

## 5\. 协调死锁

两个代理互相等待。代理 A 无法继续，直到代理 B 完成。代理 B 无法开始，直到代理 A 写入共享存储。工作流停滞。

预防:

- 工作流脚本中的显式依赖图。Claude 的编排脚本在代码中编码依赖关系，而非隐式的对话顺序。
- 每次调用代理时设置超时。如果代理在 X 秒内未返回，编排器将标记其为失败并绕过它。
- 设计阶段在展开之前必须真正独立。依赖映射是模块8的飞行前检查清单。

* * *

## 模块 6 :治理层

每个多智能体系统都需要三个结构层才能可靠运行：

治理层是区分演示系统和生产系统的关键。

* * *

## 治理层的功能

1.  权限范围: 每个代理都有一个声明的权限集。安全审计代理仅拥有只读访问权限。迁移代理仅对特定路径拥有写访问权限。任何代理的权限都不应超出其任务所需的范围。
2.  人在回路门： 定义哪些操作在执行前需要人工审批。不可逆操作（文件删除、生产环境 API 调用、模式迁移）总是需要经过人在回路门。
3.  Audit trails: Every agent decision, every action, every tool call gets logged with the agent ID and the reasoning that led to it. When something breaks, you need to replay exactly what happened. 审计跟踪： 每个代理决策、每个操作、每次工具调用都会被记录，包含代理 ID 以及导致该决策/操作/调用的推理过程。当出现问题时，需要精确重放当时发生的情况。
4.  爆炸半径限制： 定义任何单个代理在行为不当情况下可能造成的最大破坏范围。文件系统写入限定在工作树内，而非仓库根目录。API 调用限制在预发布环境，且无明确的生产环境访问权限。

* * *

## 在 Claude 动态工作流中实施治理

治理层转化为三个具体的工件：

```markdown
CLAUDE.md rules (apply to all agents in the session):

t## Agent Permissions
- Read access: entire repository
- Write access: only paths listed in the task prompt
- Shell commands: only commands on the approved list
- Network: no external calls unless the task prompt specifies an endpoint

## Error Handling
- Silent failures are not permitted
- Every error must be reported before halting

## Irreversible Action Policy
- Database writes require explicit approval in the task prompt
- File deletions require explicit approval in the task prompt
- No production API calls without "production: true" in the task prompt
```

## 模块 7：生产中的五种 Claude 原生模式

这些是 Anthropic 记录的五种模式，这些模式源自 Claude 生产系统中可靠运行的实践。每一种模式都直接对应一个动态工作流结构。

* * *

## 模式1：提示链

1.  将一个复杂任务分解为一系列更简单的提示。前一个的输出成为下一个的输入。每一步都足够小，使得代理能够可靠地完成它。
2.  何时使用： 任务具有明确的顺序阶段。文档处理（先提取，再分析，然后总结）、数据转换管道、代码生成后进行测试，然后进行审查。

Claude 工作流形态

```markdown
Phase 1: Parse and extract -> Phase 2: Analyze -> Phase 3: Generate report
```

每个阶段都是一次独立的代理调用。阶段1的输出通过脚本变量成为阶段2的输入。

* * *

## 模式2：路由

1.  分类器代理读取输入并将其路由到相应的专科医生。分类器不处理任务，仅负责路由。
2.  何时使用： 任务以异构流的形式到达。编码任务分配给代码代理，安全问题分配给安全代理，文档问题分配给文档代理。

Claude 工作流形态

```markdown
text[Classifier Agent: reads task, returns agent_type]
 |
 -> dynamic dispatch to [Security | Code | Performance | Documentation]
```

在工作流脚本的路由逻辑中实现调度

* * *

## 模式3：并行化

同时向多个代理分发独立的子任务，最后合并结果。

适用场景：子任务之间没有依赖。审计多个文件、搜索多个数据源、同时运行多个分析类别。

Claude 工作流形态

```javascript
/ Workflow script structure
const files = getFilesInScope();
const results = await Promise.all(
  files.map(file => runAgent({ task: 'audit', scope: file }))
);
const merged = mergeAndDeduplicate(results);
```

动态工作流最多可运行16个并发代理。与顺序链式调用相比，令牌使用量减少60-90%，因为中间结果保留在脚本变量中。

* * *

## 模式 4：编排器-子代理

1.  编排器接收高级别目标，将其分解为子任务，分配给专门的子代理，并综合它们的输出。
2.  何时使用： 工作需要多个专家领域。需要安全专家、性能专家和覆盖率专家同时进行的代码库审计。

Claude 工作流形态

```markdown
[Orchestrator: decompose goal into subtasks]
 |
 [Security Agent] [Perf Agent] [Coverage Agent]
 | | |
 [Orchestrator: synthesize findings]
```

编排器的唯一工作是分解与合成。领域推理属于专家。

* * *

## 模式5：评估器-优化器

1.  生成器代理生成输出。评估器代理根据明确的标准对其进行评分。评分和反馈返回给生成器。循环直到输出通过或达到最大迭代次数。
2.  何时使用： 输出质量至关重要，且评估标准可被明确写入规则。安全发现不能是误报。迁移计划必须通过对抗性审查。测试用例必须覆盖指定的边缘情况。

Claude 工作流形态

```markdown
Phase 1: Generator agent produces initial output
Phase 2: Evaluator agent scores against criteria schema
  - Score >= threshold: forward to output
  - Score < threshold: feedback -> Phase 1 with iteration count + 1
Phase 3: Max iterations reached: flag for human review

Set a hard max iteration count (3-5). Without it, the loop can run indefinitely on ambiguous evaluation criteria.
```

## 模块8：从零开始的系统设计

在编写单个工作流提示之前设计多智能体系统的一个可重复流程。

* * *

## 步骤1：任务分解

用一句话写下顶层任务。然后列出完成该任务所需的每一个不同操作。针对每个操作，回答两个问题：

1.  这个操作是否依赖另一个操作的输出？(顺序依赖)
2.  这个操作可以与其他操作同时运行吗？（并行候选）

将顺序依赖的操作分组为阶段。在每个阶段内将并行候选分组为扇出。

输出: 一个带有明确依赖箭头的相图。

* * *

## 步骤 2：专科医生识别

对于你的阶段图中的每个操作，识别它需要的专家代理。定义：

- 代理人的角色 （一句话，无歧义）
- 代理的工具访问权限 （只读？写入哪些路径？哪些 shell 命令？）
- 代理的 输出合约 （精确的 JSON schema）
- 代理的 失败行为 (当它无法完成任务时的行为)

避免通用型代理。什么都做的“代码代理”是一个上下文臃肿的单一代理，而不是专家。

* * *

## 步骤 3：传播设计

决定：子层介导的还是直接的？对于大多数系统，答案是子层介导的，通过工作流的脚本变量（对于动态工作流）或共享文件系统（对于代理团队）。

绘制数据流：哪个代理写入什么数据，写入到哪个位置，何时写入。绘制读写图。如果任何代理从一个被其他多个代理写入的位置读取数据，那么就存在潜在的上下文污染向量。在该读取操作前添加一个验证步骤。

* * *

## 步骤 4 : 治理合同

在编写任何工作流提示之前，先编写 CLAUDE.md 代理规则。这迫使你将权限、错误处理和人工在环门控作为明确的决策，而非事后想法。模块 6 的成果物将作为你的模板。

## 步骤5：飞行前检查清单

在运行任何多智能体工作流之前，在真实代码仓库上：

- 在 git worktree 或特性分支中工作，而非主分支
- 每个代理的权限范围在任务提示中被明确界定
- 为每个写入共享存储的代理定义的输出契约
- 每个生成器代理在关键路径上均配备验证器/评估器代理
- 为所有不可逆操作定义的 HITL 门
- 所有评估器-优化器循环上设置的最大迭代次数
- 为每个代理定义的故障行为（明显失败，绝不静默替换）
- 运行前检查/usage 以了解 token 预算

## 模块 9：使用 Claude 的编排栈构建

* * *

## 实用架构：动态工作流 + 代理团队

对于大多数生产工程任务，该架构结合了两个 Claude 原语：

1.  外层: 动态工作流 Claude 编写编排脚本。该脚本处理分解、扇出、结果收集和阶段排序。中间状态存储在脚本变量中。该工作流可重新运行：将其另存为斜杠命令，整个编排流程就变成了一个团队命令。
2.  内层: 专家子代理 工作流中的每个阶段都会调度专业子代理。每个子代理都有一个限定范围的系统提示（通过工作流中的任务提供）、特定文件路径、已定义的输出模式以及失败策略。
3.  对于需要代理间通信的任务：代理团队 当专科医生需要直接互相发送消息（而不仅仅是向协调器汇报）时，请使用 Claude Code 的代理团队。每个团队成员都是一个拥有独立上下文的完整 Claude Code 会话。他们通过邮箱进行沟通。团队负责人进行协调，不进行微观管理。

* * *

Claude Code 的内置可观测性

\`/workflows\` 命令为你提供对每个正在运行的动态工作流的实时可观测性：

- 阶段级别的状态（运行中，已完成，已失败）
- 代理级下钻：任务提示，当前状态，目前输出
- 能够暂停、重新启动单个代理或停止整个工作流
- 在会话中从检查点恢复

对于坐席团队，每个团队成员会话均可独立检查。您可以直接与队友互动，无需经过负责人。

## 模块 10：扩展与成本控制

多智能体系统没有线性成本曲线。成本随智能体数量复合增长。

## Token 成本架构

多智能体系统中的 Token 使用来自三个来源：

1.  编排规划: 编写工作流脚本或分解任务会预先消耗令牌。这是按任务固定的，而非按代理固定。
2.  代理执行： 每个代理读取其任务，读取其输入文件，调用工具，并生成输出。成本随代理数量增加而增加。
3.  合成： 编排器读取所有代理输出并进行合成。成本随总输出量变化。

动态工作流通过将中间结果保存在脚本变量中而不是将它们全部传递到编排器的上下文中，从而降低了合成成本。

## 3-7代理规则

保持团队规模小。每个工作流阶段3-7名成员。除此之外，建立层级结构：每组设一名团队负责人，团队负责人向全局编排器汇报。扁平化架构中，若协调层有20名以上成员，会产生二次方的沟通成本和协调死锁风险。

## 模块 11 : 决策指南：何时构建多智能体

最昂贵的错误是为一项单个优秀智能体（或单个优秀功能）就能处理的任务构建多智能体系统。

## 构建多智能体时

- 该任务具有真正独立的并行路径（并且您可以列举它们）
- 该任务超出了单个代理的上下文窗口，无法无损总结
- 你需要对抗性验证（经得起反驳的发现比单次验证的发现更有价值）
- 该作业运行数小时到数天，且需要检查点恢复
- 该流程是可重复的（审计、迁移、测试生成），并且编排本身应是一个可复用的工件
- 不同阶段需要真正不同的专业专长或工具集

## 当保持单代理时

- 该任务是串行的，没有并行性
- 该工作在一个上下文窗口中适配得很舒适
- 协调开销将超过执行时间
- 您仍然在快速构建和修改系统（多智能体架构重构成本高昂）

## 最大的单一架构错误

将所有代理结果通过编排器的上下文回传。一旦你这样做，你就用额外的网络跳数重建了单代理上下文瓶颈。中间状态属于底层（脚本变量、文件系统、结构化文档），而不是在编排器的对话历史中。

> 编排器的上下文应该包含计划和最终合成。仅此而已。
