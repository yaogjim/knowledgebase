# 我们如何使 Ramp Sheets 自维护

我们构建了一个智能代理系统来维护

[Ramp Sheets](https://labs.ramp.com/sheets)。它持续监控生产环境，对警报进行分类处理并提出修复建议，无需人工干预——尽管没有工程师审核，代码不会被合并。该系统运行在一千个 AI 生成的监控器上，每 75 行代码对应一个监控器。

我们构建这个是因为：

- 代理运行成本低、无限耐心且易于并行化。这些特性使得在生产规模上进行全面监控成为可能。
- 团队都讨厌负责可观测性，我们自己也不例外。将这些繁琐的工作交给代理来处理，能让我们更快地交付。
- 强大的可观测性和质量保证意味着更少的缺陷、更少的停机时间，以及为 Ramp 客户带来更好的体验。

## 坡道检查

我们选择使用

[Ramp Inspect](https://builders.ramp.com/post/why-we-built-our-background-agent) 来构建我们的维护系统，我们内部的后台编码代理。每个 Inspect 会话启动一个完整的沙箱化开发环境，允许代理发起真实的 API 请求、运行测试，并针对实时代码端到端地复现错误。这种交互性至关重要，因为细微的故障模式很少能从静态代码审查中发现。

## 计划审计

我们第一次尝试自我维护采取了定期代理审查的形式。每天晚上，我们会自动启动一个代理，对 Ramp Sheets 进行质量检查，指示该代理执行：

- 核心功能的健全性测试
- 对最近合并的 PR 进行压力测试
- 探测现有功能中的潜在漏洞

这个设计效果很好，每天都能发现几个真实的生产环境漏洞。此外，我们将工作流程设计为一个行动机制：如果代理发现了真实问题，它会提交一个 PR 来解决根本原因。不止一次，工程师发布了一个带有他们未注意到的 bug 的功能；到第二天早上，代理已经发现了回归问题并推送了修复。

![Image](https://pbs.twimg.com/media/HEHXS8YboAAnN5Q?format=jpg&name=large)

我们的 QA 代理在 Sheets 的流式架构中发现了一个竞态条件，并实施了修复。

然而，夜间代理存在严重的局限性。由于没有特定任务，该代理在质量保证（QA）工作流程中总是沿着相同的路径推进，阅读相同的文件、调查相同的功能、执行相同的测试。虽然这种模式在发现高范围问题时被证明有效，但它无法捕捉到狭窄的、情境性的缺陷。

虽然 Ramp Sheets 在 Datadog 上进行了广泛的仪器化，我们缺乏针对性的 QA 代理难以从遥测数据中提取细微的洞察。当前的前沿模型能够胜任广泛的软件工程任务，但它们无法综合分析具有较大可观测性范围的大型代码库并确定需要关注的内容。生产规模的优先级排序需要一种超越当前任何模型的智能水平。

## 监控驱动的维护

在我们的下一次迭代中，我们使用 Datadog 监控器将代理定向到特定的生产问题。这些监控器会监控指标和日志模式，并在错误率激增、延迟回归或其他偏离预期行为时触发警报。该系统通过两个步骤工作：

- 当 PR 合并时，代理读取差异并生成监控器以对新代码进行插桩。
- 当监视器触发时，一个
 
 [Datadog webhook](https://docs.datadoghq.com/integrations/webhooks/) 启动一个带有告警上下文的新代理。该代理在其沙箱中复现问题，推送修复，并在 Slack 上通知我们。
 

![Image](https://pbs.twimg.com/media/HEHXGWpaIAA8ub-?format=jpg&name=large)

代理生成的监控器具体且复杂。该复合监控器整合来自 Ramp Sheets 后端和 SSE 队列的信号，当代理活动偏离广播事件吞吐量时发出警报。

这种模式使我们能够以显著的速度和粒度检测和响应事件。在系统上线的第一周内，该系统捕获了 40 个真实存在的漏洞，每个漏洞都在用户触发问题后的几分钟内被发现。有一次，一名用户上传了一份电子表格，其中包含一种独特类型的嵌入式图片，而我们现有的逻辑无法处理这种图片；由此产生的异常触发了一个监控机制，片刻之后，代理程序就已经向我们发出了警报，并附带了准备好的修复方案。另一个案例中，一名内部用户通过 Slack 联系我们，反馈了一个功能故障——但在他的消息到达之前，我们的系统已经标记出了这个确切的问题。

## 过滤噪声

这种方法的主要缺点是噪声问题。自动生成的监控规则阈值设置不当。常规用户操作触发了一连串告警，其中大部分是误报。此外，监控规则会针对同一问题重复触发，导致 Slack 被重复通知淹没。

为了过滤噪声，我们添加了一个分类筛选步骤。对于每一个警报，代理程序首先评估问题的范围：

- 如果这是一个实际问题，代理会推送修复并在 Slack 上发布。
- 如果是噪声，代理将调整或删除该监控器。

为了防范重复告警，我们在监控器本身存储状态。当代理推送修复时，它会将 PR 链接追加到监控器描述中。后续代理看到该链接后会停止操作。

![Image](https://pbs.twimg.com/media/HEHXl_KaIAAD_ut?format=png&name=large)

## 结果

几周内，我们将 Ramp Sheets 从 10 个手写监控工具扩展到了 1000 多个，每 75 行代码对应一个。我们的人工监控工具较为粗略：仅在前端崩溃或 API 调用超时的时候发出警报。而 AI 生成的监控工具则要细致得多，如同一张紧密的网覆盖在代码的确切结构上；每当该结构与预期不符时，我们都会收到通知。

![Image](https://pbs.twimg.com/media/HEHmumTWsAAr2uO?format=jpg&name=large)

## 我们学到的

检测一切，有选择地通知。 系统应该监控所有信号，但传递给人类的每个警报都应该有意义。团队会忽略干扰性强的监控器，也会忽略干扰性强的代理。

委托给代理。 让它确定问题范围、评估影响、进行修改并过滤干扰。它在这方面非常擅长，并且随着模型的改进会变得更好。

沙箱化的复现提升结果。 在我们的系统中，代理针对线上代码复现故障，仅在该复现测试通过后才推送修复。这种模式确保了问题是真实存在的，并且代理提出的修复方案在实际中有效。

模型选择很重要。 虽然 GPT-5 模型系列是非常细致的调试工具，但我们发现 Opus 4.6 是更准确的分类评估工具，并且在过滤干扰性警报方面表现尤其出色。

![Image](https://pbs.twimg.com/media/HEHaZfBXAAAAKkP?format=jpg&name=large)

紧密的可观测性孕育客户同理心。 当每次加载缓慢或输出不良触发通知时，团队能像用户一样感知产品。我们发现了那些仅凭自身判断绝不会优先处理的 bug。

保持你现有的技术栈。 自动生成的监控器功能强大但不透明，还不够可靠，无法成为你唯一的防御手段。当情况严重出错时，你仍然需要你自行编写并信任的检测工具。随着模型的改进，这种情况将会改变。
