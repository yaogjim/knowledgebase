# Agent Vault：开源凭证代理和代理保管库

一段时间以来，行业一直面临一个重大问题：我们如何在不允许代理读取任何密钥的情况下，为代理提供对服务的安全访问？

[Agent Vault](https://github.com/Infisical/agent-vault)，一个开源的 HTTP 凭证代理和密钥库。

在

[@infisical](https://x.com/@infisical), 我们每月处理数十亿个密钥，这些密钥将应用配置和密钥数据发送到需要它们的团队、CI/CD 流水线以及服务器/应用程序。我们见识过从基于身份的集中式密钥管理到自动化

[密钥轮换](https://infisical.com/docs/documentation/platform/secrets-mgmt/concepts/secrets-rotation)

和

[动态密钥](https://infisical.com/docs/integrations/dynamic-secrets)

方案，用于即时生成密钥。因此，当我们最初考虑代理如何与密钥交互时，我们认为传统的密钥管理技术就足够了。我们大错特错。

本文探讨了我们对该问题的思考方式，以及为何认为 Agent Vault 在 AI 时代恰好契合机密管理的形式。希望本文能引人入胜，并对其他可能需要为自己的代理设计机密管理解决方案的人有所帮助；您甚至可以考虑

[Agent Vault](https://github.com/Infisical/agent-vault) for a spin.

# 挑战

当今的计算范式并非为代理设计，而是为传统工作负载设计的。这里的问题在于，代理（无论是编码代理还是沙箱执行代理）的运作方式与我们以往所见的任何事物都存在根本差异；它们具有非确定性，且易于操纵，这打破了传统系统所依赖的许多假设。

比如，密钥管理领域过去十年的做法一直是直接从集中式密钥库向工作负载交付密钥；这对执行路径固定的程序效果良好，但当程序被诱导以其作者从未预料到的方式使用这些密钥时，这种做法就会失效。

考虑这种攻击向量：一个恶意行为者

[提示注入](https://en.wikipedia.org/wiki/Prompt_injection) 一个代理，指示它扫描并返回代理环境中可用的机密；代理服从并将机密暴露回调用者。无论是 RAG 管道中的被污染文档，还是工具调用引入的恶意网页（指示代理将机密转发到攻击者控制的端点），代理都有多种被提示注入的方式，使其成为一个极易受攻击的表面。不幸的是，即使有足够的

[安全护栏](https://render.com/articles/what-s-the-best-way-to-implement-guardrails-against-prompt-injection)

到位，也无法保证代理不会被操纵以泄露其机密。

这是凭证泄露的问题凭证泄露并且，如果发生这种情况，攻击者将拥有执行数据泄露数据泄露 ，这是一个相关问题，他们现在可以利用被泄露的凭证访问有价值的数据。正如你所料，成功操纵具备电子邮件功能的代理的攻击者，可以窃取代表用户读取和发送电子邮件所需的凭证——非常可怕。

# 早期解决方案

我们接触过的大多数团队都实施了基本的防护措施、安全控制以及更多传统的规避措施，以缓解凭证泄露风险。此类措施的一个例子是为代理提供尽可能短期的凭证，例如如果对于支持 OAuth2 的 API，使用访问/刷新令牌模式是可行的；这种短暂性也可以通过自动化

[密钥轮换](https://infisical.com/docs/documentation/platform/secret-rotation/overview)以及

[动态密钥](https://infisical.com/docs/documentation/platform/dynamic-secrets/overview)

方案。

在这种情况下，如果攻击者能够获取到暴露的凭证，那么他们只能在有限的时间段内使用它。然而，这是不理想的，因为这些措施并没有改变凭证仍然可能被外泄的事实。

最优秀的团队会开发自己的定制管道系统来防范凭证泄露。例如，Anthropic 的

[Managed Agents](https://www.anthropic.com/engineering/managed-agents) 架构博客描述了为代理构建一个专门的代理服务，该服务从保险库中获取凭证并将其附加到通过该代理的出站请求中；该博客提到，框架从未知晓这些凭证。

[sandboxed agent to control plane architecture](https://browser-use.com/posts/two-ways-to-sandbox-agents)

[credential brokering](https://vercel.com/changelog/safely-inject-credentials-in-http-headers-with-vercel-sandbox)

[outbound workers](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/outbound-workers/)

Browser Use 是一家为 AI 代理提供网页浏览器的基础设施公司，采用沙箱化代理到控制平面架构，该架构通过一个专用服务路由代理请求，该服务在代理层注入凭证。最近几天，我们还看到云服务提供商推出了各自特定于提供商的解决方案，例如 Vercel 的凭证代理或 Cloudflare 的出站 Worker，这些方案仅在其特定生态系统内运行。

这是一个强烈信号，表明向传统工作负载传递密钥的旧模式对代理不起作用。这也是一个强烈信号，表明这不是每个团队都应该独自解决的问题。

# 解决方案

当你考察最佳团队如何构建和使用安全代理时，你会注意到他们在代理和凭证之间划定了信任边界。毕竟，如果代理不能被信任安全处理凭证，那么最初为什么要给它任何凭证呢？或许更合理的做法是在代理和它试图访问的服务之间的代理层中代理凭证。这正成为我们整个行业目前正逐步走向的主要方法： 凭证代理 .

简而言之，代理不应被信任直接访问任何密钥。相反，应该由其他实体代表代理持有密钥，并在代理通过它发送请求时将其附加到边缘。edge

# 代理保管库

今天，我们宣布

[Agent Vault](https://github.com/Infisical/agent-vault)，一个处于研究预览阶段的开源项目，其核心理念很简单：agents 永远不应该首先看到底层的密钥。

借助 Agent Vault，我们正在重新思考代理应如何使用密钥，并以代理为优先，同时考虑到人类因素。我们认为密钥库和/或密钥存储将持续存在，但为适应代理操作人体工程学而交付密钥的方式将发生巨大变化。

代理（至少在当前状态下）不能被信任直接持有密钥，因此每个代理旁必须部署一个专用的正向 HTTP 代理，无论是通过专用服务、sidecar 还是出口层；以安全地代理凭证，使其能够访问外部世界。部署此代理后，你可以检查经过代理的请求，并且在未来，可以应用防火墙规则来限制通过代理的流量。

Agent Vault 项目是对一种趋势的早期洞察，我们认为包括 Anthropic、

[Brex](https://x.com/pedroh96/status/2046604993982009825) 以及一些开源项目也意识到的是，将代理与其凭证分离。

尽管我们预计 Agent Vault 的形态在未来一年会发生变化，并且还有大量工作要做，以便在代理环境中更易于设置，但我们认为这代表了在如何正确思考 AI 代理的密钥管理，以及具体地说如何为它们进行设计的人体工程学方面的根本性进步。

# 工作原理

Agent Vault 以可移植二进制文件形式提供，它同时作为服务器和命令行界面(CLI)客户端；它是一种专用服务，也可部署为 Docker 容器。你可以在本地与类似 Claude Code 的编码代理一起使用 Agent Vault，或部署到你的虚拟专用服务器(VPS)，与你自定义的代理基础设施一起运行。

如果您正在运行沙箱代理，我们建议您在靠近代理的位置部署一个 Agent Vault 实例，并为代理提供对特定保险库的访问权限（更多内容将在下文介绍）。

在 Agent Vault 中，我们介绍四个构建块：保险库、凭证、服务和代理。

- 保管库是一个用于存储凭证的安全逻辑容器，其提供的服务定义了代理如何通过它转发请求。
- 凭证是存储在保管库中的敏感值，Agent Vault 会将其附加到代理请求中。这可以是 API 密钥、数据库凭证、密码或任何其他敏感材料。
- 服务是一个主机，例如
 
 [api.stripe.com](//api.stripe.com) 代理可以通过代理库访问的主机。当向库中添加服务时，您需要指定该服务的主机名和认证方案（例如 Bearer、API Key 等）；您可以指定用于服务认证的库凭证，或者省略并将代理视为直通模式。当代理发出代理请求时，代理库会将目标主机与库中的服务进行匹配，附加配置的凭证，并转发请求。
 
- 代理表示像 Claude Code、OpenClaw、Hermes 这样的 AI 代理，或者一个拥有自己凭证的自定义代理；如果您打算通过用户颁发的服务令牌将保险库访问权限委派给代理系统，这种构建并不总是必需的。

为了使用 Agent Vault，您首先需要创建一个保管库，向其中添加凭证，并指定哪些服务可以通过该保管库访问以及对这些服务如何进行认证。从那里，您创建一个带有代理令牌的代理，配置沙箱代理的环境以信任 Agent Vault 的 CA 证书，并设置 HTTPS\_PROXY 环境变量以指向保管库；其格式为 HTTPS\_PROXY=<agent\_credential>:vault@agent-vault\_url.com。这样，它会指示大多数语言的 HTTP 客户端、CLI 和运行时将流量重定向到代理，并在 TLS 层配置信任，以便代理将保管库接受为有效的上游服务。最后，您在网络层切断所有出站流量的访问，以便只有 Agent Vault 实例可从沙箱或容器化环境访问。

最终结果是这样的流程：

1.  代理调用 CLI 命令、SDK 方法、MCP 工具，或向 LLM 或 API 服务发起 API 调用，例如
 
 [api.anthropic.com](//api.anthropic.com)。
 
2.  该请求通过 Agent Vault 被自动路由，而代理对此一无所知。
3.  Agent Vault 拦截请求，附加凭证，应用任何预定义规则，并将请求转发到目标。
4.  好了。请求回到代理，代理完成其工作。它从未看到底层的秘密，并且/或者必须修改其工作流程。

虽然 Agent Vault 的初步设计使用起来有些笨拙，我们本希望有更多时间来优化开发者体验，特别是在代理开始通过它转发请求的配置设置方面；但 AI 领域的发展速度极快，我们认为最好开源这项技术，并与社区合作逐步改进，使其在所有代理用例中都能无缝工作，因为每个用例都有其独特之处。

# 设计架构

在设计 Agent Vault 时，我们首先考虑的是代理通常如何在沙箱环境内外与外部服务交互；实际情况是，可用的选项太多了：API、CLI、SDK、MCP。在构建代理 vault 时，我们本可以设计另一个“MCP 网关”（剧透：我们确实用

[Agent Sentinel](https://infisical.com/docs/documentation/platform/agent-sentinel/overview)）但这只会适用于使用 MCP 的代理，而代理可能使用其他三种方法中的任何一种来调用外部服务。必须找到另一种方法，一种与接口无关的解决方案，来代理出站流量的凭证。

人们意识到，无论代理是调用 API、通过 CLI 执行命令、使用 SDK 还是调用 MCP 工具，每个请求最终都会变成一个出站 HTTPS 连接。接口在栈的上层分化，在底层汇聚。管理凭证最理想的位置是在接口之下，即在所有代理流量实际共享的那一层——HTTPS 本身。

## 界面下方操作

因此，与引入另一个类似 SDK 的特定于接口的抽象不同，Agent Vault 在更低的一层运作，作为一个本地正向代理，代理所指向的 HTTPS\_PROXY。这只是一个你设置的环境变量，大多数运行时和工具已经能够识别它。事实上，这与 curl、Python、Node、Go 以及大多数 HTTP 客户端多年来支持的机制是相同的。

配置完成后，代理发出的每个出站请求都将经过保管库，无论其发起方式如何。需要注意的是，仅设置此环境变量并不能保证流量会通过代理，因为代理可能会取消设置该变量，这仅仅是一种用于引导合规客户端的措施；在完整部署中，必须对网络进行锁定，以确保所有出站流量都被强制通过 Agent Vault。

## 请求实际如何流转

当代理尝试访问类似

[api.stripe.com](//api.stripe.com)，其 HTTP 客户端使用 HTTP CONNECT 建立到 Agent Vault 的隧道。在传统代理中，该隧道保持不透明，仅转发加密流量。对于凭证代理而言，该模型失效，因为在不查看请求的情况下无法注入头信息。

为解决此问题，Agent Vault 终止 TLS。它使用本地可信证书颁发机构，将自身标识为上游服务，允许代理与它建立安全连接，并通过隧道以明文形式发送请求。

在那时，Agent Vault 可以匹配请求，剥离代理附加的任何凭证，从其加密存储中注入正确的凭证，并通过适当的验证建立到真实上游的新 TLS 连接。MITM 架构意味着，未来 Agent Vault 可以扩展类似防火墙的功能，以在参数级别分析请求并对请求采取行动。

响应沿相同路径返回，从代理的角度来看，一切都没有变化；它发出了一个正常的 HTTPS 请求并收到了一个正常的响应。区别在于它最初从未处理过凭证。

## 为什么这有效

因为这发生在应用层之下，集成面缩减至几乎为零，而策略在任何地方都变得一致。白名单、速率限制、审计日志和每个代理凭证范围界定可以在 API、CLI、SDK 以及代理使用的任何其他接口上统一实施，无需要求这些层中的每一层都理解密钥。

有几个细节使其实用。代理在 CONNECT 握手期间通过会话令牌验证请求，确保每个请求都限定于特定的代理上下文。上游目标在连接时固定，防止请求中途重定向，并且代理的所有出站连接都通过标准 TLS 验证重新建立。用于拦截的证书颁发机构被视为敏感材料，并受到与凭证本身相同的模型保护。

所有这一切归根结底是一个简单的理念：如果一个代理无法被信任持有凭证，就不应该拥有这些凭证。
