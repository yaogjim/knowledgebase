### **一、 上下文工程的兴起与核心挑战**

**主题**：该段落首先介绍了“上下文工程” (Context Engineering) 这一概念的由来，将其与早期流行的“提示工程” (Prompt Engineering) 进行对比，并阐明了其在 AI 代理 (AI Agents) 时代的重要性。接着，深入剖析了 AI 代理在执行任务时面临的核心挑战——上下文窗口的无限制增长及其导致的性能衰退问题。

**要点**：
*   **概念演变**：从“提示工程”到“上下文工程”的转变，反映了 AI 应用从简单的聊天交互向复杂的、自主的代理系统的演进。
*   **代理的工作机制**：AI 代理通过循环调用工具来完成任务，每次调用都会产生观测结果并追加到对话历史中，导致上下文信息急剧膨胀。
*   **上下文爆炸**：典型的代理任务可能需要约 50 次工具调用，而生产环境中的对话可持续数百轮，这使得上下文窗口面临“无界爆炸”的风险。
*   **性能悖论**：代理的有效运作依赖于大量的上下文信息，但研究和实践均表明，随着上下文长度的增加，模型的性能（如推理质量和速度）会显著下降，这种现象被称为“上下文衰退” (context rot)。
*   **上下文工程的定义**：引用 Andrej Karpathy 的观点，上下文工程被定义为“在每一步中，用恰到好处的信息填充上下文窗口的精巧艺术与科学”，旨在解决上述的性能悖论。

### **二、 上下文工程的五大核心策略**

**主题**：该段落系统性地介绍了当前业界应对上下文挑战的五种主流技术策略，分别由 LangChain 的创始工程师 Lance Martin 进行阐述。每种策略都通过引用具体的项目和实践案例（如 Manus、Claude、Deep Agents 等）来具体说明其应用方式和效果。

**要点**：
*   **上下文卸载 (Context Offloading)**：核心思想是将非必要或冗长的信息（如工具调用的完整输出）移出上下文窗口，存储在外部系统（如文件系统）中，仅在上下文中保留一个轻量级的引用（如文件路径），从而减轻上下文压力。
*   **上下文缩减 (Context Reduction)**：通过总结或压缩来减少上下文中的信息量。具体方法包括总结工具调用的输出、修剪（pruning）旧的工具调用记录，或是在代理交接时对整个消息历史进行压缩。
*   **上下文检索 (Context Retrieval)**：当信息被卸载后，代理需要一种机制在需要时将其重新调入。常见的检索方法包括基于文件系统的简单搜索工具（如 glob 和 grep）以及更复杂的索引和语义搜索（如向量存储）。
*   **上下文隔离 (Context Isolation)**：通过将复杂任务分解给多个子代理（sub-agents）来管理上下文。每个子代理拥有独立的上下文窗口，专注于特定子任务，从而避免单个上下文窗口的过度膨胀，并实现“关注点分离”。
*   **上下文缓存 (Context Caching)**：一种高效利用计算资源的技巧，通过缓存重复或相似的上下文信息来加速处理。

### **三、 Manus 对上下文工程的深入实践与哲学**

**主题**：由 Manus 的联合创始人兼首席科学家 Peak 接续演讲，分享了他们在构建 Manus 过程中对上下文工程更深层次的思考和独特的实践经验。他不仅阐述了“为什么”需要上下文工程，还深入探讨了他们在上下文缩减、隔离和卸载方面的创新方法。

**要点**：
*   **战略定位**：Peak 强调，在应用和模型之间，上下文工程是当前最清晰和最实用的边界。初创公司应尽可能久地依赖通用模型和上下文工程，而不是过早投入资源进行模型的微调或专门化训练，以保持产品的迭代速度和灵活性。
*   **对上下文缩减的精细化区分**：
    *   **压缩 (Compaction)**：一种“可逆”的缩减方法。将工具调用的结果写入文件系统后，仅在上下文中保留文件路径等关键引用，而删除冗长的内容。这种方法保证了信息不会真正丢失，可以在需要时被完全恢复。
    *   **摘要 (Summarization)**：一种“不可逆”的缩减方法。它会永久性地丢失部分信息。Manus 非常谨慎地使用摘要，通常在多轮“压缩”后效果不佳时才启用，并且在摘要前会先卸载关键信息，同时保留最近几次的完整交互记录以维持连贯性。
*   **对上下文隔离的模式划分**：
    *   **通过通信共享 (By Communicating)**：经典的子代理模式。主代理向子代理发送一个清晰、简短的指令，子代理在自己的独立上下文中完成任务并只返回最终结果。适用于任务目标明确、过程不重要的场景。
    *   **通过共享内存/上下文 (By Sharing Memory/Context)**：子代理可以访问主代理的全部历史上下文。适用于最终报告依赖大量中间过程和笔记的复杂场景（如深度研究），这样可以避免子代理重复读取文件，节省延迟和 token 消耗。
*   **避免过度工程的哲学**：Peak 总结道，Manus 取得的最大性能飞跃并非来自增加复杂的管理层或技巧，而是来自“简化”和“移除”不必要的环节，并更多地信任模型本身。核心理念是“构建得更少，理解得更多” (Build less, and understand more)，确保上下文工程的目的是让模型的工作更简单，而非更复杂。

### **四、 Manus 的创新：分层式行动空间**

**主题**：该段落详细介绍了 Manus 为解决“工具过多导致上下文混淆”问题而设计的创新架构——一个三层式的行动空间。这种设计巧妙地将大量工具能力卸载到模型的核心上下文之外，同时保持了接口的简洁和高效。

**要点**：
*   **问题的提出**：当一个代理拥有过多工具时，不仅会占用宝贵的上下文空间，还会导致模型在选择工具时产生混淆，调用错误或不存在的工具。
*   **第一层：函数调用 (Function Calling)**：这是最核心、最直接的一层。Manus 在此层面只保留了少数（约 10-20 个）核心的“原子”功能，如读写文件、执行 Shell 命令、文件搜索和浏览器操作。这些功能边界清晰，可以组合完成复杂工作流，并且因为数量固定，易于模型掌握且对 KV 缓存友好。
*   **第二层：沙箱工具 (Sandbox Utilities)**：将大量其他功能作为预装在虚拟机沙箱中的命令行工具。模型通过调用第一层的“执行 Shell 命令”功能来使用这些工具。例如，格式转换器、语音识别工具，甚至与模型市场 (MCP) 交互的命令行接口 (CLI) 都属于这一层。这种方式极大地扩展了代理的能力，而无需改变模型的函数调用空间。
*   **第三层：软件包与 API (Packages and APIs)**：允许代理编写并执行 Python 脚本来调用预授权的第三方 API 或自定义软件包。这非常适合需要大量计算或处理内存中数据的任务（如分析全年股票数据），脚本可以在外部完成计算，只将最终的摘要结果返回到上下文中。
*   **统一的接口**：从模型的角度来看，无论是调用第二层还是第三层的工具，最终都通过第一层的标准函数（如 `execute_shell` 或 `write_file`）来完成。这保持了接口的简洁性、正交性和对 KV 缓存的友好性。

### **五、 问答环节的深度探讨**

**主题**：此部分记录了演讲后的问答环节，涵盖了关于 AI 代理开发的多个具体技术和策略问题。讨论内容进一步揭示了 Manus 在架构设计、模型选择、多代理协作、安全性和评估方面的实践细节和思考。

**要点**：
*   **关于索引与文件系统**：Manus 目前更依赖类似 Claude Code 的方式，使用 `grep` 和 `glob` 等文件搜索工具，而非即时构建向量索引，主要是因为每个会话都在一个新的沙箱中，追求快速交互，没有时间进行索引。但对于需要长期记忆或集成企业知识库的场景，向量索引仍然是必要的。
*   **关于长期记忆**：Manus 采用一种“显式记忆”机制，称为“知识” (Knowledge)。当代理从交互中学到新东西时，会弹窗请求用户确认是否保存。同时，他们也在探索利用“集体反馈” (collective feedback) 来实现一种无参数的在线学习，让代理从多个用户的相同修正中自我改进。
*   **关于模型迭代与架构演进**：面对模型能力的快速提升，Manus 采取了持续重构的策略（上线后已重构五次）。他们评估架构是否“面向未来” (future-proof) 的一个独特方法是：固定架构，然后在强弱不同的模型间切换。如果架构能从更强的模型中获得显著性能提升，则说明该架构是健康的。
*   **关于摘要与通信的结构化**：为了生成高质量的摘要并确保代理间有效通信，Manus 广泛使用“模式” (schema) 和结构化输出，而不是自由形式的文本。例如，摘要是通过让模型填写一个包含多个字段的表单来完成的；主代理会为子代理定义一个输出模式，子代理必须通过一个 `submit_result` 工具并遵循该模式来返回结果。
*   **关于多代理系统的设计哲学**：Manus 避免创建拟人化的、按角色划分的代理（如设计师代理、程序员代理），认为这是对人类组织局限性的不必要模仿。相反，他们的多代理系统按功能划分，只有少数几个核心代理，如通用执行器、规划器和知识管理器，并通过“工具即代理” (agent as tool) 的模式实现更多功能，保持系统简洁。
*   **关于安全与防护**：由于代理运行在联网的沙箱中，安全是重中之重。Manus 采取了多层防护措施，包括严格的出站流量检查（防止 token 等敏感信息泄露）、对敏感操作（如浏览器登录、沙箱内执行）要求用户手动确认，并与模型提供商紧密合作，利用其内置的安全护栏。
*   **关于评估 (Evals)**：Manus 采用三管齐下的评估体系：最重要的是用户的星级评分（1-5 星），这是黄金标准；其次是内部自动化的、具有可验证结果的测试集（特别是针对“执行”类任务）；最后，对于数据可视化、网站生成等主观性强的任务，他们雇佣了大量实习生进行人工评估。

### **用上下文工程构建 AI 代理：LangChain 与 Manus 的前沿实践**

在人工智能迅速发展的浪潮中，继“提示工程”之后，“上下文工程” (Context Engineering) 已成为构建高效、可靠 AI 代理 (AI Agents) 的核心学科。LangChain 的创始工程师 Lance Martin 与 Manus 的联合创始人兼首席科学家 Peak 共同深入探讨了这一关键领域，分享了他们在生产环境中管理上下文窗口、优化模型性能并构建可扩展代理系统的宝贵经验与深刻见解。

#### **上下文工程的兴起：源于 AI 代理的核心挑战**

Lance Martin 首先为“上下文工程”的出现设定了背景。与主要处理单轮或短对话的聊天模型不同，AI 代理被设计为能够自主地、循环地调用多种工具来完成复杂且长期的任务。这一特性带来了前所未有的挑战：上下文的无限制爆炸。

代理的每一次工具调用，无论是进行网络搜索、读取文件还是执行代码，都会生成一个“观测结果”，该结果会作为一个新的消息被追加到其工作记忆（即上下文窗口）中。Manus 的实践数据显示，一个典型任务平均需要约 50 次工具调用。而 Anthropic 的研究也指出，生产环境中的代理对话可持续长达数百轮。这种机制导致上下文信息像滚雪球一样迅速累积。

然而，一个严峻的现实是，几乎所有的大语言模型都存在“上下文衰退” (context rot) 现象。当上下文窗口被填满大量信息时，模型的性能，包括推理质量、指令遵循能力乃至响应速度，都会显著下降。这就形成了一个棘手的悖论：代理的强大功能依赖于丰富的上下文信息，但过长的上下文却会扼杀其性能。

正是在这一背景下，“上下文工程”应运而生。它被精辟地定义为“**在代理执行的每一步中，用恰到好处的信息填充上下文窗口的精巧艺术与科学**”。其根本目标，就是在保证代理获取完成下一步所需全部信息的同时，最大限度地减少上下文的“认知负荷”，以维持模型的最佳性能状态。

#### **管理上下文的五大核心策略**

为了应对上下文爆炸的挑战，业界已经发展出一套行之有效的策略组合。Lance Martin 将其归纳为五个核心方向：

1.  **上下文卸载 (Context Offloading)**：这是最基础也是最关键的一步。其核心思想是将冗长、非核心的信息从上下文窗口中“卸载”出去，存放在外部系统中。最常见的做法是利用文件系统。例如，当代理执行一次网络搜索后，可以将数千字的搜索结果保存到一个文本文件中，然后在上下文中只保留一个简短的引用，如“搜索结果已保存至 `search_results_1.txt`”。这样做极大地压缩了上下文长度，同时保留了对完整信息的访问能力。包括 Manus、Claude Code 以及 LangChain 的 Deep Agents 项目在内的众多生产级代理都广泛采用了这一策略。

2.  **上下文缩减 (Context Reduction)**：此策略旨在直接减少上下文中的信息量。主要有两种方式：
    *   **总结 (Summarization)**：对信息进行概括，例如，将冗长的工具输出总结为几句关键要点。
    *   **修剪 (Pruning)**：移除旧的、可能不再相关的信息。一个有趣的例子是，新版本的 Claude API 已经内置了自动修剪旧工具调用的功能。Cognition 公司也提到，在代理与代理的任务交接点进行信息总结或修剪，是保持系统高效的有效手段。

3.  **上下文检索 (Context Retrieval)**：信息被卸载后，代理必须有能力在需要时将其“检索”回上下文中。关于如何实现高效检索，业界存在不同的技术路线。像 Claude Code 这样的系统，倾向于依赖强大的基础模型能力，使用如 `glob` (文件模式匹配) 和 `grep` (文本搜索) 等简单而直接的文件系统工具进行检索。而另一些系统，如 Cursor，则采用了更为复杂的方法，结合了传统的代码搜索工具和现代的索引及语义搜索技术（如向量数据库），以实现更精准的检索。

4.  **上下文隔离 (Context Isolation)**：当面对极其复杂的任务时，与其让一个代理背负无限膨胀的上下文，不如将任务分解，采用多代理（或子代理）架构。每个子代理拥有自己独立的、更小、更专注的上下文窗口，负责处理整体任务的一个环节。这种“分而治之”的方法，不仅有效地隔离了上下文，防止了信息过载，还实现了模块化的“关注点分离”，使得整个系统更加健壮和易于管理。

5.  **上下文缓存 (Context Caching)**：这是一个旨在提升效率和降低成本的技术。通过缓存已经处理过的上下文或计算结果（如 KV cache），可以显著加快后续相似任务的处理速度。Peak 在后续的分享中特别强调了 KV 缓存命中率对于生产级代理系统的重要性。

#### **Manus 的实践哲学：在精细化与简约化之间寻求平衡**

Peak 的分享从一个更具战略性的视角展开。他明确指出，**上下文工程是当前应用层与模型层之间最清晰、最实用的边界**。对于初创公司而言，与其过早地投入资源进行模型的微调或专门化训练——这会极大地拖慢产品迭代速度，不如将精力集中在上下文工程上，充分利用通用模型的强大能力，保持产品的灵活性和快速发展。

基于这一理念，Manus 对上述策略进行了更深入的探索和精细化实践：

*   **对“缩减”的精细化区分：压缩 (Compaction) vs. 摘要 (Summarization)**
    Manus 严格区分了两种上下文缩减的方法。**压缩**被定义为一种**可逆**的操作。例如，当一个工具调用将内容写入文件后，其在上下文中的表示可以从包含完整内容的“完整格式”被压缩为仅包含文件路径的“紧凑格式”。由于文件内容依然存在于外部环境中，这个过程是完全可逆的，没有信息丢失。代理在需要时，可以通过读取文件路径来恢复全部信息。

    而**摘要**则是一种**不可逆**的操作，会永久性地丢失信息。因此，Manus 对其使用极为谨慎。只有在多轮“压缩”后，上下文缩-减的收益变得微乎其微，且窗口仍然接近性能衰退的阈值时，才会启动摘要流程。在执行摘要前，Manus 甚至会采取更保险的措施：将摘要前的完整上下文转储为一个日志文件，以便在极端情况下进行追溯。此外，为了保证连贯性，摘要操作会保留最近几次的完整工具调用记录，确保模型清楚地知道任务“进行到了哪里”。

*   **对“隔离”的模式划分：通信模式 (By Communicating) vs. 共享内存模式 (By Sharing Memory)**
    在多代理协作中，如何传递上下文至关重要。Manus 借鉴了计算机编程中的经典思想，定义了两种协作模式：
    *   **通信模式**：这是经典的子代理设置。主代理向子代理发送一个简短、明确的指令，子代理在一个几乎空白的上下文中完成任务，并仅返回最终结果。主代理不关心子代理的实现过程。这种模式适用于目标清晰、过程不重要的任务，例如在代码库中搜索特定的代码片段。
    *   **共享内存模式**：在这种模式下，子代理被授予访问主代理完整历史上下文的权限。它可以看到所有的工具使用历史和中间笔记。这种模式适用于最终产出严重依赖于过程细节的复杂任务，比如撰写一份深度研究报告。虽然这种方式会增加子代理的初始 token 消耗，但它避免了子代理需要从头开始重复读取和理解所有背景文件，从而节省了总体延迟和 token 使用。

#### **架构创新：解决工具过载的分层式行动空间**

Peak 坦言，随着代理能力的增强，一个常见的问题是工具数量的爆炸式增长，这会导致模型在选择工具时产生“上下文混淆”。为了解决这个问题，Manus 设计了一种创新的**三层式行动空间 (Layered Action Space)**，巧妙地将绝大多数工具能力“卸载”到了核心上下文之外：

*   **第一层：函数调用 (Function Calling)**：这是模型直接与之交互的接口层。Manus 刻意将这一层的工具数量保持在极低的水平（大约 10-20 个），只包含那些最核心、最基础的“原子”功能，如读写文件 (`read/write_file`)、执行 Shell 命令 (`execute_shell`)、互联网搜索 (`search_internet`) 等。这些工具边界清晰、功能正交，且高度可组合。

*   **第二层：沙箱工具 (Sandbox Utilities)**：大量的功能被实现为预装在 Manus 虚拟机沙箱中的命令行工具。这些工具可以是格式转换器、数据处理器，甚至是与模型市场 (MCP) 交互的客户端。模型并不直接“看到”这些工具的定义，而是通过调用第一层的 `execute_shell` 功能来使用它们。模型可以通过执行 `command --help` 来动态地学习如何使用一个新工具。

*   **第三层：软件包与 API (Packages and APIs)**：这一层赋予了代理编写并执行 Python 脚本的能力，从而可以调用任意预授权的第三方 API 或本地软件包。这对于需要大量内存计算或复杂数据处理的任务至关重要。例如，在分析一支股票全年的价格数据时，代理可以编写一个脚本来完成所有的计算，然后只将最终的分析摘要（如平均值、波动率）返回到上下文中，而不是将成千上万个数据点全部塞入。

这种分层架构的精妙之处在于，从模型的视角看，无论它想使用哪一层的功能，最终都收敛到调用第一层的少数几个核心函数。这不仅保持了上下文的简洁，极大地降低了模型的选择困惑，还有效地保护了 KV 缓存，从而在扩展代理能力的同时，保证了系统的低延迟和低成本。

#### **最终的启示：少即是多，理解胜于构建**

在演讲的最后，Peak 分享了一条发人深省的核心哲学：**避免上下文的过度工程化**。他回顾说，Manus 在发展过程中取得的最大性能飞跃，往往不是来自于增加了更复杂的管理技巧或新潮的检索算法，而是来自于**简化架构、移除不必要的环节，并给予模型更多的信任**。

“上下文工程的目标，是让模型的工作变得更简单，而不是更复杂”，Peak 总结道，“**构建得更少，理解得更多 (Build less, understand more)**”。这提醒所有 AI 代理的开发者，真正的突破来自于对模型能力的深刻理解和对信息流的精妙驾驭，而非盲目地堆砌复杂的工程技巧。

在与会者的热烈讨论中，这场关于上下文工程的对话，为如何构建下一代真正强大、通用且可靠的 AI 代理系统，提供了清晰的路线图和宝贵的实践指南。
