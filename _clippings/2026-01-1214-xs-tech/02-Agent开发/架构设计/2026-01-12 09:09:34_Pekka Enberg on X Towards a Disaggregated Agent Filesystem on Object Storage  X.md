文件系统抽象是 AI 代理的有效接口，并且 AgentFS 正好在 SQLite 数据库文件之上提供了这一点。但随着代理工作负载随着更多代理、更长运行时间的任务以及多代理协作而扩展，我们需要超越本地磁盘上的单文件模型。状态需要在临时计算环境中持久化，在机器间迁移，并且无需配置持久卷即可扩展。本文探讨了 SQLite 的基于 WAL 的架构与 Turso 的基于 S3 的无盘架构如何为对象存储上的非集中式代理文件系统提供一条路径。

代理需要一个文件系统。文件系统抽象是 AI 代理的有效接口。基础模型在训练过程中吸收了大量的 Shell 脚本、Unix 文档和基于文件的工作流。给代理提供 grep、sed、awk、cat 和 git 的访问权限，它就会变得异常强大和有效，无需定制工具。Unix 在 50 多年前建立的“万物皆文件”理念创造了一个由数千个专门命令行工具组成的生态系统，这些工具都围绕着一个共同的抽象构建。对于代理而言，这代表了其训练数据的很大一部分，也是与世界交互的自然方式。

问题在于，真实的文件系统需要真实的基础设施。运行具有文件系统访问权限的代理意味着要么启动容器、管理虚拟机，要么接受代理直接在你的机器上运行命令的安全风险。此外，在无服务器或基于浏览器的代理等轻量级环境中，从一开始就没有可访问的文件系统。即使你确实有文件系统，大规模操作持久卷来承载它们也只是很困难。

代理需要被快照并恢复。 自主系统本质上不可预测。它们的推理链可能导致不可预见的结果，当出现问题时，你需要对每一个决策、每一个创建的文件、每一个状态变化都有可见性。你需要能够在任何时候捕获代理的整个运行时，以用于调试、可重现性、合规性以及回滚错误。

传统方法之所以不足，是因为它们需要拼凑多种工具：用于状态存储的数据库、用于审计跟踪的日志系统、用于存储工件的本地文件系统，以及用于历史记录的版本控制。固有的碎片化造成了复杂性，并且在可观测性方面留下了空白。你真正想要的是能够通过复制一个文件来对代理的完整状态进行快照，然后在之后恢复它，以重现确切的执行条件或测试假设性场景。

代理状态需要可移植。 将代理计算保持在特定机器上既麻烦又昂贵。代理可能会因超时、扩缩容决策或故障而被中断。此外，无服务器平台在设计上是短暂的：你的代码启动、运行后就消失了。如果代理状态存储在本地文件系统或内存中，它也会消失。

当你需要创建快照和恢复时，状态可移植性尤为重要。一个处理长任务的代理可能会检查其进度，然后被驱逐，几小时后需要在一台完全不同的机器上恢复。或者你可以暂停一个代理，检查其状态，然后从上次停止的地方继续。如果状态绑定到特定实例或卷，这些都无法实现。

调试和协作也需要可移植性。当出问题时，你得拿到代理的完整状态文件、上下文、工具调用历史——并在本地复现问题。你可能想和同事共享这个状态，或者把它附到 bug 报告里。你或许还想对比两次运行，或者用 SQL 精确查询发生了什么。关键是要有一个能作为单个可移植单元移动的状态，而不是分散在文件系统、环境变量和临时容器里的碎片。

 AgentFS 是一个为代理设计的文件系统抽象。它不依赖于宿主操作系统的文件系统，而是将所有内容存储在 SQLite 数据库中：文件、目录、元数据、键值状态以及工具调用的审计日志。这种方法为你提供了代理所期望的熟悉的文件系统语义，同时使整个代理运行时可移植、可查询且可作为单个文件进行快照。

设计提供了三个核心接口。文件系统接口提供了对文件和目录的类 POSIX 操作——读取、写入、创建、重命名和删除。代理与它交互的方式和与普通文件系统交互的方式相同。键值接口将会话状态和上下文存储为 JSON 序列化的值，用于会话数据、配置或中间计算结果。工具调用接口记录每次工具调用的仅追加审计日志，捕获输入、输出和时间信息以用于调试和合规。

从本质上讲，文件系统存储采用了经典的 inode/目录项（dentry）设计。目录项（dentry）表将名称映射到目录层次结构中的位置，充当查找缓存。inode 表存储实际文件内容和元数据（大小、权限和时间戳）。这种分离反映了操作系统内核组织文件系统数据的方式，但完全通过 SQLite 表实现。叠加场景中的删除操作采用白 out 机制：覆盖层不会修改基础层，而是在白 out 表中记录被删除的路径，并在读取时过滤掉这些路径。

关键洞察是 SQLite 恰好提供了代理所需的特性。一个文件就包含了完整的代理运行时，你可以将其复制到另一台机器、纳入版本控制，或者附加到错误报告中。你可以通过复制数据库文件在任何时候快照状态，之后再恢复它以重现精确的执行条件。而且由于所有内容都是结构化数据，你可以用 SQL 查询代理行为——找出过去一小时内修改的所有文件、追踪导致错误的工具调用序列，或者提取指标进行分析。

对于需要原生工具兼容性的代理，AgentFS 在 Linux 上提供 FUSE 支持（macOS 上提供 NFS 支持），可将 SQLite 支持的文件系统挂载为真实的 POSIX 文件系统，让你无需集成代码即可直接运行 git、grep、ffmpeg 或任何 Unix 工具。如图 1 所示，代理调用 bash 执行命令。这些命令通过系统调用与操作系统内核交互。打开和关闭等文件系统操作被委托给 AgentFS 提供的用户空间守护进程，以访问存储在 SQLite 数据库文件中的文件系统元数据。从文件读取非常高效，因为内核页缓存分摊了从 FUSE 用户空间守护进程读取的成本。写入文件时也会先写入内核页缓存，然后异步写回 FUSE 模块。

Figure 1: AgentFS 和 FUSE 架构。代理生成一个执行命令的 bash 进程。像 open 和 close 这样的系统调用会经过内核的 VFS 层到达 FUSE 模块，该模块将任务委托给 AgentFS 用户空间守护进程。守护进程将文件系统元数据存储在 Turso/SQLite 中。读取操作受益于内核页缓存，避免了重复的 FUSE 调用。写入操作在页缓存中进行缓冲，并异步写回。

AgentFS 还支持其他集成模式，具体取决于环境。支持 TypeScript、Python 和 Rust 的 SDK 为使用 AI SDK、Mastra 等框架构建的代理提供编程访问。对于无法挂载文件系统的轻量级环境（如无服务器或浏览器环境），bash-tool 集成提供了对可直接在 AgentFS 上运行的常用 shell 命令的 TypeScript 重新实现。

AgentFS 的设计将所有内容存储在本地磁盘的单个 SQLite 数据库文件中。这种方法在单机场景下效果良好：它提供原子性、持久性、可查询性和可移植性。然而，随着代理工作负载的扩展（更多代理、更长时间运行的任务或多代理工作负载），我们需要一种分离模型，其中代理文件系统位于对象存储中。

一种解耦元数据、由对象支持的分布式文件系统（例如 JuiceFS 或 HopsFS），通过分离文件系统的元数据和数据，并分别将它们存储在键值或关系型数据库以及对象存储中，解决了这一问题。然而，在 SQLite 之上构建 AgentFS 实现了在不同层面（即数据库本身）的解耦。SQLite 使用预写日志（WAL），该日志会在所有变更被检查点写入主数据库文件之前，将所有变更捕获为一系列修改。数据库文件表示已提交的状态；WAL 表示正在进行中的变更。

借助 Turso 的同步协议，本地变更以逻辑变更的形式推送到远程，而远程变更则以物理页面的形式被拉取。对象存储充当事实源。这意味着你可以对数据库文件进行检查点操作并存储到对象存储中，通过协调层流式传输预写日志（WAL）条目，并在任何机器上重建代理状态。如图 2 所示，代理可以在本地工作，并通过协调器增量同步到 S3。当需要时（例如，迁移计算资源），我们可以将所有变更同步到云端，在另一台机器上启动代理，并无缝拉取变更以继续工作。

图 2：通过增量同步实现代理状态可移植性。工作期间，WAL 帧被批处理并推送到协调器，协调器会立即将其持久化到 S3 以确保持久性。当计算迁移到新实例时，它会从协调器的缓存中拉取页面和 WAL 以实现快速恢复。计算是临时的，状态持久化。

这种混合方法能让你兼顾两者的优势。读写操作以本地磁盘速度进行，针对的是内存中或本地缓存的数据库。WAL 以最小的开销捕获变更。后台同步处理持久性和到对象存储的复制，且不会阻塞代理。而且由于远程状态是事实来源，当多个代理修改同一个文件系统时，你会获得自动冲突解决，就像使用 之类的工具时一样，例如。

这种方法还解锁了代理所需的一些额外能力。临时计算，持久化状态让无服务器平台上的代理能够启动，从 S3 拉取文件系统状态，执行任务，推送更改，然后消失。无需配置持久卷，无需管理 EBS 快照，代理休眠时也没有存储成本。时间回溯和分支很容易实现，因为 WAL 记录了每一次变更；你可以回滚到任何之前的状态，或者分叉代理的文件系统以探索其他路径。想看看代理如何处理不同的方法吗？从检查点分叉，让它运行，然后比较结果。传统分布式文件系统仅存储当前状态，而这种方法免费提供历史记录。

此外，多智能体协作指多个智能体可以在同一个文件系统上工作。协调层处理冲突——默认采用最后推送优先，必要时可通过转换钩子实现自定义合并逻辑。离线执行指智能体无需持续连接对象存储。拉取检查点，在本地工作，完成后推送变更。同步协议处理合并。这对于间歇性连接或在承诺使用云资源之前希望在本地运行实验的情况很重要。

此处描述的解耦架构是一个方向，而非一个完成的系统。还有几个未解决的问题。

写入并发。 SQLite 采用单写入器模型，这限制了写入并发。这对多线程或多进程的代理工作负载尤其成问题，因为对基于 SQLite 的文件系统的写入操作容易成为瓶颈。Turso 中的多版本并发控制实现支持多个写入器，这缓解了该问题，但需要在 AgentFS 中启用。

检查点开销。Turso 和 SQLite 需要定期将 WAL 合并到数据库文件中以保持良好的读取性能。此检查点过程会引入延迟，影响文件系统性能。虽然代理通常对延迟敏感，但可能需要采用增量检查点方法。

写入放大。 SQLite 的写入以页粒度（通常为 4KB）进行。即使是单字节的修改也会将整个页面写入 WAL。FUSE 和 NFS 通过内核页缓存对写入进行批处理来缓解这一问题，但底层的放大效应仍然存在。生理日志（结合了逻辑操作与物理页面引用）可以通过仅传输实际修改而非整个页面来减少放大效应。

大文件。 SQLite 在许多小文件场景下表现良好，但生成大量大型文件（如视频、数据集或模型权重）的代理程序该如何处理？将多 GB 的二进制大对象存储在 SQLite 的页中效率低下，因为存储引擎必须将它们分割成固定大小页面的长链，从而导致随机 I/O 操作和更高的写放大（例如）。可能需要一种混合方法：直接将大文件存储在 S3 中，同时将元数据保存在 SQLite 中。

代理需要文件系统。它们经过数十年 Unix 工具链和基于文件的工作流的训练。AgentFS 在 SQLite 之上提供了这种抽象，让你可以在单个文件中获得可移植性、可查询性和快照功能。

但本地磁盘上的单个文件的扩展性是有限的。当计算是临时的、代理需要在机器间迁移、多个代理协作处理共享状态时，你需要解聚合。SQLite 的基于 WAL 的架构与 Turso 的同步协议相结合，提供了一条可行路径：本地速度的读写操作、后台同步到对象存储，以及可在机器间移动的状态。
