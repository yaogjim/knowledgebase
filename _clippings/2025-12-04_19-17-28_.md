# Building Cursor Composer – Lee Robinson, Cursor
https://www.youtube.com/watch?v=fL1iJHtl51Q

很高兴回到纽约，我也非常兴奋能代表 Cursor 的所有工程和研究团队，在这里分享关于构建 Cursor Composer（我们的第一个智能体模型）的内容。我的同事 Sasha 最近其实也做过一个类似主题的演讲，所以我很高兴能从我自己的角度来谈谈这个话题。

Cursor Composer 是一个专为现实世界软件工程设计的模型，它的目标是既要“快”又要“聪明”。根据我们针对自身基准测试的评估，它优于目前最好的开源模型。它能够与最近的前沿模型（如 Sonnet 3.5、GPT-4o 等）相媲美，但在智能水平上略低于这些最新的前沿模型。但它真正的亮点在于效率：在同等智能水平下，它的 Token 生成效率大约是其他模型的四倍。所以，我们致力于将速度与智能完美结合。

### 为什么要构建这个模型？

显而易见，Cursor 是一个 IDE（集成开发环境）。我们为什么要涉足模型领域？为什么我们在乎这个？

我们的研究和产品团队一直在构建一个名为 Tab 的模型，用于代码自动补全。也许你们中的一些人在 Cursor 中使用过它。我们想采取同样的低延迟方法，并将其应用于编程智能体（Agents）。但说实话，起初我们并不确定这是否行得通。

因此，我们开始针对这个模型构建一些早期的原型版本，发布并收集用户反馈。让我们感到惊讶的是，人们非常喜欢我们发布的这个早期版本。他们非常喜欢它的速度，但我们得到的反馈是：它还不够聪明，不足以成为许多人日常编程的主力工具。

所以我们需要它既聪明又快。绝对需要足够聪明。因此，我们着手制定了一个内部基准测试，该测试代表了我们在自己的代码库上的使用情况以及我们实际构建软件的方式。如果我们拥有一个既快又聪明，且生成的检查点（checkpoint）能让我们的开发人员每天用来构建产品和所有软件的模型，我们就知道我们成功了。

例如，这里的一个重大改变——它确实帮助我们将模型推向了人们愿意使用的水平——是能够并行调用工具，并能够非常有效地使用我们的语义搜索工具。稍后我们会详细讨论这一点。

如果你还没见过，这是 Cursor 2.0 的新界面，我们将使用 Composer 1 模型。你会注意到它正在非常快速地执行许多操作。它并行调用了一堆工具，比如 grep（读取大量文件）、执行 Shell 命令、进行文件编辑、编写和管理待办事项列表。你可以在前台非常快速地处理任务。在这个例子中，我正在调查一个开源代码库中的问题。

我不确定大家的感觉如何，但对我来说，这是一种截然不同的编程体验。我已经使用编程智能体一段时间了，这与那种启动一个智能体然后等待（比如等待 20 分钟让它完成，期间你会切换上下文）的体验完全不同。这种方式确实有助于让你保持在“心流”状态，我认为这是一种不同风格的编程方式。

### 基础设施与训练挑战

我想谈谈我们是如何做到这一点的，希望对大家来说通俗易懂。我不是机器学习研究员，但我确实非常喜欢这些东西。我们将探讨我们学到了什么，面临的一些基础设施挑战，以及我们未来的发展方向。

在 Cursor 中，用户向我们的后端提交查询。智能体读取该查询，然后决定进行一系列工具调用。我们的智能体大约有 10 个工具，但我们将重点关注其中的 5 个：读取文件、编辑文件、搜索代码库、查看 Lint（代码静态分析）以及运行终端或 Shell 命令。

然后，智能体能够自主决定是串行调用还是并行运行这些工具。我们在强化学习（RL）中的目标是尽可能紧密地模拟 Cursor 的生产环境。因此，对于训练数据，我们要假装实际上是在调用真实的 Cursor 查询。

为此，我们运行了一系列的 Rollouts（采样运行）。例如，在一次 Rollout 中，我们会调用一系列工具，如读取文件和编辑文件。当我们运行更多的 Rollouts 时，我们可以从相同的初始起点开始，但可能会调用一组完全不同的工具。例如，在另一次运行中，我们可能还会执行代码库搜索。我们会对输出进行评分，决定哪个更好，然后根据该变化更新模型的参数。

从概念上讲，这是一个非常简单的想法。挑战在于当你采用这个简单的想法并试图将其扩展到非常大的规模时。主要有三个挑战：

1.  **环境匹配**：首先是尝试匹配训练和推理环境。在这个案例中，对于 Composer，我们正在训练一个大型的混合专家模型（Mixture of Experts），它在数千个 GPU 上并行运行。如果我们不加速这个过程，训练将耗费极长的时间。所以，我们希望让它非常快，并使训练和采样的版本尽可能接近。
2.  **复杂性**：当你看向现实世界的数据时，Rollouts 可能会变得相当复杂。模型将使用数十万到数百万个 Token，进行数百次不同的工具调用。而且每个 Rollout 所需的时间可能截然不同。有的可能进行大量工具调用，有的则较少，它们的完成时间各不相同。所以，我们必须弄清楚如何应对这一挑战。
3.  **一致性**：还有一致性的挑战。如果我们想尽可能紧密地模拟 Cursor 的生产环境，我们需要使用完全相同的工具格式和工具响应。但在训练中，我们要处理极其突发性的计算量。基本上，我们是一次性完成所有这些训练，这与生产环境不同。

所以，这实际上是一个基础设施挑战。我们面临这三个机器学习挑战，而巧合的是，所有的解决方案实际上都是基础设施问题的解决方案。

### 解决方案与架构

让我们谈谈我们在基础设施层面上如何解决其中的一些问题。

我们的架构对于涉足该领域的人来说可能很熟悉，但我认为在宏观层面上讨论它仍然很有趣。我们有三种不同的服务器：
1.  **推理服务器（Inference Server）**。
2.  **标准的 ML 栈**（使用 PyTorch）。
3.  **环境服务器（Environment Servers）**：这就是我们进行我刚才提到的 Rollouts 的地方，我们在这里使用 Ray。这些服务器模拟了我提到的 Cursor 环境。

所有这些服务器都在相互通信。例如，推理服务器可以将优势函数（Advantages）发送回训练器，根据 Rollout 的结果“微调”模型，更新模型并获取新参数。

这部分更偏向机器学习侧，但我们要训练一个非常大的模型，并尽可能快地完成。我们的团队在研究方面能够做到这一点的一种方法是开发一个自定义算子（Kernels）库，允许进行极低精度的训练。这基本上允许我们大幅加快训练过程，并且更容易部署到我们的推理服务器。

如果你是那种喜欢钻研这些的人，我们写了一篇博客文章，深入探讨了我们的自定义算子。如果你感兴趣的话，简而言之，我们发现混合专家（MoE）层的速度在英伟达 Blackwell 芯片上提高了约 3.5 倍。所以，这对我们的训练运行产生了相当显著的影响。

一旦我们更新了权重，我们需要在训练过程中将它们发送回推理服务器。推理服务器负责执行我提到的所有 Rollouts，调用工具并管理我们发送的内容。

这里的挑战在于它们完成的时间各不相同。如果采用简单的版本，会有很多浪费的时间。因此，我们能够做的是在不同的线程和进程之间进行负载均衡，基本上是转移工作负载，避免大量的空闲时间。例如，如果一个 Rollout 进行了大量的工具调用，也许是安装一些包或库，我们不会只是坐在那里等待所有其他任务完成。

推理服务器花费所有时间在与环境进行来回通信，进行工具调用并获取工具结果。再次强调，这是在服务器之间进行通信，我们希望该环境尽可能接近 Cursor 产品。

### 云端智能体与虚拟机

拥有一体化的编码智能体、IDE，以及我们自己进行模型研究和训练的好处之一是，我们可以协同设计这些东西。

当我们为这个模型构建大量强化学习（RL）工作时，我们也在构建我们的 Cloud Agents（云端智能体）产品。这让你可以在离线状态下运行 Cursor 智能体。你可以在手机上、网页上运行它，或者从 Slack 启动它。为了做到这一点，我们在云端启动虚拟机（VM）。每一个虚拟机都会加载用户的代码。它允许智能体在一个安全的沙箱中进行文件更改、运行工具和编辑代码。

巧合的是，这是强化学习和我们训练使用的完美基础设施。所以我们拥有这支云端虚拟机舰队，以及一个与 Cursor 生产环境非常匹配的环境，我们可以将其用于训练。

这仍然存在一些挑战。我刚才提到训练工作负载具有很强的突发性（Spiky），这与运行云端智能体产品时的标准推理不同。所以我们需要构建基础设施来支持所有这些虚拟机并在它们之间进行编排。我们有许多不同的集群，这里有成千上万个虚拟机。你可以在我身后看到我们用 Composer 构建的一个内部仪表板，用来可视化舰队中的所有不同虚拟机。

### 为什么在乎环境匹配？

为什么还要花这么多时间试图让环境尽可能接近 Cursor 生产环境呢？我已经提到过几次了。我们可以使用 Mock（模拟）数据，我们可以仿真它。

但一个非常好的好处是，我们可以为模型提供我们认为在智能体内部非常有价值的特定工具。其中之一是我们训练了自己的嵌入模型（Embedding Model），允许你进行语义搜索。当你使用 Cursor 时，我们会索引你的代码库，然后允许智能体进行自然语言查询，以找到它可能想要编辑的文件。

我们最近对此进行了一些研究。我们发现语义搜索不仅帮助了 Cursor 智能体工具集中的每一个模型，而且对 Composer 特别有帮助。仔细想想，这是有道理的。我们在与推理时完全相同的环境中训练 Composer。因此，模型变成了这个工具的“超级用户”，这非常有效。

### 发布与未来展望

让我们谈谈发布的情况以及接下来的方向。

在我们进行训练的过程中，当我们能够不断改进模型并在越来越多的 Rollouts 后开始看到更多改进时，我们就知道强化学习起作用了。我们起步时的性能与最好的开放模型差不多，然后随着我们训练并投入更多算力，性能持续提升，直到今天我们接近了目前可用的最佳编码智能体的前沿水平。

我个人认为，这对于能够采用并扩展强化学习，将其应用于像我们例子中的编码这样的非常困难的专业任务来说，是一个极好的迹象。它也可以应用于其他领域。

强化学习还允许我们以对 Cursor 产品非常有用的方式更改模型的属性。我们希望模型在生成 Token 时既要快，又要保证端到端体验的结果是有帮助的。例如，与其逐个读取文件，你可以通过工具调用并行读取 10 个文件。正如你在前面的演示中看到的，这使得 Composer 感觉快得多。而且我们认为这仅仅是个开始，在这个领域我们还有很多可以做的事情来加速模型。

第二点是模型学会了如何作为一个智能体更好地行事。一开始，模型会进行过多的编辑。有时这些编辑是不必要的。但随着我们将训练进行得越来越深入，模型在学习更多地搜索和读取文件方面出奇地变得更好了。所以，它会在尝试进行编辑之前先去找到正确的东西。总体而言，这使得它更加有效。

我们在上个月的 Cursor 2.0 中发布了 Composer，目前看来大家似乎很喜欢它。在座的有谁试过这个模型吗？好的，太棒了。比我预期的要多。很高兴听到这个。

我想从我使用这个模型和使用编码智能体一段时间的角度来看，我把这个问题描述为像“飞机上的 Wi-Fi”。当你在飞机上使用 Wi-Fi 时，它能用，但有点令人沮丧。你真的很想做你要做的事情，但它有点慢，甚至有时你会希望干脆没有 Wi-Fi。

我认为对于我们中一些很早就采用编码智能体的人来说，有时感觉就像飞机上的 Wi-Fi。因为它需要 10 或 20 分钟，你处于这个奇怪的——Swyx 称之为“半异步死亡谷”（Semi-async valley of death）的状态，你要么想要非常快的东西，要么想要最强大、最智能的模型，可以在后台运行相当长的时间（也许 30 分钟甚至几天）。我认为当你卡在中间时，那是——那是由于非常痛苦的。

所以对我来说，Composer 以及我认为对其他人来说，它把很多乐趣带回了编码智能体的使用中，感觉更像是在手动编写代码，你非常紧密地参与其中（In-the-loop），非常同步。所以我很高兴看到更多人也在探索这个领域。

对我来说，日常工作中，我正在使用最新的前沿模型（如 GPT-4o 等）编写很多计划（Plans），这非常适合做计划。然后我使用 Composer 来实际执行该计划，就像 Dex 谈到的那样，利用上下文工程工作，然后实际去构建它。

### 总结与反思

我们就构建 Composer 这一过程，来自研究和产品团队的几点反思：

1.  **RL 的有效性**：强化学习在训练非常特定的模型方面效果出奇地好，前提是给它高质量的数据和一定量的算力。在 Cursor，我们不是在试图构建通用人工智能（AGI）。我们不是在试图构建 AGI。我们试图构建非常优秀的编码模型，而 RL 在这方面效果出奇地好。
2.  **工具加速研发**：像 Cursor 这样的 AI 工具（不一定非得是 Cursor，但像 Cursor 这样的工具）确实有助于加速研发。当然，我们整个团队都使用 Cursor 来帮助他们更高效地编写和调试代码，但这种速度的提升实际上在我们所有的工程工作中产生了复利效应。所以我们能够尝试更多的想法，更快地发布产品，尝试新的研究。这真的非常有帮助。
3.  **基础设施的重要性**：最后一点，对我个人来说非常有趣的是，看到多少机器学习工作和训练过程实际上也是基础设施问题。它们是非常相关的。回想我在 Vercel 的时光，我们看到了非常相似的事情，在 JavaScript 或 Python 领域使用框架时的许多“神奇时刻”，你也需要稍微思考一下它们实际部署的基础设施。所以这些事情比人们想象的更加相关。

以上就是我们的一些反思。听起来你们中的一些人已经试用过了。如果你对此感兴趣并致力于此，Cursor 目前正在全面招聘。如果你在纽约，我们刚刚在纽约开设了一个办公室。我们很乐意与你探讨构建世界上最好的编码模型。

谢谢大家。
