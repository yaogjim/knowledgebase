# ## Pi：OpenClaw 内部的最小代理

## Pi：OpenClaw 内部的最小代理

如果你不是一直躲在石头下，你会注意到本周我朋友 Peter 的一个项目 [在网上病毒式传播了](https://en.wikipedia.org/wiki/OpenClaw) 。这个项目有很多名字。最近的名字是 [OpenClaw](https://openclaw.ai/) ，但在新闻中你可能会看到它被称为 ClawdBot 或 MoltBot，具体取决于你阅读的时间。它是一个连接到你选择的通信渠道的代理，它只是 [运行代码](https://lucumr.pocoo.org/2025/7/3/tools/) 。

你可能不太熟悉的是，OpenClaw 的底层是一个叫做 [Pi](https://github.com/badlogic/pi-mono/) 的小型编码代理。而 Pi 恰好是我目前几乎唯一使用的编码代理。在过去几周里，我越来越成为这个小代理的狂热拥护者。最近我做了一个关于这个的演讲后，我意识到我还没有在这个博客上写过关于 Pi 的内容，所以我觉得我可能需要提供一些背景信息，说明我为什么痴迷于它，以及它与 OpenClaw 的关系。

Pi 由 [Mario Zechner](https://mariozechner.at/) 编写，与 Peter 不同——Peter 追求“带有一丝疯狂的科幻” [1](#fn-1) ，Mario 则非常务实。尽管方法不同，OpenClaw 和 Pi 都遵循相同的理念：LLMs 非常擅长编写和运行代码，因此要拥抱这一点。在某种程度上，我认为这并非偶然，因为 Peter 让我和 Mario 对这个想法以及去年的智能体着迷。

## What is Pi?

所以 Pi 是一个编码代理。而且有很多编码代理。实际上，我认为现在你几乎可以随便挑选一个现成的编码代理来使用，这样就能体验代理式编程的感觉。在我博客的评论中，我曾对 AMP 给予过积极评价，我之所以对 AMP 产生强烈共鸣的原因之一，是它给人的感觉确实像是由那些既沉迷于代理式编程，又尝试过多种不同方法来验证哪些方法有效（而非仅仅围绕它构建一个花哨的用户界面）的人开发的产品。

Pi 对我来说很有趣，因为有两个主要原因：

- 首先，它有一个微小的核心。它拥有我所知道的所有智能体中最短的系统提示，并且只配备了四个工具：Read、Write、Edit、Bash。
- 第二点是，它通过提供一个扩展系统来弥补其微小的核心，这个扩展系统还允许扩展将状态持久化到会话中，这非常强大。

还有一个小惊喜：Pi 本身被编写得如同优秀的软件。它不会闪烁，不会占用大量内存，不会随机崩溃，非常可靠，而且是由一位对软件内部实现极为用心的人编写的。

Pi 也是一个小组件的集合，你可以用它来构建自己的代理 在顶部。这就是 OpenClaw 的构建方式，而这也是我构建自己的小 agent 的方式。 Telegram 机器人以及马里奥如何构建他的机器人 [妈妈](https://github.com/badlogic/pi-mono/tree/main/packages/mom) 。如果你想构建你自己的代理，连接到某个事物，当 Pi 指向自身和妈妈时，它会为你创造一个。

## Pi 中没有什么

并且，为了理解 Pi 中包含的内容，理解……更为重要 什么不在 Pi 中，为什么它不在 Pi 中，以及更重要的是：为什么它不会在 Pi 中 Pi。最明显的缺失是对 MCP 的支持。在...中没有对 MCP 的支持。 它。虽然你可以为它构建一个扩展，但你也可以像 OpenClaw 那样做。 用于支持 MCP，而 MCP 是用于 [mcporter](https://github.com/steipete/mcporter) 。mcporter 通过命令行界面或 TypeScript 绑定公开 MCP 调用，也许你的代理可以用它做些什么。或者不做，我也不清楚:)

这不是一种懒惰的疏忽。这源于 Pi 的工作原理的理念。Pi 的整个理念是，如果你希望代理做它尚未能做的事情，你不需要去下载一个扩展或一项技能或者诸如此类的东西。你让代理自行扩展。它推崇编写代码和运行代码的理念。

这并不是说你不能下载扩展。这是非常支持的。但不是一定要鼓励你下载别人的扩展，你也可以将你的代理指向一个已有的扩展，比如说，像你在那边看到的那个东西一样构建它，但对它进行你喜欢的修改。

## 为构建代理的代理而构建的代理

当你观察 Pi 以及其延伸的 OpenClaw 正在做什么时，会发现这是一个像黏土一样可塑的软件示例。这为其底层架构设定了某些要求，而这些要求实际上在很多方面对系统施加了某些限制，这些限制确实需要纳入核心设计中。

例如，Pi 的底层 AI SDK 被设计为一个会话能够真正包含来自许多不同模型提供商的许多不同消息。它认识到会话的可移植性在不同模型提供商之间在一定程度上受到限制，因此，它不会过度依赖任何无法转移到其他模型提供商的特定于模型提供商的功能集。

第二点是，除了模型消息外，它还在会话文件中维护自定义消息，这些消息可供扩展用于存储状态，或由系统本身用于维护要么完全不发送给 AI、要么仅发送部分内容的信息。

因为该系统存在，并且扩展状态也可以持久化到磁盘，所以它具有内置的热重载功能，使代理能够编写代码、重新加载、测试并循环操作，直到扩展真正可用。它还附带代理本身可以用来自我扩展的文档和示例。更妙的是：Pi 中的会话是树形结构。你可以在会话中进行分支和导航，这带来了各种有趣的可能性，例如实现修复损坏代理工具的支线任务工作流，而不浪费主会话中的上下文。工具修复后，我可以将会话回滚到之前的状态，Pi 会总结另一个分支上发生的事情。

这一切都很重要，因为比如说，如果你考虑 MCP 的工作原理，在大多数模型提供商那里，MCP 的工具（就像任何 LLM 的工具一样）需要在会话开始时加载到系统上下文或其工具部分中。这使得完全重新加载工具的功能变得非常困难，甚至不可能——而不破坏整个缓存，也不会让 AI 对之前的调用如何不同地工作感到困惑。

## Tools Outside The Context

Pi 中的一个扩展可以注册一个工具，供 LLM 调用，我偶尔会觉得这很有用。例如，尽管我批评 Beads 的实现方式，但我确实认为让代理访问待办事项列表是一件非常有用的事情。而且我确实使用了一个特定于代理的本地问题跟踪器，这是我让代理自己构建的。并且因为我希望代理也能管理待办事项，在这个特定的情况下，我决定给它一个工具而不是 CLI。这似乎适合该问题的范围，并且目前是我加载到上下文中的唯一额外工具。

但在很大程度上，我为代理添加的内容要么是技能，要么是 TUI 扩展，目的是让与代理的交互更愉快。除了斜杠命令之外，Pi 扩展可以直接在终端中渲染自定义 TUI 组件：旋转加载指示器、进度条、交互式文件选择器、数据表格、预览窗格。TUI 足够灵活，以至于 Mario 证明你可以 [在其中运行 Doom](https://x.com/badlogicgames/status/2008702661093454039) 。虽然不实用，但既然你能运行 Doom，你当然可以构建一个有用的仪表盘或调试界面。

我想强调一下我的一些扩展，让你了解有哪些可能性。虽然你可以直接使用它们而不做修改，但核心思想其实是将你的代理指向其中一个，并随心所欲地重新混合它。

### /answer

I [don’t use plan mode](/2025/12/17/what-is-plan-mode/). I encourage the agent to ask questions and there’s a productive back and forth. But I don’t like structured question dialogs that happen if you give the agent a question tool. I prefer the agent’s natural prose with explanations and diagrams interspersed.

问题：在对话中直接回答问题会变得很混乱。因此 `/answer` 会读取代理的最后一次响应，提取所有问题，并将它们重新格式化为一个美观的输入框。

![The /answer extension showing a question dialog](/static/pi-answer.png)

### /todos

尽管我批评 [Beads](https://github.com/steveyegge/beads) 的实现，但给代理一个待办事项列表确实非常有用。这个 `/todos` 命令将显示存储在 `.pi/todos` 中的所有项目，以 Markdown 文件的形式。代理和我都可以操作它们，并且会话可以认领任务以将其标记为进行中。

### /review

随着代理生成的代码越来越多，在代理先审核之前就把未完成的工作交给人类处理，这没什么意义。由于 Pi 会话是树形结构，我可以分支到一个新的审核上下文，获取审核结果，然后将修复内容带回主会话。

![The /review extension showing review preset options](/static/pi-review.png)

该界面仿照 Codex 设计，可轻松查看提交、差异、未提交的更改或远程拉取请求。提示词会关注我关心的内容，以便获取我需要的标注信息（例如：我要求它标注新添加的依赖项）。

### /control

一个我尝试使用但不主动使用的扩展。它允许一个 Pi 代理向另一个 Pi 代理发送提示。这是一个简单的多代理系统，没有复杂的编排，对实验很有用。

### /files

列出会话中更改或引用的所有文件。你可以在 Finder，VS Code 中的 diff，快速查看它们，或在你的提示中引用它们。 `shift+ctrl+r` 快速预览最近提到的文件，这在代理生成 PDF 时非常方便。

其他人也开发了扩展： [Nico 的子代理扩展](https://github.com/nicobailon/pi-subagents) 和 [交互式 Shell](https://www.npmjs.com/package/pi-interactive-shell) which lets Pi autonomously run interactive CLIs in an observable TUI overlay.

## Software Building Software

这些都只是关于你可以用你的代理做什么的想法。它的重点是。 主要是这些都不是我写的，是代理为我创建的 规格。我让 Pi 做一个扩展，它做到了。没有 MCP，有 没有社区技能，什么都没有。别误会我，我用了超多技能。但是 它们是由我的 clanker 手工制作的，而不是从任何地方下载的。对于 实例，我完全用一个替换了我所有用于浏览器自动化的命令行界面或 MCPs [使用 CDP 的技能](https://github.com/mitsuhiko/agent-stuff/blob/main/skills/web-browser/SKILL.md) 。不是因为替代方案不起作用或者不好，而是因为这简单又自然。代理保持自身的功能。

我的代理有 [相当多的技能](https://github.com/mitsuhiko/agent-stuff/tree/main/skills) ，关键是，如果我不需要某个技能，我就会舍弃它。例如，我给它添加了一个能够读取其他工程师分享的 Pi 会话的技能，这有助于代码审查。或者，我有一个技能可以帮助代理生成我想要的提交信息和提交行为，以及如何更新更新日志。这些原本是斜杠命令，但我目前正在将它们迁移为技能，以查看这样是否同样有效。我还有一个技能，希望能帮助 Pi 使用 `uv` 而不是 `pip` ，但我也添加了一个自定义扩展来拦截对 `pip` 和 `python` 的调用，将它们重定向到 `uv` 。

与像 Pi 这样的最小代理协作带给我的一部分魅力在于，它让你亲身践行“使用能够构建更多软件的软件”这一理念。将这一理念推向极致，就是去除用户界面（UI）和输出，将其与你的聊天功能连接。这正是 OpenClaw 正在做的事情。考虑到它的巨大发展，我越来越觉得，无论如何，这将成为我们的未来。
