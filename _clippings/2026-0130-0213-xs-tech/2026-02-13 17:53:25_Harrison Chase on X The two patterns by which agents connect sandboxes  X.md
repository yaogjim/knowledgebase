-   越来越多的代理需要一个工作空间：一台他们可以运行代码、安装软件包并访问文件的计算机。沙箱提供了这样的工作空间。
    
-   将代理与沙箱集成的架构模式有两种： - 模式1（代理在沙箱内）：代理在沙箱内运行，你通过网络与其通信。优势：与本地开发一致，代理与环境之间的紧密耦合。 模式 2（沙箱作为工具）：代理在本地/您的服务器上运行，远程调用沙箱进行执行。优势：代理逻辑易于更新，API 密钥保留在沙箱外部，关注点分离更清晰。
    

感谢来自 Witan Labs 的 Nuno Campos、来自 E2B 的 Tomas Beran 和 Mikayel Harutyunyan、来自 Runloop 的 Jonathan Wall 以及来自 Zo Computer 的 Ben Guo 提供的审阅和评论。

越来越多的代理需要一个工作空间——一个可以运行代码、安装软件包和访问文件的计算机。该工作空间需要被隔离，以确保代理无法访问您的凭证、文件或网络。沙箱通过在代理的环境和您的主机系统之间创建边界来提供这种隔离。构建这些代理的团队面临的问题不是是否使用沙箱——而是如何集成它们与他们的代理架构集成。

存在两种常见模式，取决于代理运行的位置：沙箱内部或沙箱外部。每种模式都有不同的优势和权衡。

注意：这篇文章关注的是能为代理提供完整“计算机”环境的沙箱——即完整的执行环境，例如 Docker 容器或虚拟机（VM）。我们不会讨论进程级沙箱（如 bubblewrap）或语言级沙箱（如 Pyodide）。

在这种模式下，代理在沙箱内部运行。你通过网络与它通信。

构建一个已预装代理框架的 Docker 或虚拟机镜像，在沙箱内运行该镜像，并从外部连接以发送消息。代理暴露一个 API 端点（通常为 HTTP 或 WebSocket），你的应用程序通过沙箱边界与其进行通信。

这种模式与本地开发非常相似——在本地终端中运行 deepagents 时，你需要在沙箱中执行相同的命令。代理拥有直接的文件系统访问权限，并且能够修改其环境。当代理与执行环境紧密耦合时（例如，代理需要与特定库交互或维护复杂的环境状态），这种模式非常有用。

沙箱边界之间的通信需要基础设施。一些服务提供商在其 SDK 中处理这一问题——例如，像 OpenCode 这样的代理在沙箱内部运行服务器，而像 E2B 这样的服务提供商可以通过简洁的 API 公开这一功能。如果你的服务提供商不提供这一功能，你需要自己构建 WebSocket 或 HTTP 层，包括会话管理和错误处理。

API 密钥必须位于沙箱内部，以便代理进行推理调用。如果沙箱被入侵，这会带来潜在的安全风险，无论是由于隔离技术的漏洞，还是由于提示注入攻击窃取凭证。注：我们看到 E2B 和 Runloop 等供应商正在开发秘密保管库功能，这解决了这一问题。

更新需要重新构建容器镜像并重新部署，这可能会减慢开发过程中的迭代周期。

另一个缺点是，沙箱必须在代理激活前恢复，这通常需要额外的逻辑。

对于那些担心保护其代理知识产权的人来说，如果你的代理在沙箱中运行，那么窃取代理的整个代码和提示词就会变得容易得多。

维坦实验室（Witan Labs）的努诺·坎波斯（Nuno Campos）也指出了另一个安全风险：“我想说沙箱中的代理的另一个缺点是，实际上你的代理的任何部分都不能拥有比 bash 工具更多的权限。例如，想象你需要一个既有 bash 工具又有能进行网页搜索或网页抓取的工具的代理，那么所有 LLM 生成的代码都可以进行无限制的网页抓取（这是一个很大的安全风险）。如果沙箱是作为工具存在的，那么你可以让工具拥有比赋予 LLM 生成代码更多的权限（这对许多代理来说听起来非常有用），因为安全边界围绕着 bash 工具，而不是整个代理。”

在这种模式下，代理运行在您的机器或服务器上。当它需要执行代码时，会通过 API 调用远程沙箱。

[

你的代理在本地（或你的服务器上）运行，当它生成需要执行的代码时，会调用沙箱提供商的 API（例如 E2B、Modal、Daytona、Runloop）。提供商的 SDK 处理所有通信细节。从你的代理的角度来看，沙箱只是另一个工具。

你可以即时更新代理代码，而无需重新构建容器镜像，这加快了开发过程中的迭代速度。API 密钥保留在沙箱之外——只有执行过程在隔离环境中进行。这提供了更清晰的关注点分离：代理状态（对话历史、推理链、记忆）存在于代理运行的环境中，与沙箱分离。这意味着沙箱故障不会导致代理状态丢失，并且你可以切换沙箱后端而不会影响代理的核心逻辑。

该选项的另外两个优势，正如 E2B 的 Tomas Beran 所指出的：

1.  可以选择在多个远程沙箱中并行运行任务
    
2.  仅在执行代码时为沙箱付费，而非为整个流程的运行时付费。
    

Ben Guo 补充了最后一点关于将代理运行时与沙箱运行时分离的好处：“我们选择了模式 2，原因正如您所提及的，同时也是为未来做准备——届时在 GPU 机器上运行代理框架会更合理。总体而言，持久化沙箱与推理框架之间的环境需求将会出现差异。”

网络延迟是主要缺点。每次执行调用都会跨越网络边界。对于有许多小型执行的工作负载，这可能会累积起来。

许多沙箱提供商提供有状态会话，其中变量、文件和已安装的软件包在同一会话内的多次调用中保持不变。这可以通过减少所需的往返次数来减轻一些延迟问题。

-   代理与执行环境紧密耦合（例如，代理需要对特定库或复杂环境状态进行持久访问）
    
-   你希望生产环境紧密镜像本地开发
    
-   您的服务提供商的 SDK 为您处理通信层
    

-   在开发中，你需要快速迭代 agent 逻辑
    
-   你希望将 API 密钥保存在沙箱之外
    
-   您更倾向于在代理状态和执行环境之间实现更清晰的分离
    

为了让这些模式具体化，我们将展示使用

，一个具有内置沙箱支持的开源代理框架。类似的模式适用于其他代理框架。

对于模式1，首先你构建一个预先安装了你的代理的镜像：

```
FROM python:3.11
RUN pip install deepagents-cli
```

然后在沙箱内运行它。完整的实现需要额外的基础设施来处理你的应用程序与沙箱内代理之间的通信（WebSocket 或 HTTP 服务器、会话管理、错误处理）。这超出了本文的范围，但我们将有一些后续文章更详细地探讨这一点。

```
from daytona import Daytona
from langchain_anthropic import ChatAnthropic

from deepagents import create_deep_agent
from langchain_daytona import DaytonaSandbox

# Can also do this with E2B, Runloop, Modal
sandbox = Daytona().create()
backend = DaytonaSandbox(sandbox=sandbox)

agent = create_deep_agent(
    model=ChatAnthropic(model="claude-sonnet-4-20250514"),
    system_prompt="You are a Python coding assistant with sandbox access.",
    backend=backend,
)

result = agent.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "Run a small python script",
            }
        ]
    }
)

sandbox.stop()
```

1.  代理在你的本地机器上计划
    
2.  它生成 Python 代码以解决这个问题
    
3.  它调用 Runloop API，该 API 在远程沙箱中执行代码
    
4.  沙箱返回结果
    
5.  代理看到输出并继续在本地进行推理
    

代理需要在隔离环境中执行代码以确保安全。存在两种架构模式：在沙箱内运行代理（模拟本地开发，紧耦合）或在外部运行代理并将沙箱作为工具（易于更新，API 密钥保持安全）。每种模式都有不同的优势和权衡，具体取决于您的需求。

deepagents 支持两种模式，配置简单。
