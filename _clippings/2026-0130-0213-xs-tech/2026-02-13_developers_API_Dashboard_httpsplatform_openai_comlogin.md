# [API Dashboard](httpsplatform.openai.comlogin)

[API Dashboard](https://platform.openai.com/login)

![Shell + Skills + Compaction: Tips for long-running agents that do real work](/images/blog/skills-shell-tips.png)

我们正在从单轮助手转向长期运行的代理，这些代理处理真实的知识工作：读取大型数据集、更新文件以及编写应用程序。

基于开发者反馈以及我们构建 Codex 和内部代理的自身经验，我们正在发布一套新的代理原语，这些原语使长期工作更具实用性：

- [**技能**](/api/docs/guides/tools-skills) (与 Agent Skills 开放标准一致): 可重复使用的、版本化的指令，你可以将其挂载到容器中，以便代理能够更可靠地执行任务。
- 升级后的 [**shell**](/api/docs/guides/tools-shell) 工具：一个由 OpenAI 托管的容器，具备受控互联网访问权限，代理可在其中安装依赖项、运行脚本并输出结果（例如，报告和工件）。
- [**服务器端压缩**](/api/docs/guides/context-management) : 一种简单的方法，可自动压缩长期的代理运行，从而避免上下文限制。

文档和 API 参考分别涵盖了上述的每一项内容。这篇文章聚焦于我们到目前为止发现最有效的那些不明显的技巧和模式，无论是在我们 OpenAI 的工作中，还是在早期技能客户 Glean 的生产环境中。

## A brief mental model

### 技能：模型可按需加载的“Procedures”

一个技能是一个文件集合，外加一个包含前置内容和说明的 `SKILL.md` 清单文件。可以这么想：一个模型在需要执行实际工作时可以查阅的带版本的操作手册。

当技能可用时，平台会向模型暴露每个技能的 `name` 、 `description` 和 `path` 。模型会使用该元数据来决定是否调用某个技能。如果决定调用，模型会读取 `SKILL.md` 以获取完整的工作流程。

### Shell 工具：“执行”针对代理

Shell 工具让模型在真实的终端环境中工作，或者：

- 由 OpenAI 管理的托管容器。
- 你自己执行的本地 shell 运行时（相同的工具语义，但你控制这台机器）。

托管 Shell 通过 Responses API 运行，这意味着你的请求包含有状态工作、工具调用、多轮对话延续以及工件。

### Compaction: 保持长时间运行持续进行

随着工作流变得越来越长，它们会遇到上下文窗口限制。服务器端压缩通过管理上下文窗口并自动压缩对话历史记录，使长时间运行的工作流能够持续推进。

Responses API 中的压缩功能为您提供两种处理该问题的方式：

- **服务器端压缩（新）：** 当上下文超过阈值时，压缩会自动在流内运行，因此无需单独调用压缩操作。
- **独立压缩端点：** 使用 `/responses/compact` 当你想要对压缩发生的时机进行显式控制时。

### 为什么它们一起更好

- 技能通过将稳定的流程和示例整合到可复用的包中，减少了提示词的面条化。
- Shell 提供了一个完整的执行环境，让你安装代码、运行脚本并写入输出。
- Compaction 保持长时间运行中的连续性，因此相同的工作流可以在无需手动进行上下文操作的情况下持续执行。
- 一起，你可以获得带有实际执行的可重复工作流，而不会将你的系统提示变成脆弱的巨型文档。

## Tips and tricks

你的技能描述实际上是模型的决策边界。它应该回答：

- When should I use this?
- When should I not use this?
- 什么是输出和成功标准？

一种实用的模式是在描述中直接包含一个简短的“何时使用 vs. 何时不使用”区块，并使其具体（包含输入、涉及的工具、预期成果）。

### 2) 添加负面示例和边界情况以减少误触发

一个令人惊讶的故障模式是，使技能可用最初可能会降低正确触发的概率。我们发现有效的一种修复方法是负例加上边界情况覆盖。

在实际操作中，这意味着编写一些明确的“不要在……时调用此技能”的场景（以及替代方案是什么）。这有助于模型更清晰地进行路由，尤其是当你有多个乍一看很相似的技能时。

Glean 直接观察到这一点：基于技能的路由在目标评估中最初使触发量下降了约 **20%** ，但在他们在描述中添加了负面示例和边缘情况覆盖后，触发量又恢复了。

### 3) 将模板和示例放在技能内部（它们在未使用时基本上是免费的）

如果你一直在强行往系统提示里塞模板，别再这样做了。

技能中的模板和工作示例有两个优势：

- 它们在需要时恰好可用（当技能被调用时）。
- 它们不会为不相关的查询虚增 token。

这对于知识工作的产出尤其有效，例如：

- Structured reports.
- Escalation triage summaries.
- Account plans.
- Data analysis writeups.

Glean 报告称，这种模式在生产环境中带来了他们在质量和延迟方面的最大提升，因为这些示例仅在技能触发时才被加载。

### 4) 尽早设计支持长时间运行，结合容器复用与压缩

长视距代理作为单次提示很少能成功。从一开始就规划连续性：

- 当你需要稳定的依赖项、缓存文件和中间输出时，跨步骤重用同一个容器。
- 传递 `previous_response_id` ，以便模型能在同一个线程中继续工作。
- 将压缩作为默认的长期运行基本原语，而非紧急回退。

这种组合减少了重启行为，并随着线程增长保持多步骤任务的连贯性。

### 5) 当你需要确定性时，明确地告诉模型使用该技能

默认行为是模型决定何时使用技能。这通常是你想要的。

但当你在运行一个具有明确契约的生产工作流时（并且你宁愿追求确定性而非巧妙），只需说：

使用 `<skill name>` 技能。

这是你能使用的最简单的可靠性杠杆。它将模糊的路由转变为明确的契约。

### 6) 将技能与人脉视为高风险组合（设计用于控制）

这是一个现在容易被忽视、以后难以修复的安全提示。

**将技能与开放网络访问相结合会为数据外泄创造高风险路径。** 如果使用网络，请严格设置网络允许列表，假设工具输出不可信，并避免在用户期望有严格确认控制的面向消费者的流程中同时使用开放互联网和强大的操作流程。

A strong default posture:

- Skills: **allowed**
- Shell: **allowed**
- 网络： **仅通过最小白名单启用** ，根据请求，用于范围狭窄的任务

### 7) 将 /mnt/data 设为你的工件交接边界

对于托管的 Shell 工作流，请将 `/mnt/data` 视为写入输出内容的标准位置，这些输出内容将被后续步骤检索、查看或传递回。示例包括报告、清洗后的数据集和已完成的电子表格。

一个良好的心理模型：工具写入磁盘，模型基于磁盘进行推理，开发者从磁盘检索。

### 8) 理解允许列表是一个两层系统（组织级和请求级）

网络在两个地方受到控制：

- 组织级允许列表（由管理员配置），该列表设置了最大允许的目标位置。
- 一个请求级别的 `network_policy` ，该策略必须是组织白名单的子集。

两个在操作层面重要的影响：

1.  保持组织的白名单小且稳定（你信任的已批准目的地集合）
2.  保持请求白名单甚至更小（此任务所需的目标集合）

如果请求包含不在组织白名单中的域，将会报错。

### 9) 使用 domain\_secrets 进行身份验证调用（避免凭证泄露）

如果允许的域名需要认证头，请使用 `domain_secrets` ，这样模型就不会看到原始凭证。

在运行时，该模型会看到占位符（例如， `$API_KEY` ），而边车（sidecar）仅对已批准的目标注入真实值。任何时候你的代理需要从容器内部调用受保护的 API，这都是一个强有力的默认设置。

### 10) 在云端和本地使用相同的 API

你可以使用这两种原语，而无需承诺托管所有内容：

- 技巧可与托管 Shell 和本地 Shell 模式配合使用。
- Shell 有一个本地执行模式，在该模式下你需要自己执行 `shell_call` 并将 `shell_call_output` 返回给模型。
- 如果你正在使用 Agents SDK，你也可以插入自己的 shell 执行器。

一个实用的开发循环看起来像：

1.  在本地启动（快速迭代、访问内部工具、易于调试）
2.  当你需要可重复性、隔离性和部署一致性时，迁移到托管容器。
3.  保持两种模式下的技能一致（即使执行过程发生变动，工作流也保持稳定）

## Three build patterns

虽然你可以随意尝试这些新的智能体原语，但这里有三个如何组合它们来构建有用应用的例子。

### 模式 A：安装 -> 获取 -> 写入制品

这是利用托管 Shell 的最简单方式：代理安装依赖项、获取外部数据并生成具体的交付成果。

For example:

- Install a couple libraries.
- Scrape or call an API.
- Write a report to `/mnt/data/report.md`.

这种模式是实际工作代理的基础，因为它创建了一个清晰的审查边界：你的应用可以向用户展示工件、记录它、对比它，或输入到后续步骤中。

### 模式 B: 技能 + Shell 用于可重复的工作流

一旦你构建了一两个成功的 Shell 工作流，你会发现下一个问题：这能正常工作，但当提示漂移时，可靠性会下降。

这就是技能的用武之地。这里有一个可以遵循的持久结构：

1.  在技能中对工作流（步骤、护栏、模板）进行编码。
2.  将技能挂载到你的 Shell 环境中。
3.  让代理遵循该技能以确定性地生成工件。

这对于像……这样的工作流特别有效：

- 电子表格分析或编辑。
- 数据集清洗与摘要生成
- 针对重复性业务流程的标准化报表生成

### 模式 C（高级）：技能作为企业工作流的载体

我们观察到的一个早期模式是，单一工具调用与多工具编排之间的差距会导致准确性下降。技能能够通过使工具推理更具程序性来填补这一差距，同时不会让系统提示变得臃肿。

Glean 的一个具体示例

- 一项面向 Salesforce 的技能将评估准确率从 **73%提升至 85%** ，并将 **首次 token 时间** 减少了 **18.1%** 。
- 实用策略包括精心的路由、负面示例，以及将模板/示例嵌入到技能中。
- Glean 还使用技巧来编码企业工作流程中的重复任务，包括客户规划、升级分类和与品牌一致的内容生成。

这就是事物变得强大的形态。技能转化为动态的标准操作程序（SOP）：随着你的组织发展而更新，并由代理一致执行。

## Build once, run anywhere

长期运行的代理在既能遵循流程又能在计算机上执行实际工作时，会变得极其有用。技能、托管的 Shell 和压缩共同构建了这一基础。总结一下：

- 使用技巧来编码“如何”（流程、模板、护栏）
- 使用 Shell 执行操作（安装、运行、写入制品）
- 使用压缩来保持长时间运行的连贯性（无需手动管理上下文）
- 当你快速迭代时，先在本地启动。
- 当你需要可重复、隔离的执行时，迁移到托管容器。
- 保持网络严格受限，使用组织级和请求级白名单，并使用域密钥进行认证调用。

开始使用你自己的应用。查看 [技能文档](/api/docs/guides/tools-skills) 、 [Shell 文档](/api/docs/guides/tools-shell) 和 [压缩文档](/api/docs/guides/context-management) 以了解如何操作。
