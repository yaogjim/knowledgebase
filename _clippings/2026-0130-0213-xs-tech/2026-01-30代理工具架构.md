支撑代理内存的 Unix 文件系统命令简直令人惊叹……而且看起来也很有趣。

20 世纪 80 年代构建 CPU 内存层次结构，使内存看起来既无限又快速所面临的挑战，与当前的情况有着很强的相似性。

在 CPU 发展的早期，内存容量很小，CPU 之外的一切运行速度都很慢。缓存、RAM 和虚拟内存构建了一个层级结构，平衡了程序的运行速度和内存大小。Commodore 64 只有 64KB 的内存，整个程序都必须在这个限制内运行。后来，Intel 80486 在 20 世纪 80 年代末普及了片上缓存，使得频繁访问的数据看起来速度很快，而虚拟内存则让内存看起来几乎是无限的。对于代理程序来说，文件系统充当内存的角色，代理工具则在无限存储空间和返回可用上下文之间进行动态权衡，以便代理程序能够持续运行。

令人惊讶的是，我们仅使用少量 Unix 命令行工具（特别是 grep、ls 和 glob），就解锁了一种强大的代理内存形式。

过去一年，“文件系统+Unix”方案在 Cursor 和 Claude Code 等工具的成功中得到了充分体现。这些工具利用简单的 Unix 原语处理大量数据。我们尤其关注 Cursor 和 Claude Code（市场上两款领先的智能生产力工具）中对这种方案的运用，并将它们与我们用 Alyx 构建的系统进行了比较。

Claude 和 Cursor 的成果是智能体上下文和内存管理领域新兴标准技术的典范。它们借鉴了以往的经验，但实现方式却截然不同，而且令人着迷的是，这种方法并非自上而下的设计决策，而是源于智能体自身。接下来，我们将深入探讨这些具体技术及其工作原理。

在数据库或搜索引擎中，索引是一种预先计算的数据结构，它回答以下问题：“给定这个键/查询，数据在哪里？”

```

┌─────────────────────────────────────────────────────────┐
│  INDEX (pre-built)                                      │
│  ─────────────────                                      │
│  key → pointer to record/location                       │
│                                                         │
│  Example: B-tree index on "country" column              │
│    "Australia" → [row 12, row 98, row 455, ...]         │
│    "Canada"    → [row 3, row 7, row 22, ...]            │
└─────────────────────────────────────────────────────────┘
```

像“ls”、“find”、“grep”这样的命令没有预先构建的索引。相反，它们会在运行时进行扫描，并生成一个类似于索引的输出：

可以将跨度表预览视为索引。每个单元格中的截断文本为 LLM 提供有关底层上下文的提示，而跨度 ID 则充当指向完整上下文的指针。

我们尽量不删除任何列，以便 Alyx 可以从每个单元格中获取提示，然后根据需要查找 span ID。我们会删除一些行，以确保所有内容都能显示在上下文窗口中，Alyx 可以根据需要分页显示更多行。

Alyx 还提供了用于查找单个 span ID 的工具（类似于地址查找），以及用于获取更多数据页的工具。这遵循了代理的一般原则，即使用可组合的工具来访问不同级别的数据保真度。

为了兼顾实时查询 API 和基于过滤器的文件下载的速度，代理可以根据任务的复杂性，在远程查询和本地执行之间做出合适的权衡。我们认为这种模式将定义未来代理内存系统的构建方式：数据库为我们一开始讨论的无限上下文层次结构增添了一个新的环节。
