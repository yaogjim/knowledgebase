在课程、项目和期中考试之间，还有一整个你没人真正提醒过的额外工作层面。不是编程，不是学习，只是后勤工作。

寻找公司。弄清楚谁实际上在那里工作。查找电子邮件。研究每个人，让你的信息显得个性化。撰写一些深思熟虑的内容。重复十到二十次。

这是数小时的努力，却并不真正感觉像是在做工程，反而更像行政工作。

与此同时，我正支付高昂的学费学习计算机科学，然而大多数夜晚我却埋首于浏览器，同时打开二十个标签页。领英。公司网站。Hunter。Google。谷歌文档。复制。粘贴。研究。起草。重复。

所以我做了任何计算机科学专业的学生都会做的事。我试图将其自动化。

我使用 GPT 寻找公司。编写了小型脚本来抓取联系人。尝试了像 Hunter 和 Apollo 这样的工具。每一项都节省了几分钟。但它们都没有真正让我脱离这个流程。我仍然需要手动一步一步地安排所有事情。

如果这整个事情显然是一个工作流程，为什么我要执行它？

在某个时候，很明显这不是一个“更好的提示词”的问题。我不需要更智能的文本生成。我需要的是一种能够规划步骤、分配任务、并行处理任务，并且在我想要审批时能够暂停的系统。基本上，是一个真正的系统。

所以我没有编写另一个脚本，而是构建了一个代理管道。

那个项目成为 DeepReach，一个由 LangChain 的 Deep Agents 驱动的 CLI。

DeepReach 只是一个命令行界面。没有仪表盘。没有浏览器插件。你只需填写一次表单进行初始化，然后运行一个命令：

[

![Image](https://pbs.twimg.com/media/HAvz8BvaUAAGl2j?format=jpg&name=medium)



](https://x.com/LangChain_JS/article/2020980499276235222/media/2020977070390792192)

1.  搜索相关公司
    
2.  暂停并向你展示待审批列表
    
3.  并行处理每个已批准的公司
    
4.  将所有结果写入磁盘
    

审批步骤是经过深思熟虑的。在代理消耗 API 额度进行研究和联系人查询之前，你会收到一个检查点来引导它。如果你说“更多早期初创企业”或“更多基础设施相关”，它会再次搜索。一旦获得批准，每个公司将独立运作。对于每一家公司，代理将：

-   研究公司的业务
    
-   查找工程联系人
    
-   查询每个人
    
-   起草一封简短的个性化电子邮件

打开 drafts.json，你会看到一个已完整撰写的电子邮件列表，其中包含关于每封电子邮件如何进行个性化处理的备注。你可以编辑它们，进行合理性检查，然后在准备好后发送。

我的第一直觉是用一个基本的工具调用代理在单循环中构建它。这对于小型工作流来说运行良好。但这个流程有一些特性，会很快打破那些更简单的模式。

存在一个严格的依赖图。在找到联系人之前不能起草电子邮件，在选择公司之前不能找到联系人。因此，工作流程自然分为几个阶段：发现 → 审批 → 研究 → 起草。在单代理循环中，所有这些工作都会堆积到一个不断增长的上下文窗口中。中间工具输出和研究往往会泄露到后续步骤中，到了第三家或第四家公司时，代理开始将上下文混合在一起。隔离很重要。

然后是并行问题。依次处理公司很慢，每个公司大约需要30到40秒。如果有十个公司，你就得干等六分钟看着那个转圈的加载动画。但每个公司都是独立的，没有理由不并行处理它们。一个单一的循环会迫使所有事情都按顺序进行。我真正想要的是十个并行运行的工作线程。

我不想要一个完全自主的黑箱。如果代理选择了错误的公司或不相关的领域，我希望在它浪费时间和积分之前阻止它。基本循环会带来全有或全无的执行，没有检查点。我需要能够暂停工作流程，查看已找到的公司，然后继续。

系统还需要在多次运行间保持状态。如果我上周给某家公司发过邮件，下次运行时不应该再次联系他们。该信息必须在工作流退出并完成后仍然存在。无状态循环无法妥善处理这种情况。

总体上我需要几个关键要素：明确的阶段、公司之间的上下文隔离、并行执行、带有持久化状态的可恢复检查点。正是在这一点上，基本的代理循环开始失效，因此我转向了 DeepAgents。

如果你还没遇到过它，deepagents 是一个基于 LangGraph 构建的独立库。

它专为比单个提示循环更庞大的代理工作流而设计。这类系统需要规划、工具、状态和任务委派。例如 Claude Code 或深度研究型代理。

开箱即用，Deep Agents 为你提供三个基本原语：

-   规划： 内置的待办事项编写工具，使代理能够将复杂工作分解为明确的步骤。
    
-   文件系统：像 read\_file、write\_file、ls 和 edit\_file 这样的工具，由可插拔存储支持。
    
-   子代理生成: 一种任务工具，让主代理能够将工作委派给隔离的子代理。
    
-   后端层： 代理的状态实际存储的位置。这可以是本地文件系统（对命令行界面(CLI)和大量工件的工作流非常适用），或者 一个能够安全独立地执行代码和工具的沙箱环境。
    

创建 DeepAgent 会自动将所有这些连接起来：

我的项目主要是在这些基本构建块的基础上进行配置：定义工作流、定义一些领域工具，并让框架处理底层机制。让我结合项目中的实际代码，详细讲解 DeepReach 实际上如何使用这些基本构建块。

Deep Agents 在调用 createDeepAgent() 时会自动附加 FilesystemMiddleware，这为每个代理提供了开箱即用的 read\_file、write\_file 和 edit\_file 功能。在 DeepReach 中，这些工具直接指向您的本地磁盘。

所以当代理写入文件时，它只是在你的机器上写入一个普通文件。没有隐藏状态，也没有数据库。

工作区分为两个目录：runs/ 和 storage/。

[

![Image](https://pbs.twimg.com/media/HAv0q7QbUAAqug2?format=png&name=900x900)



](https://x.com/LangChain_JS/article/2020980499276235222/media/2020977876104073216)

runs/ 每次执行都会获得一个专属文件夹，其中包含该次执行过程中产生的所有内容：公司信息、联系人以及草稿邮件。由于所有内容都会保存到磁盘，您可以随时查看、编辑和发送邮件。每次执行都是工作流的一个干净且可检查的快照。

storage/ 是持久的。它在多次运行中保持持久，并充当内存。当编排器启动时，它会读取 storage/contacted.json 文件，以避免重新向相同的公司发送邮件。当一次运行完成时，它会追加新条目。这个单一文件成为一个简单的去重层，这意味着不需要数据库。

-   每次运行产物 → runs/<id>/
    
-   跨运行知识 → 存储/
    

不需要数据库。目录结构本身就划分了边界。它的基础设施很简单，文件易于检查、调试和版本控制。

> 一次运行如下所示：Orchestrator 发现 8 家公司 8个公司代理生成 42个接触代理生成 已撰写 42 篇草稿

这听起来可能有点小题大做，但它解决了两个非常实际的问题。

每个代理只能看到与其任务相关的信息。编排器永远不会看到原始搜索数据或冗长的联系人列表。公司代理永远不会看到其他公司。联系人代理只能看到一个人。这实现了代理之间的“上下文隔离”，防止交叉污染并使令牌使用可预测。

当独立的工作流并发运行时，并行性会自然而然地产生。如果有十家公司是独立的，只需生成十个子代理即可。无需自定义异步代码。编排器负责委派任务，每个子代理独立运行，并在完成后进行汇报。这是系统感觉运行快速的主要原因。

深度代理让子代理保持简单，因为子代理只是另一个代理图。在实际应用中，使用 createDeepAgent()创建的任何内容本身都可以作为子代理传入，因此你可以通过其他深度代理来组合深度代理，而不必连接自定义中间件或委托逻辑。这就是我在这里使用的方法：编排器是一个深度代理，公司流程也是一个完整的深度代理，并且它反过来会生成联系人个性化代理。每一层都定义自己的提示词和工具，并且由于每个深度代理都已包含任务工具，嵌套委托会自动生效。

完全自主听起来不错，但对于这个工作流程来说，这不是个好主意。

公司发现过程存在噪声。如果代理选择了质量差或不相关的公司，你会在每个公司上浪费时间和下游的 API 额度。因此，编排代理会在进行高成本工作前暂停，并让用户审核公司列表。Deep Agents 通过 interruptOn 支持这一点。

当编排器调用 review\_companies(companies) 时：

1.  执行暂停
    
2.  状态已被检查点化
    
3.  CLI 显示公司列表
    
4.  你批准或提供反馈
    
5.  代理恢复
    
6.  如果被拒绝，编排器再次搜索，找到新的公司，并再次调用 review\_companies（形成一个循环直到获得批准）
    

最初让我感到惊讶的一个设计决策是，系统的行为中有多少部分存在于提示中。

系统提示类似于架构规范。它们编码阶段、顺序、检查点和委托规则。运行时执行该图，但提示定义了必须发生的事情及其顺序。我没有编写编排代码，而是以声明式方式描述工作流。

[

![Image](https://pbs.twimg.com/media/HAv1_wMaQAAj7NE?format=png&name=900x900)



](https://x.com/LangChain_JS/article/2020980499276235222/media/2020979333423316992)

在这里，任务是关键原语。它生成一个具有独立上下文和自身工具的子代理，使其独立运行，然后将结果返回给父代理。因此，这个提示词起到了契约的作用：

-   阶段定义顺序
    
-   所需工具定义检查点
    
-   多个任务()调用定义了并行性
    
-   文件写入定义状态
    

没有自定义异步代码或手动扇出。代理发出多个 task() 调用，运行时并发执行这些调用。并行完全由提示驱动。相同的模式适用于更低的层级：

-   公司流程: 研究公司 → 获取联系人 → 生成联系人任务
    
-   联系人个性化: 调研一个人 → 撰写一封电子邮件
    

每个代理都有狭窄的职责范围和明确的责任。该系统不再是一个大型通用循环，而是由小型工作单元构成的层级结构。

Deep Agents 支持技能，这些技能是可重复使用的领域专业知识提示包，以

文件形式存储，代理仅在相关时加载这些文件。与将所有指令塞进系统提示不同，技能是按需调用的。这降低了 token 使用量，使行为更专注。

我在联系人个性化中使用这个来处理防幻觉规则。起草指南包含在冷邮件撰写技能中。这包括代理在没有证据的情况下不能声称的内容、允许来源的等级排序、安全的备用钩子以及示例模板。

代理仅在实际撰写电子邮件时加载此技能，而非在早期研究阶段。

主要优势是能够切换。我可以为不同的外展策略定义多种技能。例如，一种使用更柔和语言的咨询型外展技能，或一种强调共享技术的技术型外展技能。代理根据用户的语气偏好选择合适的技能，无需重写提示词。

构建完这个之后，主要的结论很简单：我不需要编写太多基础设施代码。没有自定义调度器。没有作业队列。没有异步编排。没有数据库。没有状态机。

并行执行、上下文隔离、文件系统工具、暂停和恢复，这些都来自 Deep Agents。我的工作只是定义工作流阶段、一小套领域工具以及指定职责的提示词。其他所有事情都由 Deep Agents 处理。

最终，DeepReach 并不真的是关于冷联系或寻找实习机会。它只是一个更广泛模式的便捷示例。它反映了真实团队的运作方式：协调者将任务分配给专家，而专家在需要时会进一步分解工作。这种结构清晰地映射到代理系统，因为它使职责范围狭窄且上下文范围小。

当一个问题看起来像是一个包含独立任务和偶尔人工检查点的多步骤工作流时，这种方法就很自然地适用。与其说是精心设计更智能的提示词，不如说是设计一个恰好使用语言模型的分布式、明确的系统。
