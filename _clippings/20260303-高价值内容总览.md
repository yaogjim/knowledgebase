## 🏗️ Agent 基础设施

### [[2026-03-03_Ashpreet_Bedi_Ashpreet_Bedi_智能体软件工程_注意_这篇文章是关于构建你自己的代理_代 | 智能体软件工程]] @Ashpreet Bedi
**来源**: Agno 创始人 | **标签**: #AgentOS #分布式系统 #生产环境

Agno 创始人 Ashpreet Bedi 深入论述如何将 Agent 作为生产服务构建和扩展，强调"构建智能体很容易，有 75 个框架可以帮助你，但难点在于运行时"。

**背景问题**: 大多数人认为 Agent 就是"循环中的提示 + 工具"，但这并非生产环境架构。当 Agent 需要知道与谁交谈、维护状态、处理并发请求、执行敏感操作以及在工具调用失败时生存，它就不再是"LLM + 工具"，而变成了分布式系统。

**核心洞察**:
- **Agent 六大支柱**:
  1. **持久性**: 跨步骤推理、暂停/恢复/检查点、优雅故障恢复而非完全重启
  2. **隔离性**: 每用户独立会话/内存/上下文，数据库、向量存储、模型提供商都必须尊重用户边界
  3. **治理**: 三层授权机制——自动执行工具 → 用户确认工具 → 管理员审批工具
  4. **持久化**: 会话、记忆、知识存储到数据库，使聊天机器人成为真正产品
  5. **可扩展性**: 围绕无法控制的外部依赖（模型 API、第三方工具）进行扩展
  6. **可组合性**: Agent 作为服务被其他 Agent、前端、Slack 机器人、MCP 客户端调用
- **核心理念**: "构建 Agent 是 AI 工程，运行 Agent 是软件工程，两者结合构成 Agent 软件工程"
- **AgentOS 模板**: 容器化服务，含 Postgres 持久存储、知识 Agent(Agentic RAG)、MCP Agent(外部工具)、REST API

**实践代码**: 三层授权示例
```python
support = Agent(
    tools=[
        lookup_order,        # 自动执行
        search_help_docs,    # 自动执行
        issue_refund,        # 需要用户确认
        UserFeedbackTools(), # 结构化问题
    ]
)
```

### [[2026-03-03_Lance_Martin_Lance_Martin_给克劳德一台电脑_TL_DR_程序化工具调用_PTC | 程序化工具调用 PTC]] @Lance Martin
**来源**: X/Twitter | **标签**: #PTC #Claude46 #工具调用 #性能优化

Claude Opus/Sonnet 4.6 中的 Programmatic Tool Calls(PTC) 功能详解——让 Claude 编写代码在容器内协调工具调用，而非每次工具调用都经过 Claude 的上下文窗口。

**传统工具调用的问题**: 每次工具调用都会将结果序列化到上下文（即使下一步只需五行数据，也传递数千行），增加延迟并引入额外推理步骤。组合成本随操作数量增加而增加。

**PTC 工作原理**:
1. Claude 定义工具并编写代码将它们组合成函数
2. 代码在容器中执行，调用工具时（如 `await web_search(query)`）容器暂停
3. 工具调用以类型化工具使用事件形式跨越沙箱边界，由处理程序/MCP 服务器处理
4. **关键区别**: 结果返回给正在运行的代码，而非 Claude 的上下文窗口
5. 代码按 Claude 指定的控制流处理结果（调用另一个工具、过滤数据、累积结果）
6. 只有最终输出到达 Claude

**核心洞察**:
- **性能提升**: 输入 token 减少 **24%**，搜索基准准确率提升 **11%**
- **代码可组合性**: Claude 可在代码中表达分支、循环、提前返回（而非线性工具调用链）
- **动态滤波**: 以编程方式解析、筛选和交叉引用结果，保留相关信息，丢弃其余
- Opus 4.6 + PTC 在 LMArena 搜索竞技场排名第一
- PTC 已内置于网络搜索工具，API 调用自动优化

**适用场景**:
- UX: AskUserQuestion 工具捕获特定操作并呈现给用户
- 安全防护：文件编辑工具运行过期检查验证文件是否已更改
- 并发控制：只读工具并行运行
- 可观测性：隔离特定操作进行日志记录
- 自主性：按自主级别分组操作，可撤销的操作可更自由批准

### [[2026-03-03_Dan_Farrelly_Inngest_com_Dan_Farrelly_Inngest_com_你的经纪人需要的是工具_而不是框架 | Agent 基础设施与 Inngest]] @Dan Farrelly | Inngest.com
**来源**: X/Twitter | **标签**: #Inngest #基础设施 #事件驱动

使用事件驱动的持久化基础设施（Inngest）而非 Agent 框架构建 Agent——每个 LLM 调用和工具执行都成为可独立重试的持久化步骤。

**核心类比**: 线束（Wiring Harness）在工程中的角色——连接、保护和协调各组件但自身不执行工作。汽车线束连接发动机、传感器和仪表盘；测试线束提供代码可重复运行框架；安全带在跌倒时保护。Agent 运行时需要同样的东西。

**问题陈述**: 每个 Agent 框架都在从零开始构建基础设施——自己的重试逻辑、状态持久化、任务队列、事件路由。但这些都是已解决的问题。

**核心洞察**:
- **基础设施即框架**: 持久化的事件驱动基础设施已解决重试、状态持久化、并发、事件路由问题
- **步骤化执行**: 每次 LLM 调用或工具调用成为独立可重试的工作单元
- **故障恢复**: 流程在第五次迭代终止时，前四次迭代数据已持久化可恢复
- **事件路由**: 事件在函数之间路由触发器，标准"思考→行动→观察"循环
- **并发控制**: 防止消息冲突，单一并发确保每个会话一个 Agent
- **可观测性**: 步骤级跟踪可全面观察 Agent 循环的每一次迭代

**Utah 框架验证**: 通用触发代理框架，可与 Telegram/Slack 对话，具备工具、内存、子 Agent 委托和完全持久性。使用极简 TypeScript 的 trigger 函数、step 和 event，无需任何 Agent 框架。可视为"持久耐用、可部署云端的 OpenClaw"。

### [[2026-03-03_Nav_Toor_Nav_Toor_17_项最佳实践让_Claude_Cowork_的效能提升_100_倍 | Claude Cowork 17 项最佳实践]] @Nav Toor
**来源**: X/Twitter | **标签**: #Cowork #最佳实践 #上下文架构

Nav Toor 在 7 周 400+ Cowork 会话中总结的 17 项最佳实践——覆盖上下文架构、任务设计、自动化、插件、安全，按影响程度排序。

**核心理念**: "ChatGPT 奖励提示工程，Cowork 奖励系统工程"。真正决定产出质量的是围绕提示构建的上下文、结构、技能和约束，而非提示本身。

**第一部分：上下文架构**（实践 1-5）

1. **`_MANIFEST.md` 文件**: 告诉 Claude 哪些文档是权威来源
   - 第一层：权威文档（品牌指南、项目简报、战略文档）
   - 第二层：域映射（`/pricing` → 定价模型，`/research` → 竞品分析）
   - 第三层：存档（旧草稿、被取代版本，除非明确要求否则不加载）
   - 下划线前缀确保文件名显示在文件夹顶部

2. **Global Instructions**: 永久操作系统，适用于所有会话
   - 在所有文件、提示词甚至 Claude 查看文件夹之前加载
   - 示例："我是 [姓名][角色]。启动任务前先查找 `_MANIFEST.md` 并阅读第一层文件。执行前务必提问。行动前提供简要计划。默认输出 .docx。"

3. **三个持久上下文文件**:
   - `about-me.md`: 职业形象、当前工作重点、优秀案例
   - `brand-voice.md`: 语气描述、用词偏好、实际写作示例
   - `working-style.md`: 协作规则、默认格式、质量标准、避免事项
   - 每周改进，每次 Claude 写出不满意内容时添加规则

4. **文件夹说明**: 项目特定规则（客户名称、目标、术语、交付格式、截止日期）

5. **刻意缩小上下文范围**: 更大上下文≠更好输出，精心设计的上下文管理是稳定结果的关键

**第二部分：任务设计**（实践 6-10）

6. **定义最终状态而非过程**: 错误—"整理文件"；正确—"按客户名称整理到子文件夹，YYYY-MM-DD-描述性名称格式，创建摘要日志，不删除任何文件，不确定放入/needs-review"

7. **执行前索取计划**: 一行代码避免 90% 灾难，"执行前提交简要计划，等待批准"

8. **不确定性处理**: "日期不明确标记'待核实'，文件可放多文件夹放入'需要审核'，把握不足 80% 标记不猜测"

9. **批量相关工作到单个会话**: 减少启动成本，任务间共享上下文

10. **并行子代理**: "启动子代理并行处理这些任务"，四供应商研究从 40 分钟缩短到 10 分钟

**第三部分：自动化**（实践 11-13）

11. **`/schedule` 命令**: 每日/周/月自动任务（周一早间简报、周五状态报告、每日竞品追踪）

12. **外部化到文件**: Cowork 无记忆，将偏好、计划、SOP、决策全部外部化到文件

13. **`/schedule` + 连接器**: Gmail/Slack/Drive/Notion/Asana 实时数据自动化

**第四部分：插件和技能**（实践 14-16）

14. **插件堆叠**: 数据分析 + 销售插件组合，单工作流使用多领域功能

15. **自定义技能**: Markdown 文件定义用途、输入、流程、输出、约束

16. **对话式构建插件**: 插件管理插件辅助创建，无需代码/GitHub/Markdown 语法

**第五部分：安全**（实践 17）

17. **尊重权力**: 备份文件、隔离敏感文件、"不删除"约束、监控前几次运行、警惕 prompt 注入

**实施清单**:
- 今天（30 分钟）: 三个上下文文件 + 全局指令
- 本周：`_MANIFEST.md` + 2-3 个插件 + 一个定时任务
- 本月：第一个自定义技能 + 子 Agent 复杂任务

### [[2026-03-03_Ankit_Jain_如何扼杀代码审查_Ankit_Jain_著_Latent_Space_How_to_Ki | 代码审查的终结]] @Ankit Jain
**来源**: Latent.Space (Aviator CEO) | **标签**: #代码审查 #意图审查 #BDD #规范驱动

Ankit Jain 论证 AI 团队应从"代码审查"转向"意图审查"——人类在代码生成前定义验收标准，而非生成后审查代码。

**数据驱动问题**: 来自 1255 个团队 10000+ 开发者的数据显示，AI 应用程度高的团队：
- 完成任务数量 **+21%**
- 合并 PR 数量 **+98%**
- 但 PR 审核时间 **+91%**

**根本矛盾**: 两件事正指数级增长——变更数量和变更规模。我们根本无法处理如此庞大的代码量。开发人员抱怨审查 AI 生成代码比审查同事代码更耗时。

**核心论点**:
- **代码审查是过时的审批流程**: 从瀑布式验收→持续集成，现在应迁移到"规范驱动"
- **PR 后审查的局限性**: "新鲜血液"只是另一个有盲点的 Agent，价值在迭代循环而非审批环节
- **规范成为真相源**: 代码成为规范产物，审查步骤/验证规则/契约而非 500 行 diff

**五层信任体系**（瑞士奶酪模型）:

1. **比较多个选项**: 让三个 Agent 尝试不同方法选最佳，按通过验证步骤数量、差异最小、不引入新依赖排序

2. **确定性护栏**:
   - 编码规范（自定义检查器）
   - 组织不变规则（禁止硬编码凭证）
   - 领域合约（支付领域：所有金额用 Money 类型）
   - 验收标准（特定任务）
   - 验证步骤在写代码前定义

3. **人类定义验收标准**（BDD）:
   - 规范是主要成果，Agent 负责实现
   - "验收标准由人制定，由机器验证"
   - 人类价值在上游定义"正确"含义

4. **权限架构**:
   - 细粒度权限（修复 bug 的 Agent 不应访问基础设施配置）
   - 升级触发器（修改认证逻辑/数据库 schema/新依赖自动标记人工审核）

5. **对抗性验证**:
   - 职责分离：编码 Agent 不知验证 Agent 检查什么
   - 红队/蓝队自动化，每次变更运行

**金句**: "我们无法靠阅读胜过机器——我们需要在上游思考，在决策真正起作用的地方"、"未来是快速出海、观察一切、快速回溯"

### [[2026-03-03_Graham_Neubig_Graham_Neubig_我非常喜欢我们为改进生产环境中的_SKILL_md_文件而制定的 | SKILL.md 文件工作流]] @Graham Neubig

**核心问题**: 对于编码 Agent，技能是自动化重复工作流程的好方法，但如何在生产环境中持续改进这些技能？

**四步流水线**:

1. **记录**（Log）:
   - 保存完整的 Agent 执行轨迹

   - A/B 测试不同提示词/流程

   - 生产环境实时跟踪技能表现
   - 检测性能下降或异常模式
   - 建立告警阈值

4. **改进**（Improve）:
   - 基于评估数据迭代技能
   - 将成功案例添加到技能文档
   - 修正失败模式

**关键洞察**:
- 技能评估需要真实用户反馈信号（如代码审查接受率）
- 记录完整轨迹便于调试和归因分析
- 生产环境技能需要持续维护而非一劳永逸

### [[2026-03-03_manjeet_singh_苹果 M4 神经网络引擎内部结构_第一部分_逆向工程_Inside_the_M4_Appl | Apple M4 神经网络引擎逆向工程]] @manjeet_singh
**来源**: X/Twitter | **标签**: #Apple #ANE #逆向工程 #硬件黑客

maderix 成功绕过 CoreML 直接编程 Apple M4 的 Neural Engine(ANE)，并揭示了大量硬件细节。

**核心发现**:

1. **ANE 本质是卷积引擎**:
   - 并非矩阵乘法引擎
   - 将矩阵乘法重写为 1x1 卷积可获得 **3 倍** 吞吐量
   - 这是性能优化的关键洞察

2. **内存架构**:
   - ~32MB SRAM 每核心
   - 16 核心流水线架构
   - 内存带宽是关键瓶颈

3. **性能真相**:
   - "38 TOPS INT8"是营销数字
   - 实际峰值：**19 TFLOPS FP16**
   - INT8 只是将 INT8 反量化为 FP16 计算

4. **功耗管理**:
   - 硬件电源门控
   - 空闲时真正 **0mW** 功耗
   - 比软件控制的功耗管理更高效

5. **推理优化**:
   - 127 级队列深度用于流式推理
   - 支持连续推理任务无间断执行
   - 通过 `_ANEInMemoryModelDescriptor` 直接内存编译

**技术突破**:
- 绕过 CoreML 直接调用 ANE

### [[2026-03-03_Andrew_Altshuler_Andrew_Altshuler_nanograph_面向智能体和人类的设备端图数据库 | nanograph - 设备端图数据库]] @Andrew Altshuler
**来源**: X/Twitter | **标签**: #图数据库 #本地优先 #Agent 内存 #嵌入式

Andrew Altshuler（前 Graph Databases 专家）构建的 nanograph——本地优先、代码即模式的图数据库，专为 Agent 工作流设计。

**问题陈述**: 传统图数据库对 Agent 工作流过于笨重——服务器、Docker、缓慢的 MCP、模式维护地狱。它们是云优先的企业单体架构。

**设计灵感**: "如果图数据库像 SQLite/DuckDB 一样——打开、查询、完成——但类型、迁移和人体工程学都为 Agent 构建，会怎样？"

**五大支柱**:

1. **设备端**（On-device）:
   - 数据库是文件夹而非服务
   - `<name>.nano/` 文件夹即可复制、git 打包、加密
   - 无服务器、无 Docker、无网络配置

2. **零配置**（Zero-config）:
   - 开箱即用，无需复杂设置
   - 适合快速原型和迭代

3. **代码即模式**（Schema-as-code）:
   - 模式定义为代码而非外部配置
   - 模式强制执行防止 Agent 创建的边出现语义漂移
   - 类型安全的图操作

4. **时间机器**（Time Machine）:
   - CDC（变更数据捕获）+ 事件溯源
   - 完整历史追溯能力
   - Agent 可查询历史状态

5. **强大搜索**（Powerful Search）:
   - 全文搜索 + 语义搜索 + 混合搜索
   - 适合 Agent 记忆检索

**nanoQL**: Datalog 语义 + GraphQL 语法的查询语言

**应用场景**:
- Agent 内存管理
- 项目上下文构建
- 复合知识库
- 可放入代码库的图数据库

### [[2026-03-03_宝玉_宝玉_设计流程已死_Anthropic_设计负责人_Jenny_Wen_谈_AI_时代的 | 设计流程已死 - Jenny Wen 访谈]] @宝玉
**来源**: Lenny's Podcast | **标签**: #设计 #Anthropic #AI 时代 #招聘

Anthropic Claude 设计负责人 Jenny Wen（前 Figma 设计总监，主导 FigJam 和 Slides 从 0 到 1）谈 AI 时代的设计转型。

**背景**: Jenny 目前主导 Claude Co-work 的设计工作，加入 Anthropic 前是 Figma 设计总监，更早任职于 Dropbox、Square、Shopify。

**五大议题**: 传统设计流程为何走到尽头、AI 实验室设计工作感受、AI 是否取代人类品味、Co-work 设计过程、当前招聘策略。

**核心洞察**:

1. **设计师时间分配剧变**:
   - 设计时间：60-70% → 30-40%
   - 工程协作：20% → 30-40%
   - 新增：自己写代码
   - 经典"发散 - 收敛 - 发散 - 收敛"流程被工程速度倒逼

2. **愿景规划压缩**:
   - 从 2-5 年压缩到 3-6 个月
   - AI 加速产品迭代周期
   - 长期规划变得不切实际

3. **三类设计师招聘策略**:
   - **多面手**（Square）: 多领域 80 分，适应快速变化
   - **T 型专家**: 一专多能，深度 + 广度结合
   - **工艺导向新人**: 专注设计工艺的新毕业生
   - "硬的不是构建软件，而是人类关于构建什么的分歧"

4. **AI 与设计的关系**:
   - AI 不会取代品味和判断力
   - 人类价值在于定义"什么是好"
   - AI 加速执行，人类定义方向

5. **Co-work 设计过程**:
   - 设计与工程深度协作
   - 设计师直接参与代码实现
   - 快速迭代验证设计假设

### [[2026-03-03_Han_Qin_Han_Qin_AI 的天花板不是一层_是三层_但整个行业都卡在第一层_AI 的天花板到底在 | AI 的三层天花板]] @Han Qin
**来源**: X/Twitter | **标签**: #AI 理论 #扩展定律 #多模态 #架构创新

Han Qin 提出 AI 进展的理论框架——将 AI 进步类比为数系扩展：整数→有理数→无理数→虚数。

**理论框架**:

**天花板 1：参数扩展**（如 Rational 数逼近π）
- 增加参数数量提升性能
- 边际递减是结构性的，非缺陷
- 类似有理数可以无限逼近π但永远达不到
- 行业投资绝大部分集中在此

**天花板 2：架构变革**（如 Irrational 数填补空白）
- Transformer 是典型代表
- 填补有理数（传统架构）无法到达的空白
- 质的飞跃而非量的积累
- 历史案例：CNN→Transformer

**天花板 3：多模态**（如 Imaginary 虚数）
- 添加正交维度
- 2D 视觉、3D 视频、时序音频
- 扩展问题空间而非解决问题
- 类似虚数扩展实数轴到复平面

**核心洞察**:
- "AI 的天花板不是一层，是三层，但整个行业都卡在第一层"
- 天花板 1 投资过剩，天花板 2 和 3 有更多增长空间
- 参数扩展的边际递减是数学结构决定的
- 真正突破来自架构变革或维度扩展

**投资启示**:
- 关注架构创新（天花板 2）
- 关注多模态融合（天花板 3）
- 警惕纯参数扩展项目的长期价值

## 🤝 多 Agent 系统

### [[2026-03-03_凡人小北_凡人小北_这篇文章提供了一个新思路_当你真的需要多_Agent_协作时_怎么做才不会变成差 | 多 Agent 文件系统协作]] @凡人小北
**来源**: X/Twitter | **标签**: #多 Agent #文件系统 #协作模式 #无魔法

凡人小北分享的简单而强大的多 Agent 协作方案——用文件系统作为协作层，一个 Agent 写文件，其他 Agent 读取。

**核心问题**: 当你真的需要多 Agent 协作时，如何避免"差生文具多"的困境？

**解决方案**:
- **协作层**: 磁盘上的 markdown 文件
- **工作流**: 一个 Agent 写文件，其他 Agent 读取并基于此继续工作
- **信息丰富化**: 模型不会自动变聪明，但它周围的文件会越来越丰富

**实验数据**:
- 作者用 8 个 Agent 运行 40 天
- 使用同一模型
- 产出质量天差地别
- 关键变量：文件系统的组织和丰富程度

**核心洞察**: "多聊"——让 Agent 通过文件持续交流，每个 Agent 的贡献都沉淀为后续 Agent 的上下文。

**作者实践**: "我的 AI 采用多 skills + 多 subagent + swarm ccg，但基础一样，全是文件，没有魔法。"

**与复杂框架对比**:
- 无需复杂的 Agent 通信协议
- 无需中央协调器
- 文件即状态，文件即历史
- 可调试、可追溯、可恢复
