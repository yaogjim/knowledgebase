### Cursor 的起源故事：从 3D CAD 到 AI 编码

**Martin Cassada:** 好的，太好了。我们从一点历史开始。我最近见了一家公司，他们进来说：“我们是 3D 领域的 Cursor。” 我说：“真有趣，因为 Cursor 曾经也是一家 3D 公司。” 是这样吗？

**Michael Truell:** 是的。

**Martin Cassada:** 你介意谈谈公司的起源故事吗？

**Michael Truell:** 当然。实际上，有很多不同的方式来定义我们的起始日期。但基本上，公司是这样开始的：我和我的联合创始人们是学校和其他地方的亲密同事。有两个时刻让我们对创办公司感到非常兴奋。

第一个是尝试了首批真正有用的 AI 产品，特别是尝试了 GitHub Copilot，也就是我们这个领域的“现任者”。这让我们兴奋的原因是，这些产品“真的有用”。这是第一个存在证明，表明 AI 不应该只待在实验室里，现在是时候在现实世界中构建系统了，并且你可以做真正有用的事情。

第二个让我们兴奋的是“规模法则”（scaling laws）。我们对这样一个事实感到兴奋：即使这个领域（AI）的想法枯竭了，模型似乎也会变得更好。这大约是在2021年到2022年初。

然后，Cursor 或多或少是来自一次白板讨论。我们当时对为许多不同领域构建一个“Cursor for X”（某个领域的Cursor）感到非常兴奋。这是什么意思呢？我们当时认为，对于许多不同的知识工作垂直领域，都会有一家公司来自动化该领域的工作，每个领域都有一家。

这家公司会做几件事：首先，它会为该领域打造最好的产品。随着 AI 的成熟和进步，它将重新定义该知识工作的实际形态。然后，凭借该产品，它将赢得“分发渠道”（distribution），赢得庞大的业务，并获得数据和资本等资源。接着，它会回归到某种更像“实验室”的东西——虽然不是基础模型实验室——它会开始利用它获得的数据，来研究底层模型，推动该领域的“自主性”（autonomy）。这反过来又会推动产品向前发展，改变最佳产品的形态。你就得到了这样一个飞轮。

我们对此非常非常感兴趣。我们当时认为微软会为“编码”领域做这件事。而我们想在一个“沉睡的”、竞争不那么激烈的领域工作。我们有一些同事是做机械工程的，我们对 CAD 系统很熟悉。所以，最初有一个“错误的开始”，我们实际上是去研究机械工程，研究“机械模型”（mech models），帮助人们在 CAD 系统中提高生产力，并且我们也在构建自己的 CAD（系统）。

这就是我们开始的方式。这是个坏主E意。我们的“创始人市场契合度”（founder-market fit）糟透了。存在一个“盲人摸象”的问题，我们会和机械工程师（mechis）通电话，问他们白天都做什么。我们从来没有真正对它有一个直观的感觉。我甚至希望，在我们研究那个方向的六七个月里，我们能去一家公司当实习生，真正了解那个领域。

但最终，我们把那个想法放在一边，回到了我们真正最感兴趣的事情上，那就是“编程”。

### 早期成功关键：极度专注

**Martin Cassada:** 我有一个理论，不知道你是否认同，关于为什么 Cursor 在早期做得这么好。这个理论其实很平庸。当时我们正在调研这个领域，有很多公司在做很多不同的事情，很多都非常“科幻”，比如“我们要创造一个能成为软件工程师的智能体”，或者“我们要用这种新技术创建一个模型”，或者“我们要重写编辑器”等等。

我的理论之一是，Cursor 早期之所以成功，是因为你们**极度专注**。你们选择了 VS Code，当时 Copilot 已经培育了市场好几年。你们（Cursor）提供的是一个狭窄但**好得多的产品**。

所以我的问题是：A）你认为这个观点合理吗？B）当其他所有人都在做“所有事情”时，你们是如何决定并保持专注的？因为那正是构建智能体或构建模型的“黄金时代”。

**Michael Truell:** 是的，我绝对认为你说的很有道理。但同时，也有一个重要的“星号”*，那就是这家公司的故事“仍有待书写”，未来还有很多事情要做。

**Martin Cassada:** 当然，当然。我的意思是达到目前这个阶段的成功，已经有了这样的上升势头。

**Michael Truell:** 是的。回到我们做 CAD 的时候，那个领域的“冷启动”问题比我们现在这个领域要困难得多。要想开始帮助人们提高生产力，建立他们要在现实世界中制造的东西的机械模型，那些“开箱即用”的模型没有一个擅长这个。实际上，当时没有好的 3D 表现形式，也没有开源的 3D 模型可以迁移学习。

如果你采用现有的基于文本的 LLM，试图让它们擅长 CAD，它们也做不到。因此，我们花在 CAD 想法上的大量时间，除了和我们根本不理解其日常工作的机械工程师打电话之外（这显然是个大问题），我们还花了很多时间在“建模工作”和“数据抓取工作”上。

当我们决定放弃它并转向编程时，我们对此（建模和数据）有点“创伤后应激障碍”（PTSD）。所以，是的，最初我们超级专注，我们超级“权宜”，我们做了一个又一个的“hacks”（临时方案），只为尽快把东西推向世界，并开始获得一些动力。

部分原因是，我们当时没有……我们有一些资金，但和今天的种子轮融资完全没法比。我们有四个联合创始人，我们谈论过招聘和扩大团队，但我认为我们当时仍在学习如何做到这一点。

是的，当时的竞争格局是微软和几十家创业公司。这些创业公司分为几类：有些试图立即构建大型基础模型；有些则有“高流动性”的产品创意，试图彻底改变人们的工作流程。

而我们，只是想尽快推出一些东西。我记得当时，对我们来说，像“承诺装置”（commitment device）一样的东西是每月的“投资者更新报告”——尽管当时可能根本没人读。从决定做 Cursor 的第一天起，我们花了几周时间做出了一个我们自己会用的 IDE。最初我们甚至没有“fork”（复刻）VS Code，我们实际上是“从头开始构建”的。我们从零开始构建了一个 IDE，作为我们自己的日常驱动。又花了几周时间，我们把它交到了其他人手中。然后，总共在几个月的时间里，我们向互联网发布了第一个 Beta 版。

它立刻引起了人们的兴趣。然后，你知道的，这股势头就开始了。

**Martin Cassada:** 具体来说，当势头正在形成时，同一领域的许多其他参与者正在迅速“扩大范围”，比如他们很快就去做 CLI（命令行界面），或者集成到 IntelliJ（另一款IDE）。而你们决定不这样做。这是非常刻意的吗？还是说你们只是在正确的方向上获得了足够的牵引力，有足够多的工作要做了？

**Michael Truell:** 那些（战略）想法是刻意的。我们几乎所有时间都在工作。四个联合创始人，每天的早餐、午餐和晚餐，你们会谈论什么呢？你会无休止地辩论这些核心战略问题：你是应该构建一个编辑器还是一个扩展？你是否应该在模型方面做点什么？

我们非常非常刻意地想要“拥有那个界面”（own the surface）。在当时，这（做编辑器）还不是一个主流看法，但人们就是觉得做编辑器很奇怪，不管是不是 fork。他们说：“你不可能让人们切换他们的代码编辑器，他们的（使用）惯性太强了。”

但我们知道这是错的。因为我们自己就是因为 Copilot 而切换到 VS Code 生态系统的。我们之前都是使用命令行 Vim 的顽固分子。所以我们知道，如果你造出了一个“更好的捕鼠器”，你是可以让人转换过来的，只是这个门槛会很高。

然后，是的，我们非常刻意地决定，我们“未来”想要触及模型方面的工作——这背后有一整套故事，而且它确实已经成为我们一个非常重要的产品杠;杆——但我们不想从那里开始。我们只想先把东西推向世界，暂时不碰任何建模的东西。

### 应对“疯狂”的规模增长

**Martin Cassada:** 我跟你讲过这个轶事，但你说你不记得了，但我记得很清楚。早期是关于“规模”的。我这30年来见过很多公司，但我从未见过在这么小的团队下，规模增长如此之快的。

我记得有一天晚上，你给我打电话说：“听着，我们把某个‘大云服务商’搞垮了，因为他们无法处理我们的规模。” 当时出现了一个相对较小的服务中断，然后你们很快就修复了。但显然，在那段时间里，有人真的出现在了 Cursor 办公室，把一个 iPad 贴在窗户上，上面写着“Cursor 挂了”。

这对我来说很震惊，因为那是一个非常不起眼的建筑，他们居然找到了。所以，我很想听听你和团队是如何思考应对如此大的规模的？尤其是当你们甚至在给你们所依赖的平台（那些已经是最大的平台）施加压力时。

**Michael Truell:** 是的，那个轶事已经消失在众多（轶事）之中了。

早期，我们遇到规模问题的方式是：一个“极小的团队”在运营一个开始“飞速增长”的服务。我的联合创始人们非常出色，但（如果你们看不出来的话）我们并不是最有经验的团队——就工作年限而言。

所以很快，我们就有了大量的用户。特别是在我们有自己的文件同步系统之类的东西上……在 Cursor 内部，有一个类似“AI 搜索引擎”的东西。表面上听起来不应该那么复杂，但构建起来却很烦人。根据你构建它的方式，它肯定会开始给你依赖的系统带来压力。

我们很快就在“常规无聊的云服务”方面达到了一个很高的规模。这背后有一整套故事：我们当时运行着一个非常非常大的 Kubernetes 集群，比许多其他公司都大。然后，在公司总共只有五个人的情况下，我们试图“边飞边修”，解决各种问题和麻烦。

当我们通过做出一些正确的架构决策和增加团队，刚刚解决了这个问题时，下一个巨大的规模问题出现了：我们开始给“API 
提供商”带来了巨大压力。

解决这个规模问题，靠的不是在技术上非常聪明，而更多的是靠“关系”。我觉得那些 API 提供商真的不知道该拿我们怎么办。你知道，这四个二十几岁的年轻人，他们的业务现在占了他们 API 收入的“极高比例”的两位数百分比。现在，他们将不得不做出“容量规划”决策，甚至是“融资决策”，来处理（我们带来的）增长。

这更多的是关于……我认为我们仍在学习……与人建立关系。这也关乎到变得非常聪明，事实证明，你可以从许多不同的提供商那里获得相同模型的 API token。市面上有“token 经销商”。而且，将（需求）分散到多个有承诺合同的提供商，在战略上是很有帮助的。所以我们变得非常擅长在全世界搜寻所有存在的 Sonnet（一个模型）token。那是一个很棘手的规模问题。

现在，我们自己做相当多的“模型训练”和一些“模型推理”。所以，现在我们又面临着一个全新的规模问题。

**Martin Cassada:** 你认为这（基础设施）最终会趋向于依赖异构的第三方，还是会趋向于你们自己运行大部分基础设施？

**Michael Truell:** 对于我们的网站、桌面应用、后端这些东西，我认为我们从一开始就是“多云”的。所以我们绝对是在一条默认的、依赖多个提供商的异构路径上。我们有 Databricks、Snowflake，我们同时在用 AWS、GCP 和 Azure。我们用 PlanetScale 做数据库……

对我们来说，多个提供商在不同的事情上都很出色，所以这就是我们的计划。

### 从单一产品到多产品

**Martin Cassada:** 在谈论人才之前，最后一个问题。你必须平衡“专注”（你做得很好）和“多产品”扩张（你做了 Bugbot、CLI 和基础设施改进）。在多大程度上，这个（扩张）决策是“有机的”、“显而易见的”？在多大程度上，你们是以一种更“深思熟虑”的方式来确定优先级的？

**Michael Truell:** 这是非常深思熟虑的。我们努力对很多事情说“不”。但我确实认为，展望未来，我们需要成为一家“多产品公司”。我认为在我们的领域有一个巨大的多产品机会。有一整套“AI 编码捆绑包”有待构建，我们希望成为许多客户的“AI 编码提供商”。

到目前为止，我们都专注于这个“楔子”——也就是当你作为一名工程师在构建软件时，你所面对的那个“玻璃面板”，也就是“编辑器”。我们认为在那里还有很多事情要做，这是我们的主要焦点，也是我们投入资源的地方。

但我们也认为，编辑器内的工作方式正在发生变化，这也开始影响“团队”协同工作的方式。所以我们认为这既带来了一个巨大的战略机遇，也是为了拥有“最好的编辑器”所必需的补充——它（新产品）帮助团队更好地审查和协作。

所以我们对此是有意为之的。我们仍在学习如何把它做好。比如，如何为这样的项目提供“空中掩护”（支持），如何做“交叉销售”（cross-ell）。

**Martin Cassada:** 我得说，很多创始人低估了从单一产品到多产品在“走向市场”（go-to-market）方面的难度。这非常非常复杂。

**Michael Truell:** 是的，我们在那方面还有很多东西要学。但我们对早期的结果感到非常兴奋。

### 人才招聘：独特的“两日现场”试用

**Martin Cassada:** 我想转向人才话题。我认为你们拥有我见过的最严格、最深思熟虑的人才招聘流程之一。我试着把我的晚上和周末的一部分时间预留出来，帮你和候选人交谈、招募他们。在我加入每一次通话之前，我都会收到一份极其周到的（邮件），写着：“目前进展到哪里”、“我们做了什么”……这个流程背后一定有很多（思考）。你介意分享一下你是如何思考招聘、如何运作流程，以及你发现了什么有效、什么无效吗？

**Michael Truell:** （笑）让你的董事会成员多打几个电话，直到他们哭着求饶。利用好他们的时间。

嗯，我们是如何考虑招聘的。我认为在某些方面，我们的流程是相当“正统”的。但有一些可能是独特的。

其中之一是，通常当你是一家小公司时，对于第一批工程师，你会让他们以“合同工”的形式和你一起工作，你可能不会走常规的 LeetCode 风格的面试流程。我们也这么做了。这感觉最自然，因为你是在寻找“你是否能和这个人很好地合作”这个“地面真相”。

通常，人们在招聘了几个人之后就会停止这种做法。我们……我们曾多次试图在内部“扼杀”这个流程，我也试过……但我们“仍然”在这样做。

**每一个**被工程团队和设计团队录用的人，都必须在办公室待**两天**。他们会做一个项目。这非常自由，不像“你有一个白板面试，然后又一个白板面试，你这两天排得满满的”，而是：“这是一张桌子，这是一台笔记本电脑。这里有三个你可以做的项目。这是一个“冻结”的、较旧版本的代码库，开发环境已经搭好了。你去干吧。”

这有两个功能。第一个功能是，我认为这是一个非常好的测试，它测试了与我们在现场面试（on-site）前进行的“常规编码风格面试”所不同的东西（orthogonal things）。你可以看到：他们能在代码库中“端到端”地工作吗？他们有“能动性”（agentic）吗？我们的工程、设计和产品是紧密耦合的，所以我们试图招聘具有“产品感”的“产品工程师”。这能让你感觉到，如果把他们单独留在一个“真空”里，他们会做出什么。

这在“原始技术技能”方面给了我们很多信号。

第二个功能是……只是（为了看看）和这个人相处（hang out）的感觉。这也给了我们一个感觉：“我们想不想和你待在一起？你想不想和我们待在一起？”

第三个好处是，它给了候选人大量关于公司的信息，关于他们第一天来上班会是什么样子。我认为这也导致了他们那边的“契合度”非常高，如果他们最终选择加入的话。

这就是我们做的比较“非正统”的事情之一：我们有这个为期两天的“现场（试用）”，即使我们现在已经超过200人了，我们仍然坚持这样做。

**Martin Cassada:** 你们对“走向市场”（go-to-market）或其他（非技术）岗位也这样做吗？

**Michael Truell:** 我们最初也这样做。为了招聘我们的第一个销售代表，我们会给他们真实的“入站线索”（inbound leads）。

**Martin Cassada:** 哇，给他们一个配额（quota）。

**Michael Truell:** 是的。它会更有条理一些，比如他们会做一个演示，做一些模拟的客户沟通。但我们会给他们访问“真实数据”的权限，让他们去挖掘。我记得我们做的第一个，那个代表进来了，我们给他看了所有东西，然后说：“来教教我们该怎么做销售。”

### M&A（并购）战略：为获取最优秀的人才

**Martin Cassada:** 我认为这股（AI）浪潮正在改变关于如何建立公司的许多“正统观念”。你在这方面绝对处于最前沿。你让相对“初级”的人在管理非常大的组织，而且效果非常好。
