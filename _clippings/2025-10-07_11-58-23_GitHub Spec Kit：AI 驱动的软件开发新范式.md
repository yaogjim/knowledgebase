# **GitHub Spec Kit：AI 驱动的软件开发新范式**

大家好，今天我们要聊的是 GitHub Spec Kit，一个旨在利用 AI 让你更快、更好地构建高质量软件的新项目。在这个视频中，我们将深入了解 Spec Kit 是什么，它能做什么，工作原理如何，并尝试用它从零开始构建一个应用。

#### **颠覆传统：什么是规格驱动开发？**

你可以在 GitHub 的官方仓库中找到 Spec Kit，地址是 `github.com/github/spec-kit`。

当我们查看它的 `README` 文件时，首先映入眼帘的是它的核心理念：“**构建高质量软件，更快。**”

> 这是一个旨在让组织能够专注于产品场景，而不是编写无差异化代码的努力，其核心是借助**规格驱动开发（Spec-Driven Development）**。

那么，到底什么是规格驱动开发呢？

根据文档的解释，规格驱动开发**颠覆了传统的软件开发模式**。在过去几十年的开发流程中，“代码为王”，而规格说明（specifications）往往只是一个临时的脚手架，一旦真正的编码工作开始，它就会被丢弃。

而 Spec Kit 的理念则完全相反。它将**规格说明本身变成了可执行的（executable）**，可以直接生成可工作的代码实现，而不仅仅是起指导作用。

简单来说，过去我们是先有模糊的想法，然后开始写代码，在写的过程中不断迭代，最后再补上文档。而 Spec Kit 要求我们先定义好一切——**规格即是最终的资产**，代码只是这个规格的表达形式。我们作为开发者，更应该关注“做什么”（What）和“为什么做”（Why），而不是“如何做”（How）。

#### **快速上手：安装与初始化**

要开始使用 Spec Kit，你需要先安装一个名为 `specify` 的工具。

```powershell
uvx --from git+https://github.com/github/spec-kit.git specify init <PROJECT_NAME>
```

这个命令会使用一个名为 `uvx` 的 Python 安装器来安装。如果你没有 `uvx`，可以从 Astral 的官方网站上找到安装方法，它支持 Windows、Linux 和 macOS。

#### **实战演练：从零到一构建 The Urlist**

我们将用 Spec Kit 来构建一个我经常用来测试新工具的应用——**The Urlist**。

这是一个简单的 Web 应用，功能是让用户可以创建和分享一个链接列表。这个项目虽然简单，但因为它涉及到前端、后端和数据库，足以检验一个开发工具的综合能力。

##### **1. 初始化项目**

我在 VS Code 中已经创建好了一个 Next.js 项目。现在，我们在终端中运行初始化命令。由于我们已经在项目目录中，所以可以省略项目名称。

```powershell
uvx --from git+https://github.com/github/spec-kit.git specify init
```

运行后，它会提示我们选择一个 AI 助手。这里有几个选项：

*   `copilot`: GitHub Copilot
*   `claude`: Claude Code
*   `gemini`: Gemini CLI
*   `cursor`: Cursor

我们选择 **GitHub Copilot**。接着，它会让你选择脚本类型，我选择 **PowerShell**。

完成后，项目中会生成 `.github` 和 `.specify` 两个隐藏文件夹，里面包含了 Spec Kit 工作所需的所有模板和脚本。

##### **2. 定义项目“宪法” (Constitution)**

在 `.specify/memory` 文件夹下，有一个非常重要的文件：`constitution.md`。

这个文件就是项目的“宪法”，你可以在这里定义项目的**非协商性原则**，比如技术栈、代码风格、分支策略等等。AI 在后续的所有工作中都会严格遵守这个文件的规定。

现在，我们让 AI 帮我们更新这个文件，告诉它我们将使用的技术：

> `更新这个宪法文件，为使用 nextjs、shadcn-ui 和 postgres 进行开发设定非协商性原则。`

AI 很快就为我们生成了一套详尽的原则，包括：

*   **产品与简洁性优先**：每个变更都必须服务于明确的用户目标，避免过度概括。
*   **Next.js App Router 规范**：规定了服务器组件是默认选项，客户端组件仅在需要时使用。
*   **shadcn/ui 的 UI 一致性**：所有交互式基元都应来自 shadcn/ui，以保证 UI 的统一。
*   **数据库完整性与性能**：PostgreSQL 是唯一的数据源，迁移先行，所有查询都必须参数化。

##### **3. 创建规格 (Spec)**

定义好“宪法”后，我们就可以开始创建应用的具体规格了。我们使用 `specify` 命令来描述我们想要构建的应用。注意，这里我们只关注**功能和目的**，完全不提技术实现。

```bash
/specify 你正在设计一个名为 The Urlist 的 Web 应用，其目的是让用户创建和分享 URL 集合。用户应该能够创建一个新的空列表，并通过输入字段添加 URL。列表应该显示所有已添加的 URL，并清晰地展示其标题和描述。用户应该能够编辑或删除单个 URL，以及删除整个列表。每个列表都应该有一个唯一的 URL，可以由用户选择或由系统自动生成。发布后，列表及其 URL 将变为公开可见且易于分享。访问共享链接的接收者应该能够看到这个 URL 集合。
```

发送这个指令后，Spec Kit 开始了它的工作。它首先创建了一个名为 `spec.md` 的文件，将我们的自然语言需求转化成了一份极其详尽的、结构化的规格文档。

这份规格文档包含了：

*   **功能分支（Feature Branch）**: 自动创建了一个 Git 分支 `001-design-web-application`。
*   **执行流程（Execution Flow）**: 将用户需求解析成一步步的执行计划。
*   **关键实体（Key Entities）**: 定义了数据模型，如 `List`、`URL Entry`、`Slug`、`User` 等。
*   **用户场景与测试（User Scenarios & Testing）**: 包含了主要的用户故事和详细的验收场景（Acceptance Scenarios）。
*   **边缘情况（Edge Cases）**: 列出了各种可能出现的边缘情况，比如添加重复的 URL、URL 过长、元数据获取失败等。
*   **功能需求（Functional Requirements）**: 将所有需求分解为一个个带有唯一编号（如 `FR-001`）的具体功能点。

##### **4. 生成技术实现计划 (Plan)**

有了详尽的规格，下一步就是制定技术计划。我们使用 `/plan` 命令，并提供我们的技术栈信息。

```bash
/plan 该应用使用 Next.js，搭配最少数量的库。使用原生 HTML、CSS 和 JavaScript。
```

Spec Kit 接收到指令后，生成了一系列新的 Markdown 文件，包括：

*   `plan.md`: 整体计划。
*   `tasks.md`: 详细的任务分解列表。
*   `data-model.md`: 数据库模型和 SQL 迁移草图。
*   `lists.md`: API 接口契约（API Contract）。
*   `research.md`: AI 对技术选型的研究和决策记录。
*   `quickstart.md`: 一个给开发者看的快速上手指南，包含了如何设置环境、运行项目等步骤。

`tasks.md` 文件将整个开发过程分成了多个阶段（Phase），从环境设置、数据库模式、API 实现，到前端 UI 组件，再到集成和最终的润色，每一步都清晰明了。

##### **5. 自动执行与实现 (Implement)**

万事俱备，我们现在只需执行最后一个命令，让 AI 开始编码。

```bash
/implement tasks.md
```

这个过程耗时非常长，在我的演示中足足花了一个小时。期间，它会创建 59 个文件，总计写入超过 2000 行代码。

这个过程并非一帆风顺，AI 会在关键节点停下来，请求确认：

*   **中途确认**：它会询问是否可以继续执行任务列表中的所有步骤。
*   **数据库迁移**：在创建数据库模型后，它会提示我手动运行数据库迁移命令，因为这涉及到本地环境的配置。
*   **修复 Bug**：在开发过程中，它遇到了 Next.js 路由的 Bug（slug 和 id 路由冲突），我需要手动修复这个问题。它还遇到了主页无法渲染的问题，我也进行了手动修复。

尽管遇到了一些小插曲，但它最终还是完成了所有的任务。

#### **成果展示与总结**

最终，我们得到了一个可以运行的 Web 应用。



虽然界面非常基础，但核心功能已经全部实现。我们可以创建一个新的列表，添加 URL 条目，编辑标题和描述，设置一个自定义的 slug，然后发布它。所有的数据都已成功写入数据库。

**总结**

GitHub Spec Kit 提供了一种非常新颖且强大的开发工作流。

*   **优点**：
    *   **高度结构化**：通过规格、计划、任务的分解，让整个开发过程有条不紊。
    *   **质量保证**：从一开始就考虑了测试、边缘情况和非功能性需求，有助于构建更健壮的软件。
    *   **自动化程度高**：能够自动完成大量的样板代码和基础功能实现，解放了开发者。
*   **待改进之处**：
    *   **耗时过长**：目前整个过程非常耗时，不适合快速原型开发。
    *   **需要人工干预**：它仍然会在多个环节要求开发者介入，并非完全的“一键生成”。
    *   **学习曲线**：开发者需要适应这种“先规格后代码”的思维模式，并学会如何审查 AI 生成的大量文档。

总的来说，Spec Kit 虽然还处于早期阶段，但它所代表的“规格驱动开发”理念无疑是软件工程领域一个激动人心的方向。它让我们看到了一个未来：开发者可以更专注于创造性的架构设计和产品规划，而将具体的实现细节交给越来越智能的 AI 助手。
