# 今天仔细听了张小珺和王冠的访谈，很受启发！第一次见王冠还是24年春节前，他刚从moonshot出来打

**Janet** @genie0309 [2025-12-17](https://x.com/genie0309/status/2001342860063649856)

今天仔细听了张小珺和王冠的访谈，很受启发！第一次见王冠还是24年春节前，他刚从moonshot出来打算创业，两年前，他就有着对大模型非常深刻的理解。我记得当时最shock我的一句话：「在moonshot我把大模型当产品去定义和设计，长文本本质上是个产品定义问题」。而这个思想，其实一直贯穿始终，从产品设计到今天的组织思考。非常赞，真的值得好好细品！

这期播客，王冠提出了一个反直觉的判断：AI时代，产品经理的价值在变大，而不是变小。 因为战场变了——从"设计功能"到"设计智能本身"。写Eval比写PRD更重要，定义"什么是好"比定义"做什么功能"更关键。

以下文章，是在这期播客基础上，我做的进一步思考和延展，希望对各位AI应用创业路上的小伙伴有启发👇👇

【AI应用创业的认知重构】

一个悖论：产品经理的价值在变大

一个流行的焦虑是：AI会让产品经理失业。当模型可以自己生成PRD、自己做竞品分析、自己写用户故事，产品经理还能做什么？

但如果我们换一个角度看这个问题，会发现完全相反的picture。

传统产品经理的工作是"设计功能"。你定义一个功能，工程师实现它，功能的边界是清晰的，行为是确定的。互联网时代的产品经理进化了一步，开始"设计体验"——不只是功能本身，还包括用户如何感知这个功能、如何被引导、如何形成习惯。

但AI时代的产品经理要做的事情，比这两者都更底层：设计智能本身。

这听起来很抽象，让我们拆开看。一个AI产品的能力从哪里来？从模型。模型的能力从哪里来？从数据。那么，谁来决定用什么数据、怎么筛选数据、什么样的数据代表"好"？

答案是产品经理。

这就是为什么"写Eval比写PRD更重要"。Eval是评测标准，定义了"什么是好的输出"。这个定义决定了数据筛选的方向，数据筛选决定了模型能力的边界。产品经理不再是在已有能力上做包装，而是从源头塑造能力本身。

更具体一点：当一个AI产品在某个场景表现不好，算法团队会说"再去搞一些数据"。为什么是产品经理去搞？因为"什么样的数据能让这个场景变好"是一个产品问题，不是技术问题。它需要对场景的深刻理解，需要知道用户真正想要什么，需要能把这个"想要"转化成可标注、可训练的形式。

所以产品经理的价值不是在变小，而是在变大。只不过，这个价值的实现方式完全变了。

第三份数据：应用公司的护城河在哪里

一个困扰很多人的问题是：做AI应用，会不会被模型公司碾压？

这个担忧有其道理。模型能力在快速迭代，今天你辛苦搭建的功能，明天可能被新版本的基座模型直接覆盖。OpenAI做了GPT Store，Google做了Gemini Apps，大厂下场似乎是必然的。

但这个担忧忽略了一个关键区分：数据的三种类型。

第一种是公域数据——互联网上已经存在的文本、图片、视频。这些数据已经被大模型吃完了，你没有优势。

第二种是领域数据——特定行业的专有数据，比如医疗记录、法律文书、金融交易。这些数据确实是护城河，但它们往往掌握在大厂或传统行业巨头手里，创业公司很难获取。

第三种是内生数据——你的产品形态创造出来的、之前不存在的数据。

ChatGPT为什么强大？不只是因为GPT-4的基座能力，更因为它通过对话这种产品形态，创造了一份全新的数据：人类如何与AI对话、在什么场景下问什么问题、对什么样的回答满意。这份数据以前不存在，是ChatGPT这个产品"生产"出来的。

这才是应用公司真正的护城河：设计一种产品形态，让用户在使用过程中自然产生一份新数据，这份数据可以训回模型，让你的产品变得更好。

这个逻辑形成了一个飞轮：产品吸引用户 → 用户产生数据 → 数据优化模型 → 模型让产品更好 → 产品吸引更多用户。只要这个飞轮转起来，你和基座模型就是共生关系，而不是被替代关系。

但这里有一个前提：你必须有能力设计这份数据。它是什么形式？如何收集？如何确保质量？如何筛选出真正有价值的部分？这些问题，都是产品问题。

Context Engineering：技术架构背后的认知密度

从Prompt Engineering到Context Engineering，听起来只是技术栈的升级——从写一段提示词，变成搭建RAG、Agent框架、Workflow编排。很多团队确实是这么理解的，于是他们堆技术方案、追最新架构、比拼谁的Agent更复杂。

但真正的难点不在这里。

技术上把这些东西拼起来，并不难。有成熟的开源方案，有详细的教程，一个合格的工程师几周就能搭出一个能跑的系统。

难的是：你往context里放什么。

同样一个视频剪辑场景，你可以往context里塞剪辑软件的官方文档，可以塞YouTube上的剪辑教程文字稿，可以塞专业剪辑师的工作流记录，可以塞用户过去三个月的剪辑偏好。技术上都能实现，代码改几行的事。但效果会天差地别。

选择放什么，本质上是在回答一个问题：在这个场景里，什么信息是真正重要的？

这个问题没有标准答案，也很难从数据里直接学出来。它需要对场景的深度理解，需要知道用户在这个时刻的真实需求是什么，需要能区分"表面上想要的"和"实际上需要的"。

所以Context Engineering的本质不是技术问题，是认知问题。它考验的是你对业务的理解深度、对行业know-how的积累、以及把这些隐性知识转化成模型能理解的形式的能力。

这也解释了为什么同样用GPT-4的两个产品，效果可以差很多。基座模型一样，差距在context的质量和效率上。谁的context更有效、token消耗更少、对用户意图的捕捉更准，谁就赢。

这是产品经理的战场，不是工程师的战场。

生成系统：理解AI时代产品范式的钥匙

如果要用一个概念来理解AI时代的产品逻辑，"生成系统"可能是最有解释力的框架。

这个概念可以类比推荐系统。推荐系统是一种方法论——通过算法匹配信息商品和用户偏好。你可以用它推荐文章、推荐视频、推荐商品，形态不同，底层逻辑一致。推荐系统定义了互联网时代的产品范式，从今日头条到抖音到淘宝，本质上都是推荐系统的不同实现。

生成系统也是一种方法论——通过AI直接生产信息商品。你可以用它生成视频、生成音乐、生成软件，形态不同，底层逻辑一致。

生成系统有三层架构。

第一层是DSL，领域专用语言。你要生成的东西，必须先能被精确描述。一个视频是什么、它是如何被制作出来的，都要能用结构化的方式表达。这是整个系统的地基。没有精确的描述，就没有精确的生成、精确的评价、精确的改进。

第二层是Context。所有帮助模型更好生成的"上下文"都在这一层——Agent框架、Workflow编排、专业知识库、用户偏好、历史记录。Context的作用是降低两种熵：用户意图的熵（把模糊指令变成精确需求）和智能体行动的熵（让AI知道具体该做什么）。

第三层是Environment，用户和AI共同活动的环境。这不只是一个软件界面，而是一个可以产生数据、可以被学习、可以持续进化的空间。人在里面操作，AI也在里面操作，所有活动都被记录，好的活动被筛选出来训练更好的模型。

这三层加在一起，构成了一个完整的生成系统。它和推荐系统的本质区别在于：推荐系统是在已有内容里做匹配，生成系统是直接生产内容本身。

这个区别带来一个深远的影响：当生产可以即时响应需求，分配环节就被压缩了。抖音、淘宝、今日头条，本质上都是中间商——连接生产者和消费者，靠分配赚钱。但生成系统"没有中间商赚差价"。你想要什么内容，系统直接为你生成，不需要从一个库存里挑选。

这不只是效率的提升，而是经济结构的变化。

Recipe经济：创作者的新角色

如果生成系统能直接生产内容，创作者还有价值吗？

答案是有，但角色变了。

传统创作者生产"内容"——一篇文章、一个视频、一首歌。每一件作品都是独立的、一次性的。你写了这篇文章，它就是这篇文章，别人想要类似的，你得再写一篇。

AI时代的创作者生产"Recipe"——一种可复用的方法。这个方法定义了"如何生产某一类内容"，系统用这个方法去生成海量具体内容。

举个例子。一个擅长解释复杂概念的博主，他的价值不在于他写的某一篇具体文章，而在于他"如何把复杂概念讲清楚"的方法。这个方法可以被编码成一个Recipe——包括他的思考框架、表达结构、类比习惯、节奏控制。有了这个Recipe，系统可以用它来解释任何复杂概念，产出的内容带有这个博主的风格和水准。

这改变了创作者的价值来源。以前，价值来自具体作品。现在，价值来自方法本身。方法是可复用的，一个好的Recipe可以无限次被调用。

但这也带来一个问题：如果方法可以被编码，创作者的不可替代性在哪里？

答案是品味。Recipe定义的是"如何做"，但"做什么"、"做成什么样"，需要人来判断。什么题材值得做、什么角度更有意思、什么表达更打动人——这些判断无法被完全编码，因为它们本身就在不断演化。

所以未来的创作者是"方法提供者"和"品味提供者"的组合。方法可以被系统学习和复用，品味是创作者持续贡献的独特价值。

这个转变已经在发生。Prompt库、Agent模板、Workflow配方，本质上都是Recipe的早期形态。最好的创作者不是那些产出最多内容的人，而是那些能设计出最好Recipe的人。

Scale最强的人：一个反直觉的商业策略

传统SaaS的增长逻辑是：获取更多用户，提高ARPU，扩大营收。用户数是核心指标，增长团队的KPI是拉新、留存、转化。

但有一种不同的思路：不追求用户数量，追求用户质量。三个用户产生一百万营收，比十万用户产生一百万营收更好。

这听起来反直觉。更少的用户怎么会更好？

逻辑是这样的：生成系统的核心价值是"scale最强的人"。最强的人能把系统用到极致，他们产生的数据质量更高、使用模式更值得学习。这些数据训回模型，让系统对"高水平使用"的理解更深，进而吸引更多高水平用户。

反过来，如果你的系统靠海量普通用户堆营收，你收集到的数据可能是低质量的、同质化的。这些数据训回模型，只会让系统在"普通使用"上变得更好，而不是在"极致使用"上变得更好。

这是两种完全不同的飞轮。

前者：高质量用户 → 高质量数据 → 更强的系统 → 吸引更多高质量用户

后者：海量用户 → 平均质量数据 → 更"通用"的系统 → 继续获取海量用户

两种飞轮都能转，但通向不同的终局。前者可能做成一个小而美的高利润业务，后者可能做成一个大而平庸的commodity工具。

最好的生成系统，应该让最强的人变得更强，而不是让所有人变得一样。

组织作为环境：当劳动力变成Token

如果AI的逻辑渗透到组织设计，会发生什么？

传统管理思维把组织看成机器——有输入、有流程、有产出，管理者的工作是让机器高效运转。但还有另一种看法：组织是environment，员工是在里面活动的智能体。

这两种隐喻的区别在于控制方式。机器需要被操控，你要设计每个零件的功能、每个流程的步骤。环境只需要被设计，你设计好规则和激励，让智能体自己找到最优路径。

在AI时代，这个区别变得更有意义。因为劳动力越来越多以token的形式存在。很多执行性工作可以被AI完成，人的角色从"执行"转向"判断"和"创造"。而判断和创造这两样东西，人多了反而可能稀释——太多人参与决策会带来共识成本，太多人参与创造会带来风格不一致。

这意味着组织的最优规模可能在变小。

一个30人的团队，如果每个人都是自驱的、目标对齐的、能独立产出高质量工作，可能比一个300人的团队更有效率。因为前者不需要管理层级、不需要协调会议、不需要那些在机器隐喻下必不可少的"润滑剂"。

但这也意味着招聘逻辑要变。不是"这个岗位需要什么能力"，而是"这个人热爱什么，这个热爱和我们要做的事有没有交集"。不是给员工指定目标，而是找那些自己本来就有目标的人，然后把他们的目标和公司目标对齐。

这是一种更高要求的招聘标准：你要找的是那些不需要被管理的人。这样的人本来就稀缺，所以组织增长会比较慢。但省掉的是大量内耗和管理成本。

把管理问题在招聘时解决，而不是在运营时解决。

一个Mental Model：设计一份新数据

如果要用一句话概括AI应用公司的本质，可能是这样：

AI应用公司的本质不是"用AI做产品"，而是"设计一个能持续产生有效数据的生成系统"。

这个定义包含几个关键词。

"设计"——不是被动地使用AI能力，而是主动地定义AI应该学会什么。

"持续产生"——不是一次性的数据采集，而是产品运转过程中自然生成的数据流。

"有效数据"——不是所有数据都有价值，只有高于模型当前水平的数据才能让系统进化。

"生成系统"——不是一个静态的工具，而是一个会成长的有机体。

围绕这个定义，我们可以重新理解很多事情。

产品形态为什么重要？因为它决定了能产生什么数据。

Context Engineering为什么是核心？因为它决定了数据的质量和效率。

为什么要scale最强的人？因为最强的人产生最有价值的数据。

为什么组织要小而精？因为设计数据需要深度理解，不需要大量执行。

所有这些判断，都从同一个原点出发：谁能设计出最好的数据生产机制，谁就掌握了AI时代的核心资产。

这不是一个技术判断，而是一个认知判断。它考验的是你对场景的理解、对用户的洞察、对"什么是好"的定义能力。

技术会迭代，模型会进化，但"设计一份新数据"的能力，是跨越周期的。
