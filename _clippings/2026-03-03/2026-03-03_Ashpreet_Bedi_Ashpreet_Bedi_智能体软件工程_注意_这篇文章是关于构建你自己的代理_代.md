# 智能体软件工程

> 注意：这篇文章是关于构建你自己的代理（代理软件工程），而不是关于使用编码代理。

想必你已经使用过一些代理程序，或者至少听说过 Claude Code、Codex 或 OpenClaw。有没有想过构建自己的代理程序需要哪些条件？

大多数人认为代理就是循环中的提示和工具。这种假设合情合理，但这并非生产环境架构。

当你的代理需要知道它正在与谁交谈、维护状态、处理并发请求、执行敏感操作以及在工具调用失败的情况下生存时，它就不再是“LLM + 工具”，而变成了一个分布式系统。

构建智能体很容易，有 75 个框架可以帮助你完成这项工作。难点在于运行时：也就是围绕智能体构建的、使其能够在现实世界中运行的底层框架。这正是智能体软件工程的核心所在。

# 建设。服务。连接。

以下是我对货运代理软件的看法。

1.  构建代理。定义模型、工具、知识库、内存、存储和防护机制。这是大多数框架提供的功能层。
2.  将其作为 API 提供 。支持用户级、会话级和水平扩展。添加持久存储、流式传输、后台执行和重试机制。大多数代理产品都止步于此。并非代理本身无法工作，而是缺乏相应的底层架构来支持其大规模可靠运行。
3.  将它连接到用户所在的平台。无论是你的产品、Slack、Discord、MCP，还是其他任何地方。笔记本里的代理只是一个实验品。而用户所在的代理才是真正的产品。

# 智能体软件的六大支柱

构建智能体是人工智能工程，在生产环境中运行智能体是软件工程。两者结合起来构成了智能体软件工程：即构建、运行和扩展智能体作为生产服务的实践。

支撑它的六大支柱如下：

1.  持久性。 代理程序需要跨多个步骤进行推理，调用可能超时的工具，并在执​​行过程中失败。如果代理程序在 15 个步骤中的第 12 个步骤崩溃，重新启动可能会重复产生副作用或丢失关键上下文。代理软件需要能够优雅地暂停、恢复、创建检查点和进行恢复。持久性可以将故障转化为恢复，而不是完全重启。
2.  隔离。 代理软件同时服务数千用户。每个用户都需要自己的会话、内存和上下文。在每个请求中传递 user\_id 很容易，但隔离代理访问的每个资源才是工程设计的精髓所在。你的数据库、向量存储、模型提供程序，所有这些都必须尊重用户边界。任何一个过滤器的缺失都可能导致数据泄露。
3.  治理。 能够采取行动的代理也可能造成损害。查询记录本身并无害处。删除记录或退款则需要审批。代理软件需要分层权限：哪些操作自动运行，哪些需要人工审批，哪些需要管理员签字。如今，大多数代理程序在极少监督的情况下自动执行。随着其功能日益强大，治理本身也成为产品的一部分。
4.  持久性。 没有持久存储的智能体无法学习、无法构建上下文、也无法改进。我们需要将会话、记忆和知识存储在数据库中。持久状态使聊天机器人成为真正的产品。每一次对话都会让下一次对话变得更好。
5.  规模。 成千上万的用户同时访问您的代理。请求会排队，您会遇到模型速率限制，而且各种工具调用都会争用资源。传统服务调用您自己的后端。而代理软件调用外部模型 API 和第三方工具，这意味着您需要承担它们的速率限制、延迟和停机时间。扩展代理软件意味着要围绕您无法控制的依赖项进行扩展。
6.  可组合性。 当一个代理作为一项服务时，其他代理可以调用​​它。你的前端可以调用它。你的 Slack 机器人可以调用它。MCP 客户端可以发现它。它成为你架构中的一个构建模块，每一次新的集成都变成了一个标准的 API 调用。这就是单代理工具如何演变为多代理系统的过程。

这些都不是什么新鲜事。几十年来，我们一直在构建可靠的分布式系统。人工智能行业只是还没有吸取这些经验教训，而每一次部署失败都让我们深切感受到这一点。

# 从理论到实践

和往常一样，我带来了代码。以下是如何立即开始构建您自己的代理服务的方法。

```bash
# 1. Clone the repo
git clone \
 https://github.com/agno-agi/agentos-docker-template.git \
 agentos

cd agentos

# 2. Set your model provider key
cp example.env .env
# Edit .env and add OPENAI_API_KEY

# 3. Start the application
docker compose up -d --build

# 4. Load documents for the knowledge agent
docker exec -it agentos-api python -m agents.knowledge_agent
```

这为您提供了一个容器化的服务，具有持久存储（Postgres）、两个启动代理（一个使用 Agentic RAG 的知识代理和一个用于外部工具的 MCP 代理）以及一个您可以从任何地方连接的 REST API。

我之所以在这个模板中使用 Docker，是因为 Docker 可以在任何地方运行：你的笔记本电脑、AWS、GCP、Azure、铁路。你在本地开发的容器就可以部署到生产环境。 自述文件涵盖入门所需的一切。

服务运行后：

1.  打开 http://localhost:8000/docs 查看您的 API。
2.  连接到 Web 用户界面 os.agno.com 您可以在这里与客服人员聊天、追踪运行情况、管理知识库、创建日程安排并批准敏感工具调用。一个统一的客服软件用户界面。

添加您自己的代理只需几行 Python 代码并重启即可。只需一行代码即可替换模型。添加来自 100 多个集成的工具。模板只是一个起点。阅读 Agno 文档了解更多信息。

# 治理与征求

大多数代理人在执行工具调用时缺乏足够的监督或审计。实际上，我们需要分层授权：

1.  自由运行的工具
2.  需要用户批准的工具
3.  需要管理员批准的工具

特工还需要提出问题（通常称为引导提问）。克劳德代码团队分享了一个好文章在 Claude 使用的 AskUserQuestion 工具上。

在 Agno 中，此功能以“UserFeedbackTools”的形式提供。它提供了一个支持代理，可以自由查找订单，在需要更多信息时向客户提出结构化问题，并在退款前等待用户批准：

```python
support = Agent(
 id="support",
 name="Support",
 model=OpenAIResponses(id="gpt-5.2"),
 db=agent_db,
 tools=[
 lookup_order, # auto-execute
 search_help_docs, # auto-execute
 issue_refund, # requires user confirmation
 UserFeedbackTools(), # structured questions
 ],
 instructions=instructions,
 enable_agentic_memory=True,
)
```

看看当顾客要求退款时会发生什么。

- 代理人自行查找订单，无需获得许可。
- 然后就到了决定点：顾客为什么要退款？
- 它不让玩家猜测，而是提出一个结构化的问题，并提供明确的选项：有缺陷的、错误的商品、改变主意。
- 客户选择后，客服人员调用退款工具，但由于退款会产生实际后果，因此需要等待用户确认。
- 审核通过后，代理人会运行退款工具。

一次对话中涉及三个层级的代理权。您可以查看完整代码在此 。

代理知道何时行动、何时询问、何时等待。这就是治理在实践中的体现。运行时必须支持所有三种模式，并且它们之间的转换必须自然流畅。

> 注意：用户界面上的审批流程正在积极开发中。退款应等待管理员审批，而非用户审批。此功能已在 SDK 中实现，但尚未在用户界面中实现。我们将在本周内修复此问题。
