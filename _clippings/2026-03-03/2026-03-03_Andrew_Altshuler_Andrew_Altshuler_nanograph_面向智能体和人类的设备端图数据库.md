# Andrew Altshuler # nanograph：面向智能体和人类的设备端图数据库

**Andrew Altshuler**

# nanograph：面向智能体和人类的设备端图数据库

我构建了一个图数据库。

原因如下： 我喜欢图表，而且我经常使用图表！

- 用于代理内存
- 用于构建项目背景
- 用于构建复合知识库

然而，传统的图数据库对于智能体工作流程来说太过笨重。 它们是专为企业基础设施构建的云优先单体架构： 服务器、Docker、缓慢的 MCP 和模式维护地狱。

纳米图谱最初源于一个问题：

> 如果图数据库的使用体验像 SQLite/DuckDB 一样—— 打开、查询、完成 ——但类型 、 迁移和人体工程学都是为代理构建的，那会怎样 ？

拆卸和重建速度快，足够安全可靠，而且足够简单，可以保存在代码库中。

我找不到符合我设想的图数据库， 所以我就自己建了一个。

设备端嵌入式、模式即代码的图数据库。

现在让我们来详细分析一下：

- 为什么要绘制图表？
- 为什么选择设备端？
- 为什么需要将模式视为代码？

## 为什么需要图表？

图表帮助智能体通过数据进行推理。

智能体是信息丰富的探索者。当智能体调查某个问题时，它会遍历上下文图。这些图为智能体提供推理结构。

现在将决策轨迹添加到等式中：明确的“如何”和“为什么”——工作流程、异常情况、推理。

智能体现在可以：解决问题 → 遍历图 → 编写新的轨迹 → 绘制化合物图。

新的推理路径被创造出来——智能体变得更加智能。

顺便说一下，这个图不需要独立存在。它可以作为语义层叠加在你的数据之上：可以是 SQL/NoSQL 数据库，也可以是 MD 文件集合。

## 为什么选择设备端？

编码代理将我们拉回基本原理： 文件系统、命令行界面、Markdown、SQLite/DuckDB。

在 PKM 领域，Obsidian 正在取得胜利，而像 qmd 这样的工具也获得了真正的关注。

如果所有操作都在设备端进行，一切都会变得简单。完全的隐私保护源于架构，而非策略。即使在监管严格的企业环境中，您也可以使用自己的工具。

代理商需要直接、快速、确定性的数据访问权限。他们不需要 MCP 认证，也不需要处理连接错误。

## 为什么需要将模式视为代码？

未强制执行的模式意味着垃圾信息的积累。

智能体极富创造力！ 给它们一个无模式图，它们就能自由驰骋。它们会创造出诸如 knows、met、connected\_to、spoke\_with 之类的边——所有这些边都表示同一件事。 这会开创投毒先例。 语义漂移会沿着推理层传播。你的图会变得嘈杂，检索结果也会变得不可靠。

既定的模式可以避免这种情况。而模式即代码是强制执行模式和跟踪变更的最佳方式。

另一个好处是： 它能记录你与代理之间的契约演变过程。随着模型的变化，契约也会随之改变。通过追踪模式历史记录，代理可以看到你的模型是如何演变的。这便成为另一条极其有用的推理路径。

# 那么，什么是纳米图？

纳米图是一个设备端图形数据库 ，打包为 CLI + 一个文件夹。

围绕五大支柱构建：

- 设备端 ——一个文件夹，而非服务。无需 Docker，无需云端。超快的本地查询速度，远胜于缓慢的云端往返。
- 零配置 - init 命令根据模式创建数据库，load 命令导入数据。删除和重新创建只需几秒钟。
- Schema-as-code（模式即代码）——仓库中的 .pg 文件，进行版本控制。类型在加载和查询编译时强制执行。
- 时间机器 ——内置疾病控制与预防中心（CDC）和事件溯源功能。每一次突变都是账本上的一个条目。
- 强大的搜索功能 ——全文搜索、语义搜索、模糊搜索、BM25 搜索、混合搜索以及图约束重排序。

nanograph 数据库是一个构建产物，而不是一个正在运行的服务。它是一个文件夹：<name> .nano/ 包含您的所有图表数据：复制它、git 打包它、zip 打包它、加密它。

要让它以这种方式运行，难度相当大。 智能体非常擅长编写 Rust 代码，但 LLM 往往倾向于采用默认的架构和人体工程学思维。

我想要一个前沿的图数据库，所以我直接进入了研究模式。 在某个时候，我发现了 Apache Arrow（用于内存）和 Lance（用于存储）之间的一种巧妙的相互作用。 然后设计了查询语言： nanoQL——将 Datalog 语义与 GraphQL 语法相结合。

那是我感觉非常合适的原型机！

然后我又深入了一层。我以为自己很了解数据库——我这辈子都在和数据库打交道。但事实证明，事情远比我想象的要复杂得多。

我深入研究了基本原理： 索引、压缩、WAL、CDC、缓存、混合搜索。 使用超级智能模型（GPT-5.2 PRO 和 Gemini 3 Deep Thinking）进行规格制定。

真是太不可思议了： 我正努力突破自己工程和数学能力的极限。

纳米图是我做过的最精妙的工程作品。

我强烈建议你试一试！

## 快速入门

给你的代理一个指向代码库的链接，它就会完成所有设置：github.com/aaltshuler/nanograph

或者使用 brew：

```bash
brew install nanograph/tap/nanograph
```

该仓库提供了两个可直接运行的示例图。

## 星球大战图表

角色、电影、派系和师徒关系的知识图谱： 9 种节点类型 25 种边缘类型 66个节点 非常适合探索模式基础知识、图遍历和完整的搜索堆栈（文本、语义、混合）。

该模式定义了具有枚举和键标识的类型化节点：

```rust
node Character {
 slug: String @key
 name: String
 species: String
 alignment: enum(hero, villain, neutral)
}

edge HasMentor: Character - Character
edge DebutsIn: Character - Film
```

初始化、加载和查询：

```bash
nanograph init sw.nano --schema examples/starwars/starwars.pg
nanograph load sw.nano --data examples/starwars/starwars.jsonl --mode overwrite
nanograph run --db sw.nano --query examples/starwars/starwars.gq --name students_of --param name="Yoda"
```

查询会根据模式进行类型检查——错误的属性名称、类型不匹配和无效的遍历会在执行前被捕获。

## RevOps 上下文图

RevOps 上下文图：情报获取 → 丰富 → 筛选 → 决策 → 交付。

10种节点类型 21种边型

这就是 nanograph 设计的真正亮点所在：决策轨迹、通过 Supersedes 边进行策略版本控制，以及从信号到结果的多跳遍历。

https://www.nanograph.io/docs/examples/context-graph

决策追踪查询从机会出发，追溯到是谁做出了决定以及是什么信号驱动了这一决定——这是代理人需要回答的“为什么会发生这种情况？”的问题。

## 哪种纳米图谱最适合

- 上下文图 （决策轨迹、因果链、结构化上下文）
- 代理内存 （用于编码代理的设备端内存）
- 个人知识 （书签、笔记、联系人；本地优先、强制执行模式、版本控制）
- 依赖关系图 （服务、软件包、血缘跟踪）

## 纳米图不适用于

nanograph 有意避免成为包罗万象的事物。

- 不是多租户分布式云图
- 并非一个没有模式纪律的万能商店
- 并非交易记录系统或账簿

重点恰恰相反： 保持你的纳米图简洁、独立、打印和聚焦。

根据需要创建任意数量的实例。初始化只需几秒钟，删除也只需几秒钟。可以按项目、按代理、按实验分别启动。

nanograph 是开源软件，可以免费使用。 您的代理将为您下载并设置它，然后帮助您创建架构并导入数据。
