# Qwen3.5-35B-A3B：你只需要一块 RTX 3090。在 262K 满上下文中达到 112 tok/s。

我把它放在一块 RTX 3090 显卡上，在 262K 满上下文的情况下达到了每秒 112 个令牌的速度。从 4K 降到 262K 没有速度下降。这不是笔误。这种架构使得上下文扩展几乎不消耗资源。

然后我发布了这些数据。48 小时后，社区就收到了来自 5090、4090、3090 以及 AMD 显卡的测试结果。我分享的优化参数让大多数人的速度一夜之间翻了一番。一个默认设置下速度只有 50 tok/s 的模型，到第五天在 5090 显卡上就达到了 176 tok/s。

## 建筑设计（为何与众不同）

大多数 35B 型号都是纯粹的 Transformer 架构。每一层都会构建一个键值缓存，该缓存会随着上下文长度的增长而增长。上下文越多，需要的显存就越多，缓存生成速度就越慢。这就是为什么大多数配备 24GB 显存的型号在超过 32K 上下文后就会开始出现性能瓶颈的原因。

Qwen3.5-35B-A3B 的工作方式并非如此。40 层中只有 10 层使用了带有 KV 缓存的传统注意力机制。其余 30 层是带有固定大小循环状态的门控 DeltaNet 层。上下文信息量增加，而模型 75% 的内存占用保持不变。

结果：4K 分辨率下速度为 112 tok/s，262K 分辨率下速度为 113 tok/s，速度相同。该模型确实不关心上下文的长度。

显存满格 262K 情况下：18.5GB 模型 + 2.7GB KV 缓存 + 63MB 循环状态 = 总计 22.4GB。24GB 显卡剩余 2.1GB。

作为对比，一个参数量为 350 亿的纯 Transformer 程序，在 262K 的键值缓存下，大约需要 10GB 的缓存。总共需要 30GB 以上。24GB 的内存装不下。游戏结束。

## 旗帜（让所有人的速度翻倍）

大多数人下载了模型，使用默认设置运行了 llama.cpp，得到了 40-70 tok/s 的速度。还算可以，但远未达到该模型应有的速度。

五面旗帜改变了一切：

\-ngl 99 将所有 41 层都放在 GPU 上执行。默认情况下，部分任务会卸载到 CPU 上。不要这样做。

\`--cache-type-k q8\_0 --cache-type-v q8\_0\` 会将 KV 缓存的显存减半，速度不会损失。这是影响最大的一个参数。如果没有它，24GB 内存上会出现 262K 次上下文内存溢出。

\-c 262144 设置完整的原生上下文窗口。默认值为 2048。这样就浪费了该模型 99% 的功能。

\-np 1 将循环状态缓冲区从 251MB 减少到 63MB，释放 VRAM。这仅在您运行单用户推理时才重要，而您目前正是在本地 GPU 上运行单用户推理。

\-fa 启用闪存注意功能。占用更少的显存，预填充速度更快。

结果：一夜之间，用户吞吐量从 50 tok/s 提升到了 112 tok/s。硬件配置相同，型号相同，只是使用了不同的标志。

解锁一切的命令：

```bash
`llama-server -m qwen3.5-35b-a3b-ud-q4_k_xl.gguf -ngl 99 -c 262144 -fa --cache-type-k q8_0 --cache-type-v q8_0 -np 1 --host 0.0.0.0 --port 8080`
```

## AMD 的意外

R9700 达到 128 tok/s 的速度并非基于 ROCm，而是基于 Vulkan。llama.cpp 的 Vulkan 后端无需驱动，也无需 ROCm 配置，就能正常工作。

与此同时，6800XT 在 ROCm 下的吞吐量仅为 20-30 tok/s。没有人提交优化后的 ROCm 测试结果。AMD 平台上的所有人都选择了 Vulkan。这足以说明 ROCm 的现状。

硬件不是瓶颈，软件才是。AMD GPU 的显存带宽足够，只是优化方案还不够完善。

## 比较（3B vs 80B）

我在两个模型上运行了相同的任务：构建粒子模拟。

Qwen3-Coder-Next：800 亿个参数。2 块 RTX 3090 显卡。46 tok/s 运算速度。564 行代码。经过两次迭代才成功。

Qwen3.5-35B-A3B：30 亿个活动参数。1 块 RTX 3090 显卡。112 tok/s 运算速度。461 行代码。首次尝试。

速度提升 2.4 倍。仅需一半的 GPU。代码行数更少。代码更简洁。一次成功。

较小的模型胜出，并非因为其每个令牌的智能更高，而是因为扩展性（MoE）+速度+长上下文意味着在更便宜的硬件上每小时可以进行更多次迭代。在局部推理中，运行速度更快的模型胜出。当相同时间内可以运行三倍的尝试次数时，每个令牌的原始智能就显得不那么重要了。

## 代理人问题

模型运行速度很快，功能也很强大，问题出在代理框架上。我测试了两种配置：相同的模型、相同的 GPU、相同的本地主机端点。分别使用 Claude Code 和 OpenCode。

Claude Code 每隔 3-5 分钟就会中断一次流程。工具调用失败，流程停止，你重新提示。它恢复正常。2 分钟后再次停止。模型本身没有问题。问题出在本地推理延迟上。

OpenCode 本身不会崩溃，整个流程运行流畅，完全自主。但当模型失去状态跟踪时，就会陷入循环，同一个读取调用会重复 10 次以上。30 亿个活动参数无法在相同的工具调用中始终保持其位置一致。

Claude Code 的链式中断机制是一种粗糙的安全措施。OpenCode 的持久化功能在变成漏洞之前是个优点。

结论：本地推理已经就绪，模型也已准备就绪，但代理框架尚未就绪。瓶颈现在在于你和模型之间的工具层，而不是 GPU，也不是权重，而是封装层。
