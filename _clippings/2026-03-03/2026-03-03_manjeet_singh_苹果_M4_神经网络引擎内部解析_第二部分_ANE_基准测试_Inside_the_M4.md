# 苹果 M4 神经网络引擎内部解析（第二部分）：ANE 基准测试 --- Inside the M4 Apple Neural Engine, Part 2: ANE Benchmarks

衡量苹果神经网络加速器的实际性能 苹果公司称 M4 神经网络引擎的运算速度为 38 TOPS。让我们来测试一下。 在 第一部分中 ，我们对 ANE 软件栈进行了逆向工程，并通过 _ANEClient 获得了直接访问权限 ，完全绕过了 CoreML。现在我们可以进行基准测试，而无需担心 CoreML 的开销会扭曲测试结果。 我们的发现令人惊讶。“38 TOPS”这个数字从技术上讲并没有错，但它极具误导性。而且，还有一些方法可以最大限度地提高吞吐量，而苹果公司从未公开说明过。 测试设置 硬件： M4 Mac Mini（10 核 CPU，16 核 ANE） 软件： macOS 15.x，直接使用 _ANEClient API（不使用 CoreML） 计时： mach_absolute_time() ，100 多次迭代，报告中位数 精度： FP16 计算（ANE 本机），FP32 I/O Matmul 缩放：基础知识 让我们从最简单的基准测试开始：不断增大的方阵乘法。 有两点显而易见： 256×256 的分辨率受限于调度 ：耗时 0.101 毫秒，其中大部分时间（约 0.095 毫秒）都花在了 XPC 和 IOKit 的开销上。实际计算时间仅约 0.006 毫秒。 性能在 4096 处下降 ：从 2048 处的 5.7 TFLOPS 降至 4096 处的 4.0 TFLOPS。某些东西溢出了。 SRAM 悬崖 2048→4096 的性能下降是 SRAM 的断崖效应。矩阵乘法运算的工作集包含 3 个矩阵（A、B、C）。在 FP16 模式下： 在 2048×2048 分辨率下，24 MB 的工作集可以放入 SRAM 中，并获得峰值单次操作吞吐量（5.7 TFLOPS）。在 4096×4096 分辨率下，96 MB 的工作集大约是 SRAM 的 3 倍，迫使数据溢出到 DRAM，导致吞吐量下降 30%。 24 MB（快）和 96 MB（慢）之间的容量差距，使得 ANE 的片上 SRAM 容量约为 32 MB 。这种过渡并非突然中断——性能是逐渐下降的，这表明其采用的是类似缓存的层级结构，而非简单的临时存储介质。 卷积 > 矩阵乘法 苹果的文档中并没有明确指出这一点： ANE 本质上是一个卷积引擎 。用 1×1 卷积代替矩阵乘法来表达相同的计算，可以显著提高吞吐量。 矩阵乘法 C[M,N] = A[M,K] @ B[K,N] 可以通过重塑表示为 1×1 卷积： 输入： (1, K, 1, M) 重量： (N, K, 1, 1) 输出： (1, N, 1, M) 相同的浮点运算次数，相同的结果，但 ANE 的卷积数据通路处理效率要高得多。 深度图填充管道 单个矩阵乘法运算仅使用 ANE 峰值容量的约 30%。该硬件专为 图运算而设计 ——即一系列操作链，这些操作链会占用所有 16 个核心。串联的操作越多，就越接近理论峰值容量： 最大化 ANE 吞吐量的规则： 图线要深，不要宽。 一个军工项目中要包含 16-64 个操作。单个操作会浪费 70% 的容量。 卷积优于矩阵乘法。1 ×1 卷积使用快速数据通路。矩阵乘法的速度慢 3 倍。 保持在 32 MB 以下。 每个张量占用的内存应尽可能少，最好只占用 SRAM。溢出到 DRAM 会严重降低吞吐量。 避免执行受限于调度的操作。 任何低于约 1 毫秒的操作都会受到 0.095 毫秒调度开销的严重影响。 CoreML 与 _ANEClient：额外开销 CoreML 究竟损失了多少性能？我们通过两种不同的路径测试了相同的操作： 对于小型操作， CoreML 会增加 2-4 倍的开销 。在高吞吐量配置下，由于 ANE 计算时间占据主导地位，这种差距会缩小。但对于延迟敏感型工作负载（例如 LLM 令牌解码、实时推理），CoreML 的开销则非常显著。 INT8 = FP16：《38 TOPS》的现实 苹果声称 M4 神经网络引擎的运算速度为“38 TOPS”。这究竟意味着什么？ 我们在 FP16 和 INT8 中测量了相同的操作： 结论： INT8 算法的加速比并未达到 2 倍。INT8 和 FP16 的吞吐量几乎相同。ANE 在计算之前会将 INT8 的权重反量化为 FP16 。 INT8 只节省内存带宽（从 DRAM 加载的权重更小），不节省计算周期。 苹果的“38 TOPS INT8”是根据业界惯例计算的 ，即 19 TFLOPS FP16 × 2 ，INT8 运算速度是 FP16 运算速度的两倍。但实际上，硬件执行 INT8 运算的速度并没有翻倍。 真正的峰值是 19 TFLOPS FP16，无论量化与否，你都会得到这个结果。 这相当于我们根据硬件配置（16 个核心 × 每个核心约 1.2 TFLOPS）计算出的理论峰值的 100%。在 32 层以上的层深度下达到 94%的利用率意味着我们实际上是在测量硬件的原始性能。 能源效率：ANE 的秘密武器 如果仅以吞吐量作为衡量标准，GPU 总是会胜出。但 ANE 的真正优势在于效率。 零功耗。毫瓦级。待机状态下也是如此。ANE 采用 硬性电源门控 ——它不仅会进行时钟门控，而且在不使用时会完全断电。无漏电，无待机功耗。 在峰值负载下，其性能为 6.6 TFLOPS/W 。作为参考： 计算效率（TFLOPS/W）M4 ANE6.6M4 GPU~1.0A100 GPU~0.08H100 GPU~0.13 ANE 的 每 FLOP 效率大约是 A100 的 80 倍 。当然，A100 的总吞吐量是 ANE 的 50 倍。但对于使用电池供电的设备端推理而言，ANE 的表现非常出色。 ANE 与 SME：何时使用哪种 M4 的 CPU 核心也采用了苹果的 SME（可扩展矩阵扩展）技术。以下是它们的对比： ANE 适用于： 大批量推理、16 层以上的深度图、能量受限场景以及持续吞吐量。 SME 的用途包括： 单标记解码（零调度开销）、ANE 不支持的自定义操作、小型矩阵以及任何需要 FP32+ 精度的操作。 M4 上理想的 LLM 推理策略是 混合的 ：在 ANE 上进行预填充（大批量、高吞吐量），在 SME 上进行解码（单标记、对延迟敏感）。 可重复性 所有基准测试代码均可在 github.com/maderix/ANE 的 ane/ 目录中找到 。关键文件： ane/inmem_bench.m — 内存 ANE 基准测试 ane/inmem_peak.m — 峰值吞吐量测量（深度卷积图）
