-   在传统软件中，你读代码来理解应用的功能——决策逻辑存在于你的代码库中
    
-   在 AI 代理中，代码只是脚手架——实际的决策发生在模型的运行时
    
-   因此，你的应用的事实依据从代码转为追踪记录——追踪记录了代理实际做了什么及原因
    
-   这改变了我们调试、测试、优化、监控、协作以及理解产品使用的方式
    
-   如果你在构建缺乏良好可观测性的智能体，你就错过了了解系统实际行为的真相来源
    

传统软件里，出问题就看代码，想搞懂功能怎么工作也看代码，想优化性能就剖析代码。代码就是真相之源。

在传统软件中，如果你想了解用户提交表单时发生了什么，你打开 handleSubmit()函数并阅读它。决策逻辑就在那里：验证输入、检查认证、调用 API、处理错误。它是确定性的——相同的输入，相同的代码路径，相同的输出。

代理 = 代理( model="GPT-4", 工具=\[搜索工具, 分析工具, 可视化工具\], system\_prompt="你是一位乐于助人的数据分析师..." ) result = （用户查询）

你已经定义了这些组件：用哪个模型，哪些工具，什么指令。但决策逻辑不在你的代码里。它只是编排 LLM 调用。

实际决策——何时调用哪个工具、如何推理解决问题、何时停止、优先考虑什么——所有这些都在模型运行时发生。

💡 随着大语言模型(LLM)越来越多地驱动你的应用（就像代理的情况一样），仅仅通过查看代码，你对应用实际会做什么的了解会越来越少。

你仍然可以调试你的编排代码——工具调用是否有效、解析是否有效都可以调试。但你无法调试智能本身。智能体是否能做出良好决策、是否能有效推理——这个逻辑存在于模型中，而非你的代码库。

轨迹是代理所执行的一系列步骤。它记录了你的应用的逻辑——每一步的推理、调用了哪些工具及原因、结果和时间。

💡 这意味着，你在软件世界中原本会对代码执行的操作，现在在代理世界中要对轨迹执行了。

调试、测试、性能分析、监控——所有这些都从处理代码转向处理执行轨迹。

在传统软件中，如果两次运行产生不同的输出，你会认为是输入不同或代码不同。而在 AI 代理中，相同的输入和相同的代码可能会产生不同的输出。不同的工具调用、不同的推理链、不同的结果。

理解发生了什么的唯一方法是查看轨迹。为什么任务 A 成功了而任务 B 失败了？对比轨迹。你的提示词修改是否提升了推理能力？对比修改前后的轨迹。为什么智能体总是犯同样的错误？看看所有轨迹中的模式。

当逻辑的真理来源从代码转向跟踪记录时，其他一切都随之而来。你过去在代码上做的所有操作——调试、测试、优化、监控——现在都需要围绕跟踪记录展开。让我们看看这在实际中意味着什么。

当用户报告“代理失败”时，你不应该直接打开代码找 bug，而是应该打开 trace 看看推理哪里出了问题。代理是误解了任务？调用了错误的工具？还是陷入了循环？

这个“bug”不是你代码中的逻辑错误。而是智能体实际做的事情中的推理错误。

一个代理会对同一个失败的 API 调用不断重试五次，然后放弃。你的代码有重试逻辑——这没问题。问题在于这个代理没有从错误信息中学习。你只能在追踪中看到这种情况：同样的工具调用、相同的参数、同样的失败，重复发生。

在传统软件中，当你发现 bug 时，你会在代码中设置断点。

在 AI 代理中，你无法在推理过程中设置断点。决策发生在模型内部。

但是你可以在逻辑中设置断点。使用跟踪 + 游乐场。在特定时间点打开一个跟踪 - 就在代理做出错误决策之前。将该确切状态加载到游乐场中。这个游乐场就像一个调试器，但用于推理而非代码。

你可以看到：这个智能体的上下文是什么？它的记忆里有什么？有哪些可用的工具？提示词是什么样的？然后你进行迭代——调整提示词、改变上下文、尝试不同方法——看看智能体是否能做出更好的决策。

既然逻辑的真理来源在于痕迹，你需要检验这些痕迹。这意味着两件事：

首先：你需要一个数据管道来将追踪数据添加到你的测试数据集中。当你的智能体运行时，你捕获追踪数据并将其添加到一个你可以用来评估的数据集里。

第二：你需要在生产环境中评估执行轨迹。在传统软件中，你会在部署前进行测试并发布。而在人工智能中，智能体具有非确定性，因此需要在生产环境中持续评估，以发现质量下降和漂移问题。

在传统软件中，你需要分析代码以找到热点循环并优化算法。在 AI 智能体中，你分析轨迹以发现决策模式——不必要的工具调用、冗余的推理、低效路径。瓶颈在于智能体的决策，而这些决策仅存在于轨迹中。

一个代理即使零错误也可能表现得很糟糕——在错误任务上“成功”，以10倍成本低效完成，或给出正确但无帮助的回答。

你需要监控决策质量，不只是系统健康——任务成功率、推理质量、工具使用效率。你无法在不抽样和分析轨迹的情况下监控质量。

传统软件里，协作都在 GitHub 上。你审查代码，给 PR 留评论，在 issues 里讨论实现。代码是大家都用的工件。

在 AI 代理中，逻辑不在代码里——而在轨迹中。所以协作也必须发生在轨迹存在的地方。当然，你仍然使用 GitHub 进行编排代码。但当你调试代理为何做出错误决策时，你需要分享轨迹，在特定决策点添加注释，讨论它为何选择这条路径。你的可观测性平台将成为协作工具，而不仅仅是监控工具。

传统软件中，产品分析和调试是分开的。Mixpanel 会告诉你用户点击了什么。错误日志会告诉你哪里出了问题。它们是针对不同问题的不同工具。

在 AI 代理中，这些会融合。不理解代理行为，就无法理解用户行为。当你在数据分析中看到“30%的用户感到沮丧”时，你需要查看追踪记录，看看代理哪里做错了。当你看到“用户要求数据分析功能”时，你需要查看追踪记录，看看代理已经在使用哪些工具，哪些是有效的。用户体验是代理的决策，而这些决策都记录在追踪记录中——因此产品分析必须建立在追踪记录之上。

在传统软件中，代码就是你的文档。在 AI 代理中，轨迹就是你的文档。

这种转变很简单：当决策逻辑从你的代码库转移到模型中时，你的事实来源从代码转向了轨迹。

💡你以前用代码做的所有事情——调试、测试、优化、监控、协作——现在你用追踪来做了。

要让这一切顺利运行，你需要良好的可观测性。结构化追踪，让你能够搜索、筛选和比较。能够看到完整的推理链——调用了哪些工具、耗时多久、成本多少。能够基于历史数据进行评估，以随时间监控质量。

如果你在构建代理，却没有这个东西，那你就是在盲目工作。重要的逻辑只存在于那些痕迹中。
