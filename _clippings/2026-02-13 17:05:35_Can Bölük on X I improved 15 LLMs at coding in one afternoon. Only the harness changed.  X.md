现在的讨论几乎完全集中在哪个模型最擅长编码，是 GPT-5.3 还是 Opus。Gemini 与本周发布的其他模型。这种表述方式越来越具有误导性，因为它将模型视为唯一重要的变量，而实际上，其中一个瓶颈是更平凡的东西：测试框架。

它不仅是你给用户留下第一印象的地方（是不受控制地滚动，还是如黄油般顺滑？），也是每个输入令牌的来源，并且是用户输出与对工作区所做的每处修改之间的界面。

我维护一个小小的“爱好型框架”，，是 Pi 的一个分支，一个由 Mario Zechner 开发的出色开源编码代理。到目前为止，我已经提交了约 1300 次代码，主要是在随意尝试，并在发现痛点时（ 或者突然觉得“不对劲”，觉得可以通过 N-API 嵌入更多 Rust 代码，因为“启动 rg 感觉不对”）时不时地进行一些小的改进。

你问，何必呢？Opus 可能是一个很棒的模型，但 Claude Code 至今仍会从子代理输出中泄露原始 JSONL，浪费数十万 token。我得说，“去他妈的，子代理现在输出结构化数据了”。

工具架构、错误消息、状态管理，以及介于“模型知道要修改什么”和“问题解决”之间的一切。这是实践中大多数失败发生的地方。

作为与模型无关的工具，它是一个绝佳的测试平台，因为模型只是一个参数。真正的变量是测试框架，你对它拥有难以想象的控制。

Codex 使用 apply\_patch: 它接受一个字符串作为输入，本质上是一个 OpenAI 风格的 diff，并且不依赖结构化模式，测试框架只要求这个数据块（blob）遵循严格的规则集。由于 OpenAI 的人员无疑很聪明，我相信在 GPT 的 Codex 变体的 LLM 网关处，token 选择过程会偏向于适配这种结构，类似于其他约束（如 JSON 模式或必需的工具调用）的工作方式。

但把这个给其他任何模型，完全不知道这件事？补丁失败率会飙升。Grok 4 在我的基准测试中的补丁失败率是 50.7%，GLM-4.7 的是 46.2%。这些模型并不差，它们只是不懂这种语言。

Claude Code（以及大多数其他工具）使用 str\_replace：查找完全匹配的旧文本，替换为新文本。这个思路非常简单。但模型必须完美复现每个字符，包括空格和缩进。多个匹配？不被接受。“文件中未找到要替换的字符串”错误非常常见，甚至有

Cursor 训练了一个独立的神经网络 : 一个微调的 70B 模型，其全部工作是接收草稿编辑并正确合并到文件中。框架问题非常棘手，以至于一家资金最充足的 AI 公司之一决定再投入一个模型来解决它，即便如此，他们在自己的

表明，格式选择本身就使 GPT-4 Turbo 的成绩从 26%提升到 59%，但在相同格式下，GPT-3.5 的得分仅为 19%，因为它无法可靠地生成有效的差异。格式与模型同样重要。

JetBrains 的 Diff-XYZ 基准测试系统地证实了这一点：

在模型和用例中，没有单一的编辑格式占主导地位。

发现只有一个模型在真实编辑任务中达到了超过 60%的 pass@1 通过率。

正如你所见，对于“如何改变事物”这个简单问题的“最佳解决方案”并没有真正的共识。

我的 5c： 这些工具中没有一个能给模型一个稳定且可验证的标识符，用于它想要修改的代码行，同时不会浪费大量上下文且不需要依赖完美的记忆。 它们都依赖于模型重现它已经见过的内容。当它做不到时（而且它经常做不到），用户就会指责模型。

现在请耐心听我说。如果当模型读取文件或进行 grep 搜索时，每一行都会附带一个 2-3 字符的内容哈希值，会怎么样呢？

```
1:a3|function hello() {
2:f1|  return "world";
3:0e|}
```

当模型进行编辑时，会引用这些标签："替换第 2 行：f1，替换范围 1:a3 到 3:0e，在 3:0e 之后插入。"如果文件自上次读取后发生了变化，哈希值（乐观地）将不匹配，并且在任何内容被损坏之前就会拒绝该编辑。

如果他们能记住一个伪随机标签，很可能他们就知道自己在编辑什么。这样模型就不需要重现旧内容，或者更糟糕的是空白内容，来展示一个可信的“锚点”，以基于该锚点表达其修改。

1.  从 React 代码库中选取一个随机文件。
    
2.  通过一次编辑引入变异（被当作错误），其逆操作是我们可以预期的（例如：运算符交换、布尔值翻转、差一错误、移除可选链、重命名标识符）。
    
3.  用通俗易懂的英语描述该问题。
    

```
# Fix the bug in `useCommitFilteringAndNavigation.js`

A guard clause (early return) was removed.

The issue is in the `useCommitFilteringAndNavigation` function. 
Restore the missing guard clause (if statement with early return).
```

自然地，我们并不期望这里有 100%的成功率，因为模型可能会提出一个独特的解决方案，不一定是完全相同的文件，但这些 bug 的机械性足够强，以至于大多数时候，修复方法就是恢复我们的突变。

每个任务3次运行，每次运行180个任务。每次使用全新的代理会话，四个工具（读取、编辑、写入）。我们仅提供临时工作区，传递提示词，代理停止后，对比格式化前后的原始文件。

16 个模型、3 种编辑工具，结果清晰明了：patch 是几乎所有模型中最差的格式，大多数情况下 hashline 与 replace 持平或更优，最弱的模型提升最显著。Grok Code Fast 1 的表现从 6.7%提升至 68.3%，提升了十倍，这是因为 patch 格式的灾难性失败导致模型的实际编码能力几乎完全被机械性编辑失败所掩盖。MiniMax 的表现翻倍以上。Grok 4 Fast 的输出 token 数量下降了 61%，因为它不再在重试循环中消耗 token。

Gemini 的成功率提高 8%，这比大多数模型升级带来的提升更大，并且训练算力成本为零。只需进行少量实验（并且花费了约 300 美元用于基准测试）。

通常，模型在理解任务方面并不存在不可靠的问题，而是在表达自身时存在不可靠的问题。你在把起落架的问题归咎于飞行员。

未被限流。未被警告。已禁用。用于运行基准测试：同一个基准测试显示 Gemini 3 Flash 以一项新技术达到了 78.3% 的成绩，该技术比他们的最佳尝试高出 5.0 个百分点。我甚至不知道这是为了什么。

这就是为什么这是倒退的原因。我刚刚证明了，一种不同的编辑格式可以将他们自己的模型提升 5 到 14 个百分点，同时将输出 token 减少约 20%。这不是威胁，而是免费的研发（R&D）。

没有厂商会为竞争对手的模型进行测试框架优化。Anthropic 不会为 Grok 调优。xAI 不会为 Gemini 调优。OpenAI 不会为 Claude 调优。但一个开源框架会为所有这些模型进行调优，因为贡献者会使用不同的模型并修复他们个人遇到的问题。

模型是护城河，框架是桥梁。烧桥就意味着更少的人愿意跨越。将框架视为已解决的问题，甚至认为其无关紧要，是非常目光短浅的。

我有游戏安全领域的背景。作弊者对整个生态系统造成极大破坏。当然，他们会被封禁、追捕、起诉，但一个众所周知的秘密是，最终安全团队会问：“酷！想不想给我们展示你是怎么绕过那个的？”然后他们就会加入防御工作。

当有人滥用你的 API 并利用其工具积累了大量粉丝时，正确的回应是“告诉我们更多”，而不是“让我们大规模封禁数千人；不过，如果想撤销封禁，麻烦在私信中请求”。

测试框架问题是真实存在且可衡量的，而且是目前最具创新杠杆作用的地方。“酷炫演示”与“可靠工具”之间的差距并非源于模型的神奇之处，而是在工具边界上进行的谨慎、相当枯燥但基于经验的工程工作。

测试框架问题将得到解决。问题在于，这个问题是由一家公司私下为单个模型解决，还是由一个社区公开为所有模型解决。
