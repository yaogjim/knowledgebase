我们推出了 本周作为一种无代码方式来构建代理。代理构建器的一个关键部分是它的记忆系统。在这篇博客中，我们将介绍我们优先考虑记忆系统的理由、构建该系统的技术细节、构建记忆系统的经验教训、记忆系统的功能，以及讨论未来的工作。

LangSmith Agent Builder 是一个无代码代理构建器。它基于 Deep Agents 系统。它是一个面向技术轻量级公民开发者的托管式网络解决方案。在 LangSmith Agent Builder 中，构建者将创建一个代理来自动化特定的工作流程或他们日常的一部分。示例包括电子邮件助手和文档助手等。

一开始我们就有意识地选择将记忆作为平台的一部分优先考虑。这并非一个显而易见的选择——大多数 AI 产品最初推出时都没有任何形式的记忆功能，即使后来添加了它就像有些人可能预期的那样。我们优先考虑它的原因是用户的使用模式。

与 ChatGPT、Claude 或 Cursor 不同，LangSmith Agent Builder 并非通用代理。相反，它专门设计用于让构建者为特定任务定制代理。在通用代理中，你会执行各种可能完全无关的任务，因此一次会话中从代理获得的经验可能对下一次会话不适用。当 LangSmith 代理执行任务时，它会反复执行相同的任务。一次会话的经验能更高比例地应用到下一次会话中。事实上，如果没有记忆功能，用户体验会很糟糕——这意味着你不得不在不同会话中反复向代理重复说明。

当思考记忆对 LangSmith 代理到底意味着什么时，我们转向了第三方对记忆的定义。The 将代理的记忆分为三类：

-   程序性：可应用于工作记忆以确定主体行为的一组规则
    
-   语义：关于世界的事实
    
-   情景式：智能体的过去行为序列

我们在 Agent Builder 中将记忆表示为一组文件。这是一个刻意的选择，目的是利用模型是 。通过这种方式，我们可以轻松地让代理读取和修改其记忆，而无需给它专门的工具——我们只需要给它文件系统的访问权限！

在可能的情况下，我们尽量使用行业标准。我们使用 来定义代理的核心指令集。我们使用 为代理提供针对特定任务的特定专业指令。目前没有子代理标准，但我们采用。对于 访问，我们使用一个自定义的 tools.json 文件。我们使用自定义 tools.json 文件而不是标准 mcp.json 的原因是，我们希望允许用户只给代理 MCP 服务器中的部分工具，以避免上下文溢出。

我们也允许用户（以及代理本身）向代理的内存文件夹写入其他文件。这些文件也可以包含代理在运行时可以引用的任意知识。代理会在工作时编辑这些文件，“”.

我们实际上并不使用真实的文件系统来存储这些文件。而是将它们存储在 Postgres 中，并以文件系统的形式暴露给代理。我们这样做是因为 LLMs 非常擅长处理文件系统，但从基础设施的角度来看，使用数据库更简单高效。这种“虚拟文件系统”是 \- 并且完全可插拔，因此你可以使用任何你想要的存储层（s3、MySQL 等）。

能够在不使用任何代码或领域特定语言（DSL）的情况下构建复杂智能体的原因是，我们在底层使用了类似 Deep Agents 这样的通用智能体框架。Deep Agents 抽象掉了大量复杂的上下文工程（比如、、以及），并让你通过相对简单的配置来操控你的智能体。

这些文件很好地对应到 COALA 论文中定义的内存类型。程序性记忆——驱动核心代理指令的东西——是 AGENTS.md 和 tools.json。语义记忆是代理技能和其他知识文件。唯一缺失的记忆类型是情景记忆，我们认为这种记忆对这类代理来说不如另外两种重要。

我们可以看看我们内部一直在使用的一个真实代理——一个 LinkedIn 招聘人员——它是基于 LangSmith Agent Builder 构建的。

-   AGENTS.md: 定义核心代理指令
    
-   子代理/ : 定义仅一个 LinkedIn 搜索子代理：在主代理完成搜索校准后，将启动该代理以寻找约 50 名候选人。
    
-   tools.json：定义一个可访问 LinkedIn 搜索工具的 MCP 服务器
    
-   目前内存里还有另外 3 个文件，代表不同候选人的 JD。由于我们和代理一起处理这些搜索，它已经更新并维护了这些 JD。

为了更具体地说明记忆怎么运作，我们可以用一个例子来讲解。

> 总结会议记录

代理生成段落摘要。你纠正它：“改用项目符号。”代理进行修改 为：

> \# 格式偏好 用户更喜欢用项目符号来做总结，而不是段落。

你让代理总结另一场会议。它读取自己的记忆并自动使用项目符号。不需要提醒。在本次会话中：“在最后单独提取行动项。” 记忆更新：

> \# 格式偏好 用户更喜欢用项目符号来做总结，而不是段落。 在末尾单独部分中提取行动项

这两种模式会自动生效。你需要随着新的边缘情况出现持续添加优化。

代理的记忆包含了更多的偏好、术语、区别、重复概念、会议处理以及通过使用积累的边界情况修正。这个记忆文件可能看起来像这样：

> \# 会议总结偏好 ## 格式 使用项目符号，而非段落 将行动项提取到末尾的单独部分 决定时用过去时态 在顶部包含时间戳 ## 会议类型 工程会议：突出技术决策及决策依据 计划会议：强调优先级和时间线 客户会议：脱敏敏感信息 短会（<10分钟）：只说重点 人们 Sarah Chen（工程负责人）- 专注于技术细节 Mike Rodriguez (产品经理) - 专注于业务影响 ...

AGENTS.md 是通过修正而非预先的文档自我构建的。我们通过迭代的方式逐步形成了一个足够详细的代理规范，在此过程中用户从未手动修改过 AGENTS.md。

构建一个能记住事情的智能体，最困难的部分是提示。几乎所有智能体表现不佳的情况，解决办法都是优化提示。通过这种方式解决的问题示例：

-   这个代理没有记得它应该什么时候（做）
    
-   这个代理人当时在回忆那些不该回忆的时候
    

-   客服人员不知道技能文件的正确格式
    
-   ……更多
    

我们有一个人全职负责提示记忆相关的工作（这在团队中占了很大比例）。

有几个文件需要遵守特定的模式（比如 tools.json 需要包含有效的 MCP 服务器，skills 需要有正确的前置内容等）。我们发现 Agent Builder 有时会忘记这一点，导致生成了无效的文件。我们添加了一个步骤来明确验证这些自定义结构，如果验证失败，就将错误返回给 LLM，而不是提交文件。

代理们在工作时会编辑自己的记忆。他们很擅长往文件里添加具体内容。不过，有一件事他们做得不好，就是知道什么时候该整合所学。比如：我的邮件助手有段时间开始列出所有应该忽略冷邮件的具体供应商，而不是更新自己以忽略所有冷邮件。

即使代理在工作时能够更新其记忆，但仍有几种情况，作为最终用户，我们觉得明确提示代理管理其记忆很有用。其中一个情况是在其工作结束时，反思对话内容并更新其记忆以记录可能遗漏的内容。另一个情况是提示它压缩其记忆，以解决它只记住具体案例而不进行概括的情况。

我们对记忆系统进行了所有编辑，使其进入人工参与模式——也就是说，在更新前需要明确的人工审核。这主要是为了最小化提示注入的潜在攻击向量。我们确实为用户提供了一种关闭该功能的方式（“YOLO 模式”），适用于用户对此不太担心的情况。

除了更好的产品体验，以这种方式呈现记忆还能实现很多事情。

无代码构建工具的问题之一是，它们要求你学习一种不熟悉的领域特定语言（DSL），而这种语言难以随着复杂度扩展。通过将代理表示为 Markdown 和 JSON 文件，代理现在采用的格式（a）对大多数技术小白来说是熟悉的，（b）更易于扩展。

记忆确实能带来更好的智能体构建体验。智能体构建是一个非常迭代的过程——很大程度上是因为直到你尝试后才知道智能体会做什么。记忆让迭代变得更容易，因为你不需要每次手动更新智能体配置，只需用自然语言给出反馈，它就能自动更新。

文件非常可移植！这让你可以轻松地将在代理构建器中构建的代理移植到其他框架（只要它们使用相同的文件规范）。出于这个原因，我们尽量使用尽可能多的标准规范。例如，我们希望能让在代理构建器中构建的代理轻松地在 Deep Agents CLI 中使用，或者完全在其他代理框架中使用，比如 Claude Code 或 OpenCode。

我们有很多内存改进想要实现，但在发布前没时间也没足够信心去完成。

COALA 记忆类型中，Agent Builder 缺少的是情景记忆：智能体的过去行为序列。我们计划通过将之前的对话作为文件暴露在文件系统中，使智能体能够与之交互来实现这一点。

现在，所有的记忆都在“热路径”（hot path）中更新，也就是代理运行时。我们想添加一个后台进程（可能是某种 cron 任务，大约每天运行一次），来回顾所有对话并更新记忆。我们认为这能捕捉到代理在当下未能识别的内容，并且对归纳特定的学习成果会特别有用。

我们想要引入一个明确的/remember 命令，这样你就可以提示代理回顾对话并更新它的记忆。我们发现自己偶尔会这样做，并且获益匪浅，因此希望让这个操作更简便、更鼓励大家使用。

虽然能够用 glob 和 grep 搜索记忆是个不错的起点，但在某些情况下，允许代理对其记忆进行语义搜索会带来一些优势。

现在，所有的记忆都是针对那个代理的。我们没有用户级或组织级记忆的概念。我们计划通过向代理暴露代表这些类型记忆的特定目录，并提示代理相应地使用和更新这些记忆来实现这一点。
