#### 核心内容

作者Dabit这篇文章教你怎么用Claude Agent SDK从零开始搭建一个代码审查Agent。以前你要自己写Agent的话，得不停地调用API，检查模型是不是要用工具，执行工具，再把结果喂回去，这个循环写起来特别烦。

SDK直接把这个循环封装好了，你只需要告诉它要干什么，它自己就能跑起来。

**入门示例**:
- 安装Claude Code CLI
- 创建项目，写几行代码让Claude列出当前目录文件
- 返回异步生成器，stream显示Claude在想什么、用什么工具

**代码审查Agent**:
- 指定目录，自动读代码文件
- 用grep搜索可疑模式（数组越界、空值检查、敏感信息等）
- 支持JSON Schema定义输出格式
- 返回结构化报告（问题列表、严重程度、文件位置、修复建议）

**高级特性**:
- **权限管理**: 默认需要批准，可设置自动批准读操作
- **子Agent**: 主Agent协调，委派给专门的安全Agent、测试Agent
- **不同模型**: 复杂任务用Opus，简单任务用Haiku省钱
- **Session管理**: 保存会话ID，Claude记住之前的上下文
- **Hooks机制**: 工具执行前后插入自定义逻辑（审计日志、拦截危险命令）
- **成本追踪**: 每次运行结束告诉你花了多少钱、用了多少token
- **MCP扩展**: 自定义工具（如计算代码复杂度）

#### 关键信息

- **内置工具**: 读文件、写文件、编辑代码、跑bash命令、搜索文件
- **JSON Schema**: 程序化处理结果（生成报告、触发告警）
- **子Agent架构**: 处理复杂项目的关键，可以分而治之
- **成本优化**: 用Haiku处理简单任务节省成本

#### 高价值信息

> "如果你想要更细粒度的控制，还能写个自定义的权限处理函数，比如允许读文件但禁止修改env配置文件这种规则。"

权限管理的灵活性对于企业级应用至关重要。SDK不仅提供了工具，还提供了安全框架。

- **自动化闭环**: 文案生成 → 评价 → 迭代 → 再生成
- **人类角色**: 不是执行，而是判断和把关
- **业务壁垒**: 独特的判断力和品味

#### 高价值信息

> "AI可以代替你说话，但是不能代替你表达你的思想，这是我们进行AI写作需要把关的地方。"

### 5. [企业Agent开发实践：基于Claude Agent SDK的完整案例](./04-工具使用与配置/通用/2026-01-09_dotey_朋友负责的团队面临的是一个真实的企业痛点_公司有完整的内部设计系统_Design_System_和私.md)

#### 核心内容

**企业痛点**: 公司有完整的内部设计系统（Design System）和私有前端框架，但这些代码从未被AI训练过，通用模型根本无法直接生成符合规范的代码。目标：做一个类似Lovable的工具，但用自己的Design System。

**技术实现**:
1. **推荐基于Claude Agent SDK**而非从零造轮子
   - Claude Code已验证可行
   - 开箱即用，内置工具足够
   - 可自定义工具、接入MCP、自定义Skill
   - 可接入国产兼容模型

2. **本地文件系统**: 给Agent一个本地文件系统（虚拟机或目录），每个会话独立环境，Agent可以自由读取、修改、编译代码

3. **私有组件学习**: 把Agent当作新员工，用高质量文档和参考代码教会它。把设计系统说明、组件列表、API文档全部Markdown化，让Agent按需检索

4. **质量保证**: "生成 → 验证 → 修复"自动化闭环
   - Lint静态检查
   - 编译验证
   - 视觉比对（Chrome DevTool MCP做截图对比）

**产品困境**:
系统跑通了，Demo很惊艳，但很快没什么人用。通过深度访谈发现：

- **习惯阻力**: 设计师和产品经理更习惯在Figma里工作，从舒适区跳到陌生区的门槛很高
- **80/20瓶颈**: Agent能实现80%的效果，但剩下20%需要花大量时间调整
- **信任问题**: 用户不完全信任Agent生成的代码

#### 关键信息

- **先跑通再优化**: 构建Agent最难的不是技术，而是完整跑通流程
- **MCP扩展**: 开源了代码 https://github.com/JimLiu/claude-agent-kit
- **产品 > 技术**: 技术成功了，但产品失败了

#### 高价值信息

> "初期大家觉得新鲜，但很快就弃用了。开始和他们一起深度复盘，发现问题根本不在技术，而在产品逻辑与用户习惯的错位。"

一个非常重要的教训：技术成功不等于产品成功。企业级应用不仅要解决技术问题，还要解决用户习惯、工作流程、信任等问题。
