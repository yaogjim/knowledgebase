# [Anthropic 的工程实践](engineering) ![](httpswww-cd

[Anthropic 的工程实践](/engineering) ![](https://www-cdn.anthropic.com/images/4zrzovbb/website/33b03d9dd1e6aec266ef22a616aec8f5676223f6-1000x1000.svg)

## AI 智能体的高效上下文工程

在提示工程成为应用人工智能领域焦点数年之后，一个新术语崭露头角： **上下文工程** 。使用语言模型进行构建的重点，已从寻找提示词的最佳表述，转向回答更宏观的问题：“怎样的上下文配置最有可能引导模型产生我们期望的行为？”

**上下文** 指的是从大型语言模型（LLM）采样时包含的令牌集合。当前面临的 **工程** 问题是在 LLM 固有约束条件下优化这些令牌的效用，以持续达成预期目标。有效驾驭 LLM 往往需要 *上下文思维* ——换言之：考量 LLM 在任何时刻可获取的整体状态，以及该状态可能引发的潜在行为。

在这篇文章中，我们将探讨新兴的语境工程艺术，并提供一个精炼的心智模型，用于构建可引导且高效的人工智能体。

## 语境工程与提示工程

在 Anthropic，我们将语境工程视为提示工程的必然演进。提示工程指的是为达成最佳效果而编写和组织 LLM 指令的方法（概述和实用策略请参阅 [我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview) ）。 **语境工程** 则是指在 LLM 推理过程中，策划和维护最优令牌（信息）集合的策略体系，这包括提示之外可能进入上下文的所有其他信息。

在 LLM 工程应用的早期阶段，提示工程是 AI 工程工作的核心组成部分，因为除了日常对话交互外，大多数应用场景都需要针对单次分类或文本生成任务优化的提示词。顾名思义，提示工程主要关注如何编写有效的提示词，尤其是系统提示词。但随着我们转向构建更强大的智能体——这些智能体需要在多轮推理和更长的时间跨度上运行——我们需要管理整个上下文状态的策略（包括系统指令、工具、 [模型上下文协议](https://modelcontextprotocol.io/docs/getting-started/intro) （MCP）、外部数据、消息历史记录等）。

在循环中运行的智能体会生成越来越多 *可能* 与下一轮推理相关的数据，这些信息必须被循环精炼。语境工程正是从不断演变的可能信息宇宙中，为有限上下文窗口筛选内容的 [艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en) 。

![Prompt engineering vs. context engineering](/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Ffaa261102e46c7f090a2402a49000ffae18c5dd6-2292x1290.png&w=3840&q=75)

与编写提示词这种离散任务不同，语境工程是迭代式的——每当我们决定向模型传递哪些信息时，就进入了信息策展阶段。

## 为何情境工程对构建强大智能体至关重要

尽管 LLMs 处理数据的速度越来越快、容量越来越大，但我们观察到它们和人类一样，在某个临界点会出现注意力涣散或思维混乱。针对“大海捞针”式基准测试的研究揭示了一个概念—— [语境衰减](https://research.trychroma.com/context-rot) ：当上下文窗口中的 token 数量增加时，模型从这些上下文中准确提取信息的能力反而会下降。

虽然某些模型的表现比其他模型更为平缓，但这一特性在所有模型中普遍存在。因此，必须将上下文视为边际收益递减的有限资源。如同人类拥有 [有限的工作记忆容量](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277) ，LLMs 在解析大量上下文时也需要消耗"注意力预算"。每个新增的标记都会消耗部分预算，这就要求我们更审慎地筛选可供 LLM 使用的标记。

这种注意力稀缺源于 LLMs 的架构限制。LLMs 基于 [Transformer 架构](https://arxiv.org/abs/1706.03762) ，该架构使得每个标记都能 [关注到上下文中的所有其他标记](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need) 。对于 n 个标记而言，这会产生 n²对相互关系。

随着上下文长度的增加，模型捕捉这些成对关系的能力会变得捉襟见肘，从而在上下文规模与注意力聚焦之间形成天然的张力。此外，模型的注意力模式源自训练数据分布，其中短序列通常比长序列更为常见。这意味着模型在处理跨上下文的依赖关系方面经验较少，且专门参数也更为匮乏。

像 [位置编码插值](https://arxiv.org/pdf/2306.15595) 这样的技术，通过让模型适应原本训练的较小上下文来处理更长的序列，尽管在标记位置理解上会有所下降。这些因素形成了性能梯度而非断崖式下跌：模型在较长上下文中仍保持强大能力，但在信息检索和长程推理方面的精确度可能较其在短上下文中的表现有所降低。

这些现实情况意味着，精心设计上下文工程对于构建强大智能体至关重要。

## 高效语境的结构剖析

考虑到 LLMs 受限于有限的注意力资源， *优秀* 的上下文工程意味着找到 *尽可能小* 的高信息量标记集合，以最大化实现预期结果的可能性。实施这一原则远比口头表述更为复杂，但在接下来的章节中，我们将阐述这一指导原则在实际应用中如何贯穿上下文的不同组成部分。

**系统提示** 必须极其清晰，使用简单直接的语言，以 *恰当的高度* 向智能体呈现思想。这个恰当高度是两种常见故障模式之间的黄金平衡点。一个极端是工程师在提示中硬编码复杂脆弱的逻辑来激发精确的智能体行为，这种做法会带来脆弱性并随时间增加维护复杂度。另一个极端是工程师有时提供模糊的高层指导，既无法为 LLM 提供明确的目标输出信号，又错误假设存在共享上下文。最佳高度在于取得平衡：既要足够具体以有效引导行为，又要保持足够灵活性为模型提供强大的启发式指导。

![Calibrating the system prompt in the process of context engineering.](/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F0442fe138158e84ffce92bed1624dd09f37ac46f-2292x1288.png&w=3840&q=75)

在光谱的一端，我们看到僵化的硬编码 if-else 式提示词，而在另一端，则是过于笼统或错误假设共享上下文的提示词。

我们建议将提示语组织成不同的部分（如 `<background_information>` 、 `<instructions>` 、 `## 工具指引` 、 `## 输出描述` 等），并使用 XML 标签或 Markdown 标题等技术来划分这些部分，尽管随着模型能力的提升，提示语的具体格式可能变得不那么重要。

无论你如何设计系统提示，都应致力于用最精简的信息完整勾勒出预期行为。（请注意，精简不等于简短；你仍需预先为智能体提供足够信息，确保其遵循既定行为模式。）最佳实践是先用最精简的提示在最优模型上测试任务表现，再根据初始测试发现的失败模式，逐步添加明确指令和示例来提升性能。

**工具** 使智能体能够与环境互动，并在工作过程中引入新的额外情境。由于工具定义了智能体与其信息/行动空间之间的契约，因此工具必须提升效率——既要返回具有令牌效率的信息，也要促进智能体的高效行为，这一点至关重要。

在 [为 AI 智能体编写工具——与 AI 智能体协作](https://www.anthropic.com/engineering/writing-tools-for-agents) 中，我们探讨了如何构建既能让 LLMs 充分理解、又实现功能最小重叠的工具。与设计良好的代码库功能类似，工具应当具备自包含性、错误鲁棒性，且用途极其明确。输入参数同样需要具备描述性、无歧义性，并能充分发挥模型的内在优势。

我们最常见的失败模式之一，就是工具集过于臃肿——要么覆盖过多功能，要么导致选择工具时出现模糊决策点。如果人类工程师都无法在特定情境下明确判断该使用哪个工具，就更不能指望 AI 智能体做得更好。正如后文将讨论的，为智能体精心设计最小可行工具集，还能在长期交互中实现更可靠的上下文维护与精简。

提供示例，即所谓的小样本提示，是我们持续强烈推荐的公认最佳实践。然而，团队常会将一堆边缘案例塞进提示中，试图穷尽 LLM 执行特定任务时应遵循的所有规则。我们不建议这样做，而是主张精心筛选一组多样化的典型示例，有效展现智能体的预期行为。对 LLM 而言，示例正是"一图胜千言"的生动写照。

我们在处理上下文的不同组成部分（系统提示 **、** 工具 **、** 示例 **、** 消息历史等）时的总体指导原则是：要深思熟虑，确保上下文信息丰富且紧凑。现在，让我们深入探讨在运行时动态检索上下文的方法。

在 [构建高效 AI 智能体](https://www.anthropic.com/research/building-effective-agents) 时，我们曾强调基于 LLM 的工作流与智能体之间的差异。自该文发布以来，我们逐渐倾向于采用 [简明定义](https://simonwillison.net/2025/Sep/18/agents/) 来界定智能体：即 LLM 在循环中自主使用工具的系统。

在与客户的合作中，我们观察到业界正逐渐统一于这一简洁范式。随着底层模型能力不断增强，智能体的自主性水平得以提升：更聪明的模型使智能体能够独立应对复杂问题空间，并具备从错误中自我修复的能力。

如今，工程师们对智能体上下文设计的思考方式正在发生转变。当前，许多 AI 原生应用采用基于嵌入的预推理检索机制，为智能体提供关键上下文以进行推理。随着该领域向更具自主性的方法转型，越来越多的团队开始通过"即时"上下文策略来增强这些检索系统。

采用“即时”方法构建的智能体并非预先处理所有相关数据，而是维护轻量级标识符（文件路径、存储查询、网页链接等），并通过工具在运行时动态将这些数据加载到上下文中。Anthropic 的智能编码解决方案 [Claude Code](https://www.anthropic.com/claude-code) 正是运用这种方法对大型数据库进行复杂数据分析。该模型能编写针对性查询、存储结果，并利用 head、tail 等 Bash 命令分析海量数据，而无需将完整数据对象载入上下文。这种方式与人类认知模式相呼应：我们通常不会记忆全部信息库，而是通过文件系统、收件箱、书签等外部组织与索引系统，按需调取相关信息。

除了存储效率之外，这些引用的元数据还提供了一种有效优化行为的机制，无论是明确提供的还是直观的。对于在文件系统中运行的智能体而言，位于 `tests` 文件夹中名为 `test_utils.py` 的文件，其用途与位于 `src/core_logic/` 目录下同名文件截然不同。文件夹层级结构、命名规范和时间戳都提供了重要信号，帮助人类和智能体理解如何以及何时利用这些信息。

让智能体自主导航和检索数据还能实现渐进式信息呈现——换言之，通过探索让智能体逐步发现相关上下文。每次交互产生的上下文都会为下一个决策提供依据：文件大小暗示复杂程度；命名规则暗含用途；时间戳可作为相关性的参考指标。智能体能够逐层构建认知，仅在工作记忆中保留必要信息，并利用笔记策略实现更持久的记忆。这种自我管理的上下文窗口使智能体始终聚焦于相关子集，而非淹没在详尽却可能无关的信息洪流中。

当然，这需要权衡取舍：运行时探索比检索预计算数据更慢。不仅如此，还需要经过深思熟虑的工程化设计，确保 LLM 具备合适的工具和启发式方法，以有效驾驭其信息环境。若缺乏正确引导，智能体可能因误用工具、陷入死胡同或未能识别关键信息而浪费上下文资源。

在某些场景下，最有效的智能体可能采用混合策略：预先检索部分数据以保证速度，同时根据实际情况自主进行深度探索。自主性的"恰当"程度取决于具体任务。Claude Code 正是采用这种混合模式的智能体： [CLAUDE.md](http://claude.md) 文件会被直接预加载至上下文，而 glob 和 grep 等基础工具则使其能够实时导航环境并检索文件，从而有效规避索引过时和复杂语法树的问题。

混合策略可能更适合内容动态性较低的领域，例如法律或金融工作。随着模型能力的提升，智能体设计将趋向于让智能模型自主发挥智能，逐步减少人工干预。鉴于该领域的快速发展，"采用最简单有效的方案"很可能仍是基于 Claude 构建智能体的团队的最佳建议。

### 长周期任务的情境工程

长周期任务要求智能体在行动序列中保持连贯性、上下文一致性以及目标导向行为，这些序列的标记数量往往超出 LLM 的上下文窗口容量。对于持续数十分钟至数小时的连续性工作（例如大型代码库迁移或综合性研究项目），智能体需要采用专门技术来突破上下文窗口的尺寸限制。

等待更大的上下文窗口看似是显而易见的策略。但在可预见的未来，各种规模的上下文窗口都难免遭遇信息污染与相关性难题——至少在追求极致智能体表现的场景下如此。为了让智能体能在更长时间跨度中高效运作，我们开发了若干直接应对上下文污染限制的技术：信息压缩、结构化笔记以及多智能体架构。

**Compaction**

压缩是指当对话接近上下文窗口限制时，对其内容进行总结，并利用摘要重新开启新上下文窗口的做法。压缩通常是上下文工程中的首要手段，旨在提升长期连贯性。其核心在于以高保真方式提炼上下文窗口的内容，使智能体能够以最小性能损耗持续运作。

例如在 Claude Code 中，我们通过将消息历史传递给模型进行总结和压缩关键细节来实现这一功能。模型会保留架构决策、未解决的错误和实现细节，同时舍弃冗余的工具输出或消息。随后，智能体可以基于压缩后的上下文加上最近访问的五个文件继续工作。用户既能保持工作连续性，又无需担心上下文窗口的限制。

压缩的艺术在于取舍之道，过度激进的压缩可能导致微妙却关键的上文信息丢失，而这些信息的重要性往往在后续环节才显现。对于实现压缩系统的工程师，我们建议在复杂的智能体运行轨迹上精心调试提示词：先以最大化召回率为目标，确保压缩提示能捕捉轨迹中的每个相关信息片段，再通过迭代剔除冗余内容来提升精准度。

一个唾手可得的冗余内容示例是清理工具调用和结果——当工具已在消息历史记录深处被调用后，智能体为何还需要再次查看原始结果？最安全、最轻量级的压缩方式之一就是清理工具结果，该功能最近作为 [Claude 开发者平台的一项特性](https://www.anthropic.com/news/context-management) 推出。

**结构化笔记**

结构化笔记，或称智能体记忆技术，是一种让智能体定期将笔记写入上下文窗口外持久化存储的方法。这些笔记会在后续需要时重新载入上下文窗口中使用。

这种策略能以最小开销实现持久记忆。如同 Claude Code 创建待办清单，或您的自定义智能体维护 NOTES.md 文件，这种简单模式能让智能体在复杂任务中追踪进度，保持关键上下文和依赖关系——这些信息原本可能在数十次工具调用中丢失。

[Claude 玩《宝可梦》](https://www.twitch.tv/claudeplayspokemon) 展示了记忆如何改变智能体在非编程领域的能力。该智能体在数千次游戏步骤中保持精确记录——追踪诸如"在最近 1234 步中，我一直在 1 号道路训练宝可梦，皮卡丘已提升 8 级，距离目标 10 级还差 2 级"等目标。在没有任何记忆结构提示的情况下，它能绘制已探索区域的地图，记住已解锁的关键成就，并保存战斗策略的战术笔记，帮助它了解哪些攻击对不同对手最有效。

在上下文重置后，智能体会读取自己的笔记，继续执行长达数小时的训练序列或地牢探索。这种跨越摘要步骤的连贯性，使得实现长远策略成为可能——若仅依靠 LLM 上下文窗口保存所有信息，这类策略将无法实现。

在我们推出 [Sonnet 4.5](https://www.anthropic.com/effective-context-engineering-for-ai-agents) 版本的同时，我们于 Claude 开发者平台发布了 [记忆工具](http://anthropic.com/news/context-management) 的公开测试版，通过基于文件的系统更便捷地存储和调用上下文窗口之外的信息。这使得智能体能够逐步构建知识库，跨会话维持项目状态，并参考先前工作内容，而无需将所有信息都保留在上下文中。

**子代理架构**

子代理架构为解决上下文限制提供了另一种思路。不同于单一代理试图在整个项目中维持状态，专业化的子代理能够通过独立的上下文窗口处理特定任务。主代理负责高层规划协调，而子代理则执行深度技术工作或使用工具查找相关信息。每个子代理可能进行大规模探索（消耗数万甚至更多 token），但最终仅返回其工作的精炼摘要（通常为 1000-2000token）。

这种方法实现了清晰的职责分离——详细的搜索上下文被隔离在子智能体中，而主导智能体则专注于综合与分析结果。正如 [我们如何构建多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system) 中所讨论的，这种模式在复杂研究任务上相比单智能体系统展现出显著提升。

选择哪种方法取决于任务特性。例如：

- 压缩机制在需要频繁来回交流的任务中维持对话的流畅性；
- 笔记记录在具有明确里程碑的迭代开发中表现出色；
- 多智能体架构擅长处理需要并行探索才能获得回报的复杂研究与分析任务。

即便模型持续改进，在长时间互动中保持连贯性的挑战，仍是构建更高效智能体的核心难题。

## Conclusion

语境工程代表着我们构建 LLMs 方式的根本性转变。随着模型能力不断增强，挑战不再仅仅是设计完美的提示——而是需要精心策划哪些信息能在每个步骤进入模型有限的注意力预算。无论您是在为长期任务实施信息压缩、设计令牌高效的工具，还是让智能体能够即时探索环境，指导原则始终如一：找到能最大化实现预期结果的最小高信号令牌集合。

我们概述的这些技术将随着模型进步而持续演化。我们已经看到，更智能的模型需要更少的规范性工程，使得智能体能够以更高自主性运作。但即使在能力扩展的同时，将上下文视为珍贵而有限的资源，仍将是构建可靠高效智能体的核心所在。
