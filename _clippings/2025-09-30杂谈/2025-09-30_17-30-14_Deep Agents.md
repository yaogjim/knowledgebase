# Deep Agents

#### **Deep Agents 概念简介**
Deep Agents 是一种高级的智能代理（Agent）架构，它通过结合规划工具、子代理、文件系统访问和详细的系统提示，克服了简单工具调用循环的局限性，使其能够处理更长、更复杂的任务。

*   **核心定义**：Deep Agents 是在简单的工具调用循环基础上，内置了特定工具和行为的智能代理。
*   **四大核心组件**：
    *   **规划工具（Planning Tool）**：包含一个待办事项列表（to-do list），用于任务规划。
    *   **文件系统（File System）**：用于存储和读取上下文信息，实现持久化记忆。
    *   **子代理（Sub Agents）**：能够为独立的、隔离的任务生成专门的子代理。
    *   **系统提示（System Prompt）**：一个非常详细的指令，用于指导代理的行为。

#### **代码实践：创建 Deep Agent**
视频通过 `create_deep_agent` 函数展示了如何实例化一个 Deep Agent，并介绍了其关键参数，如工具（tools）、指令（instructions）和子代理（subagents）。

*   **核心函数**：使用 `create_deep_agent` 函数来构建代理。
*   **关键参数**：
    *   `tools`：传递给代理使用的工具集。
    *   `instructions`：为代理提供自定义的指令，这些指令会成为系统提示的一部分。
    *   `subagents`：定义代理可以调用和分派工作的子代理。

#### **架构核心：Agent Builder 与中间件（Middleware）**
新版 Deep Agents 构建于 LangChain V1 之上，其核心是 `agent_builder` 函数和中间件（Middleware）这一新概念。中间件以可堆叠的方式为基础代理添加复杂功能。

*   **核心构建器**：`agent_builder` 函数是创建代理的核心。
*   **中间件概念**：中间件是 LangChain V1 引入的核心抽象，它能够修改和增强一个简单的 ReAct 代理。
*   **功能实现**：Deep Agents 的四大核心功能（规划、文件系统、子代理、摘要）都是通过各自的中间件来实现的。
*   **可堆叠性**：中间件可以像堆积木一样层层叠加，其应用顺序决定了系统提示（System Prompt）的组合顺序。

#### **具体中间件实现细节**
详细介绍了规划、文件系统和子代理等功能的中间件是如何通过扩展代理的状态（State）、添加工具（Tools）和修改模型请求（Model Request）来实现的。

*   **PlanningMiddleware**：
    *   扩展代理状态，增加一个待办事项列表（todos）。
    *   添加 `write_todos` 工具，允许代理管理这个列表。
    *   修改模型请求，在系统提示中加入如何使用规划工具的指令。
*   **FilesystemMiddleware**：
    *   扩展代理状态，增加一个文件字典（files）。
    *   添加文件操作工具（如 `ls`, `read_file`, `write_file`）。
    *   修改模型请求，在系统提示中加入文件系统工具的使用说明。
*   **SubAgentMiddleware**：
    *   通过 `create_task_tool` 创建一个通用的“任务工具”（task tool）。
    *   该工具允许主代理调用和分派任务给不同的子代理。
    *   子代理可以是通用的，也可以是为特定领域任务定制的。

#### **高级功能与扩展性**
介绍了 Deep Agents 的高级功能，如“人在回路”（Human-in-the-Loop）中间件，并强调了整个架构的灵活性和可扩展性。

*   **人在回路（Human-in-the-Loop）**：提供一个中间件，允许在执行关键任务（如发送邮件）前暂停代理，并请求人类用户批准、编辑或拒绝该操作。
*   **自定义与扩展**：开发者可以轻松移除不需要的默认中间件，或添加自己编写的自定义中间件，以满足特定的业务需求。

### **详细内容阐述**

#### **Deep Agents 概念简介**

演讲者首先解释了 Deep Agents 的核心思想。最简单的智能代理形式是使用一个大型语言模型（LLM）在循环中调用工具。然而，这种“浅层”架构在处理长期、复杂的任务时会遇到困难。为了解决这个问题，像 "Deep Research"、"Manus" 和 "Claude Code" 这样的应用通过实现一种更复杂的架构来增强代理的能力。

这种高级架构就是 Deep Agents，它由四个关键部分组合而成：
1.  **规划工具（Planning Tool）**：它不仅仅是调用工具，还包含一个待办事项列表，帮助代理制定和跟踪计划。
2.  **文件系统（File System）**：允许代理将信息“卸载”到外部文件中，以便稍后读取。这解决了上下文窗口的限制，为代理提供了长期记忆。
3.  **子代理（Sub Agents）**：主代理可以将复杂的任务分解，并生成专门的子代理来处理这些独立的子任务。
4.  **详细的系统提示（System Prompt）**：一个精心设计的、非常详细的系统级指令，它精确地指导代理如何思考和行动。

这套架构的目标是让开发者能够轻松构建出功能强大的智能代理。

#### **代码实践：创建 Deep Agent**

接下来，演讲者展示了如何通过代码来使用 Deep Agents。核心是一个名为 `create_deep_agent` 的预构建函数。通过调用这个函数，可以轻松创建一个 Deep Agent 实例。

在代码示例中，他指出了几个可以传递给该函数的关键参数：
*   `tools=[internet_search]`：这是一个工具列表，定义了代理可以使用的外部工具，例如进行互联网搜索。
*   `instructions=research_instructions`：可以传入自定义的指令字符串，这些指令会被整合到代理的系统提示中，从而定制代理的行为。例如，可以指示它“你是一个专家级研究员”。
*   `subagents=[critique_sub_agent, research_sub_agent]`：这是一个子代理列表。主代理可以根据任务需要，决定调用哪个子代理来执行具体工作。

#### **架构核心：Agent Builder 与中间件（Middleware）**

演讲者深入讲解了 Deep Agents 的底层实现。他指出，新版本的 Deep Agents 是基于即将发布的 LangChain V1 构建的，并引入了一个名为“中间件（Middleware）”的核心概念。

他解释道，`create_deep_agent` 函数内部实际上调用了一个更核心的 `agent_builder` 函数。在这个构建器函数中，可以看到 Deep Agents 的核心功能——规划、文件系统访问、子代理管理以及为防止上下文过长而设的摘要功能——都是通过一系列中间件来实现的。

中间件的一个重要特性是**可堆叠性（stackable）**。这意味着你可以定义任意数量的中间件，并将它们按顺序应用到一个基础的 ReAct 代理上。每个中间件都会对代理的功能进行修改或增强。例如，在代码中，`PlanningMiddleware`、`FilesystemMiddleware` 和 `SubAgentMiddleware` 被依次应用。这种顺序很重要，因为它决定了最终生成的系统提示中各个功能模块指令的排列顺序。

#### **具体中间件实现细节**

为了让观众更清晰地理解中间件的工作原理，演讲者逐一剖析了几个关键的中间件：

*   **PlanningMiddleware (规划中间件)**
    这个中间件做了三件事：首先，它通过 `state_schema` 扩展了代理的状态（State），为其添加了一个名为 `todos` 的待办事项列表。其次，它向代理的工具集中添加了一个 `write_todos` 工具，让代理能够创建和更新这个列表。最后，它通过 `modify_model_request` 函数，在原始的系统提示末尾追加了一段专门的指令，告诉代理如何使用 `write_todos` 工具来管理任务。

*   **FilesystemMiddleware (文件系统中间件)**
    与规划中间件类似，它首先扩展了代理的状态，增加了一个用于存储文件的 `files` 字典。然后，它为代理提供了一整套文件操作工具，包括 `ls`（列出文件）、`read_file`（读取文件）、`write_file`（写入文件）和 `edit_file`（编辑文件）。最后，它同样会修改系统提示，加入关于如何与这个私有文件系统交互的详细说明。

*   **SubAgentMiddleware (子代理中间件)**
    这个中间件的实现更为复杂。它动态地创建了一个名为“task tool”的工具。这个工具的作用是充当一个任务分发器。当主代理决定需要将一个任务委托出去时，它会调用这个“task tool”，并指定要使用的子代理类型以及任务的具体描述。
    子代理分为两类：
    1.  **通用子代理（general-purpose sub-agent）**：默认情况下，每个 Deep Agent 都会有一个通用子代理，它继承了主代理的所有工具，用于处理没有特定子代理可以处理的常规任务。
    2.  **定制子代理**：开发者可以定义具有特定工具集、模型或指令的专用子代理。例如，可以创建一个只负责代码审查的子代理。此外，如果开发者已经有了一个用 LangGraph 构建的复杂流程图（Graph），也可以直接将其作为一个“自定义子代理”封装起来，供主代理调用。

#### **高级功能与扩展性**

最后，演讲者介绍了一些高级功能，并再次强调了该架构的灵活性。

*   **Human-in-the-Loop Middleware (人在回路中间件)**
    对于一些需要高度安全性的“关键任务”（mission-critical），比如自动发送邮件或修改生产环境数据，开发者可能希望在执行前进行人工确认。`HumanInTheLoopMiddleware` 就是为此设计的。通过配置，你可以指定当代理尝试调用某个特定工具时，流程会暂停，并等待人类用户的指令。人类用户可以选择批准（approve）、编辑后批准（edit）或拒绝并提供反馈（respond）。

*   **架构的灵活性**
    整个 Deep Agents 的设计是模块化的。如果你构建的代理不需要文件系统功能，你可以在创建时从中间件列表中移除 `FilesystemMiddleware`。同样地，你也可以非常方便地编写自己的中间件，来为代理添加全新的功能。这使得 Deep Agents 不仅是一个功能完备的开箱即用方案，也是一个高度可扩展的开发框架。

# **Deep Agents：架构深度解析**

#### **引言：Deep Agents 概念简介**

演讲者：我们重写了 LangChain 的 Deep Agents 包，使其构建于即将发布的 LangChain V1 Alpha 版本之上。在这段视频中，我将带你深入了解我们所做的改动，以及这个更新版本的 Deep Agents 为何具有更强的扩展性。

在深入代码之前，让我们快速回顾一下什么是 Deep Agents。

我喜欢将 Deep Agents 看作是内置了一些特定工具和行为的、简单的工具调用循环代理。具体来说，它开箱即用地集成了以下四个核心组件：

1.  **规划工具（Planning Tool）**：带有一个待办事项列表（to-do list），用于任务规划和跟踪。
2.  **文件系统（File System）**：允许代理将上下文信息存储到外部，以便后续读取，从而实现长期记忆。
3.  **子代理（Sub Agents）**：能够为独立的、隔离的任务生成专门的子代理。
4.  **详细的系统提示（System Prompt）**：一个非常详尽的系统级指令，用于精确地指导代理的行为。

这些工具在像 Manus 和 Claude Code 这样的产品中已被证明非常有效。我们开发 Deep Agents 这个包的目标，就是为了让像你们这样的开发者能够轻松地构建出功能强大的智能代理。

#### **代码实践：创建 Deep Agent**

演讲者：好了，让我们深入代码部分。

我们来看看如何使用 Deep Agents。在我们的代码库中，有一个预构建的函数叫做 `create_deep_agent`。你将使用这个函数来创建你的 Deep Agents。

在这里，我们可以看到一些你可能会传入的参数。当然，你需要为你代理传入一些工具。你也可以传入自定义的指令，还可以传入子代理，你的 Deep Agent 之后可以调用这些子代理并把工作分派给它们。

#### **架构核心：Agent Builder 与中间件（Middleware）**

演讲者：让我们仔细看看 Deep Agents 是如何被创建的。我真正想关注的函数是我们的 `agent_builder`（代理构建器）。

让我们详细了解一下这个 `agent_builder` 函数是如何工作的。我们首先要考虑的第一个参数是模型（model）。默认情况下，我们使用 `sonnet-4`，但你可以传入任何你想使用的模型。

这一代的 Deep Agents 是建立在 LangChain V1 之上的。而 LangChain V1 在代理构建中引入了一个新的核心概念，叫做“中间件”（Middleware）。我们最近发布了一篇详细的博客和视频，深入探讨了中间件的工作原理，如果你想全面了解中间件的功能，我强烈推荐你去看看。

简单来说，中间件能够修改一个简单的 ReAct 代理。我们稍后会看到具体是如何实现的。首先需要注意的重要一点是，中间件是一个可堆叠的抽象概念（stackable abstraction）。这意味着你可以定义任意数量的中间件，并将它们按顺序应用到 `create_agent` 函数上，而我们现在正是这么做的。

正如我之前提到的，有几个不同的支柱构成了 Deep Agent。
1.  首先是代理有能力创建并遵循一个计划。
2.  其次是代理可以访问一个文件系统。
3.  第三是代理能够为隔离的子任务生成子代理。

我们所做的就是为这三个功能中的每一个都编写了一个自定义的中间件。让我们逐一详细分析，看看它们是如何工作的。

#### **具体中间件实现细节**

演讲者：点击进入我们的 **PlanningMiddleware（规划中间件）**，可以看到它虽然很短，但功能强大。它做的第一件事是扩展代理的状态模式（state schema），为其添加了一个待办事项列表。这是很重要的一点，中间件现在被用来扩展代理的状态模式。看看这个 `PlanningState`，就像之前一样，它增加了一个 `todos` 列表。

除了扩展状态模式，中间件还可以扩展工具的数量以及你的 ReAct 代理可以使用的具体工具。在这种情况下，对于规划功能，我们只需要一个工具：写入待办事项列表的能力，或者更具体地说，写入我们刚刚添加到状态模式中的 `todos` 键的能力。我们的 `write_todos` 工具正是这样做的，它允许我们用模型创建的待办事项来更新我们的状态。

我们在这里做的最后一件事也非常重要。我们重写了 `modify_model_request` 函数，并在系统提示的末尾附加了一个自定义的提示，其中包含了关于代理应如何使用 `write_todos` 工具的指令。这一点至关重要。仅仅扩展模式并给模型一个工具而不给任何指令，效果并不好。在这里，我们有系统提示，它详细说明了如何使用 `write_todos` 工具，而这个提示是作为此中间件的一部分提供给代理的。

现在让我们看看我们的 **FilesystemMiddleware（文件系统中间件）**。就像上面一样，文件系统中间件继承自 `AgentMiddleware`，这使得它能够用文件系统状态来扩展我们的状态模式。这个状态只包含一个 `files` 键，它是一个字典。不同之处在于，我们的代理与这些文件交互的方式有很多种，而不是像之前那样只有一个工具。这些交互方式体现在我们添加到文件系统中间件中的不同工具里。我们可以列出文件，可以将特定文件读入上下文，可以写入新文件以存储信息，还可以编辑现有文件来更新其中的信息。

就像之前一样，我们的中间件允许我们修改模型请求本身。我们在这里附加了一个文件系统提示，其中包含了关于如何使用这些工具来更新本地文件系统的具体指令。

记住，中间件是可堆叠和可扩展的。你可以向代理添加不同的中间件，它们会按照添加的顺序被应用。这对我们来说意味着，我们的系统提示会首先被我们的规划指令扩展，然后是文件系统指令，再然后是我们的子代理指令。

现在让我们仔细看看我们的 **SubAgentMiddleware（子代理中间件）**。这一个要复杂一些，我们可以看到它实际上接受了几个参数。具体来说，它接受一个默认子代理工具的列表，这个列表会被传递给一个我们创建的默认子代理。它还接受一个具体定义的子代理的列表。

在这个中间件中，我们创建了一个“任务工具”（task tool），并将这个工具绑定到我们的代理上让其调用。这个任务工具附带了一个任务系统提示，其中包含了如何调用任务工具的额外信息，以及主代理究竟应该在何时选择生成子代理。

#### **高级功能与扩展性**

演讲者：我们来看看 `get_agents` 函数。可以看到，我们也在子代理中使用了中间件的概念。每个在 Deep Agent 中创建的子代理都会获得一些默认的中间件，包括规划、文件系统，还有摘要功能。我们还没有明确讨论过摘要功能，但它的作用是，当上下文窗口超过一定数量的 token 时，我们会通过摘要来自动压缩我们的对话历史，同时保留一定数量的消息，让我们能看到最近发生了什么。

现在我们来构建我们的子代理。每个 Deep Agent 默认都会得到一个“通用”（general-purpose）子代理，它拥有与主代理相同的工具。根据我的经验，我们创建子代理主要有两个原因。一个是为了隔离上下文，这正是通用子代理真正有用的地方。就像我说的，它拥有和主代理一样的工具，但可以被赋予一个单一的、狭窄的、隔离的任务来完成。当它完成这个任务时，它可以向主代理返回一个全面的响应，完全回答了问题，但没有任何来自中间工具调用、中断或其他浪费上下文的冗余信息。从长远来看，这帮助我们节省了大量的 token 和时间。

我通常创建子代理的第二个原因，是当我想给一个子代理一个专注的领域任务，让它在这方面做得特别好。这通常意味着一个定制的、狭窄的提示，以及一套专门针对该任务的特定工具。这些子代理是从传递给 `create_deep_agent` 的列表中创建的。

指定这种领域特定子代理有两种方式。一种是从头开始创建一个工具调用子代理。这个子代理会得到一个自定义的提示，它还会得到一个子代理可以使用的工具列表，请注意，这个工具列表可以与主代理拥有的工具完全不同。你还可以为这个子代理指定一个自定义模型。

正如我之前提到的，我们的子代理也使用中间件。你可以指定任何你想要的预构建或自定义的中间件，来扩展状态或为子代理提供更多工具。

你还可以创建更灵活的自定义子代理。我们从早期 Deep Agents 版本中收到的一个反馈是，很多人已经创建了 LangGraph 的计算图（Graph），他们希望将这些图作为子代理暴露给他们的主代理。你可以通过将可运行的图（runnable graph）直接传递到一个 `CustomSubAgent` 中来实现这一点。

总而言之，SubAgentMiddleware 所做的就是构建一个子代理列表，并通过“任务工具”来暴露这些子代理。这样，每当你的主代理决定需要启动一个任务时，它就会调用任务工具，指定它想要调用的子代理类型，并传递任何相关信息给那个子代理。然后你的子代理会去完成任务，并向主代理返回一个全面的响应，而不会有任何中间的冗余信息。

回到我们的 `agent_builder`，这就是 Deep Agents 的主要内容。我们刚刚讨论了所有三个支柱，它们现在都是通过中间件这个抽象来实现的。这里的美妙之处在于，我们也独立地暴露了每一个中间件。假设你构建了一个代理，并且你很确定由于某种原因它不需要文件系统，但你认为它确实可以从一些规划功能中受益。你可以直接从我们的包中导入 `PlanningMiddleware`，然后只把这个中间件添加到你的代理中。

我们发现所有这三个中间件都相当有用，但肯定存在你可能只需要部分功能的场景。

我们的默认 Deep Agent 还附带了 **SummarizationMiddleware（摘要中间件）**，它在我们上下文窗口变得太长时保护我们，并允许我们压缩现有的对话。

还有一些我认为值得介绍的概念。其中一个比较有趣的是 **HumanInTheLoopMiddleware（人在回路中间件）**。很多关键任务代理，顾名思义，必须调用关键任务工具。有时候你可能想暂停代理，让一个人类来审查一个预期的工具调用。你可以用 `HumanInTheLoopMiddleware` 轻松做到这一点。

Deep Agents 接受一个 `tool_configs` 参数，我们会把它传递给这个中间件。在这个字典中指定的任何工具，在执行前都会被中断。配置（config）则指定了一个人类可以在这个工具调用上采取什么行动。也许在一个发送邮件或上报问题的敏感工具执行之前，你可以指定一个工具配置，允许人类批准当前的操作，或者编辑它，或者用反馈来回应，告诉代理可以怎样做得不同。这个“人在回路”的功能现在通过使用中间件直接内置到 Deep Agents 中了。

最后我想指出的一点是，你可以向你的 Deep Agent 添加你自己的自定义中间件。我们有一些预构建的东西，我们认为对大多数代理来说是普遍有用的。但你的用例就是你的用例，你可能需要更多的状态键，你可能需要特定的工具，你可能需要在模型调用前后进行其他修改，你可以通过用你自己的中间件来扩展 Deep Agent 来添加所有这些功能。
