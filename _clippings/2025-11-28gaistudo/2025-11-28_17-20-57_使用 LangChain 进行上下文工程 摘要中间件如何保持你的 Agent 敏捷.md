# 使用 LangChain 进行上下文工程：摘要中间件如何保持你的 Agent 敏捷

**YouTube 视频地址：** https://www.youtube.com/watch?v=AOKdC5d6XlE

大家好，我是来自 LangChain 的 Christian。

如果你使用像 Cursor 这样的编码 Agent（智能体）进行开发，你可能对这种情况很熟悉：在与 Agent 交互的前几轮对话中，效果非常棒。但是，当你在这个线程中继续与 Agent 对话时，质量开始下滑。决策变得越来越模糊，整体的代码质量也在下降。

然后，Cursor 会抛出这样一行系统提示：“Chat context summarized”（聊天上下文已摘要）。

也就是在那一刻，你知道你已经越过了上下文的边界线。

## 为什么摘要对于上下文工程如此重要？

你构建的每一个 Agent 都生活在一个固定的内存窗口中。无论是 10 万、20 万还是 100 万个 Token，这取决于模型支持的上限。这个窗口既是你的超能力，也是你的瓶颈。

随着对话的深入，你增加的每一轮对话都在争夺这个上下文中的空间。无论是早期的推理、早期的工具输出，还是早期的代码片段。

因此，如果没有一个好的策略，会发生两件糟糕的事情：
1.  **模型会遗忘：** 它会忘记重要的步骤或重复已做过的工作。这就是经典的“上下文漂移（Context Drift）”。
2.  **浪费成本：** 你开始为那些甚至不会影响下一次预测的 Token 付费。

**摘要中间件（Summarization Middleware）** 让你能够精确地控制这种权衡。它能缩减历史记录，但是是以一种智能的方式进行的。让我们以此深入探讨一下。

## 上下文管理的挑战

在讨论摘要如何提供帮助之前，有必要了解为什么上下文管理如此棘手。当 Agent 运行一段时间后，它们开始遭遇一些人所说的“上下文故障（Context Failures）”。

例如，你会遇到：
*   **上下文中毒（Poisoning）：** 一个小的错误溜进了上下文，并被大语言模型（LLM）反复使用。
*   **上下文分心（Distraction）：** 上下文过多，导致模型不知所措，忽略了重要的信息。
*   **上下文困惑（Confusion）：** 太多无关紧要的细节导致回答偏题或质量低下。
*   **上下文冲突（Context Clash）：** 新信息与上下文中已有的旧信息发生冲突，导致推理混乱。

Drew Breunig 有一篇非常棒的文章，专门讨论了过长的上下文是如何导致 Agent 失败的。

## 上下文窗口管理的策略

那么，我们如何确保这种情况不会发生在我们的 Agent 身上呢？有一些成熟的策略可以用来保持 Agent 上下文的清洁和高效：

1.  **RAG（检索增强生成）：** 只提取与 Agent 工作实际相关的信息。
2.  **工具加载（Tool Loadout）：** 不要把所有的工具定义都扔给 Agent，只加载当前任务所需的工具。
3.  **上下文隔离（Context Quarantine）：** 尝试将长任务隔离在单独的线程中，以免污染其他对话。
4.  **修剪（Pruning）：** 删除噪音、不相关的信息或过时的工具输出。
5.  **卸载（Offloading）：** 将数据存储在上下文之外（例如 Scratchpad 或内存中），并在需要时加载回来。
6.  **摘要（Summarization）：** 这是我们本期视频的重点。与其直接删除上下文，不如将旧的历史记录压缩成一个紧凑的摘要。这样既保留了重要的上下文，又释放了空间。

## 代码实战：Next.js 沙盒应用

现在，在这个 Next.js 沙盒应用中，我们有一个专注于摘要中间件的 Agent 场景。我们的“摘要 Agent”是一个编码 Agent，它将帮助我们重构项目。

### 代码结构
代码非常简单。我们有一个 Next.js 的 POST 端点，它接收请求载荷（Payload），并将其传递给摘要 Agent。载荷包含消息、API Key 和线程 ID（Thread ID）。

摘要 Agent 拥有一个模拟的文件系统，并配备了两个工具：读取文件（Read Files）和列出文件（List Files）。

### 配置摘要中间件
我们基本上是在对话中途启动演示。为了确保能触发上下文窗口限制，我预设了一些初始消息来填满上下文。

接下来，我们定义了两个模型：
1.  **Agent 模型：** 用于执行重构工作的模型（例如 Claude Sonnet）。
2.  **摘要模型：** 用于生成摘要的模型。

在 `createAgent` 函数中，我们将所有内容组装在一起：
*   定义 Agent 模型。
*   定义用于重构的工具。
*   **定义 `summarizationMiddleware`（摘要中间件）。**

这个摘要中间件也需要一个模型。这里我们可以使用一个更便宜的模型，比如 Claude Haiku。

### 设置触发器和保留策略
你可以定义何时触发摘要中间件，以及保留什么类型的信息。

*   **Trigger（触发器）：** 你可以设置多个触发条件。例如，当上下文窗口使用了 80% 时触发，或者在特定的 Token 数量后触发。在这个演示中，为了方便展示，我们设置为在大约 2000 个 Token 后触发。你也可以设置为在一定数量的消息后触发。
*   **Keep（保留）：** 这个属性允许你定义要保留的信息。这里我们设置为保留最后的 1000 个 Token。
*   **Summary Prefix（摘要前缀）：** 你可以自定义摘要的前缀，例如“Previous conversation summary:”（之前的对话摘要：）。

最后，我们将所有组件连接起来，并使用初始消息触发 Agent。

## 演示：运行 Agent

让我们试一试。这里有一个示例提示词：“Let's continue with the refactoring. Can you help me create the dateUtils.ts file?”（让我们继续重构。你能帮我创建 dateUtils.ts 文件吗？）

**观察上下文变化：**
1.  你可以看到，我们的上下文窗口立即填满到了约 1400 个 Token。
2.  Agent 开始通过编写代码来帮助我们。
3.  Agent 询问：“你想让我建议任何额外的改进吗？”
4.  我们回答：“Sure”（当然）。
5.  Agent 接着建议了更多的改进代码。

此时，你可以看到我们已经将上下文窗口填满到了 **2487** 个 Token。这意味着，下一次与 Agent 的交互将在发送消息给 Agent **之前** 触发摘要功能。

让我们发送新指令：“Help me format the code”（帮我格式化代码）。

**请注意两点：**
1.  摘要中间件将被激活。
2.  我们的上下文窗口将缩小回 1000 个 Token 左右。

**结果：**
一旦 Token 统计更新，我们看到“Summarization Middleware Activated”（摘要中间件已激活）。它摘要了我们的上下文。此时，上下文窗口大小降到了 **1100** 个 Token 左右。

如果你查看生成的摘要，你会发现 Agent 已经总结了：
*   我们的意图。
*   项目结构。
*   当前的代码文件。
*   已识别的目标和问题。
*   重构计划。

我们成功地将之前的历史记录压缩成了一条单一的消息，从而在上下文窗口中释放了大量空间，且不丢失关键信息。现在我们可以继续调用工具、读取文件，再次填满上下文窗口，而 Agent 依然保持敏捷。

## 总结

总而言之，上下文管理不仅仅是将信息塞进 Token 窗口中。它是关于**工程化**你的 Agent 能够记住什么，以及它如何随着时间的推移进行推理。

使用 LangChain 的摘要中间件，你可以在上下文填满时自动压缩长历史记录，从而保持 Agent 敏捷、高效且经济实惠。

你可以通过几行配置代码，完全控制何时触发摘要、保留多少上下文以及保留什么内容。
