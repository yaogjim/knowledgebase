# Ship Smart 第一部分：忙碌技术领导者的 Git + Cursor 工作流

**YouTube 视频地址：** https://www.youtube.com/watch?v=FpH3P-7X8k0

如果你是一名 CTO、产品经理，或者是一名需要在不破坏生产环境的情况下快速发布功能的高级工程师，那么这个工作流就是为你准备的。

我将向你展示如何结合使用 **Git** 和 **Cursor**，在不到 10 分钟的时间内为我的在线应用添加功能。我们将从通过 Git 和 Cursor 将想法转化为生产就绪代码的全过程。我曾在苹果公司担任工程师长达 12 年，这是我用来“智能发布”（Ship Smart）的最简流程。

这是我的 **Ship Smart** 系列的第一部分，在这个系列中，我将展示作为一个需要同时兼顾多个项目的人，我是如何实际发布软件的。

今天我们将涵盖基础部分，即基本的 Git 工作流，它允许你在代码进入生产环境之前，安全地测试 AI 生成的代码。

我们将为我的应用 **AnimeLeak** 添加真实的功能。用户一直要求能够预览原始图像和处理后图像的对比，我将向你展示基于分支（Branch-based）的工作流是如何防止你部署错误代码的。

我们将使用的技术栈包括：
*   **GitHub**：用于版本控制。
*   **Vercel**：用于部署，因为它们会自动处理所有基础设施。

这基本上意味着你不必将时间花在运维（DevOps）上。让我们开始吧。

---

### Git 分支策略与可视化

首先看到的是我们在 **Git Tower** 中的主分支（Main Branch）。这里的一切都是当前生产环境中正在运行的实时代码。你可以看到提交历史、当前状态，一切都是可视化的。

我现在使用 Git Tower 是因为我喜欢它的可视化表现，但你也可以使用像 **SourceTree**、**GitKraken** 这样的免费工具，甚至是在 Cursor 内部使用 VS Code 扩展来实现类似的分支可视化。

**第一条规则：在做任何事情之前，永远不要直接修改主分支（Main Branch）。永远不要。**

相反，我们要创建一个**功能分支（Feature Branch）**。看着用可视化工具操作有多简单。

为了从主分支创建一个新分支，我们只需右键点击，选择“Create New Branch from Main”（从主分支创建新分支）。在这里，我们要将其命名为 `feature/add-image-preview-toggle`。你可以看到它会自动为我们添加连字符。我们要确保选中“Checkout Branch”（检出分支）的设置，然后点击创建。

这一步会自动创建该分支名并自动切换过去。

现在，这个分支基本上是隔离的。在这里做的任何事情都不会影响主分支，直到我将其合并（Merge）。这稍后我们会详细讲。这就是我喜欢 Git Tower 的原因，你可以直观地看到分支结构，这在视觉上对我很有帮助。希望对你也是如此。

### 使用 Cursor 和 AI 编写代码

现在我们有了功能分支，这就是 **Cursor** 发挥作用的地方。

我将使用 AI 来编写这个“图像预览切换”功能。因为我们在一个分支上，如果 AI 生成了垃圾代码，其实也无所谓，生产环境是完全安全的。

我们要做的功能非常直观。用户只想看到原始图像和处理后的图像并排对比。我们在 Blob 存储中已经同时拥有了这两张图。现在我们需要做的就是构建用户界面（UI）。

我们还要确保使用 **Next.js 15** 的优化功能来进行缓存和预获取（Prefetching）。看看我们构建这个功能有多快。

我喜欢从 Cursor 的 **Agent Window**（智能体窗口）开始。我按 `Shift + Tab` 进入**计划模式（Plan Mode）**（你可以看到黄色的规划模式界面）。我最喜欢的模型是 **Sonnet 4.5**（注：此处可能指 Claude 3.5 Sonnet 或视频中特定的高版本），并开启思考框架。

基本上我会输入这样一个提示（Prompt）：

> “用户想要在处理后的图像和原始图像之间切换。我们在 Blob 存储中已经存储了这两者。我想添加一个切换 UI 组件，用于在它们之间进行切换。我想使用 Next.js 15 的 Image 组件，配合适当的缓存，并确保我们要预获取这两张图像以实现平滑过渡。请随意使用 Ref MCP 和 Exa Code MCPs 进行研究。”

因为我们处于计划模式，Agent 会在这个环境中做大量工作，找到我们需要的研究资料，确保我们使用的是 Next.js 15 的最新标准。

Cursor 的一个优点是，它会在继续之前向我们提出一些问题。我会回答这些问题：

1.  **切换哪些版本？** 原始上传版和 AI 处理版。目前只显示处理版，用户想看两者。
2.  **切换按钮在哪里？** 仅在 Image Modal（图像模态框）中，也就是用户点击查看全尺寸图片时。
3.  **预获取策略？** 当模态框打开时预获取两张图片。

阅读计划的细节非常重要。如果你使用的是 GPT-5 或 o1 等新模型，它们会严格遵循计划中的每一个字。如果计划有误，AI 就会严格执行错误的指令。所以一定要仔细阅读细节。

计划生成完毕后，我做了一个快速审查，看起来涵盖了所有内容：后端更改、前端更改以及优化工作。然后我点击 **Build**（构建），让 Sonnet 开始编写代码。

我选择这个模型而不是其他模型（如 Composer 1）的原因是，我更看重准确性。虽然其他模型可能更快，但有时会遗漏细节。对我来说，时间就是金钱，我不介意多花一点钱来保证准确性。可靠性是关键。

### 代码审查与本地测试

Cursor 的 Agent 窗口允许我们进行审查。点击 **Review**（审查），我们可以看到所有正在飞入的更改。它正在修改 Convex 中的 `images` 组件和前端的 `ImageModal` 组件。

代码生成完成后，Cursor 会进行最后的构建和 Lint 检查，确保一切看起来不错。

我现在按 `Command + J` 打开终端。
1.  运行 `bun x convex dev` 启动 Convex 服务器（后端函数）。
2.  按 `Command + \` 分屏终端。
3.  运行 `bun dev` 启动前端。

按住 Command 点击链接打开本地服务器。网站重新构建了。

如果我现在点击一张图片，就可以看到“Show Original”（显示原图）的按钮。点击它，显示原图；再点击，显示处理后的图片。

这就完成了！仅仅通过一个提示词。即使是简单的图片，能一次性成功也很棒。我们甚至可以检查移动端视图，确保它也能正常工作。非常棒。

### Git 提交与推送

既然验证了功能正常，我们来看看 Git 工作流。

在 Cursor 中，点击右上角展开侧边栏，点击 **Branch**（分支）图标。你可以看到当前的更改。
1.  点击 **Stage All Changes**（暂存所有更改）。
2.  点击小星星图标 **Generate Commit Message**（生成提交信息）。Cursor 会自动生成一条清晰的提交信息，这对于保持良好的代码提交习惯很有帮助。
3.  点击 **Commit**。

现在这些更改保存在了本地机器上。我们需要将它们推送到云端。
点击 **Publish Branch**（发布分支）。

回到 Git Tower，我们可以看到分支已经有了远程跟踪，更改已经推送到了 GitHub。

---

### Vercel 预览环境

如果你在 Cursor 中高亮选中并点击“Open in GitHub”，你会看到刚才的提交已经到了云端。

因为我们连接了 **Vercel**，当我们把分支推送到 GitHub 时，Vercel 会自动启动一个 **Preview Deployment**（预览部署）。

这能节省大量时间。我们可以在真实的服务器基础设施上预览此功能，而不仅仅是在本地主机上。

在 Vercel 的部署面板中，我们可以看到构建在不到一分钟内完成了。点击 **Visit**（访问），它会带我们去预览 URL。

我们再次进行测试：
*   点击已有图片：切换功能正常。
*   上传新图片：我上传了一张狗狗的照片。我们在类似生产环境的开发环境中测试完整的上传流程。
*   结果：转换完成后，切换查看原图和处理图都正常。

---

### 合并请求 (Pull Request) 与自动检查

现在我们验证了预览环境一切正常，图片加载快，切换流畅。我们准备合并到生产环境了。

在 GitHub 上，点击 **Compare & Pull Request**。
这里会发生合并到生产环境之前的最后一步检查。

我们可以看到 **Cursor BugBot** 正在运行。我已经安装了它（每月 40 美元），它会对代码进行额外的自动审查，寻找潜在的错误。如果你在做生产环境代码，多一双眼睛（哪怕是 AI 的）也是值得的。我还使用了 **Graphite** 进行 AI 审查。

注意：Cursor BugBot 提出了一个“Bug”，说“上传过程中不会显示切换按钮”。但这其实是**按设计预期（As Intended）**的。我们不希望在图像还没处理好之前就显示切换按钮。所以我们可以忽略这个提示。如果真的是 Bug，我们可以点击“Fix in Cursor”，它会带回编辑器修复并重新构建。

由于所有检查都通过了（或者已确认为设计预期），且功能在预览环境中验证无误，我们可以点击 **Merge pull request**（合并拉取请求），然后确认合并。

合并成功后，我们可以安全地点击 **Delete branch**（删除分支），保持良好的卫生习惯。

---

### 生产环境部署

回到 Vercel，因为我们要合并到 `main` 分支，Vercel 会自动检测并启动 **Production Build**（生产环境构建）。

构建完成后，最终的软件就会在 `animeleak.com` 上对所有用户可用。

构建刚刚完成。如果我们现在去 `animeleak.com`（生产环境），登录并上传一张照片。
我们可以看到：
*   显示原图。
*   切换关闭。
*   再切换回来。

这就是了！我们刚刚使用这个工作流将功能发布到了生产环境。

---

### 同步本地环境

最后一步，回到我们的代码环境。
在 Git Tower 中，我们可以看到 `main` 分支有更新（因为我们在云端进行了合并）。
1.  双击 `main` 分支切换回主分支。
2.  你会看到提示有代码需要拉取。
3.  点击 **Pull**（拉取）按钮同步分支。

现在，我们的本地机器上就有了最新的代码，可以准备开始下一个功能的开发了。

---

### 总结

这就是我完整的 **Ship Smart** 工作流：
1.  Git Tower 管理分支。
2.  Cursor 进行 AI 开发。
3.  自动生成提交信息。
4.  预览环境测试。
5.  最终生产部署。

这个流程之所以有效，是因为**关注点分离**。你永远不会拿生产环境去赌博。每一个变更都会先在真实环境中测试，并且你有每一个变更的完整可视化历史。

而且像 Vercel 这样的平台自动处理了基础设施，你不需要花费时间去搭建 CI/CD 管道或管理部署脚本。对我来说，我宁愿花时间发布功能，也不愿做运维。
