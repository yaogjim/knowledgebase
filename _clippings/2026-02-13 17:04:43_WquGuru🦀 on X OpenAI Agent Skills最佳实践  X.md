> 在 OpenAI Responses API 中，使用 Skills、托管 shell 和服务器端压缩的实用模式

OpenAI正在从单轮助手转向能够处理真实知识工作的长时间运行代理：读取大型数据集、更新文件和编写应用。基于开发者反馈以及在 OpenAI 构建 Codex 和内部代理的经验，OpenAI发布了一组新的代理原语，使长时间任务更实用：

-   Skills：可复用、带版本的指令，你可以将它们挂载到容器中，让代理更可靠地执行任务（与 Agent Skills 开源标准一致）
    
-   升级后的 shell 工具：OpenAI 托管的容器，带有受控的互联网访问权限，代理可以在其中安装依赖、运行脚本并写入输出（例如报告和工件）
    
-   服务器端压缩（Compaction）：一种自动压缩长时间代理运行的简单方式，确保永远不会达到上下文限制
    

文档和 API 参考分别详细介绍了上述每一项。本文重点分享我们目前看到的最有效但不明显的提示和模式，这些模式来自 OpenAI 的工作以及早期 Skills 客户 Glean 的生产实践。

Skills 是一组文件加上包含前置元数据和指令的

清单。可以将其视为模型在需要执行真实工作时可以参考的带版本的 playbook。

当 Skills 可用时，平台会向模型暴露每个 Skills 的 name、description 和 path。模型使用这些元数据决定是否调用 Skills。如果调用，它会读取

获取完整工作流。

Shell 工具让模型在真实的终端环境中工作，可以是：

-   OpenAI 托管的容器
    
-   你自己执行的本地 shell 运行时（工具语义相同，但你控制机器）
    

托管 shell 通过 Responses API 运行，这意味着你的请求带有状态化工作、工具调用、多轮延续和工件。

随着工作流变长，会遇到上下文窗口限制。服务器端压缩通过自动管理上下文窗口和压缩对话历史来保持长运行的连续性。

Responses API 中的压缩提供两种处理方式：

-   服务器端压缩（新功能）：当上下文超过阈值时，压缩会自动在流中运行，无需单独的压缩调用
    
-   独立的压缩端点：当你希望明确控制压缩时机时，使用 /responses/compact
    

-   Skills 通过将稳定程序和示例移入可复用包，避免提示混乱
    
-   Shell 提供完整的执行环境，允许安装代码、运行脚本并写入输出
    
-   压缩在长运行中保持连续性，使同一工作流无需手动上下文处理即可持续执行
    
-   组合起来，你获得可重复的工作流和真实执行，而无需将系统提示变成脆弱的巨型文档
    

1\. 将 Skills 描述写成路由逻辑（而不是营销文案）

Skills 的描述实际上是模型的决策边界。它应该回答：

-   什么时候应该使用这个？
    
-   什么时候不应该使用这个？
    
-   输出和成功标准是什么？
    

一个实用模式是在描述中直接包含简短的“使用时机 vs. 不使用时机”块，并保持具体（输入、涉及的工具、预期工件）。

一个令人惊讶的失败模式是，仅仅提供 Skills 最初可能会降低正确触发率。我们看到的一个有效修复是添加负面示例和边缘情况覆盖。

实践中，这意味着明确写出几个“不调用此 Skills 的情况……”（以及替代方案）。这有助于模型更干净地路由，尤其是在有多个表面相似的 Skills 时。

Glean 直接观察到：在 Skills 路由最初将针对性评估的触发率降低了约 20%，随后通过在描述中添加负面示例和边缘情况覆盖后恢复。

3\. 将模板和示例放入 Skills 中（未使用时几乎免费）

如果你一直将模板塞进系统提示，请停止。Skills 中的模板和工作示例有两个优势：

-   它们仅在需要时可用（Skills 被调用时）
    

-   结构化报告
    
-   升级分类摘要
    
-   账户计划
    
-   数据分析报告
    

Glean 报告称，这种模式在生产中带来了他们最大的质量和延迟提升，因为这些示例仅在 Skills 触发时加载。

长时间代理很少作为单次提示成功。从一开始就规划连续性：

-   在需要稳定依赖、缓存文件和中间输出时，跨步骤复用同一容器
    
-   传递以让模型在同一线程中继续工作
    
-   将压缩作为默认长运行原语，而不是紧急后备
    

5\. 当需要确定性时，明确告诉模型使用 Skills

默认行为是模型决定何时使用 Skills。这通常是你想要的。但在运行有明确契约的生产工作流时（你更希望确定性而非聪明），直接说：“使用 Skills。”

这是你可以拉动的最简单的可靠性杠杆。它将模糊路由变成明确契约。

6\. 将 Skills + 网络视为高风险组合（设计为隔离）

这是容易现在忽略、以后难修复的安全提示。将 Skills 与开放网络访问结合会创建高风险的数据泄露路径。

如果使用网络，请保持网络允许列表严格，假设工具输出不可信，并在用户期望强确认控制的消费者流程中避免开放互联网 + 强大程序。

-   Skills：允许
    
-   Shell：允许
    
-   网络：仅对狭窄范围任务启用最小允许列表，按请求
    

对于托管 shell 工作流，将 /mnt/data 视为写入你将检索、审查或传递到后续步骤的输出的标准位置。例如报告、清理数据集和完成的电子表格。

一个好的心智模型：工具写入磁盘，模型在磁盘上推理，开发者从磁盘检索。

-   组织级允许列表（由管理员配置），设置最大允许目的地
    
-   请求级 network\_policy，必须是组织允许列表的子集
    

1.  保持组织允许列表小而稳定（“你信任的批准目的地”集合）
    
2.  保持请求允许列表更小（“此作业所需的目的地”集合）
    

9\. 使用 domain\_secrets 进行认证调用（避免凭证泄露）

如果允许的域名需要认证头，使用 domain\_secrets，这样模型永远不会看到原始凭证。

在运行时，模型看到占位符（例如

\_KEY），侧车仅为批准目的地注入真实值。这在代理需要从容器内调用受保护 API 时是强默认。

-   Skills 适用于托管 shell 和本地 shell 模式
    
-   Shell 有本地执行模式，你自己执行 shell\_call 并将 shell\_call\_output 返回给模型
    
-   如果使用 Agents SDK，你也可以插入自己的 shell 执行器
    

1.  从本地开始（快速迭代、访问内部工具、易调试）
    
2.  当需要可重复性、隔离和部署一致性时，移到托管容器
    
3.  在两种模式下保持 Skills 相同（即使执行移动，工作流也保持稳定）
    

虽然你可以自由实验这些新的代理原语，但以下是三种组合它们构建有用应用的示例。

这是从托管 shell 受益的最简单方式：代理安装依赖、获取外部数据并产生具体可交付物。

-   安装几个库
    
-   抓取或调用 API
    
-   将报告写入 /mnt/data/report.md
    

这种模式是真实工作代理的基础，因为它创建了清晰的审查边界：你的应用可以向用户展示工件、记录它、比较它或将其输入后续步骤。

模式 B：Skills + shell 用于可重复工作流

一旦你构建了一两个成功的 shell 工作流，你会注意到下一个问题：它有效，但提示漂移时可靠性下降。这就是 Skills 的用武之地。

1.  将工作流（步骤、护栏、模板）编码到 Skills 中
    
2.  将 Skills 挂载到 shell 环境中
    
3.  让代理遵循 Skills 确定性地产生工件
    

-   电子表格分析或编辑
    
-   数据集清理 + 摘要生成
    
-   标准化报告生成，用于重复业务流程
    

模式 C（高级）：Skills 作为企业工作流载体

我们看到的一个早期模式是单工具调用与多工具编排之间的准确性损失。Skills 可以通过使工具推理更程序化来缩小这一差距，而不会膨胀系统提示。

-   一个面向 Salesforce 的 Skills 将评估准确率从 73% 提升到 85%，并将首 token 时间减少 18.1%
    
-   实用策略包括仔细路由、负面示例和在 Skills 中嵌入模板/示例
    
-   Glean 还使用 Skills 编码企业工作流中的重复任务，包括账户规划、升级分类和品牌一致的内容生成
    

这就是事情变得强大的形状。Skills 成为活的 SOP（标准操作程序）：随着你的组织演变而更新，并由代理一致执行。

当长时间运行的代理既能遵循程序又能在计算机上执行真实工作时，它们会变得极其有用。Skills、托管 shell 和压缩创造了这一基础。

-   使用 Skills 编码“如何”（程序、模板、护栏）
    
-   使用 shell 执行“做什么”（安装、运行、写入工件）
    
-   使用压缩保持长运行连贯（无需手动管理上下文）
    
-   快速迭代时从本地开始
    
-   需要可重复、隔离执行时移到托管容器
    
-   使用组织级和请求级允许列表锁定网络，并对认证调用使用域名秘密
