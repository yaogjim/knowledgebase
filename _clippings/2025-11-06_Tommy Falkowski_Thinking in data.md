## 人类的一小步，我的一大步

最近我突然顿悟，意识到一个对多数软件开发者而言可能显而易见的道理：一旦开始用数据的视角思考问题，许多事情就豁然开朗了！虽然这个发现肯定拿不了诺贝尔奖，但对我而言却像摘下了眼罩。尽管我本职是机械工程师，也一直喜欢折腾电脑，但事实上我大半辈子都没怎么认真思考过数据。自从开始自建软件工具并将大部分工作流程迁移到终端后，我彻底被数据思维“洗礼”了！这种思维方式在与人工智能协作时尤其强大！下面我来解释为何这个认知可能对你同样重要——即便你掌握这个智慧的时间远比我更久。

## 数据无处不在

在研究这一课题时，我偶然发现了 [DIKW 金字塔模型](https://en.wikipedia.org/wiki/DIKW_pyramid) 。虽然之前见过这个模型，但它显然没给我留下深刻印象。如今我认为，即便这个模型非常简化，它仍是理解数据重要性的绝佳框架。该模型自下而上分为四层：数据、信息、知识与智慧。每一层都是构建下一层的基石。没有数据，一切便是空中楼阁。当我提出“数据思维”时，特指的是结构化或半结构化数据。数据可以包罗万象——从传感器采集的测量值，到人工撰写的报告，再到网站上的表单。但除非你是程序员或数据科学家，否则很少会深入思考数据的存在形式。对大多数人而言，数据或许只是文字和数字而已。然而随着越来越多人试图用人工智能实现自动化，我们确实需要更深入地思考数据结构。对于早已具备系统思维的工程师而言更是如此——当人工智能日益融入这些系统时，他们也该开始构建数据思维了！

## 预测下一个标记

大多数系统都可以分解为具有输入、功能和输出的独立组件。到目前为止都很简单。LLMs（大语言模型）也完全一样。给定一些输入标记后，它们会循环预测下一个标记，直到遇到序列结束标记。累积生成的标记构成了系统的输出。对某些人来说这如同魔法，而另一些人只看到在 GPU 上运行的一堆矩阵运算。我介于两者之间，但必须承认自己是“下一标记预测”的重度用户。将这类系统用作聊天机器人固然不错，尤其适合学习新主题，但我认为对企业而言最大的潜力在于借助 LLMs 实现任务自动化。

流程自动化绝非近期才有的创新，它可能自流程诞生之初便已存在。好吧，或许没那么久远，但至少可以追溯到工业革命开端。然而即便随着计算机、互联网和机器人流程自动化的出现，始终存在一个主要瓶颈：现实世界纷繁复杂，许多事物并非天然以结构化数据形式呈现。除非找到可靠方法来自动从任意输入中提取数据，否则这一步骤仍需人工完成。对于某些类型的信息，简单的正则表达式或许就足够用了，比如检测电话号码或电子邮件地址。但对于稍微模糊或异构的内容，就不得不开始创建启发式规则，甚至训练专门的自然语言处理模型。试想基于内容将文件分类归档、将格式千变万化的文档信息录入 [ERP](https://en.wikipedia.org/wiki/Enterprise_resource_planning) 系统，或是判断收件箱中消息的情感和紧急程度——这类任务传统上对许多中小企业而言曾是遥不可及的。 我并非说这完全不可能，但前期所需投入的工作量相当大，常常导致人们决定不再深入追求，而是继续手动执行各个步骤。

## 消除瓶颈

硅谷的人们或许会对此感到惊讶，但现实是，如今许多公司中仍存在大量手工流程。即便没有人工智能，流程自动化的潜力也巨大到令人难以置信。在我看来，人工智能，尤其是大型语言模型之所以能带来革命性变化，在于它们能够将模糊的输入转化为结构化数据。突然间，瓶颈消失了。根据具体流程，你几乎能实现整个工作流的全自动化。

老实说，当前许多工作仍是将信息从一种格式复制粘贴到另一种格式。比如打开 PDF 文档，用眼睛扫描，提取相关内容，再录入 ERP 系统。我认为这个认知非常重要，因为大多数人并不具备数据思维。他们不知道存在哪些数据结构，甚至不了解数据类型是什么。所以当你和企业谈论流程自动化时，他们常误以为人工智能能默认处理所有事情。如果能说服人们开始用结构化数据的思维方式思考，潜力将是巨大的。人们可以自行评估工作中哪些环节——尤其是最繁琐的部分——能够实现自动化。一旦学会识别这些模式，就能将其应用到各个场景。在日常工作中，你可以自问：能否从这个流程中提取结构化数据？

就个人而言，我极其厌恶像 SAP 那样的表单驱动工作流程，简直糟糕透顶。不得不点击无穷无尽的表单，有时还要多次输入相同的信息比如日期，简直让人抓狂。例如，预订一次出差可能需要重复输入四次相同的日期。这根本不是良好的流程设计，而是遗留系统的痕迹。而这样的遗留问题无处不在。你无法一夜之间替换这些系统。正因如此，当你开始识别这些模式时，就会意识到一个强大的可能性：或许你无法替换遗留系统，但你可以采用模糊的自然语言输入——用户只需说明需要什么样的行程、目的地和时间——剩下的交给 AI 处理。这对 AI 来说轻而易举。但要使这种方案稳定可靠，关键并非从结构化输入到结构化输出，而是从模糊输入到结构化输出。输入应当保持非结构化，因为这才是推动用户采纳的关键——人们更倾向于自然的交互方式。但输出必须是结构化的，以便系统能够轻松解析。

我知道你可能会想：“为什么不直接构建一个能处理所有事情的 AI 代理呢？”当然，你可以尝试这样做，把一堆 AI 调用串联起来就完事——一个处理输入，另一个解析输入，依此类推。但作为理性的工程师，我们需要自问：真的需要在每个环节都动用 AI 吗？传统软件完全可以高效处理许多环节。真正的瓶颈其实在于从模糊信息到结构化数据的转换。正因如此，我认为学会用数据和数据结构的思维方式来思考才是无价的技能。一旦掌握这种模式，你会发现它无处不在。你甚至无需立即设计完整流程，完全可以从最大化使用 AI 入手验证可行性，再逐步精简，在合适的环节用确定性系统替代 AI 模块。

## Inputs and Outputs

让 LLM 返回结构化输出曾是个棘手问题。网上充斥着"兄弟，求你了直接返回 JSON 吧！"的梗图，这至今仍算是个有效方法。早期 LLM 常常过于啰嗦，在 json 代码块前后添加对话内容。但随着大模型能力突飞猛进，现在往往无需特殊技巧就能获得合规 JSON。若想实现可靠自动化并确保始终生成统一的结构化输出，可能需要更正式的方法，例如结构化输出模式。OpenAI 的 API 通过 JSON 模式支持此功能，确保模型仅返回符合模式定义的输出。

本地模型同样能做到这一点。例如， [Llama.cpp](https://github.com/ggml-org/llama.cpp) 支持语法规则，这是一种定义有效生成模式的方法。模型只能生成符合这些规则的输出。虽然这会略微限制模型输出的创造性导致准确性下降，但能有效确保生成合法的 JSON（或表情符号，以及任何你能定义的结构）。另一种方法是微调，但这需要优质的数据集。或者你也可以依靠传统的提示工程，逐字优化提示词直到模型完全输出所需内容（求你了兄弟！）。但既然人工智能可能比你做得更好，何必手动操作呢？这正是 [DSPy](https://github.com/stanfordnlp/dspy) 的用武之地。DSPy 已问世一段时间，但需要适应过程，这也是为什么我花了比预期更长的时间才真正掌握它。

## 使用 DSPy 进行提示编程

DSPy 的核心思想是编程式调用 LLMs 而非直接编写提示词。您无需撰写冗长的提示，而是通过签名（类似 Rust 等类型语言中的函数签名）定义输入输出行为。只需提供简短文档字符串并定义结构，DSPy 便会处理后续工作。其最强大的功能在于优化器：最新推出的 GEPA 优化器会获取您的签名和少量输入输出示例（我用了约十组），自动尝试不同提示方案，最终根据您的评估指标找到效果最佳的版本。

定义一个良好的衡量标准至关重要。针对我将非结构化文本转换为结构化 JSON 的应用场景，我采用的衡量标准会特别关注以下几点：

- 输出是否为有效的 JSON？
- 它是否符合架构？
- 正确字段与缺失或虚构字段各有多少？

这些因素共同构成了评分标准，指导教师模型帮助学生模型提升表现。最终生成的优化提示词，其效果往往优于手动设计的方案。虽然通过人工方式最终也可能找到同等优质的提示词，但耗时可能远超想象。DSPy 正是为了自动化这项工作而生，唯一的要求是您能运行教师模型和学生模型（针对本地模型），或支付相应 token 费用（针对云端模型）。我本人始终青睐本地部署方案——过去几天一直在 M2 Ultra 芯片的 MacStudio 上运行 gpt-oss-120B 模型，并在本地 M4 芯片的 MacBook Pro 上运行 Qwen3-Coder-30B 模型。以下是我当前使用的评估指标概览：

```toml
[metrics]
# Weight for extra/hallucinated fields (0.0-1.0, default: 0.5)
# Lower values = lighter penalty for hallucinations vs wrong values
extra_field_weight = 0.5

# Beta parameter for F-beta score (default: 1.5)
# Values > 1.0 favor recall over precision, < 1.0 favor precision
# 1.5 means recall is 1.5x more important than precision
beta = 1.5

# Base score awarded for valid JSON parsing (default: 0.2)
base_parse_score = 0.2

# Additional score for schema validation (default: 0.2)
base_schema_score = 0.2

# Weight for field-level quality (F-beta of precision/recall) (default: 0.5)
field_weight = 0.5

# Weight for coverage bonus (encourages completeness) (default: 0.1)
coverage_weight = 0.1
```

而其中的美妙之处在于：一旦你在本地运行这个程序，就不再依赖云端 AI 模型了。本地模型足以胜任许多任务，特别是当你将复杂工作流程拆分成小块时。你甚至可以利用 DSPy 优化的提示词来生成新的训练数据，以备后续微调之需——尽管在多数情况下可能并不需要。单凭 DSPy 就能显著提升效果。看看这个通过 DSPy 生成的 [提示词](https://gist.github.com/WismutHansen/caf5f866e366a3003115c452fb02091b) ，它帮我成功提取了联系方式。

DSPy 也支持除 Python 以外的其他语言：有适用于 Rust 的 [DSRs](https://dsrs.herumbshandilya.com/) 、适用于 TypeScript 的 [ax](https://github.com/ax-llm/ax) ，相信后续还会有更多语言支持。如果你想亲自尝试，可以查看我的 [示例代码库](https://github.com/byteowlz/xtr-py) 。它演示的正是如何根据预定义的 JSON 模式将非结构化文本转换为结构化输出。当然，DSPy 不仅限于结构化输出，但基于签名的方法无疑非常适合用于结构化数据的思考！
