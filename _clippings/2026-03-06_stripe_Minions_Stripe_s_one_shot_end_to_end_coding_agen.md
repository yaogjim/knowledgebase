# Minions: Stripe’s one-shot, end-to-end coding agents | Stripe Dot Dev Blog

Minions：Stripe 的单次端到端编程代理 Minions：Stripe 的单次端到端编程代理 / Article 在整个行业中，agentic coding 已从新颖有趣发展到行业标配，并且随着底层模型持续改进，无人值守的编码代理已从可能变为现实。 Minions 是 Stripe 自主研发的编码代理。它们完全无人值守，专为一次性任务设计。Stripe 每周合并的超过一千个拉取请求完全由 Minions 生成，尽管这些拉取请求需经过人工审核，但其中不含任何人工编写的代码。 我们的开发人员仍然可以与 Claude 和 Cursor 等代理进行规划和协作，但在开发者注意力成为最受限制的资源之一的环境中，无人值守的代理能够实现任务的并行化。 典型的 minion 运行从 Slack 消息开始，以一个通过持续集成（CI）且准备好进行人工审核的拉取请求结束，中间没有任何交互。我们经常看到工程师并行启动多个 minion，以便他们能够并行完成许多不同的任务。在值班轮换期间，这对于有效解决可能出现的许多小问题特别有帮助。 在本博客文章系列的第一部分中，我们将向您展示我们的工程师如何使用 minions 以及它们能做什么。在第二部分中，我们将深入探讨底层实现以及我们是如何构建它们的。 为什么我们要自己构建它？ Vibe 从零开始编写原型代码与向 Stripe 代码库提交代码有本质区别。 Stripe 的代码库包含横跨几个大型代码仓库的数亿行代码。我们的后端大部分使用 Ruby（非 Rails）编写，并带有 Sorbet 类型检查，这是一个相对不常见的技术栈。贯穿始终，我们的代码使用了大量 Stripe 独有的自主开发库，因此这些库对大语言模型（LLMs）来说本质上并不熟悉。 风险很高：这段代码每年处理超过 1 万亿美元的支付量，并在生产环境中运行。同时，Stripe 面临着许多复杂的现实世界依赖关系，这些依赖关系涉及金融机构以及监管和合规义务，而我们的代码必须遵守这些义务。 LLM 代理在系统约束相对较少的情况下，非常擅长从零开始构建软件。然而，对任何规模、复杂度和成熟度都与 Stripe 相当的代码库进行迭代，本质上要困难得多。人类必须构建复杂的心智模型，才能在我们的代码仓库中进行有效修改，而使代理能够在其上下文窗口的范围内形成正确的直觉并使用正确的工具，这是一项挑战。 多年来，Stripe 一直投入开发人员生产力基础建设，这些基础支持我们在开发生命周期的各个阶段满足独特的约束条件——包括源代码管理、环境管理、代码生成、持续集成等众多方面——因此，我们定制的 minion 框架紧密集成到这些工具中。Minions 使用相同的开发人员工具，这些工具同样使 Stripe 的人类工程师能够在我们的规模下高效工作：如果对人类有效，对 LLMs 同样有效。 使用 minion 的体验如何？ minions 有几个不同的入口点，设计为尽可能符合人体工程学地与 Stripe 的环境集成。虽然我们提供命令行界面（CLI）和网页界面来启动 minions，但工程师最常从 Slack 启动一个。通过标记我们的 Slack 应用，工程师可以直接从讨论变更的线程中启动一个 minion，并且该 minion 能够访问整个线程以及作为上下文包含的任何链接。 如果你是一名从事内部工具开发的工程师，你可能会用类似这样的消息来启动一个 minion： 一条调用 minion 运行的 Slack 消息 Minions 也可以在 Stripe 内部的其他应用程序中被调用。我们的内部文档平台、特性标志平台以及内部工单系统用户界面都与 Minions 集成。例如，当我们的 CI 系统检测到不稳定测试时，我们会创建自动工单，提示用户使用 Minion 解决问题。 一个带有启动 minion 按钮的不稳定测试工单，该 minion 能修复它 当 minion 工作时，或者事后，工程师可以在 Web UI 中查看 minion 做出的决策和采取的行动。 管理 minion 运行的网页界面示例 一旦完成任务，minion 会创建一个分支，推送到 CI，然后按照 Stripe 的 PR 模板准备拉取请求。如果代码看起来没问题，工程师会打开该拉取请求并请求另一位 Stripe 工程师进行审查。如果代码不符合要求，工程师可以给 minion 进一步的指示，而 minion 在完成后会将更新后的代码推送到该分支。 工程师也可以在一个已完成的 minion 运行结束后手动对其进行迭代。虽然我们的北极星是一个无需任何人工代码生成的拉取请求，但一个不完全正确的 minion 运行通常仍然是工程师专注工作的绝佳起点。 How do minions work?一个 minion 有很多阶段，在本系列的第二部分中，我们将详细介绍 minion 的工作原理。很多细节是 Stripe 特有的，但我们确实认为其中有一些可推广的经验。为了勾起你的兴趣，这里有一个简短的时间线导览。 一次 minion 运行始于一个隔离的开发环境——或称为“devbox”——这种机器与 Stripe 工程师编写代码所用的机器类型相同。开发箱是预预热的，因此可以在 10 秒内启动一个，其中预装了 Stripe 的代码和服务。它们与生产资源和互联网隔离，因此我们可以在开发箱上运行 minion，而无需人工权限检查。这还能实现并行化，而无需像 git 工作树那样的开销，而这种方式在 Stripe 环境下无法扩展。 核心代理循环运行在 Block 的编码代理 goose 的一个分叉版本上，这是最早广泛使用的编码代理之一，我们很早就对其进行了分叉。我们以一种有主见的方式定制了编排流程，将代理循环与确定性代码（如 git 操作、linter、测试等）交织在一起，因此 minion 运行时既融合了代理的创造性，又能确保始终完成 Stripe 要求的步骤（如 linter 检查）。 一般而言，minions 会读取与 Cursor 和 Claude Code 等人工操作工具相同的编码代理规则文件，处理多种不同格式的代理规则文件。不过，Stripe 若设置大量无条件规则会不切实际，因此 Stripe 几乎所有代理规则均基于子目录进行有条件应用。 Minions 与 MCP 相连，MCP 为可联网的 LLM 函数调用提供通用语言。这就是它们如何收集上下文的，比如内部文档、工单详情、构建状态、通过 Sourcegraph 搜索获取的代码智能等。事实上，在 Minion 运行开始之前，我们会确定性地在看起来可能相关的链接上运行相关的 MCP 工具，以更好地充实上下文。 由于 MCP 是 Stripe 所有代理（而非仅 Minions）的通用语言，我们构建了一个名为 Toolshed 的中央内部 MCP 服务器，该服务器托管了 400 多种 MCP 工具，涵盖 Stripe 内部系统和我们使用的 SaaS 平台。Minions 和其他代理可以连接到全部工具中经过精心挑选且可配置的子集。 Minions 被构建的目标是一次性完成任务，但如果它们无法做到，关键是要给这些代理提供反馈。我们通过多个自动化测试层来实现这一点，这些测试层可供 Minions 进行迭代优化。第一道防线是一个自动化本地可执行程序，它使用启发式方法在每次 git push 时选择并自动运行选定的 lints。这一过程耗时不到五秒。 在考虑开发者生产力时，我们希望“将反馈左移”。这意味着，对于开发者和代理而言，如果任何在持续集成（CI）中会失败的 Lint 步骤，最好在 IDE 中或执行 git push 时就强制实施，并立即反馈给工程师。 如果本地测试没有发现任何问题，持续集成（CI）会在代码推送时，从 Stripe 的测试套件（其中包含超过三百万个测试用例）中选择部分测试运行。我们的许多测试都针对失败情况提供自动修复，我们会自动应用这些修复。如果测试失败没有自动修复，我们会将其返回给 minion 尝试修复。 由于 CI 运行会消耗 tokens、计算资源和时间，我们最多只进行两轮 CI 运行。如果首次推送后测试失败，我们会提示 minion 修复失败的测试并再次推送，但之后就不再继续了。这里需要在速度和完整性之间进行权衡，而且对于 LLM 来说，进行多轮完整的 CI 循环会带来边际收益递减。我们认为这个指导原则——“通常一次，最多两次 CI 运行——并且只在我们已经在本地修复了所有能修复的问题之后进行”——达到了良好的平衡。 简而言之，Minions 配备了我们提供给人类工程师的相同工具，以及在编写代码时遵循 Stripe 最佳实践所需的必要上下文。工程师能够并且确实可以以符合人体工程学的方式调用它们，作为其日常工作职责的一部分。 What’s next?Minions 已经重新构想了在 Stripe 进行编码的体验。行业仍在探索代理式编码的未来会是什么样子，但我们确信，无人值守的代码代理应用场景将仍然是代理的最令人兴奋的应用之一。 In 第 2 部分 , 我们将深入探讨我们如何实现了 minions。
