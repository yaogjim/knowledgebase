**George**

# 线束工程是控制论

阅读 OpenAI 的 harness engineering post, 我一直有种无法确定的感觉。然后我突然明白了：我以前见过这种模式。不是一次——是三次。

第一个是詹姆斯·瓦特的离心调速器，它出现在18世纪80年代。在此之前，一名工人站在蒸汽机旁手动调节阀门。在此之后，一个带配重的飞球机构感应转速并自动调节阀门。工人并没有消失，工作发生了变化：从转动阀门变成了设计调速器。

第二个是 Kubernetes. 你声明期望状态——三个副本、这个镜像、这些资源限制。控制器持续观察实际状态。当两者出现偏差时，控制器进行协调：重启崩溃的 Pod、调整副本数量、回滚不良部署。工程师的工作从重启服务转变为编写系统用于协调的规范。

第三个就是现在。OpenAI 描述了那些不再编写代码的工程师。相反，他们设计环境、构建反馈循环并将架构约束编码化——然后由代理程序编写代码。 五个月内百万行代码 ，零行由人工编写。他们称之为“工程化管理”。

每次都是同样的模式。 诺伯特·维纳在 1948 年将其命名为：控制论（cybernetics），源自希腊语 κυβερνήτης（意为舵手）。你停止转动阀门。你在操控。

每次该模式出现，都是因为有人构建了足够强大的传感器和执行器，能够在该层级实现闭环。

## 为什么代码库是那个拒不妥协的部分

代码库存在反馈循环，但仅存在于较低层级。编译器在语法层面形成闭环，测试套件在行为层面形成闭环，代码检查器在风格层面形成闭环。这些是真正的控制论控制——但它们仅作用于可通过机械方式检查的属性：它能否编译？能否通过测试？是否遵循规则？

以上这些——这个变更是否符合系统架构？这是否是正确的方法？随着代码库的增长，这种抽象是否会带来问题？——当时既没有传感器也没有执行器。只有人类才能在那个层面上操作，在两个方面都是如此：判断质量和编写修复。

LLMs 同时发生了两种转变。它们能够在人类曾经达到的水平上感知——并以同样的水平行动：重组一个模块、重新设计不一致的界面、围绕真正重要的契约重写测试套件。这是首次，反馈循环可以在做出重要决策的地方闭合。

但闭环是必要而非充分的。瓦特调速器需要调整。Kubernetes 控制器需要正确的规格。而在你的代码库上运行的 LLM 需要更难提供的东西。

## 校准传感器和执行器

建立基本的反馈循环——代理能够运行的测试、提供可解析输出的 CI、指向修复方法的错误消息——是基本要求。卡利尼演示了这一点，当时他让 16 个并行代理构建一个 C 编译器：极其简单的提示词，但精心设计的测试基础设施。“我的大部分精力都用于围绕 Claude 设计环境——测试、环境和反馈。”

更难的问题是利用特定于你的系统的知识来校准传感器和执行器。这是大多数人遇到困难的地方，也是他们指责智能体的地方。

它一直在做错事。它不理解我们的代码库。诊断几乎总是错误的。这个代理之所以失败，不是因为它缺乏能力，而是因为它所需要的知识——对系统而言“好”的定义、你的架构奖励哪些模式、规避哪些模式——都锁在你的脑子里，而你没有将其外化。代理不会通过潜移默化的方式学习。如果你不把它写下来，这个代理在第一百次运行时会和第一次一样犯同样的错误。

这项工作正在让你的判断变得机器可读。描述实际分层和依赖方向的架构文档。内置修复说明的自定义代码检查工具。编码了团队偏好的黄金原则。OpenAI 找到了完全符合这一点 : 他们每周五都会花 20%的时间清理“AI 垃圾”——直到他们将自己的标准编码到工具链本身中。

## 唯一的前进道路

这要求的实践——文档、自动化测试、编码化的架构决策、快速反馈循环——一直都是正确的。过去三十年间的每一本工程书籍都推荐这些做法。大多数人都会跳过这些做法，因为跳过它们的代价是缓慢且分散的：质量的逐步下降、痛苦的入职过程、悄无声息累积的技术债务。

代理工程使成本变得极高。跳过文档，代理会无视你的规范——不是只在一个 PR 上，而是在每一个 PR 上，以机器速度，全天候。跳过测试，反馈循环根本无法闭环。跳过架构约束，漂移会比你能修复的速度更快地加剧。而这里有个陷阱：如果代理不知道“干净”的样子，你就无法用代理来清理混乱。没有校准，制造问题的机器也无法解决问题。

这些做法没有改变。忽视这些做法的惩罚变得难以忍受。

生成-验证不对称性——背后的直觉 P vs NP, 通过 Cobbe 等人实证证明由 Cobbe 等人提出——指出了这一方向。生成正确解比验证解更难。你不需要超越机器的实现能力。你需要超越对它的评估：明确“正确”的标准是什么，识别输出何时存在偏差，判断方向是否正确。

设计瓦特调速器的工人们没有回去转动阀门。不是因为他们做不到，而是因为这不再有意义。
