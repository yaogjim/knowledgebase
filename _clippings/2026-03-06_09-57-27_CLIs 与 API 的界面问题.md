### 什么是这个帖子的背景？

先从简单说起：这个X帖子（推文）是Rhys Sullivan（@RhysSullivan）在2026年2月24日发布的，他是在回应AI大牛Andrej Karpathy（@karpathy）的观点。Karpathy认为，CLI（Command Line Interface，命令行界面）对AI代理（AI Agents）来说超级酷，因为CLI是“老古董”技术，AI可以轻松调用和组合它们。比如，你可以让AI安装一个Polymarket的CLI工具，然后让它生成仪表盘或处理数据。Karpathy的口号是“It's 2026. Build. For. Agents.”——意思是2026年了，大家要为AI代理构建东西。

Rhys不同意，他觉得CLI只是一个“局部最大值”（local maxima），意思是它看起来不错，但不是全局最佳解决方案。相反，他推崇用标准的REST API（一种网络接口）加上CIMD（可能是Client Identity and Metadata Dynamic registration，动态客户端注册的标准，类似于OAuth/OIDC的一部分，用于安全认证）。为什么？因为这样AI代理可以直接调用API，就像人类上网搜索文档然后操作一样。

简单比喻：CLI就像给AI一个“命令行玩具箱”，里面有各种工具（如ripgrep搜索文件），AI可以本地玩。但Rhys说，这不够优雅；API就像一个“在线超市”，AI可以上网搜索、挑选商品（端点），然后直接下单（调用），更灵活、更安全。

### 为什么Rhys觉得CLI不是最佳选择？

深入一点，我们拆解他的论点：

1. **发现性（Discoverability）差**：
   - CLI：你得先安装工具，然后运行`--help`看用法。但怎么知道世界上有哪些CLI？AI得一个个试，或者用户手动安装。想象一下，如果你想设置域名DNS记录，你不会先安装一个Vercel CLI吧？
   - API：AI像人类一样Google搜索“Set DNS record on Vercel Domain”，找到文档，文档里直接列出API端点（比如`/api/dns/set`）。AI直接调用，不用安装任何东西。发现性强，因为全网可搜。

2. **没有输入/输出类型化（No Input/Output Typing）**：
   - CLI：输入输出都是纯文本，AI容易搞错。比如输入格式不对，CLI就崩溃，AI得猜。
   - API：有严格的类型定义（如JSON schema），AI知道参数是字符串还是数字。出错时更容易修复。Rhys在帖子附的视频里演示：AI幻觉（hallucinate）了一个错的工具名（如`tools.github.create_issue`应该是`tools.issues.create`），但因为API全索引了，AI可以用语义搜索纠正自己。

3. **权限控制和安全性难搞（Harder for Permission Profiling）**：
   - CLI：安装后，它就能访问本地系统，风险高。怎么限制？比如不允许删除文件？CLI不擅长细粒度控制。而且，如果你有多个账户（比如3个GitHub账号），CLI怎么切换？
   - API：用CIMD动态注册客户端，凭证（credentials）自动插入（AI看不到敏感信息）。可以设置策略，如只允许GET请求（读数据），POST（写数据）需要用户批准。超级安全，尤其对非本地AI。

4. **整体生态**：
   - CLI适合本地工具（如ripgrep搜索文件），但不适合云服务（如Polymarket市场数据）。服务商已经有了API，为什么还要额外建CLI？CLI本质上还是调用API，多此一举。
   - API是20多年的成熟技术，公司只需完善文档和API，就能让AI无缝接入。不用为AI单独建“技能”（Skills），人类和AI共用一套接口。

Rhys说，CLI是临时方案（stop gap），但长远看，公司该专注好API和文档。他的比喻：人类设置DNS是搜文档→按按钮→按钮调API；AI也该这样，而不是安装CLI。

### Rhys的原型演示和未来愿景

他开源了一个原型：letagentscallapis.com（GitHub链接也给了）。你可以玩玩，看看这个世界长啥样。核心是AI写代码调用API（像Cloudflare的codemode），执行环境自动处理认证和错误恢复。

在后续回复里，他澄清：
- 打字错误：凭证是“动态插入哪里AI访问不到”（dynamically inserted where the agent can't access them）。
- 这套系统该对AI和用户“隐形”（invisible），公司建AI时内置执行环境。
- 对于编码代理（如opencode，他刚加入的公司），CLI还有用，但对服务如Polymarket，API更好。

### 回复中的辩论：CLI vs API

帖子引发热议（129回复、727赞）。一些观点：
- @swyx（swyx）调侃：你不是刚加入CLI公司吗？Rhys回：是代理公司！CLI适合ripgrep，不适合Polymarket。
- @johncodes（John McBride）反驳：CLI发现性好（`--help`），有POSIX补全API，易分发特定工具。API有混淆代理问题（confused deputy）。Rhys反：怎么知道所有工具？安装每个服务的CLI？CLI不适合多账户，且父母辈用户不会装CLI。
- @burkeholland（Burke Holland）支持CLI：API乱七八糟，认证复杂；CLI简单，`help`通用，易更新。工具限制是问题，但CLI整体最简。Rhys回：API更结构化，易整合，尤其非本地环境；CLI是野蛮生长。

总体，辩论焦点：CLI简单易用，但API更 scalable、安全、可发现。Rhys觉得API是未来，因为AI会像人类一样“上网”。

### 为什么这个讨论重要？（深入思考）

在2026年，AI代理正从玩具变生产力工具。Karpathy推CLI是因为它“原生”兼容终端生态，便于快速原型。但Rhys看长远：生态会爆炸式增长，成千上万服务不可能都装CLI。API让一切标准化，像Web2.0的REST革命。潜在影响：服务商（如Polymarket、GitHub）若建好API，AI经济会加速；否则，CLI碎片化会拖后腿。

如果你是开发者，这提醒：建产品时，想想AI怎么用？文档要Markdown导出，API要易搜、安全调用。Rhys的原型是个起点，值得试试。
