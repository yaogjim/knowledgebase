你像结对编程一样与一个智能代理协作。你给出提示，它进行编码。你进行审查，它进行修复。反馈循环很紧密，感觉很熟悉——就像和一个打字非常非常快的新同事一起工作。

他们在同一台机器上打开了多个 VS Code 实例，以并行方式运行代理会话。他们为不同任务生成了子代理。他们没有一次一项地向代理分配工作，而是开始组建小型的 AI 协作者团队并让它们运行。

从理论上讲，这似乎是一个简单直接的提升生产力的成果。但在实际操作中，它暴露了大多数开发工作流程本就无法应对的协调问题。

当协作主要是串行进行时，Git 的表现很好。分支偶尔会分叉，合并点很少出现，而且人类通常能够阅读 diff 并理解变更内容。

当多个代理同时针对同一系统编写代码时，那个模型会失效。

合并冲突的堆积速度快得让人来不及处理。差异变得太大，无法有信心地进行审查。提交历史不断增长，但它不再是有用的意图记录。Git 不再是协作工具，反而开始成为你需要绕开的障碍。

团队已经开始尝试变通方法。Git 工作树将代理隔离到单独的目录中。文件级锁定可防止同时编辑。这些方法在短期内可能有帮助，但它们是叠加在假设不同工作方式的基础设施上的适应措施。¹

越来越明显的是，我们正在推行一种超出其原本设计条件的协调模型。

在《人月神话》中，弗雷德·布鲁克斯解释了为什么软件生产力不会随着人员的增加而线性扩展。随着更多参与者的加入，沟通成本增加，假设出现分歧，整合成为主要成本。在项目后期增加人力会使项目更晚完成，而非更快。

当多个代理被分配到一个定义不明确的任务时，每个代理都能快速取得进展。问题在于，他们往往基于对“完成”的不同理解来推进工作。最终的工作成果可能会孤立运行，并且在整合阶段仍然失败。布鲁克斯所描述的协调成本依然存在——只是它出现的时间从数月缩短到了数小时。

当审视工作通常是如何被定义时，这一点变得尤为明显。

问题跟踪系统和任务列表对人类来说运作得相当不错。像“优化入职流程”这样的工单，假定工程师会推断出缺失的上下文、提出澄清性问题，并随着了解更多信息而进行调整。

如果你不明确目标、约束条件和成功标准，每个代理都会孤立地解读任务。这就是为什么你最终会得到五个在技术上可行但仍然无法整合的实现方案。

当并行执行的速度超过团队对实际正在构建内容的推理能力时，你就能最清楚地看到这一点。

最近关于代理生成的拉取请求的研究发现，模糊的任务描述和缺失的上下文是代理拉取请求被拒绝的主要原因之一。不理解其构建内容全部范围的代理生成的工作无法集成。²

埃萨尼等人，"人工智能编码代理在何处失效？"，arXiv:2601.15195（2026）

这与其说是代理的局限，不如说是工作描述方式与代理实际操作方式之间的不匹配。

一旦你并行运行多个代理，规范就不再是流程，而开始成为基础设施。这是它们的工作能够可靠汇聚的唯一地方。

代理不会共享直觉或协商歧义。他们只基于已明确的内容采取行动。没有共享的参考点时，每个代理会做出合理的局部决策，导致系统漂移。你只有在最后才会发现问题，此时各部分无法契合，而你在执行中节省的时间因整合工作而付诸东流。

一个简略的规范没什么帮助。“构建支付集成”失败的原因和模糊的任务单失败的原因相同：它没有明确说明关键决策。有效的规范需要明确两点：关于成功的定义和重要约束的人为判断，以及系统上下文（包括代码需要遵循的模式、依赖关系和故障模式）。

当两者都存在时，评审会提前进行且成本更低。你只需一次性验证意图，而不是事后协调多个实现。

在那个时候，计划就变成了产品。代码仅仅是执行该计划的结果。

代码生成的成本正不断降低。每一次模型改进都会降低实现成本。但无法以同样速度降低成本的是决定构建什么、定义边界，以及在边缘情况造成损害之前识别它们。这项工作仍然需要判断，而且无法很好地并行化。

这改变了何为有效。在代理驱动系统中，成功的开发者并非那些最能巧妙地发出提示的人，而是那些能够明确意图和清晰界定约束的人。

代理协调使得这不可避免。你不能仅凭直觉运行多个代理。它们需要一个共享的参考点——某种比聊天记录更结构化、比静态文档更具可操作性的东西。规范可以扮演这个角色，但只有当它基于真实的系统上下文时：现有模式、已知故障模式，以及团队通常非正式掌握的“部落知识”。

这也暴露了现有工具的局限性。Git 假定协作是以人类工作节奏进行的，且大多是串行协作。在多主体并行执行的情况下，Git 仅跟踪变更，而不跟踪意图。规范为团队提供了可版本化的内容，这些内容反映了他们原本想要构建的目标，而不仅仅是生成的文件。³

随着输出量增加，审查必须向上提升抽象层级。审查大量生成的代码无法扩展，而审查意图则可以扩展。在规划阶段发现问题比在执行后解决它成本更低。

分歧会更早出现，出现在计划层面，而非在相互冲突的执行过程中。并行工作更容易协调，因为每个人都遵循相同的工作指南。

这改变了需要审查和版本化的内容。团队不再是在代码中发现不一致，而是能够在仍有时间调整计划时就发现问题。

Intent 将规范视为事实记录系统，而非叠加在生成代码之上的注解。规范是意图所在之处、工作划分之处以及正确性评估之处。代码是在该决策之后生成的，而非被视为主要产物。

如果协作崩溃，更快的执行并无帮助。需要解决的问题是，随着产出增加，如何保持团队一致。

长期以来，开发者生产力意味着更高效地将意图转化为代码：更好的编辑器、更好的语言、更好的框架。所有这些都优化于执行。

那个假设正在减弱。实现变得廉价。约束不再是我们能否构建它 ，而是我们是否知道我们正在构建什么 .

当意图不明确时，代理团队会高效地朝着错误的目标执行。速度不再是优势，反而开始放大错误。

适应的开发者将是那些能够在编写任何代码之前明确“完成”的定义，并在计划层面而非生成的输出中识别故障模式的开发者。

成功的工具将为那个现实而构建。规格说明不会是事后编写的文档，它们将成为主要的成果。
