### QANDA 为何以及如何发生了变化？

QANDA 应用程序的上一个版本以其核心功能而闻名：允许学生拍摄他们不理解的问题的照片，并获得人工智能生成的解决方案。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*S7tmT6CuV-Iib2jS_8nHig.png)

然而，此功能严重侧重于特定用例——当学生遇到难题时提供解决方案。  
因此，在支持更广泛的学习目标时，它存在局限性，比如概念解释、推荐相似问题或生成测验。

**🗺 一个新定义的方向**

所以，我们设定了一个新目标：

> 实时了解用户的学习意图，并利用大型语言模型相应地提供最佳的用户界面/用户体验。

凭借这一新方向，QANDA 已从一个简单的问题解决助手转变为一个能够满足广泛教育需求的 **主动式人工智能学习助手** 。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*lh33zMh_5wFkNZPUUqswlg.png)

### 一种全新的工程范式

从核心来讲，我们构建的新系统就是通常所说的“智能体”。  
我们需要的不是简单地基于预定义逻辑做出反应，而是一种能够理解广泛用户请求并智能选择合适工具来解决问题的结构。

最初，我们遵循典型的产品开发流程：列出用户需求，为每个需求定义功能，然后在用户界面中实现这些功能。例如：

- “我不知道如何解决这个问题。” → 提供逐步的解决方案
- “我自己解出来了——你能检查一下它是否正确吗？”→ 对手写答案进行审核并给出反馈
- “我不理解这个概念。”→ 用例子解释这个概念
- “我想练习相似的问题。” → 搜索并推荐相似的题目
- “我想我开始明白了。” → 生成一个测验来检查理解情况

在传统设置中，这些请求中的每一个都需要单独的 API 和相应的专用用户界面组件。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*Wqx0bKwtZ4c2EfY2FpEN3w.png)

然而，我们选择了一种不同的方法：一个统一的智能体，它通过一个基于聊天的单一界面推动与学生的互动。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*3yW4XXbLCyMwUeQXNUPeAg.png)

换句话说，我们的目标是构建一个能够在单一对话流程中处理各种用户需求的结构。为了实现这一点，我们必须仔细考虑三个关键的技术挑战：

✅ 1. 定义聊天界面组件  
→ 该系统需要根据用户请求动态组合不同的模块。

✅ 2. 智能体意图分析  
→ 智能问答代理必须从自然语言输入中理解用户的学习意图。

✅ 3. 为智能体设计一个工具框架  
→ 智能代理必须能够通过组合多种工具来解决复杂任务。

有了这些原则，我们能够将整个系统抽象为以下三个核心概念：

> **智能体（意图理解）→工具（问题解决）→模块（可视化响应）**

### 理解学生意图

如前所述，准确<强 id = 0>识别学生意图对于 QANDA 灵活支持广泛的学习用例至关重要。

例如，即使学生上传了同一道题目的照片，他们的意图也可能有很大差异：

- 他们可能只是想要一个解决方案
- 他们可能想要关于自己答案的反馈
- 他们可能在寻找概念解释
- 他们可能想练习类似的问题
- 他们可能想要根据该内容生成一个测验

这些多样化的需求使得意图识别至关重要。然而，在实际应用中，当前的语言模型很难在一次尝试中完美地对所有这些意图进行分类。

此外，由于新的学习需求和用例将不断涌现，从一开始就以可扩展性和灵活性为设计理念来构建系统至关重要。

**🤖 一种用于意图分析与执行的多智能体策略**

为了解决这个问题，我们首先将用户需求分为两个主要流程：

- **以解决问题为导向：** 流程专注于帮助学生解决问题，例如提供反馈、解释和概念澄清
- **以内容创作为导向：** 专注于生成学习材料的流程，如测验、抽认卡和总结笔记

基于这种分离，我们决定构建负责每个流程的独立代理。这就产生了以下架构：

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*2b4YmlRBw-G-Id1o4WUQ1Q.png)

**🕸️ 多智能体群体架构**

这种架构类似于通常所说的 ***群体架构*** 。每个智能体专注于其 **特定的专业领域** ，超出其范围的请求会被 **移交** 给另一个合适的智能体。（ [参考](https://langchain-ai.github.io/langgraph/agents/multi-agent/#swarm) ）

初始请求由 `determine_active_agent` 处理，它将职责委托给 **回答问题代理** （专注于解决问题）或 **生成学习材料代理** （专注于内容创建）。  
从那时起，活跃的代理处理对话，直到上下文发生变化，此时它会根据需要将会话移交给另一个代理。

（供参考： `info_agent` 处理与 QANDA 策略相关的问题，而 `vanilla_agent` 是为配额已用完的用户提供的免费层级代理。）

这种方法的主要优点包括：

- ✅ 更清晰的上下文管理  
	→ 每个智能体只需要知道自己的角色，这将提示的复杂性和历史记录跟踪降至最低。
- ✅ 特定用例的评估与测试  
	→ 可以针对每个用例独立设计评估指标和测试场景。
- ✅ 关注点分离以实现专注开发  
	→ 开发人员可以带着明确的目标和职责开展工作，因为每个智能体都有明确的用途。
- ✅ **智能体的高可扩展性和可重用性**  
	→ 可以通过添加或组合独立代理来支持新的用例。  
	→ 同一个智能体可以在不同场景中重复使用。

当然，与任何架构决策一样，都存在权衡取舍。在这种情况下，Swarm 架构可能会增加获得最终输出的时间和成本。我们将在未来的一篇文章中介绍我们是如何应对这一挑战的。

接下来，我们将深入探讨每个代理的具体角色和特点。

### 问题解决代理：规划与执行

我们开始开发的第一个组件是 **问题解决代理** 。这个代理需要满足广泛的学习需求，包括：

- 针对学生不理解的问题的 **逐步解决方案**
- 通过分析问题类型并从 QANDA 数据库中检索相关问题来提供 **相似问题推荐**
- **对手写答案的反馈** ，审阅并评论学生自己的解答
- **图形生成** ，在需要时以可视化方式表示函数或几何概念
- 在一张图像中 **处理多个问题** ，逐个分离并解决这些问题
- **术语解释** 针对求解过程中出现的概念

还有一些系统层面的目标和约束条件需要考虑：

- 保持一个 **最低答案准确率** （例如，n%）
- 通过增加基于数据库的问题资源的使用来\*\*优化成本\*\*

**🧠 初始方法：基于 ReAct 的架构**

我们最初的设计将系统设想为一组 **模块化工具** ，智能体根据用户查询的上下文选择并调用适当的工具。这种方法与 ***ReAct*** （推理+行动）策略非常相似（），并遵循如下流程：

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*LSNpJNaACDHGeB2N8HaMzw.png)

Simple ReAct Agent

然而，一旦我们开始进行实际评估，一些局限性就变得明显了：

回答中缺乏整体连贯性，特别是在处理单个请求中的多个问题时，系统常常会丢失上下文或混淆顺序。

例如，当用户提交一张包含多个问题的图片，并要求智能体解决其中两个问题时，我们经常观察到如下问题：

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*zldh_bLtrYYgj8sfoguiMA.png)

预期的行为是该智能体在第一轮解决问题 a)和 b)，然后在下一轮继续解决问题 c)和 d)。然而，我们经常看到一些问题，比如智能体重新解决问题 a)和 b)，或者完全跳过问题 c)而直接跳到 d)。

此外，该智能体本应首先查阅 QANDA 数据库，并在存在匹配问题时返回一个匹配问题。但在实际操作中，它常常表现出一种 **贪婪倾向** ——只关注眼前的问题，而不考虑更广泛的背景。

当然，如果任务仅仅是解决单个问题，那么该智能体的表现会好得多。然而，由于解决问题的智能体需要处理各种复杂且多层次的请求，我们需要一种不同的方法。

👉 **策略转变：引入规划与执行架构**

因此，我们摒弃了依赖于反应式工具调用的 ReAct 风格方法，转而采用了一种 **计划 → 执行** 架构。（参考资料）(r [eference](https://langchain-ai.github.io/langgraph/tutorials/plan-and-execute/plan-and-execute/))

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*M5NSMOl9S3U6jsmMMbCueg.png)

在 **计划** 阶段，系统会分析请求的整体结构，并按顺序列出必要的任务。然后，在 **执行** 阶段，它会一步步遵循该计划——调用适当的工具并在此过程中更新系统状态。

“重新规划”阶段是可选的，在任务执行后发挥作用，系统可以根据中间结果调整计划。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*uwrAmzv3zdrV8NRMaOpaJQ.png)

该图表可能看起来有点复杂，但它反映了我们生产中的问题解决代理的实际架构。如上所述，该代理通过经历 **规划** 、 **执行** 以及可选的 **重新规划** 阶段来完成问题解决过程。

在处理 **多步问题、顺序请求以及生成复杂回复** 时，这种方法展现出了更为稳定的性能。由于智能体现在能够以更结构化的方式进行思考，所以它能够给出更连贯、一致的回复。  
之前“贪婪”行为的问题也得到了有效解决——通过引入 **重新规划** 阶段，智能体现在可以在继续操作之前检查是否存在重复问题或已经回答过的问题。

**🦾 正在运行的 QANDA 问题解决助手**  
让我们来看看新构建的问题解决代理如何为我们产品中的实际功能提供支持，通过问题数据帮助学生学习。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*UTf4pjUNuCZdepGcgWM1Pg.png)

上图展示了询问一个关于等比数列的问题后的结果。智能体首先创建了一个<强 id=0>计划 ，以便根据用户的手写解答提供反馈，然后使用<强 id=1>反馈工具来<强 id=2>执行该计划——给出一个经过修正和注释的回应。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*sLHpfqlXPzMCZA3zgTLhNQ.png)

查看上面的流程图可能会使事情更容易理解——你可以看到<强 id=0>规划器如何分析用户的请求，决定使用哪个<强 id=1>工具 ，并将该计划传递给<强 id=2>执行器 。

In contrast,

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*Ri1wDaKeuz-3ABmmxdRtoQ.png)

如果用户使用同一图像，还想搜索相似的解决方案，

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*FlN5y4R1XMMffmwh3XpyCA.png)

如上图流程图所示，如果是这种情况， **规划器** 可以将查询 QANDA 数据库的 **搜索工具** 作为其计划的一部分。然后， **执行器** 通过执行搜索并返回匹配的问题来跟进。

实际上，规划器可处理各种各样的用例，这使得它的作用更加关键。为了支持这一点，我们在 QANDA 中实施了一些精心设计的指导提示，以帮助有效地引导规划器的行为。

通过这种方式， **问题解决代理** 成为了 QANDA 系统中首个被设计出来的组件，同时也是处理场景范围最广的组件。因此，它不仅是一项核心产品功能，还是用于验证诸如推理、工具使用以及处理用户请求等关键代理设计概念的试验台。

在构建问题解决代理时，QANDA 后端团队探索并评估了多种架构方法，包括 <强 id=0>ReAct 和<强 id=1>计划与执行框架。通过这样做，我们积累了关于哪些结构最适合不同类型任务的宝贵知识。

我们还解决了许多实际挑战，例如如何处理代理流程中的故障、如何将模型的内部消息与面向用户的响应分开等等。

我们在这个过程中获得的见解，在我们着手开发为内容创作工作流程提供支持的 **生成器代理** 时，成为了坚实的基础。  
接下来，我们将介绍该智能助手是如何设计的，它不仅能解决问题，还能在学生的学习过程中提供主动帮助。

### 内容生成代理：创建学习材料

虽然解题代理专注于 *寻找正确答案的过程* ，但<强 id=1>内容生成代理负责塑造学习之旅——帮助学习者积极参与，并通过互动体验增强他们的理解。

例如，生成测验或抽认卡的过程并非以单个响应结束：

- 生成学习内容本身需要更多时间
- 并且它涉及多个后续交互，例如 **解出测验、评分、重新生成或编辑** ，
- 所有这些都需要一个 **专用用户界面** 以及超越传统聊天界面的流程。

在为这种交互进行设计时，许多基于大语言模型（LLM）的产品生态系统将这些元素称为 **画布** 或 **工件** —— 这是在标准聊天范式之外定义的不同组件。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*aN2i_cxrr2usNjpm_snsgQ.png)

我们还在 QANDA 中采用了“工件”一词，以便在系统层面清晰地定义这些以内容为中心的体验，并将其与标准聊天流程区分开来。

**🎛️ 什么是工件？**

一个 **工件** 不仅仅是一个单一的响应块。它代表了在 **一个单独的查看器界面** 中发生的独立学习体验，在这个界面中， **用户可以直接进行交互** ——而这些交互会影响系统状态和未来的人工智能响应。

工件的关键特性包括：

- 用户可以在专用查看器中进行交互，并直接修改信息。
- 这些更改 **会影响后续人工智能回复的上下文** 。  
	例如：根据用户是尚未进行测验，还是已经完成并复习了测验，LLM 给出的反馈和建议会有很大差异。
- 为了支持这种行为，与普通响应不同，工件需要后端逻辑来进行 **状态管理、数据持久化、变更跟踪** ，有时甚至需要由其自己的专用服务进行 **管理** 。

**❓何时某物可被认定为工件？**

从开发的角度来看，如果一个特性满足以下一个或多个标准，我们通常将其归类为工件：

- 事件不仅仅发生在简单的 **读取** 操作中，例如，用户的操作会导致系统状态的更改（创建/更新/删除）。
- 会话状态或结果需要持久存储。
- 该交互无法仅通过聊天来处理，而是需要一个 **专用用户界面或任务流程** 。
- 示例包括：参加测验并获得评分、查看和编辑手写笔记等。

工件不仅仅是一个视觉元素——它是用户体验中的一个分支点，在这个点上， **数据发生变化** ， **系统上下文发生转变** ，并且 **交互式学习得以发生** 。

**生成器代理** 旨在引领这些由工件驱动的体验。它充当一个主动学习助手，鼓励学生更积极地参与他们的学习之旅。

**🧮 QANDA 如何生成工件**

有了这个定义后，我们开发了 **生成器代理** 及其交互模式的架构，如下所示：

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*hoJ44wu--TdO8bcYSqtn9w.png)

首先，关于智能体的结构——我们在这里也采用了一种<强 id=0>规划与执行方法，因为该智能体需要支持各种交互，例如创建和修改工件。

然而，一个关键的区别在于，我们没有包含一个“重新规划”阶段，因为不存在需要动态重新规划的复杂条件流或分支逻辑。

此外，由于聊天中的代理无法一直等待生成工件，一旦触发生成工具，就会在工件域（在这种情况下是一个测验）中异步启动一个 **新流程** ，如下所示。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*Oh6WAUP-omecZ1GfCt5cQw.png)

以下图表提供了整体结构的高层次视图 ——  
展示系统如何动态响应用户请求，以及一旦触发， **工件域如何独立运行** 。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*r0nm8PsH-NxTBVS2CVI5OQ.png)

**问答代理** 是在上文所述领域内运行的工件代理。

虽然创建、修改和检索的 **路由和请求处理** 由 **智能体集群** 和 **内容生成智能体** 管理，但实际逻辑在 **工件智能体** 自身内部执行。（此处省略了关于规划器和相关组件的详细信息。）

例如，如下图所示：

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*qgNL5_T82ITLSlvEZ1WYVg.png)

当用户说“为我创建一个测验”时， **智能体集群** 检测到测验生成意图，并将任务委托给 **内容生成智能体** 。然后该智能体向 **测验后端** 发送创建请求，生成的 **工件** 会在聊天界面中呈现。

每个工件都遵循特定领域的逻辑，例如创建、修改或进度跟踪。在这种情况下， **测验工件** 显示正在加载，然后成功完成其生成。

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*3lsvpdgRPllQBbyg1G9UtA.png)

此 **工件** 有其自己专门的视图，允许用户独立与之交互——无论是通过在查看器中直接交互，还是如上图所示通过聊天创建或修改新工件。

到目前为止，我们已经介绍了两个核心代理。现在，让我们来谈谈我们是如何设计这个系统以 **高效管理和运行这些代理** 的。

### 代理与聊天逻辑分离

在一个处理复杂学习流程和多样用户交互的系统中，明确划分 **智能体逻辑** 和 **聊天界面流程** 之间的职责至关重要。

最初，我们设想的架构是让智能体处理整个流程：接收用户消息、生成回复、将回复转换为块并直接在聊天窗口中呈现。

然而，这种紧密耦合的结构导致了几个问题：

- 该代理变得 **过于臃肿** ，增加了复杂性并使测试变得更加困难
- 聊天 **用户界面/用户体验逻辑与代理逻辑相互交织** ，使得复用和可扩展性变得更加困难
- 聊天流程或用户界面的任何更改都会对智能体的行为产生 **意外的副作用**

**👷 架构改进策略**

为了解决这个问题，我们重新设计了结构，以使智能体与聊天系统<强 id=0>解耦 ，并明确界定它们各自的职责：

- 该<强 id=0>智能问答代理仅专注于其核心职责： *理解用户意图 → 选择并使用工具 → 生成回答*
- 其他所有事情——比如检查用户配额、将回复转换为用户界面组件、管理对话流程以及渲染——都由一个单独的 **后端聊天编排层** 来处理

以下是我们在设计过程中使用的一个可视化表示，以帮助更轻松地理解这种分离：

![](https://miro.medium.com/v2/resize:fit:640/format:webp/1*DAUDRYUGMBuzZ2jABCfEpQ.png)

“用户”标签代表聊天界面，“后端（数据库）”标签指由聊天后端服务器处理和存储的流程，而“智能体”标签对应智能体集群。

通过这种架构分离，我们获得了几个关键优势：

- ✅ **模块化** ：现在可以独立开发智能体，并在系统的不同部分重复使用。例如， **生成器智能体** 可以作为独立产品发布，或作为 API 提供，而无需与 QANDA 的用户界面紧密耦合。
- ✅ **可扩展性** ：聊天界面现在可以灵活调整，以支持新的流程和用户界面设计。
- ✅ **稳定性** ：与系统可靠性相关的关键功能（如配额管理和消息流控制）已从代理中移出，从而提高了整体稳健性。
- ✅ **可维护性** ：通过确保每一层仅管理其自身的职责，我们将变更的影响范围最小化，并使系统更易于维护。

这种架构最终为 QANDA 未来在更广泛的平台和渠道上进行拓展奠定了基础。

**📈 监控：延迟与成本优化**

如前所述，生成式人工智能系统的关键挑战之一是在丰富、准确的回答与快速、经济高效的执行之间取得恰当的平衡。

我们持续监控几个关键指标：

**Latency**

- TTFT（首次生成令牌时间）：从用户输入到首个令牌出现的时间
- TPOT（每个输出令牌的时间）：生成令牌之间的平均时间
- 总延迟：生成完整响应的时间

**Cost**

- 每个回复的 LLM 调用总成本
- 每个代理/每个工具的成本明细
- Cached prompt ratio

在未来的一篇文章中，我们将分享基于这些指标所应用的优化策略、已取得的改进成果，以及我们计划在未来引入的护栏系统。

# QANDA 新一代智能体系统通俗总结

## 1. 背景与目标
- ** 过去 **：QANDA 主要帮学生拍照解题，但功能局限于 “问题 → 答案”。
- ** 现在 **：升级为能理解学习意图、主动提供多种学习支持的 **AI 学习助手 **，包括：
  - 解题 & 检查答案
  - 概念讲解
  - 推荐相似题目 / 出测验
  - 持续跟踪和个性化学习

## 2. 核心理念与架构
QANDA 的新架构核心是一个 ** 多智能体系统（Swarm Architecture）**：
- 每个代理 (Agent) 各司其职，例如：
  - 问题解决代理（Problem Solver）
  - 内容生成代理（Content Creator）
- 初始请求会分配给合适的代理，必要时可在对话中切换。

### 架构优势
✅ 上下文更清晰，避免混乱  
✅ 针对不同任务独立测试和优化  
✅ 高可扩展性，可新增或者复用其他代理  

---

## 3. 两大主力智能体

### 🧩 问题解决代理 Problem-solving Agent
- 职责：逐步解答、批改反馈、推荐类似问题、多问处理等。
- 技术演进：
  - 放弃简单反应式 (ReAct) 策略 → 引入 ** 规划 (Plan) → 执行 (Execute)** 流程，更结构化稳定。
- 好处：回答连贯、不遗漏或重复，多步任务表现佳。

### 📚 内容生成代理 Content Generation Agent
- 职责：创建互动式学习材料，如测验、抽认卡等 —— 称为 “工件 (Artifact)”。
- 工件特点：
    - 独立交互界面，可修改并影响之后的 AI 回复。
    - 涉及状态管理、数据持久化，而不仅仅是聊天消息。
  
---

## 4. 智能体与聊天逻辑解耦

🔹 原本 UI/UX 与逻辑紧耦合 ➡️ 导致臃肿难维护。  
🔹 改进后：
   - 智能体只负责 "理解意图→选工具→生成回答"；
   - 对话编排层负责 UI 渲染、流程控制、权限校验等。  

好处：模块化、更易扩展、更稳健。

3. ** 长短期记忆系统 **
   > 支持个性化推荐，提高留存率，比如了解你的科目偏好和水平发展情况。  
4. 提示词管理 & A/B 测试体系建设  
5. 基于 LangGraph 的可视化多智能体实现经验分享
