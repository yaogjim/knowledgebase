**Andrej Karpathy**

我也想到了这一点，所以一直在 NanoChat 里尝试。比如，这里有 8 个智能体（4 个 Claude，4 个 Codex），每个智能体都用 1 个 GPU 运行 NanoChat 实验（尝试在不出现回归的情况下删除 logit 软上限）。简而言之，它行不通，而且一团糟……不过看起来还是很漂亮的 :) 我尝试了几种设置：8 个独立的研究人员，1 个首席科学家给 8 个初级研究人员分配任务等等。每个研究项目都是一个 Git 分支，每个科学家将其 fork 到一个特性分支，使用 Git 工作树进行隔离，使用简单的文件进行通信，目前为了简单起见，暂不使用 Docker/虚拟机（我发现指令足以防止相互干扰）。研究机构在 tmux 窗口网格中运行交互式会话（类似 Teams），这样界面美观，方便查看每个人的工作，并在需要时“接管”（即不使用 -p 参数）。但目前为止，它运行不正常的原因是，即使在最高智能水平下，智能体的初始想法也相当糟糕。它们没有认真思考实验设计，运行了一些毫无意义的变体，没有建立可靠的基线并正确地进行消融，也没有仔细控制运行时间和失败次数。（举个例子，昨天一个智能体“发现”增加网络的隐藏层大小可以改善验证损失，这完全是错误的，因为在无限数据的情况下，更大的网络应该具有更低的验证损失，但这样做也会延长训练时间，我也不明白为什么我还要特意指出这一点。）它们非常擅长实现任何给定的、范围明确且描述清晰的想法，但它们缺乏创造性地生成想法的能力。但最终目标是对一个组织（例如“研究组织”）及其成员进行编程，因此“源代码”指的是构成该组织的提示、技能、工具等以及流程的集合。例如，每天早上的站会现在也成为了“组织代码”的一部分。而优化纳米聊天预训练只是众多任务之一（几乎就像一项评估）。那么，给定一个任意任务，你的研究组织能够以多快的速度取得进展？
