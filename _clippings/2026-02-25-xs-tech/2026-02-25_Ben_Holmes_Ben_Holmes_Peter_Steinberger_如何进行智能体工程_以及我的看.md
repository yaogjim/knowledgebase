# Peter Steinberger 如何进行智能体工程，以及我的看法

[@steipete](https://x.com/@steipete)

他对智能体开发的态度与我所见过的许多被炒作驱动的“智慧”背道而驰。传统的开发模式认为你需要拉尔夫·维格姆循环、Git 工作树、子智能体、规划步骤以及跨智能体通信协议。把所有环节都协调起来！

[彼得使用的……以上都不是](https://steipete.me/posts/just-talk-to-it)

他只有一个 Git 仓库、一个开发服务器和一个主分支，同时运行着 3-8 个 Codex 实例。

我想探究他是如何处理经纪人的，并根据我自己的经验添加一些细微差别。

## 

低爆炸半径

首先，彼得依靠明确定义的任务来最大限度地减少代理人之间的交叉，并在需要时介入进行引导。他称之为保持“

[低爆炸半径](https://steipete.me/posts/just-talk-to-it#blast-radius)

针对每个代理任务。

代理可以在同一分支的同一目录下自由工作。如果委派得当，代理不太可能交叉修改相同的文件，并且每次更改都可以在同一开发服务器上进行测试，而不会造成不必要的冲突。

到了发布阶段，代理会根据它们修改过的文件进行原子性提交。这意味着（理论上）你可以将功能分组提交，而无需使用单独的分支。

说实话，至少在团队合作中，我并不是这样工作的。在与 Warp 的工程师合作时，我更倾向于云沙箱隔离、独立分支和 PR 审核。

[@zachlloydtweets](https://x.com/@zachlloydtweets)

[写了一篇很棒的文章](https://x.com/zachlloydtweets/status/2019877685980196937)

关于这一点，对我来说最重要的是： 如果代理需要访问计算机，例如使用鼠标在原生应用程序中进行点击操作，那么它们就无法同时测试各自的功能。这就需要使用沙箱来并行运行代理。

我在原生应用开发中看到的最大胜利是让代理商能够完成整个流程。

[点击浏览他们开发的应用程序](https://x.com/warpdotdev/status/2022407710940279220?s=20)

到目前为止，我发现的唯一方法是将代理从我的机器转移到云端，特别是对于无法使用浏览器沙箱的原生应用程序而言。

PR 审查也让团队成员有机会凭借比我更深入的代码库知识发表意见；我们的创始工程师对系统架构的见解肯定比我更加细致入微。

话虽如此，我的批评似乎有点跑题了，因为彼得的情况很特殊。他一手打造了整个项目，至今仍提交了超过 95% 的代码。当项目的大部分内容都存在于他的脑海中时，为什么还要在每个功能之间增加 PR 审查的麻烦呢？或许他的方法更适合业余项目，或者开源社区中那些仁慈的独裁者……

## 

实际上，这很复杂。即使是副业项目也是如此。

我正在我的一个副项目中采用这种多代理、单主分支的工作流程：

[Hubble.md](https://github.com/bholmesdev/hubble.md)

说实话，我还没有真正把“原子提交”和“小影响范围”变成一种成功的实践。

也许我正在进行的项目规模太小，无法拆分成有意义的小块。但即使将两项独立的 UI 更改分别委托给两个代理，我很快也发现测试每个代理提交的更改时会出现问题。如果一个代理正在运行，而另一个代理已经准备好进行审核，那么由于代码更改仍在进行中，应用程序可能仍然无法使用。Codex 5.3 比 Opus 4.6 更不容易出现运行中错误，但仍然存在足够的摩擦，以至于我不得不手动停止和启动代理来测试每一项更改。我想做的是管理者，而不是交通管制员！

回到我们关于云沙箱的论点：“如果代理（以及延伸开来，人类）需要访问计算机，就无法同时测试他们的工作。”

随着项目的推进，我会继续审视这个想法，看看能否找到最合适的授权方式。但就目前而言，为每个代理创建独立的分支似乎更适合大多数项目规模。

## 

关于 AGENTS\[md\]

Peter 处理代理内存的方式也值得借鉴。首先，他没有使用工具内置的 AGENTS\[md\] 生成器（/init）。这与我的发现一致，因为 /init 会迅速膨胀上下文，其中包含项目结构和可用命令的详细信息，而代理可以通过工具调用轻松获取这些信息。这种膨胀的上下文也会导致性能下降，正如我们观察到的那样。

[在最近一项关于 AGENTS\[md\] 使用情况的研究中](https://arxiv.org/abs/2602.11988)

在开源项目中，我会和 Warp 团队确认如何改进我们自己的框架中的 \`/init\` 的质量，或者从长远来看是否真的需要它。

至于 Peter 在 AGENTS\[md\]中添加的那些行 ， 他在 Lex Fridman 的播客节目中承认，他几乎不写也不审阅这些内容。他只是在需要记住某些信息时提醒代理人更新文件，然后让差异自动生成。这在比喻意义上是合理的；我为什么要去干预同事的记忆呢？但他承认，在实际操作中，你有时需要审查 AGENTS\[md\]的更改 ，并根据需要进行精简。精简至上。

## 

要点总结

如果说有什么普遍适用的经验，那就是： 不要过度设计你的方案。 先从一个分支中的一个代理开始，看看你能构建出什么。如果等待时间过长， 可以参考 Twitter 上的做法，在同一个目录下扩展到两到三个代理。如果发现代理之间相互干扰，请改进你的委托流程。如果仍然遇到冲突，请在 AGENTS\[md\] 文件中编写一些规则。如果这还不够，可以探索更清晰的边界，例如为每个代理创建单独的分支、工作树，甚至是云环境。从零开始，逐步构建。
