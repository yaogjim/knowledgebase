# Harness engineering: leveraging Codex in an agent-first world | OpenAI

Harness engineering: leveraging Codex in an agent-first world | OpenAI 在过去五个月中，我们团队一直在进行一项实验：构建并发布一款软件产品的内部测试版，使用 0 行手动编写的代码.该产品拥有内部日常用户和外部 Alpha 测试人员。它会发布、部署、出现故障并得到修复。不同之处在于，每一行代码——应用逻辑、测试、CI 配置、文档、可观测性和内部工具——均由 Codex 编写。我们估计，开发该产品所花费的时间约为手动编写代码所需时间的十分之一。 Humans steer. Agents execute.我们有意选择了这一限制条件，以构建必要的内容，将工程效率提升数个数量级。我们仅用几周时间就交付了最终达到百万行代码的成果。为了做到这一点，我们需要理解，当软件工程团队的主要任务不再是编写代码，而是设计环境、明确意图以及构建反馈循环（使 Codex 代理能够完成可靠工作）时，会发生哪些变化。 这篇文章讲述了我们与代理团队共同打造全新产品的过程中所学到的经验——遇到的问题、使情况恶化的因素，以及如何最大化我们唯一真正稀缺的资源：人类的时间和注意力。 我们从一个空的 Git 代码仓库开始 首次提交到空代码仓库发生在2025年8月下旬。 初始脚手架——代码仓库结构、CI 配置、格式化规则、包管理器设置和应用框架——由 Codex CLI 使用 GPT‑5 生成，由一小部分现有的模板指导。就连最初的 AGENTS.md 文件（该文件指导代理如何在代码仓库中工作）本身也是由 Codex 编写的。 没有预先存在的人工编写的代码来锚定系统。从一开始，这个代码仓库就由代理塑造。 五个月后，这个代码仓库包含了大约一百万行代码，涉及应用逻辑、基础设施、工具链、文档以及内部开发者工具。在此期间，大约有 1,500 个拉取请求被打开并合并，由仅三名工程师组成的小团队负责开发 Codex。这意味着平均每位工程师每天的吞吐量为 3.5 个拉取请求，令人惊讶的是，随着团队规模扩大到七名工程师，吞吐量反而有所增加。重要的是，这并非为了产出而产出：该产品已被数百名内部用户使用，其中包括内部的日常活跃用户。 在整个开发过程中，人类从未直接贡献过任何代码。这成为了团队的核心理念： 无手动编写的代码.重新定义工程师的角色 缺乏动手实践的人工编码 引入了另一种工程工作，侧重于系统、脚手架和利用.早期进展比我们预期的要慢，不是因为 Codex 能力不足，而是因为环境定义不充分。智能体缺乏实现高级目标所需的工具、抽象机制和内部结构。我们工程团队的主要任务变成了使智能体能够完成有用的工作。 在实践中，这意味着采用深度优先的工作方式：将较大的目标分解为较小的构建块（设计、编码、审查、测试等），引导代理构建这些构建块，并利用它们解锁更复杂的任务。当出现问题时，解决方案几乎从来不是“再努力试试”。因为取得进展的唯一方法是让 Codex 完成工作，人类工程师总是介入该任务并询问：“缺少了什么能力，我们如何使这种能力对代理既清晰易懂又可执行？” 人类几乎完全通过提示与系统交互：工程师描述任务，运行代理，并允许其创建拉取请求。为了完成拉取请求，我们指示 Codex 在本地审查其自身的更改，在本地和云端请求额外的特定代理审查，回应用户或代理给出的任何反馈，并循环迭代直到所有代理审查者满意（实际上这就是所谓的 Ralph Wiggum Loop⁠）。Codex 直接使用我们的标准开发工具（gh、本地脚本和仓库嵌入式技能）来收集上下文，而无需人类将内容复制粘贴到命令行界面（CLI）。 人类可以审核拉取请求，但并非必须。随着时间的推移，我们已将几乎所有的审核工作转向由代理之间处理。 提高应用程序的可读性 随着代码吞吐量的增加，我们的瓶颈变成了人工质量保证（QA）能力。由于固定的约束因素一直是人力时间和注意力，我们通过让应用程序 UI、日志和应用指标等内容本身能被 Codex 直接清晰识别，来为代理添加更多能力。 例如，我们让应用程序基于 Git 工作树实现可启动，这样 Codex 就能为每次变更启动并驱动一个实例。我们还将 Chrome DevTools 协议接入代理运行时，并创建了处理 DOM 快照、截图和导航的技能。这使得 Codex 能够复现缺陷、验证修复，并直接推理 UI 行为。 Diagram titled LogQL 查询日志，使用 PromQL 查询指标。有了这些可用的上下文，像“确保服务启动在 800 毫秒内完成”或“这四个关键用户旅程中没有任何跨度超过两秒”这样的提示就变得可处理了。 Diagram titled “Giving Codex a full observability stack in local dev.” An app sends logs, metrics, and Codex uses these signals to query, correlate, and reason, then implements fixes in the codebase, restarts the app, re-runs workloads, tests UI journeys, and repeats in a feedback loop.我们经常看到单个 Codex 运行处理单个任务长达六小时以上（常常是在人类睡觉的时候）。 我们使代码仓库知识成为记录系统 上下文管理是让智能体在大型复杂任务中高效运作的最大挑战之一。我们学到的最早的经验之一很简单： 给 Codex 一份地图，而不是一本 1000 页的说明书。 我们尝试了“一个大的 AGENTS.md⁠ ”方法。它以可预见的方式失败了： 上下文是一种稀缺资源。 庞大的指令文件会排挤掉任务、代码和相关文档——因此，代理要么忽略关键约束，要么开始针对错误的目标进行优化。 过多的指导会变成无指导。当所有事情都被认为是“重要的”时，就没有什么是重要的了。代理最终会在局部范围内进行模式匹配，而不是有意地进行导航。 它会立即失效。 庞大的手册变成了过时规则的坟场。智能体无法分辨哪些内容仍然有效，人类停止维护它，这个文件悄无声息地变成了一个诱人的麻烦。 难以验证。 单个 blob 不适合进行自动化检查（覆盖度、新鲜度、归属、交叉链接），因此漂移不可避免。 因此，与其将 AGENTS.md 视为百科全书，我们将其视为 目录.代码仓库的知识库存在于一个结构化的 docs/ 目录中，该目录被视为记录系统。一个简短的 AGENTS.md （约 100 行）被注入到上下文中，主要用作映射，指向其他地方更深入的真实来源。 Plain Text 的设计决策框架也需要演进。 因为这个代码仓库完全由代理生成，所以首先针对 Codex 的 可读性 进行优化。同样地，团队希望为新入职的工程师提升代码的可导航性，而我们的人类工程师的目标是让代理能够 直接从代码仓库本身 推理整个业务领域。 从代理的角度来看，在有效运行时无法在上下文中访问的任何事物都不存在。存在于 Google Docs、聊天线程或人们头脑中的知识，系统无法访问。代码仓库本地的、版本化的制品（例如代码、markdown、模式、可执行计划）是它能看到的全部内容。 Diagram titled “The limits of agent knowledge: What Codex can’t see doesn’t exist.” Codex’s knowledge is shown as a bounded bubble. Arrows indicate that to make this information visible to Codex, it must be encoded into the codebase as markdown.我们认识到，随着时间的推移，需要将越来越多的上下文信息纳入仓库中。那个使团队就架构模式达成一致的 Slack 讨论？如果这个讨论对智能体来说不可发现，那么它就如同无法被理解，就像三个月后加入的新员工对其一无所知一样。 为 Codex 提供更多上下文意味着整理并提供恰当的信息，以便代理能够基于这些信息进行推理，而不是用临时指令淹没它。就像你会让新队友熟悉产品原则、工程规范和团队文化（包括表情符号偏好）一样，向代理提供这些信息会产生更一致的输出。 这种框架澄清了许多权衡问题。我们更倾向于那些可以在仓库内完全内部化并进行推理的依赖项和抽象。那些常被描述为“枯燥的”技术由于可组合性、API 稳定性以及在训练集中的表示，往往更容易被智能体建模。在某些情况下，让智能体重新实现部分功能比规避公共库中不透明的上游行为更划算。例如，我们没有引入通用的 p-limit 风格的包，而是实现了我们自己的带并发的 map 助手：它与我们的 OpenTelemetry 仪器紧密集成，拥有 100%的测试覆盖率，并且行为完全符合我们运行时的预期。 将更多系统内容以代理能够直接检查、验证和修改的形式呈现，这会提升效能——不仅对 Codex 如此，对其他也在代码库上工作的代理（例如 Aardvark ）同样有效。 强制执行架构与风格 仅靠文档无法使完全由代理生成的代码库保持连贯。 通过强制实施不变量，而非对实现细节进行微观管理，我们让代理能够快速交付，同时不破坏基础。 例如，我们要求 Codex 在边界处解析数据形状⁠，但并不规定具体如何解析（模型似乎喜欢 Zod，但我们并未指定那个特定的库）。 代理在具有严格边界和可预测结构的环境中最有效，因此我们围绕刚性架构模型构建了该应用。每个业务域被划分为固定的一组层级，具有严格验证的依赖方向和有限的允许边集合。这些约束通过自定义的 linter（当然是由 Codex 生成的！）和结构测试机械地强制执行。 下图展示了该规则：在每个业务领域（例如应用设置）内，代码只能通过固定的一组层级（类型 → 配置 → 代码仓库 → 服务 → 运行时 → 用户界面）向前依赖。横切关注点（身份验证、连接器、遥测、功能开关）通过单一显式接口进入：提供器。其他任何内容均不被允许，并被机械地强制实施。 Diagram titled “Layered domain architecture with explicit cross-cutting boundaries.” Inside the business logic domain are modules: Types → Config → Repo, and Providers → Service → Runtime → UI, with App Wiring + UI at the bottom. A Utils module sits outside the boundary and feeds into Providers.这种架构你通常会推迟到拥有数百名工程师时才着手构建。而借助编码代理（coding agents），这就成了早期必备条件：正是这些约束条件，使得系统能够在不发生退化或架构漂移的情况下实现高效推进。 在实际操作中，我们通过自定义代码检查工具（linters）和结构化测试，以及一小部分“风格不变量”来执行这些规则。例如，我们使用自定义代码检查规则，静态地强制实施结构化日志记录、模式（schemas）和类型（types）的命名规范、文件大小限制，以及特定平台的可靠性要求。由于这些代码检查规则是自定义的，我们会编写错误消息，以便将修复说明注入到代理（agent）上下文中。 在以人类为中心的工作流程中，这些规则可能会显得吹毛求疵或具有约束性。而借助智能代理，这些规则则会成为倍增器：一旦被编码，它们就能同时适用于所有地方。 同时，我们明确指出哪些地方需要约束，哪些地方不需要。这类似于领导一个大型工程平台组织：在中央层面执行边界，在本地层面给予自主权。你高度关注边界、正确性和可重复性。在这些边界之内，你允许团队（或代理）在解决方案的表达方式上拥有较大自由度。 生成的代码并不总是符合人类的风格偏好，这没关系。只要输出内容正确、可维护，并且对未来的代理运行具有可读性，就达到了标准。 人类的偏好持续反馈到系统中。审核评论、重构拉取请求以及面向用户的漏洞被记录为文档更新，或者直接编码到工具中。当文档不足时，我们将规则编码到代码中。 吞吐量改变了合并理念 随着 Codex 的吞吐量增加，许多传统的工程规范变得适得其反。 代码仓库以最少的阻塞性合并门方式运作。拉取请求是短期的。测试不稳定问题通常通过后续运行来解决，而非无限期阻塞进度。在代理吞吐量远远超过人类注意力的系统中，修正成本低，而等待成本高。 在低吞吐量环境中，这会是不负责任的做法。在这种情况下，这通常是合适的权衡。 代理生成的实际含义是什么 当我们说代码库是由 Codex 代理生成的时，我们指的是代码库中的所有内容。 Agents produce:人类始终处于闭环之中，但工作的抽象层次与以往不同。我们优先处理工作，将用户反馈转化为验收标准，并验证成果。当代理出现困难时，我们将其视为一个信号：识别缺失的内容——工具、护栏、文档——并将其反馈到代码仓库中，始终由 Codex 本身编写修复代码。 代理直接使用我们的标准开发工具。他们拉取审核反馈，内联回复，推送更新，并且通常会压缩合并自己的拉取请求。 Increasing levels of autonomy 随着越来越多的开发循环被直接编码到系统中——测试、验证、审查、反馈处理和恢复——代码仓库最近跨越了一个重要的门槛，在这个门槛下，Codex 可以端到端地驱动新功能。 给定一个提示词，该智能体现在能够： 验证代码库的当前状态 Reproduce a reported bug 录制一个演示故障的视频 Implement a fix 通过运行应用程序来验证修复 录制第二个演示分辨率的视频 Open a pull request 回应代理和人类反馈 检测并修复构建失败 只有在需要判断时才升级到人工 Merge the change 这种行为在很大程度上取决于该代码仓库的具体结构和工具配置，并且不应假设在没有类似投入的情况下可以推广——至少目前还不能。 熵和垃圾回收 代理的完全自主性也会引入新的问题。 Codex 会复制代码仓库中已存在的模式——甚至是那些不一致或次优的模式。随着时间的推移，这不可避免地会导致漂移。 最初，人类手动处理了这个问题。我们团队过去常常在每个周五（每周的 20%）清理“AI 垃圾”。不足为奇的是，这种方式无法扩展。 相反，我们开始直接将所谓的“黄金原则”编码到代码仓库中，并建立了一个周期性的清理流程。这些原则是明确且机械的规则，确保代码库对未来的代理运行清晰且一致。例如：(1) 我们更喜欢使用共享工具包而非手动编写的辅助函数，以集中管理不变量；(2) 我们不会以“YOLO 风格”探测数据——我们会验证边界或依赖带类型的 SDK，以防止代理意外地基于猜测的结构进行构建。定期地，我们有一系列后台的 Codex 任务，这些任务会扫描偏差、更新质量等级，并发起针对性的重构拉取请求。这些任务中的大多数可以在一分钟内完成审查并自动合并。
