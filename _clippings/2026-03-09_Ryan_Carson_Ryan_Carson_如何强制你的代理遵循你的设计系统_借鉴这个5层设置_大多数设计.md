# 如何强制你的代理遵循你的设计系统（借鉴这个5层设置）

大多数设计系统失败的原因很简单：它们是可选的。

如果你想要可靠的 UI 一致性，就需要停止将你的设计系统视为指导，转而将其视为一份契约。

本文将介绍一种实用且可重复的方法来实现这一点。该方法基于我的实际生产环境，但这种模式足够通用，可用于任何代码库、任何框架以及任何编码代理。

（你也可以走捷径，直接让你的代理阅读这段内容并实施该系统 :D）

## 什么是设计系统？

设计系统是关于你的用户界面如何构建以及如何表现的共享约定。

至少，它通常包括：

- 设计标记（颜色、间距、排版、圆角、层级）
- 可复用组件（按钮、表单、卡片、模态框等）
- 交互模式（布局、导航、错误状态、渐进式展示）
- 使用规则（应该做什么、应该避免什么以及必须做什么）

没有这份合同，每一个新的表面都会漂移。有了它，你的产品即使在代理快速生成代码时也能保持一致。

## 为什么仅靠文档不起作用

文档是必要的，但不充分。

代理可以读取您的样式规则，同时仍然生成原始间距类。

代理可以获取你的排版标准，同时仍然硬编码 \`text-\[44px\]\` 以匹配原型。

代理可以跳过您的表单包装器并直接导入原始类型。

这一切都不会发生是因为你的代理试图故意刁难你。它发生是因为系统没有让正确的事情变得最容易。

要解决这个问题，你需要在工作的每个阶段进行执行。

## 执行模型

一个确定性的设计系统工作流程包含五个层级：

1.  规范文档：视觉语言和交互规则的唯一事实来源。
2.  座席路由：一种强制座席使用那些文档的技能或指令层。
3.  本地代码检查规则：在不符合规范的代码上会失败的自定义检查。
4.  提交前置钩子：在提交之前自动运行的暂存文件检查。
5.  CI 门控：合并时检查，阻止漂移进入主分支。

重点不在于任何单一的层。重点在于重叠。如果一个层遗漏了某些内容，另一个层会捕捉到它。

## 1) 规范文档：编写能够被执行的规则

大多数风格指南过于模糊，无法用于代码检查。

“使用一致的间距”不可被 lint 检查。

使用语义间距标记（\`xxs\`、\`xs\`、\`s\`、\`m\`、\`l\`），而非原始数字工具类（\`mt-3\`、\`px-4\`、\`gap-2\`）” 是可被 lint 检查的。

在编写设计文档时，将它们分为三个具有明确职责的文档

- 设计规则：硬性的 DO/NEVER 政策
- 视觉语言：标记映射，组件样式基元，排版/颜色契约。
- 交互模式：流程和界面的布局与行为契约

然后添加一个明确的“Machine Enforcement”部分，明确列出命令和闸门行为。如果它不在该部分中，那么它在合同上就不具有效力。

## 2) 座席路由：使座席首先查阅正确的来源

如果你使用编码代理，添加一个专门的设计系统/SKILL.md。

它的工作很简单：

- 将与路由设计相关的任务分配到正确的文档。
- 防止临时的样式决策
- 保持视觉引导集中。

这将“记得检查设计系统”转变为确定性行为。

一个有用的思维模型：你的代理应该表现得像一个编译器管道，而不是聊天伙伴。输入经过策略，然后执行才会发生。

## 3) 自定义 lint 规则：用代码编码你的设计契约

现成的代码检查工具无法完全执行你的设计系统。你需要针对实际标准制定自定义规则。

典型的高价值检查:

- 间距标记检查：禁止原始间距工具；要求语义化间距标记。
- 颜色标记检查：禁止原始十六进制/RGB/HSL 字面量和任意颜色工具。
- 令牌合约检查：确保 CSS 变量、Tailwind 令牌和组件原语保持对齐。
- 排版常量检查：要求共享的标题常量，禁止原始的标题工具类。
- 共享包装器检查：强制使用包装器类型来包装原始基本类型。

规则要严格但实用。为罕见的边缘情况添加明确的异常标记，并且在使用时要求说明理由。

```typescript
// pseudo-rule
if (classToken.matches(/^(mt|mb|px|py)-\d+$/)) {
  fail("Use semantic spacing token (e.g. mt-s), not numeric utility");
}
```

具体实现不如原则重要：如果能够检测到违规行为，就应该自动阻止。

## 4) 提交前钩子：对暂存文件快速失败

Pre-commit 是合规成为习惯的地方。

在钩子中以单个命令运行你的 design-system 分阶段 lint 检查。保持一个入口点，这样代理就不必通过多个重复的命令进行路由。

```bash
npm run lint:design-system:staged
```

该命令应该编排你的设计检查（间距、颜色、令牌契约、表单、排版等）以处理暂存文件。

为什么分阶段？

- 快速反馈
- 聚焦信号
- 迭代工作的低摩擦

当代理在提交前发现即时、可操作的失败时，修复会在上下文仍清晰时进行。

## 5) CI 门禁：远程执行相同的合约

本地检查是必要的，但不具有权威性。

CI 必须运行相同的设计系统契约，如果引入漂移则使拉取请求（PR）失败。否则，合规性取决于每个本地执行环境是否运行了相同的检查。

推荐模式：

- 在拉取请求上运行变更文件设计系统 Lint 检查
- 可选地按计划或在主要发布分支之前执行全仓库扫描。
- 将失败视为阻碍。

这是“我们鼓励设计一致性”和“我们保证设计一致性”之间的区别。

## 范围是一切

执行项目失败的一个原因：团队试图立即对所有内容进行 lint 检查。

从有意设定的范围开始

对于许多产品，这意味着首先要优先处理已登录应用，同时将管理界面和旧版营销页面推迟到它们完成专门的重新设计流程之后。

在你的文档和代码检查规则范围中都清晰地记录这一点。模糊的范围会导致无尽的误报和策略疲劳。

## 无混乱的异常处理

你将需要异常。目标是受控异常。

采用简单的策略：

- 异常需要内联标记。
- Marker 必须包含一个简短的原因。
- 异常像代码债务一样被审查。
- 定期审计并移除过时的异常。

这使你的系统保持严格而不变得脆弱。

## 这日常是什么样子的

典型的工作流程如下：

1.  一个任务提示要求代理构建一个新的 UI 界面。
2.  Agent 通过设计系统的技能和文档进行路由。
3.  Agent 使用共享的常量/令牌/包装器编写代码。
4.  Pre-commit 运行暂存的设计 lint。
5.  任何违规行为将立即失败并附带特定消息。
6.  代理修复违规。
7.  CI 在 PR 上重新运行相同的合约。
8.  只有当设计检查为绿色时，合并才会进行。

在那种情况下，设计一致性不再依赖于记忆、品味或自律。

## 如何在你的仓库中采用这个

你可以推出这个，如果保持范围紧凑：

1.  将设计文档整合为清晰的政策 + 令牌引用。
2.  为你的代理添加一个设计系统技能/指令路由。
3.  首先实施 2-3 项高价值的自定义 Lint 检查（间距、颜色、包装器）。
4.  创建一个编排器命令 (\`lint:design-system\`)
5.  添加暂存变体并将其集成到 pre-commit 中。
6.  使用相同的命令契约添加 CI 门。
7.  添加明确的范围和异常策略。
8.  随着违规行为趋于稳定，逐步扩展规则。

不要从完美开始。从决定论开始。

## 常见的失效模式

注意这些：

- 多个相互竞争的 lint 入口点混淆了代理工作流。
- 引用已删除文件或过时命令的文档
- 严格但不可执行的规则
- 过早包含未迁移表面的范围
- 无异常策略，导致静默的临时绕过。

解决方法总是一样的：集中化、简化，并且明确执行。

## 最终要点

如果你希望你的代理使用你的设计系统，不要礼貌地请求。

将设计系统编码为契约。

将每一个 UI 任务通过它路由。

运行本地和远程的确定性失效的门。

保持文档、代码检查工具、钩子和 CI 步调一致。

一旦你做到这一点，设计一致性就不再是遥不可及的目标，而是开始变得自动。
