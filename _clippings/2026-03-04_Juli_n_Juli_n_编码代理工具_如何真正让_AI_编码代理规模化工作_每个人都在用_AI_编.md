# 编码代理工具：如何真正让 AI 编码代理规模化工作

每个人都在用 AI 编码代理进行开发。但只有极少数人能获得稳定的结果。

区别不在于模型、IDE 或提供商。而在于代理框架：围绕代理构建的结构化上下文、工具和护栏系统，以确保代理每次都能可靠运行。

上下文工程技术

根本的学科是 上下文工程 : 设计和控制 LLM 在生成单个 token 之前所看到的一切。

代理工具是付诸实践的上下文工程：将理论转化为可重复成果的具体实现。

在 MercadoLibre，我们正在向近 2 万名开发者和数千个代码库推出这一举措。以下是我们的经验、有效做法以及大多数团队存在的误区。

## 为什么上下文工程？

这是一个改变了我对 AI 代理思考方式的思维模型：

> 你的 AI 编程代理是一位入职第一天就才华横溢的新员工。它反应迅速、充满热情，却对你的代码库、编码规范和架构一无所知。

你不会仅仅说“修复这个漏洞”或“实现这个功能”然后就继续。

你需要让他们入职：文档、技术栈、风格指南、发布流程工作流、获取合适的工具，以及一位导师来审核他们的工作。

这就是情境工程： 构建围绕模型的系统 所以它可以 始终如一地做到最好。

## 代理循环及其瓶颈

受欢迎的 AI 编码代理如 Claude Code、Cursor 和 Codex，都具有相同的基本循环：

阅读 → 规划 → 编码 → 验证 → 迭代

代理读取你的文件，规划方法，编写代码，运行测试，如果出现问题则循环返回。这个循环很强大，但每次迭代都消耗相同的有限资源： 上下文窗口 .

上下文窗口是智能体当前任务的实时工作区。智能体在任何给定时刻可引用的所有内容都必须容纳在其中。并且在循环的每个阶段，它都会增长：

上下文窗口使用 - Anthropic

该图表展示了 token 如何在有限的上下文窗口内进行分配。系统规则固定在顶部，而工具结果和对话历史则随着每一轮对话而增长。

这是我们正在围绕其进行工程设计的约束条件进行工程设计围绕。

- 系统提示和自定义规则 ：在每一轮开始时注入。如果规则对当前任务没有帮助，它们就浪费空间。
- 工具定义 : 你配置的每个 MCP 服务器都会添加其架构。更多工具 = 其他所有内容的空间就越小。
- 对话历史 ：每一条之前的消息线性累积。
- 工具结果 : 文件内容、终端输出、API 响应。读取单个大文件可能会一次性消耗数千个 token。
- 代理的自身输出 : 它编写的代码也存在于上下文窗口中。

每一个消耗在冗长的工具结果或过于冗长的规则文件上的 token，都是无法用于代理正在处理的实际代码的 token。随着上下文不断填充，准确性和召回率会下降，这种现象通常被称为 context rot。

过了某个临界点，一些研究表明当上下文窗口容量利用率达到大约60%时，更多的上下文会使智能体的表现反而更差。

关于更多见解， 上下文衰减我发现了一篇最近的博客：https://www.morphllm.com/context-rot

即使上下文窗口达到 100 万或更多 token，根本挑战仍然存在。

最好的代理工具设计时都以这一现实为核心：在恰当的时机注入恰当的上下文，避免用无关信息污染窗口，并合理安排长时间运行的任务以保持其简洁高效。

## 代理工具：你需要掌握的四个杠杆

代理控制集是一组结构化的控制，用于塑造代理的知识、能力以及工作验证方式。有四个关键杠杆：

自定义规则（光标/规则、AGENTS.md、CLAUDE.md 等等）

这是最容易上手的切入点，大多数团队应该从这里开始。自定义规则是在每次交互开始时自动注入到代理上下文的文件。

自定义规则中包含什么？

- 您的项目的技术栈和架构模式
- 命名规范和代码风格偏好
- 测试理念（始终编写表格驱动输入的单元测试）
- 特定于你的代码库的常见陷阱
- 不要做什么（你多次看到该代理产生的反模式）

什么不属于

- 整个 API 文档（太长，浪费上下文）
- 明显的指导（编写整洁的代码）
- 矛盾的 规则

关键见解： 自定义规则是动态文档。 每次代理犯错时，你可以询问代理如何改进其框架。几周后，你的规则文件将成为极其有效的行为指南。

撰写有效自定义规则的技巧：

- 篇幅控制在 500 行以内。 说明务必准确无误 。
- 让它们模块化。 将规则按关注点拆分为专注文件：架构、测试、代码、安全。这样代理可以仅加载任务所需的内容。
- 使用少样本示例。模型从示例中学习远远优于从抽象指令中学习，但不要过度使用冗长的示例。
- 不要让所有东西都保持开启状态。 很少有规则需要在每个会话中注入。当你的工具支持时，使用条件加载。这是技能补充自定义规则的地方：将详细的、需要大量上下文的指令转移到按需激活的技能中。

2\. MCP 服务器（模型上下文协议）

MCPs 是你为代理提供超越读写文件的工具 。可以将它们视为扩展代理能力的插件。

开箱即用，编码代理可以读取文件、编写代码并运行终端命令。但借助 MCPs，它还能：

- 查询你的数据库以了解模式和数据
- 搜索你的内部文档或维基
- 查阅内部 API 契约
- 与你的 CI/CD 流水线交互
- 从 Figma 获取设计规范
- 测试它的实际实现

MCPs 的能力在于弥合代理与贵组织知识之间的鸿沟。没有它们，代理只能局限于代码库中的内容。有了它们，代理就能访问人类开发者所能使用的相同资源。

它们对实际代理输出的验证也很强大，稍后我会讨论反馈循环。

3\. 技能

技能可以赋予代理新的能力和领域专业知识 。它们是 Harness 中最强大的杠杆，因为它们将上下文注入与可执行逻辑。

技能是一个包含 SKILL.md 作为入口点的目录，该目录可以打包模板、示例输出、参考文档和可执行脚本。

仅简短描述会保留在上下文中，以便代理知道有哪些可用内容。完整内容只有在调用技能时才会被注入，调用方式可以是用户通过(/skill-name)指令，或者代理在检测到相关性时自动调用。

这种按需加载意味着技能可以根据需要变得非常详细， 而不会永久占用您的上下文预算。

它们有两种类型：参考技能（传授知识，包括惯例、模式、领域背景）和任务技能（针对特定操作提供分步指导）。

但真正的强大之处在于，技能可以组合并执行脚本，这使得可扩展性实际上是无限的：从生成交互式可视化到获取实时 CI 数据。它们还可以在隔离的子代理中运行，拥有自己干净的上下文窗口，避免繁重的任务污染您的主会话。

技能是 可编程、上下文感知、可组合的代理行为单元.

4\. 规范驱动开发（终极工具）

这一点值得特别关注，因为它彻底改变了你与代理人互动的方式 。

当前 Coding Agents 面临的主要瓶颈之一存在于椅子和屏幕之间：是你。这是由于沟通问题 。

当 人们开始使用编码代理时，普通用户没有提供足够的细节，因此代理必须'预测'正确的实现方式。

创建一个新功能，用于从后台添加新项。

看起来很简单，但没有具体说明任何内容：技术栈、后台管理系统在哪里、API 契约、新项存储在哪里。

在这种情况下，代理将读取当前代码库，规划实施，并可能实现一个可行的 MVP。你从 BO 添加一个新项，它能正常工作，同时将该项目存储到现有的 MySQL 中。

但是当你再次点击“添加”按钮时，它会将该项目插入两次。

很明显，代理应该通过 ID 管理幂等性。在我们的业务中，只有一个角色可以插入项目，这是很明显的。

问题不在于代理，而在于原始的初始输入。

那是 Spec Driven Development（规范驱动开发）旨在解决的主要问题之一。那么，它是什么？

规范驱动开发（SDD）是在代理编写第一行代码之前编写详细规范的实践。这些规范包括：该功能的作用、它如何与现有代码集成、什么是边缘情况、验收标准是什么样的，以及测试计划是什么。

为什么 SDD 上下文工程处于最纯粹的形式？因为规范成为了框架。

当你给代理一个写得好的规范时，你不仅仅是告诉它要构建什么。你是在一次性设计它的整个上下文窗口。该规范整合了自定义规则（架构决策）、分步指导和验收标准（如评审代理），所有这些内容都整合在一个或多个制品中。

最棒的部分： 你也可以使用代理来编写规范。

我将在另一篇文章中详细阐述规范驱动开发、框架、优缺点以及我们如何大规模实施它。

## 反馈循环

上面的四个杠杆定义了智能体所了解的内容和它能执行的操作。但有一个部分不在上下文工程之外，而是使整个系统运转起来： 反馈循环。 测试、代码检查工具、类型检查器、构建脚本：每个产生通过/失败信号的工具都成为智能体用来自我修正的反馈机制。

代理反馈循环

可获得的结构化反馈越多，需要的人工参与就越少。

实施这一要求最有力的机制之一是代理钩子：用户定义的命令，这些命令会在代理生命周期的特定时刻自动执行。将你的验证逻辑绑定到停止钩子中，代理实际上必须等到检查通过才能完成。这不是一个它可能会忽略的建议。这是一个强制执行的关卡。

我也会在另一篇专门的文章中深入探讨反馈循环：钩子、评审代理、停止钩子模式，以及如何使整个代理生命周期可编程。

## 我们在 MercadoLibre 如何规模化运作

理论不错，但现实会找上门来。

真正的规模化需要将这些杠杆协调成一个能在整个组织内运行的系统。

有很多规模问题需要解决：不同的技术和版本、数千个（遗留）仓库、多个知识领域，当然还有使用不当的成本。

我们目前正在实施规范驱动开发，仍在获得内部采纳（已覆盖4000名开发者），因为改变开发者的日常工作流程很困难，但我会在另一篇文章中详细讨论。

以下是我们做的一些其他做法：

标准化规则针对每一种技术

我们在组织层面维护一套精心挑选的自定义规则，这些规则针对我们所有的技术（9+）栈、内部库以及代码审查标准进行了优化。团队继承这一基础，然后添加针对仓库的特定规则。

这些规则的质量至关重要。过于具体可能会破坏遗留项目。使用未经批准的外部库可能会导致安全漏洞。

内部 MCPs 用于我们的内部开发平台

我们搭建了具备内部云平台能力和上下文的内部 MCP 服务器。其中一个主要的 MCP 具备完整的工具包上下文，以使用对齐的服务和内部 SDK。

提供来自 RAG 结果或更新的应用程序文档的业务背景的内部 MCPs

自定义 代码审查代理

我们构建了独立的代码审查代理，这些代理作为我们 CI 流水线的一部分运行。每个 PR，无论是由人工编写还是由 AI 编码代理生成，在人工审查者查看之前都会被自动分析。

它们返回优先排序的发现结果，因此工程师能优先看到最关键的问题，而不是一份没有优先级的评论列表。这样人工评审人员就能专注于高层次的设计决策，而不是去发现格式违规或未遵循的规范。缺陷在生产前被发现。

结果是：更快的代码审查周期、更一致的代码质量，以及一个能随着拉取请求（PR）数量而非审查人员数量扩展的安全网。

## 大局

上下文工程不仅仅是一套技术。它是一门新兴的工程学科 。而代理框架是其有形的产出：你实际构建、维护和迭代的东西。

随着 AI 编码智能体的能力日益增强，获胜的团队不会是那些使用最先进模型的团队。他们将是那些拥有设计最精良的整合系统的团队：自定义规则、MCPs、专业技能以及规范驱动的工作流协同构成一个系统，同时具备紧密的反馈循环以确保所有部分都朝着目标收敛。

机遇非常巨大。但这需要我们不把 AI 代理视为魔法盒，而是将其视为需要适当入职培训、工具支持和监督的出色团队成员。

我从哪里开始？我的建议是采用最简单的方法：关于最佳编码实践的自定义规则或技巧。编码愉快！
