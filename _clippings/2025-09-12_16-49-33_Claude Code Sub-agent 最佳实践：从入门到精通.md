# Claude Code Sub-agent 最佳实践：从入门到精通

大家好，今天我想分享一下我是如何思考、设计和使用 Claude Code 的 sub-agent（子代理）系统的。

#### 一、 Sub-agent 的初期问题与最佳实践的发现

Claude Code 在几周前推出了 sub-agent 功能。这是一个非常令人兴奋的概念。然而，对于很多尝试过它的人来说，初期的体验常常是负面的。大家普遍反映，sub-agent 速度很慢，消耗的 token（代币）非常多，而且最重要的是，感觉它并没有对最终结果产生什么实质性的帮助。

我也是这些人中的一员。但就在最近，我开始学习使用 sub-agent 的最佳实践，这完全改变了游戏规则，让我的 Claude Code 性能表现得更加出色和稳定。

#### 二、 Sub-agent 的核心作用：上下文工程与优化

首先，我们需要理解 Claude Code 最初为什么要引入 sub-agent 的概念。

如果你不了解 Claude Code 代理的工作原理，它本质上是一个“工具调用代理”（Tool-calling Agent），配备了一系列工具，比如读取文件、列出文件、编辑文件等等。其中一些工具，比如“读取文件”，会消耗大量的 token，因为它需要把整个文件内容都包含到对话历史中。

在 sub-agent 功能出现之前，所有任务都由主代理自己完成。这意味着，在它真正开始实施代码之前，可能就已经用掉了 80% 的上下文窗口（Context Window）来进行前期的研究工作，比如搜索和阅读相关文件。当上下文窗口被填满时，就会触发一个叫做“compact”的对话压缩机制，它会尝试总结整个对话历史。我们都知道，每一次对话被压缩，代理的性能就会急剧下降，因为它开始丢失之前做过什么的具体上下文信息。

这就是 sub-agent 派上用场的地方。后来，他们引入了一个 `task`（任务）工具，允许主代理将一个任务分配给另一个代理。这个新的子代理拥有和主代理完全相同的工具集。你可以让这个子代理去扫描整个代码库，理解所有需要修改的相关文件，然后基于这些信息，返回一份总结报告。

这种方式节省 token 的原理在于，从主代理的视角来看，子代理在中间执行的所有步骤（比如读取了多少个文件，搜索了多少次）都不会成为主对话历史的一部分。主代理只能看到它分配了一个任务，然后子代理带着一份研究报告的摘要回来了。

通过这种方式，你实际上将那些可能消耗超过 9 万 token 的大量操作（比如读取、搜索文件），转化成了一份只有几百 token 的摘要，但这份摘要依然包含了指导下一步行动所需要的最重要信息。

所以，sub-agent 的整个目的，始终是围绕着**上下文工程（Context Engineering）和上下文优化（Context Optimization）**。

#### 三、 常见误区：将 Sub-agent 用于直接执行任务

那么，事情是在哪里出错的呢？当人们开始尝试让 sub-agent 不仅仅做研究工作，而是直接进行代码实现时，问题就出现了。

举个例子，我最初的想法是，我们能不能有一个“前端开发代理”和一个“后端开发代理”？主代理只需要负责协调，将任务分配给它们。比如，构建一个待办事项应用，先分配给前端代理做界面，完成后，再告诉它“干得不错，现在我们来构建后端”，然后把任务分配给后端代理。

这个想法听起来很美好，但问题在于，一旦 sub-agent 实现的东西不是 100% 正确，你想让它修复时，麻烦就开始了。因为对于每一个代理来说，它所拥有的信息都是非常有限的。

- **前端开发代理**：它只知道在它那个特定任务会话中，它采取了哪些行动，以及它生成的最终消息。
- **后端开发代理**：同理，它也只了解自己的任务上下文。
- **主代理**：它也只有有限的信息，因为它看不到子代理执行的具体步骤和细节，比如创建了哪些文件，文件里写了什么。它只知道“我分配了任务”和“它说任务完成了”。

所以，当你说“这里有个前端的 bug”并再次把任务分配给前端代理时，实际上是开启了一个全新的、独立的会话。这个新的前端代理会话，完全不知道上一个前端会话里发生了什么，更不知道后端代理做了什么。每个任务都是一个高度封闭的会话。

这种情况很可能会被未来的更新解决，比如当我们找到一个好的方法在不同代理间共享上下文（Shared Context）或记忆时。但就目前而言，最佳的实践是：**把每个 sub-agent 看作一个研究员**。

#### 四、 最佳实践：专家代理与文件系统上下文共享

Adam Wolff，Claude Code 团队的一位核心工程师，也给出了类似的反馈。他说：“不要把 sub-agent ‘拟人化’。用它们来组织你的提示词（prompts）和精简上下文。Sub-agent 在能做大量工作，然后只把少量信息反馈给主对话线程时，效果是最好的。”

基于这一点，我产生了一个想法：如果每个服务提供商，比如 Vercel、Netlify、Supabase，都有自己的 sub-agent 呢？每个 agent 都预装了该服务的最新文档、知识和工作流，并且可以按需调用。

于是我开始尝试创建不同的“专家 sub-agent”（Expert Sub-agents）。

- **shadcn-expert**：配备了专门的 MCP（Model Context Protocol）服务器，可以获取 shadcn 的主题和组件信息。
- **Vercel-ai-sdk-expert**：加载了最新的 Vercel AI SDK v5 文档。
- **stripe-expert**：加载了最新的 Stripe 文档和 context7（一个相关工具）。

与此同时，我也对跨代理的上下文共享做了一些优化。这个灵感来自 Manus 团队的一篇关于上下文工程的博客。他们提出的一个核心观点是：**使用文件系统作为最终的上下文（Use the File System as Context）**。

与其将所有工具的调用结果都塞进对话历史，他们选择将结果保存到本地文件中，以便后续随时读取。

我设计的流程是这样的：

1.  **统一的上下文文件**：在 `.claude/tasks/` 目录下，有一个 `context_session_X.md` 文件。这个文件是所有代理共享的“真相之源”，记录了项目的整体目标、当前状态、任务列表和进度日志。
2.  **子代理的工作流程**：
    -   在开始工作前，每个子代理**必须**先读取这个 `context_session.md` 文件，以获取完整的项目背景。
    -   完成研究和规划后，子代理会创建一个详细的实现计划文档（例如 `ui_implementation_plan.md`）保存在 `.claude/doc/` 目录下。
    -   同时，它会更新 `context_session.md` 文件，记录下它完成了哪些工作以及关键的发现。
3.  **主代理的角色**：主代理负责协调，它会读取子代理生成的计划文档，然后执行具体的实现步骤。

通过这种方式，主代理、shadcn 专家、Vercel AI 专家等所有代理，都通过读写共享的 markdown 文件来保持信息同步。这个设计极大地提升了我的 Claude Code 的成功率和最终结果的质量。

#### 五、 实战演示：构建 ChatGPT 应用

现在，我们来实际操作一下。

我会给出一个提示：“帮我构建一个 ChatGPT 的复制品，使用 shadcn 做前端，Vercel AI SDK 5 做 AI 服务。我们先构建 UI，确保咨询了 sub-agent。”

1.  **创建上下文**：首先，它会创建一个 `context_session_1.md` 文件，里面包含了项目目标、技术栈、当前状态、任务和进度日志。
2.  **咨询 UI 专家**：接着，它会调用 `shadcn-ui-expert` 这个子代理来设计和规划 UI。
3.  **UI 专家工作**：`shadcn-ui-expert` 读取了上下文文件，然后开始使用 `shadcn-components` 这个 MCP 工具来列出所有可用的组件，并进行研究。
4.  **生成 UI 实现计划**：最终，它在 `.claude/doc/` 目录下创建了一个 `chatgpt_ui_implementation_plan.md` 文件。这个文件非常详细，包括了项目架构、核心 UI 结构图、组件层级、要构建的关键组件列表，以及分阶段的实现步骤。
5.  **主代理执行**：主代理读取了这份详细的计划，然后开始执行。它会更新 `todos`，然后一步步安装 shadcn 组件、创建布局和页面。
6.  **修复 Bug**：在运行过程中，出现了一个 hydration 错误。我把错误信息粘贴回去，因为它有完整的上下文，所以它能够理解问题所在（`SidebarMenuAction` 已经是一个按钮，不应该再被另一个 `Button` 组件包裹），并迅速修复了它。
7.  **集成 AI 服务**：UI 完成后，我让它继续集成 Vercel AI SDK。
8.  **咨询 Vercel AI 专家**：它调用了 `vercel-ai-sdk-implementation-planner` 子代理。
9.  **Vercel AI 专家工作**：这个代理同样读取了上下文文件，分析了现有代码库，然后创建了一份 Vercel AI SDK 的集成计划文档。
10. **主代理再次执行**：主代理读取这份新计划，然后开始安装依赖、设置环境变量、创建 API 路由等。

最终，这个应用在一次成功的流程中就完成了，并且质量非常高，几乎和 ChatGPT 的原生界面一模一样。

这就是我学到的关于如何有效使用 sub-agent 的一些最佳实践。希望对你有所帮助！

**第一部分：Sub-agent 功能的初期问题与最佳实践的发现 (0:04-0:28)**

- **初期问题**
  - Claude Code 的 sub-agent 功能刚推出时，虽然概念新颖，但实际体验不佳。
  - 用户普遍反映其速度慢、消耗大量 token，且效果不明显。
  - 主讲人也曾有同样的负面体验。

- **发现最佳实践**
  - 最近，主讲人开始学习如何正确使用 sub-agent，从而彻底改变了 Claude Code 的表现，使其性能更稳定、更出色。

**第二部分：Sub-agent 的核心作用：上下文优化 (0:33-2:13)**

- **设计初衷**
  - Claude Code 的核心是一个能够调用多种工具（如`读写文件`、`列出文件`、`编辑文件`等）的 AI 代理。
  - 读取文件这类工具会消耗大量 token，因为需要将整个文件内容加载到对话历史中。
  - 在没有 sub-agent 之前，所有任务都由主代理完成，导致在执行任务前，可能已有 80% 的上下文窗口被研究和准备工作占用。
  - 这会触发“compact”压缩对话历史的机制，进而导致性能下降和信息丢失。

- **Sub-agent 的解决方案**
  - Sub-agent 允许主代理将特定任务（如研究）分配给另一个独立的代理。
  - 这个子代理拥有与主代理相同的工具集，可以独立完成文件扫描、代码库分析等工作。
  - 子代理完成任务后，只会将一份简洁的摘要（research report）返回给主代理，而不是把所有中间步骤都塞进主对话历史。
  - 这种方式将原本可能消耗数万 token 的操作，压缩成仅几百 token 的摘要，同时保留了核心信息，极大地节约了 token 并优化了上下文。
  - 因此，sub-agent 的核心价值在于**上下文工程（context engineering）和上下文优化（context optimization）**。

**第三部分：常见误区：将 Sub-agent 用于直接执行任务 (2:14-4:09)**

- **错误的使用方式**
  - 很多人（包括主讲人自己）曾尝试将 sub-agent 直接用于执行任务，例如创建一个“前端开发代理”和一个“后端开发代理”，让主代理负责协调。
  - 这种方式看似美好，但存在致命缺陷。

- **问题根源**
  - 每个 sub-agent 任务都是一个独立的、封闭的会话。
  - 当主代理将一个 bug 修复任务再次分配给“前端开发代理”时，这个代理并不知道上一次会话中发生了什么，也无法获取“后端开发代理”的工作内容。
  - 主代理也同样存在信息盲区，因为它看不到 sub-agent 的具体执行步骤，只能看到任务分配和完成的简单信息。
  - 这种信息隔离导致 sub-agent 之间无法协作，也难以进行有效的 Debug。

- **最佳实践**
  - Adam Wolff（Claude Code 核心工程师之一）的建议：不要将 sub-agent “拟人化”，而应将其作为组织 prompt 和精简上下文的工具。
  - Sub-agent 最适合的场景是：**完成大量信息检索和研究工作，然后将少量关键信息反馈给主对话线程**。

**第四部分：理想的 Sub-agent 设计模式：专家代理 (4:21-6:43)**

- **设计理念**
  - 主讲人提出，可以为每个服务或框架创建一个专属的“专家 sub-agent”（expert sub-agent）。
  - 例如，可以创建 `shadcn-expert`、`Vercel-ai-sdk-expert`、`stripe-expert` 等。
  - 每个专家代理都预装了对应服务的最新文档、最佳实践、设计模式等专业知识。
  - 主代理只需调用这些专家代理进行研究和规划，而将具体的执行工作留给自己。

- **共享上下文的机制：文件系统**
  - 主讲人借鉴了 Manus 团队的“上下文工程”理念，即**使用文件系统作为最终的上下文管理系统**。
  - 具体做法是：
    1.  **主代理**：创建一个统一的 `context_session.md` 文件，用于记录项目的整体规划和当前状态。
    2.  **Sub-agent**：在执行任务前，必须先读取这个 `context_session.md` 文件，了解全局信息。
    3.  **Sub-agent**：完成研究和规划后，将详细的实现计划（Implementation Plan）写入一个独立的文档中（例如 `ui_implementation_plan.md`），并更新 `context_session.md` 文件。
    4.  **主代理**：读取 sub-agent 生成的实现计划，然后开始执行具体的编码工作。

- **效果**
  - 这种设计模式确保了所有代理（包括主代理和子代理）都能通过读写共享文件来保持信息同步，从而大大提高了任务的成功率和结果的质量。

**第五部分：实战演示：创建一个 ChatGPT 复制品 (11:49-14:38)**

- **任务描述**
  - 使用 shadcn 作为前端，Vercel AI SDK V5 作为 AI 服务，构建一个 ChatGPT 的复制品。

- **执行流程**
  1.  **初始化**：主代理首先创建一个 `context_session_1.md` 文件，记录了项目目标、技术栈、任务分解等初始信息。
  2.  **UI 规划**：主代理调用 `shadcn-ui-expert` 子代理，要求它基于上下文文件来设计 UI 实现方案。
  3.  **Sub-agent 工作**：`shadcn-ui-expert` 读取上下文文件，然后利用其内置的专业知识和 MCP 工具（Model Context Protocol，一种用于获取 shadcn 组件信息的工具）进行研究，最终生成一份详细的 `chatgpt_ui_implementation_plan.md` 文档。
  4.  **UI 实现**：主代理读取这份 UI 实现计划，然后开始按部就班地执行编码任务，包括安装依赖、创建布局和组件等。
  5.  **AI 功能集成**：UI 构建完成后，主代理再调用 `vercel-ai-sdk-implementation-planner` 子代理，规划 AI 功能的集成方案。
  6.  **Sub-agent 工作**：该子代理同样先读取上下文文件，然后结合其掌握的 Vercel AI SDK V5 最新文档知识，生成一份 AI 集成的详细计划。
  7.  **AI 功能实现**：主代理根据这份新计划，完成后续的编码工作。

- **结果**
  - 整个过程一气呵成，最终成功构建了一个功能完善、UI 精美的 ChatGPT Clone 应用，证明了这套 sub-agent 设计模式的有效性。
