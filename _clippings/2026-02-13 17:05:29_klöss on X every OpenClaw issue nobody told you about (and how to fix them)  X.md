如果你来自旧版 OpenClaw 安装，好消息是安装程序实际上能很好地处理迁移。它会将你的.clawdbot 目录移动到.openclaw，并创建一个符号链接回原位置，这样不会有任何问题，你的配置、soul 文件、内存和工作区都会保留下来。clawdbot 包也作为兼容性适配层保留。

真正的问题在于它没有真正清理掉的部分。在某些情况下，旧的 clawdbot-gateway.service 可能会继续与新的 openclaw-gateway.service 同时运行，当两者都试图占用端口 18789 时，就会出现重启循环，新的网关会反复因“另一个网关实例已在监听”而失败切换。看起来 OpenClaw 出了问题，但实际上只是它自己与前身在争夺端口。

在安装 OpenClaw 之前，请完全停止并禁用旧服务：

```
systemctl --user stop clawdbot-gateway.service
systemctl --user disable clawdbot-gateway.service
rm -f ~/.config/systemd/user/clawdbot-gateway.service
systemctl --user daemon-reload
```

然后卸载旧的 npm 包（npm uninstall -g clawdbot），并检查 /usr/local/bin/clawdbot 或 /usr/local/lib/node\_modules/clawdbot 中是否有残留文件，因为残留的包可能会悄无声息地干扰新安装。之后，全新安装 OpenClaw，您现有的工作区文件将被自动识别。

OpenClaw 有一个内置的诊断命令，名为 openclaw doctor，可一次性检查你的配置、网关、通道、工作区和权限。使用 --fix 标志运行它（openclaw doctor --fix），并针对实际问题进行修复，它将自动修复常见问题，如权限问题、缺失的目录、旧版配置键和过时的服务路径。在进行修改前，它会备份你的配置，并且不会修改你的 API 密钥或凭证，因此无论何时感觉有问题或升级后，都可以安全运行。你也可以不使用 --fix 标志运行它，有些用户发现这样效果更好。

首先，理解代理和子代理之间的区别，因为大多数人会混淆它们。

代理是你的团队，每个代理都有独特的个性、专属的工作空间、专属的 SOUL (.md)、专属的模型和专属的角色。可以把它们想象成员工：你的 CEO 代理负责战略和对外沟通，CTO 代理负责技术决策，CMO 代理负责内容和营销。它们都是高层级的、持久存在的，并且随时可用。

子代理是临时后台工作者，团队中的任何代理都可以生成子代理来处理任务而不阻塞其主会话。子代理在独立会话中运行，执行工作，完成后汇报并在被归档前结束。它们是一次性工作者，而非永久团队成员。

重要区别：默认情况下，子代理无法生成其他子代理。这是有意为之的。它可以防止失控的委托链以指数级销毁代币。目前有一个功能请求希望使这一设置可配置，但目前，每次生成时嵌套层级限制为一级。

为了控制您的团队成员可以委派给哪些座席，请设置允许列表：

```
{ "id": "ceo", "subagents": { "allowAgents": ["cto", "cmo", "cro"] } }
```

您的 CEO 可以以 CTO、CMO 或 CRO 代理的身份创建子代理。您的 CMO 不能以 CTO 的身份创建工作项，除非您明确允许。这为您提供了清晰的组织层级，避免了失控的交叉授权。

不是团队中的每个代理都需要最昂贵的模型。您的首席执行官需要强大的推理能力来进行编排和决策。您的首席技术官的代理需要代码优化的模型。负责运营任务的首席运营官可以使用更轻量、更便宜的工具。

您的首席执行官使用 Opus 进行复杂推理和战略决策。您的首席技术官使用 Codex 进行代码生成和技术工作。您的首席运营官使用 Haiku 进行快速运营任务和日常协调。

在你的配置中设置全局默认值，然后为每个代理覆盖这些默认值。这就是你在关键之处不牺牲质量的前提下控制成本的方法。执行快速研究任务的子代理不需要 Opus。通过 agents.defaults.subagents.model 将更便宜的模型设置为子代理的默认模型，并让你的顶级代理使用更高质量的模型。

OpenClaw 的默认值是有意设置为保守的。有两个设置控制并行处理：

maxConcurrent: 4 控制同一时间可以运行的顶级会话数量。subagents.maxConcurrent: 8 控制子代理会话可以并行运行的数量。

如果你的硬件能支持，就把这些调高。更多的并发意味着你的多智能体系统处理工作更快，而不是让所有任务都在瓶颈处排队。

默认情况下，子代理无法生成其他子代理。OpenClaw 硬编码了这一限制，以防止委托链螺旋式蔓延并导致代币指数级销毁的失控扇出。

有效的架构是让顶层代理（CEO、CTO、CMO）各自生成子代理来处理后台工作，这些子代理一次性完成任务并汇报。不存在更深层次的嵌套，也不存在子代理生成子代理的链式结构。

正在讨论一种可配置的覆盖（通过设置 allowNesting: true 或在子代理工具允许列表中添加 sessions\_spawn），但默认行为的存在有其合理原因。保持委托结构扁平化，让顶层代理将工作分解为子代理能够完成并返回的原子单元。

您团队中的每个代理都拥有自己的工作空间、个性和模型。但所有外部通信都应通过一个代理（您的 CEO 或主要代理）进行路由。

这是大多数人要么完全跳过，要么因为把所有内容都塞进一个文件而做错的地方。

OpenClaw 将身份分离为不同的文件，每个文件都有特定的用途。SOUL (.md)定义了你的代理是谁，而不是它能做什么或如何配置，而是它的核心本质：它的理念、风格、边界和个性。AGENTS (.md)定义了操作规则和行为指令，而 IDENTITY (.md)定义了显示名称和头像等展示细节。

SOUL (.md) 文件让你团队中的每个代理感觉像是不同的人，而不是同一个模型戴着不同的帽子。OpenClaw 的默认 SOUL (.md) 模板以这样的内容开头：“你不是一个聊天机器人。你正在成为某个人。” 这就是那种心态。你正在编写一个角色表，而不是一个配置文件。

对于 CTO 代理，你的 SOUL（.md）可能定义一种精确的、持怀疑态度的、以证据为优先的个性，这种个性对模糊的需求过敏，偏好技术细节，并对模棱两可的要求提出反对。对于 CMO 代理，SOUL（.md）定义的是一个有创造力、有战略眼光、注重品牌的人，专注于叙事和定位。相同的底层模型，但思维模式完全不同。

编写良好的 SOUL 文件的关键原则：具体性优于通用性，真实观点优于安全立场，明确边界优于无限制灵活性。如果有人阅读你的代理的 SOUL(.md)文件时，无法预测该代理对新情况的回应方式，那么这个文件就过于模糊。

每个代理在每次会话开始时读取其 SOUL (.md)文件。它被注入到系统提示中，作为代理身份的基础。如果代理修改了自己的 SOUL (.md)文件（它可以这么做），它会告诉你，因为该文件是它的身份，你应该知道它何时发生了变化。

```
"agentDir": "~/.openclaw/agents/cto/agent"
```

将每个代理指向其自己的目录。SOUL (.md) 放在工作区中，与 AGENTS (.md) 和 USER (.md) 并列。个性文件决定了每个代理如何处理问题、格式化输出、与其他代理沟通，以及决定哪些内容值得提出反对意见。

我遇到了一个特定的故障模式，花了一段时间才诊断出来：一个子代理在存在正在运行的开发服务器的代码仓库上执行了 rm -rf .next 命令，这导致开发服务器悄无声息地终止，没有错误、没有崩溃日志，只是停止提供服务。

解决这个问题的规则是，子代理通过 tsc --noEmit（类型检查不进行构建）验证其工作，并且只有拥有工作区的顶层代理会操作开发服务器。子代理从不直接与运行中的进程交互，它们只执行各自的独立任务并汇报结果。

当5个子代理大致同时完成任务时，每个子代理都会将其结果返回给父代理。通知队列出现积压。网关可能会超时。

设置清理：对非关键子代理生成的实例执行“删除”操作，以便它们在通知后立即归档，而非滞留。错开启动时间，确保子代理不会同时全部完成。请注意，通知操作是尽力而为的。如果在通知未完成时网关重启，则相关结果将丢失。

cron 配置中的模型别名并不总是能正确解析。你的 cron 任务写着“haiku”，系统不知道你指的是哪个“haiku”。

始终使用完整的模型字符串：anthropic/claude-haiku-4-5，而非 haiku。这可避免你调试 cron 运行但使用错误模型或根本不使用模型时出现的幽灵故障。

在长时间的会话中，上下文会被过时的工具输出填满。旧的 API 响应、过时的文件内容、已完成的任务结果。这个智能体开始变得困惑，因为它引用了不再相关的信息。

```
"agents": { "defaults": { "contextPruning": { "mode": "cache-ttl", "ttl": "30m", "keepLastAssistants": 3 } } }
```

当会话的最后一次 Anthropic API 调用早于 TTL 时，修剪机制会启动并从内存中的上下文中修剪掉过大的工具结果。它不会重写磁盘上的会话历史，而只是精简下一次调用时发送给模型的内容。最后 3 条助手回复保持不变。大幅节省 token，且智能体保持专注于当前内容。

在 OpenClaw 压缩你的上下文窗口之前，你希望代理首先将其记忆保存到磁盘。否则，上下文压缩可能会擦除代理尚未存储在任何地方的信息。

```
"compaction": { "mode": "safeguard", "memoryFlush": { "enabled": true } }
```

代理会在压缩运行前获得一个静默的时机，将持久化笔记写入到 memory/YYYY-MM-DD (.md)。尚未保存的上下文永远不会被静默丢弃。

MEMORY (.md)和其他工作区文件会在每次消息时被注入到你的代理的上下文中，而 OpenClaw 有一个引导预算（bootstrap budget），用于限制总共加载的工作区内容量。当文件超过该预算时，会使用 70/20/10 的分割方式进行截断：70%来自开头，20%来自结尾，中间部分被截断。聊天过程中不会有错误或警告提示，因此代理只会丢失臃肿文件中间的内容。

保持 MEMORY (.md) 精简，并将详细信息移至 memory/ 目录下的子文件中，供 agent 按需读取。将 MEMORY (.md) 视为一个索引而非数据库，在其中你只需指向内容，而非直接存储所有内容。

默认心跳目标是 "last"，即代理最近使用的任何通道。当你在多个通道上处于活跃状态时，这会导致问题，因为心跳会不可预测地跳动。

```
"heartbeat": { "target": "telegram" }
```

明确心跳消息的去向并将其锁定，而不是让其随意浮动。

你的机器人拥有管理员权限，但无法读取某些频道。这是因为 OpenClaw 的权限检查器没有正确考虑管理员权限覆盖与

修复方法：在机器人需要访问的每个频道上明确添加机器人角色权限。不要依赖管理员权限自动级联到所有内容。理论上应该这样工作，但 OpenClaw 目前尚未正确处理这一点。

这能发现随时间累积的细微故障，例如服务器漂移、分支不匹配和权限变更，在这些问题成为真正的问题之前将其全部暴露出来。

当出现问题时，首先检查 gateway.err.log。不是你的配置，不是你的代码，不是插件设置，只是错误日志。

每次我试图猜测哪里出了问题而不是仅仅查看日志时，我都会把问题弄得更糟。日志会准确告诉你发生了什么，所以永远从那里开始。

这直接关联到第23节中的截断问题，但它值得单独设立一节，因为大多数人对整个内存架构存在误解。

OpenClaw 的内存系统有两个官方层级。MEMORY（.md）是您用于存储决策、偏好及持久事实的精心整理的长期记忆，仅在私人（DM）会话中加载，绝不会在群组场景中加载，以保护敏感信息。memory/YYYY-MM-DD.md 文件是每日日志，采用仅追加且原始的形式，记录当天发生的所有事情，代理会在会话开始时读取当天的文件以及前一天的文件，以确保连续性。

那个两层系统是默认设置。但如果您运行任何复杂的东西，应该进一步拆分：

保持 memory/active-tasks (.md) 文件作为你的实时任务跟踪器，用于记录进行中的任务、待处理的任务和被阻塞的任务，基本上是你崩溃恢复的保存策略（更多内容见下文第 30 节）。使用 memory/projects (.md) 存储不会随日常变化而改变的项目特定背景信息，并使用 memory/lessons (.md) 捕捉代理随时间学到的模式和修正方法，以避免重复错误。

其原理是，你的代理在每次会话中都会以全新状态启动，而这些文件就是它的大脑。如果你把所有内容都塞进 MEMORY (.md)，就会触发 20K 字符限制，并且代理会加载当前任务不需要的上下文；但如果进行智能拆分，它只会加载相关内容。MEMORY (.md) 会变成一个指向详细文件的索引，代理会根据需求深入查看特定文件，而不是在每次会话中都携带整个历史记录。

内存搜索系统（由 memory-core 或 QMD 提供支持）通过语义和关键词搜索对 memory/下的所有内容进行索引。因此，即使代理在会话开始时不加载文件，当对话需要时，它也能找到该文件。

人们将这些互换使用，然后疑惑为什么他们的自动化要么浪费要么不可靠。它们的用途完全不同。

心跳在你的主会话中以固定间隔（默认每 30 分钟）运行，此时代理会唤醒，读取 HEARTBEAT(.md)，执行检查清单，然后判断是否有需要你注意的事项。如果没有需要注意的事项，它会发送静默的 HEARTBEAT\_OK 并再次进入休眠状态，不会产生通知干扰。心跳非常适合将多个周期性检查批量处理到一次代理轮次中，例如扫描收件箱、查看日历和查看待办任务，所有这些操作都在单个代理轮次中完成，并且保留完整的对话上下文。

Cron 作业按照精确的时间表在隔离的会话中运行，每个作业拥有自己的上下文、自己的模型（如果需要的话）以及自己的交付目标。由于它们在精确的时间触发，不管主会话在做什么，因此不会因为加载完整的对话历史而浪费 token。

规则：如果需要定期检查某事物且该事物得益于对话上下文，使用 heartbeat。如果需要在特定时间执行某操作且需要独立执行，使用 cron。

```
openclaw cron add \
  --name "Morning briefing" \
  --cron "0 7 * * *" \
  --session isolated \
  --message "Generate today's briefing: weather, calendar, top emails." \
  --model opus \
  --announce \
  --channel telegram
```

每日内容创意在6点，凌晨2点的隔夜研究探索，上午8点的技术监控，每个任务都在独立环境中运行，拥有各自的上下文。干净、可预测，且任务间无干扰。

社区注意点：如果 HEARTBEAT (.md)为空（或仅包含注释），使用 wakeMode: "now"的定时任务可能会被错误跳过。针对此问题存在已知漏洞及修复方法。如果你的定时任务显示为“空闲”且从未触发，请检查 HEARTBEAT (.md)是否至少包含一行非注释内容，或使用隔离会话目标完全绕过心跳运行器。

你的代理将会崩溃，网关将会重启，而当全天候运行时这是不可避免的，因此你需要一个能优雅处理这种情况的系统，而不是每次都从零开始。

模式很简单：在你的记忆目录中维护一个 active-tasks (.md)文件。

当你启动任务时，将其写入文件。当你生成子代理时，记录会话密钥。当任务完成时，更新状态；当任务失败时，记录错误原因。

在你的 Boot（.md）\[第 26 节\]中，添加一个在每次网关重启时读取 active-tasks（.md）的步骤。代理重新上线后读取该文件，查看正在进行的任务，并自主恢复。无需“我们刚才在做什么？”的对话，它从文件中自行判断并从上次中断处继续。

这与第 22 节中的压缩保护机制相配合。在任何上下文压缩之前，代理会将重要状态刷新到磁盘。在启动时的 Boot (.md)和长时间会话期间的压缩保护机制之间，两端均具备崩溃恢复能力。

如果你的代理读取任何外部内容，比如电子邮件、网页、推文或文章，这比你想象的更重要。

对于处理外部内容的任何任务，请使用您最强的模型（Opus）。因为较弱的模型更容易受到恶意网站和被操纵文本的提示注入攻击。在网页或电子邮件中的精心设计的注入可以改变较弱模型的行为，而较强的模型则更难被误导。

对于文件读取、提醒和本地工作区操作等内部任务，使用 Sonnet 或 Haiku 即可，因为内容是可信的（你可以控制这些内容）。但一旦你的代理从互联网获取内容或处理来自未知发件人的入站电子邮件，就将此类任务通过你最强大的模型进行处理。

这也是使用第 12 节中的按代理模型覆盖和第 29 节中的 cron 模型标志的一个很好理由，在这里你的内部操作代理可以低成本运行，而处理入站内容的面向外部的代理应该高成本运行。

每次 HEARTBEAT (.md)运行时，都会加载到代理的上下文中并消耗代币。默认间隔为 30 分钟，臃肿的心跳文件在一天内会累积成严重的成本。

保持在20行以内，仅使用一个简单的清单，涵盖以下内容：活跃任务的时效性、会话健康状态（归档臃肿会话）、每几小时进行一次自我检查，以及标记任何紧急事项。

工作内容就这些了。繁重的工作应该放在带有独立会话的 cron 任务中，而不是在心跳里处理。心跳的作用是察觉情况，而不是执行任务。如果它发现需要处理的问题，就会提醒你或者触发一个 cron 任务。它不应该每 30 分钟就生成报告、生成内容或运行复杂分析。

OpenClaw 文档直接指出：“保持 HEARTBEAT (.md) 小巧以最小化 token 开销。” 照字面意思理解并认真对待。

如果安装了多个技能，代理会根据每个技能 YAML 前置内容中的名称和描述来决定使用哪个技能。技能主体仅在代理决定触发该技能后才会加载。这意味着你的路由逻辑完全存在于描述字段中。

如果每个技能描述中没有明确的“使用时机”和“不使用时机”触发条件，智能体就会误触发并选错技能来完成任务。你会看到它在你需要编码技能时却抓取了研究技能，或者在你只需要状态检查时却触发了部署技能。

可以将其视为为你的代理的决策过程编写 if/else 逻辑。每个技能描述必须明确其触发条件：什么上下文会激活它、什么上下文不应该激活它，以及它会做什么和不会做什么。OpenClaw 技能文档强调了这一点：描述是主要的触发机制，所有“何时使用”的信息都必须放在描述中，而不是在技能本身里。

经过一周的全天候运行和调试上述所有内容后，这是实际上对我适用的模式（永远不要假设别人的配置会完美适用于你，首先要检查它，甚至可以咨询 OpenClaw）：

你构建一支专业代理团队，每个代理都有自己的 SOUL (.md)个性、工作空间和模型。其中一名代理（即你的 CEO 代理）通过 Telegram、Discord 或你使用的任何渠道处理所有外部沟通。团队中的其他成员（CTO、CMO、COO 或你需要的其他角色）负责内部工作，专注于各自的专业领域。团队中的任何代理都可以为后台工作生成子代理（否则这些工作会阻塞其主会话），这些子代理会完成原子任务并汇报结果。共享状态存储在符号链接文件中，确保所有人都从单一事实来源读取数据；上下文会自动清理，内存保持精简，

在每次重启时捕捉漂移，而错误日志是任何出错时你首先查看的地方。
