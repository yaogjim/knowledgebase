### **Droid 如何处理超长上下文窗口**

在一次长达七百万 Token 的编程会话中，用户能够持续工作而无需创建新的聊天窗口或丢失上下文，这背后是 Factory 团队对上下文管理问题的深度思考和独特架构。主持人 Ray 对此感到不可思议，他提到自己进行了一次长达七百万 Token 的会话，并在第二天的直播中再次进行了六百万 Token 的会话，全程都保持了上下文的连贯性。他直接向 Factory 的工程师 Luke Abollero 提问，想了解这背后“魔法般”的技术实现。

Luke Abollero 详细解释了 Factory 的上下文管理哲学。他指出，团队很早就开始深入研究上下文问题，并得出了一个核心结论：**必须将上下文视为一个在会话生命周期中需要持续解决的问题，并从迭代的角度来处理它**。Factory 的工程师 Theo 曾在一篇博客文章中阐述了这一理念，这种理念最终引导他们采取了一种独特的、以迭代为核心的方法。

具体来说，Factory 认为上下文会随着会话的进行而不断增长，当达到某个临界点时，必须对其进行压缩，使会话状态恢复到一个可管理的范围内。Luke 提到，根据他们的观察，大型语言模型（LLM）在 **140,000 Token** 左右的上下文窗口内表现最佳。因此，Droid 的核心目标就是确保会话始终保持在这个“最佳点”（sweet spot）附近，从而为用户提供最好的体验。

团队的探索过程并非一帆风顺。最初，他们尝试了一种 Luke 称之为“过度复杂”的方案。该方案涉及维护多个独立的文档：一个文档记录会话中已经完成的任务，另一个文档记录用户提供的初始需求和期望。这种多文档管理方式非常“笨重”（heavy-handed）。

然而，在过去六个月的实践以及在 Droid CLI 的开发中，他们发现从一个更简单的方法入手效果最好。这个简单的方法是：**一旦上下文达到 140k Token 的窗口上限，就先对所有内容进行一次全面的压缩**。他们会设计一个高质量的提示（prompt），将其提供给像 Sonic 4.5 这样的强大模型，观察压缩效果，并从中发现不足之处。这个过程自然会暴露很多陷阱，促使他们不断迭代和优化。

在针对 TerminalBench 这个基准测试进行优化时（Luke 强调不应完全为了基准而优化，但它确实能提供有价值的信号），他们通过分析大量的模型追踪记录发现了一个关键问题：每次压缩之后，模型都需要花费大量时间重新探索环境，比如重新浏览文件、通过 Git 命令回顾已做的更改等，这无疑降低了效率。这个发现让他们意识到，无论采用何种压缩方式，都有一些核心信息必须以其原始形式被保留下来。这些信息就像是给模型的“热线”，必须直接连接到最新的状态。

### **智能体指令（Agent.md）与持续性上下文管理**

在长时间的编程会话中，一个常见的痛点是 AI 智能体随着上下文窗口的增长，会逐渐“忘记”或忽略开发者预设的规则和指令，导致输出质量下降。主持人 Ray 分享了他的亲身经历，他习惯在代码仓库的不同文件夹中放置名为 `Agent.md` 的文件，用以向 AI 代理提供关键的背景信息和行为指南。例如，在他的后端文件夹中，`Agent.md` 文件会说明他正在使用 Convex 这个反应式数据库，其操作方式与常规数据库有所不同。他发现，在许多其他平台上，当上下文窗口变大后，AI 代理往往不再遵循这些 `Agent.md` 文件中的指示。然而，在他使用 Droid 进行的长达七百万 Token 的会话中，Droid 始终能够遵守这些规则，无需他反复提醒。

Luke Abollero 对此进行了解释，他强调，**上下文管理的责任主要在于智能体的构建者，而非模型本身**。当我们将上下文压缩成一两条消息发送给大语言模型时，如果天真地认为模型能自动理解所有关键信息，那是不现实的。因此，Droid 架构的核心之一就是确保在压缩过程中，最重要的信息能够被准确无误地呈现给模型。

Luke 进一步阐述了哪些信息是必须保留的。首先，他再次提到了“待办事项列表”（to-do list）。如果一个任务已经完成了 50%，模型在下一次交互时必须清楚地知道自己进行到了哪一步。其次，正如 Ray 所提到的，像 `Agent.md` 这样的指令文件，及其递归结构，必须被确保持久地加载到会话中。

最关键的一点是，从模型中提取和构建压缩后上下文的方式，应该模拟一个真实的人类开发者在交接工作时的沟通方式。Luke 用了一个生动的比喻来阐述这个观点：“如果我要把一堆工作交接给你，我不会只简单地说‘我正在处理这张工单，祝你好运’。我会告诉你这张工单的具体内容，提供复现问题的方法，或者指出新功能需要在 UI 或代码的哪个部分构建。我还会给你一系列的澄清说明，告诉你哪些文件可能需要修改，我过去遇到过哪些错误，以及我尝试过但失败了的方法。”

Droid 的上下文压缩管理系统正是围绕这一理念构建的。它会将所有这些关键信息——任务背景、技术栈说明、已尝试的路径、遇到的障碍、待办事项列表、`Agent.md` 文件中的规则——系统地整合起来。这样，当上下文被“交接”给下一次模型调用时，模型就能获得一个直观且完整的信息包，使其能够拥有成功执行任务所需的一切条件。这种精心设计的上下文交接方式，是 Droid 能够长时间保持一致性和准确性的核心秘诀。

### **“规程模式”（Spec Mode）与“计划模式”（Plan Mode）的深度解析**

在当前的 AI 编码工具中，“计划模式”（Plan Mode）已成为一个常见的功能，例如 Claude Code 和 Cursor 都引入了类似的概念。主持人 Ray 注意到 Droid 提供了一个名为“规程模式”（Spec Mode）的功能，他好奇这与其他的“计划模式”有何不同，是仅仅命名上的差异，还是背后有更深层次的设计理念。

Luke Abollero 承认两者之间存在相似之处，并称赞 Claude Code 的计划模式“能力非常强”（incredibly capable）。但他接着详细阐述了 Droid 的“规程模式”在理念上的根本区别。他解释说，其他工具的“计划模式”更多地是从智能体的视角出发，思考**“智能体下一步要做什么”**，它本质上是一个为了达成用户初始指令而制定的分步行动目标。

相比之下，Droid 的“规程模式”则是一个更宏大的概念，它被视为**“一个用于构建软件的整体性规程（holistic specification）”**。Luke 将其类比于传统的软件开发流程：从产品需求文档（PRD）阶段开始，到工程设计，再到最终构建原型。这个过程涉及多个阶段和需求。一个完整的软件规程需要思考以下几个核心问题：
*   **你究竟想构建什么？**（What you're actually trying to build）
*   **目标用户是谁？**（Who the target audience is）
*   **你将如何衡量成功？**（How you're going to measure success）
*   **你正在构建的产品或体验存在哪些潜在的陷阱？**（What are the pitfalls of this product or this experience）

“规程模式”的核心正是要捕捉到对一个功能的全面理解，并明确其成功标准。Luke 透露，这个模式已经成为 Factory 内部工程师的“日常驱动力”（daily driver）。他强烈建议 Droid 用户通过快捷键 `Shift + Tab` 直接进入规程模式来开始他们的会话，并认为这是目前使用 Factory 产品最成功的方式。

Luke 还提到，团队正在积极对“规程模式”进行优化。近期，一些内部工程师反馈说迭代规程的过程有点慢，这个问题立刻引起了整个团队的重视并迅速得到了修复，用户很快会体验到更快的规程迭代速度。

从智能体的角度来看，拥有一个清晰的规程也极大地帮助了它追踪自身进度。在每次上下文压缩后，这个规程都会被完整保留。无论是在线上评估还是基准测试中，团队都严格确保智能体能够高度尊重（very, very happily）规程模式中定义的内容。实践证明，只要用户在会话开始时与 Droid 合作迭代出一个高质量的规程，Droid 就能非常出色地执行它。Ray 补充说，他曾经在一个大型功能开发中，基于研究创建了一个长达 2000 行的庞大规程文档，这极大地推动了开发进程。Luke 也确认，用户可以通过 `/settings` 命令将规程保存为文件，以便后续修改和引用，这进一步增强了开发者与智能体之间的信任和协同工作的直观性。

### **从 Block 的 Goose 到 Factory：Luke 的智能体开发历程**

Luke Abollero 的职业生涯与开发者体验紧密相连，这为他在 Factory 开发 Droid 奠定了坚实的基础。他在分享自己的背景时提到，过去五年他一直专注于提升开发者体验。他的职业生涯始于 Square（Block 公司的前身），负责构建面向外部开发者的产品，如 API 和应用市场。随后，他转向内部开发者生产力工具的研发，加入了公司的开发工具团队。

正是在那个时期，GPT-3.5 模型横空出世，引发了技术浪潮。当时，几乎所有公司都在思考如何将大语言模型应用于开发者工具，打造公司专属的、经过微调的 GitHub Copilot 成为了一种潮流。在 Block 内部，Luke 所在的团队刚刚在全公司推广了 Copilot，他们思考的下一个问题是：如何让开发者更自然地在其工作流中使用这些模型？

Luke 的探索始于构建一些能为公司主要代码仓库自动生成测试的工具。最终，这个探索演变成了一个更宏大的项目：**围绕一个配备了工具的大语言模型（LLM）构建一个“while 循环”**。这便是 Goose 的雏形，诞生于大约两年前，甚至早于 Claude Code 和 Codex CLI 等知名工具。当时，开源社区中一个名为 Ader 的工具因其成功地对文件应用补丁（patches）而备受关注。Goose 借鉴了其中的一些经验，并最终发展成一个名为 Goose 的命令行工具。

Luke 与另一位名叫 Bradley Axon 的工程师共同开发 Goose。这个项目在 Block（Square 的母公司）内部获得了越来越多的关注和支持，团队规模也随之扩大。他们开始在全公司范围内推广 Goose，面临着如何让 **5,000 名工程师**接受并使用这个能从根本上改变开发者工作流的工具的挑战。这个过程并非一帆风顺，既有来自习惯传统编码方式的工程师的阻力，也充满了兴奋和期待。

团队的视野并未局限于开发者工具。他们开始思考如何将 Goose 在开发者社区取得的成功复制到公司的非开发者群体中。这个想法促使他们构想了一个更宏大的蓝图，这个蓝图与后来出现的 MCP（Multi-agent Collaboration Platform）服务器架构不谋而合。他们的设想是创建一个基于服务器的系统，允许任何人通过编写与特定用例（如 Sentry 或 Salesforce）相关的自定义工具来扩展任何兼容的智能体。然而，就在他们朝着这个方向努力时，MCP 正式发布了。Luke 回忆道：“我们当时就想，‘哇，这正是我们正在构建的东西’”。于是，他们调整了方向，重新聚焦于打造一个任何人都可以使用的开源产品，以及解决 Block 公司特定问题的内部工具。

这段经历让 Luke 深刻地认识到：**为了打造出优秀的产品，你必须亲身参与到智能体的构建过程中，才能理解那些决定产品好坏的微观决策**。这个核心信念最终引导他加入了 Factory。他坚信，与通用智能体（general purpose agents）相比，专注的智能体（focused agent）具有其局限性，但也因此更具优势。如今，**“智能体脚手架”（agent scaffolding）** 已成为构建智能体最关键的部分。专注于一个狭窄的问题领域，意味着你可以对这个脚手架进行更紧密、更快速的迭代。而在通用智能体中，脚手架必须能应对任何问题，这使得迭代变得更加困难和缓慢。

正是基于对开发者工具的热情和对构建最顶尖智能体的渴望，Luke 来到了 Factory。他的目标不仅是解决编码问题，而是要构建一个能够覆盖整个软件开发生命周期（SDLC）的智能体，因为他深知，无论某个环节做得多好，“用户总是会被你没有构建的部分所瓶颈”（Folks are going to be bottlenecked by whatever you don't build）。

### **技术揭秘（一）：锚点摘要（Anchored Summaries）与增量压缩机制**

Droid 能够支持长达数百万 Token 的会话而保持上下文连贯，其核心技术之一是独特的上下文压缩系统，Luke 将其称为基于“锚点摘要”（Anchored Summaries）的机制。这个系统旨在解决当会话历史变得过长，超出模型最佳处理范围时如何有效压缩信息的问题。

Luke 详细解释了这个过程的工作原理。在一个与大语言模型的对话流中，当消息历史的 Token 数量达到一个预设的阈值时，比如之前提到的 140,000 Token，系统就会认为当前会话超出了“最佳上下文限制”。触发这个阈值的最后一条消息就成为了一个**“锚点”（anchor point）**。

一旦一个锚点被确定，压缩过程便会启动。系统会执行以下操作：
1.  **定位锚点**：系统将触发阈值的消息标记为锚点。
2.  **压缩前期内容**：所有在该锚点消息**之前**的对话历史都会被提取出来。
3.  **智能摘要**：系统会调用一个大语言模型（LLM），将这些前期内容进行摘要。这个摘要过程并非简单的文本浓缩，而是结构化的信息提炼。它会精心设计提示（prompt），确保摘要中包含了关键信息，例如：
    *   **用户意图（intent）**：用户最初想要达成的目标是什么。
    *   **整体方法（overall approach）**：到目前为止，智能体采取了什么样的策略。
    *   **澄清问题（clarification questions）**：用户在对话中提出的关键问题和得到的解答。
    *   **持久化信息**：之前提到的“待办事项列表”（to-do list）和 `Agents.md` 文件中的规则等关键上下文信息也会被整合进摘要中。

这个过程解决了单次压缩的问题，但更精妙之处在于它如何处理多次压缩。当会话继续进行，比如在第一次压缩后又产生了 100 多条新消息，并再次达到了压缩阈值时，系统会如何处理？这时，第一次压缩时生成的“锚点消息”（它本身就是一个包含了丰富摘要信息的长消息）将扮演新的角色。

在第二次压缩时，系统会：
1.  **给予旧摘要高权重**：将上一个锚点消息（即第一次的摘要结果）作为输入的一部分，并在下一次的 LLM 摘要调用中给予它很高的权重。这确保了历史信息的精华得以传承。
2.  **整合新内容**：将第一次压缩点到第二次压缩点之间的所有新消息也纳入摘要范围。
3.  **再次提炼**：结合高权重的旧摘要和新的对话内容，生成一个全新的、更全面的摘要。同时，依然会确保“待办事项列表”、`Agents.md` 等关键信息在新的摘要中得到正确体现。

通过这种**“锚定-压缩-再锚定”**的迭代过程，Droid 实现了一种增量式的上下文管理。每一次压缩都是在前一次的基础上进行的，形成了一个信息层次不断递进的摘要链。Luke 坦言，团队曾经尝试过更复杂的系统，但最终发现，一个**“简单但经过深思熟虑”（simple but very well thought out）**的系统，并辅以所有必要的附加信息（addendums），是实现无 bug 且高效上下文管理的关键。这种简单而强大的机制，正是 Droid 上下文管理解决方案如此强大的原因。

### **技术揭秘（二）：智能体脚手架（Agent Scaffolding）的核心理念**

除了上下文压缩，另一个支撑 Droid 强大能力的核心概念是 Luke 反复强调的“智能体脚手架”（Agent Scaffolding）。他指出，如今人们在讨论 AI 智能体时，往往只关注提示工程或上下文管理，但这远非全貌。“智能体脚手架”是一个更全面的概念，它涵盖了构建一个可靠、高效的智能体所涉及的数百个行为配置和设计模式。

Luke 将“智能体脚手架”定义为一系列相互关联的组件和策略，这些共同决定了智能体的最终表现。他列举了其中的关键要素：
*   **系统通知（System Notifications）**：如何向用户或模型传达系统状态和警告。
*   **工具描述（Tool Descriptions）**：工具的描述是否清晰、准确，直接影响模型能否正确调用它们。
*   **工具实现（Tool Implementations）**：工具本身的实现质量，包括其健壮性和效率。例如，如何处理文件读写中的换行符问题，虽然看似微小，但在大规模会话中可能导致成千上万次失败。
*   **工具超时（Tool Timeouts）**：为不同工具设置合理的超时时间，以确保产品感觉“非常快”（really, really snappy）。
*   **模型响应等待时间**：决定等待 LLM 响应多长时间。
*   **提示缓存（Prompt Caching）**：如何设计消息历史结构以最大化缓存命中率，从而提升速度。
*   **模型无关的适配层（Model Agnostic Harness）**：一个能够与任何插入的模型良好协作的框架。

Luke 特别强调了**为不同模型构建特定脚手架**的重要性。在过去六个月里，Factory 的一个重要成就是围绕多种模型进行构建，而不是试图用一套完全通用的方案来适应所有模型。他举了一个具体的例子：OpenAI 风格的模型在编辑和创建文件时，偏好使用一种名为 `Apply Patch` 的专有工具，该工具通过应用差异（diff）来修改文件。而 Anthropic 风格的模型则更倾向于使用一种基于文本查找和替换的工具，类似于 Git diff 格式。如果只是简单地将一个新模型接入系统，而不为其提供定制化的工具集，其性能将会“显著下降”（significantly degraded performance）。因此，为每个模型构建特定的工具和调用方式，是“脚手架做对了”（scaffolding done right）的典范。

Luke 提出了一个核心观点：**“智能体的好坏取决于其最薄弱的环节”（Agents are really as good as their weakest link）**。要想提升智能体的质量，就必须尽可能减少其走向负面轨迹的可能性。在实践中，这意味着要**极度专注于修复 bug**。这包括：
*   **文件编辑问题**：如前面提到的换行符问题。
*   **引导机制（Nudge Mechanisms）**：当 IDE 诊断出问题或出现 lint 警告时，如何巧妙地提醒模型进行修复。
*   **后台进程**：正确使用后台进程，例如，当智能体启动一个服务器时，不应阻塞整个智能体循环，而应能够继续执行其他任务。

最后，Luke 谈到了提示缓存和消息历史结构。他指出，Factory CLI 工具之所以速度更快，一个重要原因是它采用了更优的提示缓存策略。其核心是**将消息历史设计为“仅追加”（append only）模式**。这种线性的、不可变的历史结构可以确保缓存永远不会中断，从而使会话运行得更快。他认为，那些试图通过动态插入和删除消息来操纵上下文的“更高级”方法，实际上可能会“搬起石头砸自己的脚”（shooting yourself in the foot），因为这种做法会在不经意间迷惑模型。

### **技术揭忌（三）：并行化（Parallelization）的挑战与未来方向**

并行化是提升 AI 编码智能体效率和能力的关键，也是当前领域内所有工具（包括 Droid）尚未完全解决的一大挑战。Luke 深入探讨了并行化的复杂性，并将其分解为不同层次，指出了未来的发展方向。

他首先提到了业界其他产品的尝试，例如 Claude Code 推出的子智能体（sub-agent）解决方案。这种方法的逻辑是：主模型调用一个子智能体去完成一项特定任务，子智能体在执行过程中会产生大量的对话和中间步骤，但最终它只会返回一个结构化的输出，总结其所有工作和发现。这个最终的摘要被交还给主模型。通过这种方式，一个冗长的对话线程被压缩成一个简洁的最终结果，从而节省了主会话的上下文空间。

然而，Luke 认为这种方法虽然有价值，但当前的工具对“并行化”的理解还不够深入。他将软件工程任务中的并行化分解为三种不同的类型：

1.  **任务间并行化（Inter-task Parallelization）**：这指的是同时处理多个独立任务的能力。Luke 将每个任务比作一个“线性工单”（linear ticket）。实现任务间并行化意味着智能体可以同时在五个不同的工单上取得进展，而不会因为某个环节（无论是编码还是代码审查）而被完全阻塞。

2.  **任务内并行化（Intra-task Parallelization）**：这指的是在**单个任务内部**实现并行处理。子智能体是实现这一点的一种方式。但还存在其他可能性，例如：
    *   **“N选最佳”（Best of N）方法**：同时启动多个 Droid 实例，让它们在不同的 Git 工作树（work trees）上分别尝试解决同一个问题，最后选择最可行的那个方案。
    *   **协作智能体**：让多个智能体在同一个代码分支上协同工作，它们可能共享一个参考文档作为工作状态的同步点。这种方式面临的挑战是如何让每个智能体都清楚地知道在整个大型会话中已经完成了哪些工作。

3.  **大任务分解（Large Task Decomposition）**：这涉及到将一个庞大而复杂的任务分解成多个子任务，是上述两种并行化方法的混合体。

Luke 认为，**并行化是未来六个月内编码工具需要解决的“大问题”（the big problem）**。目前，开发者工作流中一个巨大的瓶颈是代码审查（review）。上述提到的不同类型的并行化问题，都需要截然不同的解决方案。Factory 作为一家深度思考 AI 编码和软件开发生命周期的公司，其角色是让所有这些复杂的并行化操作对开发者来说变得“非常直观”（very intuitive）。

他观察到，尽管很多人在思考如何实现并行化，但这通常需要耗费大量的“脑力带宽”（mental bandwidth），并且现有的工具在一定程度上限制了开发者尝试不同方法的可能性。因此，他个人非常期待看到 Droid 在这方面持续改进，并明确表示这是 Factory 公司未来六个月的重点发展方向。

### **社区问答：深入探讨技术实现与最佳实践**

在直播的互动环节，社区成员提出了一系列技术性很强的问题，Luke 针对这些问题给出了深入的解答，进一步揭示了 Droid 的设计哲学和技术细节。

**GraphRAG 与语义摘要的比较**
一位名叫 Human Jesse 的观众询问 Luke 对 GraphRAG（图形检索增强生成）与语义摘要（semantic summary）在压缩上下文方面的看法。Luke 回答说，他的核心方法论是**“从最简单的解决方案开始，并对其进行衡量”（start with the simplest solution and measure it）**。他坦言，过去团队曾尝试在没有经过这两个重要初始步骤的情况下解决问题，结果导致无法准确评估哪个方案才是应该优化的起点。虽然团队在产品的不同阶段都使用过这两种方法，并且认为 RAG 仍然是一个非常有用的工具，但随着他们越来越重视提示缓存，RAG 的适用场景在某种程度上有所减少。他认为，当前模型已经非常擅长主动进行研究，只要在初始规程文件中提供了正确的上下文和信息来源（这本身就是 RAG 的一个极佳用例），就应该让模型自己去调查，并最大化利用提示缓存。关键在于让模型在会话中的运行方式与其预训练后的工作方式高度重叠，这样才能获得最大的成功几率。

**规程模式的 Token 消耗问题**
有用户反馈，在规程模式（Spec Mode）中进行规划会消耗大量 Token。Luke 承认这是一个亟待解决的问题，无论是在成本还是速度方面，当前的体验都还有提升空间。他透露了一个即将上线的重大更新：团队正计划在本周内推出一个新功能，**将规程的迭代过程转变为在本地文件系统上进行**。目前消耗 Token 的主要原因是每次迭代规程时，系统都会从头开始重写整个规程。新方案将允许 Droid 使用文件编辑和应用补丁（apply patch）的技术来修改规程文件，这将大大提高 Token 的使用效率。

**何时应该清除上下文或开启新会话**
MIT Games 提问，应该多久清理一次 Droid 的上下文，以及在同一个代码库中处理新任务时是否应该开启新的对话。Luke 认为这是一个非常好的问题，他自己也在反思自己的工作流。他个人倾向于使用长时间的会话，因为 Droid 强大的压缩系统让他无需像以前那样频繁地预加载上下文。他对此非常有信心，相信压缩系统能将 Token 数量维持在最佳范围内，同时保留正确的计划。他给出的决策框架是：
*   **如果你正在处理同一个相关联的任务，完全可以安全地在同一个会话中继续工作**，甚至可能从中受益。
*   **一旦你切换到另一个不相关的任务时**（即他之前提到的“任务间并行化”），他建议**开启一个新的会话**。这样做可以确保新任务的上下文不会被旧任务的信息所“污染”（unpolluted），同时你仍然可以随时返回之前的会话，比如当你发现 Droid 犯了一个小错误时，可以回去提供反馈并进行修正。

**Droid SDK 的发布计划**
有观众询问 Droid SDK 的发布时间以及是否有 IntelliJ 等 IDE 的插件计划。Luke 解释说，SDK 通常意味着一个 API SDK，而 Droid 是一个在本地机器上运行的进程，这与传统的 API 不同。尽管如此，团队正在积极考虑 Droid SDK。他建议，目前想要在 Droid 之上进行构建的用户可以使用 `droid exec` 命令。只需输入 `droid exec` 后跟上你的查询或提示，Droid 就会以无头（headless）模式开始执行任务。这是当前并行运行一个或多个 Droid 实例的方式。他确认 Droid SDK 正在开发中，并且已在内部使用，但团队希望在公开发布前确保其 API 足够稳定，以免给早期使用者带来麻烦。

### **Factory 的商业模式与未来展望**

面对关于公司可持续性的问题，例如 Factory 是否在“烧钱”，以及用户是否需要担心公司未来会消失，Luke Abollero 给予了明确且令人安心的回答。他首先简短有力地表示：“我们不会消失”（we're not going to be disappearing）。他透露，**Factory 在几个月前刚刚完成了一轮 B 轮融资**，这笔资金将确保公司能够长期运营。

接着，他详细阐述了 Factory 的商业哲学和业务模式。Factory 本质上是一个**“企业优先”（enterprise first）**的工具。公司的 Web 应用在过去两年多的时间里，一直在为大型企业的 AI 软件开发生命周期之旅提供支持。这种稳定的企业业务为公司提供了可持续的收入来源，使其能够同时支持那些在业余时间或工作中独立使用 Droid 的个人开发者，即便他们没有通过企业协议购买服务。

Luke 强调，公司绝不会“抽地毯”（rug pulling），即突然放弃对个人用户的支持。他做出了两个重要承诺：
1.  **BYOK 模式将永远存在**：Droid 工具将始终提供“自带密钥”（Bring Your Own Key）的模式，用户可以一直使用自己的 API 密钥来运行 Droid，而无需付费订阅。
2.  **持续集成最佳模型**：团队会持续跟进业界最先进的模型。目前是 OpenAI 和 Anthropic，如果未来有新的竞争者推出同样强大的模型，Factory 会迅速跟进，为新模型构建合适的脚手架，并确保用户可以通过 BYOK 模式使用它。

此外，他也指出，即使对于独立开发者，Factory 的定价模型也“非常好”（really, really good）。其核心优势在于将所有顶尖模型整合到一个套餐中。用户无需分别为 Anthropic 和 OpenAI 购买最高级别的订阅计划，只需订阅 Factory 的一个计划，就可以在一个地方灵活切换使用所有这些模型，享受它们的全部优势。

最后，Luke 表达了对未来的兴奋之情。他认为这个领域还有很多工作要做，并对未来六个月到一年的发展充满期待。这种以企业业务为基础，同时积极拥抱个人开发者社区的混合模式，为 Factory 的长期发展提供了坚实的保障。

### **智能体的十年：对软件开发未来的预测**

当被问及对未来的看法时，Luke Abollero 描绘了一幅由 AI 智能体深刻改变软件开发领域的蓝图。他同意 Andrej Karpathy 的观点，即我们正处在一个“智能体的十年”（decade of agents）的开端，并分享了他作为一线实践者对未来趋势的几点预测。

首先，他认为**迭代和优化“智能体脚手架”是当前最具价值的工作**。Factory 之所以敢于公开分享其工作原理（例如通过博客文章解释上下文压缩），是因为他们相信真正的护城河不在于某个具体的实现细节。当其他人花时间追赶并实现当前的技术时，Factory 团队已经在解决下一代的脚手架问题，从而不断提升产品力。

其次，他预测未来 AI 工具的产出将发生质变。它们将不再仅仅是一个“氛围编码器”（VibeCoder），即需要开发者不断引导才能产出符合规范的代码。相反，**AI 工具的输出将越来越像一个成熟的软件组织**。这意味着 AI 会主动意识到代码库的结构，并在结构缺失时引导开发者建立起来。诸如代码规范检查（linting）、端到端测试、单元测试和持续集成/持续部署（CI/CD）等最佳实践，将被无缝集成到开发流程中，即使对于小型项目也是如此。这将使所有开发者，无论经验深浅，都能直观地学习和应用这些行业标准。

第三，他预见**单体仓库（Monorepos）将变得更加普遍**。随着 AI 智能体越来越多地参与代码编写，确保 CI（持续集成）能够“全绿通过”（go green altogether）变得前所未有的重要。单体仓库能够保证当一个智能体做出修改时，所有相关的部分都能被一同测试，从而确保整个系统的协同工作。相比之下，在多个分散的仓库中协调和验证变更要困难得多。

第四，**传统意义上的“迁移”（migrations）概念将会改变**。Luke 以 Cursor 最近发布的 2.0 版本为例，他们没有在旧版本上进行渐进式迁移，而是几乎重构了整个应用。他透露 Factory 内部也正在用类似的方式重构其 Web 应用，以匹配 CLI 工具的强大能力。借助 Droid，**一个原本需要一年时间的工作量，现在可以在三周内完成**。未来，当需要进行重大架构升级时，开发者可能会选择用 AI 工具快速从零开始构建一个新版本，而不是在旧有代码上进行繁琐的迁移。这种“原型即产品”的模式将成为新的常态。

最后，他强调了**成本效益和自托管模型的重要性**。虽然当前最前沿的模型（如 Claude Opus 或 Sonnet）已经非常强大，能够处理 3-4 小时复杂度的任务，但他认为，除了追求更强的能力外，提供更有竞争力的价格和更好的上下文管理也同样关键。他对此感到非常兴奋，并认为**能够在本地机器上运行的开源、开放权重模型，是模型领域的“下一个前沿”（the next frontier）**，这将大大降低使用 AI 智能体的成本，从而推动其更广泛的应用。

### **给初级开发者的建议：在 AI 时代如何成长**

在直播的最后，针对许多年轻开发者和在校学生对 AI 未来可能带来的职业冲击感到的焦虑和恐惧，Luke Abollero 给出了一段充满鼓励和智慧的建议。

首先，他澄清了 Factory 团队的初衷。他强调：“我们不是在构建会取代你的工具，我们是在构建能让你更具生产力的工具”（We're not building tools that will replace you. We're building tools that will make you more productive）。他希望大家在使用这些工具或听到网络上的负面言论时，能记住工具构建者的目标是赋能而非替代。

对于那些在求职路上遇到困难的初级开发者，他分享了贯穿自己整个职业生涯的一个重要经验：**找到一个你真正充满激情去解决的问题**。他承认，面试过程可能会充满挫折和拒绝，这总是很难熬的。但如果你能找到一件你每天都热爱去做的事情——无论是在工作中，还是在没有工作的情况下——那将是你成长最快的地方。当你对一个问题怀有如此深厚的热情时，你会日夜思考它，不断地进行迭代和探索。

他鼓励处于职业生涯早期的年轻人，去寻找那个能让你“夜不能寐”（keeps you awake）的问题领域，并在业余时间积极地去研究和实践它。他相信，只要你坚持下去，最终一定会在世界上找到同样热爱这个问题的人。他用 Factory 两位创始人的相遇来比喻这种状态，称之为“一见钟情般的思想碰撞”（intellectual love at first sight）。

Luke 的核心信息是，**通过对一个问题日复一日、夜复一夜的深度思考和反复实践，你会逐渐建立起该领域的专业知识（domain expertise）**。这种专业知识会像磁铁一样，自然而然地吸引来机会和志同道合的人。当你与同样 passionate 的人交流时，这种由长期积累而来的深度理解会让你立刻产生共鸣，从而打开职业发展的大门。

他认为，在困境中“碰壁”（hitting your head against the wall）是工程师成长周期中不可或缺的一部分。正是通过不断面对和解决这些难题，开发者才能积累经验，建立起对细节的关注，并最终能够胜任处理数十亿人使用的软件的重任。这种由激情驱动的、持之以恒的努力，是任何时代下个人成长的根本动力。
