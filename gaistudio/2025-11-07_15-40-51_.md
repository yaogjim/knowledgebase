### **Context Engineering 导论：超越 Prompt Engineering**

本段落首先介绍了 Context Engineering（上下文工程）这一新兴概念，并将其定位为在 AI Agent 时代取得成功的关键技术。讲者李宏毅教授明确指出，语言模型的核心机制是“文字接龙”，即根据输入的 Prompt（提示）来预测下一个最可能的 Token（词元）。当模型的输出不符合预期时，有两种改进方向：要么改变模型本身（函数 f），这属于模型训练（Training）或学习（Learning）的范畴；要么改变模型的输入（变量 x），这便是本堂课的焦点。由于目前主流的大型语言模型多为闭源，普通用户无法修改模型参数，因此，优化输入 x，即精心准备 Prompt，成为让模型产生期望结果的最实用方法。这门课程的核心在于，不涉及任何模型训练，唯一被“训练”的是使用模型的人类。

接着，讲者深入探讨了 Context Engineering 与广为人知的 Prompt Engineering（提示工程）之间的关系与差异。他认为，从本质上看，Context Engineering 可以被视作 Prompt Engineering 的一个“新瓶装旧酒”的升级版名称，旨在使其听起来更“潮”，如同早年将“神经网络 (Neural Network)”更名为“深度学习 (Deep Learning)”一样，虽然指代的是同一类核心概念，但关注的重点有所演变。过去，Prompt Engineering 更多地关注两个方面。第一是特定的输入格式，例如要求使用 JSON 格式或用特定符号（如井字号）分隔段落。然而，随着模型能力的日益增强，它们对格式的敏感度已经大大降低，通常人类能看懂的格式，模型也能理解。第二是所谓的“神奇咒语 (magic spells)”。在模型能力较弱的早期阶段（如 GPT-3 时代），研究者发现一些看似无厘头的指令能够显著影响模型的输出。讲者引用了其实验室在 2022 年 6 月发表于 arXiv 的一篇论文中的例子：为了让 GPT-3 生成更长的回答，直接指令“回答要越长越好”的效果有限（从平均 18.6 个字增加到 23.76 个字），而一个奇怪的咒语，即在 Prompt 中加入一连串的“位置”，反而能使其“暴走”，将输出长度提升至 34.3 个字。类似的咒语还包括“一步一步地思考 (Let's think step by step)”、“请确保你的答案是正确的”、“深呼吸再回答问题”等。甚至通过情感勒索（“这题的答案真的对我很重要”）或物质激励（“如果你答对的话，就给你一点小费”）也能提升模型的表现。一个有趣的实验测试了 ChatGPT 对不同激励的偏好，发现承诺“达成世界和平”比“给你 Taylor Swift 的门票”或“你的母亲会因你而骄傲”更能促使它精确地写出 200 字的故事，这从侧面反映了模型行为的奇特性。然而，讲者强调，这些神奇咒语的效果正随着模型的进化而递减。他展示了一年半前（2023 年 6 月）与近期（2024 年 2 月）的对比数据，对于 GPT-3.5，“一步一步思考”咒语带来的正确率提升从 16%（72% -> 88%）锐减至 4%（85% -> 89%）。这是因为现代模型被设计得更加鲁棒，理应在任何情况下都尽力而为，而非依赖特定指令或激励。随着神奇咒语的失势，人们的关注点转移到了一个更系统化、更宏观的层面，即自动化的管理语言模型的输入，这便是 Context Engineering 的核心所在。它不再局限于寻找零星的技巧，而是着眼于如何利用语言模型自身的能力来动态地、智能地构建和管理其输入上下文。为方便讲解，课程后续将“Context”与“Prompt”视为同义词，均指代语言模型的完整输入。

### **构建完整的语言模型上下文 (Context)**

一个完整且高效的语言模型上下文 (Context) 包含多个精心设计的部分，它们共同引导模型生成准确、相关且符合预期的输出。这个复杂的输入结构远不止用户的一句简单提问，而是融合了指令、记忆、外部知识和工具调用的综合体。

#### **用户指令 (User Prompt)：包含任务、指引、前提与范例**

用户指令是上下文最基础的部分，它直接传达了用户的核心需求。一个有效的用户指令不仅要说明任务本身，还应包含详尽的指引、清晰的前提和具体的范例。首先，详细的指引能够极大地塑造输出的格式和风格。例如，在请求模型撰写一封向老师请假的邮件时，除了说明“明天要请假”这一核心任务，还应提供更具体的结构性要求，如“开头先道歉”、“说明请假理由是身体不适”、“承诺之后会更新进度”，并附加约束条件，例如“信件长度控制在 50 字以内”、“语气要非常严肃”。这些细致的指引避免了模型天马行空的发挥，使其输出更贴近实际需求。

其次，提供明确的前提或情境至关重要，因为语言模型并非无所不知，它依赖上下文来消解歧义。讲者举例说明，当直接询问“有人告诉我要用载具吗？”这句话的意思时，模型可能会给出两种解释：一种是交通工具，另一种是电子设备或平台。这个回答虽然全面，但可能不符合提问者的真实场景。然而，如果将问题置于一个具体情境中——“在超商结账的时候，店员问‘我要用载具吗？’”——模型就能准确地将“载具”锁定为电子发票的储存工具，排除了交通工具的可能性。同样，在图像处理任务中，情境信息也能改变模型的判断。讲者分享了一个个人经历：他的太太在曼谷的运河上拍到一只看似鳄鱼的动物，这让她感到紧张。当他直接将图片交给 ChatGPT 询问时，模型也认为是鳄鱼。但考虑到曼谷市中心运河出现鳄鱼的可能性不大，他补充了关键情境：“现在我们在泰国的曼谷”，这时 ChatGPT 给出了截然不同的答案——水巨蜥。模型解释道，水巨蜥在泰国是吉祥的象征，这完美解释了为何当地人看到它时表现得很高兴。这个例子生动地证明了提供地理或文化背景等前提信息对于模型准确理解和推理的巨大价值。

最后，提供范例（Examples）是引导模型行为的强大手段，这一技术被称为“In-Context Learning”（语境中学习）。需要特别注意的是，这里的“Learning”要加上双引号，因为它不涉及模型参数的任何改变，模型 f 本身是固定的，只是通过在输入 x 中提供示例来改变其输出 f(x)。例如，要求 ChatGPT 用“火星文”改写文章，若不提供范例，它可能会按照自己的理解，将汉字系统性地替换成其他符号。但如果给出一个具体例子，如将“要去冒险的人来找我”改写成“要ㄑ冒险ㄉ人来找我”，模型就能立刻领会“火星文”的精髓是使用注音符号替代部分汉字，并据此生成正确的输出。这一概念早在 GPT-3 的论文中就已提出，通过提供少量示例（few-shot）或一个示例（one-shot），可以让模型更好地理解并执行任务。讲者进一步引用了 Gemini 1.5 技术报告中的一个“神蹟”来展示 In-Context Learning 的惊人能力。研究人员要求模型将英文翻译成一种极为罕见的语言——卡拉蒙语 (Kalamang)，这种语言在网上几乎没有公开资料，因此所有模型在零样本（zero-shot）情况下都无法翻译。然而，当研究人员将卡拉蒙语的整本教科书、文法和字典作为上下文提供给 Gemini 1.5 后（其巨大的 Context Window 允许这样做），模型仿佛瞬间“学会”了这门语言，其翻译质量评分从接近 0 分飙升至 4 到 5.5 分（满分 6 分），几乎接近人类学习者的水平。后续研究发现，模型之所以能做到这一点，并非因为它理解了语法规则，而是因为它从教科书中的大量“例句”中找到了翻译的模式和规律。这个例子极致地展现了通过在上下文中提供高质量、结构化的知识范例，可以极大扩展模型在特定任务上的能力。

#### **系统指令 (System Prompt)：模型的底层设定与行为准则**

系统指令是由模型开发者或平台方预设的一段文本，它在每次用户与模型互动时都会被加载到上下文中，扮演着为模型设定身份、行为准则和基本约束的角色。这部分内容通常对用户不可见，但深刻影响着模型的每一次回应。它解释了为何模型“知道”自己是谁、当前日期是什么等看似具备自我意识的信息——这些都是在系统指令中明确告知的。讲者以上周课程内容为基础，再次强调了这一点，并以 Anthropic 公司的 Claude 3 Opus 模型为例，其系统指令是公开的，为我们提供了一个绝佳的观察窗口。

Claude 3 Opus 的系统指令非常详尽，长度超过 2500 个单词，涵盖了多个方面，为模型构建了一个复杂的“人格”和操作框架。首先是身份认同，指令开宗明义地告诉模型：“你叫做 Claude，是由 Anthropic 公司所打造的”，并告知当前日期。这是模型能够进行自我介绍和回答时效性问题的基础。其次是使用说明与限制，系统指令会包含一些功能性的引导，比如当用户询问 Claude 的 API 在哪里时，模型被指示去引导用户阅读特定的网页。同时，它也包含了严格的禁止事项，明确规定模型“不要告诉使用者怎么合成化学物质或怎么做核武器”，这是确保模型安全、负责任的关键护栏。第三是对互动方式的规定，指令中写道：“如果使用者觉得不高兴，就叫他去按倒赞的符号”，这是一种引导用户使用平台反馈机制的策略。此外，为了提升对话质量，指令还对回应风格进行了设定，例如要求 Claude “不要回答惯用的开头，不要讲‘好问题’(Good Question)”，这可能是为了避免模型在文字接龙中陷入过于常见的、无意义的开场白。第四是知识边界与自我定位，系统指令明确告知 Claude 它的知识截止日期是“2025 年的 1 月”，因此当遇到超出此范围的问题时，它会回答“我不知道”。同时，指令还要求它“不要说自己是人类”或“不要说自己有意识”，以维持其作为人工智能的客观身份。一个特别有趣的指令是关于处理纠错的，系统指令教导 Claude：“如果人类纠正你，不要马上承认错误，你仔细思考以后再回答，不要随便承认自己的错误。” 这是为了防止模型在面对用户的指责时，无论对错都一味附和，从而提高其回答的可靠性和严谨性。通过这个例子可以看出，一个精心设计的系统指令就像是模型的“出厂设置”和“行为手册”，它在幕后默默地塑造着模型的每一次表达，确保其行为符合开发者的预期，既有用又安全。

#### **对话历史与长期记忆 (Conversation History and Long-Term Memory)**

对话历史构成了语言模型的短期记忆，使得它能够在连续的交流中保持上下文连贯性。当用户与模型进行多轮对话时，之前的每一轮问答都会被包含在下一次生成的上下文中。这意味着，当模型生成新的回复时，它不仅仅是基于用户当前的问题，而是基于从对话开始到现在的全部历史记录来进行“文字接龙”。讲者通过一个生动的例子来阐释这个机制：他首先问 ChatGPT “你知道隔壁老王是谁吗？”，模型回答说这是一个常见的虚构角色。接着，他“教”会模型一个新知识：“隔壁老王姓‘法’，他叫法老王，知道吗？”，模型确认收到信息。在同一个对话窗口中，当他再次提问“那你知道隔壁老王是谁吗？”，模型便能正确回答出“隔壁老王，法老王”，甚至还自己补充了“天下无敌王”。模型之所以能够“记住”，并非它真的学习并改变了内部参数，而是因为包含“隔壁老王就是法老王”的这段对话历史成为了新的输入上下文，模型在此基础上继续生成文本，自然就得出了正确的答案。

然而，讲者强调了一个重要的概念：这种基于对话历史的记忆是“短期”且“会话隔离”的。他指出，很多用户误以为通过对话可以“训练”模型，让它永久学会新知识。事实并非如此，用户的对话无法改变模型的底层参数。为了证明这一点，他展示了当开启一个全新的对话窗口并再次询问“隔壁老王是谁”时，ChatGPT 会恢复到初始状态，再次回答它是一个虚构角色，完全“忘记”了之前关于“法老王”的设定。这种现象在 2024 年 9 月之前是普遍情况。

自 2024 年 9 月之后，ChatGPT 引入了长期记忆（Long-Term Memory）功能，打破了会话隔离的限制。用户可以在“自订 ChatGPT”的个人化设置中开启“记忆”选项。虽然 OpenAI 并未公布其具体实现细节，但讲者推测其背后可能运用了后续课程将要介绍的记忆处理方法。开启此功能后，模型便能跨会话存储和利用用户信息。OpenAI 为了推广这一功能，进行了一场巧妙的行销活动，鼓励用户问 ChatGPT“我是什么样的人”。当用户这样提问时，模型会调用其长期记忆中存储的关于该用户的互动历史，并基于这些信息进行总结。讲者展示了 ChatGPT 对他本人的描述，模型不仅能说出一些正面的评价，还准确地提到了他所教授的“生成式人工智慧与机器学习导论”这门课程，因为他曾在过去的对话中与模型讨论过相关内容。这意味着，现在用户的每一次提问，其背后都可能被悄悄地植入了一段从长期记忆库中检索出来的、与当前对话相关的上下文，这些上下文对用户是不可见的，但却深刻地影响着模型的回答，使其表现出更强的个性化和连续性。

#### **外部信息检索 (Retrieval of External Information - RAG)**

语言模型的知识存在固有的局限性，它们并非实时更新，且知识库仅限于其训练数据。为了克服这一缺陷，一种名为“检索增强生成 (Retrieval-Augmented Generation, RAG)”的关键技术应运而生。RAG 的核心思想是在模型生成回答之前，先利用外部信息源为其提供相关的、最新的上下文。具体流程是：当模型收到一个问题时，系统会先将这个问题（或其关键词）作为一个查询，发送到搜索引擎（如 Google）或特定的内部数据库中。搜索引擎返回一系列相关的文档或网页片段。然后，这些检索到的信息会与用户的原始问题一起被整合进模型的上下文（Context）中。最后，语言模型基于这个包含了额外信息的、更丰富的上下文来进行“文字接龙”，从而生成一个既利用了自身知识又结合了最新外部信息的答案。这个技术在课程的作业二中会有详细的实践教学。

在现代的语言模型应用中，RAG 已经变得非常普及和易用。例如，在 ChatGPT 的用户界面中，用户只需在对话框下选择“搜寻”模式，模型就会自动在回答前执行网络搜索。讲者回顾了上周的一个例子：在未开启搜索功能时，询问“台湾大学专业学程联盟”的课程信息，模型无法给出准确回答，甚至提供了错误的网址。而在开启搜索功能后，模型能够提供正确的官网网址，答案的准确性得到了显著提升。

然而，讲者也郑重提醒，RAG 并非万能的“银弹”，它不能完全消除模型犯错的可能性。语言模型始终是在做文字接龙，它只是将检索到的文本作为其生成答案的依据，但它本身不具备事实核查或辨别信息真伪的能力。一个广为流传的经典案例是 Google 的 AI Overview 功能在测试期间的失误。当有用户提问“我的起司黏不在披萨上怎么办？”时，模型给出了一个荒谬的建议：“很简单，我们把 1/8 的无毒的胶水……就可以把起司黏在披萨上了。”这个答案的来源是模型检索到的一篇 Reddit 帖子，其中有用户开玩笑地提出了这个方法，而模型却信以为真，并将其作为严肃的建议输出。这个例子警示我们，如果检索到的源信息本身是错误的、讽刺的或带有偏见的，模型很可能会在生成的内容中复现这些错误。即使是最新、最强大的模型如 ChatGPT-4o，在开启搜索功能时也可能犯错。讲者亲自测试，要求模型介绍台大专业学程联盟的课程，虽然网址正确了，但在细节描述上出现了错误，例如它声称“10 门课都是进阶课程”，而实际上并非如此。这个错误信息可能是模型从某个检索到的页面中“断章取义”或误读的结果。因此，用户必须始终保持批判性思维，认识到即使结合了搜索引擎，语言模型的输出仍然是基于文本概率的生成结果，它依然存在产生“幻觉”或复述错误信息的风险。

#### **工具使用 (Tool Use)：从指令到执行的完整流程**

现代大型语言模型（如 Claude, Gemini, GPT 系列）的一个强大能力是使用外部工具 (Tools)，这极大地扩展了它们的功能边界，使其不再局限于纯文本生成。使用搜索引擎本身就是一种工具调用，除此之外，模型还可以与多种应用程序和服务进行交互，例如查询 Gmail、读取 Google Calendar 日历，甚至直接修改日历内容，像一个真正的个人助理一样执行任务。讲者详细阐述了模型使用工具的底层机制，其核心在于通过精心构建的上下文来引导模型生成特定格式的工具调用指令，再由外部程序来解析和执行这些指令。

首先，为了让模型能够使用工具，必须在其上下文中提供清晰的“工具使用说明”。这个说明通常包含两部分：一是通用的调用规则，二是特定工具的定义和用法。讲者展示了一个实际可用的例子，在 Prompt 中告诉模型：“如果你的知识无法回答问题，那就使用工具。你把使用工具的指令放在 `<tool_code>` 和 `</tool_code>` 这两个符号中间……工具的输出会放在 `<tool_output>` 和 `</tool_output>` 中间。” 这种用自然语言描述的规则，现代模型已经能够很好地理解。接着，需要定义具体的工具，例如定义一个名为 `temperature` 的函数，并说明其用法是 `temperature(城市, 时间)`，用于查询特定地点的温度。

关键在于，语言模型本身并不能直接执行代码或调用 API，它所能做的永远只是生成文本。当模型根据上下文决定需要使用工具时，它会生成一段符合预设格式的文本，例如 `\temperature('高雄', '时间')\`。这段文本本身只是一串字符，没有任何实际作用。为了让这个“意图”变为“行动”，需要一个外部的“协调者”程序。这个程序会持续监控模型的输出，一旦检测到类似 `\temperature(...)` 这样的工具调用指令，它就会：
1.  **提取指令**：从模型的输出文本中解析出工具名称（`temperature`）和参数（'高雄', '时间'）。
2.  **执行工具**：在程序环境中（例如 Python）真正地调用 `temperature` 这个函数，并传入相应的参数。
3.  **获取结果**：函数执行后会返回一个结果，比如“摄氏 32 度”。
4.  **反馈给模型**：将这个结果包装成预设的格式，例如 `\攝氏 32 度\`，然后将其添加到对话历史中，作为新的上下文输入给模型。
5.  **继续生成**：模型看到包含了工具调用和其输出结果的完整上下文后，再继续进行文字接龙，最终生成给用户的自然语言回答，如“某年某月某日高雄的气温是摄氏 32 度”。

在这个过程中，工具调用的中间步骤（模型的指令输出、工具的实际执行和结果返回）可以对用户隐藏，用户看到的只是最终的、仿佛模型“知道”答案的流畅回答。

讲者通过一个 Colab 笔记本的现场演示，生动地展示了这一过程。他首先定义了两个简单的 Python 函数作为工具：`multiply(a, b)` 用于乘法，`divide(a, b)` 用于除法。然后，他强调了 `eval()` 函数的关键作用，`eval()` 可以将一个字符串当作 Python 表达式来执行，这是将模型生成的文本指令转化为实际操作的桥梁。
*   **失败的尝试**：在第一次实验中，他仅仅在 System Prompt 中告诉模型如何使用这两个工具，然后让模型计算“111 乘以 222 除以 777”。模型输出了一个看似完整的调用过程，包括 `<tool_code>multiply(111, 222)</tool_code>` 和 `<tool_output>24642</tool_output>` 等。然而，讲者揭示，这一切都只是模型的“文字接龙”和“幻觉”，它并没有真正调用任何工具。它正确地心算出了 111 * 222 = 24642，但在计算 24642 / 777 时，它心算的结果是 32.258，而正确答案是 31.714 左右。这证明了模型只是在“扮演”使用工具的角色。
*   **成功的实现**：在第二次实验中，他实现了一个循环（while loop）来扮演“协调者”的角色。这个循环不断地：
    1.  将当前对话历史（messages）发送给模型。
    2.  检查模型的输出（response）是否包含 `<tool_code>`。
    3.  如果包含，就提取其中的指令（如 `multiply(111, 222)`），并使用 `eval()` 来执行它，得到真实的结果（`24642`）。
    4.  将模型的调用指令和工具的真实输出结果都追加到对话历史中。
    5.  重复这个过程，直到模型的输出不再包含工具调用指令。
    6.  最后，将模型的最终自然语言回答打印出来。
    通过这个流程，模型成功地、分两步依次调用了 `multiply` 和 `divide` 工具，并得到了精确的计算结果 31.714。

演示还扩展到了一个查询天气的假工具 `get_temperature`。模型能够正确调用它并报告温度。更有趣的是，当讲者故意让工具返回一个荒谬的高温（如太阳表面温度）时，模型表现出了判断力，它在回答中质疑道：“哇！高雄气温居然这么高，这有点离谱，你是不是输入有误？” 这表明模型并非盲目相信工具的输出，而是会结合自身知识进行一定程度的合理性判断。最后，当被问及一个不需要工具的问题（如“你好吗？”）时，模型也能自行判断，直接生成回答而不会尝试调用任何工具。

这一系列演示清晰地揭示了语言模型使用工具的本质：一个基于“生成-解析-执行-反馈”循环的协同工作流程，其中上下文工程在定义工具、规范格式和管理对话历史方面起到了决定性的作用。其中，一个最通用且强大的工具是直接操作电脑，即 Computer Use。像 Claude 和 ChatGPT 等模型已经具备了这项能力，它们可以接收屏幕截图和任务指令，然后输出控制鼠标和键盘的操作。讲者展示了 ChatGPT 的 Agent Mode 订购高铁票的视频，模型通过模拟在一个云端电脑上的操作，逐步完成搜索网站、选择站点、日期和票数的任务，尽管过程中有些操作不太流畅（如多次点击才选中日期），但这展示了巨大的潜力。其原理与普通工具使用类似，只是工具集变成了 `move_mouse(x, y)`, `click_left()`, `type_keyboard('text')` 等。讲者通过一个静态截图的例子，让 ChatGPT 指出订阅他 YouTube 频道的下一步操作，模型准确地给出了移动鼠标到搜索框坐标、点击、输入“李宏毅 YouTube”并按 Enter 的步骤序列，验证了这一原理的可行性。

#### **模型自身的思考过程 (Reasoning)**

除了接收来自外部的上下文信息，现代先进的语言模型（如 GPT-O 系列、DeepMind R 系列）还能够在上下文中包含其自身生成的思考过程，这通常被称为“深度思考”或“推理 (Reasoning)”。这种机制允许模型在给出最终答案之前，先进行一番内部的“脑内小剧场”或“草稿演算”。这个过程本身也成为了上下文的一部分，为后续的文字接龙提供了更坚实的逻辑基础。

具体来说，当模型接收到一个复杂的问题，尤其是需要多步推理的问题（如数学应用题）时，它不会立即输出答案。相反，它会先生成一段自我对话或思考链（Chain of Thought）。在这个内部独白中，模型可能会：
1.  **规划解题步骤**：明确为了解决问题需要采取哪些步骤。
2.  **探索多种可能性**：尝试用不同的方法或思路来解决问题。例如，它可能会说：“先来用 A 解法解看看……验算一下，答案不对。试一下 B 解法，好像是对的。那 C 解法也可以试一下，看起来不太好。”
3.  **进行自我验证和修正**：在尝试每种解法后，模型会评估结果的合理性，并对错误进行修正。

这个“脑内小剧场”完整地记录了模型的推理路径，包括其尝试、错误和最终选择的策略。在完成了这个详尽的思考过程之后，模型会基于这个刚刚由自己生成的、充满逻辑推演的上下文，再进行最后一步的文字接龙，从而给出条理清晰、逻辑严密的最终答案。

对于用户而言，这个内部思考过程的可见性是可选择的。在某些应用中，模型会明确展示其“step-by-step”的思考过程，让用户能够理解其结论的由来。而在像 ChatGPT 这样的产品中，这个过程通常是隐藏的，或者只展示一个高度概括的摘要。用户可能看不到模型完整的、曲折的探索过程，但这个过程确实发生了，并且是其高质量回答的关键所在。

从上下文工程的角度看，模型自己产生的思考过程是上下文的一个特殊组成部分。它并非由人类外部注入，而是模型在响应过程中动态生成的。这个“自生成上下文”极大地增强了模型的复杂问题解决能力，因为它将一个复杂的任务分解成了多个更小、更易于管理的思考步骤，并通过自我纠错来提高最终答案的准确性。讲者还提及，如果想深入了解模型是如何“学会”这种深度思考能力的，可以参考他在上学期《机器学习》课程第七讲中关于 DeepMind R 系列模型的讲解。

### **AI Agent 时代下 Context Engineering 的重要性**

在介绍了上下文的构成要素后，讲者将话题引向了 Context Engineering 的核心目标和其在 AI Agent 时代的极端重要性。一个完整的上下文包含了用户指令、系统指令、对话历史、长期记忆、外部检索信息、工具使用记录以及模型的思考过程，其内容非常庞杂且长度会随互动不断增长。因此，Context Engineering 的核心目标可以凝练为一句话：“避免塞爆 context”，即通过智能化的管理，只将当前任务所必需的信息放入上下文，并及时清理掉无关或冗余的内容，保持上下文的简洁和高效。

这一需求在 AI Agent 的背景下显得尤为迫切。讲者首先清晰地界定了从传统 AI 使用方式到 AI Agent 的演进路径。过去，我们与 AI 的互动多为“一问一答”模式。后来发展出“Agentic Workflow”（代理工作流），即为 AI 设定一个标准操作流程 (SOP)，让它按部就班地完成复杂任务，例如批改作业时，可以设定“检查是否为真实作业 -> 评分 -> 验证分数合理性”的固定步骤。而 AI Agent 则更进一步，它不再依赖预设的 SOP，而是能够自主地规划解决问题的步骤，并根据环境的实时反馈灵活调整其计划。例如，要解决一个研究问题，AI Agent 可能会自主进行“上网搜集资料 -> 形成假设 -> 编写代码进行实验 -> 分析实验结果 -> 修正假设或收集更多资料”的循环，直至最终产出技术报告。

AI Agent 的工作模式可以被看作一个持续的循环：
1.  **观察 (Observation)**：Agent 接收来自人类的目标和当前环境的状态信息。
2.  **行动 (Action)**：基于观察，Agent（语言模型）决定并输出一个行为，这可能是调用工具、写代码、与人交流等。
3.  **环境反馈 (Environment Feedback)**：Agent 的行动对环境（包括工具、人类用户等）产生影响，环境状态发生改变，并产生新的观察信息。
这个“观察-行动-反馈”的循环会不断进行，直到任务完成。与传统的 Agent（如 AlphaGo 只能在棋盘上落子）相比，基于语言模型的 AI Agent 拥有近乎无限的行动空间（因为其输出是自然语言），并且能够通过语言与人类进行复杂的交互和接收反馈。

为了让观众直观感受 AI Agent 的能力，讲者现场演示了免费的 Gemini CLI 工具。他向 Gemini CLI 下达指令，如“关闭开启的投影片”，在征得用户同意后，Gemini CLI 真的执行了系统命令，关闭了演示文稿。接着，他要求制作一个“贪食蛇”游戏，Gemini CLI 展示了其自主规划的能力：它先提出一个开发计划，经用户同意后，开始执行创建文件夹、编写 HTML/CSS/JavaScript 三个文件等一系列操作，最终成功生成了一个可以玩的网页游戏。当讲者反馈“太快了，没法好好玩”时，Agent 能理解这个模糊的指令，并自动修改代码中的速度参数（将 `100` 改为 `150`），展现了其理解、执行、接收反馈并迭代改进的完整 Agentic 循环。最后，它甚至能根据指令重新打开刚才关闭的投影片，充分证明了其作为电脑操作代理的强大能力。

然而，运行 AI Agent 面临着巨大的挑战，其中最核心的就是上下文长度问题。由于 Agent 需要执行大量步骤，其对话历史和行动记录会迅速累积，导致上下文变得极长。尽管现代模型的 Context Window Size（上下文窗口大小，即模型能处理的最大输入长度）已经从 GPT-4 的数万 Token 发展到 Claude 的 10 万、Gemini 1.5 的 100-200 万，乃至 Llama 4 宣称的 1000 万 Token，但这并不能从根本上解决问题。

讲者指出，能输入百万 Token 并不代表能“读懂”百万 Token。一系列研究揭示了长上下文的陷阱：
*   **性能下降**：Databricks 的一篇博文指出，在 RAG 任务中，提供过多的检索文档反而会降低模型的准确率。当上下文过长时，模型会“头晕目眩”，表现甚至不如只给少量信息时。
*   **中间信息丢失 (Lost in the middle)**：一篇论文发现，模型对于上下文中开头和结尾部分的信息记忆更深刻，而放在中间的信息则很容易被“遗忘”或忽略。实验表明，如果正确答案位于 20 篇文章的中间部分，模型的表现甚至比不提供任何参考资料、仅凭自身知识回答还要差。
*   **在冗长对话中迷失**：另一项近期研究表明，将一个复杂问题拆分成多轮、挤牙膏式的对话，会导致模型的表现（Capability）和稳定性（Unreliability）双双下降。这说明在冗长的互动中，模型会逐渐“迷失自我”。
*   **上下文腐烂 (Context Rot)**：一篇知名文章通过一个简单的“复述”实验（复制一长串包含微小变化的文本），发现即便是号称支持超长上下文的模型，在输入长度远未达到其上限时（如 1 万 Token），复制的准确率就已经急剧下降。

这些现象共同指向一个结论：无限制地增长上下文是不可行的，甚至是有害的。AI Agent 的长时间、多步骤运行特性，使其极易触发长上下文的种种弊端。因此，必须采用有效的 Context Engineering 策略来主动管理上下文，确保其在模型的有效处理范围内，同时保留所有关键信息，这正是 Context Engineering 成为驱动 AI Agent 成功的核心技术的根本原因。

### **Context Engineering 的三大核心策略**

为了应对长上下文带来的挑战，并有效管理 AI Agent 的信息流，Context Engineering 提出了一系列基本操作。这些操作的核心思想是两句话：“把需要的东西放进 context 里面”和“把不需要的东西把它清出来”。实现这一目标往往也需要借助语言模型自身的能力。讲者介绍了三种常用的 Context Engineering 核心策略：选择 (Selection)、压缩 (Compression) 和多智能体系统 (Multi-Agent)。

#### **选择 (Selection)：精选有用的信息**

“选择”策略的核心思想是，不将所有可用的信息都塞入上下文，而是通过筛选机制，只挑选出与当前任务最相关、最有用的部分。这是一种主动的信息过滤，旨在保持上下文的简洁和高效。

最典型的例子就是前文提到的 RAG (Retrieval-Augmented Generation)。我们不会把整个互联网的内容都作为模型的上下文，而是先通过搜索引擎筛选出相关的几篇文章。在这个基础之上，还可以进行更精细的选择：
1.  **查询重构 (Query Rewriting)**：用户的原始提问可能不是一个好的搜索关键词。可以先让一个语言模型分析用户的任务，生成多个更适合搜索引擎的、更精确的关键词，从而提高检索结果的质量。
2.  **文档重排 (Reranking)**：搜索引擎返回的文档列表，其排序不一定完全符合当前任务的需求。可以再用一个（通常是较小的）语言模型，根据用户的原始问题逐一评估每篇检索到的文档的相关性，然后重新排序，只将最相关的几篇放入最终的上下文中。
3.  **句子级别的选择**：更进一步，一篇名为 "Provence" 的研究甚至将选择的粒度细化到句子层面。它使用一个极小的模型（参数小于 300M）快速遍历所有检索到的文档，判断每一个句子是否与用户问题相关，最终只将这些被选中的句子片段组合成上下文。这种极致的筛选可以最大程度地减少无用信息。

这种选择策略同样适用于**工具的选择**。当一个 Agent 拥有成百上千个可用工具时，如果将所有工具的使用说明都放入 System Prompt，会极大地占用上下文空间，并可能导致模型混淆。正确的做法是实现一个“工具版 RAG”：将每个工具的说明文档化，当用户提出需求时，先进行一次检索，只找出可能用得上的几个工具，并将它们的说明动态加载到上下文中。这解释了为何早期 ChatGPT 的插件 (Plugin) 功能虽然商店里有大量工具，但用户每次最多只能选择三个，因为“less is more”，过多的选择反而会降低模型的性能。

**记忆的选择**也是至关重要的一环。让 Agent 拥有长期记忆，最天真的方法是把过去发生的所有事情都记录下来并全部加载。但这显然不现实，会让模型在每次决策时都背负沉重的历史包袱。因此，需要对记忆进行 RAG 式的选择。讲者引用了“史丹佛小镇 (Stanford Town)”这个早期 AI Agent 模拟实验的例子。小镇中的每个 AI 角色（如 Isabella）都有自己的记忆流，但这些记忆（如“有一张床，啥事也没发生”）都存储在外部数据库中，而非直接放入上下文。当需要决策或回答问题（如“你现在最想干嘛？”）时，系统会根据三个指标对所有记忆进行评分和排序：
*   **新近度 (Recency)**：最近发生的记忆得分更高。
*   **重要性 (Importance)**：每条记忆在存入时都会被 Agent 自我评估其重要性（例如，“有人跟我告白”的重要性是 9，“有张床”的重要性是 0）。
*   **相关性 (Relevance)**：记忆内容与当前问题的关联程度。
只有综合得分最高的几条记忆才会被“选择”出来，放入上下文中，供 Agent 进行决策。

最后，讲者分享了一篇由 Appier 研究人员发表在 NeurIPS 的论文（关于 SpringBench），该研究发现，选择性地提供过去的成功经验对模型学习最有帮助。实验中，模型需要回答一系列问题，并在每次回答后得到“对”或“错”的反馈。结果表明，如果能根据当前问题，用 RAG 的方式从历史记录中挑选出相关的、并且是“答对”的例子放入上下文，模型的表现是最好的。有趣的是，如果只给模型看过去“答错”的例子，反而会对其造成伤害，表现比没有记忆时更差。这好比“不要想白熊”的心理效应，告诉模型什么是错的，反而可能强化了错误路径。这并不意味着负面经验完全无用，而是说明如何有效地利用负面经验来引导模型修正错误，本身就是一个值得深入研究的课题。

#### **压缩 (Compression)：对历史记录进行摘要**

“压缩”策略主要用于处理随时间无限增长的对话历史或行动记录。当 AI Agent 长时间运行时，其互动历史很快就会超出上下文窗口的限制。直接丢弃旧的记录会导致模型“失忆”，而一个更优雅的解决方案是进行压缩或摘要。

其基本流程是，当上下文即将被填满时，调用一个（可能是专门用于摘要的）语言模型，让它阅读过去一段时间的历史记录，并将其中的关键信息提炼成一段简短的摘要。然后，用这段摘要来替换掉冗长的原始记录。这样，Agent 在继续与环境互动时，它所携带的就不是琐碎的对话细节，而是一个高度概括的“长期记忆”。

这种压缩可以是**递归式的 (recursive)**。例如，可以设定一个规则：每互动 100 个回合，就进行一次压缩。第一次压缩后得到摘要1。再互动 100 回合后，将摘要1和新的100回合记录合在一起，进行第二次压缩，得到摘要2。如此循环往复，非常久远的记忆就会在一次又一次的压缩中逐渐淡化，细节会随风而逝，只留下最核心的印象，这非常符合人类记忆的规律。讲者推测，ChatGPT 的长期记忆系统可能就采用了类似的技术。它有一套用户可以明确指示记下的“笔记式”记忆，还有一套会随时间变化的、不可直接编辑的“随风而逝”的记忆，后者可能就是通过这种递归压缩机制实现的。

压缩之所以有效，是因为 Agent 与环境的大量互动本身就包含了许多琐碎的、对于未来决策无用的信息，尤其是在 **Computer Use** 场景下。例如，一个 Agent 为了预订餐厅，可能经历了打开网页、移动鼠标、点击按钮、关闭突然弹出的广告窗口等一系列繁琐的操作。这一长串的屏幕交互记录对于未来的任务规划毫无价值。通过压缩，这一整个过程可以被浓缩为一句话：“A 餐厅订位成功，9 月 19 号下午 6 点，10 个人。” Agent 只需要记住这个结果，而无需保留订位过程中的所有细节。

当然，压缩也有可能丢失关键信息。为了应对这种情况，可以采用混合策略：
1.  **摘要 + 外部存储**：在进行摘要的同时，将未压缩的、完整的原始日志保存到一个外部的长期存储空间（如硬盘上的一个 .txt 文件）。因为硬盘空间近乎无限，而上下文是极其有限的。
2.  **在摘要中留下索引**：在生成的摘要中，可以留下一条“线索”，例如，“如果你想知道更详尽的内容，其实打开这一个 .txt 档，里面有你那年夏天美好的回忆。” 如果 Agent 具备读取文件的能力，当它在未来的某个时刻确实需要这些细节时，就可以根据摘要中的指示去读取原始文件，从而避免了 RAG 检索可能带来的不确定性。

通过这种方式，“压缩”策略在保持上下文简洁和控制其长度的同时，也通过与外部存储的结合，为信息的完整性提供了保障。

#### **多智能体系统 (Multi-Agent Systems)：分散上下文的负担**

“多智能体”策略是一种更宏观的上下文管理方法，它通过将一个复杂的任务分解给多个协同工作的 Agent 来解决单个 Agent 上下文过载的问题。从表面上看，多智能体系统的好处在于可以实现专业分工，比如有的 Agent 擅长写代码（程序员），有的擅长沟通协调（CEO）。但从 Context Engineering 的角度看，其更深层的价值在于，它是一种天然的上下文“分布式”管理框架。

讲者以一个“组织出游”的任务为例来说明。如果只有一个 Agent，它需要负责与人类沟通、规划行程、上网预订餐厅、再上网预订旅馆。订餐厅和订旅馆都需要大量的 Computer Use 操作，会产生极度冗长的交互记录，很快就会塞满这个 Agent 的上下文，导致其后续无法正常工作。

而采用多智能体系统则可以完美解决这个问题。我们可以设计一个三层的结构：
*   **总召 Agent (Leader)**：负责与人类直接沟通，进行高层次的规划和任务分配。
*   **订餐厅 Agent (Agent 1)**：专门负责执行订餐厅的任务。
*   **订旅馆 Agent (Agent 2)**：专门负责执行订旅馆的任务。

工作流程变为：人类告诉总召要组织出游。总召规划好行程后，它不会自己去订餐厅，而是像调用一个工具一样，向 Agent 1 下达一个简单的指令：“去订 A 餐厅”。Agent 1 接收到指令后，开始与餐厅网页进行复杂的 Computer Use 互动，完成后向总召回報一个简单的结果：“订好了”。此时，总召只需要在自己的上下文中记录“餐厅订好了”这一条信息即可。然后它再向 Agent 2 下达指令：“去订 B 旅馆”，Agent 2 执行并回报“订好了”。

在这个结构中，每个 Agent 的上下文都得到了极大的简化：
*   **总召 Agent** 的上下文中只包含高层次的规划和任务状态（餐厅订好、旅馆订好），完全没有订位过程的繁琐细节。
*   **订餐厅 Agent** 的上下文中只包含与订餐厅相关的信息，它完全不需要知道任何关于订旅馆的事情。
*   **订旅馆 Agent** 的上下文也同样只专注于自己的任务。

通过这种方式，原本集中在一个 Agent 上的巨大上下文负担，被有效地分散到了多个 Agent 上。讲者强调，即使所有 Agent 使用的是同一个底层模型，没有所谓的“专业特长”，这种架构依然有意义。因为总召将订餐厅的任务“外包”给 Agent 1，本质上就是将处理这部分任务所需的上下文负担也一并“外包”了出去，从而保持了自身上下文的清爽，使其能更高效地进行宏观调控。

另一个例子是撰写一篇**综述性论文 (overview paper)**。这项工作需要阅读上百篇文献。如果让单个 Agent 来做，将所有论文都放入其上下文是不现实的。而多智能体的方法则可以模仿人类的科研团队：让 N 个 Agent 并行工作，每个 Agent 只负责阅读一篇或几篇论文并撰写摘要。它们的上下文负担都很轻。最后，再由一个“主笔”Agent 负责整合所有这些摘要，撰写最终的综述。

LangChain 的一篇研究也证实了多智能体的优势。实验结果显示，在任务比较简单时，单个 Agent 因为信息集中，效率可能更高。但随着任务复杂度的急剧增加，单个 Agent 的表现会迅速崩溃，而精心设计的多智能体系统则能凭借其分工协作和分散上下文负担的能力，展现出巨大的优势。因此，多智能体系统不仅是一种任务协作模式，更是一种高级而有效的 Context Engineering 策略。
